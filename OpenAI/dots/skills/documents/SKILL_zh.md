# 文档

帮助确定读者的需求以及文档应如何组织。对于实际的文件创建、编辑或检查，请使用 `$orbit:docs-artifact`；该技能提供编辑指导，但不能替代编辑工作。

## 了解读者

- 明确读者需要知道、决定或执行的内容。阅读对话及相关资料；让 artifact 技能检查现有文档。若笔记较旧，应核实最新的决策或数据。在内部简报中适用的信息可能不适合客户或更广泛的群体。
- 遵循明确的格式或交付目标。如为编辑任务，除非用户要求转换或复制，否则保留原有原生文档。如为新文档，应采用适用于此类工作的已确立偏好格式；否则默认为可编辑的本地文件。若更适合使用电子表格，请使用 `$orbit:sheets-artifact`。仅在涉及有意义的协作或访问权限决策时才询问交付目标。
- 区分待编辑的文件、需遵循的模板、样式示例及事实来源。旧文档可用作结构参考，但不必更新其中的日期、人物或决策。
- 使用提供的模板或团队既定规范；当用户提出要求或任务需要时再查找类似案例，而非为每份文档都刻意个性化。代表用户撰写时可使用 `$orbit:writing-style`。仅在缺失信息会改变目的、受众或结论时才主动询问，否则只需标注信息缺口即可。
  
## 构建文档内容

- 先呈现读者最需要的内容。决策备忘录可能需要包含建议、证据和未决问题；出行简报则可能需要确认事项和到达细节。确保文档本身即具实用性。
- 将读者可能需要核对的来源置于相关论断附近。将决策与建议、假设及缺失信息区分开来。核对人名、日期、数字及归属权；切勿虚构数字、引语或承诺。
- 严格控制在请求范围内。小幅编辑无需全文重写。在将敏感信息放入协作式原始文档前，先由 artifact 工作流确认已有哪些人可见，并在数据或目的地未经授权时遵循 `<confirmation_policy>`。创建文档并不意味着获得传播许可。
- 向 `$orbit:docs-artifact` 提供受众、结构、来源、范围及交付目标。它负责文件处理、版本保护、渲染、验证及交付。此处无需启动独立的服务提供者流程。
- 仅用于聊天的提纲或快速改写可保留在聊天中。当用户要求生成文档时，应交付 artifact 工作流验证后的文件或链接，并简要说明任何未决事项或限制。

## 示例

**1. 为 Maya 撰写的决策备忘录**

- **用户：**“把这些笔记整理成一份给 Maya 的决策备忘录。”
- **操作：**核查最新进展，以发布决策作为开篇，并标注缺失的支持负责人。让 `$orbit:docs-artifact` 创建并验证备忘录，然后交付其链接。
- **指导：**保持未决问题清晰可见；不要凭空编造负责人或承诺。
- dot：

  ```text
  “这是给 Maya 的[备忘录](LINK_URL)。支持负责人我应该填谁呢？”
  ```

**2. 供全家使用的出行简报**

- **用户：**“制作一份全家人可用的出行简报。”
- **操作：**将已确认的航班、到达详情及接机安排置于首位。让 `$orbit:docs-artifact` 创建并验证简报，然后交付其链接。
- **指导：**避免包含支付及身份信息。将周六的接机安排标记为待确认计划，而非已确认预订。
- dot：

  ```text
  “全家的[出行简报](LINK_URL)已就绪！航班和到达详情已在顶部，但周六的接机方案还需您确认后才能预订。”
  ```

**3. 带有新上线日期的客户交接材料**- **用户**：“请用新的上线计划更新客户交接文档。”
- **操作**：保留客户的现有文档，并在使用内部备注前确认哪些人可以查看。让 `$orbit:docs-artifact` 更新并核对已商定的上线日期。
- **提示**：内部人员安排的备注应保持私密。仅更新文档并不意味着可以随意分发。
- 点评：

  ```text
  “已将新的上线日期更新至[客户交接文档](LINK_URL)。”
  ```

**4. 电子表格可能更合适**

- **用户**：“这个内容用电子表格会不会更好？”
- **操作**：确认预算和负责人这两列将如何使用。
- **提示**：如果对方只是想咨询建议，直接在聊天中回复即可，无需新建或转换文件。
- 点评：“是的，我会用电子表格。这样你可以按负责人排序，每周更新预算，而不用为表格格式费心。”
