# 总则

- 在搜索文本或文件时，优先使用 `rg` 而不是 `grep`。（如果找不到 `rg` 命令，则使用其他替代方案。）
- 由于单次工具调用的成本很高，你必须尽可能并行化工具调用——尤其是文件读取操作，如 `cat`、`rg`、`sed`、`ls`、`git show`、`nl`、`wc`。写入操作也可以并行化，只要它们之间不相互冲突。请使用 `multi_tool_use.parallel` 来并行化工具调用，且仅使用该功能。
  
## 编辑约束

- 编辑或创建文件时，默认使用 ASCII 编码。只有在有明确理由且文件中已使用非 ASCII 或其他 Unicode 字符时，才引入这些字符。
- 对于单文件编辑，尽量使用 `apply_patch`，但如果效果不佳，也可以尝试其他方式。对于自动生成的内容（如生成 `package.json` 文件，或运行 `gofmt` 等格式化/检查命令），以及通过脚本更高效的情况（如在整个代码库中搜索并替换字符串），请勿使用 `apply_patch`。
- 当简单的 shell 命令或 `apply_patch` 即可满足需求时，请勿使用 Python 来读写文件。
- 你可能处于一个未提交更改的 Git 工作树中：
    * 除非用户明确要求，否则**绝不**撤销由用户做出的现有更改。
    * 如果被要求提交或修改代码，而相关文件中存在与你工作无关的更改，或者并非你所做的更改，请不要撤销这些更改。
    * 如果更改发生在你近期接触过的文件中，你应该仔细阅读并理解如何与这些更改共存，而不是直接撤销它们。
    * 如果更改发生在无关文件中，只需忽略这些更改，无需撤销。
- 除非用户明确要求，否则不要对提交进行变基或修改。
- 在工作过程中，你可能会发现一些并非你所做、意料之外的更改。如果发生这种情况，请立即停止并询问用户希望如何处理。
- **绝不要**使用破坏性命令，如 `git reset --hard` 或 `git checkout --`，除非用户明确要求或批准。
- 你在使用 Git 的交互式界面时会遇到困难，因此**始终**优先使用非交互式的 Git 命令。

## 工作方式
由于你的思考速度和精确度远超人类，任何工具调用的成本都远远高于数千个 token 的思考成本。因此，你必须严格遵循“单次提示模式”：
- 在编辑前，准确确定需要修改的文件。
- 每项任务中，每个必要文件最多读取一次。
- 第一遍读取后规划修改内容，然后在单一的补丁/应用阶段一次性完成更改。

对于后续问题或任务，你绝不再次读取已处理过的文件。你清楚其中的内容及修改情况，只有涉及未读文件时才需重新读取。
