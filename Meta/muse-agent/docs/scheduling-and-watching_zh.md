# 定时任务与监控

当用户请求设置监控或定时检查时，他们希望系统在后台持续监测，并将结果发送到聊天中。本文档将详细说明这种监控的具体实现方式。

## 工作原理：轮询而非实时监听

定时检查按照您设定的固定间隔运行，而不是持续进行。每次检查时，系统会扫描并报告当前状态；如果在此期间发生了变化，则会在下一次检查时捕获到。如果在两次检查之间发生了某项变更并又被撤销，那么这一变化将完全被遗漏。在两次检查之间，系统不会持续监听，也不会在等待用户下一条消息时继续轮询。基于事件的自动化同样采用轮询机制，而非实时流式处理。

时间安排较为宽松：检查会在预定时间前后几分钟内触发，有时甚至会提前。如果您设置了一个仅执行一次的任务来监控某个特定事件的发生，它并不会在该事件出现的瞬间立即触发。

更准确的说法是：“我每30分钟/每小时检查一次”，切勿承诺“事件发生时立即检测”。

## 监控会发出提醒，但无法阻止事件发生

监控的作用是发现某些事件的发生，但它无法拒绝、拦截或阻止任何传入的事件，例如日历预约、支付扣款或消息。只有源服务本身提供的工具才能对这些事件进行拦截或拒绝。监控所能提供的功能包括：事后发送一条包含操作链接的消息（如拒绝事件、对扣款提出异议或回复消息）、在日历上设置时段为“忙碌”以防止后续预约，或者直接使用源服务自身的设置。

## 后台任务可靠运行

您的设备无需一直开机。即使用户的App已关闭或手机处于关机状态，任务仍会正常执行。执行结果会以消息形式发送至聊天，若App未打开，则会通过推送通知发送到手机。此机制稳定有效。

## 消息仅发送给用户本人

监控的结果会以聊天消息和推送通知的形式呈现。监控的提醒功能无法向好友发送短信、给家人发消息，也无法通知其他任何人。当用户说“当X发生时请给我发短信”时，这实际上是指一个定时检查任务，其结果会以消息和推送形式发送给自己，而不是真正的短信，也不是发送给他人。如果任务本身需要通过已连接的账号向某人发送邮件或消息，则属于另一项独立的连接器发送行为。除非用户已为该定时任务设置了“始终允许”的权限，否则此类发送需等待用户确认。

## 查看运行记录，而非计划表

如果用户询问“我的7点检查是否已执行”，请从`cron.runs`中查询。该记录会显示哪些任务已执行、何时执行以及执行结果。仅凭计划表并不能证明任务确实已运行，运行记录才是真实依据。

## 任务的可操作性

您可以创建、更新、暂停、删除任务，或按需手动触发任务。为任务设置一个最多120字符的显示名称（即用户在App任务列表中看到的名称）。任务ID保持不变，方便后续编辑。您无法设置开始日期、结束日期或仅在特定条件下触发的条件。任务会周期性重复执行，直到您将其暂停或删除。如果任务因某些持久性问题而无法继续运行（如连接器需要重新连接、某些操作只能由用户完成、网站的机器人验证、配对设备离线或浏览器处于繁忙状态），任务会自动暂停，并在下次预定时间尝试重新运行。解决这些问题后，任务不会自动重新触发。如需立即运行，请使用`cron.run`。`cron.status`会显示当前的阻塞原因，而`next_run_at_local`则显示任务下次尝试的时间。如果任务需要满足某些条件，请将相关逻辑写入任务的具体执行内容，而非调整其触发时机。
