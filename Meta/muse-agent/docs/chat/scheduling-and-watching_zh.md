# 调度、监控与服务

在创建或变更后台任务时，请参考本指南，可在主聊天或侧边聊天中调用。

## 选择合适的机制

- Cron 用于按计划执行代理任务，包括提醒、定期检查以及需要工具或人工判断的工作。对于单次未来执行的任务使用 `runonce`，对于有限次数的重复检查则使用间隔调度。
- 钩子用于运行轻量级轮询脚本，并在满足特定条件时唤醒代理。当检测器无需每次通过代理即可检查本地或公共数据时，应使用钩子。
- systemd 服务用于监督那些需要持续运行的程序，例如流式监听器、采集器或本地服务器。如果一系列独立的检查无法完成任务，则应使用运行时的 guest systemd。

浏览器任务和子代理已具备完成后的自动移交功能，因此请优先使用它们，而无需再添加额外的监控机制。

## 已保存的任务与钩子

记录用户的范围、目标、执行频率、完成条件、负责人及交付目的地。对某项操作的监控请求应涵盖完成该操作所需的观测内容，而非重复执行该操作。如适用，可复用已有目标作为负责人。其他提醒与跟进则需明确指定跟踪负责人。

将目标所属的工作文件保存在 `~/workspace/goals/<goal-slug>/hidden_files/` 目录下，包括检查点、运行日志、水印及源码快照等。钩子脚本及其状态文件应存放在下方指定的钩子路径中。

首先检查现有任务。修改 cron 任务时，请通过 `cron.view` 和 `cron.update` 接口，以相同 ID 提交完整的修订内容，并保留无关设置。确认前务必先读取并核对。预估的调度文件为只读副本，直接编辑不会更改任务配置。若需修复权限问题，不应简单地删除后重新创建任务。

每次检查都应确保能够正常结束，并设置请求与执行的超时时间，避免任务重叠。任务体应描述工作内容及报告意图，而非直接调用终端移交工具。当任务结果已明确、被取消或已过截止时间时，应及时停止有限期的监控，并将尚未完成的交付事项与后续的源数据轮询分开处理。

钩子脚本应放置于 `~/hooks/scripts/` 目录下，其状态文件则存放在 `~/hooks/state/` 目录。遵循工具的脚本协议，包括一次明确的“静默”或“唤醒”决策。使用提供的状态辅助函数，以避免空跑占用检测资源。新建钩子默认处于禁用状态，启用前请先检查 `hooks.dry_run` 的结果。对于终结性条件，可使用 `disable_after_run` 参数。钩子不携带连接凭据，切勿在检测器中添加任何敏感信息。

两种机制均采用轮询方式，检查之间可能存在遗漏，且调度也可能延迟。它们无法提供持续观测，也无法阻塞源事件的发生。

## 当前运行时的服务

当前运行时环境虽包含 systemd，但启动的是精简的 `default.target`，而非通常的 `multi-user.target` 或登录会话。建议优先使用现有的 guest 系统管理器。启动项应指向 guest 实际到达的目标。仅当服务的管理器、配置查找、运行时目录、总线以及替换后的启动机制均已就绪时，才应使用用户服务。工具的环境变量并不能建立管理器的运行环境，切勿假设遗留进程仍在运行，亦不得依赖宿主机的操作设施。

将服务的单元文件、程序、依赖关系及状态文件统一存放于持久化的用户主目录下。使用绝对路径配置 `ExecStart` 和 `WorkingDirectory`，并确保服务以前台进程运行。合理设置 `Restart` 策略、`RestartSec` 及启动次数限制。通过 `TimeoutStopSec` 允许优雅终止，并使用 `KillMode=control-group` 控制子进程。对资源与日志进行约束，重启行为应与程序特性相匹配。成功完成或等待确认可能是程序的预期退出方式。

验证服务实际以何种用户和组身份运行，并从该服务上下文中检查访问权限。切勿假设其继承了工具的凭据、连接访问或审批权限。应使用受支持的访问路径，切勿将敏感信息写入单元文件、参数、环境文件或日志中。

## 替换后的恢复措施

运行时会管理已保存作业、子代理、定时任务、构件以及可恢复代理工作的恢复过程。自定义程序需要一条在替换后能够恢复其前置条件的启动路径。仅靠持久化单元文件和 `Restart` 设置并不能确保这条路径的建立。

在诊断故障之前，请检查已保存的状态、日志、近期输出以及部署事件。可能存在一个处于静默监听状态的组件正在等待确认；而一次失败的引导过程也可能部分成功。只有当证据明确将故障与部署关联起来时，才将其归因于部署问题。中断和恢复失败应分别排查。

请使用受支持的启动路径。如果需要执行已保存的恢复作业，应将其范围限定在所请求的组件内，并设置合理的间隔，以提供再次尝试的机会，而非作为恢复的截止时间。

恢复工作时，请按以下步骤操作：

1. 在开始任何操作之前，先读取持久化的期望状态。保留已完成的工作、待确认的任务、已取消的任务、被阻塞的状态以及重试次数限制。对于正在等待确认的监听器，不得将其当作崩溃而重启。
2. 恢复并验证所需的前置条件。在管理器启动或挂载发生变化后，应通过新的工具调用检查就绪状态。工具进程拥有独立的挂载视图，可能无法看到后续创建的挂载。延长等待时间或在同一旧调用中派生子进程，未必能解决这一视图问题。
3. 独立地对每个组件进行协调。在启动新副本之前，先检查当前运行状态。某个组件的超时不应妨碍其他不相关组件的恢复。记录部分成功的状态，以免下次尝试重复已完成的工作。
4. 从检查点继续执行，并验证是否取得了有效进展。检查点应以原子方式定期写入。突然终止可能会跳过关闭处理程序。对于外部操作，在重试不确定的结果之前，应先将记录的意图与接收方的实际结果进行核对。

在取消时，应在停止服务及其恢复作业之前保存停止状态。恢复过程不得撤销用户的决策。

## 验证与交付

应分别检查已保存的配置、实际执行情况、有效进展以及最终交付结果。对于定时任务，可使用 `cron.status` 和 `cron.runs`，然后验证所有应产出的结果是否已送达对话中。对于服务，应检查管理器和单元文件、依赖关系、日志以及近期输出。仅凭单元处于活动状态或存在 PID 并不能证明其健康状况。

测试您声称能够处理的故障模式。在管理器和总线保持完好时重启工作进程，可以验证进程监管机制的有效性。而在替换后进行恢复，则还需重新恢复这些前置条件并重新启动工作。切勿仅凭前者推断后者。应基于实际观测到的部署证据或经授权的恢复测试来判断，并明确指出尚未验证的部分。

当恢复部分成功时，应分别报告各组件的状态。一次引导失败并不意味着所有服务均已宕机；一个处于静默监听状态的组件也不能证明发生了崩溃。对于限流导致的停止、访问被拒绝以及外部交互结果不确定的情况，应予以保留，而不应将其误判为初始化失败而重试。

除非用户选择了其他允许的目标，否则应将结果交付至原始聊天。与服务提供商相连的侧聊天应保持其“精确聊天”的边界。未发生变化的观察结果除非用户要求，否则应保持沉默；而对于影响用户最终结果的失败或缺失，则应予以报告。聊天结果或推送通知并非任意的短信，也不应发送给他人。
