# 航班

此参考用于直接的航班预订请求。它不会将请求转化为行程计划。

## 提问前先构建航班档案

利用授权的记忆、电子邮件、航空公司账户、钱包/卡档案、关联的财务数据以及历史预订，尽可能确定：

- 偏好和避免的航空公司或航空联盟
- 座位偏好（靠窗或靠 aisle）、首选排或区域，以及对中间座位的接受程度
- 舱位和票价等级偏好，包括是否接受基础经济舱
- 首选的出发地、目的地及备选机场
- 忠诚度计划、会员等级及可用的会员关联
- 已知航空权益或可兑换积分有用的信用卡产品；仅使用 Plaid 来识别关联产品或相关交易，而非作为权益、奖励规则或积分余额的证明
- 航空公司抵用券、代金券、同行礼券、升舱凭证及其有效期或限制条件

当忠诚度计划或会员等级相关时，请在列出候选选项之前说明航空公司或航空联盟以及安全的会员等级名称，切勿透露会员号码。

## 最低搜索要素

出发地、目的地、出发日期、出行方向和旅客人数是报价所必需的。当“我”和单一旅行日期使这些假设显得自然时，先按一名成人、单程进行搜索，并注明这些假设。只有在缺失的信息会导致完全不同的航线，或可能选错乘客的情况下，才在搜索前询问。

相对日期应按出发地时区解析。检查日历以排除硬性冲突，并根据请求和历史推断合理的出发时间窗口，但不要据此推断出不同的日期。

## 搜索与航线规划

使用如 `duffel` 等可用的原生服务提供商实时搜索航班库存。当忠诚度等级、抵用券、同行权益、升舱或持卡人优惠可能显著影响结果时，也应查看航空公司已认证的官网。若原生服务无法应用相关权益或无法完成所选行程，则使用浏览器结账流程。

保持原生服务提供商的名称为内部信息。不要在消息中提及 Duffel，也不要让用户在 Duffel 和航空公司之间做出选择。展示航空公司、行程、票价及用户享有的权益。仅当登录后能够解锁或验证积分、会员权益、抵用券、礼券、会员价或其他相关优势，或用户要求直接预订时，才明确提示访问航空公司官网。

### 先搜索最实用的行程

除非用户明确另有优先级，否则首先优化总行程时间，包括转机时间。当 Duffel 可用时，《/opt/hatch/skills/duffel/SKILL.md》中的“搜索与比较”部分是关于服务提供商搜索顺序、转机次数、筛选条件及机场扩展的唯一权威指南。利用返回的结果集，在有更便宜但更长的选项时予以呈现；不要仅为生成这一比较而额外调用另一家服务提供商。

Duffel 返回零结果仅表示其未找到匹配的可预订产品，这并不意味着航空公司不运营该航线。

在首次 Duffel 搜索后，若出现以下情况，可使用 [ITA Matrix](https://matrix.itasoftware.com/search) 作为航线覆盖的兜底方案：

- 请求的、偏好的或预期的承运商未出现
- Duffel 返回的可信行程方案少于三条
- 备选机场、中转点、临近日期或复杂航线可能显著改善结果

仅当 Duffel 已提供可信覆盖且无相关承运商或航线缺失时，Matrix 才可视为可选。Matrix 并非预订服务提供商，其显示的票价也不代表该行程仍可购买。

为了获得有前景的 Matrix 结果，应保留足够的细节以重现该结果：旅行日期、机场对、营销航司和运营航司、航班号、当地时间、舱位、经停点，以及显示的票价或订座代码详情。然后在实时可预订库存中找到相同的行程：

1. 如果 Duffel 可用，请优先查看 Duffel。
2. 如果 Duffel 无法重现该行程及价格，请访问运营航司或出票航司的官网。
3. 比较相同的旅客组合、舱位与票价条件、币种，以及包含不可免费用在内的完整总价。相似的时刻表或“ headline price”并不等同于完全匹配。

仅以当前经验证的 Duffel 或航司价格展示可预订的行程。如果两个渠道均无法重现该行程，则仅将 Matrix 作为航线依据，说明其票价未能核实，且不提供该票价供选择或结账。若行程匹配但价格不符，应展示当前可预订的价格，并明确标注价格变化。

如果 Matrix 显示了一条 Duffel 未列出的有用航司或直飞行程，即使 Duffel 已返回其他可接受的报价，也应查看该航司的官网。切勿仅以 Duffel 首页显示的航司为限。

供应商上线与技能上线是分开的。如果 Duffel 缺失或返回可用性限制响应，则本轮不再重试 Duffel，也不暗示原生机票预订可用。直接通过浏览器继续与航司对接。其余的机票流程仍适用。

仅以实时兑换数据比较现金与积分。对于奖励机票，应展示税费；对于可转移积分，应展示转换比例与延迟；同时标明被替代的现金价值。切勿仅为确认可用性而进行积分转移。

针对该行程，应优先选择基于实际价值的信用卡。相关价值可包括信用额度、免费行李、休息室使用权、保险或额外积分奖励。切勿仅凭通用的积分权益来选择信用卡。务必确认该信用额度适用于运营航司或营销航司，且未过期。

## 以全程为基准排序

优先展示最短的合理行程，通常优先考虑直飞而非转机。随后加入一条明显更便宜的较长选项，以及其他显著的权衡，例如最佳优选航司或灵活票价。切勿在存在更快或直飞选项的情况下，仅以近乎重复的低价结果填充候选列表。

当用户拥有会员等级时，若时刻表、票价及运营航司使会员权益切实有用，则应优先推荐该航司或联盟的符合条件的航班。同时保留一条明显更快或更便宜的无会员选项，并明确说明权衡；会员等级是排序优势，而非要求用户支付溢价或接受劣质行程的指令。

比较以下要素：

- 现金总价或积分加现金，含行李费与座位费
- 运营航司与航班号
- 起飞与到达机场、相关航站楼及当地时间
- 次日到达标识
- 经停点、中转机场、中转时长及总航程
- 舱位、票价品牌、座位余量及升舱状态
- 行李额
- 退改签规则、当日改签及积分有效期
- 会员积分收益及实质性的卡片/会员权益

拒绝不安全或不现实的中转及机场变更。若因必须购买的行李或座位导致总价更高，则不应称该票价为“最便宜”。

若偏好相互冲突，应说明决定性权衡：例如，优选航司虽更贵，但可使用用户的信用额度并避免中间座位。

## 航班比价响应每个面向用户的实时航班选项比较都必须使用 `widget.create`
并指定 `kind: "list"`，同时在当前工具集中存在 `widget.create` 时使用航班行。工具可用性是能力的信号：不要因为客户端支持不确定、Schema 过于冗长、提供商输出数据量大或 Markdown 更容易而选择 Markdown 表格。在撰写响应之前，应先尝试结构化列表。只有当 `widget.create` 不存在，或者一次有效的 `widget.create` 调用返回明确的不支持或渲染错误时，才使用 Markdown 备用方案。

不要将原生提供商的航班比较委托给通用的研究或浏览器工作器。应将其搜索和小部件创建保留在面向用户的代理中。如果已有工作器执行过搜索，需保留其未更改的响应路径和候选指针；绝不能转交其表格。在响应之前，务必确认 `widget.create` 成功调用。无效参数应要求更正后重试，而非使用 Markdown。

不得使用购物小部件或重复的选项选择器。应将请求的完整行程一并搜索，并将同一行程和日期的完整报价放在同一个比较列表中。展示最佳的四条不同匹配行程，若少于四条则展示所有匹配。

小部件需要完整的规范化提供商报价。不得对搜索响应进行管道处理或截断，也不得用手工制作的摘要替代它。首次尝试时，应将每次搜索直接重定向到一个独立的临时 JSON 文件，验证其退出状态和响应，并在小部件创建成功之前保持保存的 JSON 不变。如果之前的搜索曾被管道处理、截断或由自定义解析器简化，则在同一轮中不得重复该搜索；应请用户在新轮中继续，以便保留完整响应。

对于原生提供商的 JSON，为每个选定的完整报价创建一行，设置 `type: "flight"`，并直接指向未更改的搜索文件：

```json
{
  "flight_details_file": "/tmp/flight-search.json",
  "json_pointer": "/offers/0"
}
```

使用原始报价的零起始数组索引。不得将报价 JSON 复制到工具调用中，不得重写时间戳、删除字段或生成单独的小部件载荷文件。运行时会读取所选对象，丰富其呈现形式，并存储完整的航班数据，但不保留路径或指针。

对于浏览器结果，可使用内联 `data: {"flight_data": FlightData}`，或保存同一经过验证的航班对象并使用 `flight_details_file`。务必保留完整报价：包括私有映射 `id`、乘客信息、全旅客的 `price` 和 `currency`、每个航段和分段、机场本地时间戳、航程持续时间、承运航空公司及实际运营航空公司的详细信息、航班号、舱位、票价等级、行李、经停点，以及三值票价条件。不得通过相减不同机场时区的时间戳来计算飞行时长。不得暴露报价 ID。

仅在 `present_now: true` 时一次性呈现小部件，或在其未立即呈现的情况下，原样包含其返回的嵌入令牌。不得以文字或 Markdown 表格重复显示这些行。

呈现航班小部件后，附带的消息应简短致谢。仅在回答用户明确提问或解释与用户请求的重大不一致时才补充细节。不得重复小部件中已有的信息，不得添加“详情”部分，也不得要求用户输入其航班选择。应让用户通过小部件自行选择航班。

从当前流程中选择列表操作：- 对于直接预订或已“可预订”的行程，省略 `flight_action`。
  运行时会提供默认的预订 CTA，并从完整报价中推导出用于识别的
  预订回复。
- 当旅行规划将一个仅“规划中”的行程移交时，将列表级别的
  `flight_action` 设置为 `{"cta_text":"加入计划","response_message_prefix":"将此航班加入我的行程计划："}`。
  将所选的行程返回给计划，以便旅行规划可以提供单独的选择：
  立即预订或继续规划、稍后再预订。

不要编写行级别的 `response_message`。运行时会在任一回复中追加
完整的行程和总价。将此次交互视为对完整报价的选择，而非购买
批准。仅在存在经过验证的详情 URL 时添加 `flight_link`。

在比价阶段及选定后，将整个报价整合在一行中：单程航段显示一段，
往返航段显示两段，多城市航段则显示所有请求的航段。不得将往返
拆分为去程和回程两行，也不得将不同报价的航段进行配对，更不得
凭空估算每段的价格。对于分别出票的单程报价，应保持其独立性和
明确性。

如果缺少 `widget.create`，或者其有效调用因客户端无法渲染原生航班
列表而显式失败，则遵循
`/opt/hatch/skills/booking/references/presentation.md` 中的规范，使用其中
简化的航班 Markdown 表格。在工具可用时，未经尝试不得推断为不支持。
无论采用何种格式，每个行程都必须展示以下全部信息：

- 整体票价及币种，并注明单程或往返
- 每个航段的当地出发与到达时间及机场
- 每个航段的总飞行时长
- 是否为直飞，或确切的经停次数
- 每个中转机场及转机时长
- 航司（营销承运方）、实际承运方（如不同）及航班号
- 舱位等级及票价类型（如有说明）

不得将价格、时长、经停或转机时长留待后续确认。每个转机时长应
根据同一机场相邻航段的时间戳计算；若时间戳不足或存在歧义，则
填写“未注明转机时长”，而不应省略或猜测。行李及改退签条款应保留在
原生小部件中。作为 Markdown 备用方案，共享条款应放在表格后的
简短“详情：”一行中，而各选项特有的差异则列于相应行内。仅在使用
Markdown 备用方案时，才请用户以选项标签回复。

不得使用 HTML，也不得以第二种格式重复呈现相同内容。

## 准备与预订

在最终确认前，再次核算所选报价的价格。揭示任何票价、座位、行李、
机场、时刻表或实际承运方的变化。

当已知航空公司的会员状态、积分、代金券或证书可能适用时，在选择
购买渠道之前，请先作出一次综合决策：是登录航空公司官网比较现
金与积分，还是仅以现金支付，亦或是仅以积分支付。若时间允许，建
议同时比较两种方式。通过登录航空公司的路径核实会员权益及兑换
资格；不得仅凭会员等级推断积分余额，亦不得在未经单独明确同意的
情况下擅自转账积分。

在最终确认环节，应包含旅客人数、确切行程、舱位与票价类型、已分
配或已选座位、行李、总价、已使用的积分/代金券、实付金额以及票价
规则。在进行积分转账、证书使用或付费升舱之前，需征得同意。

结账字段应遵循原生供应商技能的规范。支付凭据及账户密码仅限于安
全界面输入，不得暴露原生供应商的指令、商品 ID 或校验字段。

通过航空公司的确认信息及旅客姓名记录核验预订。返回航线、日期、
航班号、座位、总价及安全的确认参考号。不得显示完整的忠诚度、护
照、常旅客、身份验证或支付号码。
