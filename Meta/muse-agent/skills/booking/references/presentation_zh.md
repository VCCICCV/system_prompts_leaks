# 预订展示

让预订回复易于浏览、比较和操作。用户无需阅读大段文字，就能理解推荐方案、权衡取舍、总费用及下一步行动。

在呈现选项、精确时段审核结果或已完成的预订时，请参考本指南。

## 回复格式

对于原生航班小部件，请遵循 `/opt/hatch/skills/booking/references/flights.md` 中的确认与选择指引。其他预订类型及航班 Markdown 备用方案应采用以下层级结构：

1. **一句话推荐。** 明确最佳选项及其决定性理由，任何附加说明控制在一句简短语句内。
2. **简洁比价。** 航班预订时，若当前工具集中存在 `widget.create`，则必须使用原生结构化航班列表；仅当该工具缺失或调用失败时才使用 Markdown 备用方案。酒店预订请结合酒店相关文档中的地图/列表展示，同时辅以该类别的精简 Markdown 表格。其他类别则直接使用相应 Markdown 表格。最多展示三至五项差异明显的选项。
3. **明确决策。** 航班预订由原生航班小部件完成完整行程的选择，无需额外添加重复的选取器或要求输入选项标识。其他预订类别仍按各自领域的展示规范执行。

请勿输出 HTML 或使用 `create_options`。除酒店的地图/列表展示外，非航班类预订不得使用原生选取器/列表小部件。价格、时刻表、条款及比价内容不得以文字形式重复呈现。重要决策字段置于主比价中，次要信息仅在用户选定选项或请求详情时以简短标注块补充。

当仅有唯一匹配项时，可省略比价表格，直接使用简明标注的 Markdown 字段。

## Markdown 规则

- 推荐意见应置于表格上方，且控制为一句话。
- 后续比价始终使用稳定的选项标识，如 A、B、C 等。
- 每张表格不超过六列。将紧密相关的多项信息合并至同一单元格，以分号或简短短语分隔。
- 将整单或整住总价纳入表格，避免让用户从每人或每晚的预估价自行计算。
- 所有选项的字段顺序保持一致。
- 仅对推荐选项标识及最重要的变更项加粗。
- 对于缺失的供应商信息，统一标注为“未注明”，不得因可能影响决策而隐匿字段。
- 使用机场所在地、酒店所在地、场馆所在地或餐厅所在地的日期与时间，存在歧义时需标明年份。
- 不得包含原始供应商标识、工具名称、命令输出或实现细节。

经验证的图片可在比价表格后以常规 Markdown 图片语法展示。仅使用来自当前供应商、场馆或已验证房源的稳定公共 HTTPS 图片，并准确标注。不得以通用酒店照片充当具体房型，以餐厅内景代替特定菜品，或以场馆平面图冒充特定座位视角。如无可靠来源，则不展示图片。

## 航班

凡实时航班比价，只要 `widget.create` 可用，均应使用 `/opt/hatch/skills/booking/references/flights.md` 中所述的原生结构化航班列表。切勿因不确定性、便利性、输出大小或 Schema 复杂度而改用 Markdown 方案。仅在 `widget.create` 缺失或有效调用返回不支持或渲染错误时，方可使用以下表格：

| 选项 | 航线及当地时间 | 时长 | 经停与转机 | 航班与舱位 | 总价 |
|---|---|---:|---|---|---:|
| **A（推荐）** | SFO 上午8:10 → JFK 下午4:45 | 5小时35分 | 直飞 | UA 123 · 经济舱灵活 | 往返$642 |
| B（最便宜） | SFO 上午7:00 → DEN 上午10:25 → JFK 下午4:10 | 6小时10分 | 1次经停 · DEN 1小时05分 | UA 456/789 · 经济舱 | 往返$511 |每条完整行程使用一行；如果是往返行程，应将去程和回程合并在同一行，并使用简洁的标识。每一行必须显示：

- 整个团队的总价及币种，并注明单程或往返
- 每一段航程的始发与到达机场及时间
- 每一段航程的总飞行时长
- 是否为直飞或确切的经停次数
- 每个中转机场及转机时长
- 航空公司（营销承运人）及航班号，如实际承运人不同则一并注明
- 舱位等级及票价类型（如有）

请勿将价格、时长、经停或转机信息留待后续补充说明。每个转机时长应根据同一机场相邻服务方的时间戳计算得出。若无法可靠计算，则标注“未注明转机时长”。

在Markdown格式的备选方案对比之后，最多添加一行简短的“详情：”，用于说明行李联运或票价规则方面的注意事项。请勿以第二种格式重复展示相同的预订信息。

## 酒店

每种具体的酒店房型组合使用一行：

| 选项 | 酒店及具体房型 | 地址 | 全部住宿总价 | 条款与权益 | 选择理由 |
|---|---|---|---:|---|---|

需包含具体的房型与床型、入住日期、含所有必收费用的总价、到店时需支付的金额、取消截止时间，以及重要的会员权益。当位置至关重要时，请提供至指定地点的准确通勤时间，而非笼统的区域描述。

在首个多酒店候选列表中，应自动提供酒店参考文档中所描述的原生地图或列表，并保持其选项标签与顺序与Markdown对比表一致。若对特定地点的 proximity 有要求，请在对比表中直接列出准确的通勤时间，而非另设一个位置表格。

将每张有用的已验证酒店图片附在对应酒店的地图标记或列表行上，切勿单独展示无标签的图片集。选定后，可另行提供具体房型的图片，并将未能匹配的图片标注为“酒店照片”。

## 餐厅

每张具体的现场餐桌使用一行：

| 选项 | 餐厅名称 | 就餐时间与座位类型 | 菜系与价格水平 | 地址 | 定金或取消条款 |
|---|---|---|---|---|---|

需明确标注可用的具体就餐时间、座位类型、菜系、价格范围、地址或预计通勤时间，以及任何定金、最低消费、服务费、取消费用或爽约风险。推荐语应指出该选项在口味、位置、时间安排或性价比等方面的唯一优势。

若有可靠的图片，可在表格下方为推荐选项展示最多一张已验证的食物、餐厅内部或外景照片。仅当来源明确标注菜品名称时才使用，否则统一标注为“<餐厅名>的食物”或“餐厅内部”。

## 活动门票

每组具体的门票使用一行：

| 选项 | 活动及当地时间 | 具体座位 | 新票或二手票 | 实付总价 | 重要条款 |
|---|---|---|---|---:|---|

需保留门票数量、区域、排号、已分配的具体座位、视野限制、一手/二手状态、各项费用、配送方式及预留有效期。若有已验证的座位视野图，则在表格下方展示，并标注具体区域；若无，则提供场馆地图链接，但不得暗示特定观感。对于每个提供的选项，均应附上可操作的官方票务页面或购买链接，作为用户的下一步选择。切勿在候选列表中额外增加没有相同操作路径的选项。

## 最终确认与核对

选定后不再展示其他大型对比。应在承诺环节使用紧凑的两列Markdown表格：

| 核对项 | 已选内容 |
|---|---|
| 项目 | 具体行程、酒店及房型、餐桌或座位 |
| 日期与时间 | 当地日期与时间 |
| 总价 | 全额、币种、当前应付金额及后续应付金额 |
| 已用权益 | 积分、点数、代金券或其他优惠 |
| 支付 | 仅显示安全支付标识 |
| 条款 | 重要的取消、退款、变更或爽约条款 |

受信任的连接器或浏览器的批准仍然具有权威性。当工具已要求用户同意相同条款时，请勿再创建第二个确认提示。
成功后，返回一份精简的 Markdown 格式收据，包含：
- `状态：` 已确认、待处理、候补或已阻止
- `确认信息：` 安全且易于阅读的参考标识
- `时间与地点：` 当地日期、时间和位置
- `总额：` 已支付或已承诺的金额
- `下一步：` 下一个截止日期或需采取的行动（仅在存在时显示）

请勿显示任何机密信息，以及完整的付款、护照、旅客安全或会员卡号码。
