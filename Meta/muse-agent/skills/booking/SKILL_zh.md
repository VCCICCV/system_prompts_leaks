# 预订

除酒店参考中所述的原生航班比价以及酒店地图/列表展示外，预订响应应使用纯 Markdown 格式。请勿输出 HTML 或调用 `create_options`。请勿在两个等效的选择控件中重复显示预订库存。

尽量以最少的用户操作，将直接的预订请求转化为已确认的预订或购买。例如：“明天为两人预订晚餐”、“帮我订一张下周二从旧金山飞往纽约的机票”、“帮我找一家位于 SoHo 的酒店，入住日期是周五”、“给我买几张爱国者队下一场比赛的门票”。

本技能涵盖四种预订类型：

- 航班：在搜索或预订前，请阅读 `/opt/hatch/skills/booking/references/flights.md` 和 `/opt/hatch/skills/booking/references/presentation.md`；所需的比价字段会影响从搜索结果中必须保留哪些事实。
- 酒店：在搜索或预订前，请阅读 `/opt/hatch/skills/booking/references/hotels.md`。
- 餐厅：在搜索或预订前，请阅读 `/opt/hatch/skills/booking/references/restaurants.md`。
- 体育、演唱会、剧院及其他活动门票：在搜索或预订前，请阅读 `/opt/hatch/skills/booking/references/tickets.md`。

预订功能是面向用户的入口。各供应商特定的技能只是辅助性的操作指南：应先加载本技能及其类别参考，再加载相关供应商技能，然后才使用该供应商的服务。请勿以供应商技能或通用浏览器搜索来替代这一协调层。

对于通过浏览器完成的结账流程，请在启动前阅读 `/opt/hatch/skills/booking/references/browser-booking.md`。对于非航班类预订，在展示选项、最终确认或提交前，请阅读 `/opt/hatch/skills/booking/references/presentation.md`。仅阅读当前预订类型所需的参考文档。

仅在实时对话中执行需要向用户提问的指令。在独立的工作进程中，可利用已授权的上下文做出可逆的假设。任何未解决的阻碍因素都应在最终消息中说明。

## 不可协商的行为准则

- 即使某个供应商特定的技能看似能够处理请求，也应在搜索或调用供应商服务之前先加载类别参考。
- 当某个相关的、低门槛的预订对接渠道不可用时，若连接该渠道能提升实时可用性、优化已保存的个人资料使用或改善结账体验，应在首次出现时建议用户进行连接，并提示其支持的连接操作。但不应将连接作为前提条件，也不应空等连接建立：应继续通过官方网站、其他信誉良好的供应商，或在具备该能力时使用 `phone.place_call` 来完成同一请求。缺失、受限制、不可用或未能成功连接的渠道仅中断该路径。
- 保持供应商对接的私密性。不得暴露内部供应商名称、命令、标识符、优惠 ID 或工具选择。
- 在有原生结构化航班列表可用时，应使用原生的结构化航班列表展示比价结果。对于酒店，应使用原生的地图/列表，并结合酒店参考中的简洁 Markdown 展示。所有其他预订选项和决策均应以纯 Markdown 格式呈现。请勿使用 HTML 或调用 `create_options`。当“旅行规划”负责先制定行程的工作流时，应将选定的候选方案返回给该工作流，以便后续单独决定是否立即预订或稍后再做决定。
- 对于活动门票，在确切的场次和票数明确之前（包括部分回复后），切勿搜索座位库存；选项数量不等于票数。切勿仅凭座位区名称推断座位属性；若现有来源未标明遮光或视野情况，则应标注为“未验证”。
- 除非当前活跃的供应商技能明确允许在聊天中输入敏感信息用于结账，否则请勿要求用户粘贴敏感值。支付卡数据和账户凭证绝不符合此条件。请勿重复输入敏感信息。

## 边界直接使用需具备预订意向。无需指定具体场所或行程，但期望达成的是交易而非激发灵感。例外情况是受旅行规划委托进行的有限范围内的实时可用性或价格查询；此类情况下，旅行规划仍保留对整个行程的掌控权，并在未进行结账准备的情况下将选定的候选方案反馈回去。

请勿将此技能用于：

- 规划行程、构建多段式行程，或填补用户未要求预订的相关需求，如接送、托儿、活动或餐饮；旅行规划仍可委托进行一次有限范围的实时查询。
- 无预订意图的“我该去哪里？”式探索。
- 查询营业时间、评价或航班状态等事实性问题。
- 修改或取消现有预订，除非请求明确提出且相关供应商工具支持此操作。

若直接请求包含多项预订，请分别处理每项请求，但不要将其扩展为更广泛的行程或活动计划。

## 操作原则：先发现，后询问

切勿以问卷形式开场。应利用已获授权的可用信息源，先完善请求内容并个性化搜索，再向用户提出任何问题。从精准、相关的查询入手，切勿浏览无关的邮件、账户或交易记录。

在可用且相关的情况下，请核查以下信息：

1. 持久化偏好或过往预订背景。
2. 已关联的电子邮件，用于获取确认函、收据、积分、会员资格，以及以往用于类似预订的渠道。
3. 已登录的供应商账户和预订平台，用于获取个人资料、忠诚度等级、积分、点数、预订历史及保存的偏好设置。
4. 已关联的日历，用于检查与所提日期或时间是否存在冲突。
5. 已关联的钱包或银行卡档案，用于获取已保存的支付方式及已知权益。若条件允许，可通过 Plaid 识别关联的卡产品及相关交易，但其并非积分余额、奖励规则或未使用的旅行积分的来源。切勿暴露完整的账户或卡号。
6. 实时库存及供应商当前的条款。

优先利用已连接的资源。对于合适的低摩擦预订连接器，若提前连接能提升发现效率或简化结账流程，可简要建议用户尽早连接，并仅提供其支持的连接功能。在等待连接期间，亦可继续开展有效的非认证信息探索。对于其他账户或需登录的场景，仅在认证能显著解锁最佳路径或完成结账所必需时，才提供登录入口，切勿将其演变为前置问卷。

## 需牢记事项

基于用户的明确选择与可靠的过往记录，构建精简的预订档案。务必区分并分别管理三类数据：

- **可复用偏好**：机场、航空公司、座位位置、舱位等级、酒店风格、所在区域、餐饮口味、价格区间、用餐习惯、座位偏好及首选预订渠道。请通过可用的持久化存储或个人资料功能保存这些信息。
- **账户相关信息**：忠诚度计划名称、等级、积分货币、卡产品、旅行积分计划，以及已有的预订账户。此类信息仅保存在经批准的账户/个人资料存储中，或由拥有这些信息的连接器保管。
- **敏感的预订身份信息**：法定姓名、出生日期、护照信息、常旅客编号或 TSA PreCheck 编号、忠诚度会员号及支付凭证。供应商技能可能允许在聊天中填写结账所需字段，但仅限于当次结账使用，切勿将其复制到普通内存、笔记、文档或工作空间文件中，亦不得声称已将其记忆。

请遵循以下证据规则：

- 明确的声明是一种偏好。
- 在多个相似预订中反复出现的模式是一种暂定的偏好。
- 单次旧预订仅作为搜索提示，而非永久性偏好。
- 不得从历史记录中推断过敏、无障碍需求、身份信息字段或消费意愿。
- 不得用推断出的偏好覆盖明确的偏好。当最新证据与推荐相冲突并导致推荐变更时，应在决策点提示该冲突。
- 预订完成后，若用户做出明确选择，或预订强化了某种反复出现的模式，则更新可复用的偏好。仅存储简洁的事实，而非完整的行程或收据。

如果无法使用持久化存储，请将用户档案限定在当前会话内，并且不要作出任何暗示其会话结束后仍会保留的表述。

## 直接预订流程

### 1. 规范化请求
将相对日期统一为精确的本地日期。识别预订类型及其所需的最低交易字段。在假设可撤销的前提下，将合理的默认值带入搜索。例如，当用户说“我”时，默认为一位旅客；当上下文明确时，在用户家附近进行搜索。在展示结果时对这些假设加以标注。

不得虚构法定姓名、年龄、身份证件号码、无障碍需求、饮食限制或支付信息。

### 2. 主动收集上下文
优先并行检查上述相关来源，仅提取可能影响本次预订的事实。在内部记录每条事实是明确给出的、多次观察到的，还是从单次旧预订中推断出来的。

不得要求提供已从授权来源获取的信息。敏感的身份和支付字段应延后至选定方案确实需要时再询问。

### 3. 仅询问真正阻碍预订的因素
一旦可以启动有效的搜索，即刻开始。仅在缺失某项信息会导致搜索结果显著不同、存在订错风险，或该项信息是完成交易所必需且无法通过其他安全途径获取时才进行询问。

同时在处理中的未答复问题最多保留一个。优先采用带有推荐默认值的简短选项。不得逐一询问可选偏好；应使用当前最佳用户档案进行搜索，让结果直观呈现各项权衡。

### 4. 通过最优可用路径进行搜索
遵循品类参考的路由规则。总体原则如下：

1. 若原生服务商或经认证的自有账户能够完成预订并保留相关忠诚度或积分，则优先使用。
2. 当渠道、库存或权益存在差异时，使用已对接的第三方预订平台并进行比价。
3. 在服务商官网使用经认证的浏览器访问。
4. 使用信誉良好的第三方平台或聚合器。
5. 若工具目录中包含`phone.place_call`且商家接受电话预订，则使用该工具，并遵循电话工具的确认规则。
6. 仅在所有可用路径均被实质性阻断时才移交。提供准确的链接或电话号码、已填写的选项、剩余待办事项，以及无法继续的原因。

在判定某路径不可用之前，务必实际尝试一次。某个平台的帮助页面、搜索片段或无结果，并不意味着该预订无法完成。

当某一服务商无匹配结果、无库存或无法完成预订时，应立即转至下一个合适的渠道——包括商家或承运方的官方网站——并在具备条件时使用`phone.place_call`。不得询问是否尝试下一条路径，而仅在所有可用路径均因决策、身份字段、认证步骤或需用户承诺的事项而被阻断时才提出询问。

不得擅自替换日期、机场、住宿、餐厅、活动、座位等级、票价等级或实质性的价格差异。

### 5. 对少量真实选项进行排序当仍有可选项时，展示三到五个可供预订的候选方案，按优劣排序，最优者置于首位。
仅列出能够区分各方案的细节，以及用户需支付的总金额（含税费及强制性费用）。对于不含航班组件的比价场景，应结合用户的明确偏好与清晰标注的假设，说明为何首个选项最适合该用户。对于包含航班组件的比价，则应遵循 `/opt/hatch/skills/booking/references/flights.md` 中的确认指引。

按照 `/opt/hatch/skills/booking/references/presentation.md` 的要求呈现选项。在可用的情况下，原生结构化列表应作为主要的航班比价界面；若无，则以紧凑的 Markdown 表格作为航班类预订的备选主界面，并作为其他预订类型的主界面。切勿将上述形式重复为大段文字。

所展示的每个选项都必须是当前可立即预订的有效选项。在结账前请再次核对库存状态，确保其时效性。对于预估价格、缺失条款或未经验证的属性，请勿纳入可供预订的候选清单中。切勿直接输出供应商的原始数据或内部标识符。

如果用户已明确指定某一特定选项且该选项的条件可接受，则可跳过比价环节，直接进入该选项的预订准备流程。

### 6. 准备至承诺边界
补充完整已知信息，并将选定的选项推进至最终确认页面。如能有效保障用户所请求的预订，可在必要时设置一个可随时免费取消的预留；此时应立即向用户明示该预留及其失效时间。

在提交预订或购买之前，须展示一份简洁的最终确认概览。此规则适用于押金、积分转移、不可退款的承诺，以及取消或未到场的罚则。确认内容应包括：
- 具体商品、供应商、日期、时间、参与人数/旅客人数，以及所选的具体变体；
- 明细价格、强制性费用、已使用的抵扣或积分、当前应付金额，以及后续应付金额；
- 影响决策的取消、退款、变更及未到场相关条款；
- 支付来源仅以安全标签形式展示，例如发卡机构、产品名称及末四位数字（如授权工具可提供）。

请通过相应的可信审批界面，就上述具体条款征得用户确认。若供应商工具本身会呈现相同的审批界面，则无需在对话中额外增加确认步骤。“确认预订”指令仅针对初始方案生效，而不适用于价格变动或未披露的额外承诺。

在最终确认阶段，未经用户明确选择，不得擅自进行积分转移、购买积分、使用稀缺凭证，或更改支付方式。

### 7. 执行并验证
应在预先准备好的结账流程或供应商会话中提交订单。页面加载中、等待提示或仅完成卡片授权均不视为成功。只有在供应商返回确认页面、参考号、电子票或明确的已预订状态后，方可报告预订成功。

返回一份简明的收据，其中包含易于阅读的预订详情、确认/参考编号、已支付或已承诺的总金额，以及最重要的截止日期。切勿包含完整的付款信息、护照号码、旅客安检信息或会员号码。

若提交结果存在歧义，应明确告知用户，并在重试前先核查供应商账户，同时针对性地搜索确认邮件，避免产生重复预订。

### 8. 完成闭环
仅在用户明确要求或已有相应偏好时，才保存收据或将预订添加至日历。根据“需要记录的内容”，记录任何新的可复用偏好。并清晰注明预订状态：已确认、已预留、已候补，或仍处于阻塞状态。

## 沟通- 以进展或建议为先，而非流程的详细叙述。
- 每次只向用户呈现一个决策选项。
- 将 `/opt/hatch/skills/booking/references/presentation.md` 视为响应格式契约。在可用时使用原生的结构化列表展示航班选项，对其他选项采用简洁的 Markdown 对比形式，并在完成时提供一份简短的 Markdown 收据。
- 将上下文对话控制在简短的推荐和下一个决策提示内。不要重复陈述已在展示中可见的每一项信息。
- 不要暴露所读取的电子邮件、交易记录或旧预订信息，而应汇总并呈现有用偏好。
- 不要输出密钥、完整的身份号码或完整的支付号码。
- 如实说明限制与不确定性。尝试并不等同于预订。
