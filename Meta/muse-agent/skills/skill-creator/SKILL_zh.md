# 技能创建者

## 目的
创建或更新一种易于触发、加载简洁，并且仅在参考资料或辅助代码能显著提升可靠性时才予以添加的技能。

## 工作流程
1. 明确技能的功能、可能的触发短语，以及目标工作区中的技能路径（`~/workspace/skills/<name>/`）。
2. 选择一个明确而狭窄的范围。每个技能最好只负责一项清晰的任务；将不相关的任务拆分为独立的技能。
3. 在编辑前规划好文件布局：
   - 仅在 `SKILL.md` 中保留核心运行逻辑。
   - 将冗长的文档、示例、Schema 或教程移至 `references/` 目录。
   - 只有当最终输出会用到模板或资产时，才将其放置于 `assets/` 目录。
   - 尽量使用 `bin/` 目录中的辅助二进制文件或已纳入版本控制的辅助工具，而非在提示词中写明协议或认证说明。
4. 撰写或更新文件头部信息。必填项：`name`、`description`。
5. 撰写或更新正文内容：
   - 基于工具的技能：包括 `Purpose`、`Tooling`、`Auth`、`Operating Rules`。
   - 仅基于工作流的技能：包括 `Purpose`、`Workflow`、`Output Contract`、`Operating Rules`。
   - 示例应简短且可直接执行。
6. 大胆删减。从 `SKILL.md` 中移除冗长的 API 文档、Schema 清单及部署说明。若某细节虽有用但并非每次触发都需用到，则将其移至 `references/`。
7. 进行合理性检查：
   - 描述应说明技能的作用及适用的触发场景。
   - 正文应指导模型下一步该做什么，而非全面解释整个领域。
   - 命令、路径和认证流程必须与实际的代码库或运行时行为一致。

## 连接器凭据
获取提供商的凭据是通过 `credentials.request_api_access` 完成的，而不是编写一个文件。这是一个包含外部依赖的序列，工具会强制执行其顺序，并拒绝 Muse 无法表达的方案。
使用该凭据的操作在此处编写，但请勿从空文件开始。连接器连接成功后，请先进行脚手架生成：

```
/opt/hatch/skills/skill-creator/bin/scaffold-connector-skill --provider <provider>
```

该命令会从认证服务中读取连接器配置，并生成一份 `SKILL.md` 文件，其中的 `Tooling` 和 `Auth` 部分已包含凭据的处理逻辑：需要导入哪个辅助工具、凭据值存放在何处、允许哪些主机访问，以及如何替换失效的凭据。同时，它会在生成的 `bin/` 目录中写入相应的 CLI 脚本，并将上述两部分保持为自动生成的内容。
如果从提供商处收到 401 或 403 错误，这首先意味着请求本身存在问题，而非密钥错误。请确认凭据是否已正确附加：未使用辅助工具构建的请求不会携带任何凭据，而这与令牌错误或作用域不足的表现完全相同。

## 运行规则
1. 保留现有的可用命令和代码库约定，不要随意发明新的二进制文件、路径或认证流程。
2. 尽量保持文件头部信息简洁，并按需加载。仅添加技能真正需要的元数据。
3. 将认证相关内容单独列为一节，不要将其混杂在运行规则中。
4. 如有现成的部署或认证辅助工具，优先使用它们。若已有打包好的辅助工具负责相关流程，无需指示模型手动编写配置文件。
5. 仅当能显著缩短 `SKILL.md` 的长度时才创建 `references/` 目录，避免在同一内容上重复出现。
6. 若创建或修改 Python CLI，请在报告完成前使用 `python3 -m py_compile ~/workspace/skills/<skill-name>/bin/*.py` 对其进行编译。
