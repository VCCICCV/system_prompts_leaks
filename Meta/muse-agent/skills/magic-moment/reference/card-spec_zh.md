# 卡片规格 — 证据卡片与网页取证流程

`../cmm/card.py` 是所有数值的实现来源与事实依据；本文件用于说明设计意图。若两者存在不一致，以代码为准——请同步更新本文件。

## 内部机制（维护者参考 — 非代理使用指南）

`make_card(inner_img, hero=...)` 将一张经过严格裁剪的内容图像包裹在白色圆角边框内（`hero` 参数仅用于最终揭晓环节，但渲染效果相同——金色边框及“FINAL PICK”标识已弃用）；随后该卡片作为线程消息，由 `cmm/overlay.py` 的堆叠渲染器进行动画处理并进入视频。`cmm/compose.py` 和 `cmm/script.py` 是其唯二的调用方——作为代理，您只能通过剧本中的 `visual` 节拍以及 `./mm render` 来操作卡片，且验证检查已在 compose 中自动执行，请勿针对这些接口编写驱动脚本。

## 锁定的内容及其原因

**单一事实源。** 证据卡片必须是一张来自真实截取的预合成 PNG 图像。切勿在现场叠加主体图层、浅色图层和加粗图层——这会导致文本重复，并在卡片外缘露出第二道模糊缩略图。如需替换缩略图，务必先将整个区域清空为纯白色；部分清除会留下可见的第二组文字。最安全的做法是直接使用未经修改的真实主体图像。

**内容决定高度。** 卡片高度随内容变化，仅设有限高以避免极端情况。此前的缺陷曾强制设置最小高度，导致裁剪较短时卡片上半部分出现大片空白。具体的限高值写在代码的 `make_card` 函数中——以往描述可能与代码不一致，请以代码为准。

**圆角具有承载作用。** 卡片外壳为圆角设计，`verify_card` 会验证其圆角状态（透明的极角与不透明的内嵌）。任何方形元素覆盖在外壳的圆角顶部，都是证据卡片外观失真的最明显表现——请在调用 `make_card` 前将内容烘焙至内部图像，而非在成品卡片上叠加。

**卡片统一从共享舞台入场。** 卡片采用渲染器的入场与后退弧线动画。在预设停留后，它会留在线程中，并随着后续元素的加入逐渐缩小、变透明，被推至画面深处。详细展示证据时，请使用点击交互。

## 网页取证流程 — 以完整区块裁剪确保精确性

在将某截图认定为亚马逊或 FedEx 卡片之前，务必先真实获取该页面，再按当下的文稿所指内容进行裁剪。

**切勿按百分比切割。** 简单地截取“顶部 28%”会切断基线，使字符断于行间。应裁剪包含完整语义的最小*完整区块*，并四周各留约 12px 的填充，且仅保留完整行。务必确认下边界落在清晰的空白行上；若未对齐，则向下扩展直至对齐。

按站点构建裁剪映射表，以文稿使用的名词短语为键：

```python
CROP_MAP = {
  "hero_full":      {"box": (x0, y0, x1, y1), "note": "导航栏 + 标题 + 副标题，完整行"},
  "model_panel":    {"box": (x0, y0, x1, y1), "note": "规格面板 + 所有行"},
  "hold_telemetry": {"box": (x0, y0, x1, y1), "note": "控件 + 圈形指示 + 实时信号网格"},
  "punchline":      {"box": None,             "note": "最终揭晓卡片，全帧"},
}
```

具体操作：确定该时间点对应的文稿名词短语 → 查找规则键 → 按照对应框选区域裁剪。若无合适框选，则通过 `browser.spawn_task` 对目标元素调用 `getBoundingClientRect()` 重新截取，再适当填充。

**每张证据必须视觉上可区分。** 若两张裁剪结果完全相同，说明两次选择了同一规则——这是失败，而非捷径。

上述框选区域因站而异，每次截取都需重新测定——切勿复用基于不同页面测得的裁剪映射。**使用真实的配色，绝不要凭空捏造。** 通过 `getComputedStyle` 直接从页面中提取实际的调色板，而不是去猜测品牌色。即使页面加载失败也依然有用：一个无效的联邦快递运单号会返回系统错误页，这不仅验证了流程，还能获取到真实的联邦快递紫色、橙色、字体和圆角半径，从而实现精准复刻。绝不要用一个看似合理的蓝色去替代你未实测的品牌色。
对于尺寸紧凑的竖版图片（如商品主图或生成的视觉大片），完全跳过裁剪——直接使用未经处理的原始图像主体。

## 值得选用的卡片形态

这些是您按节奏编写的 HTML 的设计模式，而非代码模板——我们没有模板库；每一张合成卡片都是全新的 HTML。该 HTML 的外观（即 Muse Moments Kit 中的组件、缩放与内边距）由 `design.md` 规范定义——请在编写前先阅读它。以下是五种行之有效的形态，它们共享相同的外壳逻辑，仅在内容上有所差异：

1. **商品卡**——缩略图、标题、星级评分、价格、配送信息、购买按钮
2. **订单卡**——深色头部、订单号、日期、商品列表
3. **物流跟踪卡**——承运商专属紫色头部、状态、时间轴
4. **通话暗色卡**——深色背景、波形、发言者标签、时间戳
5. **确认绿色卡**——白色卡片、绿色勾选标记、金额、确认码

## 验证机制

`verify_card(card, name)` 和 `verify_proofs(cards)` 定义在 `../cmm/card.py` 中，会在每一个经过“外壳化”处理的视觉元素（即 `"shell"` 或 `"hero"` 节拍）上运行。而独立的视觉元素——作为默认情况——则由 `render_html` 的空白与高度检查，以及确定性的照片处理来保障。请勿手动编写这些校验逻辑。

共有三项校验，每项都会通过 `CardVerificationError` 报告其对应的失败原因：

1. **左上角透明度**——如果该角落不透明，说明方形标题被叠加在圆角外壳之上
2. **r16 内嵌不透明区域**——用于确认外壳已成功渲染
3. **卡片非空白**——捕获那些未生成任何内容的渲染结果

这里特意**未设置填充率校验**。原本可能因该校验而触发的“半空卡片”问题，是由 `make_card` 强制设定 300px 最小高度所致；如今 `make_card` 已根据内容本身计算高度（`inner_h + 2*INNER_PAD`，并限制在 180–620px 之间）。因此，所有高于 180px 底部高度的卡片，其可用高度都恰好被内容填满，校验自然不会触发。

此外，还需注意为何基于像素的填充率校验并不适用：前述裁剪规则要求扩展至底部边缘落在纯白区域，因此正确裁剪后的卡片底部本就预留了空白空间，这是设计使然。外壳的内边距与内容留白在像素层面并无区别，任何像素级检测都无法将其区分。

`verify_card` 会返回测量结果，以便调用方记录这些数据，而不仅仅是简单地断言。
