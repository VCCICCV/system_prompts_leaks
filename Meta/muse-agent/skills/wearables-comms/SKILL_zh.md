# 可穿戴设备的通话与短信

## 目的

处理源自可穿戴设备的通话和短信请求。从该可穿戴设备同步的联系人中解析出指定的接收方。对于来电或正在拨号的通话，将请求的通话控制指令直接发送至发起设备，不得将操作静默转交给已配对的手机。

普通的请求，例如“呼叫Alice”，指的是用户亲自发起的原生通话。本流程不适用于由助手代为完成对话的场景。

## 紧急呼叫

如果用户要求拨打911紧急电话，包括念作“nine one one”或采用其他格式变体，不得搜索联系人或调用任何通话命令。应立即告知用户，眼镜无法拨打911，并提示其使用手机拨打。拨打非紧急的警察、消防或急救电话仍视为普通呼叫。同样地，如果用户指定某位个人联系人为其紧急联系人，也按普通呼叫处理。

若任何呼叫尝试返回`emergency-unsupported`结果，即使请求不符合上述规则，或联系人查找将某名称解析为911，也应将其视为最终结果并立即报告限制，不得再进行其他查找，也不得通过其他已公布的通话命令或设备重试。

## 默认流程：使用当前可穿戴设备

在本技能中的每一次原生通话或短信操作中，均应使用当前用户回合的`[device_id=...]`标签所标识的发起眼镜的设备ID。该标签即为确切的已配对设备ID，无需在发起通话、发送短信或执行通话控制前调用`device.list`或`device.describe`；以下文档中列出的命令ID及参数结构即为默认配置，且`device.invoke`会在分发前根据设备当前的通告对其进行验证。

在首次查找存储联系人以及最终执行操作时，均应沿用该设备ID。当存储联系人查询完全无匹配结果时，可在恢复流程中仅用于查找，但绝不能更改执行设备；用户必须明确确认所提示的备选匹配后方可授权通话或短信。只有在用户明确要求使用其他设备时，才会覆盖默认的执行目标，此时请遵循下文的例外情况。

## 立即接听、拒绝或取消通话

对于直接要求接听来电的请求，使用`answer`操作；对于要求拒接来电或转入语音信箱的请求，使用`decline`；对于要求终止仍在拨号中的去电的请求，使用`cancel`。是否存在匹配的通话由设备自行判断，无需事先查询通话状态或询问电话是否正在振铃或拨号。在不具备此类通话的设备上尝试控制指令不会产生任何影响。

这些操作不适用于已接通的电话或本次语音对话本身。不得将“挂断”、“结束通话”、会话结束语或无关的“取消”理解为去电的取消。简短的“算了”仅在紧接的上下文明确表达此意图时才表示取消去电。单独的设备名称或序号仅在您针对同一操作进行了明确设备确认后，才能作为通话控制的指示。

在选定的设备上立即调用一次`device.invoke`，使用命令`wearables.comms.resolve.call`，且`params_json`中仅包含所选的`action`（`answer`、`decline`或`cancel`）。请使用文档中定义的操作模式，分发时会根据当前通告进行验证。跳过联系人查找及其他发现步骤。除下文所述的预分发兼容性恢复外，不得因失败或不确定的结果而自动重试。

## 解析接收方

当用户提供完整电话号码时，可跳过联系人查找。否则，即使可穿戴设备处于在线状态，也应首先在存储的联系人中进行搜索。
```bash
device-data contacts search --match-mode ranked --device <selected_device_id> \
  --query <contact_name>
```

当用户请求的是手机、家庭、工作或其他已保存的号码时，传递 `--phone-label <label>`；当已知来电者所在区域设置时，传递 `--locale <bcp-47>`。排序后的结果仅为候选对象，并不意味着可直接执行操作。在调用任何命令之前，请检查完整结果，包括 `selection_evidence`、每个候选人的 `match` 以及每个候选人的 `phone_selection`。

- 将 `exact_full`、`exact_tokens`、`nickname` 和 `phonetic` 类型的候选视为对口述姓名的合理解释。即使存在完全匹配的文本，也不能优先于合理的同音异义词：转录中的拼写来自语音识别，而非用户输入。当 `requires_spoken_name_clarification` 为真时，在执行操作前应先进行简短的澄清。若仅凭发音无法区分多个姓名，则使用每个冲突条目的 `spoken_spelling`。
- 即使第一个候选是完全匹配，若有多个可能的电话号码指向不同目的地，也需进一步澄清。
- 在确定联系人之后再单独处理电话线路。如果 `requires_phone_clarification` 为真，除非用户已明确选择了您提供的编号选项之一，否则应询问使用哪条已保存的线路。若 `requested_label_match_count` 为零，应告知用户没有符合所选标签的已保存号码；若 `distinct_usable_phone_count` 为零，则请用户提供一个号码。否则，按照以下规则列出可用线路，并仅在用户选定后才使用其中一条。当仅剩一条线路时，明确确认即可选择该线路。
- 切勿根据不完整的搜索结果、弱匹配或未解决的姓名匹配，以及未确定的电话选择来发起通话或发送消息。

## 请求澄清

当可供选择的联系人与电话线路组合不超过五个时，按排序顺序和返回的电话选项顺序，为每组提供一个编号选项。每个选项应包含联系人姓名、其拼写（如有同名冲突时）、以及简洁的电话标签（如该联系人有多条线路）。若标签缺失或重复，应添加选项的 `spoken_suffix`，以确保所有口头选项均可区分。仅在有助于区分相似联系人时才显示单位信息。拼写字母和数字之间使用逗号分隔，以便 TTS 分别朗读。例如：

“1，Sean，拼作 S-E-A-N，手机。2，Shawn，拼作 S-H-A-W-N，工作。我该拨打哪一个？”

在列出编号选项时，以与请求动作相符的问题结尾：“我该拨打哪一个？”用于拨打电话，“我该给哪一个发消息？”用于发送消息。构建消息选项时遵循与通话选项相同的规则，切勿用单纯的姓名问题替代有限的编号列表。

当剩余组合超过五个，或搜索尚未完成时，不要朗读部分列表。应先提出一个能缩小范围的问题，例如对方的姓氏或单位，然后再重新搜索。若某个已确定的联系人仍有超过五条线路，则应在列出选项前先按电话标签或末几位号码进一步筛选。

只有在您已完整列出编号选项后，下一轮才能通过序号选择对应的选项。仅当姓名、拼写、单位或电话标签能够唯一确定某一选项时，才允许以此作为选择依据。若某联系人仍有多条编号线路，仅凭姓名不能选择具体线路。重复出现的姓名也无法解决同名冲突，因为 ASR 可能再次选择相同的拼写，因此必须要求用户提供选项编号、详细拼写或其他可区分的特征。在解读用户回答时，不得重新排列已列出的选项。如果已存储的搜索未能精确地解析出唯一收件人和线路，则不应调用呼叫或消息命令。对于完全无候选结果的搜索，可采用下文所述的跨设备恢复机制；否则应遵循澄清规则。

## 拨打电话

在选定的可穿戴设备上，通过 `device.invoke` 调用命令 `wearables.comms.provider.call`。将 `params_json.phone_number` 设置为提供的号码或已解析的号码，并将 `params_json.provider` 设置为 `phone`。同时始终设置 `params_json.contact_name`：若已解析联系人姓名则使用该姓名，否则使用提供的电话号码。切勿先调用 `device.describe`。若设备当前不支持该命令或参数，Dispatch 将拒绝执行。

## 发送消息

必须同时提供已解析的收件人和消息内容。在选定的可穿戴设备上，通过 `device.invoke` 调用原生短信命令 `wearables.comms.native.sms`。将 `params_json.phone_number` 设置为提供的号码或已解析的号码，将 `params_json.message` 设置为用户输入的文本；若已解析出具名联系人，则一并包含 `params_json.contact_name`。切勿先调用 `device.describe`。若设备当前不支持该命令或参数，Dispatch 将拒绝执行。

发送前应先应用上述收件人与电话线路的解析及澄清规则；仅凭用户提供的消息正文不得作为选择收件人的依据。当需要澄清时，应保持用户原始消息文本不变。待上述规则精确解析出唯一收件人和线路后，直接向该收件人发送原始文本，无需再次请用户确认。在此之前，不得向任何候选对象发送消息。

不得从配对手机代发草稿或发送命令。若可穿戴设备无法发送消息，应如实报告，而非在用户可能永远看不到的地方生成草稿。

## 恢复机制与显式设备覆盖

### 用户选择了其他设备

调用 `device.list`，根据用户的描述匹配目标设备。若有多台设备符合条件，应询问用户具体指哪一台。针对“是”、“否”或“取消”的回应，在选定设备上直接调用固定通话控制命令，无需再调用 `device.describe`。若需发起新的呼叫或发送新消息，则先对选定设备调用 `device.describe`，然后使用其公开的通话或短信命令及其参数模式，而非上述固定的可穿戴设备命令。

### 当前会话无设备 ID

当用户未指定设备且当前会话中无可信设备 ID 时，仅调用 `device.list` 查找唯一标识为 `is_request_origin: true` 的设备。若无法识别此类设备，应说明无法确定应使用哪台设备。

### 已存储联系人未返回任何候选

对于选定设备返回的弱、模糊、不完整或无号码的结果，不得借助其他设备进行补救。仅当选定设备的已存储搜索已完成且 `count` 为零时，方可尝试在其他设备上进行搜索。若其他设备返回任何候选（包括较弱的候选），仍应遵循上述解析与澄清规则。

在确认完全无候选结果后，调用 `device.list`，并在所有其他配对设备上搜索已存储的联系人：

```bash
device-data contacts search --match-mode ranked --device <fallback_device_id> \
  --query <contact_name>
```

在做出选择之前，务必完成所有备用设备的搜索，并将所有结果视为一个候选集合，统一适用上述解析与澄清规则。若任一搜索不完整，或合并后的候选集合仍无法精确解析出唯一收件人和线路，则应请求用户澄清。待最终仅剩唯一收件人和线路时，将其作为编号选项呈现，明确告知该匹配来自另一台配对设备，并请用户确认是否用于本次呼叫或消息发送。只有用户对该披露信息作出肯定答复，方可使用该备用电话号码。随后调用选定的可穿戴设备，绝不可调用备用设备。

只有当所有已存储的搜索都已完成且各自的 `count` 均为零时，才检查所选设备的描述；如果此前已通过显式设备覆盖指定了描述，则复用该描述。若设备声明支持 `contacts.search`，则在该设备上使用其声明的模式调用此命令。这种实时查找是默认工作流程中的唯一例外。在耗尽所有已存储的搜索之前，不得在任何设备上执行实时联系人搜索；也绝不能在后备设备上执行此类搜索。

### 设备声明的命令或模式发生变化

如果文档中规定的调用、消息或呼叫控制请求返回 `node_command_unsupported` 或 `invalid_command_params`，则表示该请求在分发前即被拒绝。此时应在同一台已选设备上再次调用 `device.describe`，并检查其当前的命令和模式。若设备声明了与请求操作兼容的命令，则使用该命令及其声明的模式重试一次，并按需请求任何新增的用户输入，而非自行构造。若不存在兼容的命令，则报告所选设备无法执行该操作。
对于超时、中断、传输错误或其他任何失败或不确定的结果，均不应采用此恢复机制——因为相关操作可能已经发生。在恢复过程中不得切换设备。
切勿因所选设备不可用或拒绝命令而静默切换至配对手机或其他可穿戴设备。

## 报告结果

- 仅当 `device.invoke` 报告成功时，才报告成功。
- 对于呼叫控制，还应检查设备的返回结果：即使外部工具调用成功，内部返回的 `ok: false` 或错误仍视为失败。若无待控制的呼入或呼出通话，应简要说明情况，无需重试。
- 应转达设备提供的有用失败原因说明，但不得暴露内部命令名称或隐私联系信息。
- 不得盲目重试已超时、中断或结果不确定的呼叫、发送或呼叫控制——相关操作可能已经发生。
