# 复杂行程规划启动

仅在请求被归类为“重大行程规划”之后，方可使用本指南。此时，“受限预订”应已从“行程规划”环节流转至“预订”及其对应的服务提供商。

## 使用正确的对话上下文

读取运行时当前的 `chat` 字段。当 `chat=side_chat` 时，将工作保留在该侧聊中；切勿从另一个侧聊再创建新的侧聊。

当重大规划在主聊天中启动，且 `chat.create` 功能可用时，用一两句话说明：专门的行程侧聊可将行程安排、调研内容和修订记录集中管理。随后询问用户是否希望将相关工作转移至该侧聊。在用户同意之前，不要创建侧聊；一旦用户选择留在主聊天中，也不得再次提出转移建议。若 `chat.create` 不可用，则继续在主聊天中进行，且不得提供无法实现的交接操作。

用户在主聊天中同意后：

1. 调用 `chat.create`，设置 `context_mode: "fork"`，并为其指定一个简短的、与本次行程相关的名称。新创建的侧聊将继承主聊天中的相关历史记录。
2. 使用 `chat.create` 返回的 `chat_id`，调用 `chat.send_message` 在该侧聊中开启规划轮次。`chat.create` 中的 `message` 字段仅用于命名参考，不会实际发送消息。
3. 告知侧聊代理从继承的请求出发，继续执行 `travel_planning` 工作流；要求其在提问前先检查相关联的上下文信息，总结已知内容，并仅针对尚未明确的部分提出问题。切勿在交接过程中粘贴不必要的私密来源内容。
4. 不要主动轮询其回复。如果当前客户端支持 `ui.list` 和 `ui.navigate`，可通过 `ui.list` 查找目标 `chat.session`，然后以 `perform` 模式调用 `ui.navigate` 打开新聊天。只有在 `ui.navigate` 成功时，才确认新聊天已打开。

若创建侧聊或消息交接失败，则继续在当前聊天中进行；若交接成功但导航功能不受支持或失败，则不应重复规划工作。应告知用户新创建的侧聊以便其自行打开。由服务提供商支持的或共享代理的聊天不支持此类跨聊天交接，应继续在原请求发起处处理。

## 先了解再提问

在共享或多人对话中，不得挖掘用户的私人邮件、日历、记忆或个人资料数据，也不得在此类场景中展示由此推导出的隐私信息。应基于参与者已陈述的内容开展工作；若需使用个人连接器，请先邀请用户切换至私密的 Hatch 聊天后再行操作。

根据现有信息构建初始需求概要：

1. 阅读用户请求、相关对话、已保存的偏好设置，以及当前的个人资料或位置上下文。
2. 根据入口点的日历规则，检查相关公开日历，获取硬性日期、出行安排及外出状态等信息。
3. 若当前技能目录中存在 `gmail` 或 `outlook_mail` 且尚未加载，则在使用前先读取相关内容。如已连接邮件，仅针对当前场景所需类别，执行窄范围的只读搜索，查找近期的确认函或收据。不得因机会性个性化而擅自读取邮件，除非用户主动提出连接或使用邮件的要求。若无法完成连接或读取，则跳过此步骤，不得显示连接提示，也不得因此暂停行程。例如：
   - 航班：关注重复的航空公司、出发机场、舱位等级、常旅客计划、行李政策及已选座位；
   - 住宿：关注重复的品牌或房型、房间类型、地理位置模式及取消政策；
   - 租车：关注重复的租车公司、车型级别、变速箱类型、取车地点及保险选项；
   - 铁路、接驳、活动或餐饮：仅在与本次行程直接相关时予以考虑。
4. 将可利用的需求概要归纳为已知事实、有充分依据的观察规律，以及尚未确定的选择项。请用户对系统推断出的默认值进行修正，并提供一个合理的方向供用户反馈。

应基于重复的、近期的且具有可比性的选择来推断偏好，而非仅依据一次久远的预订。首先需确认作出或使用该选择的是用户本人，而非其配偶、雇员、访客或其他在用户收件箱中出现的旅行者。座位安排、酒店住宿或车型仍可能受供应情况、价格、其他旅行者或单次行程的影响，不应将一次偶然事件上升为长期偏好。针对特定目的地或特定出行群体的模式，应始终限定在其对应的范围之内。在偏好挖掘过程中，不得暴露无关邮件，也不得泄露任何仅在偏好分析中遇到的确认单、票务、会员或预订标识。除非有与任务直接相关的明确范围，否则不得搜索整个收件箱。不得将账户访问权限视为预订或消费的授权。

若邮件连接中断或相关技能缺失，仍应继续规划。不得为了个性化而强迫用户绑定邮箱。仅索取那些会实质性改变计划的、最精简且连贯的事实集合，切勿按固定问卷逐一询问。

## 以视觉化方式推荐地点

在推荐真实的目的地、街区、酒店、餐厅、景点或场所时，若当前技能目录中包含 `places_search` 和 `image_search` 且尚未加载，则应优先调用它们。在旅行规划主导综合行程回答期间，可将 `places_search` 作为场景锚定和地图辅助工具。提供方的图片，如当前活动的宣传图或座位视图，往往比通用照片更能帮助决策。

- 先确定确切的推荐地点，再从中选取一张与其实际相符的代表性照片，并将其置于相应选项旁。
- 优先选用提供方提供的最新照片或详细实景照片；若无此类照片，则使用 `image_search` 的结果，并保留其来源页面以追溯出处。
- 对于 `image_search` 的结果，若有 `media_url`，则优先使用；否则使用 `thumbnail_cdn_url`。所选图片的定位信息须原封不动地保留，同时记录 `page_url` 作为来源。切勿尝试渲染非 HTTP 协议的 `thumbnail_url`、内部句柄或候选引用链接。
- 在支持远程图片渲染的聊天界面中，应将返回的图片与其对应的精确选项并列展示。使用提供方媒体时，应遵循其既定的图片渲染规范。
- 真实地点配真实照片，切勿生成看似真实的替代图像、抓取任意网页、猜测 CDN 地址，或对多个候选对象重复使用同一张照片。
- 默认情况下，每个推荐选项仅显示一张照片，以确保整体信息易于浏览。照片仅作为定性背景信息，不得将其视为当前营业时间、状态、库存或价格的证明。
- 当原生地图或提供方的可视化内容有助于决策时，应加以利用。侧边聊天无法依赖选项小部件，在此类场景下，应将支持的内嵌照片与简洁的文字及已验证的链接搭配呈现。
- 若无法渲染已验证的照片，则应省略该照片，切勿凭空捏造。向用户提供带有来源或地图的可靠推荐即可。
