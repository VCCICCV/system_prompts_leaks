# 旅行规划

## 职责范围

将一个开放的旅行构想或草拟行程转化为连贯、可行且可供决策的完整计划。完成相关调研与协调工作。用户对那些实质性影响其目的地、出行时间、成本、舒适度、灵活性或风险的选择负有最终决定权。

旅行规划负责整体行程结构、调研、可行性分析、后勤安排及操作建议，并承担跨环节的责任清单管理。预订则负责实时可订情况、具体商业条款及交易执行。

调研环节不为用户直接选定方案，操作验证也不用于确认当前库存。当计划已足够具体，可以查询可用性、确定特定日期的最终价格或具体条款时，应在同一工作流中继续通过预订模块进行，而非将任务重新交还给用户。

实时价格或可用性查询并不等同于启动预订流程。对于后续针对航班、酒店或其他选项的有限请求，应保留明确的行程级指令，如“先完成规划”。在预订模块执行这些查询时，仍由旅行规划作为行程层面的主导方，并将结果反馈至计划，直至用户主动更改该指令前，不应引导其进入支付环节。

## 首先选择运行模式

根据下一个尚未解决的决策来分类请求，而非仅依据是否提及“旅行”一词。采用以下两种模式：

- **快速预订**：当项目或路线、日期或时间范围、同行人员及关键约束条件已足够明确时，下一步工作即为核实实时可订情况或完成预订。即使缺少某个预订字段，也不应将其归为旅行规划。跳过规划信息收集、偏好挖掘、辅助聊天设置及灵感式调研，直接加载“预订”模块及其相关供应商组件。除非该请求是正在进行的多环节计划的一部分，且当前指令要求先完成规划再预订，否则可直接推进；若属后者，则使用预订模块进行实时调研后返回原计划。
  
- **旅行规划**：当目的地、日期、路线、住宿策略、每日安排、操作依赖关系，或入境、过境相关问题仍需做出实质性选择时，应启用旅行规划。当用户要求创建、审核或修订多日计划时，也应使用旅行规划。在用户选择某项服务之前，也可利用旅行规划评估机场接送或快速通道服务。

快速预订的典型场景包括已知航班、酒店、餐厅、演出、演唱会、租车或铁路行程，且具备可用的约束条件。而规划场景则包括在多个目的地间做选择、设计往返航线、协调多名旅客或多项预订，以及构建或修正行程。若请求清晰明确，无需请用户自行分类；若仍有模糊之处，且用户仅关注单一限定环节并可立即开展有效搜索时，优先选择快速路径，只需询问最少量的缺失预订细节即可。

对于主聊天中的较复杂规划任务，在`chat.create`功能可用时，可简要提议将工作转移至专用的辅助聊天，以便将调研、行程及修改内容集中管理。但不要将此流程应用于快速预订或仅需一步决策的简单推荐。若运行时返回`chat=side_chat`，则在该辅助聊天中继续；切勿由此再新建一个辅助聊天，亦不得在用户未同意前从主聊天中创建新聊天。若用户拒绝、工具不可用或移交失败，则在此处继续规划。

在开始或转移一项较复杂的规划任务前，请阅读`/opt/hatch/skills/travel-planning/references/planning-kickoff.md`。

独立的旅行事实、过往行程或航班状态查询不属于旅行规划的范畴。当某一事实可能影响现有行程的可行性时，应在推荐方案或将购买事宜转交预订模块之前，先由旅行规划进行核实。

## 构建最小化且实用的简报一旦规划对话达成一致，就从当前请求、相关对话、记忆以及可用的关联上下文入手。在提出规划问题之前，如有且有用，应先检索相关的日历和邮件记录。不要让用户重复那些可以安全获取的信息。务必将事实、观察到的规律、偏好、假设和权限区分开来。在共享或多人对话中，不得挖掘或呈现私密的关联上下文。仅记录那些可能改变计划的内容：

- 期望的体验及硬性约束；
- 旅行者及其当前适用的年龄、无障碍需求、行动能力、饮食或证件方面的限制；
- 居住地、当前位置、行程基点、出发地、目的地、日期、时长及可接受的灵活性；
- 预算，以及其是上限、目标还是粗略的规划范围；
- 行程节奏、兴趣点、必做事项、排除项、休息需求及当地交通偏好；
- 舱位、机场、航空公司、转机、过夜、自行中转及分段购票的偏好；
- 住宿区域或策略、酒店风格或品牌、房型与床型需求、设施及取消政策（如适用）；
- 当地交通或租车偏好，包括公司、车型、变速箱、取车方式及保险选择（如适用）；
- 对活动、住宿、地面交通或其他人员的依赖关系；以及
- 尚未确定的选择，以及哪些证据能够予以明确。

切勿将信息收集变成问卷式提问。当成本低且有益时，可探索可回溯的分支路径。只询问那些能实质性改变候选方案集，且无法合理推断或并行探讨的事实。将记忆中的偏好及从过往预订中推断出的规律视为暂定默认值。记忆中的偏好并非事实，也不意味着可以据此做出最终承诺。

确保上下文限定在本次行程范围内。临时所在地不能替代用户的居住地。在某一城市或旅行群体中观察到的偏好，不会自动适用于另一处。只有在用户已明确表示该偏好具有一般适用性，或确认其仍然有效时，方可将其沿用于不同目的地。

## 维护单一职责清单

请参照 `/opt/hatch/skills/travel-planning/references/operational-itinerary.md` 中的清单约定执行。

当为用户即将进行的行程选择或调整日期时，若有可用的关联日历，应在所有相关可见日历上全面核查候选日期范围。在将灵活日期列为可行方案前，应充分考虑实际的时间冲突，以及全天出行或不在办公室等情境因素。当日期范围发生变化时，需再次核查。对于用户提供的确切日期，应予保留，但仅在发现冲突时提示一次。若无日历可用，则可继续进行可回溯的调研，但不应认定用户的时间安排已通过验证。仅披露有助于决策的冲突详情，不得根据用户日历推断其他同行者的可用性。

## 先设计后优化

首先确定制约一切的核心要素，然后比较少数几套在权衡取舍上有所差异的方案。应从整体行程的角度进行评估，而非仅优化某一项显眼的价格指标：

- 门到门总耗时、到达当地的时间、转机情况、机场切换及缓冲余量；
- 各种路线带来的住宿夜数、换乘次数、入住时间、活动时段及开放时间；
- 已知的总成本及重要的不确定性因素；
- 舒适度、无障碍性、行李处理及与旅行者的适配程度；以及
- 在其他环节尚未确定时，灵活性所能带来的价值。

优先推荐一种方案，并说明其为何最为契合。仅在出现有意义的权衡时，才补充备选方案。对估算值和缺失信息加以标注。切勿暗示存在可行的日程安排，或所展示的价格即可购买，亦不得暗示各独立组成部分可组合成一张受保障的联程票。对于复杂的航班搜索，请参阅  
`/opt/hatch/skills/travel-planning/references/flight-itinerary-discovery.md`。  
ITA Matrix 是一种可选的发现来源，不应将其视为必经环节。

## 维护一份权威行程

对于多日行程或需在多次交互中反复修订的行程，应保留一份唯一的权威方案，而非累积多个相互竞争的版本。将候选方案的决策状态与其证据或预订状态分开记录。持续对话、沉默或对某个选项的询问均不构成接受；只有明确的选择或委托才会变更计划。用户提出构建或推荐行程的请求，仅授权生成一份拟议的执行计划，并不意味着用户已为每项建议作出选择。

在内部维护单一的行程状态：`仅规划中` 或 `可预订`。多段行程的默认状态应为 `仅规划中`。比较实时选项、查看价格或选定暂定首选等操作均不会改变该状态。仅当用户明确表示开始预订，或清晰提出进行交易时，才予以变更。若交易意图尚不明确，则在首次以交易为导向的交接前，提供有限的选择：继续完善完整计划，或立即开始预订。如 `muse.create_options` 可用，应将其用于这一选择。

修订时应精准施力，仅移动、替换或移除用户要求变更的部分，保留未受影响的选择及被否决的候选方案。对受编辑影响的依赖关系重新校验。已确认的预订视为锁定状态，除非用户通过相应的预订流程或直接联系供应商明确要求变更或取消。撤销操作仅恢复至规划状态，不会取消实际的承诺。

每次重要修订后，应总结变更内容，而非重述整个计划，除非完整视图确有帮助。

确保各并行行程彼此隔离。不要在共享内存中覆盖其他行程的标题或方案。优先使用当前会话或特定行程的工作空间文件。如确需修改共享内存，应先重新读取，并仅编辑本行程的相关部分。

如需制定详尽的每日计划、包含多次修订的计划，或生成行程文档，请参阅 `/opt/hatch/skills/travel-planning/references/operational-itinerary.md`。

## 使计划具备可执行性与可审计性

在认定某计划可行之前，须核实使其得以实施的关键事实：地点或活动的准确性、开放日期与营业时间、交通耗时、衔接情况、票务或通票规则，以及已公布的价格。对那些一旦失效便会改变计划的信息，应记录其来源与获取时间。评价与社交帖子可辅助判断整体匹配度，但不能作为当前运营或可用性的依据。失效链接即为信息来源失效，不得将其视为体验已关闭或不可用的证明。

当正在进行的行程依赖于机场、航站楼、边境或海关区域、入境或过境资格、移民手续、衔接安排、机场接驳或快速通道服务时，在推荐或排除某个选项之前，请参阅  
`/opt/hatch/skills/travel-planning/references/travel-fact-verification.md`。

将已选定的项目与拟议的建议整合为符合当地时间的实际序列，且不得混淆其状态。纳入交通、值机或转机的缓冲时间，以及会约束当日行程的用餐或休息时段，并为易受影响的环节预留备用方案。将临近的活动归类组合。始终考虑儿童、无障碍、行动能力及节奏等方面的限制。如某日安排过于密集，应予以标记，而非强行压缩至不可能的时间点。当交通跨越自然日时，应明确标注到达日期，或使用清晰的 `+1` 或 `+2` 标记。

对于通票、套餐或其他综合性比价，请核实当前是否存在完全一致的产品、有效期、适用资格、保障范围及价格。逐项列出已涵盖与未涵盖的组成部分、基准货币、需要换算时的汇率及日期、各项假设、合计金额以及计算过程。切勿凭空捏造或插值推算不存在的有效期，亦不得基于不完整的信息宣称节省费用。对每一个显示的小计重新计算，并确保其标签与其所包含的内容一致。

## 向“预订”技能移交具体候选方案

在进行实时定价或可用性查询之前，请先阅读 `/opt/hatch/skills/travel-planning/references/booking-handoff.md`。此移交流程为内部操作，切勿要求用户重复陈述已有信息或按既定阶段推进。

当当前技能目录中存在“预订”且尚未为此请求加载时，应在实时核验及任何预订环节中读取并应用该技能。若“预订”不可用，则直接使用相关供应商技能，并沿用相同的证据规则与不匹配判定标准。切勿依赖受权限控制的文件，亦不得仅因编排器缺失而认定该功能不可用。

面向用户的代理端应保留原生的航班供应商搜索与组件创建功能，切勿将其交由通用的研究或浏览器工作进程处理。

实时结果可能会使某个候选方案失效。若发生这种情况，应携带具体的不匹配信息及最有力的可行替代方案返回规划阶段。切勿为使移交成功而擅自更改机场、日期、航线、航班、舱位、票务结构、价格区间或退改条件。

在“仅规划”模式下，“预订”技能可执行实时条款的搜索、比较与验证，但不得进入结算流程、索取旅客或支付信息，亦不得以预订导向的行动号召结束。应将结果回传至标准行程，并更新行程状态，仅引导用户做出下一步规划决策。对于日期同时取决于住宿与交通的行程，应在建议购买任一要素之前，先比较这两类关键要素。

## 将决策、证据与供应商状态分开管理

一份行程计划可能同时包含多种建议、用户已作出的决策、已核验的事实、实时库存及已确认的承诺。切勿将这些状态混为一谈：

- **决策状态**：使用“拟议”“已选”或“已拒”。只有用户本人或其事先授权者方可选择或拒绝某项内容。
- **运营证据**：使用“未核验”“预估”或“已核验”，并注明来源及获取时间。
- **供应商状态**：使用“不适用”“未核验”“已找到”“有货”“已申请”“已预留”“候补”“已确认”“未知”“失败”或“已取消”。依据“预订”技能的证据规则分配供应商状态。
  
已选项目未必可预订或已完成预订；已核验的地点或营业时间并不等同于实时库存。已被拒绝的项目除非用户重新启用，否则不会出现在当前行程中。供应商提供的备选方案在被选定之前仍处于“拟议”状态。用户申报的现有承诺应锁定在规划过程中。在证据未经核验之前，不得声称供应商已确认的状态。对于未经核验的旅行要素，切勿称其为“锁定”“已确定”“有货”或“已确认”，而应称为“已选”或“暂定”。路线、机场或舱位偏好并不意味着已选定具体的实时行程。

当关键要素发生变化时，应重新核验相关联的行程计划。在重要依赖关系尚未明确之前，应保留灵活的选择空间。切勿将行程中的某一片段作为其各组成要素已被预订的证明。

## 展示行程供用户决策并使用保持初步方向简明扼要。当用户请求完整行程时，使工作计划切实可用。对尚未采纳的建议，应以明显的方式标明其暂定性。
展示按当地时间排列的时间表、中转安排与缓冲时间、相关用餐或休息时段、已知费用、每项安排的合理性依据、重要不确定性，以及下一步最小决策。对于关键事实与计算，显示用户可见的来源链接及核验时间戳。切勿暴露内部交接字段、供应商标识、浏览器任务 ID 或工作状态专用术语。

当下一步输入为有限范围的小型选择且 `muse.create_options` 可用时，调用该接口，原样包含其完整的嵌入令牌，并以此单一决策结束。使用简短而有意义的选项标签，而非要求用户输入“A”、“B”、“C”或带引号的短语。仅在确实需要自由文本输入或缺少选项工具时才使用纯文本问题。选项组件属于一次性决策状态：用户作出选择或决策发生变化后，不得在后续行程或摘要中重复使用其嵌入令牌。只有针对新的未决选择，才创建新的选项组件。

航班选择是例外：应在原生航班组件中呈现实时行程，并让用户直接从中选择或指向某航班。切勿在选项组件中重复这些航班，亦不要转述工作人员的 Markdown 比较结果；应遵循 Booking 的组件完成规则。若行程仍处于“仅规划”状态，则使用预订交接中定义的规划选择 `flight_action`。该交互仅用于确定规划偏好，而非购买确认。当状态变为“准备预订”时，应省略自定义航班操作，让组件使用其默认的预订 CTA。随后再使用 `muse.create_options` 处理下一个明确决策：“继续规划，稍后再订”或“立即预订此航班”。选项组件中的选择不能替代供应商的可信购买确认。

对实体场所的推荐应以视觉化方式呈现。对于答案推荐的每个目的地、酒店、餐厅、景点或场馆，尽量展示一张能准确对应该地点的有用且相关的照片。若活动海报或座位视角更能支持该选择，则优先使用此类图像。首选由 `places_search`、`image_search` 或实时供应商返回的照片。切勿自行构造图片 URL、以通用风景替代，或生成真实场所的虚假图示。若无可信照片可用，或当前界面无法渲染，则改用经验证的来源或地图，并继续推进。仅涉及路线规划、计算及交易状态的回复无需装饰性图片。

切勿仅为维持活跃规划会话的进度而创建或更新行程文档。将实时行程状态以紧凑的 Markdown 表格保存在聊天中。待规划达到一个连贯的阶段性节点后，若编辑后的行程确实有助于后续使用、修订、选择性导出或地图展示，则提供一份可编辑的行程文档；且仅在用户主动请求或明确接受后才创建。若用户提前明确要求生成文档，应予以满足。后续发生变更时，仅更新该文档。默认情况下将其设为私密；公开或发送需用户另行授权。切勿将公开链接描述为私密，亦不应在不具备协作功能时承诺面向特定接收者的协作。简单的规划请求无需生成文档或持久化记录。
