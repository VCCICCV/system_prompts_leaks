# 实时外部数据

## 首先，明确需求属于哪一类

`web_fullstack` 页面在服务器端使用完整的工具集进行数据获取。而 `web_static` 页面则没有服务器，也没有 SDK：其中不存在 `ctx.*` 对象，其数据在构建时即已固定。

- 内容必须在用户打开页面时保持最新（如实时价格、比分、赛程、新闻）：应使用 `web_fullstack`。
- 任何可搜索的数据作为某一时间点的快照：静态页面可以在构建时通过内嵌的网页搜索 CLI 将真实数据烘焙进去，并标注其获取时间（见下文模式）。
- 任何需要 API 密钥、账户、服务器端缓存或定时刷新的功能：应使用 `web_fullstack`。

如果你正在构建静态页面，但数据确实需要服务器支持，请勿在浏览器中进行近似处理；应在构建完成后调用 `web_artifacts.exit_build`（状态为 `"failure"`），说明该内容需以服务器端方式构建，以便主代理能够按此方式重新构建。

## 在 web_fullstack 资产中：ctx 通道

在服务器动作中按以下顺序逐一尝试，选择首个适用的通道：

1. **`ctx.tool.finance_ticker(symbol, options?)`**：提供股票行情及历史价格数据。每次调用仅支持一个股票代码（“META GOOG”无效）；可通过 `Promise.all` 并发获取多个标的的价格信息。返回结果中的 `instrument` 包含价格、币种、涨跌幅、涨跌幅百分比、盘中高低点、52 周区间、市场状态及更新时间等字段；可通过设置 `interval: "1m" | "30m" | "1d" | "1w" | "1mo"` 获取 OHLCV 格式的 K 线数据（按时间倒序排列，最旧在前），用于绘制图表。根据用户请求的时间范围选择合适的间隔：若需展示当日/当前交易时段的行情，则使用 `1m`；若需粗略的多日分时行情，则使用 `30m`。这些是独立的上游数据序列：在交易日当天，`1m` 可能已包含当日的 K 线，而 `30m` 序列可能仍停留在前一交易日，尚未包含当日数据。切勿将 `30m` 视为 `1m` 的聚合，也勿自动切换时间间隔。
2. **`ctx.tool.sports_data(query)`**：提供赛事比分与赛程信息。每条记录包含对阵双方、比分、比赛状态（`closed` / `inprogress` / `scheduled`）以及 UTC 时间的开赛时间；球员与球队统计数据仅在上游提供时才会出现。
3. **`ctx.tool.weather(query, options?)`**：提供定位后的当前天气状况、每日预报、可选的逐小时预报及各类预警信息。当用户指定具体的逐小时预报范围时，将 `hourly_hours` 设置为请求的小时数（最大 48 小时）；两种 Web 资产运行时环境都会将其应用于上游的逐小时数据序列。
4. **`ctx.tool.web_search(query)`**：适用于其他一切场景。通常摘要片段即可满足需求；可将其通过 `ctx.inference.complete(prompt, { schema })` 进一步提炼为结构化数据行，而非直接打开网页。切勿仅为搜索而启动一个代理任务。
5. **直接使用 `fetch()` 调用公共 JSON API**：可在任意服务器动作中使用；运行时会通过平台出口代理转发请求，且简单的 GET 请求受资产可信读取权限覆盖，包括定时刷新机制。请在计划的 `data_plan.declared_hosts` 中声明所有将在运行时访问的主机地址，作为审计清单（若仅通过 `ctx.tool.web_search` 获取数据，则无需声明）。务必在构建测试阶段证明该接口针对特定查询、地区和日期能够返回有效数据；类型定义与文档本身并不足以证明这一点。
6. **`ctx.agent.spawnTask(message, { expectsAction })`**：用于需要多步骤操作的真实调研任务，启动一个具备浏览能力并可使用全部工具的独立研究代理。该方法会立即返回任务句柄，而非直接返回答案；被启动的代理将通过调用您指定的动作来交付结果。切勿让页面加载因此阻塞。

管理通道上的所有观测字段均允许为空，这是设计使然：上游服务可能省略部分价格、比分或预报信息。请优雅地降级显示，不要抛出异常，也不要使用虚构值进行替代。**打开时获取是默认的新鲜度模式。** 页面在加载时调用读取操作；该操作从 `ctx.db` 中提供最新缓存的行，并在缓存过期时从源中刷新。选择一个与业务领域相符的过期预算（例如：股市行情按分钟计，天气预报按小时计，时刻表按天计），并始终显示数据的“截至时间”。保持加载路径的高效：优先提供缓存，在后台或通过用户可见的刷新控件进行刷新；管理通道在操作自身的截止时间内默认设置为90秒超时。

**配置定时预取。** 在创建时，调度来自构建请求的“刷新触发器”。使用 `cron.add_artifact_action` 将构建阶段定义的每个任务按要求的调度和验证过的操作调用注册到调度系统中。将已安装的任务记录在 `space.json` 的 `managedCronJobs` 字段中，并通过 `cron.status` 进行确认。此操作会直接调用目标操作，成功时不产生任何反馈。如果用户希望每次刷新后都收到聊天通知，则应改用带有明确交付目标的代理调度。定时运行在相同的网页读取权限下无人值守地执行，每次最多触发一次。触发后，若发生超时、失败或中断，可能会留下已提交的效果，且不会自动重试。手动重试前请检查保存的状态；若在写入前发生崩溃，可能会导致某次运行未完成。

**缓存结构。** 按主题（股票代码、场馆、查询）存储快照，包含“截至时间”以及源端报告的任何状态（如“市场状态”、“进行中”）。读取时按键取最新一行；保留较短的保留窗口，其余部分定期清理，以确保表大小可控。

## 在 web_static 页面中：构建时固定的带日期快照

不要将静态页面配置为在打开时获取数据：页面中不得调用外部 API，不得轮询，更不能使用公开的 CORS 代理来访问那些阻止浏览器访问的源；所有打开时依赖的第三方服务都会被用户无意识地承担，而需要此类依赖的页面本质上属于本应由服务器支持却错误地构建为静态的类型。资产则不同：CDN 库、网页字体以及页面自身的图片均遵循站点的资产规则；这里的区别在于数据。静态页面真正携带的是一个真实的快照：

- 在构建时使用打包的 CLI 获取数据：运行 `/opt/hatch/bin/web-search "<query>" --out <file>` 并读取生成的文件；标准输出仅返回精简摘要，大型负载会在 shell 中被截断。这与全栈应用中的 `ctx.tool.web_search` 所使用的搜索引擎相同。在查询中加入所需的时间范围并核对来源日期；对于金融类查询可使用 `--verticals finance|sports|weather` 提供领域提示，每条金融查询只包含一个股票代码。每次调用仅搜索一个查询，如有其他问题需分别发起调用。
- 将 JSON 数据提炼为页面渲染的类型化常量，并保留原始来源名称。
- 将获取时间作为 `as_of` 嵌入并一同渲染，同时注明数据来源：页面呈现的是一个带日期的快照，这也是其契约。
- 当用户日后需要更新的数据时，只需普通编辑即可重新运行构建流程并重新生成。

CLI 是构建工具，绝非页面工具：它仅在构建过程中运行，最终生成的页面不得调用 CLI、引用其路径，也不得将其包装成页面可调用的虚构接口。页面仅渲染烘焙好的常量，除此之外不包含任何其他内容。

共享一份静态页面时，所传递的也是同一个带日期的快照；这正是共享机制所保证的内容。

## 不可协商的原则（两类）- **切勿模拟实时数据。** 禁止使用随机游走的价格动画，禁止将种子生成的数值伪造成当前行情，也禁止根据市场交易时段人为捏造价格波动。当数据源不可用时，应展示真实的错误信息，或标注 `as_of` 时间戳的过时缓存；与其呈现一个看似逼真的假象，不如坦诚地显示空状态。
- **会话相关的计算应由交易场所负责，而非由客户端处理。** 固定市场的交易时间和日度分段应以其所在时区为准（例如，美国市场使用 `America/New_York` 时区，并通过 `Intl.DateTimeFormat` 进行转换），而绝不能仅依赖本地时钟。
