# 幻灯片演示文稿编辑

如何在不从头重建的情况下，就地修改用户已有的演示文稿。您将获得该演示文稿的`<artifact-slug>`和变更请求；请在您的构建任务命名的`project_dir`中直接操作现有演示文稿。对于普通演示文稿，该目录为`~/workspace/your_files/<artifact-slug>/`；对于目标文档，则是目标自身的`files/`目录。

## 始终先加载

演示文稿的源文件按每张幻灯片存放在`.src/slides/`下（参见`workflow.md`第5步）。仅读取变更所需的内容：
- `.src/slides/deck.json`：演示文稿的幻灯片顺序。务必先读取此文件——它会告诉您哪个文件对应哪张幻灯片。
- `.src/slides/deck.css`：主题（`:root`变量）及所有共享样式规则，以及位于文件末尾的主题`@font-face`规则（包含字体字节）。请编辑这些字体规则之前的样式，不要动字体本身。
- `.src/slides/<id>.html`：仅需编辑即将更改的幻灯片。每张幻灯片内包含一个`<section class="slide">`，其图片以`data:` URI形式嵌入。
- `.src/deck_plan.md`：标题、受众、叙事结构及幻灯片列表。
- `.src/style_plan.json`：原型、配色方案、字体、每张幻灯片的`layout_plan`以及徽标布局。
- `meta.json`：演示文稿的标题及其被推广到的确切输出格式集合。

对于具有每张幻灯片独立源文件的演示文稿，请**不要**读取或编辑`.src/index.html`。该文件由上述文件组装而成，因此若读取并修改它，仅更改一张幻灯片就需要加载整个演示文稿的字节，且后续的组装步骤会丢弃该处的修改。（旧版演示文稿没有每张幻灯片的独立源文件，其`index.html`是幻灯片的唯一副本；下面的重建过程会特意读取它。）

**如果演示文稿没有`.src/slides/`，或者其`.src/slides/`因某种与您的变更无关的原因无法正常组装**（最常见的情况是某张幻灯片的`<section>` ID与其清单中的ID不匹配，这可能是旧版拆分工具造成的），则不存在可就地编辑的每张幻灯片源文件：在这种情况下，应按照`workflow.md`以当前格式重建演示文稿，保留原slug，并沿用项目原有的素材，使其仍被视为同一份演示文稿（使用`deck_plan.md`确定叙事结构和幻灯片列表，使用`style_plan.json`保持主题和布局不变，保留`.src/media/`中的图像素材，并使用旧版`index.html`作为每张幻灯片的内容）。在重建过程中应用所请求的变更，并说明该演示文稿已被重建，因为这相当于重新创作了用户未要求更改的幻灯片。以下内容仅适用于拥有每张幻灯片独立源文件的演示文稿。

在处理变更时，切勿根据简报从零开始创作一份新演示文稿；应直接对现有演示文稿进行修改。当您重写或新增幻灯片内容时，应严格按照`authoring.md`和`design-system.md`（布局类、徽标网格、字体比例）的要求进行创作，就像全新构建一样，以确保与周围演示文稿风格一致。

## 按意图应用变更

- **更改或重新调整幻灯片**（“把第3张幻灯片改成X”，“修改最后一张”）：通过`deck.json`的顺序将幻灯片编号解析为ID（第1张=第一条），然后仅编辑该`<id>.html`。不要动其他任何幻灯片文件，也别改动`deck.json`。
- **缩减**（“删到5张”，“更紧凑”）：缩减就是删除幻灯片——保留最有力的要点和叙事主线，舍弃最弱的整张幻灯片，让保留下来的幻灯片内容和现有图像完全不变（复用其已有媒体；不要重新生成、重新获取来源或重新确定风格方案）。从`deck.json`中移除被删幻灯片的条目，并删除其`<id>.html`；保留幻灯片的文件名和ID不变。绝不能为了凑数而编造填充内容。只有当用户同时要求“更精炼”时，才重写幻灯片的文字。
- **扩展或新增**（“加一张关于X的幻灯片”）：编写一个新的`<id>.html`，复用整个PPT现有的版式和视觉元素——为其指定一个同类型兄弟幻灯片已使用的版式——并在`deck.json`中按应有位置插入其条目。根据`workflow.md`第5步，为它取一个简短且稳定的、以连字符分隔的小写`id`，代表其主题；所有现有幻灯片的`id`和文件名都保持原样：这些ID在PPT的生命周期内始终标识对应幻灯片，因此绝不要因新位置而重新编号。
不要重新运行样式CLI来应用新幻灯片；那样会重新确定整个主题，导致当前主题发生偏移。仅当图片能有效说明新幻灯片的内容时，才按照`image-directive.md`和`authoring.md`的克制原则添加图像；表格、数据或对比类幻灯片应保持无图状态。
- **重新定调**（“变得更暗”，“更简约”，“换种风格”）：通过`visual.md`为新方向确定一份新的`StylePlan`。严格按此方案，在`deck.css`内完整应用——替换`:root`中的CSS变量为新方案的值——并覆盖`.src/style_plan.json`，使保存的方案与`:root`块保持一致。不要手动调整字体。`:root`中的变量已指定了新字体系列，第7步的嵌入会自动替换旧主题的字体文件。`deck.css`末尾的`@font-face`块必须原封不动，绝不手写新的字体URL。切勿自行挑选颜色或字体；色板应完全遵从已确定的方案。保持每张幻灯片的内容和版式不变，因此幻灯片文件无需修改。PPT中的照片是按旧色板进行过后期处理的（见`image-directive.md`），所以仅改变明暗而不调整色调会导致带图幻灯片看起来不协调。如果封面主图是**生成的**，则需按新色板重新生成，并将其重新嵌入到该幻灯片文件中；如果是**外采的真实图片**（来自图像搜索技能的logo或照片），则绝不再次生成：保留原图及其基于该图采样的每张幻灯片的`--hero-scrim-color`（见`design-system.md`），仅根据已确定的方案调整周围的`:root`色板。告知用户其他照片仍保留原有色调（可主动提出重新生成那些由AI生成的照片）。
- **其他操作**（重新排序、更换某张图片、调整尺寸）：只做必要的最小改动，其余部分保持原样。重新排序即移动`deck.json`中的条目，所有幻灯片文件均不变。更换图片则是通过图像搜索技能重新获取真实素材，或按`image-directive.md`重新生成概念图，然后将其`data:` URI重新嵌入到该幻灯片文件中。宽高比的调整是全局性的：更新`deck.css`中的`@page`和`.slide`，随后重新执行溢出检查。

## 除非明确要求，否则保持原有主题
对于内容类编辑（更改、缩减、新增），**不要**重新确定样式方案或修改`:root`块：保持PPT现有的色板和字体。只有在明确要求重新定调时才变更主题。对内容编辑进行静默的风格调整属于程序错误。
  
## 重新组装、重新验证并重新导出**先重新组装**（`workflow.md` 第7步）。你的编辑改变了卡片包的源文件，因此在 `assemble_deck.mjs` 运行之前，`.src/index.html` 是过时的，而下面的所有内容都会读取该文件：

```sh
SLUG="<artifact-slug>"
# `project_dir` 来自你的构建任务。目标文档会构建到该目标的 `files/` 目录下，因此硬编码的 `your_files` 路径是错误的。
# `project_dir` 来自你的构建任务。将其开头的 `~/` 写成 `$JARVIS_HOME/`：在引号内，Shell 会保留波浪号字面量，因此 `"~/workspace/..."` 会被解析为一个名为 `~` 的目录。
SRC="$JARVIS_HOME/<来自构建任务的项目目录，去掉开头的 ~/>/.src"
bun run "/opt/hatch/skills/artifacts/scripts/embed_deck_fonts.mjs" --slides "$SRC/slides"
bun run "/opt/hatch/skills/artifacts/scripts/assemble_deck.mjs" \
  --slides "$SRC/slides" \
  --out "$SRC/index.html"
```

嵌入步骤在牌组的字体或字符未发生变化时不会执行任何操作，因此在内容编辑时开销很低，这也是重新应用主题时用于重新设置字体的操作。

然后，按照全新构建的方式，完整地运行 `workflow.md` 验证循环（步骤 8-9）——以渲染报告（`ok`、`fonts.missing`、`overflow`）为门控条件，读取所有 `.src/validate` 格式的 PNG 图片，最多进行 3 次迭代；不要将其简化为单次通过（重新换主题会更换字体，因此 `fonts.missing` 很重要）。在此处的每次编辑中，包括重新换主题时，都从步骤 8 的命令中去掉 `--require-restraint`：探测器会读取每一张幻灯片，包括本次编辑必须保留不变的那些。仅在您实际编辑过的幻灯片上修正排版、大写字母和字距。同时去掉 `--require-generated-imagery`，除非本次编辑确实重新生成了图像：对于原本就已有的素材或仅包含图表的演示文稿，不存在能满足该要求的配套文件，因此保留此标志会使已完成的编辑失去合法的操作空间。`workflow.md` 中已明确这一规则。只有当您确实看到这些样式存在于未动过的幻灯片上时，才提及它们；在门控条件下构建的演示文稿本身并不包含这些样式。每次迭代都会先编辑幻灯片源文件并重新组装，然后再重新渲染。接着，仅按 `workflow.md` 的推广步骤（步骤 10）导出演示文稿已有的格式（来自 `meta.json` 中的 `outputs` 字段），而不是硬编码的 PPTX，并按步骤 11 重新计算 `meta.json`。在进行结构性编辑（删减或新增）后，还需将 `deck_plan.md` 中的幻灯片列表以及 `style_plan.json` 中的布局方案条目同步到最终的演示文稿——仅更新元数据，保持配色和字体不变。演示文稿的 slug 和链接保持不变。
