# FlightAware 技能优化——结果

FlightAware 技能的优化循环逐轮记录，依据 `trim-skill` 流程。每轮一张表，每个场景一行。随着 `/hatch-swarm` 对候选 `SKILL.md` 的扫描运行，逐步填写。

失败类型：`[Agent] 触发`, `[Agent] 行话`, `[Agent] 错误`, `[Agent] 无效调用`, `[Infra] 模拟偏差`。

## 如何运行一轮

1. 对 swarm 客户端进行一次身份验证（浏览器 OAuth）：  
   `uv run --script jarvis/.claude/skills/hatch-swarm/scripts/hatch-swarm.py auth`
2. 对于 `scenarios.yaml` 中的每个场景，启动约 10 次运行，并通过预置步骤覆盖虚拟机中自带的技能文件（详见 `../../spawn-eval-instructions.md` 中关于 `/opt/hatch/skills/flightaware/SKILL.md` 的 `sudo tee` 操作）。若未执行预置步骤，则测试的是默认技能，而非当前候选版本。
3. 将所有场景汇总为一个命名扫描，然后执行 `scans watch`。
4. 对于每次运行，读取轨迹数据（`runs tools <id>`）以及 artifacts 中的会话思考内容；按类型在下方记录失败情况。
5. 修复 `SKILL.md` 中的 `[Agent]` 类型失败，修复场景中的 `[Infra]` 类型失败。循环迭代，直至连续两轮无故障。

## 通过烟雾测试发现的阻塞问题（2026-08-06）——代理路由不匹配（405）

两次单次运行的烟雾测试（非完整一轮）验证了整个流程的端到端正确性（认证 → 预置步骤覆盖技能 → 启动 → 监控 → 解码轨迹），并暴露出一个必须在正式评分前解决的严重 **基础设施** 阻塞：

- 在当前 nightly 镜像上，所有 FlightAware 数据请求均返回  
  `broker_error:true status:405 "POST is not allowed for /hatch/flightaware/proxy-request"`。  
  （运行 f9ed2177 的 `runs tools` 轨迹；烟雾扫描 1f7a9d04。）
- 根本原因（已证实，跨仓库路径契约不一致）：
  - hatch-extensions #1107 (`9650a85b`) 将 `flightaware` CLI 迁移到使用 POST 请求轻量透传的 `/hatch/flightaware/proxy-request`。
  - Jarvis **主分支** 将 hatch-extensions 固定在 `ad91a4da`，该版本已包含 #1107，因此默认 CLI 发送的是 `/proxy-request` 请求；但 Jarvis 主分支的 stefi-proxy 仍仅路由旧的 `/hatch/flightaware/query`  
    （upstream_routing.rs:55, path_policy.rs:463）。导致每次调用都返回 405 错误。
- 计划修复方案是 Jarvis #15537（aniketdas-meta）“将 FlightAware 切换至透传路由并重新固定”，但该修复无法作为覆盖层安装：其分支落后主分支 74 次提交，因此租用 VM 的 Postgres 启动预置步骤会因 `migration 179 已应用但缺失` 而拒绝（镜像 schema 最大为 184，而 PR 为 178）。覆盖尝试失败于运行 d7e899d3 的 `spawn_preflight` 阶段（并非技能问题）。
- 基于主分支的最小修复方案（3 处修改，扩展包的重新固定已由主分支满足）：
  - upstream_routing.rs: 将 `/hatch/flightaware/query` 改为 `/hatch/flightaware/proxy-request`
  - path_policy.rs: 将 `/hatch/flightaware/query` 改为 `/hatch/flightaware/proxy-request`
  - privsep_registry.rs: 注释中将 `/query` 改为 `/proxy-request`（仅为格式调整，保持同步）
  确保基于当前主分支，使迁移版本 ≥184，从而允许覆盖层安装；随后以 `spawn --pr <该 PR>` 方式运行本轮。
- 已部署修复：Jarvis PR #15913  
  “fix(stefi-proxy): 将 FlightAware 路由至透传代理”  
  （分支 navi/fix/flightaware-proxy-route，基于当前主分支）。本地构建通过（fmt/clippy -D 警告/36 个测试）。下文的正式评分轮次即以 `spawn --pr 15913` 运行，确保租用 VM 能够路由至 `/proxy-request` 并访问实时 AeroAPI。

在路由问题修复之前，10 个阅读场景无法进行行为评分（代理收到 405 错误后会自行编造、回退或漂移——观察到运行 f9ed2177 中出现漂向 Duffel 和网页搜索的现象）。经烟雾测试，优化后的技能在状态与写入边界上的表现看似正常，但尚未进入正式评分环节。

## 第一轮（扫描 flightaware-trim-r1-pr15913，所有运行均使用 `--pr 15913`）扫描 `11dc0975-afe1-447b-97f3-2a4d1106fa59`，35个成员已落地（启动器在达到35并发上限后停止，未能发出最后一个“无预订”+1的“航班意图”请求；其中34个成功，1个因“数据受限”而未能租用虚拟机）。评分基于解码后的虚拟机轨迹数据（通过curl获取的构件包 → `trajectories-bytes/.../sessions/*.jsonl`）。

**环境限制（主导本轮测试）：** 托管的Swarm虚拟机不具备代理直通端点所强制要求的`hatch_nav_caller`身份，因此每次尝试调用FlightAware代理都会返回`401 “仅限特定用户”`。这与阻止Duffel、OpenTable和Turo在这些虚拟机上运行的正是同一道权限检查，并非技能或路由问题。最终结果是：`--pr 15913`修复了路由层面的`405`错误回归（35次运行中无一出现`405`，而修复前每次调用都会遇到），但由于`401`的存在，Swarm虚拟机上仍无法完成实时AeroAPI读取。因此，读取类场景主要验证的是技能的**Web回退机制及不伪造行为**，而非实时数据的格式化处理。

**总计：** 35次评分 · **405：0** · 401：29 · Web回退：33 · 成功代理调用：0 · 虚拟机故障：1。

### 发现
- `[基础设施] 环境401`（阻止Swarm虚拟机上的实时读取）：由`hatch_nav_caller`的授权门控所致。此问题无法在技能层面修复，需使用已配置导航调用者身份的Swarm虚拟机（或在代理端设置测试白名单）才能评估实时数据行为。PR [#15913](https://github.com/par-msl/jarvis/pull/15913) 已修复路由层的`405`问题，而401则是更底层的问题。
- `[话术] 术语泄漏`（发生于`status`场景，运行ID为6723c493）：在401环境下，话术曾向用户提示“仅限特定用户，401……我的直接FlightAware数据流在后端被拦截”，泄露了原始状态码，违反了“不得向用户展示命令、ID、令牌或原始状态码”的规则。该情况仅在环境401下触发（一旦代理放行即不会出现），但可进一步强化话术，将所有代理报错统一翻译为通俗语言。
- 数据受限：话术正确地**拒绝伪造**私人飞机位置，并清晰解释了受限原因——表现良好。
- Web回退（行李费）：话术正确地使用了网页搜索，**未强行**发起FlightAware指令——表现良好。

_总结：本轮测试验证了路由修复及回退/边界行为的有效性。若要进行包含实时数据的评分（所有读取均返回真实的AeroAPI数据），仍需使用满足代理导航调用者权限要求的Swarm虚拟机；请在该环境下重新运行并加上`--pr 15913`参数，同时补全“无预订”以及缺失的“航班意图”场景。_
