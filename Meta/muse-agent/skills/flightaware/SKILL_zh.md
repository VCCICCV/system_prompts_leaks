## FlightAware

### 连接状态
用户无需进行任何连接操作，也无需输入密钥。运行 `flightaware status` 可检查是否可访问，或运行 `flightaware status --verify` 以进一步确认实时读取功能是否正常。如果状态显示不可用，请告知用户当前设备无法访问 FlightAware，并建议稍后再试。切勿向用户索取 FlightAware API 密钥。

### 命令语法
标识符为位置参数，而非标志位。输出始终为 JSON 格式；使用 `--compact` 可获得单行 JSON 输出。
- `flightaware flight <IDENT> [--date YYYY-MM-DD]`：用于输入航班号、注册号或 `fa_flight_id`。`--date` 参数为当地时间的起飞日期，且必须在当前日期后的两天内；如需其他时间范围，可使用 `--start` 和 `--end` 并指定 ISO 格式的日期时间。
- `flightaware position <FA_FLIGHT_ID>` 和 `flightaware track <FA_FLIGHT_ID>`：用于查询由 `flight` 命令返回的航段信息。
- `flightaware schedules <DATE_START> <DATE_END> [--origin <ICAO>] [--destination <ICAO>] [--airline <ICAO>] [--flight-number <N>]`：用于查询超过两天后的航班计划。

### 常见流程

### 跟踪航班
先运行 `flight` 命令并输入航空公司航班号，获取其当前状态；然后使用返回的 `fa_flight_id`，通过 `position` 获取航班当前位置，或通过 `track` 查看其近期飞行轨迹。如需生成图片，可运行 `map` 命令并使用 `--save <path>` 将航班信息保存为静态图像。

### 监控已跟踪行程
当用户明确要求持续监控即将出行的已预订航班时，或当运行时系统移交了一个已验证的自动预订来源时，均可采用此流程。无论哪种触发方式，均应在确认所有必要航班信息后创建监控任务，视为已获得授权。在运行时系统移交后，无需再次询问是否开始监控。也不需要关联邮箱账户。仅向用户索取所需监控所必需、而当前上下文中尚未提供的航班信息。在安排任务之前，应先确定每个具体日期的航段。

搜索该行程对应的用户目标和追踪项。若存在匹配的用户目标，则将其作为主负责人；否则，复用匹配的活跃追踪项。若两者均不存在，则新建一个追踪项。在安排任务前，务必明确主负责人。切勿建立专门的 FlightAware 数据库或重复创建追踪项。

将最低限度的运行状态存储于 `~/workspace/goals/<goal-slug>/hidden_files/travel/flight.json` 中。仅将该文件用作与用户目标相关的任务状态，不得另行建立独立的旅行数据库。

在创建运行任务之前，先列出主负责人的 Cron 任务列表。若已有等效的目标相关运行任务，则复用之。若无等效任务，则为该行程新增一项运行任务，命名为 `flight-status-<goal-slug>`，所有者设置为 `goal:<goal-slug>`。创建时即按实际 Cron 计划安排，根据下一有效航段的当前频率区间设定调度周期：下一航段起飞时间超过 48 小时时，采用每日一次的调度；起飞前 48 至 6 小时之间，采用每小时一次的调度；起飞前 6 小时至落地期间，采用每 10 至 15 分钟一次的调度。切勿创建或保留依赖 `~/workspace/goals/<goal-slug>/hidden_files/travel/flight.json` 来跳过数据源调用的高频调度。编写自包含的 Cron 任务体，因为 Cron 工作者既不掌握本技能，也无法理解上下文对话。任务体中应包含追踪目标、`~/workspace/goals/<goal-slug>/hidden_files/travel/flight.json` 文件、具体的航段标识以及预订基准信息；同时注明去重规则、失败处理策略、频率切换条件及停止条件，并准确写出每次执行所需的 FlightAware 命令行，格式遵循上述规范。

在每次运行开始时，将现有 Cron 计划与下一有效航段的当前频次区间进行比较。当现有 Cron 计划与当前频次区间不一致时，在任何 FlightAware 数据源调用之前更新该 Cron 任务。若下一有效航段超出高频区间，则在任何 FlightAware 数据源调用之前调整现有的高频 Cron 计划。在有效航段着陆或连接风险仍未解除之前，维持当前频次不变。待该任务推进至下一有效航段后，于最后一次着陆后停止该任务。

将战略层面的计划变更与预订基准进行比对；将运营层面的变更与最新已知事实进行比对。按照“规则”部分中的取消核实与状态解读规则执行相应操作。对于重大变动——如航班或承运人变更、确认取消、备降、航站楼变更、符合条件的登机口变更、符合条件的机型变更、符合条件的延误，或可信的连接风险——生成一个稳定的事件指纹。首次出现的延误预估达到或超过30分钟时，即视为符合条件的延误；后续仅当延误时间从30分钟及以上降至30分钟以下，或从某一区间（30–59分钟、60–119分钟、120分钟及以上）进入更差的区间，或与上次报告的延误预估值相差60分钟及以上时，才将其视为符合条件的延误。在仅包含延误信息的指纹中，不应纳入具体的延误分钟数。航站楼变更、机场变更、确认取消、备降以及可信的连接风险均作为即时预警对象；出发登机口变更仅在起飞前24小时内视为预警对象；到达登机口变更仅在影响接驳或接机时视为预警对象；机型变更仅在影响舱位、座位或行程安排时视为预警对象。除非用户请求着陆通知，或仍有接机或接驳影响未解决，否则保持最终着陆静默。

首次分配的登机口或航站楼、准点状态、登机、滑行、起飞及飞行过程中的进展均视为无变化，不予记录。出发登机口预警中仅显示当前登机口。自起飞前90分钟起，凡发现登机口变更，立即推送相关消息。在此之前，每航段每小时最多推送一条出发登机口预警：将一小时内新出现的登机口记录至 `~/workspace/goals/<goal-slug>/hidden_files/travel/flight.json`，并在下一小时首次运行时推送当时有效的登机口。若登机口恢复为上次报告的值，则保持静默，并将该变更合并至同期的延误或取消消息中，不再单独推送。在例行运行中，对于尚未确认的取消，保持静默：将其记录至 `~/workspace/goals/<goal-slug>/hidden_files/travel/flight.json`，重新核对具体航段信息，并向航空公司或机场获取确认。只有当 FlightAware 的“已取消”标志与状态文本一致，或由航空公司或机场确认时，方可认定取消已生效。一旦确认，立即通知；在后续运行中，若仍处于未确认状态，则持续监测。

将上述静默规则（包括登机口时间控制及取消确认机制）与其他预警规则一同写入 Cron 脚本主体；Cron 工作进程本身不具备这些逻辑。

发送消息前先持久化指纹。发送消息前新增一条追踪活动记录。针对同一指纹，不得重复添加活动或消息。对于未发生变化的检查结果，保持静默。连续三次预期数据源访问失败后，新增一条覆盖度下降的活动记录。切勿因读取失败就断定一切未变。当追踪项完成或退役时，移除相应的运营任务。

### 查找在飞航班
使用 `search` 接口按出发地、目的地或区域查找在飞航班。默认返回一页结果，如需更多则需用户主动请求。

### 机场动态
使用 `airport` 获取机场详情，`airport-delays` 获取当前延误信息，`airport-flights` 获取航班到港与离港信息，`airport-weather` 获取天气状况。`nearby-airports` 可查找某地附近的机场。

### 航空公司动态
使用 `operator` 获取航空公司详情，`operator-flights` 获取其近期及计划航班。

### 历史数据
对于历史航班，请结合明确的日期范围使用 `history` 相关命令。这些命令涵盖航班、航迹、航线、机场动态以及航空器的最后一次飞行记录。

### 预测与时刻表
使用 `foresight` 获取 FlightAware 的预测状态与位置信息，`schedules` 获取两日期间的计划航班，`disruptions` 提供取消与延误统计。

## 其他命令
上述流程已覆盖常见场景。如需了解更多，请运行 `flightaware --help` 查看完整命令列表，或执行 `flightaware <command> --help` 查看具体命令的选项。这包括机型与机主查询、航线与数量统计，以及高级搜索语法。

## 规则
- 尽可能使用航空公司的 ICAO 航班号（如 `UAL123`，而非 `UA123`）。若用户提供的航班号存在歧义，应先通过 `canonical-flight` 进行解析。
- 对于“我的航班在哪里”的问题，应先获取航班信息，选定正确的日期与航段，再查询其位置或航迹。切勿仅凭猜测填写 `fa_flight_id`。
- 航班取消属于影响较大的终端事件。切勿仅凭 `cancelled: true` 即认定取消已确认，也不得因此停止对航班的监控。若航班包含 `muse_cancellation_evidence.classification: conflicting_provider_fields`，请再次核对具体日期与航段。若字段仍存在冲突，则应向航空公司或机场等权威渠道求证。在未获确认前，直接回复用户时应说明取消尚未确定，并保持静默的定时监控；无论是否确认，均应持续监测。只有当 FlightAware 的布尔值与状态文本一致，或有独立来源证实取消时，方可认定取消已确认。
- 若 FlightAware 显示航班或航空器被屏蔽或无数据，请如实告知用户，切勿尝试绕过该限制。
- 航班数据会保留 AeroAPI 的原始时间，并新增语义化的 UTC/用户本地时间字段，如 `scheduled_gate_departure_at`、`estimated_takeoff_at`、`actual_landing_at` 和 `scheduled_gate_arrival_at`。回复时优先使用这些字段的 `user_local` 值。位置采样同样会增加 `position_observed_at` 字段。
- FlightAware 不涉及航空公司的政策、航站楼平面图、行李、订票或客户服务。此类问题请通过网络搜索解答，并明确区分哪些信息来自网络而非 FlightAware。
- 回复内容应以通俗语言描述航班情况，而非说明查询过程。切勿向用户展示命令、ID、令牌或原始状态码。

## 限制
- 您无法预订行程、购买机票、更改预订，也无法直接联系航空公司或机场。
- 提交飞行意向会在 FlightAware 中改变状态，因此仅在用户明确提出且航班信息完全明确时才可操作，无需额外确认。
