# HealthEx（OAuth + MCP 健康记录）

## 用途
通过 HealthEx 的 MCP 服务器查询患者的健康记录。支持病症、用药、过敏、检验结果、生命体征、免疫接种、诊疗操作、就诊记录、临床笔记及健康摘要。

在以下情况下激活此技能：
- 用户询问其医疗数据、处方、检验结果、诊断或健康史时
- 回答若结合用户的健康背景会更有帮助时，例如饮食或膳食计划、锻炼计划、体能评估、旅行健康需求、医生就诊准备，或睡眠/压力管理优化

## 工具使用
调用方式：
```sh
$JARVIS_BIN_DIR/healthex <子命令>
```

子命令：
- `status` — 检查连接器状态（`connected`、`available` 或 `unknown`）。JSON 输出：`{ ok, provider, status, config_path, reason }`。
- `setup` — 写入启用 PKCE 的 OAuth 默认配置。JSON 输出：`{ ok, provider, status, config_path }`。
- `disconnect` — 删除已存储的 OAuth 凭证和令牌。JSON 输出：`{ ok, action, config_path, removed }`。
- `authorize-url [--state <state>]` — 生成 PKCE 授权 URL。JSON 输出：`{ ok, authorize_url, connect_url, state }`。将 `connect_url` 提供给用户（提供商的 `authorize_url` 用于服务端解析）。
- `refresh` — 刷新访问令牌（公共客户端）。JSON 输出：`{ ok, provider, status, config_path }`。通常无需直接调用——`mcp-call` 在收到 401 错误时会自动刷新。
- `mcp-list` — 列出可用的 MCP 工具。JSON 输出：`{ ok, result }`，其中 `result` 包含工具数组。
- `mcp-call --tool <name> [--args '<json>']` — 调用某个 MCP 工具。JSON 输出：`{ ok, result }`。收到 401 错误时会自动刷新令牌。

## 连接安全机制
在任何 HealthEx 数据访问之前：
1. 执行 `healthex status`。
2. 若状态为 `connected`，则继续进行数据访问。
3. 执行 `healthex authorize-url` 以生成链接。当出现 `connect_url` 时，将 `<connect_url>` 替换为返回的 URL，并展示一条包含 Markdown 链接 `[Connect HealthEx](<connect_url>)` 的消息（切勿单独粘贴原始 URL），随后附上以下同意说明：
   - 正在连接的服务：**HealthEx**——一项汇总您各医疗机构健康记录的服务
   - 授予的权限：对病症、用药、过敏、检验结果、生命体征、免疫接种、诊疗操作、就诊记录及临床笔记的**只读**访问权限
   - 有效期：该权限将持续有效，直至您在 HealthEx 账户中撤销
   - 数据用途：连接 HealthEx 后可获得个性化健康指导，例如解读检验结果、准备医生问诊、理解药物信息等，所有建议均基于您的实际健康数据
4. 回调完成后，再次执行 `healthex status`，仅当状态为 `connected` 时方可继续。

## 数据获取策略

先从整体入手，再根据用户问题逐步深入。

**步骤 1 — 概览：** 使用各分类工具（`get_conditions`、`get_medications`、`get_vitals`、`get_allergies`、`get_labs` 等）提取与问题相关的类别数据。这些工具的数据获取较为稳定可靠。`get_health_summary` 是一个便捷的汇总工具，但速度相对较慢且经常被置于后台处理（详见下文“处理缓慢或后台运行的调用”部分）；请勿将其作为唯一的上下文来源。仅当用户明确要求获取单一的整体摘要时才使用它，并且务必同时配合各分类工具一起使用。

**步骤 2 — 定向提取：** 根据问题类型，提取相应的详细信息：

| 用户意图 | 主要工具 | 次要工具 |
|---|---|---|
| “我的健康概览是什么？” | `get_conditions`、`get_medications`、`get_labs`、`get_vitals` | `get_health_summary`（可选） |
| 症状或“我是否需要看医生？” | `get_conditions`、`get_medications`、`get_vitals` | `get_labs`、`get_visits` |
| 实验室检查结果/血检报告 | `get_labs` | `get_conditions`（用于提供背景信息） |
| 用药相关问题 | `get_medications` | `get_conditions`、`get_allergies` |
| 饮食或膳食计划 | `get_conditions`、`get_medications`、`get_allergies`、`get_labs` | — |
| 锻炼或健身计划 | `get_conditions`、`get_vitals`、`get_medications` | `get_labs` |
| 就医准备 | `get_labs`、`get_medications`、`get_vitals`、`get_conditions` | `get_visits`、`get_immunizations` |
| 旅行健康 | `get_immunizations`、`get_medications`、`get_conditions` | `get_allergies` |
| “我的各项筛查是否按时完成？” | `get_labs`、`get_immunizations`、`get_visits` | `get_procedures` |

**步骤3——如有需要，运行`mcp-list`。** 如果您需要使用上表未列出的工具，或想查看参数结构，请运行`healthex mcp-list`，以获取所有可用工具及其参数。

## 临床洞察模式

在呈现健康数据时，不应仅限于原始数据，还应运用以下模式，提炼出可操作的建议：

### 1. 医疗服务缺口识别
获取数据后，检查是否存在过期或缺失的医疗服务：
- **实验室检查过期：** 标记所有超过12个月的关键实验室检查。常见缺口包括：糖化血红蛋白（针对代谢性疾病）、血脂谱、甲状腺功能检测、全血细胞计数等。示例：“您的上次糖化血红蛋白检测是在2019年5月，距今已超过6年。根据您的多囊卵巢综合征诊断，通常建议定期监测糖化血红蛋白。”
- **就诊时间间隔过长：** 若最近一次就诊距今超过12个月，予以提示。示例：“我未见您在过去3年内进行过全科医生的常规体检，建议安排一次例行检查。”
- **疫苗接种缺口：** 检查与年龄相符的疫苗接种情况，标记缺失或过期的疫苗（如流感疫苗超过1年未接种、破伤风类毒素疫苗超过10年未接种）。
- **筛查项目缺失：** 根据年龄、性别及疾病状况，标记遗漏的筛查项目（如乳腺X线摄影、结肠镜检查、糖尿病患者的眼科检查等）。

### 2. 疾病—用药—实验室检查交叉比对
将不同类型的数据关联起来：
- **有疾病但未开具相应药物：** 如高血压（血压升高）但未记录降压药。
- **有用药但未进行相应监测：** 如服用二甲双胍但近期无糖化血红蛋白检测，服用他汀类药物但近期无血脂检测。
- **实验室指标变化提示病情控制不佳：** 如空腹血糖持续偏高但尚未确诊糖尿病。
- **生命体征与治疗目标不符：** 如正在服用降压药但血压仍为149/70 mmHg，可能需要调整用药方案。

### 3. 基于个体健康状况的指导建议
根据用户的实际健康状况量身定制建议：
- **饮食计划：** 考虑疾病状况（如多囊卵巢综合征需胰岛素敏感型饮食、高血压需低钠饮食）、过敏史（避免过敏原）以及用药情况（如服用二甲双胍需监测维生素B12水平，服用华法林需保持维生素K摄入稳定）。
- **运动计划：** 考虑心脏疾病（分级活动、心率区间）、肌肉骨骼问题，以及通过生命体征评估的当前体能水平。
- **就医准备：** 总结医生可能关注的重点内容：过期的实验室检查、未达标的生命体征、用药回顾、症状随访等。

### 4. 风险因素综合分析
当多个风险因素同时存在时，应突出其叠加效应：
- 示例：多囊卵巢综合征+血压升高+近期无血脂检测+3年内未进行全科医生就诊→心血管风险状况需引起重视。
- 注意措辞，避免过度惊慌，可表述为“这些方面值得与您的医生讨论”。

## 处理耗时较长或后台执行的调用
某些调用（尤其是`get_health_summary`）可能耗时较长，此时`exec`工具会将其置于后台运行，并返回进程句柄而非直接返回结果，例如：

```json
{ "sessionId": "proc_abc123", "status": "running" }
```这**不是**答案，且**不含任何健康数据**。如果看到 `"status": "running"`（或任何未完成结果的进程句柄）：
1. 在回答之前，请**轮询后台进程直至完成**——持续检查其状态，直到变为 `completed`，再读取其实际的 `stdout`。
2. 如果在合理等待后仍未完成，请**退而使用各分类工具**（如 `get_conditions`、`get_medications`、`get_labs`、`get_vitals` 等），这些工具能可靠地返回数据。
3. **切勿**将 `running` 状态或进程句柄当作用户的真实数据来处理，也**切勿**据此推断或编造任何数值。

## 无真实数据 → 绝不捏造（最高优先级的安全准则）
对于**未返回真实记录**的工具调用，**绝不能**以此为由自行编造数据。在内部测试中，最严重的失误是未能通过“不得产生有害错误信息”或“不得生成虚构的医疗事实”的要求，原因在于模型在**未返回任何真实数据**时，却输出了具体的临床内容（如检验值、生命体征、诊断、PET/CT 报告等）。对所有四种“无真实数据”的状态，均应采取相同处理方式：明确说明数据不可用，并给出切实可行的下一步建议。**切勿**以看似合理的数值、范围或解释来替代。

| 状态 | 工具返回的内容 | 必需回应 |
|---|---|---|
| **空** | 调用已完成，无记录 | “我未在系统中找到任何 [检验/药物/等] 记录。这些信息可能尚未录入您的签约医疗机构，或者存在于未与 HealthEx 关联的系统中。” |
| **占位符** | “正在检索记录 / 即将提供” | “您的记录仍在从签约机构同步中。请先尝试各分类工具获取已有的数据；若仍为空，请告知用户记录正在同步，并建议几分钟后再试。切勿基于该占位符作出回答，也不得擅自承诺重新尝试。” |
| **仍在处理** | 进程句柄，例如 `{ "sessionId": …, "status": "running" }` | 轮询至完成（参见“处理缓慢或后台运行的调用”），或退而使用各分类工具。切勿将该句柄视作数据。
| **失败/错误** | 工具报错、非零退出码、“未连接” | 报告调用失败，并建议重试或重新连接。切勿凭记忆或假设回答临床问题。

当确实返回了数据但较为稀疏时，应妥善处理：
- **单一数据源**：“这些数据来自 [机构名称]。其他机构的记录可能未包含在内。”
- **缺失类别**：承认数据缺失，并建议用户联系其医疗机构，或通过 HealthEx 接入更多医疗系统。

## 分页
MCP 响应可能仅返回部分数据。每次响应都应检查是否存在“分页信息”部分。其中的任一标记均不能表明患者记录已结束：
- “还有更多数据：是”——表示您请求的范围尚未完整返回。请使用响应中提供的 `beforeDate` 和 `years` 参数再次发起调用。
- “请求的 N 年窗口：已完全覆盖”——仅表示您所请求的范围已满足。随着逐页回溯，可用的年数会逐渐减少，因此每条查询链最终都会遇到这种情况。这并不意味着没有更早的数据。

**唯一能表明记录已结束的标志，是返回的某个时间窗口中确实没有任何记录。**接下来该怎么做，取决于用户提出了什么问题：
- **他们指定了时间范围**（“过去两年的化验结果”）：将该范围作为 `years` 参数传递，并分页查询，直到返回“已全部覆盖”，或直到已发出10次调用，以先到者为准。如果返回了“已全部覆盖”，则说明针对用户的问题已得到完整答复，应明确告知；如果先达到调用量上限，则按如下方式报告。
- **他们未指定时间范围**（“我有哪些疾病？”、“我曾经得过X吗？”）：持续使用更早的 `beforeDate` 和新的 `years` 预算进行调用，直到**连续两个时间窗口均无记录**，或已发出10次调用。这是停止查询的唯一两种原因。**一个空窗口并不意味着记录结束**——最近的窗口通常为空，且医疗空白很常见，因此遇到单个空窗口时仍需继续查询。不要因为出现“已全部覆盖”而停止，也不要因为已获取的数据看似足够而停止。

随后报告查询结果：
- **连续两个空窗口**——在此停止，并如实说明已查询的范围：“我已查询至<日期>，未发现<日期>之前的任何记录。”这可以作为记录可能已结束的有力证据，但并非确凿证明，因此不应将结果判定为完整。
- **因达到10次调用上限而停止**——应明确告知：“我已拉取至<日期>之前的记录；可能存在更早的记录，但我尚未获取。”并主动提出继续查询的可能性。切勿将结果称为“完整”“全部”或“所有在档信息”。

**若因达到上限或遇到可能代表医疗空白的空窗口而停止查询，且未穷尽全部记录，请勿将未获取的部分视作缺失。** 仅在这种情况下：不得声称某项诊断、药物或检查结果缺失，不得将其称为“文档空白”，也不得建议用户就此与医疗服务提供者沟通。对于已成功获取的记录，上述医疗空白检测规则仍应照常适用。

## 操作规范
1. 在访问任何数据之前，务必先完成连接保护机制。
2. 调用与问题相关的各分类工具；将 `get_health_summary` 视为可选且不可靠的工具（参见“处理缓慢或后台运行的调用”）。当需要更深入或特定类别的数据时，运行 `healthex mcp-list` 以确定合适的工具及其参数结构。
3. **绝不得陈述任何未在工具的完整输出中逐字出现的具体临床数值——如化验值、生命体征、药物、诊断、剂量或日期。** 如果调用返回空结果、显示“正在运行”的状态、占位符（“正在检索记录”）或发生失败/错误，请遵循“无真实数据→绝不编造”的原则：明确说明数据不可用，然后给出具体的下一步建议。绝不能用看似合理的数值、范围或推断来填补空白。当工具未返回真实数据时，绝不可凭记忆或假设回答临床问题。这是最高优先级的安全准则——编造医疗事实是本技能最严重的失效模式（“禁止有害虚假信息”/“禁止虚构医疗事实”）。
4. 绝不作出医学诊断、治疗建议或临床解读。应如实呈现数据，并建议用户咨询其医疗服务提供者。
5. 妥善处理MCP错误——若工具调用失败，应报告错误，并建议用户重试或检查其HealthEx账户。
6. 若在自动刷新后，`mcp-call` 返回401错误，则表示令牌已过期或被撤销。请重新执行连接保护机制。
7. 绝不打印 `access_token` 或 `refresh_token` 的值。
8. 健康数据属敏感信息，不得在当前请求之外存储或保留。
9. 在呈现分析结论时，务必注明来源：“根据您的HealthEx记录……”——切勿将推论当作既定的医学事实。
10. 对于任何提示存在医疗空白或风险的发现，均应附上用户可采取的具体后续步骤。
11. 记录读取会保留原始的临床时间戳，并在来源提供准确时间点时添加语义化的UTC时间和用户本地时间形式；仅包含日期的字段则保持为日期格式。
