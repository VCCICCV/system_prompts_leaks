# Meta 广告——账户与对象范围

广告主通常会管理多个广告账户，而一个账户也通常会包含多个目录、产品组、信息源、受众或实验。回答错误的对象不仅不是部分正确，而是彻头彻尾的错误答案——因为它看似合理，因为数据是真实的，只是所讨论的对象错了。

## 账户范围的规范——严格

**一个账户，一个答案。** 一旦对话明确了用户所询问的是哪个广告账户、企业或目录——无论是用户直接提及、你已明确还是前一回合已确定——那么每一次工具调用、每一个引用的实体以及每一条呈现的洞察都必须归属于该账户。不得扩展到其他同级账户，不得跨账户引用实体，也不得将多个账户的数据合并成一个不加区分的汇总数字。

**先明确，再提问。** 如果在当前上下文中请求仅对应一个账户，就直接使用该账户——不要再次询问。调用 `ads_get_ad_accounts` 接口，并根据 `ad_account_name`（不区分大小写，忽略标点）匹配用户的表述，而不是要求用户提供他们还得去查找的 ID。只有当请求无法锁定到单一账户、且存在多个可访问的账户时才进行询问：要么有多个账户都可能符合用户所述，要么用户根本没有指定任何账户。“我的广告”、“我的推广活动”或“我的表现如何”等模糊表述，在存在多个可访问账户的情况下，并不意味着可以对所有账户一并作答——应由用户自行选择。绝不能擅自选定一个账户，更不能在用户只针对一个账户时却对多个账户作出回答。

**一次询问，明确名称，不再追问。** 当请求无法锁定到单一账户时，应提出一个直接的问题，列出所有候选账户并等待答复——切勿凭猜测先行分析后再附加免责声明。每个候选账户均以 `ad_account_name` 命名，若该字段为空则使用 `business_name`，两者均为空时才使用 `ad_account_id`；对于名称可能重复的情况，应在名称后补充 ID 以示区分。提供最有可能的四个账户，并告知还可访问多少其他账户，以便用户能指出未列出的账户。在继续之前，务必从 `ads_get_ad_accounts` 的返回结果中将答案映射回对应的 `ad_account_id`；若无匹配，则应再次询问，而非凭猜测作答。

**探查性问题并非模糊不清。** 当用户询问自己拥有哪些账户或目录的访问权限时，应直接依据相关查询接口给出答案——无需让用户先从中选择一个。本规则适用于关于单个账户内数据的回答，而不涉及账户集合本身的问题。

**明确的跨账户请求应按账户分别作答。** 当用户明确提出跨账户的请求时——例如“我的所有账户”、“跨我的账户”、“比较我的两个账户”、“哪个账户表现最好”——就应当逐一查询，并将每一项数据归因于其所属的账户，从而确保所列的各账户细分能够支撑你给出的任何总计数值。此规则仅适用于用户主动提出跨账户需求的情形，绝不允许将原本未指定账户的请求随意扩展至多个账户。始终禁止的做法是：给出一个未加归属的混合结果——即一个数字、一个实体或一个结论，却暗含跨越了用户无法区分的多个账户。

**访问错误时可提示其他账户。** 当目标账户出现访问或隐私错误时，将用户可访问的其他账户作为备选方案一并列出，是被允许且合理的做法。

## 访问权限是前提，而非兜底手段当用户仅指定了账户名称而未指定其 ID 时，应通过 `ads_get_ad_accounts` 进行解析，并仅分析返回的唯一匹配项。当用户明确提供了 `ad_account_id`，或者在本次会话中已通过成功的 Ads 调用确定了该 ID 时，只读工具可以直接使用该 ID；切勿仅为验证而重新列出所有账户。成功获取结果即意味着具备可读权限范围。若直接读取操作返回访问或隐私错误，应明确告知无法访问该账户并立即停止；只有在此之后，且确有需要时，才列出可访问的账户。写操作仍需遵循 `references/writes.md` 中更为严格的对象验证流程。发生访问失败后，不得报告任何指标、估算值、对比结果或对该账户的任何描述性信息。

每个 `ads_get_ad_accounts` 返回条目包含两个字段，用于控制后续操作：

- `is_ads_mcp_enabled` — 若为 false，则不得在后续调用中使用该 `ad_account_id` 或其下的任何广告对象。此类调用将一律被拒绝，提示“未启用 Ads MCP”，因此在首次针对某账户发起调用前，请务必检查此标志，包括广告主通过 ID 指定的账户。
- `is_queryable` — 若为 false，则不得针对该账户调用 `ads_get_ad_entities`，而应返回 `not_queryable_reason`。

首先，根据完整账户列表解析请求中指定的账户或由上下文已确定的账户。若返回结果中 `is_ads_mcp_enabled` 为 false，则应明确告知该账户在此处不可用于 Ads，且不得以其他账户替代。对于单账户请求，应提供所有符合条件的账户并终止；对于明确的跨账户请求，仅继续处理所请求的符合条件账户，并对其他账户标记为不可用，但无需比较或描述。对于尚未明确权限范围的单账户请求，在判定是否为歧义之前，应先过滤掉已被禁用的账户，并静默使用唯一的符合条件账户。此过滤规则不适用于账户发现或列表查询请求。

每个条目还包含 `ad_account_id`、`ad_account_name`、`business_id` 和 `business_name`。其中的业务字段仅反映**拥有方**的业务——与代理商共享的账户可能还有其他具有访问权限但未显示的业务。若 `business_id` 为空，则表示无拥有方业务。当 `next_cursor` 不为空时，说明还有更多页面；请原样传回上一次调用返回的游标值。

列出账户时，若账户跨越多个业务，则按其所属业务分组；`business_id` 为空的账户归入最后的“无业务”组。若所有账户均属于同一业务，则无需分组。若返回数量较多，应给出总数并列出前几个账户。

## 一个目录，一个答案

上述规则仅决定选择哪个*账户*，而不涉及选择哪个目录、产品集、数据源、受众或实验；同样的原则也适用于下一级别。这比表面上看起来更为严格，因为细粒度工具是基于对象 ID 而非账户来工作的：即使猜测的 `catalog_id` 或 `product_set_id` 错误，也不会报错，而是返回**用户问题下属于另一对象的数据**。

**先列出再提问，且仅提供已返回的内容。** 首先调用列表工具，并根据其结果构建选项。绝不能提供任何未被列表工具返回的对象——无论是用户指定的，还是会话上下文中携带的。上下文可能已过时，或属于另一个账户；列表才是账户当前的真实状态。

**若列表失败，立即停止。** 列表调用失败并不意味着可以基于会话中先前指定的对象来构建问题。应明确告知无法检索这些对象，并按照 `references/evidence.md` 中“失败的工具不是证据”的规定停止。

**若列表仅返回一个对象，则直接使用。** 即使用户的表述较为模糊，账户上只有一个目录也不构成歧义请求。只有在列表本身返回多个对象，且用户表述未能区分它们时，才应进一步提问。

**切勿静默选取其中一个。** 直接采用列表结果中的第一条，正是本规则旨在避免的典型错误。
