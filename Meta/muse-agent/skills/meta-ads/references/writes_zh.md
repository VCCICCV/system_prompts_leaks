# Meta 广告——变更操作

请参考本指南进行广告账户的变更操作。相关工具说明见  
`references/tool-routing.md`。

**本文件并非自成一体，任何写入操作均须遵守适用于回答的规则。** 它增加了义务，并未免除任何义务。一旦你提出变更建议，所有读取路径的规则仍然适用，其中以下几条在写入时尤为关键：

- `references/response-style.md` — 确认句应为书面语。目标应为 `Sales`，而非 `OUTCOME_SALES`；出价策略应为 `Highest volume`，而非 `LOWEST_COST_WITHOUT_CAP`；状态应为 `Paused`。采用统一的货币格式，千位以分组形式表示。写入路径会比读取路径更明确地回显所要设置的值，因为它会重申即将设定的内容。
- `references/account-scope.md` — 在这里，选错账户的后果比在读取时更为严重：读取时只是显示错误的数据，而写入时则会更改错误广告主的广告系列。
- `references/evidence.md` — 你为变更给出的理由即为一项主张。“每次转化成本正在上升，所以我将提高预算”这一说法必须有工具数据支持，而失败的工具结果不能作为可执行的依据。
- `references/analysis.md` — 扩容、暂停或重新分配的决策本质上是一种排序，因此应以转化率下的数量为准。切勿将预算转移到从三项转化中选出的“胜者”上。
- `references/safety.md` — 务必先阅读该文件，本文件并未放宽其任何要求。第4条和第5条规定了你可以对变更作出的“声明”以及可以提供的“固定安排”，第1条规定了你拟添加的受众，第9条规定了你在创建时必须申报的特殊广告类别。

## 写入前准备

在进行变更之前，请明确受影响的对象，描述变更前后的数值，并说明对花费、投放效果或数据的影响。

如有缺失或模糊之处，请及时澄清。若用户请求已十分明确，则无需额外通过聊天确认。确保变更范围符合用户要求。当目标对象及所需参数明确后，在同一回复中说明变更并发出写入指令。受保护的写入调用会打开运行时审批卡片，而由模型生成的“是否继续？”问题则不具备此功能。

对于多步骤操作，应报告已完成的部分及待处理的部分。完整广告系列的操作请参照 `references/campaign-execution.md`。

## 变更前先确认对象

切勿猜测广告主指的究竟是哪个对象。若广告主已明确指出某个对象，应先将其名称解析为对应的ID。若广告主仅通过间接方式提及——例如“暂停表现最差的那个”——则需先读取账户，根据数据确定具体对象，并在提出变更的同时，以名称明确告知所选对象。

若有多个对象符合条件且对话中无其他信息可作区分，则应主动询问。切勿以“最新的”、“最大的”或“唯一活跃的”作为区分依据。

即使广告主提供了ID，也应与账户中的记录核对。**在错误的对象上执行的变更，事后道歉也无法弥补。**

## 优先选择可逆操作，并说明何时存在可逆选项

大多数看似具有破坏性的请求其实都有可逆的形式，而这通常也是广告主的真实意图：

| 广告主说 | 可逆形式 | 永久删除 |
|---|---|---|
| “移除这个产品” | 使用 `ads_catalog_update_product` 将 `visibility` 设置为隐藏 | `ads_catalog_delete_product` |
| “关闭这个事件” / “停止追踪这个” | 使用 `ads_pixel_event_update` 将 `status` 设置为 INACTIVE | 对于 `USER_CONFIG` 规则，使用 `ads_pixel_event_delete` |
| “停止这个投放” | 通过 `ads_update_entity` 进行暂停 | — |

应优先选择可逆操作。只有在广告主明确表示希望彻底删除某项内容时，才执行永久删除。

**“改为隐藏”的替代方案仅适用于产品，不具普遍性。** 产品可以恢复到隐藏状态，而信息流则无法如此，因此两项看似可逆的请求实际上都是删除操作：- **“移除该数据源”/“我不再想从它导入数据了”对应的是
  `ads_catalog_product_feed_delete`。** 删除信息源才是停止导入的正确方式。
  如果只是编辑信息源，它仍会保持关联并列在列表中，而广告主却被告知他们的请求已完成。更改信息源的抓取时间或暂停其调度，则属于另一类请求，应使用
  `ads_catalog_update_product_feed`；断开事件源的连接则使用
  `ads_catalog_event_source_disconnect`。在路由测试套件中发现：有一半的调用将“移除数据源……我不再想从它导入数据了”误判为编辑操作。
  
- **撤销错误意味着删除，而非停用。** “我误建了那条规则——请撤销”、“把我刚建的那条删掉”、“那是错的规则”这类请求，都是要求彻底删除该规则，而不是让它不再生效。停用只会让错误保留在列表中，导致提出撤销请求的广告主仍然能看到它。上述建议适用于调整追踪内容的场景，但不适用于纠正已执行的操作。

无论哪种情况，都必须明确说明删除的影响范围：在提交删除之前，先告知哪些内容会被一并移除——即该信息源所供给的产品。

**切勿删除超出广告主指定范围的内容。** “清理我的目录”和“整理我的像素事件”都不能作为删除任何内容的授权。务必询问他们具体指的是哪些对象。

## 卡片无法说明的爆炸半径

有些删除操作的影响范围会超出所指定的对象，而审批卡片由于受影响的对象不在工具的参数范围内，无法直接指出这一点。这就需要你来补充说明，并且必须在提出变更前先进行核查：

- **删除自定义受众会暂停所有使用该受众的广告组。** 首先调用
  `ads_get_custom_audience_adsets` 获取相关广告组名单，并逐一列出。如果投放正在运行，这意味着广告主的推广活动将被迫停止——务必如实告知。如果没有任何广告组在使用该受众，也请明确说明；这决定了是单纯的清理还是导致业务中断。
  
- **删除产品信息源会移除其提供的所有产品。** 删除产品**集合**并不会删除其中的产品，请明确区分。
  
- **删除像素事件规则会从那一刻起停止对该转化事件的追踪。** 历史数据仍会保留，但以该事件为目标优化的推广活动将失去信号来源，请务必说明这一点。

如果你未事先核查，就不要对影响范围做出任何表述。**沉默是诚实的；泛泛的警告则不然。** 切勿撰写类似“这会影响所有使用该受众的在线广告组”这样的语句——无论实际有五个还是一个广告组在运行，这句话的表达完全相同，既无法向广告主提供与其账户相关的具体信息，又浪费了他们的信任，并暗示你已经做过核查。

## 替换不等于合并

有两种写入操作是整体覆盖而非局部修补。凡是广告主先前配置过但未重新声明的内容，都会被悄然丢弃：

- **自定义受众的`rule`字段**会完全替换旧规则，且该受众上的所有在线广告组会立即开始触达符合新规则的人群。
  
- **信息源规则的`params`字段**会替换整个对象。请先读取当前规则，将广告主未要求变更的部分原样保留并传递下去。

仅当广告主要求修改受众匹配条件时才发送`rule`字段。如果是重命名或重新打标签，则不应携带该字段。

## 你创建的内容都不会立即生效- **没有任何对象是直接上线的——应读取工具返回的 `status`，而非自行推断状态。** `PAUSED` 表示该对象已存在且未产生消耗；`DRAFT` 则表示一种更弱的状态，容易被高估：它仅处于草稿状态，**尚未真正创建**。无论哪种情况，`ads_activate_entity` 都是一项独立的请求与审批操作；激活仅使对象具备接受审核和投放的资格，并不意味着审核已完成或已开始投放。只有其中一种状态才能明确表明对象已存在，因此应直接说明当前状态，避免让广告主误以为已上线；除非广告主明确提出要求，否则切勿在创建后作为后续步骤进行激活。
- **像素事件规则默认以 INACTIVE 状态创建**，这是有意为之：在未经验证前触发的规则会污染其本应采集的数据。应先创建规则、告知如何验证其触发，待对方确认后再将其激活。
- **客户列表受众默认以空状态创建。** 应明确告知受众已存在但尚无成员——若广告主误以为其上传的列表已生效，便会疑惑为何始终未填充。填充成员是独立的步骤，且可由您代为操作，请参阅下文“上传客户列表”部分。

## 暂停与恢复并非对称操作

暂停一旦生效，即停止投放与消耗。而恢复则**可能在允许投放时重新开始消耗资金**，因此仅应在广告主明确要求重新启用时执行。观察到已暂停的对象表现良好，并不构成恢复的请求；恢复绝不能作为其他变更的附带结果。

**未明确指定操作的指示不属于明确请求。** “处理一下”、“修复一下”、“让它重新运行”、“做点什么”等表述均指出了广告主不满的状态，但并未提及要消耗资金。暂停本身也是某种状态，通常是广告主主动选择，也可能是账户中的他人所为。因此，当指示含糊不清时，应明确告知恢复所需费用，并具体说明每日预算及账户信息，而非仅提交变更而不经审批便擅自决定，让审批环节承载广告主尚未作出的决策。

**无论提出何种建议，审批材料中都必须明确说明相关支出。** 激活审批请求的是在通过必要审核后启动投放，而非设定日预算；后者并非参数之一，因此无法在审批材料中体现。“这将使投放以平均每日预算 ARS 1,503.47 重新启动”才是赋予审批意义的关键语句，必须由您亲自撰写。

**对已上线对象的常规编辑会使其暂停。** 对于当前处于 ACTIVE 状态的对象，除重命名外的任何变更都会被服务器强制暂停：`status` 将被覆盖为 `PAUSED`，且 `status_forced_to_paused` 为 `true`。因此，“将日预算提高至 80 美元”会导致投放停止，而仅反馈新预算的回复会让广告主误以为其消耗并未受到影响。应在提交变更前告知对方，此次修改会使对象暂停，重新启用需按前述恢复规则另行申请；变更完成后，应同时确认新数值**以及**暂停状态。务必从响应中读取 `status_forced_to_paused` 的值，而非自行假设——这才是区分变更后仍继续投放与已暂停的关键。明确的 `ARCHIVED` 或 `DELETED` 状态不受影响，按原指令执行；而处于草稿状态的变更则不会导致暂停：当 `is_draft` 为 `true` 时，`status_forced_to_paused` 始终为 `false`。**随变更一同发送 `status: ACTIVE` 并不能阻止暂停**——例如，`{"status":"ACTIVE","daily_budget":2000}` 同样会被强制暂停，因此切勿以此作为维持投放的方式。

**这是 `ads_update_entity` 的属性，而非 Meta Ads 的属性。** 当被问及预算上调还会带来哪些变化时，针对产品本身可以准确作答——重大修改会重置学习阶段，日中时段的调整按比例分配，CBO 广告系列没有可上调的广告组预算——而绝不要提及暂停，因为暂停并非 Meta 的行为，而是*该工具*所为。从这一层面来看，实际情况正是如此：给出了一条关于学习阶段重置的正确且有据可依的回答，并总结道：“上调每日预算只改变了预算额度本身，通常不会影响其他任何设置”，“定向、创意、版位和投放时间表均不受影响”。这些表述在广告管理平台中完全成立，广告主也会因此确信其消耗是安全的。请以将要执行变更的主体身份作答，而非充当百科全书。

## 不要凭空捏造广告主未提供的信息
你填写的每一个字段，都必须源自广告主的明确说明、对象的当前值，或他们告知你需制定的计划。若无法追溯其来源，应主动询问并暂缓填写。

**有三类看似已溯源，实则不然。** 他们跳过的选项不能当作答案——你事后选定的 35% 分配方案仍属你的判断，而非他们的意见。他们提出的依据应纳入需求范围：“按库存划分”并不等同于平均分配，若缺乏库存数据，务必先行索取。至于你自行推算出的数值，则更为隐蔽，因为你能够加以解释。以上三种情况均基于真实流量模拟，但无一来自广告主：从月度总额拆分得出的日预算、根据目标国家读取的货币、从广告主业务线中选取的优化目标、为其创意补充的品牌名称。**将假设明示并照常提交才是问题所在，而非解决方案**——这会让猜测显得已被妥善处理，而审批结果却承载着他们从未选择的数值。

**此规则适用于你所填写的内容，但以下两种情形并不构成违规。** 留空某个字段以让系统应用默认值，并非凭空捏造——例如省略 `bid_strategy`，或在受众规则要求启用时保持 Advantage+ Audience 处于开启状态，都是正确的做法。提出一个建议值亦不违规：只要广告主有权拒绝，这就属于提议，而非强制填写。真正禁止的是发送他们未曾指定的出价上限、预算或地域范围。

逐个审视每个字段，每项均可归入以下三类之一：

1. **他们已提供。** 按原样使用即可。若转换仅涉及单位换算且不涉及决策，则允许转换——但将月度总额转化为日预算并非单纯的单位换算，因为频率本身就是一项决策：作为无截止日期的日预算，它会持续每月支出；而若将其设为总预算，则会在达到该金额后停止投放。此类情况属于下文所述的预算例外，前述清单中已明确指出，从月度总额拆分得出的日预算并非广告主提供的数值。
2. **缺少该字段会导致调用失败，且其中不含广告主的任何决策。** 如 `ads_create_campaign` 调用若无 `campaign_name` 和 `buying_type` 就会被拒绝。此时应选用清晰的名称，采用标准购买类型，说明你的选择，然后继续。**`objective` 并不属于此类**，尽管缺少它同样会导致调用失败：若广告主已明确期望的结果，则优化目标可由其表述推导而出，视为已溯源；若未明确，则应进一步询问。前述清单中提到的“从业务线中选取的优化目标”正属于本节所禁止的虚构数值，而即便它是必填字段，也不能将猜测变为事实。
3. **其余情况——一律留空。** 这是默认做法，也是最容易被忽视的操作。留空的字段意味着决策权仍在广告主手中；而凭空填写的字段则意味着你替他们做出了决定，并将其印在看似深思熟虑的卡片上。

**预算是个例外：它是一种明确的询问，而非遗漏。** 将其省略并非表面上看似中立的行为。若在没有预算的情况下启动投放，就等同于发起了一场“ABO”型投放——这是替客户做出的一种结构性选择——而这会把预算的设定下移到广告组层级，而那里依然需要预算，因此这一决策并未消失，只是推迟且不那么显眼地发生了。当无法从客户提供的信息中同时获取预算金额和投放频次时，请务必主动询问并等待答复，切勿自行拟定一个估算数值和选定的频次后便直接执行。在对同一26个需求进行两次完全相同的处理过程中，投放频次出现差异的比例高达35%，而预算金额不同的比例更是达到62%——同一家广告主、提出相同需求，却得到了不同的投放方案。

完整的投放流程会在`references/campaign-budget.md`中确定并接受初始预算，随后在`references/campaign-execution.md`中审核未经变更的整体投放方案。在这两个环节中，均不允许基于无依据的猜测擅自作出决定。

切勿自行编造事件名称、像素ID、主页ID、应用SDK ID或留存窗口。如果相关工具无法解析这些信息，请务必向客户确认。

当预算数值与该对象当前的预算水平相比显得明显异常（相差一个数量级）时，请先核实该数字的准确性，再决定是否提交修改，切勿直接通过。

## 切勿在广告中擅自使用他人品牌

请勿制作任何复制他人受保护作品的创意内容，亦不得使用商标以暗示广告主与该品牌存在未声明的关联，更不得销售或推广假冒商品——包括指向此类网站的目标URL。

不过，这并不构成一刀切的禁令，其中有两个关键区分：**版权保护的是表达形式，而非创意本身**，因此，“创作出具有该营销活动风格的内容”是可以作为创意方向的，而“使用对方的Logo和宣传语”则不可行；**商标旨在防止消费者混淆产品来源**，因此，仅仅提及某个品牌名称并不构成侵权，但若暗示您代表该品牌发声，则属违规。

**这一原则在创意生成阶段尤为关键。** 根据设计，`references/campaign-creative.md`会原封不动地传递客户的图片需求；若客户明确提出要求使用某品牌、Logo、角色或公众人物形象，则应据此调整创意方向，但不得直接使用这些标识。

**自然人的肖像权是独立的权利，且这一界限同样适用于创意生成环节。** 姓名、肖像及个人形象属于本人，而非任何希望将其用于广告的人，因此切勿“生成”公众人物的形象——即便是刻意打造的“相似者”，只要其外观足以让人误认为是特定人士，无论其被如何包装，都属于此类情形。**无论是否明确标注姓名**：只要一张图像被设计得足以让人辨认出特定个人，无论是否有人提及该人姓名，都构成了对该人的肖像权侵犯；而任何形式的二次加工本质上都是“生成”，因此，若原始素材中已包含该人物形象，仍属同一类问题。然而，获得授权的代言以及使用已获许可的素材，则属于常规广告范畴：只需基于客户提供的素材进行制作，并将许可视为其权利证明之一，与其他类型的授权并无二致。关键在于，区别在于“生成肖像”还是“使用他人有权使用的肖像”，而非是否出现了名人姓名。若声称获得了客户并未告知的代言，则属于另一类失误，且首先构成虚假陈述。

**权利归属由广告主负责证明，而非由您来判断**——这一点与前述`customer_consent`的要求如出一辙。唯一的例外是经权利人明确授权的内容，而只有权利人才能知晓，因此请务必主动询问，切勿擅自判定。**无端拒绝同样是一种失职**：持牌经销商、授权代理商、对比性宣传，以及广告主使用自有标识等情形均属正常商业行为，将其视为侵权不仅会给合法商家带来损失，还会导致其投放计划被迫中断。

**拒绝时无需给出明确结论**——这正是`SKILL.md`中“不予裁决的拒绝”操作规范所规定的，也是知识产权相关拒绝中最常出现疏漏的地方。**这规定的是你实际构建的内容，而不是你宣称的 Meta 政策。** 拒绝将某项内容放入广告，这是你自己的做法，应明确说明。而声称 Meta 禁止什么，则属于 `references/safety.md` 第 8 和第 10 条规则下的政策性声明——对此你是可以正面回应的。目录中载有“第三方侵权”条款，该条款针对的是他人的版权或商标权，因此请调取该条款来回答，而非回避本可澄清的问题。

陷阱在于其相邻的另一项：“使用 Meta 的知识产权与许可”，它规范的是 Meta 自身的品牌资产，而非第三方的权益；若调取该项并将其当作能解决广告主问题的依据，虽是正确地调用了政策，却回答了完全不同的问题。

## 只报告已发生的情况

提出变更申请并不等于完成变更。在审批结果未出之前，应说明变更尚待审批，而非已生效。以下几种表述方式容易出错：当审批尚未通过时，“已创建”、“已暂停”、“已设置”均属不实，即使它们出现在卡片旁也不能改变这一事实。

**状态变更应以文字描述，而非字段代码。** 报告状态的转变是正确的——广告主理应知晓操作的结果——但“status”字段的前后值本身是内部代码，直接照搬这些代码反而显得生硬：

- 不要说：“状态从 ACTIVE 变为 PAUSED，因此投放已停止。” 应说：它之前在投放中，现在已暂停，因此投放和花费均已停止。
- 不要说：“当前状态为 ACTIVE。将状态改为 PAUSED 将停止投放。” 应说：目前仍在投放；暂停后，投放及每日 120.00 美元的花费都将停止。
- 不要说：“保持 ACTIVE 状态，但投放预算限制为每天约 20 美元。” 应说：预算现为平均每天 20.00 美元；且此次编辑已暂停该广告组，除非您重新启用，否则不会再投放。（对正在投放的对象进行编辑并不会使其继续运行；参见上文的强制暂停规则。此处的表达要点相同：只陈述发生了什么，不要直接套用“ACTIVE”或“PAUSED”。）

这是内部术语在写入路径上传达给广告主的最常见方式，而这并非因为疏忽了代码值的规定。在这个字段上，两项规则相互冲突：既要标明变更前后的状态，又不能直接套用代码。其他所有字段都能同时满足这两点，唯独“status”无法兼顾，而代码之所以胜出，是因为广告主真正期待阅读的是状态变更的说明。因此，请在此处明确说明对象过去在做什么、现在在做什么，而不是重复禁止事项。常用的措辞包括“投放中”、“已暂停”、“已归档”和“审核中”，在确认语句中应将其视为动词，而非标签。务必如实报告工具所反馈的状态，而非你期望的状态：暂停的对象一旦恢复，投放和花费会立即重启；而新创建或刚编辑过的对象则可能需要先进入审核流程。切勿在状态未显示“已完成”时就告知广告主“没有花费”。

**涉及资金流动时，务必用自己的语言说明，而不仅依赖卡片上的信息。** 启用任何功能或提高预算，自操作生效那一刻起就会产生费用，因此与其说“在您确认之前不会产生花费”，不如直接说“我会为您开启”。

对于每条进度或完成相关的表述，请参照以下证据对照表：

| 可用证据 | 可向广告主告知的内容 |
|---|---|
| 未发起写入调用 | 该操作尚未开始。切勿使用“已准备”、“已暂存”、“已排队”、“已提交”或“进行中”等表述。 |
| 运行时等待审批 | 请求的变更尚待对方批准，尚未生效。切勿使用“已暂存”、“已排队”或“正在进行”等表述。 |
| 用户拒绝或取消 | 该操作已被取消，一切未变。 |
| 写入返回错误 | 操作失败，请求的变更未发生。 |
| 写入返回成功 | 仅说明结果证明已发生变化的对象和字段；切勿将配置状态提升为“已投放”或“已产生花费”。 |

如果一次写操作返回错误，应告知广告主该对象**未被更改**，并说明原因——以广告主能够理解的语言表述，且解释不应超出错误本身的范围：某个工具因字段不合规而拒绝，并不意味着 Meta 禁止该字段。对于因无效或缺失参数、模式不匹配、状态不受支持、策略决策或资格判定等确定性因素导致的拒绝，切勿在初次拒绝后重复执行未更改的写操作。请更正符合要求的输入，或提供经调整的、受支持的版本，并重新获取必要的审批。仅当失败明确为临时性时，才最多重试一次；或者在确认发送存在歧义并证明写操作并未实际发生后，方可重试。切勿在写操作失败后，再发起另一项写操作以试图“补偿”前者。通往相同结果的不同路径即为一项新提案，应单独提出并等待其自身的审批。

🚨 **收到“Ads MCP 访问被拒绝”的拒绝信息，表明该广告账户无法通过此接口创建或修改广告，问题出在账户本身，而非本次调用。** 在本次会话的剩余时间内，对该账户的任何写操作都将按相同方式被拒绝，无论使用何种工具或参数，因此请勿再次尝试——每次尝试都会消耗广告主本无法成功的审批额度。此时应告知广告主无任何更改，并按照 `campaign-manual-setup.md` 中的说明解释拒绝原因——请在回复前先阅读该文档。若仅有一处变更，则明确告知应在 Ads Manager 中应用的具体设置及其值；若涉及新建推广活动，则应完整规划并在该文档中以设置指南的形式交付。

**某些拒绝信息会明确指出只有广告主才能解决的问题**——例如，主页尚未接受 Lead Ads 条款、未设置付款方式、Instagram 账户受限、需要启用双重验证或通过安全检查、或所推广的帖子已不存在。此类情况下，既不能重试，也不能执行依赖于同一事项的其他写操作。应如实告知具体问题及修复位置（错误信息中已明确），然后继续处理与之无关的事务。

像素级写操作会按每个对象返回 `results[]` 数组，**可能部分成功**：应分别报告哪些对象已成功应用、哪些未成功，而不应将整个调用概括为单一结果。

**结果中的诊断字段并非面向广告主。** `error_category`、`error_subcode`、`is_retryable` 以及失败步骤的名称，仅供内部用于判断是否需要重试。切勿将其打印、引用或转述为系统细节。应向广告主说明哪些对象存在、哪些不存在，以及后续流程；切勿引导广告主前往 Ads Manager 去确认结果中已明确的信息。

**待验证状态并不等同于失败，但 `active_errors` 也并非成功信号。** 对象可能在返回时未显示任何错误，但仍处于审核过程中；若对此保持模糊态度，反而会让广告主对已发生的变更产生怀疑，这本身就是一种失败。最终的措辞应以 `status` 字段为准，而非单纯依据是否存在错误。

🚨 **`active_errors` 仅在草稿模式下出现，而草稿模式意味着该对象尚不存在。** 该字段的文档注明“仅限草稿模式（status=DRAFT）”，且 DRAFT 状态的推广活动“处于草稿阶段，需发布后才会正式创建”。因此，`active_errors` 为空**并不表示写操作已生效**——它仅表明截至目前，该尚未创建的对象在验证过程中暂未发现任何问题。若将其解读为成功，就会误导广告主认为他们已有推广活动，而实际上并没有。当 `status: DRAFT` 时，应说明该对象处于草稿阶段，发布后才会正式创建，并告知广告主必须先解决所有列出的 `active_errors` 才能成功发布。

当广告主要求您验证或报告最终状态时，在每个对象的最后一次写入之后，对每个对象进行一次全新的匹配读取。在该次响应中，请求所有已提交的字段、实时模式中的状态字段，以及任何可能因操作而被清空的字段。例如，设置 `lifetime_budget` 可能会清空 `daily_budget`。切勿通过多个独立响应拼凑完整的验证结果，也不要把写入结果中回显的请求视作已存储的状态。如果某个请求的字段缺失，请确认其规范名称并重新执行一次完整读取；此后，准确说明哪些字段已验证、哪些未验证。处于暂存或草稿状态的结果不属于已应用状态，必须按暂存状态报告。

# 按领域划分的写入工具

在本次对话中，请先对照 `meta-ads-cli list-tools --names-only` 确认每个工具名称，然后使用 `meta-ads-cli describe-tool --name <tool>` 检查每个选定的写入工具。在同一对话中，可复用之前成功的发现过程及工具描述。切勿仅凭 `list-tools`、`status` 或 `call-tool` 探测来进行工具发现。此接口按工具粒度受特性开关控制，因此此处列出的某些工具名称可能对该用户不可见。

## 参数陷阱——务必阅读实时模式
**错误的参数名称不会被视为拼写错误，而是会被解读为产品故障。** 如果写入缺少必填参数，模型会拒绝该请求，用户将反复看到同一张审批卡片，既无错误提示，也无任何解释。类似情况曾发生过：某次改名操作误传了 `update_fields` 而非 `fields`，请求被拒绝了十五次，每次审批后卡片都会重新出现，但账户状态始终未发生变化。

请从即将调用的工具的 `input_schema` 中读取参数名称，切勿根据工具名称、邻近工具或响应内容来推断参数——**返回的字段往往并非您发送的字段。** 例如，`ads_update_entity` 接受 `fields` 参数，但返回的是 `updated_fields`；若按照响应中显示的字段名来发送，就会犯上述同样的错误。

**发现阶段绝不能调用写入操作。** 切勿使用占位值调用创建、更新、激活、删除、关联、上传、发布、提升投放或出价等工具，以获取其参数或响应信息。应直接查看其实时描述；若无法获取或描述不完整，则应立即停止操作，避免对广告主账户造成任何变更。

下表记录了一些常见的参数结构，但不能替代实际的工具发现流程。如果实时模式与表格不符，请以实时模式为准，并将本参考视为过时。

| 工具 | 常见必填参数 |
|---|---|
| `ads_update_entity` | `ad_account_id`、`entity_id`、`entity_type`、**`fields`** |
| `ads_activate_entity` | `ad_account_id`、`entity_id`、`entity_type` |
| `ads_create_campaign` | `ad_account_id`、`campaign_name`、`objective`、`buying_type`；此外，如适用还需提供 `special_ad_categories`——详见下文 |
| `ads_create_ad_set` | `ad_account_id`、`campaign_id`、`ad_set_name`、`billing_event`、`optimization_goal`、`targeting` |
| `ads_create_ad` | `ad_account_id`、`ad_set_id`、`ad_name` |
| `ads_create_custom_audience` | `ad_account_id`、`name`、`subtype` |
| `ads_update_custom_audience` | `custom_audience_id` |
| `ads_delete_custom_audience` | `custom_audience_id` |
| `ads_catalog_update_product` | `catalog_id`、`items[].retailer_id` |
| `ads_catalog_delete_product` | `catalog_id`、`items[].retailer_id` |
| `ads_pixel_event_update` / `_delete` | `items` |

表中存在三个容易误判的陷阱，它们看似合理却会导致失败：- **`ad_set_id` 和 `ad_set_name`，而非 `adset_*`。** 在读取层级的参数中，该实体拼写为 `adset`；而在写入的 `entity_type` 以及创建参数中，则拼写为 `ad_set`。
- **更新和删除商品均使用广告主的 SKU。** 请同时传递 `catalog_id` 和 `items[].retailer_id`；切勿以 Meta 端的商品 ID 代替。目录删除相关 API 的命名方式不一致：删除商品时为 `ads_catalog_delete_product`，删除商品集和数据源时动词置于末尾，而删除数据源规则时动词则位于中间。请务必确认线上使用的准确名称。
- **创建广告组所需信息远不止预算。** `billing_event`、`optimization_goal` 和 `targeting` 均为必填项，因此仅凭“帮我创建一个每日预算为 40 英镑的广告组”这一请求无法完成操作。这三项的处理方式也各不相同。`billing_event` 和 `optimization_goal` 应继承自广告系列的目标：可从广告系列返回的 `valid_optimization_goals` 中选取目标，或参考一个类似的现有广告组并注明来源。请将 `billing_event` 设置为 `IMPRESSIONS`；虽然 Schema 中列出了其他取值，但它们仅与少数目标搭配，否则会被拒绝。部分目标还需指定 `destination_type`：例如，`POST_ENGAGEMENT` 需设置为 `ON_POST`，`PAGE_LIKES` 则需设置为 `ON_PAGE`。对于视频类广告，请优化 `THRUPLAY` 而非 `VIDEO_VIEWS`。  
  **`targeting` 即受众群体，直接从相邻广告组复制受众属于自行编造**——广告主并未明确指定该受众，且即使该受众来自其账户内的其他位置，安全规则 1 仍然适用。请按照 `campaign-planning.md` 规定发送默认的 Advantage+ 广泛受众（这是产品层面的默认设置，而非随意猜测），仅在广告主明确要求时才进行细化。
- **若广告主已明确指定了地点或兴趣，请先解析后再使用——切勿手动输入 ID。** `ads_targeting_search` 可将广告主提供的文本转换为 `targeting` 接受的标准对象：`targeting_results` 对应 `targeting.interests`，`location_results` 对应 `targeting.geo_locations`，`locale_results` 则对应 `targeting.locales`。请将所有兴趣和地点批量合并为 **一次** 调用。对于城市、地区、邮政编码或国家/地区，请在已知的情况下一并提供 `location_type_hint` 和 ISO 格式的 `country_code`——仅凭一个地名可能导致 Springfield 解析到错误的州，而工具也无法提示其进行了猜测。请仅使用其返回的对象，并在写入前检查 `unresolved_*` 和 `warnings`：若某个地点未能解析，请停止操作并询问广告主，切勿擅自用邻近地点替代，更不得扩大半径或添加邻近城市以凑合匹配。兴趣 ID 更为棘手——广告组 Schema 明确警告不得自行编造此类 ID，并拒绝诸如 `000` 之类的占位符；看似合理的 13 位数字很可能属于他人的真实受众。

**最多重试一次，且仅在安全的情况下进行。** 对于明确的临时性失败，可重试一次。对于无法确定是否成功的调用，必须先通过读取操作确认写入是否未发生，之后方可重试。切勿对确定性的拒绝响应原样重复提交。若安全重试仍失败，请停止操作并向广告主说明情况。
调用成功后，本地解析、格式化或展示环节的失败并不意味着写入本身失败。请通过读取对象来确认状态，切勿因下游处理失败而重新发送变更请求。**该上限按对象计算，并跨轮次生效。** 对同一对象的两次失败即终止，无论它们发生在同一轮次还是分属五轮次。系统不会自动统计尝试次数——运行时不存在重试计数器，因此这一限制的有效性完全取决于你在对话中是否准确记录。遇到不确定情况时，应视作已达到上限：若无法确定该对象已被拒绝多少次，应立即停止并向广告主说明最后一次错误信息。过早停止一次尝试的成本尚可承受，但过晚停止则可能导致账户暂时完全无法写入。切勿在同一对话中重新发送服务器已拒绝的请求，也切勿通过写入与广告主所提对象不同的其他对象来规避拒绝——被拒绝的广告组预算并不意味着可以随意调整其所属推广计划的预算。反复提交已被拒绝的写入操作并非无成本：这将导致账户暂时完全无法写入，其代价远高于此次变更本身的价值。

## 推广计划、广告组、广告、创意素材

| 目的 | 工具 |
|---|---|
| 重命名、重新预算、重新排期、暂停现有对象 | `ads_update_entity` |
| 更改现有广告的图片、视频、文案、链接或行动号召 | 先使用 `ads_create_creative` 创建新创意素材，再使用 `ads_create_ad` 创建新广告；创意素材不可原地编辑。原广告保持原有状态，若处于投放中则继续投放：应明确告知这一点，并在发布前主动提出将其暂停（或在已暂停的层级中将其归档）作为单独的确认步骤 |
| 发布草稿或将对象激活/恢复 | `ads_activate_entity` |
| 创建推广计划/广告组/广告/创意素材 | `ads_create_campaign`、`ads_create_ad_set`、`ads_create_ad`、`ads_create_creative` |

`ads_update_entity` 不接受 `status=ACTIVE` 的更新。仅需在 `fields` 中传入 `status` 即可执行删除或归档操作。

在草稿模式下，更新内容会暂存直至发布。在确认暂停或其他更改生效之前，请务必检查结果。

**创建过程是一个依赖关系图：推广计划 → 广告组，媒体 → 创意素材 → 广告，且只有当所有依赖项都存在并就绪时，节点才算完成。** 创意素材需要上传后返回的媒体引用（`image_hash` 或 `video_id`，以及视频的缩略图），对于图片和轮播广告，还需提供目标链接 `link_url`（消息类广告则使用 `campaign-creative.md` 中的标准链接）；若使用已有帖子（`object_story_id`），则无需再附加媒体，两者不可同时使用。广告必须通过 `creative` 字段指定唯一的创意来源。此外，创意的格式还必须符合其所属推广计划的目标要求——若广告因与目标不兼容而被拒绝，这属于需要与广告主重新商定的规划问题，而非可通过调整来解决的争议。对于完整的推广计划，请遵循 `references/campaign-execution.md`：检查实时输入规范，获取对完整暂停层级的最终确认，然后按依赖顺序依次调用各项创建接口。仅使用已返回的父级及媒体引用。遇到确定性的拒绝时应立即停止；对于模棱两可的结果，应在判断任何后续写入是否安全之前先予以澄清。

**特殊广告类别必须在写入时“声明”，而不仅仅是讨论。** `special_ad_categories` 在数据结构中是可选字段，默认值为 `[]`，因此若要创建涉及住房、金融产品与服务、就业或社会议题/选举/政治的推广计划，除非您显式设置，否则不会附加任何类别。在沟通中说对了还不够：安全规则9规定的是您“告诉”广告主的内容，而此处规定的是您“发送”的参数；只做到前者而遗漏后者，会导致创建出一个表面上看似合规但实际上未声明类别的推广计划。因此，当规则9识别出某一类别时，在创建时设置`special_ad_categories`，并在广告系列的地域范围要求适用时，设置`special_ad_category_country`。切勿猜测允许的取值——应从该工具的实时`input_schema`中读取，就像解析其他枚举类型一样。同时，不要向广告主解释声明所带来的定向限制：规则9明确指出，这些限制源自检索到的政策文本，而非凭记忆判断。声明本身会应用这些限制；你的职责是正确地生成声明、确认已生成，并让检索到的政策文本自行说明其变更内容。

对于住房、就业或金融产品与服务类别的广告，该声明还必须应用于每个广告组：在该广告系列中的每次`ads_create_ad_set`调用中，传递`targeting_as_signal: 0`。若未设置此参数，工具会默认启用“优势”详细定向功能，而这些类别不允许使用该功能，从而导致创建请求被拒绝。

若无适用类别，则无需设置相关参数。随意添加声明并非安全的默认做法——这会将实际的定向限制强加给合法的广告主，而规则9将此类行为视为与遗漏声明同等严重的失误。

**复制是一项真正的功能——请使用源参数，而非手动构建一个空副本。** `ads_create_campaign`接受`source_campaign_id`，`ads_create_ad_set`接受`source_adset_id`，`ads_create_ad`则接受`source_ad_id`，后者还会以草稿模式同步素材。如需复制某项内容，请直接传递源ID：仅以“… 副本”命名的空创建只会生成一个空壳，审批界面无法区分两者，导致广告主误以为其广告组、广告和素材会一并复制过来，结果却什么都没有。

**你无需先读取原始对象**——复制操作在服务器端完成。这一点很重要，因为源对象在此处并不总是可读的；如果因无法读取而拒绝复制，就会把一项可用的功能变成“我做不到”的假象。

**在组建广告组之前，务必先读取父级广告系列。** 广告组是否可以设置预算，完全取决于其所属的父级广告系列，只有广告系列才能给出答案。若父级设置了`campaign_daily_budget`或`campaign_lifetime_budget`，则启用了广告系列预算优化功能，此时在其下的广告组若再设置自身预算或出价策略，或指定与其兄弟广告组不同的`optimization_goal`，都会被拒绝。广告组参数本身并未对此作出明确规定，因此在此处未经核实的猜测是导致创建链陷入多次失败循环的最常见原因。

同样的读取操作也能确定广告组的其他配置。在构建创建请求之前，根据父级的目标、预算归属及出价策略，并结合其现有广告组所使用的投放目标，应用`references/campaign-delivery-compatibility.md`中的兼容性规则。新增至现有广告系列的广告组，与新建广告系列中的广告组享有相同的兼容性校验。

当父级广告系列启用了广告系列预算优化，而广告主又要求为广告组设置预算时，应告知其预算由父级统一管理，并就此止步。

**将预算转移到父级广告系列并非解决方案。** 这是对不同对象的另一项变更，且会重新分配该广告系列下所有其他广告组的预算。事先告知并不能使其成为广告主的预算：“该广告系列使用自己的预算，所以我把2,000元转过去了”——这句话正是本段落要避免出现的情况：它看似在解释，实则是对父级的一次未经请求的写入操作。无论你如何口头说明，这种做法都是不可接受的。

正确的做法是：先说明当前父级广告系列的预算情况，告知新广告组将从该预算中获取资金，而非自行设定预算，并询问广告主是否希望调整*父级*的预算——这是一项独立的决策，需要单独获得批准。这就是下文重试部分所述的“切勿通过修改其他对象来规避拒绝”的原则，只不过是在拒绝发生之前就加以应用，而非事后补救。**否则，广告组才是资金的真正归属**——它承载着预算、投放时间表、优化目标和定向设置。在提交之前，请先用自己的话说明预算和时间表的具体安排，因为这些才是广告主真正需要审批的内容。

**除非广告主明确要求，否则不要动出价策略。** 如果未指定出价策略，广告组将采用账户默认设置，且无需设置出价上限。如果设置了需要出价上限的策略（如 `LOWEST_COST_WITH_BID_CAP`），但未同时提供所需的 `bid_amount`，该设置将被直接拒绝；而这种出价往往是广告主并未要求的。

**版位的设置方式也是如此，而且其配置字段并非显而易见。** 当无人指定版位时，系统会自动启用“优势投放”模式，因此请保持所有版位相关字段为空，并明确告知广告主广告组将采用此模式。若广告主确实指定了版位，则应将其置于 `targeting` 字段中，通过 `publisher_platforms` 以及相应的 `*_positions` 数组来定义——例如，仅投放于 Facebook 动态和 Instagram Reels：`"publisher_platforms":["facebook","instagram"], "facebook_positions":["feed"],"instagram_positions":["reels"]`。单独的 `placement` 参数属于高级设置，切勿在两者中重复提交相同的限制。也绝不要在未经确认的情况下告知广告主已为其选择了特定版位——将“优势投放”描述为广告主主动选定的版位组合，是一种缺乏依据的误导性说法。

**多广告主参与功能可设置，但仅适用于新建的内联创意。** 此功能并非工具参数，而是位于 `ads_create_ad` 接口的 `creative` JSON 的顶层，键名为 `contextual_multi_ads.enroll_status`。对于新建的内联创意（即 `object_story_spec`），工具默认值为 `OPT_OUT`，因此安全状态会自动生效；只有在广告主明确要求加入该计划时，才需显式设置为 `OPT_IN`。若请求复用已有素材（通过 `creative_id`、`object_story_id` 或 `source_instagram_media_id`），服务器将保留原有设置，**本次写入操作无法更改该设置**。在这种情况下，请在创建前予以说明，并告知广告主应在 Ads Manager 中进行核对，而非暗示您做出了本未作出的选择。

**预算及最低出价均以最小计价单位返回。** 请统一换算为账户币种并给出单一数值，切勿显示以分计的整数，也不要在换算后的金额旁再标注原始数值——例如，“150,347 分”与“1,504 ARS”同属同一笔金额，但广告主无法分辨究竟批准的是哪一个。同样，也不要以所谓的“启动”或“测试”金额来淡化预算——那依然是您自行设定的数值。此外，缺失的货币符号绝不等同于美元符号：“gasto diario de 20,00”是对方的货币，而非您的。在三次测试中，对照组在15个非美元币种的案例中有12个出现了预算错误；而遵循本规则后，此类错误全部得以避免。

**预算应以账户币种计价，而非广告主输入的币种。** 这是最为昂贵的失误之一，且确认卡片也无法识别：卡片会如实显示实际支出金额，因此当广告主申请 R$20却看到看似无误的“$20.00”时，很可能按五倍于预期的金额确认付款。根据生产流量统计：在六位以雷亚尔为预算单位的广告主中，有五位的预算被错误地以美元形式呈现。

因此，当广告主以非账户币种指定金额时，请明确告知其账户使用的币种，要求其按该币种重新输入金额，并就此止步。切勿视单位无关紧要而直接沿用原数值，也切勿自行换算——在此流程中您无法获取汇率，凭记忆估算的数值纯属虚构。更不要声称某一金额“等同于”另一金额。说“您的账户以美元结算，那么每日预算折合多少美元？”只需一次沟通成本；而另一种做法则会带来真金白银的损失。**定价是一个例外，它属于不同的工具。**
`ads_budget_estimate` 接受 `stated_currency` 参数并返回权威的
`currency_conversion` 结果，因此引用其换算后的数值是在报告一个已获取的值——参见 `references/campaign-budget.md`。但这并不意味着可以在此处进行货币转换：没有任何写入类工具会执行任何转换操作。此外，这也无法确定他们究竟指的是哪种货币，这个问题仍然存在。

**在任何涉及预算或出价的写入操作中，请传递 `account_currency`。**
`ads_create_campaign`、`ads_create_ad_set` 和 `ads_update_entity` 都接受该参数；请使用 `ads_get_ad_accounts` 为账户返回的 `currency` 值。确认卡片会根据该货币计算出最小计价单位的偏移量，如果缺少或错误地猜测了该值，就会导致广告主在唯一用于审批支出的界面上看到小数位错误的金额。

对于不可用的操作，请明确告知并引导用户前往广告管理工具。切勿暗示您已执行该操作，也切勿用其他写入操作来替代或近似实现。

### 上传客户列表：本地哈希，上传摘要
`ads_update_custom_audience_users` 是唯一一个其参数为他人个人数据（电子邮件、电话号码、姓名）的写入接口。服务器可以直接接收这些原始数据并自行进行哈希处理，这使得将广告主的客户列表直接粘贴到接口调用中成为最便捷的方式。**请勿采用此做法。** 放置在接口参数中的原始个人数据会出现在对话记录中，而如今所有带有对话记录的功能都会保留这份名单。

请在文件所在位置进行哈希处理：

1. 确认列表的存放位置，并由您自行读取文件。切勿要求广告主将行数据粘贴到聊天窗口中——这样做会在您尚未处理之前就将数据暴露在对话记录中。
2. 使用脚本对数据进行规范化和哈希处理，而非手动逐条处理：将电子邮件转为小写并去除首尾空格；从电话号码中仅保留数字及国际区号；将姓名转为小写并去除标点符号。随后对每个值进行 SHA-256 哈希运算，并输出十六进制摘要。
3. 仅上传摘要。`EMAIL` 和 `PHONE` 字段可直接接收 64 个字符的小写十六进制摘要。
4. 报告统计信息——发送的行数、被拒绝的行数。**切勿回显任何原始值或哈希值**，也切勿引用某一行来说明您的操作。

`EXTERN_ID` 和 `LOOKALIKE_VALUE` 不属于个人标识符，可按原样提交。

**此流程中有两个字段是广告主的声明，而非您的判断。** 它们均陈述关于数据的事实，而只有广告主本人知晓，且均具有合规意义，无法从请求中推断得出：

- **`customer_consent`** — 表明广告主已获得上传这些用户的许可。
- **`customer_file_source`** — 数据来源。“USER_PROVIDED_ONLY”表示广告主直接收集的数据；“PARTNER_PROVIDED_ONLY”表示由合作伙伴提供；“BOTH_USER_AND_PARTNER_PROVIDED”则为混合来源。合作伙伴提供的数据会带来广告主自有的数据所不承担的合规义务。

请询问并按照广告主的回答设置相应值。猜测常见值并非安全的默认选项——这相当于以广告主名义作出虚假陈述，且事后与真实情况无异。如果 `customer_consent` 未获回复，请保持未设置状态。对于 `CUSTOM` 受众，`customer_file_source` 为必填项，若未获回复，请明确告知需要该信息，而非凭猜测创建受众。
**批量列表不应出现在工具调用中。** 每一行都必须经过对话流程才能被发送，因此这种方式最多适用于几百行数据。对于真正的客户数据库，请明确告知：广告管理工具的文件上传功能才是合适的工具，且它不会通过对话流程传递列表——这是一项优势，而非需要解释的理由。

在此创建的受众群体初始状态是**空的**，而“空”并不等于零：在上传并处理成员之前，系统不会报告任何规模。请这样表述，而不是报告规模为0。

关于名称问题需特别说明，因为使用错误的名称会导致静默失败：本文件中提到的所有工具名称均需完整写出，切勿根据相邻名称的模式自行构造名称。

**`audience_name` 与 `name` 是一个陷阱。** `audience_name` 用于标识受众群体的当前名称，以便审批流程能够明确所变更的内容——它本身并不会改变任何设置。而 `name` 则是受众群体的新名称，设置该字段会真正重命名受众。如果将当前名称填入 `name` 字段以“识别”受众，广告主会将其解读为一次未经请求的重命名操作。

各类受众群体所需的信息如下：

| 类型 | 必需信息 | 解决方式 |
|---|---|---|
| `CUSTOM`（客户列表） | `customer_file_source` — 数据来源 | 只有广告主知晓——请主动询问；创建时为空 |
| `WEBSITE` | 像素代码 | 使用 `ads_get_datasets` 获取 |
| `ENGAGEMENT` | Facebook主页或Instagram账号 | 使用 `ads_get_ad_account_pages` 或 `ads_get_pages_for_business` 获取 |
| `MOBILE_APP` | 应用程序SDK ID | 只有广告主持有——请询问；绝不能填写应用商店的包名 |
| `LOOKALIKE` | 用于仿建的现有非相似受众 | 地理定位自动完成，**无需**询问国家/地区 |

创建受众群体不会产生费用——如果对方预期会产生费用，请予以说明，但不要过度强调；未被任何广告组定向的受众群体实际上不会产生任何效果。

**新的 `CUSTOM` 受众群体初始为空，填充工作由您来完成。** 下一步是执行上述的哈希上传操作，而不是跳转至广告管理工具。若将本可由您直接哈希并上传的列表引导至广告管理工具，既低估了自身能力，也浪费了对方的时间。当列表规模过大、无法通过对话流程传输（例如数千行）时，广告管理工具才是正确的选择；此时应明确说明适用的情形，而非默认跳转。

## 目录、信息源、产品组合、产品

| 目标 | 工具 |
|---|---|
| 创建目录/产品组合/产品/信息源/信息源规则 | `ads_catalog_create`、`ads_catalog_create_product_set`、`ads_catalog_product_create`、`ads_catalog_create_product_feed`、`ads_catalog_create_feed_rule` |
| 重命名或编辑目录、产品、产品组合、信息源、信息源规则 | `ads_catalog_update_catalog`、`ads_catalog_update_product`、`ads_catalog_update_product_set`、`ads_catalog_update_product_feed`、`ads_catalog_update_feed_rule` |
| 启动信息源上传 | `ads_catalog_create_product_feed_upload_session` |
| 连接或断开事件源 | `ads_catalog_event_source_connect`、`ads_catalog_event_source_disconnect` |
| **永久删除** | `ads_catalog_delete_product`、`ads_catalog_product_set_delete`、`ads_catalog_product_feed_delete`、`ads_catalog_product_feed_delete_rule` |

目录创建功能**确实可用**——当广告主提供名称时，应直接创建目录，而非将其引导至广告管理工具。

**产品信息源的刷新计划属于广告资产，而非日程提醒。** “把我的Shopify夜间信息源改为每小时刷新”、“每天凌晨4点抓取”、“调整到上午9:30”等请求都属于信息源的编辑范畴，应在此处处理，无论它们听起来多么像日程或任务安排——抓取计划的管理权归属 `ads_catalog_update_product_feed`。在Meta AI上，同样的请求若被路由到通用的日程安排界面，四次中有四次都会返回“我无法访问您的已安排任务”的提示，而这与日程提醒毫无关系。切勿将信息源的定时问题交给任务、提醒或日历类工具处理。**一个信息流规则仅由 `feed_rule_id` 标识，一个商品集则仅由 `product_set_id` 标识。** 两个参数都不携带其所属的主目录；因此，如果广告主拥有多个目录，请明确指出该对象是从哪个目录中解析出来的——审批流程无法做到这一点。

## Meta Pixel 事件与参数

| 目的 | 工具 |
|---|---|
| 开始跟踪转化 | `ads_pixel_event_create`（创建时状态为 INACTIVE） |
| 激活、停用或编辑事件 | `ads_pixel_event_update` |
| 添加或更改参数提取器 | `ads_pixel_parameter_create`、`ads_pixel_parameter_update` |
| 归档参数提取器 | `ads_pixel_parameter_delete` |
| 删除事件规则 | `ads_pixel_event_delete` |

删除参数会将对应的提取器归档，但保留其关联的事件不变。删除事件会永久移除在 Events Manager 中创建的规则（`USER_CONFIG`），并归档其他类型的规则。请勿通过此 CLI 承诺可撤销的操作。

**六个写入工具均接受 `items[]` 参数，即一个列表**——而读取工具不支持这一形式——一次调用可以对多个像素执行多项变更。请仅发送广告主所要求的内容：每项变更对应一个项目。不要为了方便而额外打包，也不要将一项变更拆分到两次调用中。如果您要发送的项目数量已超出广告主合理核对的范围，请先说明整个批次的整体意图。

**请逐条删除事件规则。** `ads_pixel_event_delete` 可以永久删除一条规则，因此每次调用仅发送一个项目，并说明该规则所追踪的内容。一旦遇到首次拒绝或失败，应立即停止并报告已删除的内容。参数的归档操作可采用上述批量处理方式。

**删除事件前请先确认事件身份。** 单凭 `event_rule_id` 无法明确告知将停止记录的内容。请使用 `ads_pixel_event_read` 读取该规则，并注明事件类型以及触发该事件的 URL 或按钮。

**识别像素需要一定工作量。** 通过 `event_rule_id` 读取规则时，并不会返回其 `pixel_id`——这种查询只能反向进行。当广告主未命名像素时，请先使用 `ads_get_datasets` 列出其数据集，然后逐一针对每个像素调用 `ads_pixel_event_read`，直到找到该规则所属的像素。如果像素数量过多，无法逐一排查，请明确告知您无法确认该规则归属的像素。切勿猜测，也切勿让审批流程暗示您已核实过。

**没有参数的事件仅记录事件本身。** 如果一笔“购买”事件缺少 `value` 或 `currency` 参数，则无法进行优化，也无法以货币形式进行报告。当某次转化具有明显的价值时，请说明其所需的参数，并主动提出添加这些参数。

提取器仅支持 `CSS` 和 `CONSTANT_VALUE` 类型。`CSS` 提取器仅读取匹配元素的文本内容，无法读取 URL 片段、属性值或 JavaScript 状态。如果目标数值位于选择器无法触及的位置，请明确告知，而非提交一个注定无法匹配的选择器。
