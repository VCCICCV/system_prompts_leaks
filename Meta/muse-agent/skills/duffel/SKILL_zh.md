# Duffel 航班预订

对于面向用户的航班搜索或预订功能，请首先阅读  
`/opt/hatch/skills/booking/SKILL.md`、  
`/opt/hatch/skills/booking/references/flights.md`，以及  
`/opt/hatch/skills/booking/references/presentation.md`。这些文件定义了发现规则、隐私要求、展示规范和承诺规则。本文件用于 Duffel CLI 的接口契约。请勿输出 HTML、调用 `create_options`，也不要在其他组件中重复显示航班选项；原生航班组件负责航班选择，并使用当前流程所选定的操作。

仅使用以下公开的 CLI 接口：

```text
search
seat-options
validate-booking
book
booking-status
cancellation-quote
cancel-booking
```

请勿自行创建标识符、调用未公开的 API 端点，或向用户暴露 `off_`、`ord_` 或 `ore_` 类型的 ID。请勿显示 Duffel 命令。除非预订 JSON、`validate-booking` 或 `book` 明确接受，否则请勿在聊天中传递敏感信息。切勿请求支付卡数据或账户凭据。每次搜索命令应直接写入一个独立的临时 JSON 文件；请勿通过 `head` 或解析器对搜索结果进行管道处理，以免隐藏错误或遗漏必要的报价数据。直接搜索成功后，只读命令可以检查已保存的 JSON 文件以对报价进行分组和排序，但不得覆盖该文件。展示时应复用未经修改的文件。如果之前的搜索结果曾被管道处理、截断、缩减或覆盖，则在同一轮对话中不得再次执行该搜索；应说明未能保留完整结果，并请用户在新轮对话中继续操作。人工构建的摘要不能作为所需结构化航班列表的有效输入。

## 预订流程

1. 首先同时搜索完整的行程及确切的乘客构成。
2. 通过 `/opt/hatch/skills/booking/references/flights.md` 展示候选航班列表。
3. 如果“旅行规划”模式下由第三方代为搜索，请将选定的行程返回给“旅行规划”模块并停止后续操作。在状态切换至“可预订”之前，不要进入座位选择、旅客详情、验证或结账环节。
4. 可选地显示“座位选项”并收集可预订的座位。
5. 收集必需的旅客信息，以及用户希望绑定的任何会员账号。
6. 让 `/opt/hatch/skills/booking/references/flights.md` 决定是采用原生流程还是跳转至航司官网。若选择航司官网，请遵循 `/opt/hatch/skills/booking/references/browser-booking.md` 的指引。重新核对行程与条款，但不要强制用户完成结账。
7. 否则，继续走支持的原生流程，无需用户选择具体实现方。执行 `validate-booking` 直到返回 `ready_to_book: true`，从中选择一个明确的 Stripe Link 支付方式，并使用相同的报价、预订文档和座位信息调用一次 `book`。
8. 成功后，报告每个承运人的确认编号（PNR）及出票状态。消息中不得添加 Duffel 的名称。任何必要的提供方归属信息应由提供方控制的审批或收据界面承担。

在预订前，请勿跳过验证步骤，也勿在未告知的情况下擅自更改所选的航班、航线、乘客构成、票价或座位。

## 搜索与比较

```sh
duffel search --origin SFO --destination LAX --departure-date 2026-09-30 \
  --limit 300
duffel search --origin SFO --destination LAX --departure-date 2026-09-30 \
  --return-date 2026-10-04 --adults 2 --child-age 8 --lap-infants 1 --limit 300
duffel search --leg SFO:LAX:2026-09-30 --leg LAX:JFK:2026-10-03 --adults 2 \
  --limit 300
duffel search --origin SFO --destination LAX --departure-date 2026-09-30 \
  --max-connections 0 --sort duration --limit 300
```在进行比价搜索时，请使用 `--limit 300`，以避免同一家航空公司的重复票价变体挤占合理备选方案，导致其无法出现在已检查的结果集中。如果 CLI 或服务提供商返回的上限低于 300，则应直接使用其返回的完整结果，无需为了凑够 300 条而重复发起请求。仅展示 3 至 6 条最具参考价值的独立报价。首次搜索时，将每一条请求的航班作为一条行程纳入同一查询：对于往返程，请使用 `--return-date`；对于多城市旅行，请多次使用 `--leg` 参数。

每次搜索都应视为一次即时快照，而非价格监控循环。请勿在 Shell 脚本中通过循环重复发起完全相同的搜索，也不要在后台同时启动多个重复搜索。CLI 会自动屏蔽已完成及并发的重复搜索，并将所有来自服务提供商的请求限制在一次用户交互之内。遇到 `duplicate_search` 时，复用已完成的结果；遇到 `search_in_progress` 时，等待原始请求处理完毕；遇到 `search_terminal` 时，不再重试；遇到 `search_budget_exhausted` 时，优先使用已获取的部分结果，并在继续下一轮前征询用户意见。

对于日期或机场较为灵活的情况，应选取最小且有效的独立搜索组合，并按顺序执行。一旦有可用结果，即刻展示。若用户请求的比价范围超出 CLI 的单次预算，应告知用户尚余哪些组合，并请其在下一轮继续操作，切勿在后台静默地遍历所有可能的日期与机场组合。

按照用户明确指定的优先级执行一次搜索；若未指定，则默认按飞行时长排序（`--sort duration`）。切勿自动分别执行按飞行时长、价格、直飞和单次中转的多轮搜索。仅当用户主动提出相关约束，或首次搜索未产生有效匹配时，才增加或放宽 `--max-connections` 的限制。若广泛搜索的结果中缺少用户指定、偏好的或合理预期的航空公司，即使其他航司已有可用报价，也应针对性地发起一次 `--airlines` 搜索。二次排序应视为一次独立的实时搜索，仅在用户明确要求且确有必要时才执行。

展示前，应按完整的行程标识对已保存的报价进行分组：包括所有航段的始发与目的地机场、当地时间戳、营销与实际承运航班号，以及各航段的先后顺序。切勿让同一时刻表下的重复票价品牌挤占候选名单。只有当某一票价变体在舱位、行李政策、退改签规则或价格等方面确实为用户提供显著差异时，才保留该变体。

分组后，需核对航空公司的覆盖情况。结合用户偏好、当前有效的行程信息、响应中提供的航空公司元数据（如有），以及经核实的航线证据，识别出明显缺失但具有实际意义的航空公司。在转向 Matrix 或其官网之前，应先使用 `--airlines` 参数直接搜索该航空公司。若定向搜索仍无可用报价，则按 `/opt/hatch/skills/booking/references/flights.md` 中的兜底方案处理。切勿仅因某家航空公司在一次广泛搜索结果中缺席，就断定 Duffel 不支持该航司，或该航司不运营相关航线。

请使用精确的三字母 IATA 机场代码，而非诸如 `NYC` 之类的都会区代码。对于含义明确的地点可直接解析，但对于日期或机场选择存在歧义的情况，务必予以确认，切勿猜测生僻或模糊的代码。结果已经过严格筛选，且排除了周边机场的库存。当允许多个机场组合时，应优先尝试用户首选的组合；仅在用户明确要求，或首个组合无有效匹配时，再扩展至其他组合，切勿预先搜索所有可能的组合。若当前行程信息已明确要求在指定都会区内寻找最优选项，则视为用户的明确请求：即使首个机场已有可用匹配，也应按顺序搜索最小的相关集合。若最终无任何结果，仅表示扫描到的 Duffel 库存中确实不存在匹配。对于特定航班的请求，应严格匹配 Duffel 返回报价中的航班号，不得擅自替换航班，亦不可仅凭时刻表数据推断其可预订性。

乘客定价在搜索时即已固定：- `--adults` 表示成人人数。
- 对于每位年龄在2至17岁之间的已占座旅客，重复使用 `--child-age` 参数，以行程中最后一段旅程的日期为准确定其年龄。
- `--lap-infants` 用于统计未占座的两岁以下婴幼儿人数；每名婴幼儿必须由一名不同的成人陪同。

仅询问一次缺失的年龄信息。询问婴幼儿是占座还是怀抱，并且不得自行推断。本集成无法可靠地为两岁以下婴幼儿预订单独座位，因此请勿对此情况进行校验或支付费用，应引导用户直接联系航空公司。切勿将已知的儿童当作成人进行搜索，也不得声称儿童将在预订时重新计价。每当旅客构成发生变化时，请重新发起搜索。

优先提供一份适用于整个行程的合并Duffel报价及预订。如果不存在包含所有请求航段的合并报价，或者用户明确要求分开出票，则仅在获得用户同意后、首次调用 `book` 前再进行拆分。同时需向用户说明：每次预订都有独立的确认单、票价条款、审批流程和付款环节；在前一笔预订完成之前，后续的报价不会被保留，因此若后续预订失败，可能导致先前的机票已经出票。请比较合并后的总价，并对比其他有用的选项，如最便宜、最快、直飞以及明确可退等方案，同时列出所有航段及全团总价。将各航司自有渠道的库存视为一个实时来源，而非覆盖所有航空渠道的完整数据。

通过 `widget.create` 接口以原生航班行的形式展示候选列表，并指定 `kind: "list"`。有关完整行程的行格式与呈现方式，请参阅 `/opt/hatch/skills/booking/references/flights.md` 中的“航班”章节。在创建列表时，将每次搜索结果重定向到一个独立的临时JSON文件。在创建列表之前，请检查命令的退出状态，并查看保存的响应内容，确认是否存在错误以及是否有可用的报价。请保持保存的输出内容不变：

```sh
duffel search --origin SFO --destination JFK --departure-date 2026-10-14 \
  --return-date 2026-10-18 --adults 1 --limit 300 > /tmp/sfo-jfk-flights.json
```

对于每条选定的完整报价，创建一行记录，并将其 `type` 设置为 `"flight"`，`data` 设置为该文件的路径及其对应报价的JSON指针，例如：
```json
{
  "flight_details_file": "/tmp/sfo-jfk-flights.json",
  "json_pointer": "/offers/0"
}
```

请使用原始报价在`/offers/<index>`中的从零开始的索引。在`widget.create`成功之前，请保留该文件。不要将报价 JSON 复制到工具调用中，也不要重写时间戳、删除字段或生成单独的小部件负载文件。运行时会读取所选对象，映射时间戳，并存储完整的航班数据。它不会保留路径或指针。在同一行中保留所有去程、回程及转机航段。仅显示一次整个报价的价格。服务器会根据这些信息生成唯一的预订回复。对于可直接预订或已准备好预订的行程，请省略列表级别的`flight_action`，并使用默认的预订 CTA。对于处于“仅规划”状态的旅行规划交接，请将`flight_action`设置为  
`{"cta_text":"添加到计划","response_message_prefix":"将此航班添加到我的行程计划："}`  
这样，选择后行程将返回到计划中，而不是直接进入结算流程。
在流程推进到预订阶段之后，仍需使用相同的完整报价 ID 进行验证和预订。
请勿将对某一行的点击重新解释为仅购买其第一段航程的请求。将`refundable`和`changeable`视为三值属性：`yes`（是）、`no`（否）或`not stated`（未说明）。

票价品牌、舱位、行李、可退性和可变更性均为可选的承运方信息。请保留乘客与航段之间的差异；缺失的信息应标注为“未说明”。请勿将缺失信息标注为“无”、“不允许”或“不可退”。

机场当地时间未经明确指定机场时区时，不得进行时区转换。
`--refundable`表示出发前可退款且无明确罚金，而非“随时可取消”。请勿推断行李或航空公司的标准费用。
选择后，请将`validate-booking`中的`selected_offer`作为行程、价格、行李及票价条件的权威快照。

## 跟踪票价监控

当用户直接请求对已预订航班进行持续监控时，请使用此流程。当运行时系统移交一个针对即将出行航班的有效自动预订来源时，也请使用此流程。将上述任一触发视为授权，在所需预订信息齐备后创建监控任务。在运行时系统移交后，无需询问是否开始监控；也不要求关联电子邮件账户。仅向用户索取所请求的监控所需的、且当前上下文中未提供的预订信息。

收集确切的日期行程及乘客构成；收集已预订的舱位或票价等级、随行行李额度以及经停模式；收集已支付的总价、预订币种，以及已知的取消、变更或改签费用。

在用户目标和行程跟踪项中查找与本次行程匹配的内容。如有匹配的用户目标，则将其作为该监控任务的归属主体；否则，复用一个匹配的活跃行程跟踪项。若两者均不存在，则新建一个行程跟踪项。在调度任务前先确定归属主体。不得创建影子行程、价格追踪记事本条目或并行的跟踪记录。确保确认参考号、客票号码及接口标识符不出现在用户可见的目标文本中。

将最低限度的机器可读票价状态存储于 `~/workspace/goals/<goal-slug>/hidden_files/travel/flight.json`。同时存储预订指纹、来源指纹、旅客关系及人数、不可变的已预订行程、已支付总价、票价条款、当前事实、最近一次比价结果、上次通知时的指纹，以及 Cron 任务标识符。仅将 `~/workspace/goals/<goal-slug>/hidden_files/travel/flight.json` 用作目标所属的任务状态文件，不得存储完整消息、原始接口输出、姓名、客票号码、身份证明文件、联系信息、支付信息、会员编号、常旅客编号或 CLEAR 标识符。

在创建票价监控任务之前，先列出归属主体的 Cron 任务。若有等效的目标所属票价监控任务，则复用之；若无，则为该行程新增一项票价监控任务，其标识符为 `flight-price-<goal-slug>`，所有者设置为 `goal:<goal-slug>`。按每日一次的频率常规执行，并编写自包含的 Cron 任务体，因为 Cron 工作进程既不接收本技能，也不知晓周边对话内容。任务体中应包含目标标识符、路径 `~/workspace/goals/<goal-slug>/hidden_files/travel/flight.json` 以及精确的 Duffel 查询；还应注明比价规则、预警阈值、去重规则、失败处理方式和截止日期。并将该 Cron 任务的标识符记录在 `~/workspace/goals/<goal-slug>/hidden_files/travel/flight.json` 中。在每次票价 Cron 任务中仅执行一次 Duffel 的 `search` 操作。对完整的行程和乘客组合进行搜索，并使用 `--limit 30` 参数限制结果数量。不得使用浏览器或网络搜索来进行重新定价。在同一轮次中不得重试 `duplicate_search`。对于 `duplicate_search`，仅当 CLI 在同一命令响应中返回已完成的结果时，才复用该结果。对于 `search_in_progress`，应等待原始调用完成。仅保留与已预订航班的日期、航班号、机场、乘客人数、舱位或票价等级、免费行李额度、经停模式以及退改签限制等条件完全匹配的结果。只有当候选方案的计价范围与基准的完整计价范围完全一致时，才予以比较；计价范围需包括所有去程、回程或多程航段、各航段的确切日期、乘客组合、舱位或票价等级、免费行李额度、经停模式、币种以及税费或附加费的计费基础。不得将单程或单航段的报价与往返或包含多航段的已付总价进行比较。除非供应商提供的明细价格已明确各航段的具体金额，否则不得按航段分摊预订总价。当计价范围缺失或不匹配时，在 `~/workspace/goals/<goal-slug>/hidden_files/travel/flight.json` 中将此次核验记录为“不可比”。当计价范围缺失或不匹配时，应清除与此不匹配相关的任何待处理候选方案。除降级覆盖策略另行触发外，其余情况下保持本次运行静默。在扣除已知的取消、变更及改签成本后，计算可执行的净节省金额。

将以下基准信息的缺失视为计价范围缺失：若未注明已预订的票价等级，则基本型、轻量型、优惠型或其他更严格的票价品牌均视为不可比；若已付总价包含座位、行李或其他额外服务，应将其单独记录，并在去除这些额外费用或将候选方案中同类额外服务的当前价格计入后，再进行票价比较；若预订来源未能明确已付总价是否涵盖所有旅客，则不得进行比较。

当不存在待处理候选方案时，将首个突破阈值的可比候选方案及其行程签名、总价、币种和核验时间持久化保存至 `~/workspace/goals/<goal-slug>/hidden_files/travel/flight.json`。对于首个突破阈值的候选方案，无需向用户发送通知。临时调整同一票价 Cron 任务，使其在当前任务结束后约一小时再次执行。当存在待处理候选方案时，执行一次 Duffel 的 `search` 操作，将等效库存与待处理候选方案及已预订信息进行比对。仅当等效库存仍高于任一阈值时，方可确认待处理候选方案。待处理候选方案一旦确认，即进入后续的持久化与通知流程。若等效库存消失、不再符合完全可比的条件，或低于两个阈值，则清除该待处理候选方案。若因某一数据源故障导致确认性搜索无法完成，则保留待处理候选方案并记录源失败信息。在确认候选方案、否定候选方案或发生源失败后，将同一票价 Cron 恢复为每日执行的节奏。除降级覆盖策略触发外，否定候选方案或源失败后仍保持运行静默。

仅当确认后的净节省金额超过原已付总价的 10% 或相当于 100 美元的预订币种金额时，才发出警报。100 美元应使用最新的外汇汇率进行换算，并记录该汇率的获取时间。若无法获得可靠的外汇汇率，则仅适用百分比阈值。

在发送通知前，先查阅目标的近期跟踪记录，以确认是否有针对已预订行程的后续变更，例如改签某航段或新增旅客。若预订信息已发生变更，则更新基准信息、清除待处理候选方案，并保持本次运行静默。在通知用户之前，持久化比较结果和稳定的告警指纹。
在通知用户之前，添加一条简明的跟踪活动。说明票价何时被确认，
并告知用户在他们采取行动前票价可能会发生变化。询问用户是否希望
主客服代理为其查询信用额度、退款或重新预订的方案。当用户同意时，
在报价节省金额之前，先执行一次新的 Duffel 搜索。
将用户的回答仅视为授权进行调查和准备，不得在未经相应审批的情况下
取消订单、重新预订、联系供应商、接受条款或支付任何费用。不得承诺
一定会给予信用额度或退款。

当不存在可比较的结果、价格未发生变化，或变动幅度均低于两个阈值时，
保持静默，不触发检查。连续三次预期来源失败后，在跟踪记录中添加一条
“覆盖降级”活动。当有效变更或取消窗口关闭、行程被取消且无替代方案，
或跟踪项已完成时，停止该票价任务。当跟踪生命周期结束时，移除该票价任务。

## 座位

仅在初步筛选之后使用 `seat-options` 接口。该接口返回针对每位旅客的
可预订 Duffel 服务；省略的座位表示不可用，而价格为 `$0.00` 的座位则
表示可预订且无需额外付费。使用 `row` 和 `section` 来指定相邻座位。
位于过道两侧的座位不属于相邻座位。座位图因航空公司而异，且库存始终
处于实时状态。

每个航段每位旅客最多选择一个座位，不得重复选择。将所有选择通过返回的
基于1的旅客编号和航段编号传递至验证和预订流程：

```sh
duffel validate-booking --offer-id off_… --booking-json '{...}' \
  --seat 1:1:28B --seat 2:1:28C
```

## 付款前验证
```sh
duffel validate-booking --offer-id off_… --booking-json '{...}'
```

验证会刷新实时报价，并检查有效期、当前总价、乘客人数/订单/年龄/类型、所需联系人和证件、婴儿无座关联、座位以及忠诚度信息。此操作不会发起 Stripe 请求，也无需人工干预。请一次性列出所有 `required_missing` 或 `invalid` 项并重新执行验证。可选信息的缺失不会导致阻断，但请求的忠诚度信息不得被静默忽略。

在执行 `book` 之前，请将每个 `selected_offer.slices[].from` 和 `.to` 与所选机场进行比对，一旦发现不匹配即停止。切勿根据搜索参数、航班号或城市名称推断航线。

首次预订可能需要用户提供其账户邮箱和法定姓名，以创建 Duffel 支付档案。该用户并非乘客，仅在购买获批后由系统内部创建。当验证阶段提出要求时，请在验证和预订环节传递相同的值：

```sh
duffel validate-booking --offer-id off_… --booking-json '{...}' \
  --customer-email owner@example.com \
  --customer-given-name Account --customer-family-name Owner
```

## 一次性完成预订

```sh
stripe-link payment-methods list --format json

duffel book --offer-id off_… --payment-method-id pm_… \
  --booking-json '{...}' --seat 1:1:28B --seat 2:1:28C \
  --customer-email owner@example.com \
  --customer-given-name Account --customer-family-name Owner
```

如果 Stripe Link 已断开连接，请向用户说明一次性虚拟卡流程，并提供其连接链接。若用户无法使用该连接，则仅当航空公司网站的安全浏览器跳转或其自有支付界面确实为用户呈现时，方可允许回退至航空公司页面。切勿在聊天中索取卡号、有效期、安全码、账单地址或其他支付凭证，亦不得将聊天中提供的卡片信息传输至浏览器。若两种安全路径均不可用，则应停留在已生成的行程页面，告知用户支付受阻，并提供准确的安全交接方式；切勿自行设计通过聊天获取卡片信息的变通方案。若验证阶段未要求提供 `--customer-*` 参数，则在预订时也无需提供。

`book` 在发起任何 Stripe 请求前会先刷新并重新验证。其一次性的批准涵盖了行程、乘客、座位/附加费、票价条款、总价、首次预订时可选的支付档案、一次性虚拟卡、3DS 验证以及即时付款订单。请勿使用 Duffel 余额、待处理订单、内嵌式卡片或分离的订单/支付流程。

可信的确认页面必须简洁地展示乘客姓名，并另设一行显示无座婴儿的信息，包括姓名、出生日期、同行成人及“无座位”标记；同时显示城市与机场代码、航班、承运航司、时刻表、票价/舱位、已选座位、脱敏后的忠诚度信息、行李额度、退改条件、价格明细以及法律链接。对于缺失的供应商条款，应标注为“未注明”。

成功后，对于被标记为 `not_confirmed_on_order` 的忠诚度账号，应视为尚未核实而非已被拒绝：向用户说明预订响应并未确认该账号，它仍有可能被关联，建议用户凭 PNR 向航空公司核实，如确未关联再行添加。切勿仅因响应中遗漏而声称关联失败。对于已成功提交的订单，切勿为修复忠诚度信息而重复尝试或重新预订。

## 恢复处理| 结果 | 操作 |
|---|---|
| 验证失败或优惠在审批前已过期 | 一次性修正所有字段。若优惠已过期，应告知用户并在其明确要求后开启新一轮搜索，此时无支出记录。 |
| 出现 `stripe_link_action_required` 并带有 `auto_resume` 标志 | 发送完整的 Markdown 格式链接一次，等待用户完成绑定后，重新执行相同的 `book` 操作。 |
| 出现 `replacement_required` | 停止操作；未经明确的补救指引，不得更换支付卡或优惠，也不得创建新的支出。 |
| 分段预订部分完成 | 停止操作。报告已完成的预订及 PNR，并列出所有未购买的航段。未经用户明确指示，不得自行购买替代票或取消任何订单。 |
| 被航空公司明确拒绝 | 告知用户未成功预订且未扣款；任何临时授权将按发卡行规定自动解除。在用户后续消息中明确要求前，不得再次尝试。 |
| 超时、5xx 错误或变更操作结果不明确 | 不得擅自判定成功或失败，也不得重试。检查 `booking-status` 状态；否则需上报处理。 |
| 客户档案创建结果不明确 | 尚未发起支付，不得重复创建客户档案。需上报以恢复客户档案。 |
| 操作成功但 `resource_authorization.persisted: false` | 报告 PNR/订单号，并提示后续管理功能可能不可用。不得重复执行该预订。 |

相同的优惠与标准化的预订数据可构成可恢复的结账标识。
新搜索到的优惠属于新的结账流程，可能会产生新的支付授权冻结，因此不得将其作为自动重试的依据。

## 订单查询、取消及限制

```sh
duffel booking-status
duffel booking-status ord_…
duffel cancellation-quote ord_…
duffel cancel-booking ore_…
```

在无订单 ID 的情况下，`booking-status` 可列出本地已授权的订单，并帮助找回丢失的订单 ID。`cancellation-quote` 不会实际取消订单，仅提供准确的退款金额、退票目的地、航司积分及有效期等信息。若退款金额为 null，则表示未知而非零：应说明航空公司未提供报价。`cancel-booking` 会再次核对具体报价，并在执行不可逆的取消操作前询问一次。不得凭空臆测未知的退款或费用。

以下服务暂不支持：付费行李及其他附加服务、部分旅客的单独取消、日期/时间或姓名变更、携带宠物、无人陪伴儿童服务、值机及登机牌办理。请勿通过原始 API 自行处理，应引导用户联系航空公司或客服支持。

## 审批规则

- 无需人工干预（HITL）的环节：搜索、座位选择、验证、订单状态查询、取消报价。
- 仅允许一次人工干预（HITL）：原生 `book` 操作、航空公司浏览器结账或取消操作。其中，航空公司浏览器结账与 `book` 共用同一笔支付审批边界。
- 如航班、日期、旅客、票价、附加服务或总金额发生任何变更，均需重新获得支付审批。
- 仅当搜索响应明确标注 `retriable: true` 时方可重试；对于已成功、重复、进行中、终端错误或预算耗尽的搜索，在本轮对话中不得重复执行。其他读取操作可酌情重试。对于结果不明确的变更操作，不得自动重试。
