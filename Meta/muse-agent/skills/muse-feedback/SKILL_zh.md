# Muse 反馈

## 目的

通过 `feature-request` CLI 向 Muse 团队提交用户的反馈。每条报告都会作为一条私密备注发送给 Muse 团队，其中的内容不会在任何公开渠道发布。

关于 Muse 的通用早期体验计划，请使用 `/opt/hatch/skills/muse-early-access/SKILL.md`。

当用户提出希望分享反馈时，请按照以下步骤为其提交想要发送的反馈。关于何时主动提供反馈的建议仅适用于主动提出的场景。

## 何时提供反馈

- “我希望能看到我 `<the-service>` 手表上的睡眠数据”：Muse 尚不支持的某项服务。  
  使用 `--kind missing-integration --subject <the-service>`。
- “你能扫描这份纸质表格吗？”：Muse 当前不具备该功能。  
  使用 `--kind missing-capability --subject document-scanning`。
- “在某家商店的网站上，结账页面始终无法加载”：已支持的功能在特定场景下反复出现故障。  
  使用 `--kind broken-behavior --subject <the-site>`。
- 如果某个连接或设置流程持续失败，直到用户放弃并表示“算了，我自己来”，这也属于功能缺失，即使用户并未明确说“做不到”。此时应使用 `broken-behavior`，并将相关服务作为主题。

提供临时解决方案并不意味着可以取消上报。如果用户原本期望自动连接，但最终只能通过手动粘贴、输入或自行操作来完成，那么他们最初的需求正是 Muse 团队无法直接了解的。因此，请在提供临时方案的同时一并提出上报：“我无法连接您的手表。需要我向 Muse 团队反映您希望实现这一功能吗？与此同时，您可以每天早上把数据发给我，我会以同样的方式为您记录。”

对于涉及外部服务或设备的功能请求，请使用 `missing-integration`，即使表述听起来像是功能需求，并将该服务的名称作为主题（小写、空格用短横线代替，如果是网站则去掉 `.com`）。对于与外部服务无关的功能缺失或更改限制的请求，请使用 `missing-capability`。对于 Muse 本身的问题，包括速度慢和回答质量不佳等，应使用 `broken-behavior`。

- 不要主动反馈 Muse 运行缓慢、价格昂贵、功能有限或存在故障的情况，包括登录失败、系统宕机以及模型质量等问题。对于与外部服务连接失败的情况，请遵循上述“用户放弃”时的处理原则。
- 即使是针对某个特定网站的速度问题，也不要主动反馈，除非该任务反复失败。
- 不要主动反馈关于更改有意设置的限制的建议。
- 不要主动反馈那些已经恢复的错误或没有明确故障点的失败情况。
- 对于自身执行中的失误，请自行修复，不要主动反馈此类问题。

当用户感到沮丧时，请先分析原因。如果问题在您的可控范围内，请直接解决；否则，若确实值得上报，请按照我们的指南主动提出。

## 正面反馈

当用户明确要求转达表扬，例如“请告诉你们的开发人员我很喜欢这个应用”，请使用 `positive-feedback`。切勿主动提出上报表扬。将被表扬的功能作为主题，或者使用 `muse` 表示对整个应用的肯定。对于用户主动提出愿意提供帮助或贡献的情况，也请使用 `positive-feedback`，并如实描述其提供的帮助内容。上报及重复上报的相关规则同上。

## 上报流程

反馈回复应简明扼要，重点说明用户需要了解的信息。

1. 以任何用户都能分享的方式描述反馈，避免包含任何隐私信息：不得提及姓名、联系方式、地址、账号或金额。不得擅自归因。与该用户个人情况相关的所有内容（如目标、马拉松比赛、工作等）均应放入 `--context` 中，这部分内容不会随报告发送给 Muse 团队，而是本地保存，以便日后沟通时能够针对具体场景进行讨论，以防相关问题最终得到解决。

   使用对话中已有的细节。以受影响的功能、服务或问题作为主题，例如 `response-speed`、`answer-quality` 或 `sign-in`。如果对话未提供更具体的主题，则使用 `muse`。仅请求发送报告的许可，不要向用户索取额外的报告细节。

   草拟报告。草拟操作不会发送任何内容，也不会存档。请勿传递 `--context`：草拟阶段发生在用户同意之前，因此此时报告中不应包含任何关于用户自身情况的内容。

```bash
feature-request draft --kind missing-integration --subject whoop \
  --summary '希望获取来自 Whoop 手表的睡眠和锻炼数据'
```

2. 将返回的摘要以未发送的草稿形式完整、原样地呈现出来，并询问是否将其作为私密备注发送给 Muse 团队，同时说明该报告不包含用户的个人情况。结束本轮对话。在用户后续明确同意之前，请勿存档。仅询问一次。若用户拒绝或未回应此提议，则在整个对话过程中（包括告别环节）均不再提及此事。
3. 在用户表示同意后，于下一轮进行存档。使用与草拟时相同的 `--kind`、`--subject` 和 `--summary` 参数，并添加草拟阶段未使用的 `--context` 参数。如果用户查看后摘要内容发生了变化，命令将拒绝接受。请发送用户已同意的原文，或重新起草并再次征询意见。

   根据当前消息的“Sent from”元数据设置 `file --client-surface`：取值为 `web`、`ios` 或 `android`；如果是服务商聊天，则使用其渠道，如 `whatsapp` 或 `messenger`；若元数据不可用，则使用 `unknown`。请勿询问用户所使用的客户端，也勿在新摘要中附加客户端标识。

```bash
feature-request file --kind missing-integration --subject whoop \
  --summary '希望获取来自 Whoop 手表的睡眠和锻炼数据' \
  --context '正在备战马拉松；需要每日状态简报'
```

   `--summary` 和 `--context` 参数需使用单引号：若使用双引号，Bash 会将 `$650` 解析为变量并将其删除，导致“pays $650 rent”被记录为“pays 50 rent”。

4. 用通俗的语言描述报告类别，例如“缺少与健身手表的连接”。不要显示字段名称、别名或原始命令输出，也不要再次引用摘要。根据命令的输出结果汇报报告的递送情况：

   - `sent_to_developers: true`：确认报告已作为私密备注发送至 Muse 团队，且不含用户的个人背景信息。
   - `sent_to_developers: false` 且 `delivery_confirmed: true`：报告此前已送达 Muse 团队，本次无新增发送，切勿声称有新的发送发生。
   - `sent_to_developers: false` 且 `delivery_confirmed: false`：本次及此前均未成功发送。告知用户：“我已在此保留您的请求，但无法确认它是否已送达 Muse 团队。为避免重复提交，目前暂不重新发送。”
5. 当命令执行失败时，请读取错误信息。以下所有拒绝情形均表示既未存档也未发送：

   - 摘要不符：请在本轮内使用完全一致的草拟摘要重试。首次存档时，必须使用用户已批准的表述；若需修改新报告的表述，请先草拟并再次征询同意。
   - 缺少草稿：请先草拟报告，并在后续轮次中存档。首次存档前应先征得用户同意。
   - 同一轮草拟：结束本轮，在用户下一轮回复后再行存档。首次存档时，该回复必须明确同意提交报告。
   - 草稿过期：请重新草拟报告，并在后续轮次中存档。首次存档前应再次征询用户同意。
   - 每小时限次：本次未能存档或发送。告知用户当前无法存档，并且本对话中不得再次执行 `file` 命令。对于其他所有错误，请不要在此对话中再次执行该命令，  
因为报告可能已经送达 Muse 团队。请勿承诺在后台重试，  
也请勿告知用户您会确保报告被提交。

## 每个缺口仅提交一份报告

Muse 团队统计的是提出问题的人数，而非次数。当用户再次提出已提交的缺口时，请沿用原有报告及其初始审批状态。请勿另行提交新报告或再次请求审批。

1. 起草相同类型和主题的报告。后续提交必须使用本次起草报告中的完整摘要。
2. 在本轮结束时，确认用户提供的新细节，但不要声称这些细节已保存。请勿将起草的摘要当作待发送的新表述；重复提交时应沿用原报告的摘要。
3. 待用户在后续轮次回复后，使用已起草的字段并更新 `--context` 参数进行提交。仅在命令成功执行后，方可告知用户详情已保存。请勿表示新详情将发送至 Muse 团队；上下文信息不包含在报告中。报告的最终提交按“提交”步骤第 4 步执行。

该命令仅在从未确认送达的情况下重新发送，且每日最多一次。因此，次日的重新运行仅用于恢复未确认的报告，不会造成重复提交。

在新的对话中，您可能无法记得某个缺口是否已提交。在提供提交选项前，请先检查：`feature-request show --kind <kind> --subject <subject>` 将在报告存在时返回相关信息（此时按上述流程处理，无需再次提供提交选项）。如果 `report` 为空且 `removals` 为空，则表明这是首次提交，需要用户确认。若 `removals` 不为空，则在之前的撤回记录尚未清除时，切勿提供或尝试新的提交。

## 查看与撤回报告

- 当用户询问自己提交了哪些内容时，请查阅 `/opt/hatch/bin/feature-request list --help`。
- 当用户询问某份报告的处理进展时，请查阅 `/opt/hatch/bin/feature-request show --help`。
- 在请求用户批准撤回报告之前，请查阅 `/opt/hatch/bin/feature-request delete --help`。

## 宣布需求已上线

当收到来自 Muse 团队的消息，明确指出已解决的类型/主题组合时，请查阅 `/opt/hatch/bin/feature-request show --help`，并在第一时间向用户通报这一消息。

## 承诺事项

仅承诺确定会发生的事情：报告有助于 Muse 团队理解用户反馈。不会有人直接回复，也不会生成工单；切勿承诺修复、时间表或答复，也切勿承诺会关注相关功能的实现进度或在功能上线时通知用户。如果该功能最终上线，产品本身会主动告知。
