# 媒体库

## 用途
在 Jarvis 的上传库或已连接设备的相册中查找用户的照片。`media-library` CLI 仅适用于已上传的照片。

## 设备照片

当用户请求个人照片时，若上传或附加的图片不足，可搜索已连接的相册以获取更明确的图库内容。

1. **发现设备。** 调用 `device.list`，然后调用 `device.describe`。选择一个可访问且在其 `commands` 中声明支持 `photos.search` 的设备：优先选择用户命名的设备，其次是标记为 `is_request_origin` 的设备，最后是其他手机。如有歧义，请进一步确认。
2. **搜索照片。** 调用 `photos.search`，并使用其支持的过滤条件缩小范围；“相册”指文件夹。若设备拒绝授权，应尊重其决定，并在完成必要设置后重试。遵循分页机制，若覆盖不完整，应如实报告，而非声称无匹配结果。
3. **上传照片。** 搜索结果仅返回元数据。如需查看或比对，可使用其支持的命令上传精选列表。等待上传完成，并考虑部分失败的可能性；接收并不等同于上传完成。
4. **定位照片。** 上传完成后，运行 `/opt/hatch/bin/media-library recent --limit 20` 获取照片的路径或 ID。将拍摄日期、文件名及 GPS 信息与设备端结果进行比对；对于较旧或已上传的照片，可使用 `get` 命令获取详细信息，并通过日期或 GPS 进行检索。仅凭文件名或时间先后无法证明照片身份。对于能确信匹配的照片方可直接读取；若存在不确定性，应如实报告，切勿猜测路径。

## 工具使用
对于已上传的照片，可通过 `exec` 执行 `/opt/hatch/bin/media-library <子命令> [选项]`。

子命令：
- `stats` — 查看媒体库概览（总数量、日期范围、描述状态）
- `search [--query "<terms>"] [--after YYYY-MM-DD] [--before YYYY-MM-DD] [--lat <f64>] [--long <f64>] [--radius <km>] [--has-gps] [--path <prefix>] [--limit N]` — 当指定 `--query` 时，按 BM25 算法进行全文检索排序；否则按拍摄日期进行结构化筛选。
- `recent [--limit N]` — 按上传时间列出最新上传的照片（默认 20 张，最多 50 张）。
- `scan [--ids <id1,id2,...>] [--query "<terms>"] [--after YYYY-MM-DD] [--before YYYY-MM-DD] [--limit N]` — 提供包含完整描述的更丰富摘要；至少需要指定一个筛选条件（上述任一标志，包括单独使用 `--limit`）。
- `get <media_id>` — 获取单张照片的完整详情（JSON 格式）。

输出格式说明：
- `stats`：纯文本，包含“照片总数”、“日期范围”以及描述状态统计（`ready`、`pending`、`failed`、`rejected`）。
- `search`：每行结果格式为 `<media_id> | <path> | <date> | [<location> |] <summary_short>`，下方可选显示匹配片段。
- `recent`：与 `search` 相同的简洁格式，不含匹配片段。
- `scan`：每项结果以文本块形式呈现，包含 `media_id`、`path`、`date`、`location`、`summary` 和 `detail`。
- `get`：JSON 格式，包含 `media_id`、`rel_path`、`mime_type`、`size_bytes`、`taken_at_local`、`taken_at_local_date`、`gps_latitude`、`gps_longitude`、`location_text`、`location_json`、`exif_json`、`description_status` 以及 `description`（嵌套字段：`summary_short`、`summary_full`、`people_text`、`activity_text`、`objects_text`、`ocr_text`、`location_hint_text`）。

结果中的 `path` 字段为相对于主目录的相对路径。

## 操作规则

1. **工作流程。** 首次使用时先查看“统计”→再进行“搜索”或“最近”查询→通过“扫描”获取候选对象的更详细信息→调用“获取”以获得完整信息→仅当用户希望查看图片或描述不够充分时才“读取”图片。大多数问题仅凭描述即可解答。
2. **统计结果解读。** 如果总数为0，说明上传的媒体库为空或尚未设置——简要说明这一点，并在有可用连接设备的情况下，检查其相册以响应个人照片请求。如果总数较低（少于约20张），则提示媒体库规模较小。若待处理项较多，文本搜索可能会遗漏未添加描述的项目——此时应优先使用“最近”或按日期筛选的搜索。
3. **机会性使用与主要用途。** 当媒体库可能有助于回答问题时，可快速试探性地执行一次“统计”及“搜索”或“最近”查询；若无有用结果，则无需继续深入。当用户明确要求查找、展示、识别、标注日期或定位某张照片时，应将媒体库视为主要信息源，并通过多次搜索、“扫描”和“获取”等操作进一步挖掘。
4. **上传的媒体库搜索属于低成本的本地PostgreSQL查询**（通常耗时毫秒级）。不必犹豫，可尝试多种查询——变换关键词、筛选条件和查询角度，直至找到用户所需的内容。
5. **全文检索语义。** 单纯词项之间默认以OR关系连接，按BM25算法排序（匹配词项越多，排名越高）。支持AND/OR/NOT逻辑运算。去除标点符号后进行前缀匹配。增加OR连接的词项会使结果范围*扩大*，而非缩小——若需缩小范围，应改用AND、日期筛选或GPS筛选。
6. **从用户提供的关键词出发**，而非猜测内容。仅在直接查询未能命中或返回无关结果时，再借助同义词、记忆或对话中的上下文，以及相关词项来扩展搜索范围。
7. **位置信息。** 已地理编码的城市、县、州及国家名称均包含在搜索索引中——例如，“search --query 'Tokyo'”即可生效。如需基于GPS的附近范围搜索，请先调用`map.geocode`并以该地点作为查询参数，再使用返回的坐标执行`search --lat <lat> --long <lon> --radius <km>`（尺度：0.1用于精确点位，5用于街区，50用于都市区）。
8. **人物。** 使用外貌描述（如“穿红裙的女人”），而非姓名。
9. **记忆。** 当用户提及事件或行程时，可对照记忆核对日期和地点。
10. **在查找特定照片时**，应展示已找到的结果，并确认是否为用户所要的照片。
