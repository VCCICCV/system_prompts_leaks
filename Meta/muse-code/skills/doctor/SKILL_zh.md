# 诊断

将 Muse Code 视为已安装的产品进行诊断。仅当用户明确调用 `doctor` 命令，或从二进制文件/运行时证据出发，明确要求对 Muse Code 本身进行调试/排查时，才使用此技能。假设用户拥有二进制文件，而非源代码树。帮助用户理解应用的工作原理，收集最小且安全的证据集，定位可能出错的层级，并给出下一步的安全操作建议。

## 范围

- 仅在用户明确调用 `doctor`、请求使用 `doctor` 技能，或明确要求调试/排查 Muse Code 产品的异常行为（如应用、CLI、TUI、桌面端、崩溃、提供者/模型、设置、认证、信任、技能、插件、MCP、会话、恢复、导出、追踪、审批、沙盒、更新，或非预期输出）时，才使用此技能。
- 当用户询问 Muse Code 的工作原理、状态存储位置、日志/会话/追踪的具体含义，或如何收集 Muse Code 支持包时，也使用此技能。
- 当用户询问当前 Muse Code 会话中之前发生了什么，或明确选择较早的 Muse Code 会话作为证据时，也使用此技能。这不包括普通的仓库历史记录，也不包括未指定的第三方代理会话。
- 切勿将此技能用于常规的仓库工程任务：代码实现、第三方项目缺陷、基准测试/评估任务、构建或测试失败、命令卡顿、工具链问题、CI 失败，或非 Muse Code 代码库内的本地调试。除非证据指向 Muse Code 本身，否则应按常规工程流程处理。
- 首先将用户视为产品使用者，而非仓库工程师。
- 对于纯粹的设置问题，或用户明确要求修改设置但无产品故障需要排查的情况，请改用 `manage-settings` 技能；“诊断”技能仅将设置作为其正在调查的故障的证据来读取。
- 除非用户明确要求，否则不要创建 issue、分支、提交、PR，不要安装/启用/禁用技能或插件，不要更改设置/认证/信任，不要上传日志，不要执行实时提供者/网络检查，也不要编辑代码。
- 不要输出密钥、原始提示、原始模型负载、认证令牌、API 密钥、Cookie、Bearer 头部，或完整的会话日志。优先使用脱敏后的导出数据、键值存在性检查，以及简洁的摘要。
- 如果某个模块没有独立的应用日志，请说明这一点，并改用会话日志、崩溃报告、追踪检查，或导出证据，而不是凭空臆造路径。

## 心智模型

在请求日志之前，先解释相关的产品路径：

- 二进制文件从用户的配置目录读取设置/认证/信任信息，并将会话、崩溃信息、模型目录缓存和内存数据写入数据目录。
- Muse Code 会话是恢复、追踪检查、导出和支持的主要载体。优先使用会话 ID 或会话日志路径，而非终端输出的截图。
- 提供者/认证失败通常是配置、环境、模型目录、网络或凭据问题所致。在归因于模型之前，应先排除这些因素。
- 技能/插件/MCP 是加载的产品功能。应分别诊断其发现、激活、信任、验证和运行时错误。
- 追踪/导出记录了二进制文件所见及所做，它是证据，而非可直接粘贴的原始日志文本。

## 分诊问题

1. 请指出发生故障的模块及具体症状。
2. 记录命令、当前工作目录、提供的会话 ID/路径（如有）、用户是否希望继续或检查该会话、大致时间、相关的提供者/模型，以及问题是否可复现。
3. 只有在缺少关键信息会妨碍安全的本地检查时，才请求补充缺失的信息。优先获取：确切命令、会话 ID/路径、时间范围，以及是否可复现。
4. 如果用户只是想了解原因，请先进行解释，避免立即执行检查。

## 产品证据地图

收集能够解释问题的最小只读证据集。根据症状调整证据收集方案，不要默认执行所有条目。

以下配置与数据根目录构成了 Muse Code 的全部本地状态面。位于这些目录之外的任何 config、日志或会话文件都不属于 Muse Code 的状态——切勿将其作为产品当前的配置、日志或会话证据呈现。
诸如 `CODEX_HOME` 之类的变量仅在明确请求导入或兼容性证据时才相关，并且始终归属于其所属的产品。

1. 构建/来源信息：运行 `muse --version`；当可能存在多个副本时，还应记录 `command -v muse`。
2. 配置/数据根目录：`$XDG_CONFIG_HOME/muse` 或 `$HOME/.config/muse`；`$XDG_DATA_HOME/muse` 或 `$HOME/.local/share/muse`。
3. 本地文件：`settings.json`、`auth.json` 和 `trust.json`；在必要时读取设置，但仅报告认证/信任的存在及其提供者名称。
4. 数据目录：数据目录下的 `sessions`、`memory`、`model-catalog` 和 `crashes`。对于崩溃数据，仅汇总报告元数据和文件路径，而不展示会话内容。
5. 会话证据：优先使用 `muse export --redacted --out <file>` 导出最新的工作区会话；若用户提供会话句柄，则使用 `muse export --session <id-or-session.jsonl> --redacted --out <file>`。
6. 继续会话的句柄：若用户提供了 Muse Code 会话 ID 并希望继续该会话，请引导其使用 `muse resume <session-id>` 或 `muse resume --last` 进行交互式续接。仅在用户明确要求无头续接时，才使用 `muse exec --session-id <session-id> "<follow-up>"`。只有在确认会话属于其他工作区后，才为 `muse exec --session-id` 命令添加 `--allow-workspace-switch` 参数；交互式 `muse resume` 不接受此参数。如果在退出、分叉或交接时打印了 `muse resume <session-id>`，则将该命令视为标准句柄。
7. 跟踪证据：使用 `muse trace inspect --session-log <session.jsonl> --render-mode compact`；对于多轮日志，可添加 `--run-id <uuid>` 或 `--all-runs`；仅在需要结构化分析时才使用 `--format json`。
8. 用户支持包：若有 `/feedback` 接口，优先使用；否则，优先提供经脱敏的导出会话、跟踪检查结果、崩溃元数据以及简明的复现步骤。
9. 技能/插件/MCP：若问题指向技能或插件，可使用 `muse skills list --enabled-only --json`，并安全地执行 `muse plugins ... --help` 或验证命令。
10. 环境：仅根据是否存在及具体值检查相关非敏感变量，例如 `MUSE_MODEL`、已脱敏凭据的基础 URL 变量、XDG 目录、用于导入/兼容性问题的 `CODEX_HOME`，以及遥测相关的变量（仅检查是否存在）。

## 优先使用当前会话证据

若需了解当前 Muse Code 会话中先前发生的情况，请在导出或全面检查跟踪日志之前，先使用同级的辅助脚本 `scripts/session-evidence.py`。在 `read_skill` 提供物理诊断包路径后，运行：

```bash
python3 <doctor-skill-dir>/scripts/session-evidence.py --session-log <current-session.jsonl> --workspace "$PWD"
```

运行时的会话上下文中已包含当前日志的准确路径。请勿向用户询问已存在于其中的路径，不要猜测最新会话，也不要先在会话存储中查找。主机也可能提供 `MUSE_CURRENT_SESSION_LOG`，此时该辅助脚本无需指定路径即可运行。

若需针对明确选定的早期 Muse Code 会话，请使用确切的路径或 ID：

```bash
python3 <doctor-skill-dir>/scripts/session-evidence.py --session-log <explicit-session.jsonl> --workspace "$PWD"
python3 <doctor-skill-dir>/scripts/session-evidence.py --session-id <explicit-session-id> --workspace "$PWD"
```

两种显式的早期会话形式都限定在当前工作空间范围内，并且在遇到未知的工作空间元数据、不匹配或歧义时会采取失败关闭策略。请使用 `--kind`、`--path`、`--tool`、`--run-id` 或序列范围来缩小后续证据的搜索范围。投影事件会保留其来源流，默认的边界会同时为主会话和子会话保留证据，以防止繁忙的子会话抹除父级时间线。始终将持久化操作与助手的声明进行比对，尤其是在跨压缩和子活动的情况下。只有当这种有界的投影不足以满足需求时，才使用经过脱敏的导出或压缩后的跟踪日志。切勿将原始会话日志直接粘贴到模型上下文中。

## 安全诊断实时会话的所有权

当恢复提示会话已打开，或者原始终端不再接受输入时，请按以下路径操作：

1. 首先选定确切的会话，并如上所述运行 `scripts/session-evidence.py`。限制输出范围并比较其最新持久化活动的时间戳；切勿从全局的进程或文件搜索入手。
2. 将 `.session.lock` 视为基于 inode 的内核租约，而非标记文件：文件存在并不等同于锁的所有权，`flock` 保护的是已打开的 inode。在竞争状态下删除某个路径名，可能会导致另一个进程在原写入者仍持有旧 inode 的情况下创建并锁定一个新的 inode。
3. 使用非阻塞的排他性 `flock` 对该锁进行只读探测。以不截断的方式打开文件，仅报告“可获取”、“存在竞争”、“缺失”或读取错误，随后立即关闭。切勿以探测为目的启动会话。
4. 只将锁内容中的 PID 作为参考线索。工具沙箱或 PID 命名空间可能无法看到宿主进程；在其内部通过 `ps` 或 `kill -0` 确认不到该 PID 并不能证明宿主进程已终止。当这一区别至关重要时，应请求宿主 shell 进行核查。
5. 检查有界会话证据中是否存在涉及 `.session.lock` 的先前文件变更，尤其是删除、解除链接、替换、截断或重新创建操作。如果路径已不存在而旧活动仍在推进，则应停止恢复尝试并保留相关证据。

切勿在诊断或修复过程中删除、替换、截断或重新创建 `.session.lock`。切勿在诊断阶段向所有者发送信号。不要请求接管或使用任何所有者控制端点。请用户正常退出拥有该会话的进程，然后明确地重新尝试常规恢复。

在推荐下一步行动之前，请先对结果进行分类：

| 证据 | 分类 | 安全的下一步操作 |
| --- | --- | --- |
| 租约可获取 | 当前无内核所有者；残留的路径名并无危害 | 重试常规恢复；无需为整洁而清理该文件 |
| 存在竞争但会话活动仍在推进 | 存在活跃的所有者及运行时；终端连接可能是失败的环节 | 保留所有者；检查终端/PTY 的证据，或让其正常退出 |
| 存在竞争且活动已停滞 | 内核所有者仍然存活，但运行时和终端状态未知 | 请用户正常退出拥有该会话的进程，然后明确地重新尝试常规恢复 |
| 存在遗留的所有者控制痕迹 | 来自旧版二进制的诊断残留；内核租约仍具权威性 | 仅将其视为诊断信息；在重新尝试常规恢复前，让拥有该会话的进程正常退出 |
| 锁路径已被删除或替换，而旧活动仍在继续 | 曾发生过不安全的变更，可能存在双重写入者 | 停止进一步的恢复尝试，同时保留两个 inode 和会话的时间线，并上报问题；切勿重新创建该锁 |

存在竞争的租约只能证明内核层面有活跃的所有者，而无法说明其 TUI、终端、服务提供方或运行时是否健康。在提出产品层面的修复方案之前，应结合活动记录以及宿主可见的证据，锁定故障的具体环节。

## 缩小排查范围的流程

从证据出发进行分析：1. 用一到两句话明确指出最可能的层级。
2. 说明下一项检查将如何验证或推翻该假设，并执行该项安全的本地检查。
3. 根据检查结果更新假设，仅在下一项检查仍然相关且安全时继续。
4. 如果需要使用实时服务端、真实网络、破坏性命令或上传操作，请先说明原因并获得用户的明确许可。
5. 如果怀疑存在自定义配置或本地状态问题，仅在说明不会读取或修改用户真实设置后，再与一个隔离的临时 XDG 配置/数据配置文件进行比对。

## 常见诊断路径

- 启动/认证：二进制路径 → 版本 → 配置加载 → 认证提供者是否存在 → 模型/目录选择 → 第一道网络边界。
- 提供者/模型：所选提供者/模型 → 去除凭据后的基础 URL → 认证是否生效 → 模型目录缓存 → 请求追踪/错误摘要。
- 会话/恢复：会话 ID/路径 → 工作空间匹配 → 会话日志是否存在 → 恢复/导出/追踪命令 → 确认用户是希望检查还是继续。
- 技能/插件/MCP：列表/发现 → 激活/信任 → 验证输出 → 运行时追踪或启动诊断。
- 桌面/TUI：打包应用/二进制版本 → 会话 ID → UI 可见的症状 → 崩溃/报告元数据 → 追踪/导出证据。说明何时仅通过源码测试无法确认打包应用的问题。

## 修复边界

- 仅修改设置的修复：提出具体变更，并仅在用户明确请求后才应用；保留未知设置字段，并通过回读或特定命令进行验证。
- 工作区代码修复：仅当用户明确要求修复当前仓库中的代码时，才切换至“先让测试失败再让其通过”的开发流程。先复现问题，精准修改，重新运行同一项检查，若仍失败则报告为未完全修复。
- 产品缺陷报告：若证据指向 Muse Code 本身且无安全的本地修复方案，则提供一份简洁的支持包，包含症状、版本、配置/数据路径、会话/崩溃路径、已脱敏的导出/追踪证据、可能原因及下一步行动。

## 完成报告

应包括：

- 症状及受影响的范围。
- 与此故障相关的产品心智模型。
- 收集的证据、检查的路径、执行的命令及其结果。
- 执行的脱敏处理。
- 最可能的原因及置信度。
- 已实施、拟议或未实施的修复方案。
- 剩余的不确定性及下一步最安全的检查。
