# 时刻

## 在目标处

拆分：按拟定的单元，见 `SKILL.md` § 1；形状：见 `references/roles.md` 中的“按形状拆分”；容量来自 `host-manager resources`。排序规则：用户优先级 > 依赖已就绪 > 写冲突（每个文件只有一个所有者）；绝不规划红色的目标分支。本机默认如此；其他机器仅在用户明确要求时启用，且只能保存一个。Herdr：每个项目一个工作区，每个线程一个标签页；tmux：一个窗口。独立线程绝不会因缺少依赖而等待；输入为兄弟分支未合并的线程，应立即基于该分支创建一个工作树（简述：“待<兄弟>合入后变基到主分支”），只保留尚无输入的任务。简述须说明目标、验收依据、输出格式，以及可读取的内容与边界：目标及其衡量标准，绝不涉及具体技术或代码草图（见 `references/roles.md`）。提案以 JSON 格式，或由负责人撰写并置于项目目录下（`library/`），绝不使用共享的 `/tmp`。每个频道配备独立监听器：首次行动时，在执行 `resume` 前先启动监听器。立即开启：“修复四个模块中的十个 Lint 警告”→按模块分配四个线程，并告知计划。先确认细节：“加快构建速度”（具体加速多少？）；只需一次确认性提问：是否推送到共享分支，或是否有删除操作（见 `SKILL.md` § 2）。已完成或仍开放的目标：若目标明确指出需合并，则排队或通过合并命令使其 PR 合并；仅写“每个 PR 各自处理”则保持其开放状态——应在完成条件中注明，并在计划行中说明。`init --detach --unattended` 可启动一个独立的无人值守协调器——仅当用户明确要求且无需其在场时启用，绝不在你仍在参与的聊天中启动。

## 发起后

简单目标：在一轮内完成“提出”、“发起”及制定计划（若他们在首轮前将 `PROJECT.md` 设置为 `auto`，则可在同轮内同时提出并发起）。否则需征询意见后再结束本轮；对方任何肯定答复即视为发起。发起后，于同一轮内，激活并记录唤醒机制：若监控工具存在（每位 Muse TUI 会话均配备名为 `monitor` 的工具——务必先尝试调用以确认其存在，切勿仅凭工具列表判断），则安装并记录打印出的 `go` 就绪行，并记录 `tick <slug> --arm monitor --command "<那行>"`（持久激活；该行本身见 `verbs.md` § go）——每 30 秒在消息流中输出一行 WAKE；若非该行，则记录一条警告信息；若调用失败，则以调度器作为后备方案。若无监控工具：当 `doctor` 列出调度器时，安装之，并记录 `tick <slug> --arm scheduler --command "<那条目>"`（该定时任务将在另一个进程中运行，不会主动唤醒你）；仅在两者皆不存在时才启用 `--arm passive`（并附上 `--monitor-failed "<失败调用的行>"`——下次检查将在你的下一轮进行）——无论哪种情况，都应明确告知对方，你的下一行指令将随用户的下一条消息一并发出，切勿承诺自动交接。唤醒机制仅监控项目，不监控频道。发起轮的第一行是清单：针对每个已开启的线程，原样重复 `go` 收到的命令（包括 `attach` 和 `follow`），仅在 TUI 中显示；频道仅接收计划，不含附加命令（第48条规定）。一旦唤醒机制启动，立即结束本轮；下一条 WAKE 行即为你的下一次输入：发起轮中仅有一条 `context`，不循环；第二条 `context` 若呈现相同画面，则表明一切未发生变化。运行时根据你的计划给出的 `goal` 建议不属于输入：不计入行数，也不需 `sleep 1`——本轮即告结束。收件箱路径（`wake_path: inbox`）：照常激活监控工具；线程的报告也会以消息形式更早送达你（见 `references/session-protocol.md`）。

## 在唤醒时

- `context`仅调用一次：在回合开始时调用，此后本回合不再调用。
- 每次唤醒到达时，在任何簿记操作之前——即移动了什么、下一步是什么、是否必须行动——都输出一行状态信息，置于已打印的☐/✅标记下的`plan_lines`之下；绝不会只显示确认信息，也不会流式输出进度。
- 以线程的`name`命名；当用户可能需要输入时，才在括号中附上ID；除`attach`命令外，绝不单独使用裸ID或会话名称。
- 变为`waiting-on-you`（如权限对话框）的线程，其`attach`命令应写在该行中，随后回合结束。你绝不在该面板中按任何键（包括Esc），也绝不开口或指示它选择哪个选项；由用户自行操作。
- 对于`went idle without a report`这一行：仅执行一次`read <ref> --tail`；若屏幕上出现询问，则视为其`BLOCKED(HUMAN)`（对用户而言）；若无内容，则发送一条`send <ref> --type --automated`请求报告。绝不保持沉默。
- 任何变更发生时：执行`remember <slug> --text "<发生了什么；下一步是什么；完成意味着何时变更>"`——作为单行检查点，以便`resume --takeover`时不会丢失任何信息。
- 一旦你已采取行动，即结束本轮：下一次唤醒、后续线程或用户的下一行会将你重新唤回。绝不在一轮中休眠、轮询或等待。
- 先查看：在任何`propose`、`go`、`follow`或`open`之前，先处理`context`的响应。
- 恢复现有文件夹，绝不要初始化：新的协调会话以`resume <slug>`开始，`--takeover --confirm`采用用户自己的接管指令（绝非针对线程的“go”），并在之后执行一次`tick --arm`。
- 评审轮次应发往其实时空闲线程（通过`send`），绝不去新建或发往`working`线程。
- 针对线程代理的任何操作——引导、提问、评审轮次——均应先通过`send <ref> --type`发出，绝不用对等路径（整体形式为`host-manager send <ref> --text "<line>" --type`）。单纯的`send`仅用于通知正在观察面板的人类，绝非引导；若编辑器不为空，则等待或告知用户，绝不要将其标记为已送达。
- 若向频道的`reply`失败，仅声明一次并结束本轮；下一次唤醒或用户的输入会重试——绝不要进入重试循环或休眠。
- 收件箱路径：`references/session-protocol.md`。

## 关于报告

遇到`PR: <url>`一行时，立即执行`follow <slug> --pr <url>`，每当目标允许合并时都如此操作：助手会将其传递至实时跟进线程，切勿自行将URL输入该线程（`PR:`行指代的是跟进线程，而非`land`线程；推送到本地源的分支也算PR；若某轮叙述了`PR:`行却未执行`follow`，则视为失败）。遇到`DECISIONS:`行时，先说明，再执行`accept`，一轮之内完成。先说“正在验证”，然后仅在核实证据后才执行`accept`，绝不对线程自身转述的说法直接认可，并在同一步骤中使用`remember --from-thread <id>`记录下来；其`Cost:`行即为该线程的开销。应在该线程的工作树或项目文件夹下的全新克隆中进行验证，绝不要在用户的克隆中运行测试套件或执行`git checkout`/`pull`：你在那儿完全不使用Git；所有临时操作均应在`<project>/library/`下进行，绝不在共享的`/tmp`中。
  
## 关于PR事件

除非事件是`merged`（需在目标分支上验证）或线程主动要求，否则均由跟进线程负责。
  
## 关于已消失的线程

`orphaned`：视情况决定是否重新打开；`exited`：其报告即为最终结果。
  
## 关于用户的变更

被丢弃的线程应在同一轮内停止；其分支和工作树仍保留：删除分支——无论是在远程还是用户的克隆中——都可能导致工作丢失，这是用户可选的操作，绝非你的职责。需求变更时，应先在`PROJECT.md`中重写`## Done means`/`## Scope`，然后再通过`host-manager send --type`将变更增量发送给所有受影响的实时线程，其中跟进线程优先。落地环节归跟进线程负责，绝非你或任何工作线程、收尾线程的职责。相关决策请参考`SKILL.md`中的**Decisions**列表。对于直接提出的问题，应先以带有证据的建议形式作答，而非状态报告，且应在开展任何线程相关工作之前完成。

## 已完成

所有已接受且符合要求的线程均已处理完毕：`agents.py archive <slug>`
请自行记录，然后用一行说明哪些已关闭、哪些仍保留（未合并的分支、工作树、拉取请求）；不再对每个线程单独执行 `stop`。`agents.py archive` 会移除已提交且状态干净的工作树（绝不会使用强制操作）；分支和拉取请求则会保留。只有在仍有未接受的线程运行时，才使用 `--confirm` 并以用户原话进行确认（`accept` 已结束其会话）。
