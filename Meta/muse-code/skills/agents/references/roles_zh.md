# 角色：四个简报模板

角色仅用于预填简报。没有角色动词，也没有除 `work` 和 `follow` 之外的 `kind` 属性；助手不会读取任何额外信息：只需将模板粘贴到线程的简报中，填好空缺，仅凭这段文字即可指导整个线程的运行。

**命名。** `name` = `<角色>`、`<角色> <给定名>` 或 `<角色> (<引擎>)` — 如 `Researcher Ada`、`Tester (codex)`、`Implementer core.py`；`id` 则为角色名称或 `角色-给定名`（如 `researcher`、`researcher-ada`），以便用户输入时与 ID 匹配。你编写的每一行都以角色名称开头，并在用户可能需要输入时，在括号中注明一次 ID。

| `id` | `name` | 用户看到的内容 |
| --- | --- | --- |
| `researcher` | `Researcher (muse)` | `Researcher (muse) [researcher] — 阅读解析器，只读` |

**所有权。** 每个写作者的提案行都会标注 `owns`，即其可能修改的文件；简报会为每个线程明确列出其负责的文件及其相关文件。当两个作用域共享同一文件时，应按文件而非功能来划分职责，或者让第二个线程基于第一个线程的分支进行开发。

**检出。** `worktree: null` 表示该线程在你的本地工作区中运行，除非其 `cwd` 指定了其他路径；且不会执行任何向该区域写入的 Git 操作（如 `fetch`、`worktree add` 或在用户的克隆中进行检出）。构建或分支应使用独立的 `worktree`，或在 `<project>/library/` 下创建一个克隆。

**简报。** 用一行简洁的文字开篇，说明该线程的职责——这一行内容将在“## 周围的项目”中被其他线程看到，也会在用户执行 `go` 后显示；模板则置于其下。每次都要明确以下四点：目标、输出格式、线程可读的内容以及其边界。切勿重复或与助手自身的“## 工作方式”部分相矛盾（如路径、谁负责、推送内容等）。切勿写“无需提问”或“无人值守运行”：无人值守的线程会在报告中通过 `BLOCKED(HUMAN):` 提出问题，并在该行列出选项，且绝不会打开 TUI 对话框——因为无人监控其窗口，协调人会直接向用户提出问题。当设计文档已合并至主分支时，简报应指向该文档，而不再自称为权威版本。

**报告。** 使用 `report <slug> <id> --file -` 并将文本通过标准输入传递：助手会自行写入文件，从而避免编辑器对话框阻塞有人值守的线程。

**时机。** 写作者在线程启动时即开始工作。只读角色（如评审者、测试者）此时会被提议，但仅在其负责阅读的内容（如 PR 或报告）出现时才真正开启，绝不会在没有任何内容可看时就于线程启动时启用。

**验证。** 提案行上的 `test_command` 应为目标本身的验证命令，原样照搬。切勿规划红色的目标分支：涉及行为变更的代码片段应包含对现有测试的更新，且合并闸门应确保测试套件全部通过，而非罗列一系列可接受的失败项。

**杂项。** 线程内部出现网络或权限提示时，应以一行 `BLOCKED(HUMAN):` 的形式通知协调人，切勿自行拒绝。两个线程可以共用一个模板（在两条分支上取最优结果）；也可以不使用任何模板；在用户选择之前已被提议的线程，应在简报中再次提及用户的选择；用户输入的一行指令是引导，而非简报内容。**按形态拆分。** 规则见 `SKILL.md` 第1条；其
形态为：实现 → 按所拥有的文件或模块（每个文件仅一名负责人）；追捕 → 一名负责落地修复的调查员（仅在有其他假设时才增加第二名），外加最多一条度量线程；探索或研究 → 按领域或独立问题（crate 组、子系统、假设、来源）划分，每项由一名研究员负责，最终合并地图或答案；小型树状结构或依赖性问题 → 一条线程；其余情况 → 使用同一套测试。凡标注“在 X 存在之后”的简报，应在读取 X 的回合提出并开启，绝不在 `go` 时刻开启。度量线程的首个任务在未修复的基线上于 `go` 时刻立即执行，其结果数值计入汇总——后续线程应将 PR 合入到该 PR 自身的绿色分支，而绝不能合入度量线程的循环分支，除非目标明确将度量结果作为合并条件。

若简报将失败视为可由兄弟线程修复，则规划一条红色主线：切片负责更新测试，或由测试线程在该分支上即时开启，两者同步合入。

## 实现者

- 目标：<变更内容；来自哪个 issue 或规格说明；对该线程而言，“完成”指已合并的 PR 或通过的测试>。
- 输出：在 `<worktree>` 分支上提交一个 PR；报告首行注明 `PR: <url>`；一行 `STATUS:`；运行并命名所有测试及其结果；对于简报未明确的每一项（版本号、公开名称、不在 `owns` 列表中的文件），均需添加一行 `DECISIONS:`——若需用户决策，则标注为 `BLOCKED(HUMAN):`。
- 所属：提案行中注明 `owns: [<files>]`——随后简报会告知本线程及其兄弟线程各自负责哪些文件；切勿触碰列表之外的内容。
- 可读：当前工作区内的仓库、项目的 `MEMORY.md` 和 `TASKS.md`，以及关联的 issue 和规格说明。`MEMORY.md` 及其他线程的工作区均为只读。
- 边界：仅编辑自身工作区及所拥有的文件；行为变更的测试在修复前可能失败；禁止变基与强制推送；提交 PR 并移交至报告——后续线程负责推动其合并；凡需用户决策的事项，均应写入 `BLOCKED(HUMAN):` 行。
- 记录：`worktree: "<branch>"`，`cwd: <repo>`。

工作线程的简报在其推送并出现 `PR:` 行时即告结束——“绿了就合入”、“自行合并”、“无需等待我即可推主干”、“若检查失败则修复后再次推送”，这些仅为后续线程的指示；后续行绝不在 `go` 时刻提出或开启，而是在首次出现 `PR:` 行时通过 `follow --pr` 命令生成。

## 审查者

- 目标：审查 <PR 链接或 diff>，聚焦 <单一视角：正确性、安全性、是否符合规格>。仅指出问题，不作批准。
- 输出：每行一条发现——文件、重要性、最小修复方案——并标注为 Blocker / Should / Nit；“无发现”亦为有效报告。
- 可读：PR 及其检查结果、规格说明与 issue、PR 提交点所在的仓库；`MEMORY.md`。
- 边界：绝不批准，不得对兄弟 PR 的线程提出更改请求或进行解决——所有发现均上报协调人决定；不得向其推送任何内容；不得编辑任何工作区。
- 记录：仅阅读时 `worktree: null`；需构建时则使用分支。
在读取所审查 PR 的 `PR:` 行的回合开启，而非在 `go` 时刻。

## 测试者

- 目标：以黑盒方式在 <表面层：CLI、TUI、API> 对 <变更> 进行验证；场景已列出。
- 输出：每个场景一张表格——步骤、预期、实测、结论——并附上准确的命令；日志与录制文件存于 `<project>/library/` 下。
- 可读：构建好的产品、规格中的场景、`MEMORY.md`；仓库为只读。
- 边界：除非简报另有要求，否则不得修改代码；缺陷应以复现步骤的形式记录为报告条目，而非直接修复；绝不可仅凭声称即判定场景通过。
- 记录：`worktree: null`；仅在被要求同时修复时才使用分支。
在读取所测试 PR 的 `PR:` 行或报告的回合开启，而非在 `go` 时刻。

## 研究员（只读）- 目标：以证据回答<问题>；说明协调员将据此作出何种决定。
- 输出：仅报告——先给出答案，再列出证据及其路径和链接；篇幅较长的材料存入`<project>/library/`目录下；另设一个`## 记住`小节，列出项目应保留的一两句话。
- 允许查阅：代码库、文档、问题列表，以及在任务说明允许时访问网络；还包括`MEMORY.md`及同级的任务说明文件。
- 限制：仅可读取，不得修改。`worktree: null`，无分支、无提交、无拉取请求。您的当前工作目录即为协调员的工作区：在此处修改的文件会直接更改协调员的代码树——请拒绝任何会向其中写入的操作，并在报告中说明。
- 记录：`worktree: null`，`cwd: <待读取的工作区>`。
