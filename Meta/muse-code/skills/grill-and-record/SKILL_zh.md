# 烤问与记录

仅当用户明确要求进行“烤问”并同时需要持久化文档，或直接调用本技能时，才使用此技能。仅因复杂性、模糊性或可能需要文档而触发本技能是不允许的。本技能具有独立的访谈与文档编写契约。运行时请勿加载或调用 `grill` 或 `domain-modeling`。

## 访谈契约

1. 在向用户提问之前，请先在代码库、Issue、文档和代码中尽可能查找可发现的事实。仅就无法自行获取的判断或事实向用户提问。
2. 每次只提出一个促使决策的问题。简要说明推荐答案及理由，然后等待用户的回答。
3. 对于有明确范围的决策，优先使用宿主提供的结构化输入界面：
   - 当结构化输入界面可用且决策仅涉及2–3个简短的互斥选项时，使用 `request_user_input`。将推荐答案置于首位。每次调用时发送一个问题，包含 `id`、`header`、`question` 和 `options`；省略 “Other” 和 “None”，因为客户端已提供自由文本的退出机制。在烤问过程中，切勿设置顶级的 `auto_resolution_ms`：烤问中的决策必须等待人工答复，因为在整个访谈的核心正是用户的判断时，自动选择推荐默认值始终存在风险。
   - 在 Claude Code 中，对于同样的有限选项决策，使用 `AskUserQuestion`。
   - 仅当结构化界面不可用，或答案需要自由讨论时，才使用纯聊天方式。
   不得在提供结构化选项之前，以普通助手文本或自由问答的形式提出有明确范围的检查点问题。
4. 仅当用户明确要求，或问题涉及代理产品行为（如 Claude Code 与 Codex 的比较）时，才使用对比表格。
5. 追随依赖性决策，直至本技能判断决策树已穷尽。切勿提出最终的“我们结束了吗？”这类元问题。
6. 总结已达成的契约内容：目标、非目标、各项决策、约束条件、风险、验证方案以及未决事项。

结束访谈并不意味着授权实施。只有在用户另行明确提出实施请求后，方可执行。

## 文档编写契约

1. 在提出第一个问题之前，根据用户指定的目标以及代码库现有的文档规范，确定目标文档。检查本地说明、索引、规格说明、ADR、术语表及周边文档。若目标无法确定，则提出一个问题。切勿凭空创建通用的 `docs/grilling/<date>.md` 路径。
2. 创建或更新目标文档为“草稿”状态。每达成一项决策，立即以草稿形式写入，而非等到访谈结束。未决问题应清晰标注。
3. 若被中断或取消，应保留草稿及所有文件修改，并标记未决问题，不得自动撤销文档变更。
4. 仅在实际编写特定类型的文档（如 `CONTEXT.md`、ADR、术语表或其他格式）时，才查阅相关参考资料。
5. 日常的“撰写/编辑”工具事件即为文档工作的实时证明，无需重复输出 `Updated <path>` 的状态提示。
6. 明确的文档请求是硬性完成条件：若无有效的文档创建或更新，本次会话无法成功结束。“无需文档”且无任何文件变更的情况均不符合要求。
7. 只有经用户明确接受，文档方可从“草稿”转为“正式”。决策树穷尽并不等同于用户接受。
8. 最终回复中，应列出所有已更改的文档路径，以及其状态是保持“草稿”还是已转为“正式”。
