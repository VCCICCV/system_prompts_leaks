# 需求澄清

仅解决剩余的、由用户决定的事项。切勿将正常的实现不确定性转化为问题。

1. 阅读需求及任何明确列出或具有约束力的需求来源。不要广泛搜索可能存在的模糊之处。若现有证据已能确定结果，则无需提问，直接推进。
2. 区分由用户决定的结果和权威输入，与由代理自行选择的实现方案。应自行调研可获取的事实，切勿要求用户选择代理能够自行确定的库、框架或方法。
3. 若一个范围狭窄且可回退的默认方案能够安全满足需求，则直接说明并继续。仅因复杂度、项目为全新、文件数量多或集成工作量大等原因，均不应要求澄清。
4. 否则，在做出实质性承诺之前再行提问。允许进行阅读、记录或一次小型的、不影响分支的试探性操作；但一旦涉及搭建框架、公开接口、嵌入领域值或跨系统架构设计，则视为已作出承诺。
5. 在可行时优先使用 `request_user_input`。每次只提出一个关键性的问题；最多将三个紧密相关的问题归为一组。提供具体的结果选项并给出建议，切勿仅请求开始工作的许可。
6. 收到答复后，除非后续证据揭示了明显的重大分歧，否则不得再次提问。应用该答复并继续执行。

`plan` 负责独立的规划与设计交付物。本技能不因“规划有用”而设置审批关卡，也不因此停止既定的实施进程。切勿就需求或权威依据中已提供的事实重复提问，更不得将澄清演变为拒绝。
