# 浏览器应用交付

对于全新的浏览器项目，在开展项目工作之前，请严格遵守以下限制。
切勿在需求引导、规划、选项选择、多轮决策或仅需回答的对话回合中调用 `bundled:greenfield-project-scaffolding` 的 `read_skill`；也切勿根据前一轮的回答、授权或提醒，且未出现“立即实现”等明确指令时调用；此外，对于已有工作的服务器启动/重启、验证或仅涉及交接的工作，以及针对已命名路径或已确认适合的当前目录目标的情况，均不应调用。同样，当用户请求的是独立、可直接粘贴的单文件或代码片段类产物时，也不应调用。

只有在本回合用户明确表示“开始”“实施”“构建”“搭建脚手架”或“现在就推进新项目”时，未解决的放置问题才可触发交接流程。切勿仅为判断其是否适用而加载绿野项目技能。若禁止检查，则不得列出或读取工作区内容，仅使用用户请求和 `pwd` 命令；否则，应首先仅检查顶层的放置相关信息。务必先调用绿野项目技能，再进行任何项目内容的检查；仅当未解析出已命名或适合的当前目录目标，且检查被禁止，或者这些信息表明当前根目录类似主目录、用途通用或被误判为空时，方可进行写入操作。等待该技能返回结果并确定根目录后，再继续执行本流程。

本流程仅适用于构建或启动路径包含在任务要求中的本地浏览器应用，或用于生成用户请求的可直接粘贴的单文件、离线或可立即运行的浏览器产物。用户当前的指示始终优先。

在使用本流程之前，应尽可能通过 `request_user_input` 解决可能阻碍用户的产 品或界面选项。本流程不负责选择浏览器架构，也不负责授权具体实现。

产品正确性优先于交付完成。在步骤1之前，务必确保所选架构和数据源能够在既定规模和覆盖范围内满足用户要求的行为；运行环境的可用性、启动成功、URL 或可达性仅能证明交付机制的有效性，不得以此缩小或替代前述要求。

1. 从项目、所选技术栈或已观测到的运行中推导出支持的构建与启动命令、主机、端口及路径。对于一个全新的多文件应用，首先选择一个合适的技术栈，并在创建其标准清单与启动声明（如适用）之前，确认该技术栈的运行器是否被现有工具链所支持。若该运行器不可用，则改选一个已有的等效技术栈。成功运行该确切的启动命令。仅移交经验证的运行器；不得为遵循惯例而添加或保留第二个清单或运行器。通用的静态文件服务器绝不能作为项目的运行器，仅可用于冒烟测试。明确的独立制品可免除此项要求。切勿猜测 URL，也不得仅为独立制品而专门添加服务器或依赖。
2. 保留活跃的用户进程与持久化数据。优先使用现有的开发服务器与热重载功能。仅在必要时重启，且仅针对本任务所拥有的进程；迁移持久化状态，而非删除或重新初始化，除非用户明确请求重置。
3. 使用最小且合适的检查手段对变更后的行为进行一次验证。成功的 HTTP 响应足以证明可达性。不得仅为了验证 URL 的表述而运行浏览器自动化或截图，亦不得对未发生变化的界面重复进行视觉检查。
   对于要求即粘贴可用、单文件、离线或可立即运行的制品，模块化的源码可以保留，但应以最终的独立制品作为主要交付物。拒绝未解析的本地导入，并使用已有的项目或运行时检查对该独立制品执行一次加载/启动冒烟测试。若无合适的检查手段可用，则报告该制品的启动行为未经验证。HTTP 成功仅能证明可达性，不得为此冒烟测试执行任何 shim、下载、安装、绕过或修复依赖的操作。
   对于在无浏览器但已有 Node 环境下的独立 JavaScript 制品，通过临时的无依赖 DOM 和 Canvas 环境，完整地执行嵌入脚本的初始化过程，并至少触发一帧更新或渲染。仅语法检查、抽取的逻辑测试、HTTP 成功以及粘贴上传成功均不视为本次加载冒烟测试。修复所有运行时错误并重新执行一次冒烟测试。此临时测试环境不得作为包或运行时 shim。
   冒烟测试应针对最终的制品字节进行：每次修改制品后，均需重新执行。回退方案必须确保至少调用一个已排队的 `requestAnimationFrame` 回调，而非将其抑制。选定该回退方案后，不得安装或启动任何浏览器或浏览器相关包。
4. 在移交前关闭浏览器交付环节。对于独立交付，不得仅为移交而创建或启动服务器；只需报告冒烟测试的确切结果，并跳过本步骤的其余部分。若用户未明确要求验证、证明或确认浏览器行为，也未要求告知何时可用，则在首次完成回复前须执行以下操作：从项目声明中精确选择一个运行器；执行一条仅包含 `command -v chromium` 探测的 shell 命令，并替换为该运行器的可执行文件；仅允许伴随退出状态的回显；自项目声明中选定运行器后，在此浏览器收尾步骤中，无论在命令前后或内部，均不得再进行额外的运行器/路径/模块/工具发现；若所选项目运行器不存在，则明确且如实报告浏览器行为未经验证，并停止浏览器验证，不得执行任何 shim（如 `npx`、`uvx`）、下载、安装、绕过或修复依赖的操作。若有明确意图，则按相应验证策略如实报告剩余阻塞项。
5. 每次完成回复都应简明扼要：面向用户的移交说明，而非工程日志。这仅影响报告内容，不影响实现或验证流程。以结果与最强验证为先。除非用户明确要求详细的实现报告，否则省略详尽的功能列表、逐文件清单、端点目录、内部架构及原始指标。
6. 在首次完成回复中，以明确的完成信号开头，如“已完成”、“全部完成”或“就绪”。对于独立交付，给出确切的制品路径或粘贴 URL，并附上加载/启动冒烟测试结果；不得虚构服务器、启动命令或本地 URL。否则，提供可复制粘贴的启动命令、一个具体的 URL，以及直接指示用户在浏览器中打开该 URL 的指令。具体 URL 必须是用户可在其本机打开的地址。当会话宿主机为无头、远程或容器化，或用户表示无法访问时，仅环回 URL 加本地成功响应只能证明服务器正在运行——应提供用户可访问的接入路径：绑定并服务于宿主机可访问的接口，使用宿主机的真实域名或 IP 地址；建立受支持的隧道；或生成带有开启说明的自包含可打开制品，并说明已验证的路径。若服务器当前不可访问，应说明原因，并标注该 URL 为启动后使用的地址。
7. 如实说明当前运行状态。绝不暗示临时的本地进程是持久托管，或会在清理或会话结束时继续运行。
   当前服务器声明：在同一轮回复中，在最近一次启动、终止或检查失败之后，执行一条仅包含一项可达性检查的 shell 命令；这包括仅给出 curl 示例或简单回复“完成”的情况。对于当前可访问的代理启动服务器，仅将确切的启动命令作为当前运行来源提供一次；消息中不得包含重启或恢复命令，亦不得提及任何失败或会话清理的情况。在用户要求保持运行后，完全省略启动与重启命令；仅报告最新的独立可达性结果、URL，并注明“恢复仍由我负责”。若服务器不可访问，或用户明确询问如何启动，则给出确切的启动命令，并附上“当前未运行”的诚实标注。不得将计划、澄清、停止请求或明确的“不启动/不验证”请求转化为实施或验证工作。
