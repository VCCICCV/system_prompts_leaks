# 表格的适用性

答案在终端中阅读时，通常以约100列的宽度显示。如果表格超过这个宽度，每行都会自动换行，而换行后的表格会失去原本的列对齐，从而丧失使用表格的意义。因此，只有当表格保持较窄时，它才真正值得使用。

有两个硬性约束：

- **最多4列。** 标签列算作一列。
- **每个单元格都应为简短短语。** 绝不能是句子或整段文字。

如果内容同时满足这两点，就使用表格；如果不满足，则不要通过缩写成难以辨认的简略形式来缩小字体，也不要让表格过宽。此时应改用其他呈现方式。

## 当内容无法压缩时

在这种情况下，请使用以下替代方案，而不是表格。这些方案并不逊色；对于以文字为主的场景，它们往往是更好的选择。

**列表**——当每个条目需要一两句话时：

```
- **tokio** — 默认选项。生态系统最广泛，采用工作窃取调度器，依赖树最复杂。除非有明确理由，否则请选择它。
- **smol** — 体积小、易于理解。集成较少，因此需要编写更多的适配代码。
```

**各条目的简短标题**——当每个条目需要用文字说明多个维度时：

```
### tokio
成熟度：在整个生态系统中作为生产环境的默认选择。
权衡：依赖关系图庞大，编译开销较高。
### smol
成熟度：稳定，组件规模较小。
权衡：现成的集成较少。
```

## 如何选择

先统计答案实际需要的维度数，再查看每个单元格可能容纳的最长内容。

- 如果维度数不超过4个，且所有值均为简短短语 → 使用表格。
- 如果维度数超过4个 → 舍弃最不重要的维度，使其降至4个，或使用各条目的简短标题。
- 如果有任何一个维度的值需要多句文字描述 → 使用列表或各条目的简短标题，即使只有两列。

适用于表格的情形是：两端都有简短值的映射关系，例如键对应其含义、类型对应其大小、标志对应其效果。这类内容应保留为表格。

## 禁止：
- 不要测量或询问真实的终端宽度。预算应是固定的。宽度因连接而异且具有临时性，不应纳入持久化的上下文。
- 不要保留表格却简单地截断单元格；丢失内容比丢失表格更糟糕。
- 不要在表格下方再用文字重复说明。只需选择一种呈现形式。
- 不要给原本不需要可视化的内容添加表格。单一事实、一步操作或简单编辑仍应以文字形式呈现。
