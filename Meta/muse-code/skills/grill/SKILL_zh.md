# 烧烤

仅当用户明确要求进行烧烤并附带持久性文档，或直接调用此技能时才使用该技能；如果 `agents` 协调器在计划执行前传递了一个不明确的目标，或者某个决策需要用户确认，则视为直接调用（其问题即用户的判断——目标、衡量标准、范围——这些由仓库中的事实所塑造但无法直接回答），此时的持久性记录应为项目自身的 `PROJECT.md` 或 `library/` 文件，而非仓库文档。仅因复杂性、模糊性或可能需要文档而不会激活此技能。该技能具有自身的访谈与文档编写契约。请勿在运行时加载或调用 `domain-modeling`。

## 访谈契约

1. 在向用户提问之前，请先在仓库、Issue、文档和代码中检索可发现的事实。仅就无法自行发现的判断或事实进行询问。
2. 每次只提出一个促使决策的问题。简要说明推荐答案及其理由，然后等待用户的答复。
3. 所有访谈问题均以纯文本形式作为普通助手回复提出，不得使用提问工具。
   - 当某个有限的决策可通过2–3个简短且互斥的选项来优化时，应以纯文本列出这些选项，并将推荐答案置于首位。
   - 邀请用户选择、修改或讨论这些选项，而非强制其进行结构化选择。
4. 仅当用户明确要求，或问题涉及代理与产品的行为比较（如 Claude Code 与 Codex）时，才使用对比表格。
5. 追踪相关联的决策，直至技能判断决策树已穷尽为止。切勿提出“我们是否已完成？”这类元问题。
6. 总结已确定的契约内容：目标、非目标、各项决策、约束条件、风险、验证方式，以及尚未解决的事项。

## 背景正式证据

若目标项目提供了适用的正式检查工具，请按照其本地文档准备声明的访谈输入，并在选定提纲之前以及获得相关答复或源码变更之后运行检查。阅读已完成调用的结果及源码与输入的绑定关系，然后利用未解决的义务与反例来修订下一轮问题。对变更后的输入重新检查。仅在支持的范围内和条件下复用已有答案，并保留独立的选择。每次给出答案后，将其来源及适用范围写入声明的输入和日志或《草案决策》中；在制定下一轮提纲之前，重新运行并记录剩余的待办事项。
可能的模型赋值并非人类的认可；有限的覆盖范围并不包括未列出的问题。
缺失或过时的证据会限制后续依赖性结论，但独立允许的工作仍可继续进行。请以用户熟悉的语言提出一个实际问题，提供常规选项及相应后果；在用户要求时再解释正式技术。

## 范围契约

访谈只有在书面确定的契约固定了范围，且用户明确接受该文本之后才算结束：

1. **制品级边界。** 明确说明交付物是什么（在范围内的文档、目录、拉取请求或代码路径），以及哪些制品类别不在范围内，例如后续规范、测试、运行时代码或任务计划。
2. **“完成”的含义。** 制定一份简短的检查清单，列出能够观察到的工作完成条件：已合并的提交、已关闭的问题、经验证的证据。检查清单之外的任何内容都不作为完成的依赖项。
3. **分阶段设计逐阶段审批。** 如果某份决策记录描述了后续阶段（如将宪法、规范或运行时变更分阶段推进的ADR），则应将其记为延期提案；接受该记录并不意味着批准后续阶段。每个阶段都需单独进行评审。
4. **执行指令不得扩大范围。“去吧”、“全部做完”或“落实1至5条”仅授权在已确认的边界内开展工作。如果后续工作会引入边界外的制品类别、新的拉取请求或任务计划，则应在产出之前停止，并严格遵循以下两种路径之一：要么在归属问题中获取所有者对更广边界的确切批准，要么将额外工作移至一个独立的后续问题，并为其启动单独的评审流程。绝不可先动手再请示。

将已确认的范围契约发布在执行团队及其主管可见的位置（对于仓库相关工作，即归属问题），并引用该契约的接受声明。此评论仅作为团队协调的证据，而非决策记录：它需精确引用用户的话语，并注明渠道和时间；最终的决策应记录在本技能所生成的文件中，而不在评论里。
结束评审并不意味着授权实施。只有在收到用户明确的另行请求后方可实施。

## 文档契约

1. 在提出第一个问题之前，根据用户指定的目标及仓库现有的文档规范，确定目标文档。查阅本地说明、索引、规范、ADR、术语表及周边文档。若无法确定目标，请提出一个问题。切勿随意创建一个通用的`docs/grilling/<日期>.md`位置。
2. 创建或更新目标文档为“草稿”状态。每达成一项决策，立即以草稿形式记录，而不必等到评审结束。未解决的问题应醒目标注。
3. 若评审被中断或取消，应保留草稿及所有文件修改，标记未解决的问题，且不得自动撤销文档变更。
4. 仅当正在撰写特定类型的文档时，才查阅详细的`CONTEXT.md`、ADR、术语表或其他参考文档。
5. 日常的写入/编辑操作即为文档工作的实时证明，无需额外输出“已更新<路径>”之类的状态提示。
6. 明确的文档需求是硬性完成条件：若无实质性的文档创建或更新，本次会话即视为未成功结束。“无需文档”且无任何文件变更均不符合要求。
7. 只有用户的明确接受才能将文档从“草稿”状态转为“正式”状态。决策树穷尽并不等同于接受。
8. 在最终回复中，列出所有已变更的文档路径，并注明其状态是保持为“草稿”还是已转为“正式”。
