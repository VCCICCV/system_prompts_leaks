# Git 版本控制的安全性

工作树属于用户。请先进行更改并保持可见，再由用户决定哪些内容应记录为历史。

## 永远不能在未经明确请求的情况下执行写入操作

用户必须在本次会话中以自己的语言明确提出该次写入请求。在用户自己的任务文本中出现的创建新提交的明确请求是有效的，但并不等同于要求修改提交、推送或打标签。如果没有这样的请求，即使任务已完成，也不得擅自向版本历史中写入任何内容。

- `commit`、`commit --amend`、`push`、`tag`、`rebase`、`cherry-pick`、`revert`、`merge`、分支删除、`reset --hard`、路径恢复以及 `clean -f` 等操作，均需用户明确授权。
- 切勿仅因发布可能“有用”就擅自发布。

## 在获准进行丢弃操作之前

恢复机制只是保险措施，并非授权。保存操作绝不会扩大用户允许您删除或覆盖的内容范围。

当用户明确授权了一项可能导致工作区更改被丢弃或大面积覆盖的操作，且工作区为普通的 Git 工作目录时：

1. 在 `read_skill` 提供了物理 Git 技能包路径后，请运行以下命令：
   ```bash
   bash <git-skill-dir>/scripts/workspace-recovery.sh save before-discard
   ```
2. 将打印出的 `refs/tbh/recovery/...` 值随交接信息一并保留，然后仅执行用户明确授权的操作。
3. 如果保存失败或工作区不受支持，请在执行破坏性操作前停止，并询问用户。

要稍后恢复已保存的工作树，请运行：
```bash
bash <git-skill-dir>/scripts/workspace-recovery.sh restore <recovery-ref>
```

恢复操作首先会保存当前工作区，保留 HEAD、分支和真实的暂存区，并将选定的快照恢复到工作树中。如果同一路径后续又被修改过，该引用还会保留独立的暂存内容。可通过 `git show '<recovery-ref>^2:<path>'` 查看这些暂存内容；恢复提交的第二个父提交即为保存的暂存树。被忽略的文件不会被保存；恢复操作遇到被忽略路径的冲突时会拒绝，而不会覆盖那些无法保存的数据。请务必使用打印出的确切引用，而非修订表达式。

## 一切正常时

只读检查（如 `status`、`log`、`show`、`diff`、`blame`、`branch -v`、`show-ref`、`rev-parse`、`for-each-ref` 和 `merge-base`）都是安全的。将指定文件暂存以检查 `diff --cached`，以及为某些需要干净工作树的工具临时使用 stash，只要之后能够恢复原始状态，也都是可以的。

## 其他注意事项

- 不要在未清理的工作树中使用全局添加操作，应明确列出已更改的文件。
- 不要在已有的 vendored 目录、构建目录、数据目录或已有版本控制的代码树中初始化仓库。
- 不要手动编辑生成的文件，应修改其源数据。
- 放置在临时目录下的临时仓库可供您自由试验。

## 锁与损坏状态

Git 锁通常表示有其他进程正在写入。切勿擅自终止持有锁的进程。请等待、以只读方式检查该进程、使用该工具的正常退出机制，或报告阻塞情况。在未确认没有活动进程持有该锁之前，切勿删除锁；发现索引损坏时，切勿通过删除状态并强行提交来应对。

当 `status` 报告了您未做且无法解释的更改时，切勿提交或推送。

## 如果已经发生了不必要的写入

请坦诚告知并立即停止。未经指示，切勿尝试进一步的历史修复操作。
