# 计划

在开展复杂工作之前，先制定一个脚踏实地、决策完备的计划。

## 范围

- 仅当用户明确要求制定计划时才使用此技能——即用户请求计划、设计、方案、上线或迁移策略，或者 PR 拆分，或直接调用“计划”技能（/skill plan）。
- 对于普通的实现、构建、修复、调试或重构请求，请勿使用此技能。当被要求进行代码变更时，应直接执行，无需事先规划——即使任务较为复杂。任务本身的复杂性本身并不构成触发条件；只有在用户明确提出规划需求时才适用。
- 进行规划时，需根据请求所隐含的计划类型来调整——包括实现、设计、调试、上线或迁移、评估或研究，以及 PR 拆分（参见“计划形态”）。计划类型与触发条件是两个独立的维度：即使是调试、实现或评估类型的计划，也不能单独作为在普通编码任务中调用此技能的理由。
- 对于简单的单步编辑、显而易见的缺陷修复、格式化、文案修改，以及无需规划即可直接回答的问题，可跳过此技能。
- 将其视为一种规划指导，而非由主机强制执行的模式。请勿在面向用户的文本中将其称为“模式”，也勿声称主机正在阻止您使用编写工具、命令、编辑或审批功能。
- 除非用户明确要求持久化保存，或工作空间的工作流规定必须生成一个命名的计划文档，否则不要创建计划文件。最多只能生成一份这样的 Markdown 文件。
- 在规划过程中，不得修改代码、应用补丁、格式化、生成代码、提交、推送、打开 PR，或执行任何旨在落实实施的命令。
- 可以执行非破坏性的探索性操作：读取和搜索文件、查阅文档和规范、检查 Git 状态、运行试运行命令，以及仅在不修改已跟踪文件的情况下运行测试或构建。
- 在向用户提问之前，尽量先通过本地信息获取并确认可发现的事实。
- 仅就无法从工作空间中获取的产品偏好或权衡取舍向用户询问。

## 起草前的调研

对于明确的计划需求，请按以下步骤依次进行。在完成第 1 至 5 步中的相关调研之前，请勿撰写计划文本或创建计划文件：

1. **梳理决策点。** 确认方案必须做出的关键选择，以及每项选择所需的信息。将工作空间相关事实、外部事实、用户偏好和假设区分开来。
2. **调研工作空间相关事实。** 通过有针对性地查阅相关说明文档、决策记录、归属代码或文档、调用方、测试用例、配置及现有工具，明确当前行为、约束条件、可复用选项和验证路径。将既往方案视为参考而非证据；务必核实其引用的来源。
3. **仅在必要时提问。** 用户仅在其明确要求与您共同探讨尚未解决的方案或设计选择时，才会请求召开协作式检查点；在方案起草之前提出此类请求。单纯要求制定方案、设计方案、进行评审或后续审批均不符合此条件。对于该检查点，在已调研可获取的事实后，若仍有关键的、由用户主导的产品偏好或权衡事项未决，则应在起草前予以询问，以免最终以开放性问题的形式出现在方案末尾。仅在此检查点，上述“可回退默认”原则可予例外；其余所有关于问题引导及不可用工具的规则仍应适用。  
   其他情况下，遵循以下常规规则：在调用 `request_user_input` 之前，先调研任何可能消除该问题的事实性未知项；这可能包括范围有限且独立于偏好的外部调研。切勿仅因需求范围、平台或实现细节未明确而提问。仅当剩余的、由用户决定的偏好无法从需求、工作空间或已有调研中确定，且其答案会实质性影响调研结果或推荐方案，或能避免大量返工时，才使用 `request_user_input`。若存在一个合理且可回退的默认选项，可在安全推进规划的前提下将其作为假设提出，而不必提问。提出必要问题时，应以期望达成的结果或体验为表述，而非具体的方法、库、引擎或框架名称；例如，应问“街机风格还是真实模拟”，而非“自定义物理引擎还是 Matter.js”。技术实现应由您自行调研并给出建议。当确需用户提供输入时，每次仅提一个问题。对于必要问题，不要设置 `auto_resolution_ms`，应等待用户答复。若某项选择可安全采用可回退的默认值，则无需弹出提示框，而应在方案中直接注明该假设。若所需工具不可用，应将该项选择作为开放性问题保留，并使依赖于此的推荐保持条件化。
4. **在外部事实至关重要的情况下开展调研。** 对于全新的重大项目或不熟悉的领域，在推荐具体方案之前，必须充分利用现有的外部调研资源，并查阅权威的第一手资料，以明确当前领域实践、各类库、引擎、API、平台或标准等方面的关键技术决策。若需用户输入，应在收到其答复后再开展针对特定分支的外部调研。调研应围绕用户偏好的选项展开；偏好可以限定调研范围，但不能替代调研本身。发现来源与检验来源是两回事。摘要、索引、候选清单等发现类材料仅用于定位相关来源，不能视作完整的调研。在作出关键的外部推荐之前，务必亲自检阅权威或第一手资料的原始内容。所有重要的外部论断或决策都必须追溯到本次运行中已检验的来源内容。只有当原始内容成功返回且非空时，方可认定该来源已被检验；失败、重定向、未找到、内容为空或仅为发现性结果的，均不予认可。若原始内容不可得，应记录证据缺失，并使相关推荐保持条件化。仅有空的工作空间、发现性摘要和模型记忆不足以构成充分证据。若工作空间内的现有证据已足以解答该决策，则可免于外部调研。引用时仅限于本次运行中已检验的来源内容，确保论断不超过这些来源的支持范围；遇来源冲突时优先采信官方的第一手资料。综述、对比或教程页面仅可用于筛选候选，绝不能作为最终关键决策的依据；务必对照官方文档、标准或项目仓库对候选进行验证。不得将某一来源的主张夸大，也不得凭空臆造版本、规格、性能阈值或重试策略。
5. **收尾委托的调研任务。** 在撰写方案正文或方案文件之前，立即检查您所启动的每一个子任务。等待中的子任务超时并不等于已完成状态。只要有任何子任务仍在进行中，就应持续查询其状态并继续等待。在起草前接收所有已完成的任务结果，并纳入相关发现；对于失败、被取消或无法获取的调研，应记录其缺失情况。在仍有未完成的子任务时，禁止创建方案目录或写入方案文件。若您主动取消某个子任务，应等待其进入完成状态，并记录其结果或证据缺失后再行起草。
6. **先综合，再起草。** 在起草前，构建一份私有的决策—证据映射图。凡将在方案中作为选择、备选方案、兜底方案、风险或否定项出现的外部候选，均须对应到已成功检验的权威内容。移除所有缺乏此类证据的候选；仅靠发现性页面无法填补该映射。在映射中精确记录已检验的URL，不得重构、缩略或推断出处。唯有如此，方可推荐具体方案。明确列出所有假设和未决问题，并确保关键决策、工作计划及验证计划与用户的约束条件和已收集的事实相一致。当决策地图已足够完善、可以用于制定计划时，应停止进一步调研。对于范围明确的调研任务，直接使用相关工具；仅在并行工作能显著提升证据质量时才进行委托。若用户明确要求停止或缩短调研，请遵从最新指示，并标注剩余的待填补空白。

## 质量标准

只有当计划满足以下条件时，才算准备就绪：

- **有据可依**：在存在相关来源的情况下，引用用户目标、当前事实、文档、邻近代码、测试、命令、日志、规格说明、问题或拉取请求来支撑计划；将推测标记为假设。
- **决策完备**：明确关键选择、推荐方案，并说明为何舍弃了合理的备选方案（如适用）。
- **目标匹配**：根据工作性质选择合适的计划类型：实现、设计、调试、迁移/上线、评估/调研，或评审/拆分拉取请求。
- **可执行**：将方案分解为有序的工作单元，明确依赖关系、责任人或负责模块，且不含无关的清理工作。
- **可验证**：每个工作单元都配有明确的验证命令或实际的手动检查；当模块需要时，纳入端到端、黑盒或发布二进制检查。
- **范围可控**：当非目标内容、风险、回滚机制及兼容性影响会波及实现时，应予以说明。
- **问题最少**：仅在本地探索无法解答时，才保留开放问题。
- **不止于任务清单**：清晰阐述背景、推荐方案及证据链，使他人能够在执行前对计划提出质疑。

## 显式文件输出

默认以内联方式交付计划。除非用户明确要求保存，或所在工作空间的流程规定必须生成命名的计划工件，否则不应写入计划文件。复杂度、可能的复用需求或后续交接的可能性，均不能作为写入文件的理由。

在获准持久化存储时：

- 若用户指定了路径，或工作流程已有明确规定，则使用该路径。
- 若工作空间已有既定的长期计划存放位置，则遵循该位置。优先顺序为：Spec Kit 工作下的活动 `specs/<feature>/plan.md`、现有的文档或项目计划约定路径（如 `docs/plans/`），或经文档化的计划目录。
- 若允许保存且无更优惯例，则保存至 `.agents/plans/YYYY-MM-DD-<slug>.md`。
- 必要时创建父目录。
- 可更新现有的 `specs/<feature>/plan.md`、用户指定的现有计划路径，或本会话中保存的计划文件。除用户明确要求外，不得覆盖任何其他现有文件。若新建带日期的文件时目标文件已存在，则添加简短的数字后缀。
- 最终计划不得存于 `/tmp` 目录。临时草稿不属于可供用户长期使用的工件。

## 用户可见的交付

最终回复应以如下完整语句开头，置于单独一行，以便在长篇计划折叠时仍能清晰显示下一步操作：

这是一个计划，而非特殊模式；我尚未开始实施。回复“go”以执行此计划，或告知我需修改之处。

随后，在正常的用户可见助手回复中，仅呈现一次完整的、可供审阅的 Markdown 格式计划。保存或重新读取计划文件，不等同于向用户展示该计划。使用一份规范的 Markdown 计划正文。保持简洁，但不设固定的字符或标记数限制，也不截断实质性决策、工作阶段、验证步骤、风险或待解决问题。将支持性证据压缩为简明的引用，但绝不压缩实质性决策、阶段、验证、风险或待解决问题的内容。若保存计划文件，其内容必须与规范正文完全一致。在常规助手回复中逐字复制该规范正文。在写入文件之前先选定该正文；切勿在文件中放入更长或不同的计划内容。仅当能够在下一次常规回复中完整复现该规范正文时才保存文件；否则跳过文件，直接在回复中完整呈现计划。不得生成两份独立扩展的计划版本。若保存计划，请在可见计划后注明文件路径。已保存文件仅为补充，绝不能替代常规助手回复。
当外部研究影响计划时，应在计划末尾加入一个精简的“## 来源”章节，其中仅包含来自成功且非空底层内容结果的确切 URL。每项重要的外部决策都必须引用这些 URL 之一。

## 对话交接

交付前：

- 对已保存的计划进行完整回读与修正的审核，直至其稳定；在此审核过程中不得展示计划。在最后一次写入后完整回读整个已保存计划，不得使用 `head`、部分范围或其他截断式读取，并检查用户的约束条件、关键决策、工作计划和验证计划之间是否存在矛盾。
- 从最终的规范正文构建一份完整的外部名称清单。在各部分中，列出所有支持实质性外部主张或建议的命名实体，包括库、引擎、API、平台、标准、产品或项目，尤其是在决策、备选方案、回退措施、风险、否定意见以及“来源”部分。仅重述用户约束或明确的工作空间事实的名称无需附外部 URL，应改为明确列出其用户提供的或本地证据。其余每个名称均需匹配一个在本次运行中成功返回且内容非空的权威底层内容的精确 URL。搜索或发现结果、重定向、失败、未找到及空结果均不符合要求。若某名称无符合条件的结果，应立即核查其权威内容，或删除该名称并将相关主张保留为条件性表述。在所有条目均得到解决之前，不得交付。
- 针对每项重要的外部决策，对照其匹配的来源进行审核。发现页面可记录候选出处，但不得作为最终决策依据。对于经核查的权威内容无法支持的主张，应予以研究、修正、删除或保留为条件性表述。
- 若任一最终审核导致规范正文发生变化，须重新进行一致性审核及外部名称审核。若已保存文件，则先重写并再次完整回读已保存计划。只有在经过一轮完整审核且无任何修改后方可交付。
- 下一次常规助手回复应以上述单行对话交接开头，随后是完全稳定的规范正文。对于已保存的计划，直接使用稳定的回读内容；对于仅以内联方式呈现的计划，则使用经过审核的稳定正文。不得重新生成、缩短、概括或省略任何部分。若有保存路径，将其置于完整正文之后。

交付后：

- 最终交接时不得调用 `request_user_input` 工具。该工具仍仅用于研究步骤 3 中必要的、由用户自主作出的选择。
- 在规范计划及任何保存路径之后，重复提示：“回复 `go` 以执行此计划，或告诉我需要更改的内容。”
- 交接完成后即停止，不在规划环节启动实施。
- 收到 `go` 指令后，直接执行前述计划，不得重新生成。收到变更请求时，应修订并再次完整呈现计划。

## 计划结构

编写计划时，应确保下一位执行者无需猜测即可行动。请采用本结构中最精简的子集，仅保留执行所需的决策内容：
```markdown
## 目标
## 成功标准
## 方法
## 步骤
## 验证计划
## 风险/待解决问题（仅在重要时填写）
```

对于待解决问题，只有在检查完代码库仍无答案后才填写“无”。
保持“成功标准”以结果为导向：明确工作完成时必须满足的条件。
保持“验证计划”以证据为导向：列出具体的、有针对性的命令，必要时包括端到端或黑盒测试，明确预期的证据，以及无法自动化的手动检查。

根据计划类型调整各部分：

- 对于实现类工作，“步骤”应明确代码接口、数据流、兼容性影响、可复用的现有工具及测试策略。仅当工作流程或评审风险需要时，才拆分 PR。
- 对于设计类工作，重点说明接口、不变量、被舍弃的备选方案，以及迁移或兼容性规则。
- 对于调试类工作，列出假设、所需观察、需检查的插桩或日志、复现步骤，以及能证实或证伪每个假设的证据。
- 对于发布或迁移类工作，应包含阶段、关卡、回滚机制、数据安全、监控措施及对用户可见的影响。
- 对于评估或研究类工作，应包括基准/问题、语料或数据源、对比方案、成功指标、混杂因素，以及可复现实验的证据。

不要为了填充某一部分而凭空创建 issue、spec、PR 或文件路径。如果工作空间规则要求这些内容，请引用实际存在的条目，或将缺失的前置条件列为待解决问题或阻塞项。不要重复用户已知的背景信息，也不要添加空的部分。确保计划足够完整，使实施者无需自行定义范围、接口或验证方式。

## 工作流程

1. 判断是否确实需要规划。若任务简单，直接说明并按常规流程处理或实施。
2. 如适用，先完成调研再起草计划。将计划建立在已有事实基础上：用户需求、代码库/文档/代码、日志、配置、既有决策，以及相关 issue/spec/PR 的上下文（如有）。
3. 确定计划类型，并规划一条能验证方案的最小可行路径。
4. 选择与现有模式最匹配且新增抽象或流程最少的方法。
5. 仅在顺序依赖、风险、职责归属、评审或验证需要明确边界时才拆分工作。
6. 为每个工作单元明确对应的验证证据或实际的手动检查。
7. 若用户或工作流程要求保存计划，简要说明其路径。对于常规的内联场景，无需声明文件不存在。
8. 突出显示风险最高的验证步骤。
9. 以用户可见的形式呈现计划，并在实施前等待用户的下一条指令。

## 结束

- 生成计划后，在一次正常的助手回复中，同时展示对话交接、完整的规范 Markdown 格式，以及重复的交接信息。
- 等待用户的下一条指令。不要将规划文本视为编辑许可。
- 若用户表示“开始”、“继续”或以其他方式启动执行，则直接使用先前的计划：结束规划环节，按照常规工作流程开展工作，并遵守计划中的各项约束（参见“执行计划”）。
- 在编辑前再次确认最新的用户消息，以免过时的计划假设覆盖新的指示。

## 执行计划

无论计划是由本技能生成还是由用户提供，也无论本技能是否曾被调用，这些规则在执行期间均有效。若在发布时加载了本技能，则仅适用本节内容——上述规划限制不适用。

- 计划的结构化承诺在执行过程中依然有效：差异/提交/拉取请求的拆分以及单元的顺序在工作进行并发布时均保持约束力。
- 这仅规范发布的形态，而不涉及其授权：提交、推送或发布仍需用户明确操作，以符合源代码管理的安全原则。计划步骤中指定“提交”并不自动赋予提交权限。
- 当用户要求你发布工作时，计划会将其拆分为 N 个独立的差异、提交或拉取请求，务必严格按照该拆分进行发布：按计划顺序逐个提交每个计划单元，即使一次合并提交也能满足用户的字面请求（如“提交这些内容”“发布它们”）。
- 已经在一个混合工作树中完成的工作，在发布时仍需拆分：按计划单元对变更文件进行分组，并逐单元提交。如果某个文件的变更跨越多个单元，则应在补丁块级别进行拆分（使用 `git add -p`），或将该文件归入最早的单元并予以说明。
- 用户后续关于结构的明确指示将优先于计划——请遵从；偏离通知仅用于你主动发起的偏离。
- 只有在告知用户你将如何更改及其原因之后，方可偏离计划结构——例如折叠、合并、重新排序或跳过单元——并在发布与计划承诺不同的结构之前。
