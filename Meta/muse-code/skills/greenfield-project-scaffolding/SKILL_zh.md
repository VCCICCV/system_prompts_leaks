# 绿地项目脚手架

在首次写入之前，先确定项目根目录及其标准布局。

1. 确认当前轮次的授权以及请求是否足够完整。只有当当前用户明确表示希望立即启动、实施、构建、搭建或推进一个新项目时，才视为已获得授权。先前问题的回答、规划或决策轮次，以及关于尚有工作待办的提醒，若未包含“立即实施”等明确表述，则不能作为本流程的授权依据。若未获授权，应停止任何项目结构的构建及文件写入操作；若产品行为或交付约束存在缺失、明显被截断或重大歧义，应提出一个针对性的澄清问题，并在得到解答以消除疑虑之前暂停操作。切勿仅因交付物为应用程序或游戏而触发此流程。
2. 在将其视为未知之前，先明确指定放置位置。“此处”、“此文件夹”、“当前文件夹”、“此目录”、“当前目录”等代词性表达，仅在确凿事实表明当前目录适合作为预期项目根目录时，方可作为目标路径。若当前目录类似主目录、用途广泛或看似空但实则非空，则仅凭这些代词性表述并不能使其成为合适的目标。应保留明确指定的路径及现有的项目根目录；现有仓库、项目或笔记本均不在适用范围内。
3. 遵守检查限制。若用户明确禁止检查现有文件，则必须遵守该限制，仅使用请求内容、`pwd`命令及路径语义进行判断，不得列出或读取附近内容。若因明确的“禁止窥视”约束导致放置位置无法确定，则应根据请求内容及路径语义创建一个对用户有意义的专用子目录，并跳过后续的所有发现步骤。
4. 否则，复用触发本流程的允许检查结果。利用请求内容、`pwd`命令以及观察到的顶级条目和项目标识，不得仅为本流程而重复已执行的读取操作。仅检查用户允许且仍缺失的放置相关事实，确认用户是否指定了目标路径，以及当前目录是否已是预期的项目根目录。切勿仅因附近存在无关仓库而将其采纳为项目根。
5. 在开展项目工作前，拒绝不合适的根目录。经允许的检查确认当前目录类似主目录、用途广泛，或与“空/当前即根”的前提相悖时，应将其视为需要新建专用子目录。将类似主目录、用途广泛的或看似空实则非空的当前目录视为不适合存放项目相关文件。首次项目变更必须建立该专用子目录，并确保所有脚手架路径及脚手架命令的工作目录均位于选定的根目录之下。

若本技能在当前任务的项目文件已在被拒绝的根目录下生成后才被加载，则应停止进一步的项目变更；仅将这些当前任务的文件迁移到专用子目录中，然后再进行其他项目变更。迁移而非复制这些文件，不得将其回拷、同步或镜像至被拒绝的根目录。此后应完全在专用子目录中继续操作，修复任务路径时不得检查、移动或删除无关内容。1. 恰好选择一个根目录：
   - 保留显式指定的路径或现有项目根目录。
   - 在已知条件确认当前目录合适且请求已将其设为预期项目根目录时，使用当前目录。
   - 当前目录为类似主目录或通用目录，或与请求的前提相冲突，且未指定目标时，根据所请求的产品名称创建一个用户可理解的专用子目录。
   不要在所选根目录内再添加额外的包装目录。
2. 在该根目录内采用生态系统的原生布局。将入口文件、包文件、源代码、测试和资源保留在该生态系统通常放置的位置。仅当生态系统规范或具体的近期内容需要时才创建目录；不要为了装饰而创建仅包含一个文件的目录。
   避免使用占位文件和推测性层级。对于无需构建的纯 HTML/JavaScript 可播放浏览器应用或游戏（且未明确要求为独立或单文件形式），应将入口 HTML 文件保留在专用项目根目录中，并将主要逻辑放在至少一个单独编写的 `.js` 或 `.mjs` 源文件中。
   对于框架或强类型技术栈，应使用该技术栈的常规源模块；不要强制添加根 HTML 文件或空壳 JavaScript 文件。当请求明确要求生成独立的、单文件的、可直接粘贴的或离线可用的产物时，应予以保留，并将产物打包与验证的相关机制交由 `bundled:browser-app-delivery` 处理。
3. 按照请求所需，搭建最小的完整可运行形态，然后执行相应的交付或验证流程。清晰报告所选根目录。
4. 在移交之前，对已知路径以及本次任务中新建或变更的路径进行审计。确保所有脚手架产物都位于且仅位于所选的一个项目根目录之下。仅将当前任务相关的产物移出或删除；不得检查、移动或删除无关内容。

本流程不适用于现有仓库、项目或笔记本、缺陷修复、仓库维护以及仅涉及组件的编辑。对于明确要求以独立、单文件、代码片段或可直接粘贴形式交付的请求，应予以保留，不得将其转化为项目。
