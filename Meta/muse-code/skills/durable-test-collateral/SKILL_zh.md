# 持久性测试材料

当验证能够防止相同的问题再次发生时，它就是交付项目的一部分。请使用项目现有的框架和约定。

## 将检查与项目保持一致

对于缺陷修复或行为变更，应在仓库的常规测试布局中添加或更新最小的、可维护的测试，以覆盖变更后的行为。如果某项规范将可复用的测试套件或测试类别作为交付内容，则应实现该套件，而不是将其视为私有的验证手段。

内联解释器命令、here文档、临时脚本、临时目录中的测试、演示或手动探测可能有助于诊断问题，但它们不能替代可维护的测试。除非用户明确要求使用一次性探测，否则应保留有用的自编测试。

不要为了满足这一技能要求而新增一个测试框架。如果仓库中没有可维护的测试框架，且请求也不需要它，则应说明何时持久性覆盖会显得不成比例或不可行，并改用最精简、最诚实的验证方式。

在后续迭代中，即使旧的测试套件仍然通过，且用户未再次提出测试请求，也应更新可维护的测试。要覆盖新行为，而不仅仅是对测试文件进行无关的清理。

## 证明可维护的检查有效

在实施变更之前，在安全且可运行的情况下，先观察真实的失败现象。然后进行最小的实现变更，并在完成最后一次相关源代码或测试编辑后，运行经过聚焦的可维护测试。

不要为了获得“绿色”结果而弱化或删除真实的失败测试。应修复产品，或者在修改测试期望之前，说明为什么该期望是错误的。不要仅仅为了收集证据而重复执行未更改的检查。

只有在用户、仓库的准入门禁或风险评估要求时，才运行全面或完整的测试套件。首先应进行聚焦的回归测试；广泛的验证不能替代缺失的聚焦覆盖。

如果真实的运行环境不可用，但仍然可以诚实地编写聚焦测试，则应将该测试保留在仓库中，并注明其尚未运行。切勿伪造通过的结果。
