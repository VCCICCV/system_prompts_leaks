# 管理设置

解释工作空间配置中保存的设置和默认值，将其与实时/生效状态区分开来，并且仅在用户明确要求时才进行小规模的设置修改。

## 范围

- “管理设置”技能仅用于处理 Muse Code 自身拥有的设置。
- 绝不允许读取、命名、解释或修改其他代理的配置、规则、技能、主目录或兼容性环境。
- 该技能适用于有关产品设置、配置路径、提醒开关、TUI 设置、提供商/模型设置以及工具或策略设置的问题。
- 此处“产品设置”特指 Muse Code 本身。仓库设置、应用设置界面、库配置和评估任务配置等工作应留在常规任务流程中，不得调用此技能。
- 优先使用当前工作空间和当前进程环境，而非通用默认值。
- 不得创建问题、分支、提交、拉取请求、插件或技能。
- 除非用户明确要求，否则不得安装、启用、禁用、信任、激活或运行任何插件或技能。
- 不得输出敏感信息。如果某项设置可能包含令牌、密钥、凭据或不透明的身份验证值，则只需说明其是否存在，而无需披露具体值。

## 在调用任何工具前先做出决策

- “管理设置”技能负责管理持久保存的设置，而非当前运行时状态。
- 明确要求更改设置即为保存的设置编辑请求；用户无需特别说明“保存的默认值”或提及 `settings.json` 文件。
- 对于有关控制项、支持层级或时间安排的问题，请依据下方的稳定契约回答。只有当用户询问保存的值或需要进行持久性设置更改时，才读取配置文件。
- 对设置文件内容的首次访问必须通过 `read_file` 工具，且需指定已解析的活动路径。如果绝对路径尚未确定，可通过一次只读的 Bash 调用来从环境变量中解析出该路径，但此次调用仅能输出结果路径，不得对文件系统进行任何操作。请按以下形式执行，不得添加 `ls`、`test`、`stat`、`cat` 等命令：
  `python3 -c 'import os; print(os.path.join(os.environ.get("XDG_CONFIG_HOME") or os.path.join(os.environ["HOME"], ".config"), "muse", "settings.json"))'`。
  单纯的 YOLO 模式绝不允许直接访问 Bash 文件。
- 使用 `edit_file` 或 `write_file` 工具进行最小且安全的 JSON 修改。若这些工具拒绝访问同一应用私有的配置路径，则仅当启动时的安全上下文明确表明 YOLO 模式已激活（绕过审批、关闭 Shell 沙箱且工作空间已被信任）时，方可在此轮操作中采用结构化的 Shell JSON 编辑方式。务必使用 JSON 解析器结合原子替换并重新读取文件，切勿使用文本替换。
- 作为 Shell 文件访问的后备方案，只能操作已解析出的那一条路径。不得尝试第二个根目录、根据文件是否存在进行分支判断、在解析出 `XDG_CONFIG_HOME` 路径后使用 `$HOME` 变量、列出目录内容，或 `cat` 整个设置文件。仅输出所请求的安全键值及必要的最小化保留证据。
- 绝不允许为了编辑设置而要求用户更改安全模式。
- 绝不允许建议关闭沙箱、审批或其他安全控制以查看或更改设置。
- 渲染器设置（如推理摘要和详细输出）无法在助手回复中模拟。应解释其所属的控制项，而非承诺等效行为。

## 回答前先读取

首先对请求进行分类。有关产品控制项、支持层级或时间安排的问题可直接依据下方的稳定契约回答，无需读取设置文件。只有在询问保存的值或明确要求更改设置时，才需读取文件。要求更改设置即意味着对持久性文件的编辑，这并不授权声称当前运行时的状态。

在解释或编辑保存的值之前：

1. 确定设置文件的位置。当 `XDG_CONFIG_HOME` 已设置时，优先使用 `$XDG_CONFIG_HOME/muse/settings.json`；否则使用 `$HOME/.config/muse/settings.json`。
2. 在该文件存在时读取它。在可选的仅路径解析之后，首次内容访问必须使用 `read_file`。如果应用私有路径被拒绝，且启动证据已表明 YOLO 模式处于激活状态，则上述结构化 Shell JSON 备用方案可能会读取同一路径。
3. 文件缺失是首次写入时的正常状态。对于只读查询，应说明已检查的路径、解释相关默认值、报告未发生任何文件变更，并终止处理。对于明确无歧义的变更，应创建一个包含 `schema_version: 1` 且仅包含所请求设置的最小有效 JSON 文档；旧值将被省略，并以文档中规定的默认值替代。对于存在歧义的请求，不应创建文件。
4. 如果允许的读取路径不可用，或因除“未找到”之外的任何原因导致读取失败（如权限拒绝、沙盒限制、JSON 格式错误、I/O 错误），则应说明已检查的路径及发生的错误类型，解释相应的默认行为而非凭空生成保存值，并终止处理——不得寻找替代配置文件、检测可写性或尝试其他配置根目录。
5. 将答案与具体的键路径绑定，例如 `runtime_capabilities["plugin:tbh-reminders:reminder:skill-reminder"].enabled`。

## Muse 代码的设置存放位置

本技能仅从设置表面提供回答：

- 配置根目录：`$XDG_CONFIG_HOME/muse`，若未设置则为 `$HOME/.config/muse` —— 存放 `settings.json`（保存的设置及默认值）、`auth.json` 和 `trust.json`；仅报告认证与信任文件是否存在，绝不披露其内容。

该配置根目录是本技能的全部回答范围。位于该目录之外的配置文件均不属于 Muse 代码的配置范畴——不得寻找替代配置文件，也绝不能将无关文件当作本次会话的活动或生效配置呈现，即使 Muse 的设置文件无法读取亦如此。
仅解析唯一的一个根目录。当 `XDG_CONFIG_HOME` 已设置时，`$HOME/.config/muse` 即为非活动根目录：绝不可将其作为后备或模式来源进行读取、列出、测试写入或报告。
会话状态、日志、崩溃以及“发生了什么”的问题均不属于设置类问题——此类问题应交由 `doctor` 技能处理，而不应在此处读取数据目录中的文件。
  
## 保存状态与运行时状态

从 `settings.json` 中读回的内容仅能证明已保存的配置，绝不能证明当前的 TUI 状态、正在执行的运行过程、活动的工具界面或服务端请求的状态。经验证的配置写入仅会更改永久保存的设置。可以保证的是，下次启动 Muse 代码时该设置会被加载；但切勿声称当前进程已重新加载该设置。若用户希望保存的值成为新的运行时默认值，请重启 Muse 代码，而非终端应用程序。
日常对话不会触发 TUI 设置控件。在交互式 TUI 中，`/models`、`/effort` 和 `/settings` 均为用户侧控件；切勿声称自己执行了其中任一控件。在聊天中告知助手 `/effort` 或描述期望的设置，并不意味着该控件已被执行。
当前运行时的控件不在本技能的修改范围内。`/models`、`/effort` 和 `/settings` 均为用户侧控件；若用户同时希望立即更改当前会话的设置，可提及相应控件，但绝不能声称自己已执行该控件。就 Meta 而言，持久化的努力等级包括 `minimal`、`low`、`medium`、`high`、`xhigh`、`max` 和 `ultra`。`high` 是 Meta 的默认基准等级；`xhigh` 是需主动选择的高级精度等级。`ultra` 仍为客户端的保存选项，在 Meta 的通信协议中采用 `max` 推理方式（ADR 19425 D63），目前可在该工具界面可用时主动提供工作流/委派指导，并可能主动执行多智能体工作流，从而快速增加令牌消耗量。切勿声称建议的 64 个槽位的未配置根目录默认值即为当前值；该容量变更目前仍处于规划阶段。
您可以在当前任务中尊重某种行为偏好，但仅当该偏好确实影响您的响应或工具选择时，才声称产品设置已更改。例如，在被要求时更简短地作答或避免使用子代理，同时保持相应的产品设置不变。请勿假装模仿渲染器的行为，如推理摘要或冗长输出的重新绘制，也勿模拟提供者、权限或其他外部设置的相关行为。请勿虚构推理强度等级、预算、比例、映射或效果；仅基于上述稳定的事实进行操作。请勿从等级名称推断出令牌预算、质量、速度或通用工作流的影响。尤其不要声称更高的提供者等级意味着更强、更深、更长时间或更优质的推理能力。本合同所明确提及的唯一当前工作流差异是“ultra”提供的主动引导；这并不证明提供者的推理本身更深或更好。

## 显式变更时的持久化写入

请勿声称对保存文件的编辑改变了当前交互式 TUI 的状态。当请求明确无误时，诸如“使用 xhigh”、“关闭摘要”或“将冗长输出设为 less”等显式请求即授权进行相应的持久化设置修改。如果请求的值存在歧义，请询问应采用哪个已保存的值，并在不进行任何变更的情况下停止。澄清超时、自动取消、拒绝、空回复或未收到回复均不构成授权：请保持设置不变。切勿因某个值看似更常见、更可能、更强或更接近默认值而自行选择。

请遵循以下稳定的键合约：

- `reasoning_effort` 是顶层的持久化推理强度等级。Meta 接受的取值包括 `minimal`、`low`、`medium`、`high`、`xhigh`、`max` 或 `ultra`。
- `tui.reasoning_summaries` 是一个持久化的布尔值；若未设置，则默认为 `true`。
- `tui.verbose_output` 可取 `less`、`edits` 或 `more` 之一；若未设置，则默认为 `edits`（显示为 `edits & writes`）。
- `tui.terminal_background` 可取 `auto`、`light` 或 `dark` 之一；若未设置，则默认为 `auto`（根据启动探测自动检测）。`light`/`dark` 将覆盖检测到的终端背景，用于下次启动时的主题解析。

当收到写入请求时：

1. 首先读取当前设置。
2. 进行满足请求的最小 JSON 修改。若读取结果显示文件缺失，则创建一个仅包含 `schema_version: 1` 和请求设置的最小对象。被拒绝或格式错误的文件不属于“缺失文件”，不得将其替换。
3. 保留与请求无关的键、对格式敏感的值以及未知字段。
4. 再次读取文件以确认保存的值已发生变化。请勿将再次读取的结果视为实时或生效状态的证据。
5. 报告旧的保存值（或缺失及其有效默认值）、新的保存值、该更改是永久性的、当前会话未受影响，以及该更改将在下一次启动 Muse Code 时生效。请重启 Muse Code，无需告知用户手动重启终端应用。

对于 YOLO shell 回退场景，先前成功的 shell 读取不能替代必需的 `edit_file` 或 `write_file` 操作。请先尝试在同一路径上使用文件修改工具；只有在该工具在本轮明确拒绝后，方可使用原子结构化 shell 修改功能。

如果上述允许的访问路径仍然无法读取或写入活动配置，请报告未发生任何保存设置的变更并停止。请勿尝试其他配置根目录，也不得绕过任何安全控制。

## 完成报告

对于只读回答，请包含：

- 已检查的设置路径；
- 回答问题的键路径或默认值；
- 是否有文件被修改。

对于已验证的写入，请使用以下面向用户的摘要格式：

```text
已保存的更改
- <键>: <旧保存值或缺失 + 默认值> -> <新保存值>

永久性：是
当前会话：未受影响
生效时间：下次启动 Muse Code 时
需重新加载：必须重启 Muse Code；无需重启终端应用
验证方式：已在 <路径> 重新读取 `settings.json`
```对于诸如 `reasoning_effort` 这样具有更高优先级的启动输入设置，
在“生效值”一行后添加“除非启动标志覆盖了已保存的值”。对任何有意保持不变的设置也应予以注明。

如果读取、写入或验证失败，则使用以下格式：

```text
已更改：否
原因：<确切的路径及失败原因>
重新加载：不适用
```
