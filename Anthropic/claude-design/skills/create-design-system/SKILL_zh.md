# 创建设计系统

设计系统创建说明：
设计系统是文件系统中的一个文件夹，包含排版规范、颜色、资产、品牌风格与调性指南、CSS样式，以及UI、演示文稿等的React重现。它们使设计人员能够基于公司现有产品进行设计，并使用该公司的品牌元素来创建设计资产。设计系统应包含真实的视觉资产（如Logo、品牌插图等）、底层视觉基础（如排版细节、颜色体系、阴影、边框、间距体系）、可复用的UI组件，以及高层次的UI套件（完整页面）。

无需调用create_design_system技能；它就是这个功能。

一个自动化编译器会读取该项目，将组件打包成运行时库，并对样式进行索引。它通过文件内容和同级关系来发现一切——而不是通过文件夹名称——因此唯一固定的路径是：

- 项目根目录下的`styles.css`（或`index.css` / `globals.css` / `global.css` / `main.css` / `theme.css` / `tokens.css`——以第一个匹配为准）。这是全局CSS的入口；使用者只需链接这一文件。请将其仅保留为一系列`@import`语句。所有被其间接`@import`的内容都会被交付给使用者；在该作用域内的任何地方出现的`@font-face`规则都会声明对应的网页字体。

其余部分可根据品牌需求自由组织。一个合理的默认布局如下（除非所附代码库或品牌有其自身约定，否则请使用此布局）：

- `tokens/` — CSS自定义属性，每个关注点一个文件（如`colors.css`、`typography.css`、`spacing.css`等），均从`styles.css`中`@import`引入。
- `components/<group>/` — 可复用的React UI原语组件。
- `ui_kits/<product>/` — 真实产品界面的全屏交互式重现。
- `guidelines/` — 基础样例卡片及更深入的文字说明。
- `assets/` — Logo、图标、插图、图片素材。
- `readme.md`（根目录） — 设计指南与清单。

无论路径如何，编译器会查找以下内容：
- **组件**：任何位于同一目录下且带有同名`.d.ts`文件的`<Name>.jsx`或`<Name>.tsx`文件（命名采用PascalCase）。同时添加`<Name>.prompt.md`，并在每个目录中放置一个带有`@dsCard`标签的`.html`文件（其第一行为`<!-- @dsCard group="…" -->`；具体详情见下文“组件”部分）。
- **令牌（token）**：在`styles.css`可达的文件中，在`:root`（或单选择器的主题作用域）下声明的任何`--*`自定义属性。
- **字体**：在同一作用域内出现的任何`@font-face`规则；其`src: url(…)`指向的资源即为交付给使用者的字体二进制文件。

开始时，请先根据以下任务创建一个待办清单，然后按清单执行：- 研究所提供的资产和材料，以对公司的背景、产品概况以及所涉及的各类产品等形成整体理解。逐一阅读每份资产（代码库、Figma 文件、文档等），了解其用途。查找产品文案，审视核心界面，并寻找设计系统相关的定义。
- 在项目根目录下创建一个 `readme.md` 文件，概述公司与产品的背景、所涉及的产品类型等信息。注明所获取的资源来源：完整的 Figma 链接、GitHub 仓库地址、代码库路径等。不要假设读者已拥有这些资源，但应妥善保存，以防他们后续获得访问权限。
- 调用 `set_project_title` 方法，为项目指定一个简短名称，该名称应源自品牌或产品名称（如“Acme 设计系统”）。此举将替换默认占位符，便于项目检索。
- 如果附有演示文稿，请使用 REPL 工具浏览并提取关键资产与文本，将其保存至本地。
- 深入研究代码库和/或 Figma 设计文件，编写 CSS 自定义属性文件——在 `:root` 选择器中定义基础值（如 `--fg-1`、`--font-serif-display`）及语义别名（如 `--text-body`、`--surface-card`）。将所有 Web 字体或 TTF 文件复制到项目中，并在 CSS 文件中写入相应的 `@font-face` 规则。随后，仅通过 `@import` 语句构建根样式表 `styles.css`，确保引入所有自定义属性文件和字体文件，切勿在此文件中内联任何规则。
- 继续探索，并在 `readme.md` 中新增“内容基础”章节：文案如何撰写？语气、大小写等规范是什么？采用“我”还是“你”的视角？是否使用表情符号？整体风格调性如何？请附上具体示例。
- 继续探索，在 `readme.md` 中补充“视觉基础”章节，阐述品牌的视觉元素与设计原则。包括色彩、字体、间距、背景（图片？全幅？手绘插图？重复图案/纹理？渐变？）、动效（缓动曲线？淡入淡出？弹跳效果？无动效？）、悬停状态（透明度、颜色加深或变浅？）、按压状态（颜色变化？尺寸缩小？）、边框、内外阴影体系、保护色渐变与胶囊式设计的区别、布局规则（固定元素）、透明与模糊的使用场景、图像的色调氛围（暖色？冷色？黑白？颗粒感？）、圆角半径、卡片的外观（阴影、圆角、边框）等，以及其他你能想到的内容。务必回答上述所有问题。
- 若缺少字体文件，请在 Google Fonts 中寻找最接近的替代方案。向用户说明此替换情况，并请求提供更新后的字体文件。
- 在工作过程中，创建若干基础样卡（小型 HTML 文件），用于填充“设计系统”标签页。每张样卡尺寸约为 700×150 像素（最大 400 像素），倾向于制作更多小卡片而非少数密集型卡片。按子概念拆分：将主色、中性色与语义色分别置于不同卡片；展示字体、正文字体与等宽字体分开呈现；间距变量与实际应用示例也需独立成卡。典型的基础组件集包含 12–20 张以上卡片。无需标题与框架装饰——卡片名称会显示在卡片外部，因此只需直接展示色块、样本或变量，并尽量减少额外修饰。每张卡片均引用 `styles.css`（相对路径），以便正确加载真实变量。在每张卡片的第一行添加如下标记：`<!-- @dsCard group="<Group>" viewport="700x<height>" subtitle="<one line>" name="<Card name>" -->`。“设计系统”标签页会按 `group` 属性原样分组渲染项目中所有带此标记的 `.html` 文件。建议分组名称为：“字体”、“颜色”、“间距”、“品牌”——首字母大写且保持一致。
- 将标志、图标及其他视觉资产复制至 `assets/` 目录。**若提供的素材中不含标志，则不得自行创建**：在需要标识的位置以纯文字形式呈现品牌名称，并在 `readme.md` 中注明缺失情况。切勿凭记忆绘制、重建或近似还原企业的真实标志或品牌标识——即使从字体名称或示例内容中能推断出企业身份亦不可如此——更不得擅自将用户未提供的企业形象应用于设计系统。在 `readme.md` 中新增“图标体系”章节，描述品牌在图标设计方面的策略。回答以下问题及其他相关问题：是否使用特定的图标体系？是否有内置图标字体？是否常用 SVG 或 PNG 图标？（如有，请一并复制！）是否使用表情符号？是否将 Unicode 字符用作图标？务必复制关键标志、背景图片，以及 1–2 张通用全幅图片，并收录所有发现的通用插图。切勿自行绘制 SVG 或生成图像；如有可能，请以程序化方式复制图标。
- 对于图标：首先尝试将代码库自带的图标字体、雪碧图或 SVG 复制至 `assets/` 目录。若无法获取，则检查该图标集是否可通过 CDN 获取（如 Lucide、Heroicons），并直接从 CDN 引用。若两者皆不可得，则选用 stroke 宽度与填充样式最接近的 CDN 替代方案，并在“图标体系”部分予以标注。同时记录其使用情况。
- 开发可复用组件（详见“组件”章节）。每个组件目录下的卡片 HTML 文件必须在第一行添加如下标记：`<!-- @dsCard group="Components" … -->`。
- 针对每个交付的产品（如应用程序与网站），创建一个 UI 套件——包含 `{README.md, index.html, Screen1.jsx, …}`，并置于独立目录中。详见“UI 套件”章节。务必进行视觉验证。为每个产品或界面创建一项待办任务。
- 若提供了幻灯片模板，请创建若干示例幻灯片——包含 `{index.html, TitleSlide.jsx, ComparisonSlide.jsx, BigQuoteSlide.jsx, …}`，并置于独立目录中。若未提供示例，则无需创建。为每种幻灯片类型创建一个 HTML 文件；若有现成的演示文稿，请复制其样式。结合视觉基础，并引入标志及其他资产。在每张幻灯片 HTML 的第一行添加如下标记：`<!-- @dsCard group="Slides" viewport="1280x720" -->`，使 16:9 的画布能够适配卡片尺寸。
- 为每个 UI 套件的 `index.html` 添加如下标记：`<!-- @dsCard group="<Product>" viewport="<design width>x<above-fold height>" -->`——声明的高度将限制预览范围，因此请选择值得展示的部分。
- 更新 `readme.md`，添加简短的“索引”，引导用户查看其他可用文件。该索引应作为根目录的清单，并列出组件、UI 套件等内容。
- 创建 `SKILL.md` 文件（详情见下文）。
- 完成！“设计系统”标签页将展示所有已注册的卡片。请勿对输出结果进行总结，仅列出注意事项（如未能完成或存在疑虑之处），并明确提出、清晰而坚定的请求，希望用户协助迭代优化，以臻完美。组件
- 这些是品牌的可复用 UI 原语。**当某个具体来源定义了组件库（已挂载的 .fig 文件、Figma 链接，或附加代码库中的组件库）时，该组件库即为组件清单**——严格按照来源所定义的组件族进行构建，不多也不少。如果来源未定义某些设计系统“通常”会包含的原语（如 Toast、Avatar、Tabs 等），则不应自行添加；因为与来源中无对应物的组件会被使用者视为凭空发明，而设计师也无法识别。若确有新增需求（例如针对某字形集的 Icon 包装器），请在 readme.md 的“有意新增”部分列出，并附上简短说明。只有在没有任何来源定义组件的情况下（仅基于品牌指南或从零开始的项目），才应按品牌需求自建一套标准组件集——Button、IconButton、Input、Select、Checkbox、Radio、Switch、Card、Badge、Tag、Tabs、Dialog、Toast、Tooltip 等。无论哪种情况，都应按关注点分组（例如放在您选择的父目录下的 `forms/`、`feedback/`、`navigation/` 等）；对于小型组件集，使用单一的 `core/` 组即可。
- 先枚举再构建：首先列出来源的完整组件清单（对于已挂载的 .fig 文件，请查阅 /METADATA.md 中的“Component families”章节；对于 Figma 链接，请通过 get_design_context 获取文件的页面和组件列表）。将每个组件族都列入待办清单，并按此清单逐一构建，同时跟踪进度。切勿只停留在所谓的“核心子集”。如果无法完成，请在结束时明确报告哪些组件尚未构建，并询问用户是否继续——绝不能在未完成时悄然终止。
- 每个组件对应一个文件 `<Name>.jsx`（或 `.tsx`），其中包含 `export function <Name>(props) {…}`——以 PascalCase 命名的导出函数；该名称即为公共 API，且必须使用 `export` 关键字，以便打包工具能够正确识别。保持组件的自洽性：仅导入 React，样式通过 CSS 自定义属性引用（不使用 CSS-in-JS 库，也不引入 npm 依赖包）。同级组件之间可通过相对路径互相导入。
- 在同一目录下，编写 `<Name>.d.ts` 文件，定义该组件的 props 接口——这个兄弟文件决定了组件的 props 合约、遵循规则以及作为起点的资格；缺少它的 `.jsx` 文件仍会被打包并以命名空间形式导出，但不具备上述特性。此外，还需编写 `<Name>.prompt.md` 文件（首行为一句话的“用途与适用场景”，随后是一个简短的 JSX 使用示例，最后列出值得关注的变体或 props）。
- 每个目录放置一张卡片 HTML（文件名可自定，如 `buttons.card.html`）：第一行写入注释 `<!-- @dsCard group="Components" viewport="700x<height>" name="<Directory label>" -->`。通过正确的相对路径链接 `styles.css`，并通过 `<script src="…/_ds_bundle.js">` 加载打包后的脚本（路径相对于项目根目录），然后在 `<script type="text/babel">` 块中调用 `const { <Name> } = window.<Namespace>` 来挂载组件——使用 `check_design_system` 获取确切的命名空间名称。切勿直接 `<script src>` `.jsx` 文件（其 `export` 在内联脚本中不可访问）。展示关键状态与变体（主次按钮、镂空按钮；不同尺寸；禁用状态；带图标等）。确保内容紧凑、易于浏览，而非仅呈现默认渲染效果。
- 切勿手动编写 `_ds_bundle.js`、`_ds_manifest.json`、`_adherence.oxlintrc.json` 或桶式入口文件 `index.js`——这些文件均由工具自动生成。起点
- 在消费型项目中，会显示一个“起点”选择器，允许用户以本系统中的某个组件或屏幕作为新设计的初始模板。入选需通过特定标签进行主动声明——该标签与用于填充“设计系统”选项卡的 `@dsCard` 标签是分开的。
- 要标记一个组件：在该组件的 `<Name>.d.ts` 属性接口的 JSDoc 中添加 `@startingPoint section="<group>" subtitle="<one line>" viewport="<WxH>"`。选择器中的缩略图即为该目录下带有 `@dsCard` 标签的 HTML 文件，请确保其在指定视口下能合理渲染。
- 要标记一个屏幕：在 HTML 文件的第一行添加 `<!-- @startingPoint section="<group>" subtitle="<one line>" viewport="<WxH>" -->`。屏幕本身即为缩略图。
- 当用户输入“创建起点 `<X>`”（或“将 `<X>` 添加为起点”）时，编写一个 HTML 文件，并在其第一行加入 `<!-- @startingPoint section="…" -->` 注释——项目中任何带有该标签的 `.html` 文件都会被纳入索引。通常约定使用 `ui_kits/<x>/index.html` 作为存放位置，但并非强制要求。
- 当用户请求移除或重命名某个起点时，编辑对应的标签；当用户希望更换缩略图时，编辑该组件所在目录下带有 `@dsCard` 标签的 HTML 文件（针对组件）或直接修改屏幕的 HTML 文件。

UI 套件详情：
- UI 套件是对完整界面（而非基础元素）的高度还原性视觉与交互重现。它们在功能实现上会适当简化（并非真正的生产代码），但在视觉上力求像素级精确，尽可能通过阅读原始 UI 代码来构建，或借助 Figma 的设计上下文提取工具。UI 套件由您之前编写的组件基础元素构成；请勿在套件内部重新实现 Button 等组件。每个 UI 套件的 `index.html` 应呈现产品的一个典型视图。这些是复刻作品，而非故事书式的展示。
- 首先，更新待办清单，为每个产品列出以下步骤：(1) 在 Figma 和代码中探索代码库及组件（获取设计上下文）；(2) 为每个产品创建 3–5 个核心屏幕（如首页或应用主界面），并内置可交互的点击流转组件；(3) 回顾设计上下文，对设计方案进行 1–2 次视觉迭代。
- 确定来自该公司的核心产品或代码库中的主要产品，可能是一个，也可能有多个（如移动应用、营销网站、文档网站等）。
- 每个 UI 套件包含该产品的各界面 JSX 代码（结构清晰、模块化且简洁），例如侧边栏、编辑器、文件面板、首屏区块、页眉、页脚、博客文章、视频播放器、设置页面、登录页等。
- `index.html` 文件应展示该 UI 的交互式版本（例如，聊天应用应呈现登录界面，并允许用户创建聊天、发送消息等模拟操作）。
- 应严格遵循设计上下文或代码库中的视觉规范，确保还原度准确。无需完全照搬组件的具体实现，只需制作简化且以外观为主的版本即可。务必忠实还原。
- 必须覆盖源代码中定义的所有组件类型——覆盖率指的是完整的枚举清单，而非手动挑选的子集。在 UI 套件的单个屏幕内，可以对重复内容进行简略处理（如用 3 行代替 30 行相同的布局），但绝不能遗漏任何组件类型。
- 不得为 UI 套件设计全新的方案。UI 套件的职责是复刻现有设计，而非创造新设计。请复制原设计，不要重新发明。如果项目中未出现某项内容，则应省略，或明确留空并附上说明。指导方针
- 独立运行，除非遇到关键阻碍（例如无法访问粘贴的 Figma 链接、无法访问代码库），否则不要停止。
- 在制作幻灯片和 UI 套件时，避免在图标设计上偷工减料；请直接复制图标资源！不要使用手绘 SVG、表情符号等来制作半成品的图标表示。
- 重要提示：除非别无选择，否则切勿仅凭截图重新绘制 UI！应以代码库或 Figma 的“获取设计上下文”功能作为权威来源。截图的信息损失远大于代码；可将截图作为高层次的参考，但只要可能，务必在代码库中查找组件！
- 附件中的套件是最终标准。当其数值与所参照的组件库（如 shadcn、MUI 等）的既定规范不一致时，以套件为准。从源文件中精确复制数值——内边距、圆角半径、字体大小、行高——切勿四舍五入或对齐到 4/8px 网格或框架默认值。如果套件标注为 5px，就写 5px，而不是 4px。
- 除非确实在代码库或 Figma 中看到，否则避免以下视觉元素：蓝紫色渐变、表情符号卡片、仅左侧带颜色边框且圆角的卡片。
- 避免解析 SVG 文件——这会浪费上下文信息！如果已知其用途，直接复制并引用即可。
- 使用 Figma 时，请通过“获取设计上下文”功能了解所使用的设计系统和组件。截图仅适用于高层次的参考。同时确保展开变量和子组件以获取其内容。（get_variable_defs）

SKILL.md
- 完成后，请确保该文件与 Agent SKills 兼容，以便用户可以下载并在 Claude Code 中使用。
- 创建如下格式的 SKILL.md 文件：

```
<skill-md>
---
name: {brand}-design
description: 此技能用于为 {brand} 构建高质量的品牌化界面及资产，适用于生产环境或一次性原型/样机等场景。包含必要的设计指南、颜色、字体、图标资源以及用于原型设计的 UI 组件库。
user-invocable: true
---

请阅读本技能内的 README.md 文件，并探索其他可用文件。
若需创建可视化成果（如幻灯片、样机、临时原型等），请导出相关资源并生成静态 HTML 文件供用户查看。若进行生产级开发，可复制资源并遵循此处规则，成为精通该品牌设计的专家。
若用户调用本技能而未提供其他指示，请先询问其目标，提出若干问题，并根据需求输出 HTML 成果或生产级代码，扮演专业设计师的角色。
</skill-md>
```
此外，请提醒用户在“共享”菜单中将文件类型设置为“设计系统”，以便组织内的其他成员也能查看该设计系统。
