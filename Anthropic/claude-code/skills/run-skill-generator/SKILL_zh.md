你的任务是在 `<unit>/.claude/skills/run-<unit-name>/` 目录下创建一个**技能**，使未来的智能体能够在一台全新的机器上构建、启动并**驱动**这个项目。

该技能由两部分组成，它们共同存在：

```
<unit>/.claude/skills/run-<unit-name>/
  SKILL.md      <- 面向智能体的简明指令，指向驱动程序。
  driver.mjs    <- （或 driver.py、smoke.sh 等——也可能没有：对于 Web 应用，直接使用现成的 chromium-cli，而 SKILL.md 中的 heredoc 就是脚本）
```

这几乎总是意味着**编写代码**，而不仅仅是撰写说明文档。如果应用有任何交互界面（GUI、TUI、长期运行的服务器、REPL），未来的智能体需要一种程序化的方式来与之交互。仅靠 Markdown 文件无法点击按钮——但有时“按钮点击器”已经存在：对于 Web 应用是 `chromium-cli`，对于服务器则是 `curl`。你现在就构建（或脚本化）这个交互工具，并将其与技能一同提交；`SKILL.md` 则记录如何使用它。

## 完成标准

当以下所有条件都满足时，即视为完成：

1. **你已在当前容器中启动应用并与之交互**——不是它的测试套件，而是正在运行的真实应用。对于任何带有 GUI 的应用，这意味着你必须有一张从磁盘保存下来的截图。
2. **交互驱动工具已提交**，且与技能位于同一目录下。可以是驱动脚本、REPL 包装器、冒烟测试，或者直接写在 `SKILL.md` 中的 `chromium-cli` heredoc——无论你在步骤 1 中用什么方式驱动应用。（如果它后来被移到 `scripts/` 或 `e2e/` 目录下也没关系，只需在 `SKILL.md` 中指向新位置。如果是使用现成 `chromium-cli` 的 Web 应用，内嵌的脚本就是驱动工具，无需单独文件。）
3. **`SKILL.md` 将该驱动工具作为主要操作路径**——未来智能体首先阅读的部分应是“运行此驱动程序 / 将这些命令管道到 `chromium-cli`”，而不是“运行 `npm start`，然后窗口就会打开”。
4. **`SKILL.md` 中的每个代码块都是你实际运行并成功执行过的命令**。必须是在本次会话、当前容器中运行的，而非来自 README 或推断得出的。

如果你正准备编写技能却尚未满足条件 (1)，**请立即停止**。你很可能只是在复述现有的文档。那个文档早已存在——它就是 README，而你之所以来到这里，正是因为 README 并不足够。

## 交付物是代码与文档

典型的输出是一个包含以下内容的技能目录：

```
<unit>/.claude/skills/run-<unit>/
  SKILL.md         <- 简短，指向驱动程序，并带有前端元数据，使 Claude 在收到“运行 <unit>”或“截屏 <unit>”的请求时能够自动加载。
  driver.mjs       <- （或 driver.py、smoke.sh 等——也可能没有：对于 Web 应用，直接使用现成的 chromium-cli，而 SKILL.md 中的 heredoc 就是脚本）
```

驱动程序默认存放在**技能目录内**。它与技能说明是一对：技能的指导说明和实现这些说明的代码。此处的驱动程序允许比生产代码稍显“粗糙”，因为它是智能体的工具，而非产品的用户界面。

**升级：** 如果驱动程序逐渐演变成项目自身测试套件也想复用的内容——例如共享的启动辅助工具、真正的端到端测试框架——则将其移至 `scripts/` 或 `e2e/` 目录，并更新 `SKILL.md` 以引用新的路径。技能本身保持不变，而驱动程序则找到更合适的归宿。

具体形式因项目而异，但原则始终如一：**驱动程序才是交付物**。`SKILL.md` 是它的手册页。对于 Web 应用，驱动程序可能就是现成的 `chromium-cli`（参见 [examples/playwright.md](examples/playwright.md)），而技能则是用来调用它的脚本。对于桌面应用（参见 [examples/electron.md](examples/electron.md)），驱动程序可能是 tmux 下的一个自定义 REPL，暴露 `launch`/`ss`/`click`/`eval` 等命令。对于服务器，驱动程序则是 `curl`。无论形式如何，若没有能真正触达运行中应用的交互手段，那么这个技能就只是对一个无人可触的窗口的描述。

## 技能的存放位置该技能位于 `<unit>/.claude/skills/run-<unit-name>/`，其中
`<unit>` 是 **一个可部署单元** 的目录——可以是应用、服务或库。

Claude Code 能够**原生地从嵌套的 `.claude/skills/` 目录中发现技能**：只要代理在 `<unit>` 内的任意位置运行，就会将 `/run-<unit-name>` 视为可用技能，并在请求与该技能的描述匹配时自动加载（例如，“运行桌面应用”“截取账单界面的屏幕截图”）。

- **单项目仓库**：在仓库根目录下放置 `.claude/skills/run-<repo-name>/`。
- **包含多个应用的大仓库**：每个应用各有一个技能，与其同级存放——如 `apps/billing/.claude/skills/run-billing/`、`apps/desktop/.claude/skills/run-desktop/`。
- **包含多个二进制文件的应用**：仍只保留一个技能，位于应用根目录下，每个二进制文件对应一个节。它们共享相同的初始化配置。可从最接近的单二进制示例入手，为每个二进制文件添加一个 `## Run: <name>` 节。

如果你不确定单元的边界在哪里，请**询问用户**。

对目录名进行 URL 安全化处理：全部小写，用短横线代替空格，不使用斜杠（如 `run-billing-api`，而非 `run-billing/api`）。目录名与 frontmatter 中的 `name:` 应保持一致——这就是对应的命令行指令。

## 流程

### 0. 查找现有关于运行此应用的技能

列出项目中所有技能及其描述（与 `/run` 探测使用的描述相同——用户可能给这些技能起不同的名字，因此应按描述而非名称匹配）：

```bash
d=$PWD; while :; do
  grep -Hm1 '^description:' "$d"/.claude/skills/*/SKILL.md 2>/dev/null
  [ -e "$d/.git" ] || [ "$d" = / ] && break
  d=$(dirname "$d")
done
```

如果已存在一个与启动/运行该应用相关的技能——无论其名称如何——请**优化而非重写**：核实其说明是否准确，修复错误，补充缺失内容，保留有效部分。如有驱动脚本，也请重新运行。并保留其原有名称。

（同时检查是否存在旧版的 `.claude/run.md`——早期版本的工具会生成此类文件。若找到，请将其迁移：将文件正文移至技能的 `SKILL.md`，将其中引用的脚本移入技能目录，并删除旧文件。）

若未找到相关技能，则确定创建位置（参见上文），然后继续。

### 1. 发现——并将每项声明视为可证伪的假设

明确你要编写的技能面向的对象：

- 如果当前目录即为完整的清单文件所在处（如 `package.json`、`go.mod`、`pyproject.toml` 等），且它代表一个自洽的整体，则此即为单元。
- 如果看起来像是一个大型仓库的根目录（如 `apps/`、`packages/`、`services/`），则**请询问具体是哪一个**。列出候选选项，让用户选择，然后切换到相应目录。
- 若确实难以判断，请询问用户。

在常见位置中进行调查：`README.md`、`package.json` scripts、`Dockerfile`、`Makefile`、`.github/workflows/`、`CONTRIBUTING.md`。CI 配置往往比 README 更准确。

**现有文档中的每一项声明都是一种假设**。尤其是那些否定性的声明：

| 文档中写道…… | 你该怎么做 |
|---|---|
| “仅支持 macOS/Windows” | 仍然尝试在 Linux 上启动。应用很少会直接拒绝启动——它们通常会在缺少某个 `.so` 文件时崩溃，而通过 `apt-get` 即可解决。针对你所在主机的钥匙链/通知等原生模块可能会被无操作处理；核心功能通常仍能运行。 |
| “需要 GPU” | 尝试软件渲染。Electron/Chrome 可通过 `--disable-gpu` 进行回退。 |
| “需要付费账号/功能开关” | 这类限制通常是可读的代码。找到它（环境变量？构建宏？SSR 嵌入的 JSON？），并为本地运行打上补丁。记录下这一修改。 |
| “运行 `npm start`” | 这是人工操作路径（会弹出窗口，无限等待）。寻找或构建程序化的路径——例如使用 `electron-forge start` 先构建再通过 Playwright 启动，或其他等效方式。 |

由 macOS 开发者撰写的 README 中若写着“不支持 Linux”，其实只是意味着“我从未尝试过”。而现在你就要去尝试。**如果你在此处放弃，那么你最终编写的技能就只是带额外步骤的 README。**

### 2. 执行——并搭建所需的测试框架

你现在处于一个无头的 Linux 容器中。应用很可能会与你“对抗”。这种对抗过程正是技能的核心内容。

在操作过程中持续维护一份 `NOTES.md`。记录每一次报错、每一次修复，以及最终生效的每一条命令。这份草稿将成为故障排除章节的内容。**逐步过渡到真实的交互：**

- **安装并构建。** 如果缺少某些依赖，记下确切的 `apt-get` 或 `npm install` 命令来解决。
- **启动应用。** 是启动应用本身，而不是测试套件。桌面 GUI（Electron 或原生）需要 `xvfb-run` 和一些 `lib*` 库；而由 `chromium-cli` 驱动的 Web 应用则可以无头运行，两者都不需要。在这个阶段，启动超时和难以理解的崩溃都很常见。查看堆栈信息，安装缺失的依赖，再试一次。
- **构建一个驱动框架。** 你需要一个能够控制正在运行的应用的接口，以便以编程方式发送输入并观察输出。具体形式取决于项目（见下表）。

  **覆盖 PR 实际改动的那层或几层。** 对于 UI 的改动，使用一个通过 tmux 操作 CLI 用户界面的驱动是合适的；而对于只涉及某个内部函数的 PR，则不合适。对于后者，代理应该使用 `NODE_ENV=test bun run script.ts`（或等效命令）：导入该函数，调用它，并观察结果。如果这里的大多数 PR 都在改动内部逻辑，那么直接调用的路径就是驱动的主要入口，而通过 tmux 启动的方式则是次要的。查看最近合并的 PR：它们主要改动了哪一层？就覆盖那一层。
  
  对于 **Web** 应用，`chromium-cli` 就是驱动——你只需编写脚本去操作它，而不是自己实现（参见 [examples/playwright.md](examples/playwright.md)）。对于 **桌面** GUI（Electron），则需要编写一个 REPL 驱动（通过标准输入接收命令 -> 点击/输入/截图），在 tmux 中运行，并使用 `send-keys` 和 `capture-pane`。你会不断迭代这个驱动——一开始可以很简单（仅包含 `launch`、`ss`、`quit` 等命令），然后根据需要逐步增加更多命令，直到能到达应用中感兴趣的部分。
  
- **完整地执行一次真实的用户流程。** 点击按钮，填写表单，在 DOM 中查看结果，截个图。**务必认真查看这张截图。** 如果它是空白的，或者显示的是错误页面，那就还没完成。
- **然后运行测试。** 单元测试只是用来做基本验证，不是主要目标。
- **干净地停止。**

**障碍本身就是内容。** 你会遇到各种奇怪的问题——坐标系对不上、某些 API 在当前版本的 Electron 上返回空值、功能开关把你要测试的内容隐藏起来。每一个这样的问题都应该记录在“陷阱”部分，并且通常会在你的驱动中加入相应的处理逻辑。理想状态是“陷阱”部分里写满了那些谁也想不到的坑点。
  
**驱动脚本要与技能一起提交。** 它不是临时搭建的脚手架，而是未来所有代理（以及人类）驱动这个应用的方式。默认情况下，它会放在技能目录内（对于使用 `chromium-cli` 的 Web 应用，这意味着直接写在 `SKILL.md` 里——使用 heredoc 格式来嵌入脚本）。如果脚本变得过于庞大——比如项目的正式测试套件也需要引用它——那就把它移到 `scripts/` 或 `e2e/` 目录，并更新 `SKILL.md` 来指向那里。

### 3. 编写 SKILL.md

简短明了，指向驱动脚本。以 [template.md](template.md) 作为起始模板，其中包含了必要的前言结构。

**前言很重要。** `name:` 字段将成为 Slash 命令（例如 `/run-billing`）。`description:` 则是 Claude 用来决定是否自动加载此技能的依据——请在此处填写 **代理实际会使用的动词**：“run”、“start”、“build”、“test”、“screenshot”。笼统的描述（如“有用的计费工具”）将无法匹配。  

正文结构：

1. 一段简介：说明该应用是什么，以及它的驱动方式——桌面端使用 xvfb/tmux 下的 `<driver-path>`，Web 端使用 `chromium-cli`，服务器端使用 `curl`。
2. **先决条件**——您实际执行的完整 `apt-get install` 命令。
3. **构建**——按顺序列出所有具体命令。如有需要打的补丁（如功能开关、配置覆盖），请附上对应的 `sed` 命令或修改内容。
4. **运行（Agent 路径）**——首先介绍如何启动驱动程序、它接受哪些命令、截图保存在何处。如果是 REPL，请展示 tmux 的封装。这是下一个 Agent 实际会用到的部分。
5. **运行（用户路径）**——其次，如果与 Agent 路径不同。例如 `npm start` 启动后打开窗口，然后按 Ctrl-C 结束。简要说明，注意该模式无法无头运行。
6. **常见陷阱**——实战中遇到的问题及解决办法。那些看似可行却行不通的情况，以及相应的变通方案。如果这部分内容过于泛化，则说明您没有充分应对挑战。
7. **故障排除**——从症状到解决方案。仅列出您实际遇到过的错误。

务必做到**可验证**（您亲自运行过）、**明确唯一路径**（只提供一种方案，而非多种选择）、**如实描述**（不稳定？运行慢？如实注明）。

**SKILL.md 中的路径均以 `<unit>/` 为基准，而非技能目录本身。** 如有歧义，请在开头予以说明。当驱动程序位于技能内部时，其相对于 `<unit>` 的路径为 `.claude/skills/run-<unit-name>/driver.mjs`——虽然较长，但非常清晰。

### 4. 验证
开启一个全新的终端，进入单元目录，严格按照技能的 SKILL.md 文件逐行操作，不得擅自更改。任何临时调整都会导致流程断点，需及时修复。

## 项目类型模板
为您的驱动程序选择一个初始结构。这些示例与 `/run` 技能共享（当不存在特定项目的运行技能时，会使用相同的项目类型模板作为默认方案）。如果您正在编写新的运行技能，这些示例可作为您的起始模板。

| 项目类型 | 驱动程序形态 | 示例 |
|---|---|---|
| Web 服务器 / API | 后台启动 + 基于 `curl` 的冒烟测试脚本 | [examples/server.md](examples/server.md) |
| CLI 工具 | 使用代表性参数的冒烟测试脚本，检查退出码和输出 | [examples/cli.md](examples/cli.md) |
| TUI / 交互式终端 | tmux 封装：`send-keys` / `capture-pane` | [examples/tui.md](examples/tui.md) |

| 浏览器驱动 | 开发服务器 + `chromium-cli` 脚本 | [examples/playwright.md](examples/playwright.md) |
| 库 / SDK | 导入并调用的冒烟测试脚本 | [examples/library.md](examples/library.md) |

对于 Web 应用，可从 [examples/playwright.md](examples/playwright.md) 入手——使用 `chromium-cli` 进行驱动，无需自定义驱动程序。对于桌面应用，可从 [examples/electron.md](examples/electron.md) 入手——其中包含完整的 `_electron` REPL 驱动框架、tmux 封装，以及可能遇到的各种障碍清单。

## 必须包含的内容
- **先决条件**——操作系统软件包、运行时环境、工具。Ubuntu 的 `apt-get` 安装命令，务必准确无误。
- **设置**——安装依赖、配置，以及任何必要的补丁。
- **构建**——编译或打包。
- **运行（Agent 路径）**——驱动程序的具体操作、相关命令、截图存放位置。
- **直接调用**——若可直接调用，说明如何在不启动完整应用的情况下导入并运行内部代码，以及绕过初始化保护的环境变量或标志。许多 Pull Request 只需这一部分即可。
- **运行（用户路径）**——如果与 Agent 路径有显著差异。
- **测试**——测试套件的执行命令。
- **常见陷阱**——您遇到的非显而易见的问题。
- **故障排除**——从错误现象到解决方法。
- **驱动程序本身**——提交至技能目录（或移至 `scripts/` 或 `e2e/`），或者对于基于 `chromium-cli` 的 Web 应用，直接内嵌于 SKILL.md；无论哪种情况，均应在 SKILL.md 中予以引用。

## 不必包含的内容- **任何你没有实际运行过的内容。** 如果 README 中写着 `yarn start:prod` 而你从未执行过，那么这部分就不属于该技能。就此为止。
- **为你不支持的平台文档化“正常流程”。** 你在 Linux 容器中工作。对于 macOS 专用且你无法验证的部分，都只是推测。只需提及它的存在，无需展开说明。
- **选项过于详尽。** 只需提供一条可行的路径。
- **架构相关的文字描述。** 那是其他文档的职责。
- **泛化的故障排除。** “如果构建失败，请检查你的 Node 版本”——毫无用处。只记录你实际遇到并解决过的错误。
  
## 警示信号——你可能要交付错误的内容

如果出现以下情况，请停下并重新考虑：

- **你没有为 GUI 应用截取任何屏幕截图。** 说明你根本没有运行过它。
- **你的技能没有可指向的驱动脚本或冒烟测试脚本**，而该应用又是交互式的。下一个开发者将无从驱动它。（使用 `chromium-cli` 的 Web 应用？`SKILL.md` 中的 heredoc 就是驱动脚本，无需单独文件。）
