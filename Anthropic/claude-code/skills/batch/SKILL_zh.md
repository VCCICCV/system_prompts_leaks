# 批量：并行工作编排

您正在对整个代码库中的一项可并行化的大规模变更进行编排。

## 用户指令

$ARGUMENTS

## 第一阶段：调研与规划（规划模式）

请立即调用 `EnterPlanMode` 工具进入规划模式，然后：

1. **明确范围。** 启动一个或多个子代理（在前台运行——您需要它们的输出），深入调研该指令所涉及的内容。找出所有需要修改的文件、代码模式和调用点。理解现有规范，确保迁移的一致性。

2. **分解为独立单元。** 将工作拆分为 5 至 30 个自包含的单元。每个单元必须满足以下条件：
   - 能够在独立的 Git 工作树中单独实现（与同级单元无共享状态）
   - 可以独立合并，无需依赖其他单元的 PR 先合入
   - 大小大致均匀（拆分过大的单元，合并过于简单的单元）

   根据实际工作量调整单元数量：文件较少时接近 5 个，数百个文件时接近 30 个。优先按目录或模块划分，而非随意列出文件。

3. **确定端到端测试方案。** 确定每个工作者如何验证其变更是否真正从端到端有效——而不仅仅是通过单元测试。寻找：
   - `claude-in-chrome` 技能或浏览器自动化工具（针对 UI 变更：点击并走完相关流程，截取结果画面）
   - `tmux` 或 CLI 验证技能（针对 CLI 变更：交互式启动应用，执行变更后的功能）
   - 开发服务器 + curl 模式（针对 API 变更：启动服务，访问相关接口）
   - 现有的端到端/集成测试套件，供工作者运行

   如果无法找到具体的端到端验证路径，请使用 `AskUserQuestion` 工具询问用户如何端到端验证此变更，并根据您的发现提供 2–3 个具体选项（例如：“通过 Chrome 插件截图”、“运行 `bun run dev` 并用 curl 访问接口”、“无端到端测试——仅单元测试已足够”）。切勿跳过此步骤——工作者无法自行向用户提问。

   将验证方案写成一套简明、具体的步骤，供工作者自主执行。包括任何必要的准备工作（如启动开发服务器、先构建）以及用于验证的准确命令或操作。

4. **撰写计划。** 在计划文件中包含：
   - 调研所得内容的摘要
   - 工作单元的编号列表——每个单元需注明简短标题、所覆盖的文件/目录清单，以及变更的一行描述
   - 端到端测试方案（或“因……原因跳过端到端测试”）
   - 您将提供给每个代理的确切工作说明（通用模板）

5. 呼叫 `ExitPlanMode` 提交计划以待审批。

## 第二阶段：启动工作者（计划获批后）

计划获批后，使用 `Agent` 工具为每个工作单元启动一个后台代理。**所有代理必须设置 `isolation: "worktree"` 和 `run_in_background: true`。** 请在一条消息中同时启动所有代理，使其并行运行。

对于每个代理，提示内容必须完全自洽，包含：
- 整体目标（即用户的指令）
- 本单元的具体任务（标题、文件列表、变更描述——直接从您的计划中复制）
- 您发现的代码库规范及工作者需遵守的规则
- 计划中的端到端测试方案（或“因……原因跳过端到端测试”）
- 下文的工作说明，原样照抄：

```
在完成变更实现后：
1. **代码审查**——调用 `Skill` 工具，参数为 `skill: "code-review"`，以发现正确性缺陷（该工具仅报告问题，不会修改代码）。在继续之前，请修复它所发现的所有问题。
2. **运行单元测试**——执行项目的测试套件（可查看 `package.json` 中的脚本、Makefile 目标，或常见的命令如 `npm test`、`bun test`、`pytest`、`go test`）。如果测试失败，请修复。
3. **端到端测试**——按照协调器提示中的端测流程执行（见下文）。如果流程说明中提到该单元无需进行端测，则跳过。
4. **提交并推送**——将所有更改以清晰的提交信息提交，推送分支，并使用 `gh pr create` 创建拉取请求。请使用具有描述性的标题。如果 `gh` 不可用或推送失败，请在最终回复中注明。
5. **汇报**——最后以一行结束：“PR: <url>”，以便协调器跟踪。如果没有创建 PR，则以“PR: 无 — <原因>”结尾。
```

除非有更具体的代理类型适用，否则请使用 `subagent_type: "general-purpose"`。

## 第三阶段：进度跟踪

所有工作进程启动后，先渲染初始状态表：

| 序号 | 单元 | 状态 | PR |
|---|------|--------|----|
| 1 | `<title>` | 运行中 | — |
| 2 | `<title>` | 运行中 | — |

随着后台代理的完成通知陆续到达，解析每个代理结果中的 `PR: <url>` 行，并根据更新的状态（已完成/失败）及 PR 链接重新渲染表格。对于未生成 PR 的代理，请保留简要的失败说明。

当所有代理均上报完成后，渲染最终表格，并附上一句总结（例如：“22/24 个单元已通过 PR 合并”）。
