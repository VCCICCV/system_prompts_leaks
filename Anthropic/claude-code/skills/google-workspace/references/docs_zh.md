# Google 文档参考

作为第一步，在创建或修改 Google 文档之前，您必须完整阅读以下设计规范：文档应如何呈现与阅读，以及如何进行编辑。在这些规范之后，“应用设计规范”部分将说明如何使用相关工具落实这些规范，而文件的其余部分则介绍了 Docs 连接器的 `read_doc` 和 `update_doc` 方法，以及用于辅助处理 Docs 的 Drive 工具。

# 文档设计

当用户明确提出具体要求，例如字体、颜色、篇幅或结构时，请予以满足；对于用户未明确的部分，则按以下规则处理。关于文本本身的规则请参见“写作”部分，关于修改现有文档的规则请参见“编辑现有文档”部分。

## 结构

- **撰写前先规划各部分，并将用不同表述回答同一问题的两部分内容合并。** 如果用户指定了固定节数，应将合并后的内容替换为涵盖新内容的独立章节。
- **每个章节仅出现一次。** 完成前请按顺序检查各标题，确保无重复。
- **执行摘要以结论开篇。** 其第一段应明确读者应持有的观点或采取的行动。数字应置于正文各部分，用于支撑结论，而非作为结论本身。“7种工具合计债务12亿美元，加权平均票面利率4.8%”属于数据；“再融资风险集中于2027年。鉴于当前现金状况，我们建议对2027年票据进行机会性要约回购”才是结论。仅罗列数字的摘要并未提出明确结论。
- **用户指定的篇幅为上限。** “三页”“一页”或“500字”均为硬性约束：完成前务必核对，超限则需删减。针对三页需求却写至五页属缺陷，非详尽之故。请以渲染后的文档统计页数；若无渲染结果，可按每页约3,000字符估算。
- **首次请求后仍需遵守限制。** 用户在初始阶段给出的篇幅或来源清单，在后续请求未再次提及时亦应继续遵循。
- **源自某来源的数字与引文须与原文一致。** 每个数据、引文及页码引用均应来自您实际阅读过的原文部分，切勿凭记忆摘录。如无法找到某数值，请如实说明，切勿自行估算。

## 样式

文档的外观由其样式决定：正文采用“常规”样式，各级标题则使用内置标题样式。直接应用于个别段落的格式设置会延续到后续添加的文本中，并可能在整个长文档中蔓延。

- **只需为整个文档设置一次正文字体**，而不要逐段或逐行设置。如果逐段设置字体，后续添加的段落将无法继承该字体，最终导致文档中出现两种字体。
- **标题应使用标题样式。** 切勿通过加粗、增大字号来手动创建标题：这样做会导致标题未被收录到目录和大纲中，并且其格式会延续到下一段落。
- **不要单独调整某个标题的大小。** 每个标题级别都有预设的字号，若仅对某一段落进行覆盖式调整，可能会使小节看起来像章节。如果标题的级别不正确，请更改其级别；若某一级别的所有标题都应缩小，请修改该标题样式。切勿为了缩小字号而将位置正确的标题降级。
- **同类新内容会沿用周围样式，不同类新内容则不会。** 与现有条款相邻新增的条款会继承其样式。而在列表项或标题后直接插入的表格或正文段落，则会采用“正文”样式，而不带标题的加粗格式。否则，表格单元格会出现项目符号，而正文文字则可能变为加粗或标题格式。
- **颜色应用于词组，而非整段。** 一句红色文字可起到强调作用；若三段文字均为红色，则显得过于突兀，读者会不再将其视为提示信号。若需为多段文字着色，应改用标题或标注框。请仅为文字本身着色，而非整段，以免颜色延续至下一段落。

## 字体

- **新法律文书应使用Times New Roman字体。** 当您从零开始撰写合同、诉状、动议、法律备忘录或法律信函，且无模板可用时，请将正文设置为Times New Roman字体。这是法律实务中的专业默认字体，其他字体则显得不够正式。此规则不适用于已有内容的文档（应沿用其正文字体）、模板已设定字体的文档，或用户已指定特定字体的情况。

## 列表与编号

- **在新文档中，以及在文档自动编号的列表或标题中，切勿手动输入列表标记或章节编号。** 在这些情况下，不要以文本形式输入“•”、“-”、“*”、“1.”、“3.2”或“(a)”，而应使用文档的列表和标题编号功能。手动输入的标记起初看似正常，但一旦有人在其上方插入条目或章节，编号便会错乱。
- **具有相同列表样式的相邻列表项会合并为一个列表。** 编号甚至可以在两个列表之间的段落内连续进行，因此当第二个编号列表需要重新从1开始时，请务必检查其编号是否正确。

## 表格

- **与现有表格保持一致。** 若文档中已有表格，请为新表格设置相同的边框、底纹和表头行。在三张普通表格中插入一张带有彩色表头的表格，会显得格格不入。

## 页面布局- **除非用户提出要求，否则请保持页面设置不变**；在无页文档中，请跳过以下关于页面和栏的规则。“应用设计规则”部分说明了如何识别这种情况。
- **确保每个标题与其后的段落位于同一页**。如果标题单独出现在页面底部，即使内容正确，也会显得不连贯。在您创建的文档中，请在标题样式中设置“与下段同页”，使其自动应用于所有标题；在现有文档中，当发现标题与其段落被分开时，再手动进行此设置。
- **若要将某一部分（如财务报表）完整地置于一页，请在其标题前插入一个分页符，使该部分从新页开始**。首先检查是否已有分页符：多余的分页符只会增加一张空白页。如果加上分页符后该部分仍被拆分，则说明其长度已超过一页，请直接告知用户，而不要继续添加分页符。
- **当表格长度超过一页时，应防止表格行跨页断开**，确保每行完整地显示在同一页上。
- **页码是域，而非手动输入的文本**。如果在页脚中键入“第1页”，则每一页都会显示为“1”。
- **页眉和页脚可以有不同变体**。如果文档的首页页眉与其他页面不同，或奇数页与偶数页的页眉不同，则需分别修改每一处适用的页眉。
- **栏适用于整个节，而非段落样式**。若要将文档的一部分设为双栏，请为其单独创建一个节。
- **使用真正的脚注，而非在正文中手动输入的[1]等标记**。

## 检查最终效果

请查看排版后的页面，而不仅限于文本本身。假设可能存在格式问题，并逐一排查：

- **字体**：某一段落的字体与全文不同，或某节中间出现字号变化。
- **样式**：新增的文本看起来像普通正文，而其周围的段落却是标题或已应用样式的正文。
- **编号**：列表项丢失了编号，或(a)、(b)重新从(1)、(2)开始。
- **表格**：列宽发生变化，或单元格原本不换行却出现了换行。
- **格式延续**：加粗或斜体超出应有的范围继续延伸。
- **间距**：出现双空行、段落紧贴上方段落、缩进不均匀等问题。
- **修订提示**：插入或删除标记显示混乱，或与正常文本重叠。
- **分页**：标题单独位于页面底部、出现空白页，或原本可容纳于一页的内容现在被拆分。

修复一个问题后，请检查其周围的段落和页面。对某一段落的调整往往会影响后续段落，而篇幅的变化又会改变分页位置。

## 写作规范

您在文档中撰写的文字应读起来自然流畅，仿佛出自真人之手。一旦读者认为内容由AI生成，无论实际内容如何，都会将其视为粗糙之作并失去信任。读者通常会根据一系列常见特征作出判断，如下所示，因此请务必注意避免这些情况出现在您的写作中。本规则仅适用于您自行撰写的内容；若用户或其风格指南另有要求，则以用户的要求为准。除非用户明确要求，否则请勿擅自修改用户已有的文本以符合这些规则。- 只陈述事实，不要先否定其他内容。“收入增长12%，是美国增速的三倍”，而不是“这不是增长故事，而是市场份额的故事”。不要以“关键在于”或“真正的故事是”开头段落或要点。
- 要点、例证和形容词的数量应与内容相匹配，而非固定为三个。如果有两个驱动因素就列两个要点；有五个就列五个。如果列举恰好为三项（如“快速、可靠、可扩展”），往往意味着第三项只是为了语感而添加，并非因为确实有三点要说，读者会将其视为填充内容。
- 在可以用直白词语表达时，不要使用比喻。若有明确描述（如“同样的结构”“同样的模式”“放缓”“下降”），就直接使用。比喻适用于直白表述更冗长或不够精确的情况，而这在分析性写作中很少见。检验方法：若比喻可被一个普通词语替代且不损失原意，就应替换掉。比喻会让读者将其还原为直白说法，并承载你并未刻意选择的含义。常见比喻包括：“北极星”“推动进展”“双击”（意指深入查看）“拆解”“旅程”以及“格局”（指市场）。商务写作中常见的还有：“护城河”“逆风”“拖累”（指对业绩的成本影响）“安全网”“达标”以及“落地”（指完成或总额，如“预算节省4.4万美元”）。示例：
  - 不佳：“它拥有的都是同一种类。” 佳：“它拥有的遵循同样的模式。”
  - 不佳：“一次协调一致的支出暂停会立即显现。” 佳：“若多家大型客户在同一季度削减资本开支，会在下一份指引中体现出来。”
  - 不佳：“架构转型在进入时压缩了利润率，在退出时又扩大了利润率。” 佳：“毛利率在Hopper向Blackwell过渡期间下降，待Blackwell批量出货后才恢复。”
  - 不佳：“解锁增长的杠杆。” 佳：“正是价格调整让目标得以实现。”
- 删去那些仅宣称重要却未提供证据的词汇：“真正地”“确实”“实际上”“显然”“显著地”“稳健的”“杠杆作用”“深入探讨”“可执行的洞察”“经验教训”。若这些词只是用来代替某个事实，就直接写出该事实（如“利润率下降了4个百分点”，而非“利润率显著下降”）；否则就删除。当“杠杆”或“显著”具有其财务或统计学含义时（如“净杠杆率”“统计显著”），则属于专有名词，应予保留。
- 正确使用句号、逗号，并在列表前使用冒号。文档中不得出现表情符号。
- 慎用破折号：每段最多一个，标题、主标题以及加粗标签与其后文字之间均不应使用。一段内出现多个破折号往往是读者识别机器生成文本的首要特征之一。遇到这种情况，可用逗号、冒号、括号或另起一句来替代，切勿使用一字线或带空格的连字符。
- 文档中的标题应聚焦内容，而非你的工作流程：“欧洲未达计划，差额190万美元”或“定价”，而非“我做了哪些改动”或“难点所在”。标准标签如“执行摘要”或“下一步”并无问题。若文档已有标题，则新增标题也应保持一致风格，例如采用简短标签或完整句子的形式。
- 避免在文档中引入对话式语气。当用户要求更简洁或更正式的版本时，直接调整正文，不必冠以“执行摘要（精简版）”之类的标题，也不要在开头写上“根据您的反馈已更新”。这些信息对阅读文档的读者毫无意义，应在回复中说明修改内容，而非在文档本身中体现。此规则适用于文档正文，但不涉及评论区的回复。

## 编辑现有文档
以上规则适用于任何对已有文档的修改。你新增的内容同样须遵守上述各项规定。

### 仅修改被要求的部分- **使编辑的范围与请求一致。** “填写本部分”意味着添加文本，而不是同时更改对齐方式、添加下划线、重新排版表格或调整附近段落的样式。如果检查发现有您未打算进行的格式变更，请撤销该变更。
- **仅修改覆盖变更的最小范围。** 替换发生变化的词语，而非其周围的段落或章节。切勿为修改部分内容而删除并重新构建整个段落、章节或文档：这样做会导致评论、书签、图片、图表及其他嵌入对象丢失。
- **在未明确要求更改的地方保留原文措辞。** 未经用户要求而改写内容，会增加他们查找和审核的工作量。在合同中，这属于实质性变更：“aggregate”变为“total”，或“shall not”变为“will not”，都会改变文本的含义。
- **按角色进行格式调整。** “将正文设为11号字”指正文，而非标题；“缩进章节标题”指标题。在修改前先根据样式筛选出相关段落。
- **以文档中的实际值为准，而非凭猜测。** 如果某表格的表头行错误，而其他三行正确，请从正确的行中复制相应值。当用户指出某个参考项（如“使其看起来像第3节”）时，请仔细查看该节的精确样式、字体、字号、颜色、对齐方式及行距，并照此应用。在11号字的文档中凭猜测使用18号字，反而比原问题更糟。
- **保持相似表格的一致性，但仅限于用户要求您重新格式化表格时。** 当用户要求您重新格式化一组相似表格中的某一个时，应对其他表格也作出相同调整，或告知用户您仅修改了指定的一个。
- **因其他编辑操作而被连带更改的表格应予撤销，而非将其作为模板复制到其他表格。**
- **切勿在整个文档中替换裸数字。** 通过将所有“7”替换为“6”来填补章节编号的空缺，也会误改“7.1x”的利息保障倍数、“7.5%”的票面利率以及“FY2027”等。请逐个重新编号各级标题。

### 与现有内容保持一致

- **您添加的文本应采用文档的正文字体和样式，而非编辑器的默认设置。** 插入文本后，请将其字体和字号与前一段落进行比对。
- **使用文档既定的拼写风格**，例如英式英语或美式英语。新文本应与文档已使用的拼写风格保持一致，切勿在同一文档中混用不同风格，除非用户特别要求，否则不要将现有文本改为另一种拼写风格。若文档尚无内容，则遵循用户消息所使用的拼写风格。
- **明确设置颜色时应参考文档。** 如确需设置文本颜色，请从现有正文段落中复制颜色，而非默认设为黑色：许多文档样式会使用深灰色或主题色。
- **新增的带编号标题应沿用文档的编号规则。** 若文档自动编号标题，请在输入标题文本时暂不添加编号，并赋予其与相邻标题相同的样式或列表层级，以便自动获取下一个编号。若文档采用手动编号，则应遵照该编号惯例。
- **新增的列表项应延续当前列表。** 将新项作为所属列表的一部分添加，并确认其采用了正确的项目符号：在“(a)”之后应为“(b)”，而非重复“(a)”或跳过字母顺序。
- **统一标题格式。** 当用户要求所有标题保持一致时，首先将所有手工格式化的标题（如加粗、字号大于正文）应用正确的标题样式。然后逐级设置各层级的字体，每次仅针对一层级应用其对应的字体样式；若直接对所有层级应用第一层级的字体，则会抹平各层级之间的差异。此外，直接应用于文本上的字号或颜色设置不会被标题样式覆盖，因此还需一并清除这些属性。

### 文本内部的内容处理

有些元素会嵌入段落文本中，但并不表现为独立的对象：例如脚注标记、标签（如人物、日期或文件标签）、书签边界、批注锚点，以及内嵌的图片和图表。替换或删除包含这些元素的文本范围时，它们也会被移除：脚注消失、标签被删除、书签位置改变、图表随之消失。

- **在编辑句子之前，请先检查其内部内容**，并尽量从该元素的两侧而非直接穿过它来修改文本。
- **即使段落中没有可见文本，也可能包含图片或图表**；此外，浮动形状通常也锚定在某个段落上。删除段落时，这些内容也会一并被删除，因此在删除看似空的段落前请务必确认。
- **在设置了分栏的节中，请直接编辑节内的文本**，不要删除用于保持分栏格式的节结束符。

### 模板

- **填写占位符并保留模板结构**。填充模板时切勿删除图片占位符或签名行；删除这些占位符会破坏模板，影响后续使用者。
- **在填写任何内容之前，先找到所有占位符**。模板中常使用诸如[客户名称]之类的标记文字。若模板中未使用此类标记，则可按各部分的标题定位，并在其后输入相应内容。

### 批注

- **在原批注线程中回复**。回复批注时，请在原批注下进行回复，不要新建批注。如果所用工具不支持回复功能，请将回复内容提供给用户，由其自行粘贴到相应线程中。
- **一个主题对应一个线程**。添加批注前，请先查找针对同一段文字或同一主题的现有线程，包括您之前留下的线程，并在其中回复。多个批注堆叠在同一段落上，会使当前有效的批注难以辨认。
- **批注应保留在原处**。除非用户要求，否则不要删除或关闭批注。每个批注仅回复一次，不要添加无新意的重复回复。
- **编辑带有批注的文本时，应在批注范围内修改相关词语，而非全部替换**。批注与其所标注的文本绑定在一起，若整体替换该文本，批注及其回复也将被删除。应先完成修改，再进行回复，以免回复内容与实际未发生的修改相矛盾。
- **“处理所有批注”意味着逐条处理**。对每一条批注都要予以回应：如有修改要求，即按要求进行修改；若无，则以简短的一句话回复；除非用户要求，否则应保持线程开放。

### 建议

- **使用真正的修订建议**，切勿用划掉文字并加上颜色的方式来模拟建议效果。审阅者需要对每一项更改进行接受或拒绝操作。
- **不要为了“清理”而随意接受、拒绝更改或删除批注**。在审阅过程中，建议和批注线程本身就是工作成果的一部分；接受更改会抹去变更记录，删除批注则会丢失审阅者的意见。“清理文档”指的是修正格式问题。仅对用户指定的更改执行接受、拒绝或删除操作。
- **仅标记发生变更的词语**。若整段文字被整体替换，系统会将其显示为整段被删除后再重新插入，导致审阅者无法直观地看出具体改动之处。应只替换实际发生变化的词语，并将一段文字中的多项小改动拆分为多个单独的修订操作。例如，将期限从十二个月改为六个月时，正确的修订应为“十二（12）”改为“六（6）”，而非对整个句子进行替换。

### 结构性变更之后- **保持目录最新。** 在包含目录的文档中，添加、删除或重命名标题后，请在同一步骤中更新目录：如果目录仍显示“第4节：风险因素”，而实际第4节已改为“流动性”，则属于明显的错误。请更新现有目录；除非用户明确要求，否则不要为原本没有目录的文档新增目录。如果您的工具无法自动更新，请告知用户需要手动更新。
- **删除某节时，一并清除该节内容。** 删除某个章节的段落后，可能会遗留其表格或图片。请在删除前后分别统计表格数量，并核对是否与删除的段落数量一致。
- **删除重复章节前，请先阅读两份副本。** 保留格式与其他部分一致的那一份，并向用户说明您保留的是哪一份以及原因。
- **清理删除操作留下的残余内容：** 空表格、连续两个或多个空段落（将其合并为一个）、从列表中被截断的列表项，以及位于文末、导致出现空白最后一页的空段落。

### 检查您的修改

每次修改后，请回读所更改的内容：文本、样式、字体及任何列表标记。对于可能影响版面布局的修改，例如增删内容、调整表格、更改格式，或修复外观异常等问题，还应对照上文“检查结果”中的清单，逐页检查修改后的页面及其周边页面。

# Docs 和 Drive 工具

## 应用设计规则

上述部分设计规则作用于特定样式（如正文、标题1至6）或页码字段；Docs API 可应用指定样式但无法更改样式，也无法插入页码。其他规则则依赖于页面设置。请按以下方式处理：

- **正文字体，例如为新法律文书设置 Times New Roman：** 在所有文本输入完毕后，使用 `updateTextStyle` 方法（`weightedFontFamily`, `fields: "weightedFontFamily"`）统一设置一次，并确保后续添加的文本也采用相同字体。
- **使每个标题与其下一段落保持连贯：** 使用 `updateParagraphStyle` 方法（`fields: "keepWithNext"`），将各标题段落的 `keepWithNext` 属性设为 `true`。
- **将同一级别的所有标题统一调小或调大：** 告知用户，他们可以先调整其中一个标题的字号，然后选择“格式”>“段落样式”>“标题 N”>“更新‘标题 N’以匹配”，从而更改样式本身。若用户希望由您代为操作，则可一次性将该级别所有标题的字号统一调整。
- **页码：** 建议用户通过“插入”>“页码”来添加页码。
- **判断标签页是否为无页模式：** 在 `read_doc` 返回的结果中，检查当前正在编辑的标签页。当其 `documentTab.documentStyle` 中的 `documentFormat.documentMode` 为 `PAGELESS`，或在顶层 `documentStyle` 中未包含 `tabs` 键时，即为无页模式。在无页模式下，请勿添加页码、页眉、页脚或分栏；建议用户先通过“格式”>“切换为页面模式”将其转换为有页模式。
- **页面设置（用户提出变更请求时）：** 向请求中传递 `tabId`（无需指定位置或范围），并在 `documentStyle` 中提供新值，同时仅在 `fields` 中列出相应字段名，且不带 `documentStyle.` 前缀，例如：`{"updateDocumentStyle": {"tabId": "t.0", "documentStyle": {"marginTop": {"magnitude": 54, "unit": "PT"}}, "fields": "marginTop"}}`。凡在 `fields` 中列出但在 `documentStyle` 中缺失的字段均会被清空，因此切勿使用 `*`，因为它会将所有字段全部列出。

以上内容基于 Docs API 文档编写，尚未通过连接器进行测试。

## 创建文档

调用 Drive 的 `create_file` 方法，设置 `contentMimeType: "text/html"`，并将文档内容作为 `textContent` 传入。Drive 会将 `<h1>`、`<h2>`、`<p>`、`<ul>`、`<ol>`、`<b>`、`<i>` 和 `<a>` 自动转换为 Docs 的原生格式。这种方式比通过 Docs 编辑请求逐段构建文档更快且更不易出错。后续修改请使用 Docs 连接器。若用户需下载 Word 文件而非在 Google Docs 中编辑，则应改用 `docx` 技能。

## 文档的地址表示方式文档中的每一次编辑都指向一个位置，因此在本节中，位置的模型比其他任何东西都更为重要。

- **索引是以 UTF-16 代码单元为单位**，从标签页正文的起始位置开始计数，起始索引为 1。位于基本多文种平面之外的字符（如 🙂）算作 2 个代码单元，而由多个字符组成的表情符号则算得更多：👍🏽（👍 加肤色）算作 4 个代码单元。如果尝试在表情符号内部插入内容，文档会报错“插入索引不能位于一个字素簇内”；若试图删除 🙂 中间的部分，则会报错“删除范围无效”。每个段落末尾都有一个换行符，该换行符占用一个索引。
  
- **每次插入或删除都会使后续的所有内容发生偏移。** 在一次 `update_doc` 调用中，请求按顺序执行，因此根据读取结果计算出的索引仅对第一个涉及该区域的请求有效。请按从高到低的索引顺序发出请求，确保前面的请求不会移动后面请求所依赖的位置。
  
- **任何写入操作后，索引都会失效。** 切勿重复使用上次写入之前读取时得到的索引。请重新读取后再进行计算。
  
- **所有基于索引的写入操作都必须附带修订版本号保护。** 将读取时获得的 `revisionId` 作为 `writeControl.requiredRevisionId` 传递。如果在两次读写之间有其他人编辑了文档，整个批量操作将被拒绝，并返回 400 错误，而不是写入到错误的位置。遇到此类错误时，请重新读取并重新计算索引。切勿在没有此保护的情况下重试。
  
- **标签页是独立的索引空间。** 一个文档可以包含多个标签页，以及嵌套的子标签页。每个 `location` 和 `range` 都需要指定 `tabId`；若未指定，则请求会作用于第一个标签页，这会导致用户意图不符的静默失败。粘贴的 URL 如 `.../edit?tab=t.abc123` 会明确指定标签页：`t.abc123` 即为 `tabId`。而 `replaceAllText` 的行为则相反：若未指定 `tabsCriteria`，它会修改所有标签页，包括子标签页；即使在 `tabsCriteria` 中指定了父标签页，也不会包含其子标签页。
  
- **待处理的建议也存在于索引空间中。** `read_doc` 会以内联方式返回建议的插入和删除操作，这些操作以文本片段的形式出现，并带有 `suggestedInsertionIds` 或 `suggestedDeletionIds` 标识，且它们同样占据真实的索引位置。请勿将建议的删除视为实际文本，也不要向其中插入内容。
  
- **正文末尾的换行符不可删除。** 若要追加内容，请在最后一个元素的 `endIndex - 1` 处插入。

## 读取

有两种读取方式，各自服务于不同的目的。

- **Drive 的 `read_file_content`** 会以 Markdown 格式返回文档内容：标题、表格、加粗等，通常大小为几 KB。可先使用此接口了解文档的整体内容，并找到要锚定的文本位置。但请注意，该接口返回的内容并非索引空间：它会对 Markdown 特殊字符进行转义，并将待处理的建议与周围的文本合并在一起。切勿据此计算索引。
  
- **Docs 的 `read_doc`** 会返回完整的 `documents.get` JSON 数据：每个元素及其 `startIndex` 和 `endIndex`，所有样式信息、`revisionId` 以及标签页结构。当编辑操作需要精确索引时，请使用此接口。该接口返回的数据量较大：一篇包含一张表格的两页文档可能超过 100 KB。仅在确实需要评论时才设置 `commentsIncluded: true`。有时，连接器的读取结果即使设置了该参数也会显示 `COMMENTS_VIEW_MODE_OMITTED`，表明未返回评论；此时，请通过 Drive 的 `read_file_content` 并设置 `includeComments: true` 来获取评论，或者请用户提供需要处理的评论内容。
  
`read_doc` JSON 中内容的具体位置如下：

```
revisionId
tabs[].tabProperties.tabId
tabs[].documentTab.body.content[]          正文元素，按顺序排列
  .paragraph.elements[].textRun.content    文本内容，每个元素带有 startIndex 和 endIndex
  .paragraph.paragraphStyle.namedStyleType HEADING_1、NORMAL_TEXT 等样式类型
  .table.tableRows[].tableCells[].content[] 每个单元格包含自己的段落
tabs[].childTabs[]                          嵌套的子标签页，结构相同
```

如果文档中没有 `tabs` 键，则正文直接位于顶层：`body.content[]`。

### 使用辅助脚本来处理位置信息`scripts/docs_index.py`（位于该技能的文件夹中）会从文件中读取 `read_doc` JSON，并仅输出编辑所需的内容。在可以运行代码的地方，请使用脚本处理，而不是手动逐个检查 JSON。索引错误往往就出在手动遍历 JSON 的过程中。

- 如果 `read_doc` 的结果较大，可将其保存到文件中，然后将文件路径作为输入运行脚本。
- 如果 JSON 是在上下文中返回的且文档较小，可直接从中读取位置信息。
- 如果读取被截断且未保存任何内容，则不要猜测位置。当查找文本仅匹配您要更改的文本时（可通过添加相邻词来确保匹配），可使用 `replaceAllText`，它不需要指定位置；否则，请告知用户文档过大，无法按位置进行编辑。

命令：

```
python <skill>/scripts/docs_index.py outline DOC.json
    每行对应一个元素：索引范围、样式、表格单元格位置、文本。
    待定建议以 [+inserted] / [-deleted] 标示。
    最后输出用于追加的正文结束索引。
python <skill>/scripts/docs_index.py find DOC.json "exact text"
    输出同一段落内每次匹配的索引范围、是否为粗体，以及是否处于待定建议中。匹配不能跨越非文本元素，如芯片、图片或脚注标记。
python <skill>/scripts/docs_index.py fill-table DOC.json --table N --data rows.json [--bold-header]
    用于填充空表格 N 的完整 update_doc 参数（requests + writeControl），其中 TABLE #N 是由 outline 打印出的表格编号（每个标签页及嵌套表格均计入）。
python <skill>/scripts/docs_index.py new-table --at I --data rows.json --revision REV [--tab T] [--bold-header]
    用于在 I 处插入表格的完整 update_doc 参数，I 为该表格前一段落的 endIndex - 1，并在同一调用中完成填充。无需提供 DOC.json。
```

outline 和 find 会输出 `revisionId` 和标签页 ID；fill-table 会在其 `writeControl` 中包含 `revisionId`。

## 编辑配方

每个配方对应一次 `update_doc` 调用。当文档包含多个标签页时，需在所有 `location` 和 `range` 中添加 `tabId`；凡使用索引的调用，还需添加 `writeControl: {"requiredRevisionId": ...}`。插入文本中应使用实际换行符，而非转义的 `\n`。

**更改某个单词或短语。** `replaceAllText` 无需读取文档，也无需索引：

```json
{"replaceAllText": {"containsText": {"text": "Q3 launch", "matchCase": true},
  "replaceText": "Q4 launch", "tabsCriteria": {"tabIds": ["t.0"]}}}
```

响应中会报告 `occurrencesChanged`。若为零，说明文本未完全匹配：请与 `read_file_content` 对照，但请注意文件会对诸如 `&` 和 `*` 等字符进行转义。替换后的文本会继承首个被替换字符的样式，因此替换一段以粗体开头的文本会使整个替换部分变为粗体。若此影响不可接受，可在未设置样式的字符处开始查找，或在完成后用 `find` 进行校验。该操作会更改所覆盖标签页内的所有匹配项（除非 `tabsCriteria` 明确指定了某些标签页），因此适用于需要全部更改的情况，例如用户希望全文统一修改的日期或姓名。若只需更改单个匹配项，或查找文本较短且可能出现在无关文本中（如单独的数字“7”或常用词），则应在 `find` 返回的范围内执行删除和插入操作。切勿将段落末尾的换行符纳入查找文本：被替换的段落可能会继承下一段落的样式（正文段落变成标题），或下一段落可能失去标题样式。

**重写一段落。** 从 `outline` 中获取其 `startIndex` 和 `endIndex`。先删除 `[start, end - 1]`，保留段落的换行符和样式，再在 `start` 处插入新内容：

```json
[{"deleteContentRange": {"range": {"startIndex": 120, "endIndex": 184}}},
 {"insertText": {"location": {"index": 120}, "text": "新的段落内容。"}}]
```

在处理多个段落时，应优先处理编号最高的那个。当段落中仅部分文字发生变化时，只需在 `find` 返回的范围内删除并插入这些文字，而无需替换整个段落。这样，段落中其他位置的脚注标记、内嵌元素或图片将保持不变；在修订模式下，修订内容也只会显示发生变化的文字。若要删除整个段落，请删除 `[start, end]` 所表示的范围。但在三种情况下该范围会被拒绝，提示为“无效的删除范围”或“范围不能包含段落末尾的换行符”；此时请改用以下范围：对于文档的最后一段，从上一段的 `endIndex - 1` 到本段的 `endIndex - 1` 进行删除；对于紧邻表格之前的段落，以及表格单元格中唯一的段落，仅删除文本内容，即使用 `[start, end - 1]`；空段落会保留，因为 Google 会在每个表格前和每个单元格内保留一个空段落。

**在末尾追加内容。** 在正文末尾索引减 1 的位置插入 `outline` 输出的内容。文本开头需添加一个换行符，以开始一个新的段落。新段落将沿用与其拆分自的段落相同的样式，因此在标题之后，应通过 `updateParagraphStyle` 将其设置为 `NORMAL_TEXT`。

**插入带有样式的全新段落。** 先插入文本，然后根据插入点和文本长度（以 UTF-16 单位计）计算样式范围并应用样式。标题可使用 `updateParagraphStyle`，将 `namedStyleType` 设置为 `HEADING_1` 至 `HEADING_6`、`TITLE` 或 `NORMAL_TEXT`，并指定字段 `fields: "namedStyleType"`。列表则可在相应范围内调用 `createParagraphBullets`，并指定项目符号预设，如 `BULLET_DISC_CIRCLE_SQUARE` 或 `NUMBERED_DECIMAL_ALPHA_ROMAN`。如果直接输入 `- ` 或 `1. `，系统会将其识别为普通文本而非列表；若对已输入的标记调用 `createParagraphBullets`，这些标记仍会作为文本保留，因此需先将其删除。对于嵌套列表，在每层嵌套的行首、第一个 `createParagraphBullets` 之前各添加一个制表符，它会将制表符转换为层级并将其移除，从而导致后续所有索引值增加相应的数量。若在列表后直接插入一个段落并使用相同的项目符号预设，则该段落将被添加到该列表中。插入的文本会继承其前文的样式，或在段落开头时继承该段落首个字符的样式，因此在新增正文时应通过 `updateTextStyle` 重置粗体和斜体（字段 `fields: "bold,italic"`，`textStyle` 留空）。标题则无需重置，否则会取消其粗体效果。

**添加带内容的表格。** 一次调用即可完成，无需二次读取。将表格置于某个段落后，位置为该段落的 `endIndex - 1`：若表格位于标题下方，则应放置在该节的最后一段，或若该节为空，则放置在标题本身之后。切勿使用标题的起始位置，否则会在表格上方留下一个空标题，表格单元格中会出现标题的字体，并且使用 `new-table` 时，标题本身还会被转换为正文。将各行数据写入 JSON 文件，然后运行：

```
python <skill>/scripts/docs_index.py new-table --at <endIndex - 1> --data rows.json --revision <revisionId> [--tab <tabId>] [--bold-header]
```

将该命令的输出作为单次 `update_doc` 调用中的 `requests` 和 `writeControl` 参数。它会插入表格、填充单元格、通过 `--bold-header` 加粗表头行，并将 Google 在表格后自动添加的空段落设置为 `NORMAL_TEXT`（否则，在标题之后，该段落会变成一个空标题）。当文档包含多个标签页时，务必传递 `--tab` 参数；否则所有请求都会发送到第一个标签页。该命令仅需索引、修订 ID 和标签页 ID，即使结果以聊天形式返回而非文件，也可通过 `read_doc` 获取这些信息。

若不使用脚本，可将相同请求合并为一批操作：`insertTable` 在索引 `i` 处插入的表格，其起始位置为 `i + 1`；在一个 R 行 C 列的表格中，第 (r, c) 个单元格的文本位于 `i + 4 + r × (2C + 1) + 2c`，而表格后的空段落在未插入任何文本之前位于 `i + 3 + R × (2C + 1)`，因此应在 `insertTable` 之后立即插入对该空段落的 `NORMAL_TEXT` 样式重置。填写时应从最后一个单元格开始，逐个向前填充，这样每次插入仅会影响已填充的单元格。要填充一个已存在的表格，单元格的文本应插入到其第一个段落的 `startIndex` 处，即单元格自身的 `startIndex + 1`；Google 会拒绝在单元格的 `startIndex` 处执行插入操作（“插入索引必须位于现有段落的边界内”）。通过保存的读取操作，`fill-table` 构建这些请求，并假定单元格是空的。

**更改表格结构。** `insertTableRow`、`deleteTableRow`、`insertTableColumn` 和 `deleteTableColumn` 接受 `tableCellLocation: {"tableStartLocation": {"index": <表格起始索引>}, "rowIndex": r, "columnIndex": c}`。`updateTableCellStyle` 根据相同的定位信息以及 `rowSpan` 和 `columnSpan` 构建的 `tableRange` 来设置单元格背景。颜色使用 0 到 1 的 `rgbColor` 值。在加粗的标题行下方插入的新行也会显示为加粗，而新增列则会复制相邻列的宽度和背景。要删除整个表格，请精确删除 `[表格起始索引, 表格结束索引]`。

**建议而非编辑。** 在 `writeControl` 中添加 `"writeMode": "SUGGEST"`，同样的请求将以跟踪建议的形式呈现，文档的所有者可以接受或拒绝这些建议。当用户要求提供建议、标记修订或进行审阅时，或者当文档属于他人且用户希望提出建议而非直接修改时，可使用此模式。您无法通过 API 接受或拒绝建议，因此请告知用户相关变更正在文档中等待处理。在告知用户之前，请再次使用 `read_doc` 读取文档并运行 `outline`：插入和删除的文本应显示为 `[+...]` 或 `[-...]`（大纲不会显示建议的格式更改）。如果新文本显示为普通文本，或删除的文本未显示为 `[-...]` 而是完全消失，则说明该更改是直接应用的，请明确告知用户，并且不要将其视为建议。建议的删除操作会在索引空间中保留，直到有人解决为止；详情参见“文档的地址机制”。连接器目前对此模式的响应为“不支持的 WriteControl 模式”。如果确实如此，请勿在此处进行任何直接编辑：告知用户建议功能不可用，并可在回复中列出拟议的更改，或直接进行编辑。

```json
{"documentId": "...", "requests": [...],
 "writeControl": {"writeMode": "SUGGEST", "requiredRevisionId": "..."}}
```

**标签页。** 使用 `addDocumentTab` 并指定 `tabProperties.title` 可创建一个标签页，返回结果中包含该标签页的 `tabId`。`updateDocumentTabProperties` 可用于重命名标签页（字段为 `"title"`），而 `deleteTab` 则可删除标签页及其子标签页，但不能删除唯一的标签页。设置 `tabProperties.parentTabId` 可创建子标签页；标签页最多支持三层嵌套。新建标签页初始包含一个空段落，因此其首个插入索引为 1。

## 验证

- 对于内容，请使用 Drive 的 `read_file_content` 读取文档，并检查您所修改的文本。
- 对于位置和样式，请使用 `read_doc` 读取文档，并对结果运行 `outline` 或 `find`。`find` 可以显示被替换的文本是否继承了加粗格式，以及匹配项是否处于待处理的建议状态。
- 对于版面布局，在可以运行代码的情况下，可通过 Drive 的 `download_file_content` 导出文档，并指定 `exportMimeType: "application/pdf"`，然后运行 `python <skill>/scripts/render_export.py <已保存的导出文件> <输出目录>`，将生成的页面图像与上文“检查结果”部分中的列表进行比对。如果导出结果直接返回到聊天界面而非保存为文件，请跳过渲染步骤，不要将其复制到文件中。如果您无法运行代码、跳过了渲染步骤或渲染失败，请依赖上述两项验证，并告知用户您无法直观地检查版面布局。

|---|---|---|
| `read_doc` 结果过大或被截断 | 长文档或表格较多的文档的完整 JSON 内容 | 使用 Drive 的 `read_file_content` 方法获取内容。当查找文本仅匹配您要更改的文本时，使用 `replaceAllText`（可在查找文本中加入邻近词以确保唯一性）。如果结果已保存为文件，请对其运行 `docs_index.py`。 |

| `replaceAllText` 报告未找到任何匹配项 | 查找文本是从 `read_file_content` 中复制的，其中对 `&`、`*` 等字符进行了转义，或拼接了建议内容 | 使用原始文本，或通过 `docs_index.py find` 进行检查。 |

| 编辑应用到了错误的位置 | 请求按索引从低到高执行，或使用了较早写入前的索引 | 将请求按索引从高到低排序，并在每次写入后重新读取。 |
