# 将设计系统同步至 claude.ai/design

## 本技能的用途

**Claude Design**（claude.ai/design）是 Claude 的设计工具：用户向设计代理发出指令，它会构建可运行的 UI——屏幕、流程、原型——并以真实的 React 代码在浏览器中实时渲染。开箱即用时，它使用通用组件进行设计。本技能改变了这一点：它将用户的设计系统仓库转换为 Claude Design 所需的格式并上传，从此以后，**设计代理将使用客户的真实组件进行构建**——它生成的每个设计都符合品牌规范，由客户的实际组件构成，并且与工程师可以直接交付的代码一一对应。

这一框架应指导本技能中的每一个判断决策，因为每个上传的工件都会成为该代理（或操控它的人员）的输入：

| 上传的工件 | 消费方 | 用途 |
|---|---|---|
| `_ds_bundle.js` + `_vendor/` | 设计代理的运行时 | 其生成的每个设计都会从 `window.<globalName>.*` 中渲染这些已编译的真实组件 |
| `styles.css`、`fonts/`、`tokens/`、`_ds_bundle.css` | 每个渲染的设计 | 外观——包括从 `styles.css` 的 `@import` 闭包中可访问的所有 token、字体和组件样式（设计仅接收该闭包） |
| `<Name>.d.ts`（`<Name>Props`） | 设计代理 | 它所依据的 API 合同 |
| `<Name>.prompt.md` | 设计代理 | 使用参考——如何组合该组件，并附有示例 |
| `<Name>.html` 预览卡片 | 组件选择器中的人员 | 帮助他们查找组件并信任同步结果 |
| `_ds_sync.json` | 未来的同步 | 同步锚点——通过内容哈希值，让重新同步（无论在哪台机器上）都能跳过对未发生变化组件的重复验证，并精确计算出需要上传或删除的内容 |

这就是为什么保真度是整个过程的核心：如果某个组件在这里渲染错误，那么**设计代理用它构建的每个设计都会出现同样的错误**；而错误的 `.d.ts` 或误导性的 `.prompt.md` 会导致代理在任何地方误用该 API。子技能中的验证循环正是基于这一点而存在——它们并非繁文缛节。

转换器会根据仓库自身的 `dist/` 目录，确定性地生成上述所有内容。如果有 Storybook，预览将来自仓库的故事，并与其自身 Storybook 的渲染结果进行校验（作为本地参考保留，不会上传）。如果没有 Storybook，每个组件仍然能完整可用，而丰富的预览则根据用户选定的组件，以其自身的使用示例为基础编写，并按照绝对评分标准进行评估。**核心原则：交付客户已经构建的内容**——打包文件是客户已编译的 `dist/`，绝非重新实现。

您拥有一个名为 `DesignSync` 的工具，可以读取和写入用户的 claude.ai/design 项目。如果工具调用因授权错误而失败，请原封不动地将工具的提示转达给用户——工具的消息是环境感知的（在交互式终端中会显示 `/design-login`；在 claude.ai/code 等无头会话中，则会指向适用于该环境的路径），并在用户按提示操作后重试。

## 0. 首次同步？在开始任何工作前明确预期

一次完整的同步完成后，`.design-sync/config.json` 文件中始终会同时包含 `projectId` 和 `pkg`。如果两者都存在，则本次为重新同步——请跳过本节（第 2 节介绍如何保留先前状态）。（如果存在的是旧版配置文件 `design-sync.config.json`，请将其移动到新位置：`mkdir -p .design-sync && mv -n design-sync.config.json .design-sync/config.json`，提交此次移动，然后执行相同的检查。）如果配置文件缺失，或者仅存在未完成运行留下的部分配置，则视为首次同步：在开始任何其他操作之前，务必提前告知用户：

- 未找到已完成的同步——这是一次首次导入。
- 此技能会尝试对其设计系统进行**高保真**导入：默认情况下，这意味着需要反复构建并目视验证每个组件预览的质量，对于大型代码库，这一过程可能需要**长达数小时**。
- 用户可随时中断——在运行过程中发送消息以查看进度或调整方向都是允许的，且不会导致任何问题。
- 首次导入将进入一个**为此专门创建的新 Claude Design 项目**（§1）。所有需要用户确认的事项都发生在**初期**——包括创建该项目，以及对本次上传内容的一次性批准。此后，随着运行的推进，**已验证的组件会逐步出现在项目中**：用户可随时打开项目并观察其内容填充，且最终无需等待用户的额外确认。
- 运行过程中会记录配置和备注信息，因此后续同步将更快，并且大多为确定性操作。

（如果 §1 将本次运行引导至现有项目——例如用户重新采用某个项目，或因上一次运行被中止而遗留的 `projectId` 被固定——则上述部分规则不适用；请根据 §1 的指引相应调整预期。）

接下来，请确认用户是否希望继续——此过程可能会消耗大量 token（通过 `AskUserQuestion` 提问：是继续执行完整的高保真同步，还是先调整范围）。若用户此前已知晓所需时间和成本，请予以记录并直接继续，无需再次询问。

## 1. 选择目标项目

如果 `DesignSync` 尚未在您的工具列表中，请先通过 `ToolSearch(query: "select:DesignSync")` 加载它。目标项目的选取按以下优先级顺序进行：

- **已固定**：`.design-sync/config.json` 中存在 `projectId`——即为目标项目。调用 `DesignSync(get_project)` 确认该目标项目仍存在且类型为 `PROJECT_TYPE_DESIGN_SYSTEM`，同时告知用户正在同步至哪个项目；仅当项目不存在或用户提出变更时才重新询问。
- **全新——首次导入的默认选项**：无固定项目时——**创建新项目**。新建项目是本次运行完全拥有的唯一目标；正是这种所有权使得增量上传（§3）可以一次性获得批准。这也是为何此处不会提供现有项目的原因——若将首次导入的内容混入已有文件的项目中，使用该项目的人员将看到半成品的混合状态，且无法通过同步锚点区分哪些文件属于本次运行。使用 `DesignSync(list_projects)` 选择一个**不重复的名称**（重复名称会被拒绝并增加往返开销），并通过 `AskUserQuestion` 确认该名称，随后再调用 `DesignSync(create_project)`——该操作会弹出权限提示，未经确认的创建可能导致无人值守的会话停滞。若权限提示被拒绝，请停止并询问用户如何处理；切勿未经询问就重试，也绝不能在没有目标的情况下继续。一种特殊情况：若发现某项目显然是由本仓库先前被中止的运行遗留下来的（其名称与本技能拟议的相同——可通过 `list_files` 确认其确实为空，因为 `list_projects` 不显示文件数量），则可考虑将其复用，而非再次创建，或建议安全删除。
- **重新采用——仅在用户明确要求时**：用户指定一个现有项目（可通过名称或 UUID 指定；通常是在配置丢失后重新采用前一次同步所上传的项目）。调用 `DesignSync(get_project)`，检查其类型是否为 `PROJECT_TYPE_DESIGN_SYSTEM`，然后以通俗语言（避免使用技术术语）向用户警示：同步可能会覆盖或删除项目中原有的文件——例如：“请注意：同步到该现有项目意味着我可能会替换或移除其中已有的文件，使其与本仓库保持一致。如果其中有任何不属于本仓库的文件，可能会丢失——您希望我继续，还是改为创建一个新项目？”——仅在用户确认后方可继续。这是唯一一种在未固定项目的情况下，运行会进入现有项目的情形。**在结算时记录项目 ID。** 在目标被结算——无论是新建、复用还是重新采用——的那一刻，在任何上传操作之前，**将该目标的 `projectId` 记录到 `.design-sync/config.json` 中**。这是本技能唯一的记录规则：如果后续发生任何失败，已固定的配置都会保留下来，因此重试时会通过原子路径修复同一个项目，而不会创建重复项并使原项目成为孤立状态。（子技能的原子部分中上传后的记录步骤只是对该规则的兜底保障。）

**路由上传路径。** 如果某个 `projectId` 是在本次运行开始之前就已固定，则始终走**原子路径**（即子技能的上传部分），即使最终发现该项目为空也如此；在这种情况下批量重新上传并无问题，一条通用规则胜过无数特殊情况。否则，远程端将通过针对目标的无提示 `DesignSync(list_files)` 来决定：

- **空项目**（正常情况——本次运行刚刚创建）→ **增量路径**（§3）：先进行一次前置审批，随后在运行过程中逐步上传经验证的组件。
- **非空项目**（已重新采用的项目）→ **原子路径**：由于该项目可能正在使用中，因此会在运行结束时一次性更新，且所有内容均已通过验证。

路由仅决定**上传**路径。至于**验证**范围，则由锚点负责：若项目存在 `_ds_sync.json`，则重新同步驱动程序可跳过未变更的组件；若无锚点，则无论采用何种上传路径，所有内容均需重新验证。

## 2. 先探索，再写配置

工作流程是：**先探索仓库 → 写入 `.design-sync/config.json`（§1 中的固定操作已创建目录和文件——读取并追加内容，切勿删除 `projectId`；`mkdir -p .design-sync` 仍作为对遗留状态的安全保护措施）→ 从中以确定性方式运行转换器**。转换器的发现过程基于启发式算法；每种启发式都提供配置覆盖选项（在子技能阶段脚本就位后，可通过 `grep -r ASSUMPTION .ds-sync/*.mjs .ds-sync/lib/*.mjs` 查看）。因此，对于与默认设置不符的仓库，应通过修改配置来适配，而非直接改写代码。只有在万不得已时才编辑 `lib/*.mjs`（参见子技能的“逃生通道”部分：Storybook §5、Package §故障排除）。

**上传格式即为契约；转换器是通往该格式的确定性路径，但并非唯一路径。** 应用程序所消费的内容完全由输出布局规定：包括 `_ds_bundle.js` + `@ds-bundle` 头部、`styles.css`、`components/<group>/<Name>/{.html,.jsx,.d.ts,.prompt.md}`（其中第一行为 `@dsCard`）、`_preview/`、`_vendor/`、`fonts/`，以及 `_ds_sync.json`（详见子技能的布局与上传部分）。

即便布局偏离规范，只要可行，也应生成 `_ds_sync.json`。对于包的结构，`lib/sync-hashes.mjs` 提供了 `styleShaFor`、`renderHashFor` 和 `sourceKeyFor`；封装格式为：`{shape, styleSha, renderHashes, sourceKeys, keyRecipe, scriptsSha, sourceHashes, auxSha, bundleSha12}`（参见 `package-build.mjs` 中的侧车区块——`sourceHashes` 本身来自 `lib/bundle.mjs` 中的 `stampHeader`；`sourceKeys` 可省略，这仅意味着变更的工件需要重新验证）。Storybook 的结构配方需要一些离线生成器可能不具备的场景信息；此时省略侧车区块才是诚实的选择——下一次同步将没有锚点，所有内容都将重新验证，这也是正确的做法。

手工制作布局时容易忽略的一个不变量是：渲染后的设计仅接收 `styles.css` 的传递性 `@import` 闭包。任何真正的组件 CSS（如 `_ds_bundle.css`）都必须通过 `styles.css` 进行 `@import` 引入——直接链接该 CSS 的卡片并不能证明设计的有效性。

对于确实超出转换器适用范围的仓库（例如无法使用 esbuild 打包的构建或特殊工具链），可按仓库允许的方式生成布局。但准入门槛不会改变：`package-validate.mjs` 必须顺利通过校验，且每个故事在上传前都必须经过评分——Storybook 格式的必须有真实的截图对，Package 格式的则需按照绝对标准进行评判。离线生成是合法的，但离线验证则不被允许。**来自先前运行的状态。** 如果`.design-sync/config.json`或`.design-sync/NOTES.md`已经存在，请先读取它们并遵循其中的内容——这些文件保存了之前同步时的修正信息。**每当用户在运行过程中报告问题时**（例如某个路径、构建标志、需要跳过的组件或包管理器的特殊行为），请立即将其记录下来，以便下次同步时无需再次告知：与`cfg.*`字段对应的值写入`.design-sync/config.json`；其他内容则以项目符号形式添加到`.design-sync/NOTES.md`中。两者都会在最后提交（子技能会说明具体时机）。

1. **使用仓库自带的包管理器进行忠实安装。** 使用仓库中指定的 Node.js 版本（通过`.nvmrc`或`engines.node`确定），然后根据锁文件进行检测：`yarn.lock` -> `yarn install --immutable`；`pnpm-lock.yaml` -> `pnpm i --frozen-lockfile`；`bun.lockb`/`bun.lock` -> `bun install --frozen-lockfile`；`package-lock.json` -> `npm ci`。
2. **确定源代码的形态。** 如果`.design-sync/config.json`已存在且包含`"shape"`字段，则直接使用该字段。否则，使用`Glob`模式搜索`**/.storybook/main.*`和`**/storybook/main.*`（某些仓库会省略前导点；排除`node_modules`目录）——对于 monorepo 中的设计系统，配置通常位于某个子包中，因此切勿假设它位于仓库根目录：
   - 只要找到匹配项 -> `shape = 'storybook'`。匹配项的上上级目录即为要运行的包所在目录。如果找到多个 -> `AskUserQuestion`询问哪个是设计系统的配置目录；该目录将成为`storybookConfigDir`。**即使`.storybook`不在仓库根目录，也不要仅凭此就退而求其次选择`package`形态。**
   - 在目标目录中发现了`*.stories.*`文件但没有`.storybook/`目录 -> `AskUserQuestion`：“找到了故事文件但此处没有`.storybook/`目录——这个仓库的其他地方是否有 Storybook 配置（例如 monorepo 中的`apps/storybook/.storybook`）？”如果用户指出了某个路径 -> `shape = 'storybook'`，并将该路径记录为`storybookConfigDir`。如果用户回答没有 -> `shape = 'package'`。
   - 既没有`.storybook/`也没有`*.stories.*` -> `AskUserQuestion`询问是否根本存在 Storybook。如果用户指出了一个 Storybook 配置路径，则将其记录为`storybookConfigDir`，并设置`shape = 'storybook'`。如果不存在，则设置`shape = 'package'`。

随后，`Read` `<skill-base-dir>/storybook/SKILL.md`或`<skill-base-dir>/non-storybook/SKILL.md`，并按其指引继续操作（Storybook 相关的部分会回溯到 package 形态共用的部分）。在写入`.design-sync/config.json`时记录`"shape"`（以及设置了`storybookConfigDir`时也一并记录），这样下次同步时就可以跳过检测步骤。两种形态都会运行`<skill-base-dir>/package-build.mjs`作为转换入口，并运行`<skill-base-dir>/resync.mjs`作为单次同步的驱动程序（构建 -> 比较 -> 验证 -> 范围内捕获，最终生成一份结果 JSON）；共用的适配器位于`<skill-base-dir>/lib/`，而`<skill-base-dir>/storybook/`则存放 Storybook 专用的测试框架（`compare.mjs`用于预览与 Storybook 的比对；`probe.mjs`用于提供者推断的回退机制）。

## 3. 增量上传流程（首次同步至空项目）

在增量路径下（§1），用户只需在早期阶段批准一次上传，随后便可在运行过程中实时观察已验证的组件逐步出现在项目中，而无需等到最后才等待一次性批量上传。本节描述的是共享的执行机制；子技能会说明每一步的具体触发时机（其自身的构建与验证门控，标注为“增量路径”）。子技能上传部分的执行规则同样适用于此处的所有写入操作：每次调用`write_files`不超过 256 个文件，二进制文件较多的目录应分更小的批次处理，并遵守上传规范及本地保留清单。

### 在子技能的首次清洁构建门控处打开上传通道1. **先用通俗易懂的语言说明审批内容。** 在请求审批之前，向用户明确告知他们即将批准的内容，避免使用工具术语（如“计划”“glob”或工具方法名）：例如，“我将发起一次审批，涵盖本次运行所生成的所有内容上传至新项目，并清理后续重建过程中可能遗留的文件。此后您不会再收到提示；组件将在验证通过后逐步显示在项目中。” 审批对话框本身会展示一个结构化的路径列表；而这条说明则能让从未进行过同步操作的用户理解该对话框的意义。
2. 使用 `DesignSync(finalize_plan)` 并传入以下参数：`localDir: "./ds-bundle"`，`writes: ["components/**", "tokens/**", "fonts/**", "_vendor/**", "_preview/**", "guidelines/**", "_ds_bundle.js", "_ds_bundle.css", "styles.css", "README.md", "_ds_sync.json", "_ds_needs_recompile"]`，以及 `deletes: ["components/**", "tokens/**", "fonts/**", "_vendor/**", "_preview/**", "guidelines/**"]`。删除模式的存在使得运行结束时的清理无需额外提示——而且在此场景下，用户的同意几乎可以视为理所当然：项目初始为空，因此任何可删除的文件都是本次运行已上传的内容。返回的 `planId` 适用于整个运行过程（其生命周期为当前会话）。如果在运行中途因上下文重置而丢失，则需再次调用 `finalize_plan`，并获得一次新的审批，然后再继续上传任何内容。若整个会话终止，则不会从该流程中恢复：重试时会直接进入第1步，并以原子方式正确执行——这是预期行为，而非需要绕过的缺陷。
3. **如果审批被拒绝，应立即停止并询问用户——绝不能静默继续，也绝不能未经请求就重复提示。** 用通俗语言说明被拒绝的内容及其覆盖范围（“一次性批准将本次运行的输出上传至新项目”），然后提供以下选项：重新尝试审批、选择其他项目，或在本地完成构建与验证而不上传。仅限本地运行时，除不上传任何内容外，其余流程照常进行；运行结束报告会同时提供 `ds-bundle/` 路径和项目的 URL（`https://claude.ai/design/p/<projectId>`——密钥已记录，因此后续同步会找到该项目，而不会使其成为孤立状态）。若选择其他项目，则会按照第1步的要求重新确认，并由路由系统按常规处理，包括密钥在内：若目标项目非空，则采用原子化路径并放弃当前计划；若目标项目为空，则在此处获得新的审批后继续。

### 每次验证通过后即推送一批内容

在第一批组件通过子技能的完成标志之前，不会有任何内容上传。**首次推送将共享的基础文件与第一批组件一同上传**：包括 `_ds_bundle.js`、`_ds_bundle.css`、`styles.css`、`README.md`、`_vendor/**`、`tokens/**`、`fonts/**`、`guidelines/**`，以及该批次的 `components/<group>/<Name>/` 目录和 `_preview/<Name>.*` 文件。这些内容之所以一起传输，有两个原因：一是让用户在项目中看到的第一个内容是真实的组件，而不是一个声称已上传却为空的框架；二是到第一批组件上传时，这些共享文件已经证明了自己的价值，因为对这些组件的评分正是基于同一套资源包、CSS 和字体完成的。首次推送既是项目的第一批内容，也是规模最大的一次，因此采用了完整的防护机制：首先写入哨兵文件 `_ds_needs_recompile`（用于防止应用在半上传状态下误读清单或复制逻辑），随后写入实际文件，最后再重新写入哨兵文件（此路径上的每次推送都会通过重新写入哨兵来结束——这确保了下次打开项目时应用能够刷新视图）。此次推送还应醒目地输出项目 URL：`https://claude.ai/design/p/<projectId>`——这是项目首次具备可见内容的时刻。每个后续批次在通过“完成条”后，都会写入其 `components/<group>/<Name>/` 目录和 `_preview/<Name>.*` 文件，然后重新写入哨兵文件——这样，用户下次打开或刷新项目时，新卡片就会出现。报告批次进度时，请附上项目 URL，以便用户只需点击一下即可看到新增的卡片。如果自上次推送以来已执行了完整重建（例如全局配置修复已部署），则需再次推送共享的基础文件：该修复已在本地重写了 bundle/CSS/字体文件，若不重新推送，所有组件在验证时都将基于过时的远程版本进行渲染，直到收尾阶段才会更新。这些文件已在批准的计划中，并且是幂等的，因此重新推送不会带来额外成本。

后续的批次推送无需前置分隔符——它们都很短，且每次结束时都会重新设置哨兵，因此无分隔符的时间窗口可以忽略不计（上方的首次推送和下方的长收尾才是真正需要分隔符的部分）。此外，批次机制关注的是逐步可见性，而非正确性保障：最终收尾会确保达到最终状态，因此不必过分纠结于批次的组成——某个组件即使提前推送、随后又进行了修改，只需在最后再推送一次即可。

### 收尾——在子技能的最终关卡之后

1. **先写哨兵，再写完整内容。** 在执行任何其他操作之前，先重新写入 `_ds_needs_recompile` 文件——每当用户打开项目时，应用都会清除哨兵文件（而本流程会在运行过程中触发这一动作）；且收尾阶段是写入与删除操作持续时间最长的环节，因此在此处重新设置分隔符，可避免半应用状态被误用。随后，按计划逐块写入除 `_ds_sync.json` 之外的所有内容。重复上传未更改的文件是幂等且代价极低的操作；此步骤可覆盖批次遗漏的内容以及最终重建所变更的部分，从而确保无论批次如何执行，项目最终都与最后一次验证的构建完全一致。
2. **强制执行清理删除，而非条件判断。** 调用 `DesignSync(list_files)` 对项目进行同步，并删除 `components/`、`_preview/`、`tokens/`、`fonts/`、`_vendor/`、`guidelines/` 下所有最终 `ds-bundle/` 中未包含的远程路径（计划中的删除通配符已涵盖这些路径——无需额外提示）。之所以需要这一步骤：某个组件可能在早期批次中上传，但在后续流程中被移除、重命名或重新分组，而此类变化对后续的所有重新同步差异检测都是不可见的——基于锚点的差异检测仅能识别锚点记录的内容——因此，这是唯一能够清理这类残留的机会；若跳过此步骤，残留项将永久存在。同时，这些删除操作也会使该残留组件的卡片失效：应用会根据当前已上传的文件重新构建组件索引，因此一旦哨兵被重新设置（下一步）并打开项目，该卡片便会消失。
3. **重新设置哨兵，最后再写入 `_ds_sync.json`**，且必须单独调用 `write_files` 进行写入——规则与原子路径相同，原因也一致：锚点只能确认处于完全应用的状态，且它必须在删除操作之后执行，以防止因删除失败而导致锚点不再可见的远程文件残留。最后，输出项目 URL——`https://claude.ai/design/p/<projectId>`——并附上最终总结。

若在本流程的任何环节中途终止（用户停止运行或会话中断），项目将处于“未锚定”状态——这也是文档中明确的安全状态：下一次同步会重新验证并重新上传所有内容，不会有任何无声损坏的情况发生。如同子技能上传部分所述，任何重试后仍无法清除的写入或删除失败，都意味着必须立即停止——不得重新设置哨兵，也不得写入 `_ds_sync.json`。

## 撰写规范说明文档

您刚刚花费大量精力让这个设计系统的预览得以正常渲染——摸索出组件应如何封装、需要哪些提供者和主题配置、加载顺序有何讲究，以及哪些错误会导致输出无样式。这些知识若不在这里记录下来，一旦同步结束便会付诸东流，因为这份文档正是为特定的读者而准备的。**谁会读它。** 您编写的文件会被前置到生成的 README 中（通过 `readmeHeader` 配置项），并内嵌到“设计代理”的系统提示中——这个模型会基于该组件库为用户构建应用，且这些用户根本不会看到这份文件。它既不会生成 Storybook 预览，也不会运行该仓库的构建，更不会读取其源码；它只获取 README 和已绑定的产物，仅此而已。处于这种角色的代理会严格遵循明确、枚举化的指导，无法执行未明确给出的指示：如果命名了 token，它就会使用 token；若未对类名词汇进行命名，它就不会去猜测您的命名，而是自行创造一套新的。如果要求用 Provider 包裹，它就会包裹；如果不提，它通常也不会这样做。因此，每一句话都必须通过一个检验：*设计代理能否在不凭猜测的情况下据此行动？*（“遵循设计系统的约定”这一表述无法通过该检验——请删除它，并明确写出具体的约定。）

**该写些什么**——围绕四个核心关注点，以适合当前设计系统的方式组织：

- **包裹与初始化。** 如果组件需要通过 Provider 或根容器来应用样式（通常也是 token 和主题的承载处），请明确指出，并说明缺少它会导致什么问题，同时在一段精简的代码片段中展示如何包裹；此外，还需说明主题的配置方式、加载顺序，以及任何曾让您耗费调试时间的坑点。请根据读者的职责来筛选内容：它用于构建应用，而非预览——与特定工具相关的配置（如 Storybook 的特殊处理、脚手架）应放在 NOTES.md 中；而与组件实际使用相关的内容则放在这里。
  
- **样式规范及其真实词汇。** 传授本系统特有的样式模式，而非通用套路：对于实用类系统，提供一张紧凑的类名表，其中的名称直接来自样式源码（例如 Tailwind 预设会精确列出所有类名）；对于 props/主题系统，则说明“无需 CSS 类——通过 props 进行样式控制”，并列出承载设计语言的 props；对于 token 系统，则介绍 `var(--*)` 的使用方式及具体变量名。切勿引入设计系统中不存在的样式模式。

- **真实来源的位置。** 明确代理在应用样式前应读取的样式表或源文件（即它将持有的已绑定副本，如 `_ds/<folder>/styles.css` 及其导入文件），以及各组件的独立文档。直接读取真实文件的代理远胜于任何摘要——您的任务是确保它知道去哪里查找。

- **一段符合规范的构建示例。** 提供一个简短、真实的例子——使用库中的组件实现控件，并采用设计系统的样式模式来编写布局胶水代码。可选用您已验证过的某个预览作为模板：这是您确信能正确渲染的代码。

针对不同类型的系统，具体内容如下（仅供参考，非详尽清单）：  
Tailwind 预设的设计系统 → 类名表（`bg-surface-1`、`gap-md`、`text-body` 等）+ 根包裹；  
Grommet 风格的设计系统 → 无类名，使用 `pad`/`background`/`tone` 等 props + ThemeProvider；

**发布前务必验证。** 如果一份约定文件中列出了不存在的元素，那还不如没有——代理会完全信任这份文件，从而写出无法解析的样式词汇，并静默地输出未被样式的产物。提交前，请确保您列出的每个类名、token、prop 和组件都在最终构建产物中存在：在输出目录中，通过 grep 搜索编译后的样式表来核对类名和 token；在输出目录的 `components/<group>/<Name>/` 文件夹中检查已命名的组件（您刚刚运行的构建会为每个组件生成一个这样的文件夹——该目录结构就是同步时的名称索引；`.ds-build-meta.json` 只记录数量统计）；最后再检查打包后的代码文本（最具权威性——例如，像根包裹这样的 Provider 会直接打包进 bundle 而不单独对应组件目录）。如果上述任一环节未通过验证，要么修正名称，要么将其移除；若在源码中已记录但构建产物中缺失，则属于 NOTES.md 的范畴，而非 README 头部内容。**预算。** 请尽量简洁——2000至4000字符即可涵盖所有四个关注点，使用真实名称比模糊表述更好。如果触发了构建大小警告，请查看警告中指出的是哪一部分。如果是头部侧（仅头部就超过约31.9KB）：请缩短头部——它只有在自身不超过约32KB的限制时才能在内联截断中保留；一旦超出，其尾部会被裁剪，而主体部分将不再有任何贡献。如果是主体侧：您的约定是安全的（已前置且在限制范围内）；丢失的只是生成主体的末尾部分——通常是组件索引的尾部。您可以有意识地接受这种损失，或者缩小同步范围（包结构方面：排除`componentSrcMap`中的条目，使用更窄的`tokensGlob`；Storybook结构方面：同步更少的story）——没有针对主体部分的裁剪选项。
