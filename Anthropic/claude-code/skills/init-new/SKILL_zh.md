name: init
description: |-
  初始化新的 CLAUDE.md 文件（或文件）以及可选的技能/钩子，并附上代码库文档。
---
为该仓库设置一个最小化的 CLAUDE.md 文件（可选地还包括技能和钩子）。CLAUDE.md 会在每次 Claude 编码会话中被加载，因此必须保持简洁——只包含那些没有它时 Claude 可能会出错的内容。

## 第0阶段：检查是否存在现有的 CLAUDE.md

在提出任何问题之前，请先检查项目根目录下是否已存在 CLAUDE.md 文件（只需执行 `cat ./CLAUDE.md` —— 只计根目录下的文件；暂不遍历整个目录结构）。这将决定进入第1阶段的分支。

## 第1阶段：询问用户希望进行哪些设置

使用 AskUserQuestion 来了解用户的意图。具体提问内容取决于第0阶段的结果。调用 AskUserQuestion 时**仅使用问题Q1**——不要在同一调用中同时包含 Q2。只有在看到 Q1 的回答后才提出 Q2，因为如果用户选择“让 Claude 决定”，则会跳过 Q2。

在提出第一个问题之前，以普通助手文本的形式打印以下说明，以便首次使用的用户了解相关概念：

> 简要背景：
> - **CLAUDE.md** 文件为 Claude 提供针对某个项目、个人工作流程或组织的持久化指令。Claude 在每次会话开始时都会读取这些文件。
> - **技能**是预设的指令集合，当任务匹配时 Claude 会自动调用，或者您可以通过斜杠命令（如 `/frontend-design`、`/commit-push-pr`）来触发。
> - **钩子**允许您在生命周期事件上自动执行 Shell 命令：例如，在 Claude 等待您的输入时收到通知、编辑后自动格式化、提交前强制执行检查等——这些操作是确定性的，Claude 无法跳过。

**如果 CLAUDE.md 已经存在**，请询问：
- “我找到了一个现有的 CLAUDE.md。您希望如何处理？”
  选项： “审查并改进” | “保留现有文件，设置其他内容” | “全新创建（替换现有文件）”
  改进说明：“分析代码库的变化，并对现有文件提出有针对性的修改建议。”
  保留说明：“跳过 CLAUDE.md 设置，直接进入技能和钩子的配置。”
  全新创建说明：“废弃现有文件，重新编写新的文件。”
  路由：
  - “审查并改进” → 跳过 Q1/Q2；进入探索阶段（第2阶段），提出第3阶段的简化版问题，然后进入第4阶段的差异提案，最后到第8阶段。
  - “保留现有文件” → 跳过 Q1，直接询问 Q2（并将其中的第四个选项改为“都不设置——跳过所有配置”）。如果用户选择“都不设置——跳过所有配置”，则直接进入第8阶段，提示：“无需设置——您的 CLAUDE.md 未作更改。”否则，按以下流程：第2阶段 → 第3阶段提案（无补全访谈）→ 按队列依次执行第6、7阶段 → 第8阶段。对于第7阶段的钩子目标文件，默认视为“项目”级别（`.claude/settings.json`）。
  - “全新创建” → 继续执行下方的 Q1，如同不存在任何文件一样。

**如果不存在 CLAUDE.md 文件**（或用户选择了“全新创建”），请询问：
- Q1：“/init 应该设置哪些 CLAUDE.md 文件？”
  选项： “项目级 CLAUDE.md” | “个人级 CLAUDE.local.md” | “同时设置项目和个人两级” | “让 Claude 自行决定”
  项目级说明：“团队共享的指令，已纳入版本控制——架构规范、编码标准、常用工作流程。”
  个人级说明：“您在此项目中的私有偏好设置（被 .gitignore 忽略，不共享）——您的角色、沙盒 URL、首选测试数据、工作流程中的个性化习惯。”
  让 Claude 决定说明：“最快捷的方式——仅设置项目级 CLAUDE.md，并根据当前仓库情况推荐合适的技能或钩子。后续不再提问，所有内容将在写入前由您确认。”
  如果用户选择“让 Claude 决定”，则跳过 Q2——将其视为仅设置项目级 CLAUDE.md，且不限制技能或钩子的配置。

- Q2：“是否同时设置技能和钩子？”
  选项： “技能+钩子” | “仅设置技能” | “仅设置钩子” | “仅设置 CLAUDE.md，不涉及技能和钩子”
  技能说明：“预设的指令集合，当任务匹配时 Claude 会自动调用，或者您可以通过斜杠命令（如 `/frontend-design`、`/commit-push-pr`）来触发。”
  钩子说明：“在工具事件发生时自动执行的确定性 Shell 命令（例如，每次编辑后自动格式化）。Claude 无法跳过这些操作。”
  Q2 是一种提示而非过滤条件——第3阶段会根据代码库情况提出建议，并记录任何偏离。

## 第2阶段：探索代码库启动一个子代理来调研代码库，并让它读取关键文件以理解项目：清单文件（package.json、Cargo.toml、pyproject.toml、go.mod、pom.xml 等）、README、Makefile/构建配置、CI 配置、现有的 CLAUDE.md、.claude/rules/、AGENTS.md、.cursor/rules 或 .cursorrules、.github/copilot-instructions.md、.devin/rules/ 或 .windsurf/rules/ 或 .windsurfrules、.clinerules、.mcp.json。

同时让子代理执行一次低成本的存在性检查（不是读取内容——内容由导入适配器处理）：
- OpenAI Codex 配置：~/.codex/config.toml 或 ./.codex/
- Gemini CLI 配置：~/.gemini/settings.json、./.gemini/，或项目根目录下的 GEMINI.md

记录这些文件是否存在——第 8 阶段会用到它们。

检测：
- 构建、测试和 lint 命令（尤其是非标准命令）
- 使用的语言、框架和包管理器
- 项目结构（带有工作区的 monorepo、多模块项目，还是单体项目）
- 与语言默认不同的代码风格规则
- 不明显的陷阱、必需的环境变量或工作流中的特殊之处
- 现有的 .claude/skills/ 和 .claude/rules/ 目录
- 格式化工具配置（prettier、biome、ruff、black、gofmt、rustfmt，或统一的格式化脚本，如 `npm run format` / `make fmt`）
- Git 工作树的使用情况：运行 `git worktree list` 检查该仓库是否有多个工作树（仅在用户希望创建个人 CLAUDE.local.md 时相关）

记录哪些内容仅凭代码无法确定——这些将成为后续的提问点。

## 第 3 阶段：填补空白

使用 AskUserQuestion 收集撰写高质量 CLAUDE.md 文件及技能所需的信息。只询问代码本身无法解答的问题。

如果用户选择了“项目 CLAUDE.md”、“两者都选”或“让 Claude 决定”：请询问代码库的相关实践——不常见的命令、潜在陷阱、分支/PR 规范、必需的环境配置、测试方面的特殊之处。已包含在 README 中或从清单文件中显而易见的内容可略过。不要将任何选项标记为“推荐”——这里关注的是团队的实际运作方式，而非最佳实践。

如果用户选择了“个人 CLAUDE.local.md”或“两者都选”：请询问与用户自身相关的信息，而非代码库。同样不要将任何选项标记为“推荐”——这里关注的是用户的个人偏好，而非最佳实践。示例问题：
- 他们在团队中的角色是什么？（例如，“后端工程师”、“数据科学家”、“新员工入职培训”）
- 他们对这个代码库及其所用语言/框架的熟悉程度如何？（以便 Claude 能调整讲解的深度）
- 他们是否有个人沙盒 URL、测试账号、API 密钥路径，或需要 Claude 了解的本地配置细节？
- 仅当第 2 阶段发现存在多个 Git 工作树时：询问他们的工作树是嵌套在主仓库内（如 `.claude/worktrees/<name>/`），还是作为兄弟目录或外部目录（如 `../myrepo-feature/`）。如果是嵌套结构，向上遍历文件系统即可自动找到主仓库的 CLAUDE.local.md，无需特殊处理。如果是兄弟或外部结构，个人内容应存放在用户主目录下的文件中（如 `~/.claude/<project-name>-instructions.md`），每个工作树则只需一个导入该文件的一行 CLAUDE.local.md 占位文件：`@~/.claude/<project-name>-instructions.md`。切勿将此导入语句写入项目 CLAUDE.md——那样会将个人引用提交到团队共享的文件中。
- 有任何沟通偏好吗？（例如，“简洁明了”、“始终解释权衡”、“结尾不要总结”）

如果用户在第 0 阶段选择了“审核并改进”：只需提出一个问题——“自该 CLAUDE.md 编写以来，团队的工作方式是否发生了变化（新的规范、命令、陷阱）？”选项为“没有变化”或“有变化——请描述”。若选择“有变化”，请先询问具体变化内容（自由文本），然后再继续。之后直接进入第 4 阶段。

**根据第 2 阶段的发现和补缺回答，综合生成一份提案。** 对于每一项内容，根据现有证据选择合适的产物类型：

- **Hook** — 确定性、快速的逐次编辑 Shell 命令（格式化、对已更改文件进行静态检查）。
- **Skill** — 按需多步骤工作流（如 `/verify`、`/deploy-staging`，会话报告）。
- **CLAUDE.md 注释** — 引导行为但不强制执行的指南（如编码规范、沟通风格）。

将 Q1 所暗示的 CLAUDE.md 文件（项目级、个人级、两者兼有，或“让 Claude 决定”→ 项目级）作为提案的第一个或几个要点，并为每个文件附上一行摘要说明其内容。随后列出技能/钩子/注释。若选择“保留原样”路径，则省略 CLAUDE.md 文件相关的要点及注释（第 4 阶段不会执行）。若选择“全新开始”路径且 Q1 仅限个人级，则增加一条说明：现有项目级 CLAUDE.md 将保持不变（用户选择不替换为项目级文件）。

提出最合适的方案。若用户提供了 Q2 的提示，而您的方案与其不符（例如用户要求“仅使用钩子”，但当前不存在任何钩子相关的内容），请在提案顶部用一句话说明，并仍按更匹配的方案生成相应工件。

**以普通助手文本格式输出提案**，每项一个要点：

> 我建议如下设置：
> • **[工件类型：文件/钩子/技能/注释]** — [一句话描述]
> • …

随后调用 AskUserQuestion，提出一个简单问题（“这样是否合适？”），并提供选项，如“没问题——继续”、“去掉钩子”、“去掉技能”。请勿使用 `preview` 字段——提案已在滚动日志中可见。工具会自动添加“其他”选项，供用户自定义调整。

**根据被接受的提案构建优先级队列**。每个条目包含：{类型：钩子/技能/注释，描述，目标文件，以及来自第 2 阶段的详细信息，如实际的测试或格式化命令}。第 6 阶段和第 7 阶段的钩子子任务会消费该队列；第 4/5 阶段则直接依据获批提案中的文件相关要点进行判断；第 7 阶段的 GitHub CLI 和静态检查无论队列内容如何都会执行。

## 第 4 阶段：编写 CLAUDE.md（若获批提案包含此内容，或在“评审并改进”路径下）

在项目根目录下编写一份精简版 CLAUDE.md。每一行都必须通过以下检验：“如果删除这一行，Claude 是否会犯错？”若答案为否，则将其删除。

若用户在第 0 阶段选择了“评审并改进”，则无需重新编写，而是读取现有文件，对照第 2 阶段的发现及第 3 阶段的简化回答，针对每一处提出具体的增删建议，并附上一行理由。现有文件是基准，您的任务是找出遗漏、过时或冗余的内容。打印完差异后，再调用 AskUserQuestion（问题：“应用这些修改吗？”选项包括“全部应用”、“让我挑选”、“跳过——保持原样”），然后再进行任何写入操作。

**从第 3 阶段的优先级队列中提取目标为 CLAUDE.md 的注释条目**（团队级注释），并将每条以简洁的一行形式添加到最相关的章节中。这些是用户希望 Claude 遵循但无需强制执行的行为规范（如“实施前先提出方案”、“重构时说明权衡”）。针对个人的注释则留待第 5 阶段处理。

应包含：
- Claude 无法自行推断的构建/测试/格式化命令（非标准脚本、标志或序列）
- 与语言默认规则不同的代码风格规范（如“优先使用 type 而不是 interface”）
- 测试说明及特殊用法（如“运行单个测试：pytest -k 'test_name'”）
- 仓库协作规范（分支命名、PR 规范、提交风格）
- 必要的环境变量或初始化步骤
- 非显而易见的陷阱或架构决策
- 若存在，从现有 AI 编码工具配置中摘录的重要部分（AGENTS.md、.cursor/rules、.cursorrules、.github/copilot-instructions.md、.devin/rules/、.windsurf/rules/、.windsurfrules、.clinerules）

排除：
- 文件逐个罗列的结构或组件清单（Claude 可通过阅读代码库自行发现）
- Claude 已知的标准语言规范
- 通用性建议（如“编写整洁代码”、“妥善处理错误”）
- 详细的 API 文档或长篇参考——改用 `@path/to/import` 语法（例如 `@docs/api-reference.md`），按需内联内容，避免使 CLAUDE.md 过于臃肿
- 频繁变动的信息——使用 `@path/to/import` 引用源文件，确保 Claude 始终读取最新版本
- 长篇教程或操作指南——移至单独文件并以 `@path/to/import` 引用，或将其归入技能模块
- 从清单文件中显而易见的命令（如标准的 “npm test”、“cargo test”、“pytest”）

务必具体：写成“在 TypeScript 中使用 2 空格缩进”比笼统的“正确格式化代码”更好。

不要重复，也不要凭空添加诸如“常见开发任务”或“开发技巧”之类的章节——仅包含你在所读文件中明确找到的信息。

在文件开头添加以下前缀：

```
# CLAUDE.md

本文件为 Claude Code（claude.ai/code）在处理本仓库代码时提供指导。
```

对于涉及多个关注点的项目，建议将说明整理到 `.claude/rules/` 目录下，按主题拆分为独立文件（如 `code-style.md`、`testing.md`、`security.md`）。这些文件会与 CLAUDE.md 一同自动加载，并可通过 `paths` 前置元数据限定作用于特定文件路径。

对于具有明确子目录的项目（如 monorepo 或多模块项目）：请说明可为各模块添加专门的子目录 CLAUDE.md 文件（当 Claude 在相应目录工作时会自动加载）。如用户需要，可主动协助创建。

## 第五阶段：编写 CLAUDE.local.md（若获批方案包含此步骤）

在项目根目录下编写一份极简的 CLAUDE.local.md。该文件会与 CLAUDE.md 一同自动加载。创建后，请将 `CLAUDE.local.md` 添加到项目的 .gitignore 中，以保持其私密性。

**消费第三阶段偏好队列中目标为 CLAUDE.local.md 的 `note` 条目**（个人级别笔记）——每条作为一句简洁的内容加入。若用户在第一阶段已选择仅限个人使用，则这是 `note` 条目的唯一消费方。

应包含：
- 用户的角色及对代码库的熟悉程度（以便 Claude 调整解释的深度）
- 个人沙盒地址、测试账号或本地环境配置细节
- 个人的工作流程或沟通偏好

保持简短——仅添加那些能显著提升 Claude 对该用户响应质量的内容。

若第二阶段检测到多个 Git 工作树，且用户确认使用的是兄弟级或外部工作树（而非嵌套于主仓库内）：向上遍历文件系统将无法找到所有工作树共用的单一 CLAUDE.local.md。此时，应将实际的个人内容写入 `~/.claude/<project-name>-instructions.md`，并将 CLAUDE.local.md 设为仅含一行的占位文件，内容为：`@~/.claude/<project-name>-instructions.md`。用户可将此单行占位文件复制到每个兄弟级工作树。切勿将此导入语句放入项目根目录下的 CLAUDE.md。若工作树嵌套于主仓库内（如 `.claude/worktrees/`），则无需特殊处理——主仓库的 CLAUDE.local.md 会自动被找到。

若 CLAUDE.local.md 已存在：请先读取现有内容，提出具体的补充建议，切勿静默覆盖。

## 第六阶段：建议并创建技能（若获批方案包含相关部分）

技能可为 Claude 提供按需调用的能力，而不会使每次会话的上下文过于冗长。**首先，从第三阶段的偏好队列中消费 `skill` 条目。** 每个排队的技能偏好都会被转化为一份针对用户描述量身定制的 SKILL.md。对于每一条：
- 根据偏好命名（例如：“verify-deep”、“session-report”、“deploy-sandbox”）。
- 使用访谈中用户原话以及第二阶段获取的信息（测试命令、报告格式、部署目标）撰写技能主体内容。如果该偏好映射到某个已有的捆绑技能（如 `/verify`），则编写一个项目级技能，在此基础上叠加用户的特定约束——同时告知用户原有技能仍然存在，而新增技能是对其的补充。
- 如果偏好描述不够明确，提出简短的后续问题（如：“`verify-deep` 应该运行哪个测试命令？”）。

**然后，在发现以下情况时，建议额外的技能：**
- 针对特定任务的参考知识（子系统的约定、模式、风格指南）。
- 用户希望直接触发的可重复工作流（部署、修复问题、发布流程、变更验证）。

对于每项建议的技能，提供：名称、一句话用途，以及为何适合当前仓库。

如果 `.claude/skills/` 目录下已存在技能，请先进行审查。不要覆盖现有技能——仅提出与现有内容互补的新技能。

将每个技能创建在 `.claude/skills/<skill-name>/SKILL.md` 中：

```yaml
---
name: <skill-name>
description: <技能的功能及适用场景>
---

<给 Claude 的指令>
```

默认情况下，用户和 Claude 都可以调用这些技能。对于带有副作用的工作流（如 `/deploy`、`/fix-issue 123`），添加 `disable-model-invocation: true`，使只有用户能够触发，并使用 `$ARGUMENTS` 接收输入参数。

## 第七阶段：建议进一步优化

告知用户，现在 CLAUDE.md 和技能（如已选择）均已就位，接下来将建议几项额外的优化措施。

检查环境并针对发现的缺失逐一询问用户（通过 AskUserQuestion）：
