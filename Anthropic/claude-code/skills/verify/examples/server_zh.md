# 验证服务器/API变更

工具是 `curl`（或等效工具）。证据就是响应。

## 模式

1. 启动服务器（在后台运行，并进行就绪检查——见下文）
2. 使用能触发变更分支的输入，对变更涉及的路由发起 `curl` 请求
3. 捕获完整响应（状态码、头部和正文）
4. 与预期结果进行比对

## 生命周期

如果有运行脚本，则由该脚本负责处理。如果没有：

```bash
<启动命令> &> /tmp/server.log &
SERVER_PID=$!
for i in {1..30}; do curl -sf localhost:PORT/health >/dev/null && break; sleep 1; done
# ... 你的 curl 请求 ...
kill $SERVER_PID
```

没有就绪端点？就轮询你要测试的路由，直到不再返回“连接被拒绝”的错误，然后再加一个心跳检查。

## 示例

**变更内容：** 在 `rateLimit.ts` 中为 429 响应添加了 `Retry-After` 头。
**声明（PR 文本）：** “客户端现在可以正确地退避重试。”

**推论：** 触发限流后，响应头中应包含 `Retry-After: <n>`。之前则没有。

**计划：**
1. 启动服务器
2. 向受限流保护的端点发送足够多的请求，以触发 429 状态码
3. 检查 429 响应中是否包含 `Retry-After` 头
4. 检查其值是否为正整数

**执行：**
```bash
# 触发限流——10 次快速请求，根据变更，限流为每秒 5 次
for i in {1..10}; do curl -s -o /dev/null -w "%{http_code}\n" localhost:3000/api/thing; done
# -> 200 200 200 200 200 429 429 429 429 429

# 捕获 429 的响应头
curl -si localhost:3000/api/thing | head -20
# -> HTTP/1.1 429 Too Many Requests
# -> Retry-After: 12
# -> ...
```

**结论：** 通过——存在 `Retry-After: 12`，且值为正整数。

## 失败的情况

- 头部缺失——说明变更未生效，或者你实际上并未命中 429 路径（先检查状态码）
- 头部存在但值为 `NaN` / `undefined` / 负数——说明逻辑有误
- 全部都是 200 响应——说明你从未触发变更后的路径。请加大请求并发量，或检查限流配置。
