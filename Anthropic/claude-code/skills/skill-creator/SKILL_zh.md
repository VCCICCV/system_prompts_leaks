# 技能创建者

一个用于创建新技能并对其进行迭代改进的技能。

从高层次来看，创建技能的过程如下：

- 确定你希望该技能实现的功能以及大致的实现方式
- 撰写技能初稿
- 准备几个测试提示，并使用“具备技能访问权限的Claude”运行这些提示
- 帮助用户对结果进行定性和定量评估
  - 在后台运行的同时，如果没有现成的定量评估指标，可以先草拟一些；如果有，则可以直接使用或根据需要进行修改。然后向用户解释这些评估指标（如果已有指标，也请说明现有指标）。
  - 使用`eval-viewer/generate_review.py`脚本向用户展示结果供其查看，并同时提供定量指标供参考。
- 根据用户对结果的评价反馈（以及通过定量基准发现的明显缺陷），对技能进行改写
- 重复上述步骤，直至满意为止
- 扩展测试集，以更大规模再次验证

在使用此技能时，你的任务是判断用户当前处于流程的哪个阶段，然后协助其推进各环节。例如，如果用户说：“我想做一个用于X的技能”，你可以帮助明确其具体需求、撰写初稿、设计测试用例、确定评估方案、执行所有提示，并不断迭代优化。

另一方面，如果用户已经有一个技能初稿，那么你可以直接进入评估与迭代环节。

当然，你也应保持灵活性。如果用户表示：“我不需要做大量评估，只要和我聊聊就行”，那也可以按此方式进行。

在技能开发完成后（顺序仍可灵活调整），还可以运行专门用于优化技能触发机制的描述改进工具。

明白了吗？明白了。

## 与用户沟通

技能创建者可能会被各种背景的用户使用，其中不乏对编程术语不太熟悉的人。如果你还不知道的话——其实这股潮流才刚刚兴起——Claude的强大功能正激励着水管工打开终端、让父母和祖父母去搜索“如何安装npm”。不过，大多数用户应该还是具备一定计算机知识的。

因此，请务必留意上下文线索，以便调整你的表达方式！默认情况下，以下是一些参考建议：

- “evaluation”和“benchmark”这两个词勉强可用，但最好谨慎使用。
- 对于“JSON”和“assertion”这类术语，除非你确信用户已了解其含义，否则在使用前应加以解释。

如有疑问，不妨简要解释相关术语；若不确定用户是否理解，也可用简短定义来澄清。

## 创建技能

### 捕捉意图

首先，明确用户的意图。当前对话中可能已经包含用户希望捕获的工作流程（例如，用户提到“把这个变成一个技能”）。如果是这样，可先从对话历史中提取相关信息——使用的工具、步骤顺序、用户所做的修正、观察到的输入输出格式等。用户可能需要补充缺失的部分，并在进入下一步之前予以确认。

1. 这个技能应该让Claude实现什么功能？
2. 该技能应在何种情况下触发？（即用户会使用哪些语句或情境）
3. 预期的输出格式是什么？
4. 是否需要设置测试用例来验证技能的有效性？对于那些有客观可验证输出的技能（如文件转换、数据提取、代码生成、固定工作流程步骤），设置测试用例会很有帮助；而对于主观性强的技能（如写作风格、艺术创作），则通常无需测试用例。可根据技能类型提出合适的默认建议，但最终决定权在用户手中。

### 访谈与调研主动询问有关边缘情况、输入/输出格式、示例文件、成功标准以及依赖关系的问题。在这些问题都明确之前，不要急于编写测试提示。

检查可用的MCP——如果对研究有用（如查阅文档、寻找类似技能、查找最佳实践），则在有子代理的情况下并行开展研究，否则就直接在主流程中进行。提前准备好相关背景信息，以减轻用户的负担。

### 编写SKILL.md

根据用户访谈结果，填写以下内容：

- **name**：技能标识符
- **description**：何时触发、该技能的作用。这是主要的触发机制——既要说明技能的具体功能，也要明确其适用的具体场景。所有“使用时机”的信息都应放在这里，而不是放在正文部分。注意：目前Claude有时会“触发不足”，即在应该使用技能时反而没有调用。为避免这种情况，请让技能描述稍微“强势”一些。例如，与其写成“如何构建一个简单快速的仪表板来展示Anthropic内部数据”，不如写成“如何构建一个简单快速的仪表板来展示Anthropic内部数据。每当用户提到仪表板、数据可视化、内部指标，或希望展示任何类型的公司数据时，即使他们并未明确要求‘仪表板’，也请务必使用此技能。”
- **compatibility**：所需工具及依赖项（可选，通常很少需要）
- **技能的其余部分 :)**

### 技能编写指南

#### 技能的结构

```
skill-name/
├── SKILL.md（必填）
│   ├── YAML 前置元数据（name 和 description 为必填）
│   └── Markdown 指令
└── 捆绑资源（可选）
    ├── scripts/ - 用于确定性或重复性任务的可执行代码
    ├── references/ - 根据需要加载到上下文中的文档
    └── assets/ - 输出中使用的文件（模板、图标、字体）
```

#### 渐进式披露

技能采用三级加载机制：
1. **元数据**（名称 + 描述）——始终在上下文中（约100字）
2. **SKILL.md 正文**——技能触发时始终在上下文中（理想情况下不超过500行）
3. **捆绑资源**——按需加载（数量不限，脚本无需加载即可执行）

以上字数仅为参考，如有需要可以适当延长。

**关键模式：**
- 尽量将 SKILL.md 控制在 500 行以内；若接近此上限，可增加一层层级结构，并清晰指引模型在后续步骤中应前往何处继续操作。
- 在 SKILL.md 中明确引用相关文件，并说明何时阅读这些文件。
- 对于较大的参考文件（超过300行），请添加目录。

**领域组织方式**：当一项技能支持多个领域或框架时，可按变体进行组织：
```
cloud-deploy/
├── SKILL.md（工作流与选择）
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只会读取相关的参考文件。

#### 避免意外原则

这一点不言自明，但技能内容绝不能包含恶意软件、漏洞利用代码或其他可能危害系统安全的内容。技能的内容在描述意图时不应让用户感到意外。对于那些旨在制造误导、协助未经授权访问、数据外泄或其他恶意行为的请求，请坚决拒绝。不过，“扮演某角色XYZ”之类的技能则是允许的。

#### 编写模式

建议在指令中多使用祈使句形式。

**定义输出格式**——可以这样写：
```markdown
## 报告结构
始终使用以下模板：
# [标题]
## 执行摘要
## 主要发现
## 建议
```

**示例模式**——加入示例非常有用。您可以按如下格式编写（但如果示例中已包含“输入”和“输出”，也可稍作调整）：
```markdown
## 提交信息格式
**示例1：**
输入：添加了基于 JWT 的用户认证
输出：feat(auth)：实现基于 JWT 的认证
```

### 写作风格

尝试向模型解释事情的重要性，而不是使用生硬、刻板的“必须”指令。运用心智理论，尽量让技能具有通用性，而非局限于特定的狭隘示例。先写一个初稿，然后以全新的视角审视并加以改进。

### 测试用例

在完成技能初稿后，设计2-3个贴近实际的测试提示——即真实用户可能会提出的问题。与用户分享这些测试用例：“我想试试这几个测试案例，你看这样合适吗？或者你希望再补充一些？”随后执行这些测试。

将测试用例保存至 `evals/evals.json` 文件中。目前暂不编写断言，只需记录提示内容。断言将在下一步运行期间同步编写。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "用户的任务提示",
      "expected_output": "预期结果描述",
      "files": []
    }
  ]
}
```

完整 schema（包括后续会添加的 `assertions` 字段）请参阅 `references/schemas.md`。

## 执行并评估测试用例

本节为连续流程，请勿中途停止。切勿使用 `/skill-test` 或其他任何测试技能。

将结果存放在 `<skill-name>-workspace/` 目录下，该目录应与技能目录并列。在工作空间内，按迭代编号组织子目录（如 `iteration-1/`、`iteration-2/` 等），每个测试用例再单独建一个目录（如 `eval-0/`、`eval-1/` 等）。无需提前创建所有目录，可随用随建。

### 第一步：在同一回合同时启动带技能和基准版本的运行

针对每个测试用例，在同一回合启动两个子代理：一个启用技能，另一个不启用技能。这一点很重要——不要先启动带技能的运行，之后再补跑基准版本。务必一次性全部启动，使所有运行大致同时结束。

**带技能的运行：**

```
执行以下任务：
- 技能路径：<path-to-skill>
- 任务： <eval prompt>
- 输入文件： <如有 eval 文件则列出，否则填写“none”>
- 输出保存路径： <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- 需要保存的输出： <用户关心的内容，例如“.docx 文件”、“最终 CSV”>
```

**基准运行**（提示相同，但基准版本视具体情况而定）：
- **新建技能时**：完全不使用技能，提示不变，不指定技能路径，输出保存至 `without_skill/outputs/`。
- **改进现有技能时**：使用旧版本。编辑前先对技能进行快照（`cp -r <skill-path> <workspace>/skill-snapshot/`），然后让基准子代理指向该快照，输出保存至 `old_skill/outputs/`。

为每个测试用例编写一份 `eval_metadata.json` 文件（断言字段暂时留空）。根据测试内容为每个评估取一个有描述性的名称，而不要简单命名为“eval-0”。该名称也应用于对应的目录。如果本次迭代使用了新的或修改过的评估提示，则需为每个新评估目录创建这些文件，不要假定它们会从前一次迭代沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "用户的任务提示",
  "assertions": []
}
```

### 第二步：在运行进行中编写断言

不要只是等待运行结束，可以利用这段时间高效推进。为每个测试用例起草定量断言，并向用户说明其含义。若 `evals/evals.json` 中已有断言，请复核并解释其检验内容。

优秀的断言应具备客观可验证性，并配有清晰的描述性名称，以便在基准评测查看器中一目了然地了解每项断言的具体检查内容。对于主观性强的指标（如写作风格、设计质量），更适合采用定性评估，不要强行套用断言来衡量需要人工判断的内容。

断言起草完成后，更新 `eval_metadata.json` 文件及 `evals/evals.json`，并向用户说明在评测查看器中将看到哪些内容——既包括定性输出，也包括定量基准数据。

### 第三步：随着运行完成，记录计时数据当每个子代理任务完成时，您会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。请立即将这些数据保存到运行目录下的 `timing.json` 文件中：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它们通过任务通知传递，并不会在其他地方持久化。请在每条通知到达时立即处理，不要试图批量处理。

### 第4步：评分、汇总并启动查看器

所有运行完成后：

1. **对每次运行进行评分**——启动一个评分子代理（或直接内联评分），读取 `agents/grader.md` 并根据输出评估每个断言。将结果保存到各运行目录下的 `grading.json` 文件中。`grading.json` 中的 expectations 数组必须使用 `text`、`passed` 和 `evidence` 这三个字段（不能使用 `name`/`met`/`details` 或其他变体）——查看器依赖于这些确切的字段名。对于可以程序化检查的断言，请编写并运行脚本，而不是手动目测——脚本更快速、更可靠，且可在不同迭代间重复使用。

2. **汇总为基准测试**——从 skill-creator 目录运行汇总脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   这将生成 `benchmark.json` 和 `benchmark.md`，其中包含每种配置的通过率、耗时和 token 使用量，以及均值±标准差和差异值。如果手动生成 `benchmark.json`，请参阅 `references/schemas.md`，了解查看器所期望的确切 schema。

   将每个带有技能的版本置于其基线版本之前。

3. **进行分析师复核**——阅读基准测试数据，揭示汇总统计可能掩盖的模式。请参阅 `agents/analyzer.md` 中的“分析基准测试结果”部分，了解需要关注的内容，例如无论是否使用技能都始终通过的断言（无区分度）、方差较大的评测（可能不稳定），以及时间与 token 使用之间的权衡。

4. **启动查看器**，同时展示定性输出和定量数据：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   对于第2次及以后的迭代，还需添加 `--previous-workspace <workspace>/iteration-<N-1>` 参数。

   **协作环境/无头环境**：如果 `webbrowser.open()` 不可用，或环境没有显示设备，请使用 `--static <output_path>` 选项，生成一个独立的 HTML 文件，而不是启动服务器。用户点击“提交所有评价”后，反馈将以 `feedback.json` 文件的形式下载。下载后，请将 `feedback.json` 复制到工作区目录，以便下一次迭代使用。

   注意：请使用 `generate_review.py` 创建查看器，无需编写自定义 HTML。

5. **告知用户**类似以下内容：“我已经在您的浏览器中打开了结果。有两个标签页——‘输出’允许您逐个查看每个测试用例并留下反馈，‘基准’则展示了定量比较。完成后，请回到这里告诉我。”

### 用户在查看器中看到的内容

“输出”标签页每次显示一个测试用例：
- **提示**：给出的任务
- **输出**：技能生成的文件，尽可能以内联方式呈现
- **上一次输出**（第2次及以后的迭代）：折叠区域，显示上一次迭代的输出
- **正式评分**（如果已执行评分）：折叠区域，显示断言的通过/未通过情况
- **反馈**：一个文本框，输入时自动保存
- **上一次反馈**（第2次及以后的迭代）：上次的评论，显示在文本框下方

“基准”标签页显示统计摘要：每种配置的通过率、耗时和 token 使用量，以及每次评测的细分数据和分析师观察。

可通过前后按钮或方向键进行导航。完成后，用户点击“提交所有评价”，所有反馈将被保存到 `feedback.json` 文件中。

### 第5步：读取反馈当用户告知已完成时，请读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "图表缺少坐标轴标签", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "完美，很喜欢", "timestamp": "..."}
  ],
  "status": "complete"
}
```

反馈为空表示用户认为结果没有问题。请重点改进那些用户提出具体意见的测试用例。

使用完毕后，请关闭查看器服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是整个迭代循环的核心环节。您已经运行了测试用例，用户也已审阅了结果，现在需要根据他们的反馈进一步优化技能。

### 如何思考改进方向

1. **从反馈中提炼共性。** 从根本上说，我们的目标是打造能够被千万次（甚至更多）应用于各种不同提示的技能。目前，为了加快进度，您和用户只针对少数几个示例反复迭代。用户对这些示例非常熟悉，因此能快速评估新的输出。但如果你们共同开发的技能仅适用于这几个示例，那就毫无价值。与其做繁琐而过度的调整，或施加过于严苛的限制，不如尝试拓展思路，采用不同的表达方式，或者推荐不同的工作模式。这样试错的成本相对较低，说不定还能找到更好的方案。

2. **保持提示简洁。** 去掉那些作用不大的内容。不仅要关注最终输出，还要仔细阅读对话记录——如果发现技能让模型在无意义的事情上浪费了大量时间，可以尝试移除导致这种情况的部分，并观察效果。

3. **阐明背后的理由。** 努力解释清楚您要求模型执行每一步操作的**原因**。如今的大型语言模型非常“聪明”，它们具备良好的心智理论，在得到恰当引导时，能够超越简单的指令，真正实现预期目标。即使用户的反馈简短或带有不满情绪，也要设法理解任务本身、用户为何如此撰写，以及他们实际写下了什么，然后将这种理解融入到指令中。如果您发现自己频繁使用大写的“总是”或“绝不”，或者采用过于僵化的结构，这就要引起注意了——尽可能重新表述并说明理由，让模型明白您所要求的内容为何重要。这是一种更人性化、更强大且更有效的方法。

4. **寻找各测试用例中的重复工作。** 阅读测试运行的对话记录，留意子代理是否都独立地编写了类似的辅助脚本，或者对同一问题采取了相同的多步处理流程。如果三个测试用例的子代理都生成了 `create_docx.py` 或 `build_chart.py`，这就强烈表明该技能应该将这些脚本整合起来。只需编写一次，将其放入 `scripts/` 目录，然后让技能调用即可。这样可以避免每次调用时都重复造轮子。

这项工作非常重要（我们正致力于每年创造数十亿美元的经济价值！），思考的时间不应成为瓶颈；请放慢节奏，认真推敲。建议先写出一个修改草案，然后再重新审视并进一步完善。务必设身处地站在用户的立场，深入理解他们的需求与期望。

### 迭代循环

改进技能之后：1. 将你的改进应用到技能中
2. 在一个新的 `iteration-<N+1>/` 目录下重新运行所有测试用例，包括基线运行。如果你正在创建一个新技能，基线始终是 `without_skill`（无技能）——在各次迭代中保持不变。如果你是在改进现有技能，则根据实际情况判断合适的基线：是用户最初使用的原始版本，还是上一次迭代的版本。
3. 使用 `--previous-workspace` 参数指向上一次迭代来启动评审工具。
4. 等待用户完成评审并告知你已结束。
5. 阅读新的反馈，再次改进，重复上述流程。

持续进行，直到：
- 用户表示满意
- 反馈全部为空（一切看起来都很好）
- 你无法取得有意义的进展

## 进阶：盲对比

在需要对两个版本的技能进行更严格比较的情况下（例如用户问“新版本真的更好吗？”），可以使用盲对比系统。详情请参阅 `agents/comparator.md` 和 `agents/analyzer.md`。基本思路是：将两个输出结果交给一位不知情的独立代理，由其评判质量，然后分析获胜者胜出的原因。

此功能为可选，需要子代理支持，大多数情况下用户并不需要它。通常，人工评审循环已经足够。

## 描述优化

SKILL.md 前置元数据中的描述字段是决定 Claude 是否调用某项技能的主要依据。在创建或改进技能后，可主动提供优化描述的服务，以提高触发的准确性。

### 第一步：生成触发评估查询

创建 20 条评估查询，其中包含应触发和不应触发的场景，并以 JSON 格式保存：

```json
[
  {"query": "用户的提示语", "should_trigger": true},
  {"query": "另一条提示语", "should_trigger": false}
]
```

这些查询必须贴近实际，是 Claude Code 或 Claude.ai 用户可能真正输入的内容。不要使用抽象的请求，而要选择具体、明确且细节丰富的请求，例如文件路径、用户工作或情境相关的背景信息、列名与数值、公司名称、URL，以及一些简短的背景故事。部分查询可以采用小写形式，包含缩写、拼写错误或口语化表达。查询长度应多样化，重点放在边缘场景上，而非过于清晰明确的情况（用户随后会确认这些查询）。

不良示例：“格式化这些数据”、“从 PDF 中提取文本”、“创建图表”

良好示例：“好吧，我老板刚发给我一个 XLSX 文件（在我的下载里，名字大概是‘Q4 sales final FINAL v2.xlsx’），她希望我加一列，显示利润率百分比。收入在 C 列，成本好像在 D 列。”

对于**应触发**的查询（8–10 条），要考虑覆盖范围。尝试不同措辞但表达相同意图的句子——既有正式的，也有随意的。加入一些用户未明确提及技能或文件类型，但显然需要该技能的情境。同时加入一些少见的使用场景，以及本技能与其他技能竞争时理应优先被调用的情形。

对于**不应触发**的查询（8–10 条），最有价值的是那些“擦边球”式的例子——即与技能共享关键词或概念，但实际上需要其他处理的查询。考虑相关领域、容易因关键词匹配而误触发的模糊表述，以及技能虽涉及部分内容，但在特定场景下更适合由其他工具处理的情况。

需要注意避免的一点：不要让“不应触发”的查询显得明显无关。“编写斐波那契数列函数”作为 PDF 技能的负向测试过于简单，起不到检验作用。负向测试案例应当真正具有一定的难度。

### 第二步：与用户共同审核

使用 HTML 模板向用户展示并请其审核这套评估集：1. 读取 `assets/eval_review.html` 中的模板文件。
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → 评估项的 JSON 数组（无需加引号——这是 JavaScript 变量赋值）；
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名称；
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 当前技能描述。
3. 将内容写入临时文件（例如 `/tmp/eval_review_<skill-name>.html`），并打开该文件：`open /tmp/eval_review_<skill-name>.html`。
4. 用户可以编辑查询、切换“应触发”状态、增删条目，然后点击“导出评估集”。
5. 文件会下载到 `~/Downloads/eval_set.json`；如果有多个版本（如 `eval_set (1).json`），请在“下载”文件夹中查看最新版本。

这一步很重要——不恰当的评估查询会导致糟糕的描述。

### 第三步：运行优化循环

告知用户：“这需要一些时间——我会在后台运行优化循环，并定期检查进度。”

将评估集保存到工作区，然后在后台执行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

请使用系统提示中指定的模型 ID（即当前会话所使用的模型），以确保触发测试与用户的实际体验一致。

在运行过程中，定期查看输出日志，向用户汇报当前迭代次数以及各项得分情况。

此流程会自动完成整个优化循环。它将评估集分为 60% 的训练集和 40% 的保留测试集，评估当前描述（对每个查询重复执行三次以获得可靠的触发率），然后调用 Claude 根据失败情况进行改进建议。每次生成的新描述都会在训练集和测试集上重新评估，最多迭代 5 次。完成后，会在浏览器中打开一个 HTML 报告，展示每轮迭代的结果，并返回包含 `best_description` 的 JSON 数据——选择依据是测试集得分而非训练集得分，以避免过拟合。

### 技能触发机制说明

理解触发机制有助于设计更有效的评估查询。技能会以其名称和描述出现在 Claude 的 `available_skills` 列表中，Claude 会根据该描述决定是否调用该技能。需要注意的是，Claude 只会对自身难以直接处理的任务调用技能——对于像“阅读这份 PDF”这样简单的一步式查询，即使描述完全匹配，也可能不会触发技能，因为 Claude 可以直接通过基础工具完成。而复杂、多步骤或专业化的查询，在描述匹配时则会可靠地触发技能。

这意味着您的评估查询必须足够有实质内容，让 Claude 确实能从调用技能中获益。像“读取文件 X”这样的简单查询并不是好的测试用例——无论描述质量如何，它们都不会触发技能。

### 第四步：应用优化结果

从 JSON 输出中提取 `best_description`，并更新技能的 SKILL.md 前置元数据。向用户展示优化前后的对比，并报告各项得分。

### 打包并交付（仅限具备文件交付工具时）

检查您是否拥有可向用户交付文件的工具——例如 Cowork remote 中的 `present_files` 或 `SendUserFile`。如果没有这些工具，请跳过此步骤。如果具备，则使用相应工具打包技能并将生成的 `.skill` 文件发送给用户：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

当用户所在组织允许创建技能时，呈现的 `.skill`（或纯 `SKILL.md`）文件卡片会显示一个“保存技能”按钮；点击即可将其安装到用户个人资料中。

## Claude.ai 特定说明

在 Claude.ai 中，核心工作流程相同（草稿→测试→评审→改进→重复），但由于 Claude.ai 不支持子代理，部分机制有所变化。以下是需要调整的内容：

**运行测试用例**：没有子代理意味着无法并行执行。对于每个测试用例，先阅读该技能的 SKILL.md 文件，然后按照其中的说明亲自完成测试任务。每次只执行一个。这种方式不如独立子代理那样严格（因为是你自己编写并运行技能，所以你拥有完整的上下文），但仍然是一项有用的合理性检查——而且人工评审环节可以弥补这一不足。跳过基线测试，直接使用该技能按要求完成任务。

**评审结果**：如果你无法打开浏览器（例如，Claude.ai 的虚拟机没有显示设备，或者你在远程服务器上），则完全跳过浏览器评审环节。改为直接在对话中展示结果。对于每个测试用例，同时展示提示和输出。如果输出是一个用户需要查看的文件（如 .docx 或 .xlsx），请将其保存到文件系统，并告知用户文件的存放位置，以便他们下载并检查。在对话中直接征求反馈：“您觉得这样如何？有什么需要修改的地方吗？”

**基准测试**：跳过定量基准测试——它依赖于基线对比，而在没有子代理的情况下，这种对比并无意义。重点收集用户的定性反馈。

**迭代循环**：与之前相同——改进技能、重新运行测试用例、征求反馈——只是中间不再经过浏览器评审环节。如果你有文件系统，仍然可以将每次迭代的结果整理到对应的目录中。

**描述优化**：本节需要用到 `claude` 命令行工具（特别是 `claude -p`），该工具仅在 Claude Code 中可用。如果你使用的是 Claude.ai，则可跳过此步骤。

**盲测比较**：需要子代理支持，因此跳过。

**打包**：`package_skill.py` 脚本在任何安装了 Python 和文件系统的环境中均可运行。在 Claude.ai 上，你可以运行该脚本，用户随后即可下载生成的 `.skill` 文件。

**更新现有技能**：用户可能要求你更新现有技能，而不是创建新技能。在这种情况下：
- **保留原有名称。** 记下技能的目录名和 `name` 元数据字段——保持不变。例如，如果已安装的技能名为 `research-helper`，则输出为 `research-helper.skill`（而非 `research-helper-v2`）。
- **编辑前先复制到可写位置。** 已安装技能的路径可能是只读的。请先将其复制到 `/tmp/skill-name/` 目录，在那里进行编辑，再从副本中打包。
- **若手动打包，应先暂存至 `/tmp/`，** 再复制到输出目录——直接写入可能会因权限问题而失败。

## Cowork 特定说明

如果你正在使用 Cowork，主要需要注意以下几点：

- 您已经配置了子代理，因此主工作流（并行生成测试用例、运行基线、评分等）都能正常运行。（不过，如果遇到严重的超时问题，也可以选择串行而非并行地执行测试提示。）
- 由于您没有浏览器或显示设备，在生成评估查看器时，请使用 `--static <output_path>` 参数，将结果输出为一个独立的 HTML 文件，而不是启动服务器。然后提供一个链接，供用户点击在浏览器中打开该 HTML。
- 不知为何，Cowork 环境似乎会让 Claude 在运行完测试后不再自动生成评估查看器。因此再次强调：无论是在 Cowork 还是 Claude Code 中，运行完测试后，都应通过 `generate_review.py` 脚本生成评估查看器，以便让人类先查看示例，再自行对技能进行修改和调整——不要手写定制化的 HTML 代码。在此特别提醒：务必在自己评估输入之前先生成评估查看器！越早让人类看到结果越好！
- 反馈机制有所不同：由于没有运行中的服务器，“Submit All Reviews”按钮会将 `feedback.json` 下载为文件，之后您可以直接读取该文件（可能需要先申请访问权限）。
- 打包功能正常——`package_skill.py` 只需 Python 和文件系统即可运行。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该也能正常工作，因为它通过子进程调用 `claude -p`，不依赖浏览器。不过请等到您完全完成技能开发，并且用户确认其状态良好后再执行此步骤。
- **更新现有技能**：用户可能要求您更新已有技能，而非创建新技能。请按照上文 claude.ai 部分的更新指南操作。
