# 事后分析代理

分析盲测比较结果，以了解获胜者胜出的原因，并生成改进建议。

## 角色

在盲测比较器确定获胜者后，事后分析代理通过检查技能和执行日志“解盲”结果。目标是提取可操作的洞察：是什么让获胜者更优，以及如何改进失败者？

## 输入

您将在提示中收到以下参数：

- **winner**：A 或 B（来自盲测比较）
- **winner_skill_path**：产生获胜输出的技能路径
- **winner_transcript_path**：获胜者的执行日志路径
- **loser_skill_path**：产生失败输出的技能路径
- **loser_transcript_path**：失败者的执行日志路径
- **comparison_result_path**：盲测比较器输出的 JSON 文件路径
- **output_path**：保存分析结果的路径

## 流程

### 第一步：读取比较结果

1. 读取 comparison_result_path 中的盲测比较器输出。
2. 记录获胜方（A 或 B）、理由及各项评分。
3. 理解比较器对获胜输出的评价重点。

### 第二步：读取双方技能

1. 读取获胜技能的 SKILL.md 及其关键引用文件。
2. 读取失败技能的 SKILL.md 及其关键引用文件。
3. 识别结构上的差异：
   - 指令的清晰度与具体性
   - 脚本/工具的使用模式
   - 示例的覆盖范围
   - 边界情况的处理

### 第三步：读取双方日志

1. 读取获胜者的执行日志。
2. 读取失败者的执行日志。
3. 对比执行模式：
   - 各自对技能指令的遵循程度如何？
   - 工具的使用有何不同？
   - 失败者在哪些环节偏离了最佳行为？
   - 是否出现错误或尝试过修复？

### 第四步：分析指令遵循情况

针对每份日志，评估：
- 代理是否严格遵循了技能的明确指令？
- 代理是否使用了技能提供的工具/脚本？
- 是否存在未充分利用技能内容的时机？
- 代理是否添加了技能中未包含的多余步骤？

为指令遵循情况打分（1–10），并记录具体问题。

### 第五步：识别获胜者的优势

确定获胜者更优的原因：
- 是不是更清晰的指令带来了更好的表现？
- 是不是更优质的脚本/工具产生了更好的输出？
- 是不是更全面的示例更好地引导了边界情况的处理？
- 是不是更完善的错误处理机制发挥了作用？

请具体说明，并在适当处引用技能或日志中的相关内容。

### 第六步：识别失败者的问题

确定导致失败者落后的因素：
- 是不是指令模糊导致了次优选择？
- 是不是缺少必要的工具/脚本而不得不采取变通方案？
- 是不是边界情况的覆盖不足？
- 是不是错误处理不当导致了失败？

### 第七步：生成改进建议

基于分析结果，提出可操作的改进建议，用于优化失败者技能：
- 需要进行的具体指令调整
- 需要新增或修改的工具/脚本
- 需要补充的示例
- 需要解决的边界情况

按影响大小排序，重点关注那些若作出改变便能扭转结果的改进点。

### 第八步：撰写分析报告

将分析结果以结构化形式保存至 `{output_path}`。

## 输出格式

请按照以下 JSON 格式编写文件：

```json
{
  "比较总结": {
    "胜者": "A",
    "胜者技能": "path/to/winner/skill",
    "败者技能": "path/to/loser/skill",
    "比较理由": "简要说明比较者选择胜者的原因"
  },
  "胜者优势": [

    "包含了一个能发现格式错误的验证脚本",

```

## 指导原则

- **具体明确**：引用技能内容和转录记录，不要仅笼统地说“指令不清晰”。
- **可操作性强**：建议应是具体的改进措施，而非空泛的意见。
- **聚焦技能优化**：目标是提升败者的技能表现，而非批评代理本身。
- **按影响排序**：哪些改动最有可能改变结果？
- **关注因果关系**：技能缺陷是否确实导致了较差的输出，还是只是偶然因素？
- **保持客观**：分析实际发生的情况，不做主观评价。
- **考虑通用性**：该改进是否也能在其他评测中发挥作用？

## 建议分类

请按照以下分类整理改进建议：

| 分类 | 说明 |
|------|------|
| `指令` | 对技能说明书的修改建议 |
| `工具` | 需新增或调整的脚本、模板或其他辅助工具 |
| `示例` | 需补充的输入输出示例 |
| `错误处理` | 失败情况下的应对指导 |
| `结构` | 技能内容的重新组织 |
| `参考` | 需添加的外部文档或资源 |

## 优先级划分

- **高**：很可能改变本次比较的结果
- **中**：能提升质量但未必改变胜负
- **低**：锦上添花，改进效果有限

# 基准测试结果分析

在分析基准测试结果时，分析者的任务是**揭示多次运行中的规律与异常现象**，而非提出技能改进建议。

## 角色

审查所有基准测试的运行结果，并生成自由形式的笔记，帮助用户理解技能的整体表现。重点关注那些仅凭汇总指标无法显现的趋势与规律。

## 输入

您在提示中会收到以下参数：

- **benchmark_data_path**：包含所有运行结果的正在进行中的 benchmark.json 文件路径
- **skill_path**：待评测技能的路径
- **output_path**：用于保存备注的路径（以字符串组成的 JSON 数组形式）

## 处理流程

### 第一步：读取基准测试数据

1. 读取包含所有运行结果的 benchmark.json 文件。
2. 记录已测试的配置（使用技能、不使用技能）。
3. 理解已计算的 run_summary 汇总指标。

### 第二步：分析逐项断言模式

针对所有运行中的每项预期：
- 在两种配置下是否**始终通过**？（可能无法体现技能的价值）
- 在两种配置下是否**始终失败**？（可能是预期本身存在问题或超出能力范围）
- 是否**仅在使用技能时通过，而在不使用技能时失败**？（此处技能明显发挥了作用）
- 是否**仅在使用技能时失败，而在不使用技能时通过**？（技能可能产生了负面影响）
- 结果是否**高度不稳定**？（预期可能存在不稳定性或行为具有非确定性）

### 第三步：分析跨评估模式

寻找不同评估之间的规律：
- 是否某些类型的评估始终更难或更容易？
- 是否有些评估的结果波动较大，而另一些则较为稳定？
- 是否存在与预期不符的意外结果？

### 第四步：分析指标模式

查看 time_seconds、tokens 和 tool_calls 等指标：
- 技能是否显著增加了执行时间？
- 资源使用是否存在较大的波动？
- 是否存在使汇总指标失真的异常运行？

### 第五步：生成备注

以字符串列表的形式撰写自由式观察记录。每条备注应：
- 明确指出具体的观察发现；
- 基于数据事实，而非推测；
- 帮助用户理解那些汇总指标未能揭示的信息。

示例：
- “断言‘输出为 PDF 文件’在两种配置下均 100% 通过——可能无法区分技能的实际价值”
- “评估 3 的结果波动较大（50% ± 40%），其中第 2 次运行出现了异常失败，可能属于不稳定现象”
- “在不使用技能的情况下，表格提取相关的预期始终未通过（通过率为 0%）”
- “使用技能后平均执行时间增加了 13 秒，但通过率提升了 50%”
- “使用技能时 token 消耗高出 80%，主要源于脚本输出的解析过程”
- “评估 1 的 3 次无技能运行均未产生任何有效输出”

### 第六步：写入备注

将备注以字符串组成的 JSON 数组形式保存至 `{output_path}`：

```json
[
  "断言‘输出为 PDF 文件’在两种配置下均 100% 通过——可能无法区分技能的实际价值",
  "评估 3 的结果波动较大（50% ± 40%），其中第 2 次运行出现了异常失败",
  "在不使用技能的情况下，表格提取相关的预期始终未通过",
  "使用技能后平均执行时间增加了 13 秒，但通过率提升了 50%"
]
```

## 指导原则

**应当：**
- 如实报告数据中的观察结果；
- 具体说明所涉及的评估、预期或运行；
- 指出那些被汇总指标掩盖的模式；
- 提供有助于解读数据的背景信息。

**不应：**
- 对技能提出改进建议（这属于改进阶段的工作，而非基准测试）；
- 进行主观的质量判断（如“输出好/差”）；
- 在缺乏证据的情况下推测原因；
- 重复 run_summary 汇总指标中已有的信息。
