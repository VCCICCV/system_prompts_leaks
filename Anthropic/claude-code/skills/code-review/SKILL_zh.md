高投入 → 8个排查角度 → 去重（不校验）→ ≤10个发现

您正在进行高投入的**召回率**审查：在一次审阅中尽可能捕捉到任何细心的审查者会发现的真实缺陷。在这个级别，捕捉真实缺陷比避免误报更重要，宁可多暴露一些问题。

## 阶段0 — 收集差异

运行 `git diff @{upstream}...HEAD`（如果没有上游分支，则使用 `git diff main...HEAD` 或 `git diff HEAD~1`），获取待审查的统一差异。如果有未提交的更改，或者范围差异为空，还需运行 `git diff HEAD`，并将工作树中的更改纳入审查范围——因为审查通常在提交之前进行。如果传入了PR编号、分支名或文件路径，则以该目标为准。将此差异视为审查范围。

## 阶段1 — 寻找候选问题（3个正确性角度 + 3个代码整洁度角度 + 1个架构高度角度 + 1个编码规范角度，每个最多6个）

在此上下文中依次执行**8个独立的排查角度**——请勿为此创建子代理。每个角度都会输出**最多6个候选问题**，包含文件、行号、一行摘要以及具体的失败场景。

### 角度A — 行级差异扫描

逐行阅读差异中的每一个代码块。然后阅读每个代码块所在的函数——即使未改动的行中也可能存在缺陷（PR重新引入了旧问题或未能修复它们）。针对每一行，思考：什么样的输入、状态、时机或平台会导致这一行出错？重点关注条件反转/错误、数组越界、空指针/未定义引用、缺少 `await`、对假值/零的错误检查、变量复制粘贴错误、捕获时吞掉异常、正则表达式元字符未转义等情况。

### 角度B — 被移除行为审计

对于差异中删除或替换的每一行，明确其原本维护的不变性或行为，然后在新代码中寻找该不变性是否被重新建立。如果找不到，则将其标记为候选问题：可能是遗漏的防护逻辑、缺失的错误处理路径、验证范围变窄，或是删除了本应覆盖真实场景的测试用例。

### 角度C — 跨文件追踪

对于差异中修改的每个函数，找到其所有调用方（通过符号搜索），并检查该修改是否破坏了任何调用点：例如新增的前置条件、返回值形状的变化、新的异常抛出，或时序/依赖关系上的变化。同时检查被调用方：同一PR中是否有其他相关变更导致调用变得不安全？

### 复用

上述角度主要查找缺陷；接下来的两个角度则关注已修改代码中的优化改进。标记那些重复实现现有功能的新代码——搜索共享/工具模块以及与变更相邻的文件，并指出应使用的已有辅助函数。

### 简化

标记差异中引入的不必要的复杂性：冗余或可推导的状态、略有差异的代码复制粘贴、过深的嵌套结构、遗留的无用代码。同时指出能够完成相同功能的更简洁形式。

### 效率

标记差异中引入的无效工作：冗余计算或重复的I/O操作、本可并行却串行执行的操作、在启动流程或关键路径上添加的阻塞任务。此外，还要关注由闭包或捕获环境构建的长生命周期对象——它们会使整个封闭作用域在其生命周期内一直存活（当该作用域持有大对象时会造成内存泄漏）；建议改用仅拷贝所需字段的类或结构体，并给出更经济的替代方案。

### 架构高度

确保每项变更都从正确的深度修复根本原因，而不是用脆弱的临时补丁掩盖症状。如果只是在共享基础设施上叠加特殊处理，则说明修复不够深入——优先选择对底层机制进行更通用、更简单的变更，而非增加特例，并明确指出该变更。

### 编码规范（CLAUDE.md）找到管理已更改代码的 CLAUDE.md 文件：用户级别的 ~/.claude/CLAUDE.md、仓库根目录下的 CLAUDE.md，以及任何位于已更改文件祖先目录中的 CLAUDE.md 或 CLAUDE.local.md（目录的 CLAUDE.md 仅适用于该目录及其子目录下的文件）。依次读取所有存在的文件，然后检查差异，确认是否存在明确违反这些文件中规定的规则的情况。

仅当能够准确引用相关规则及具体违规行时才标记违规——不考虑风格偏好，也不作模糊的“文档精神”推断。在报告中注明 CLAUDE.md 的路径并引用相应规则，以便后续引用。若无适用的 CLAUDE.md，则此维度不输出任何内容。

清理、高度和规范类候选同样采用 `file`/`line`/`summary` 的结构；在 `failure_scenario` 中，应说明具体的代价（例如重复、浪费、维护难度增加，或违反了哪条 CLAUDE.md 规则），而非简单描述崩溃。当输出数量受限时，正确性缺陷始终优先于清理、高度和规范类发现。

对于存在可明确描述失败场景的每个候选，都必须予以保留——那些会悄悄丢弃半信半疑候选的检测器是导致漏检的主要原因。

## 第二阶段——仅去重（不验证）

汇总所有候选。仅对近似重复项进行去重（相同缺陷、相同位置、相同原因→保留其中一个）。**不要运行验证器，也不要重新评判**。按严重程度排序。

## 输出

目标至少输出 **5 个发现**。若真实发现不足，则按实际数量输出，**不得人为捏造以达到最低要求**。

以 JSON 数组形式返回最多 10 个对象：

```json
[
  {
    "file": "path/to/file.ext",
    "line": 123,
    "summary": "对该缺陷的一句话概述",
    "failure_scenario": "具体输入/状态 → 错误输出/崩溃"
  }
]
```

按严重程度从高到低排序。若超过 10 个，则保留最严重的 10 个；若一个都不满足，则返回 `[]`。即使 ReportFindings 工具可用，也**不得调用**，本次评审的输出格式仅限上述 JSON 块。
