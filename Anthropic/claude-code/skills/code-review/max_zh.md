`最大努力 → 5+5个角度 × 8个候选 → 单票验证 → 扫描 → ≤15个发现`

您正在以**召回率**为目标，进行最高强度的审查：确保不遗漏任何一个真实缺陷。在这个阶段，捕捉真实缺陷比避免误报更重要——漏掉一个缺陷就意味着它会被发布到线上。宁可多提一些，也不要漏掉。

## 阶段0 — 获取差异范围

运行 `git diff @{upstream}...HEAD`（如果没有上游分支，则使用 `git diff main...HEAD` 或 `git diff HEAD~1`），获取待审查的统一差异。如果有未提交的更改，或者范围差异为空，还需额外运行 `git diff HEAD`，并将工作区的更改也纳入审查范围——因为审查通常在提交之前进行。如果传入了PR号、分支名或文件路径，则以该目标为准进行审查。将此差异视为本次审查的范围。

## 阶段1 — 寻找候选（5个正确性角度 + 3个清理角度 + 1个高度角度 + 1个规范角度，每个最多8个）

通过Agent工具运行**10个独立的查找角度**。每个角度最多会输出**8个候选发现**。不要让一个角度的结论压制另一个角度的结果——如果两个角度因不同原因标记了同一行，也要同时记录下来。如果当前工具链中没有Agent工具，请不要报错——在这种情况下，请手动依次执行每个角度及其验证。

### 角度A — 行级差异扫描

逐行阅读差异中的每一个代码块。然后阅读每个代码块所在的函数——即使某函数的其他部分未被修改，其中的缺陷也在审查范围内（因为PR可能重新引入了这些缺陷，或未能修复它们）。针对每一行，思考：什么样的输入、状态、时机或平台会导致这一行出错？重点关注条件颠倒/错误、数组越界、空指针/未定义引用、缺少`await`、对假值/零的错误检查、变量复制粘贴错误、捕获时吞掉了错误、正则表达式元字符未转义等情况。

### 角度B — 被移除行为审计

对于差异中删除或替换的每一行，明确其原本维护的不变量或行为，然后在新代码中寻找该不变量是否被重新建立。如果找不到，那就是一个候选：可能是某个保护性检查被移除、某个错误处理路径被删掉、验证逻辑被缩窄，或者某个覆盖真实场景的测试被删除了。

### 角度C — 跨文件追踪

对于差异中改动的每个函数，找到它的所有调用者（通过符号搜索），并检查此次改动是否破坏了任何调用点：例如新增了前置条件、返回值结构发生变化、抛出了新的异常，或是引入了时序/顺序依赖。同时也要检查被调用方：同一次PR中的另一处改动是否会让调用变得不安全？

### 角度D — 语言陷阱专家

扫描差异所涉及的语言或框架中的常见陷阱——例如：JavaScript中的假值/零、`==`类型强制转换、闭包捕获循环变量；Python中的可变默认参数、晚期绑定的闭包；Go中的空map写操作、range循环变量被捕获；SQL注入；时区/DST漂移；浮点数相等比较问题。只要差异引入了这些情况，就予以标记。

### 角度E — 包装器/代理的正确性

当PR新增或修改了一个包装其他组件的类型（如缓存、代理、装饰器、适配器）时，检查每个方法是否都正确地路由到了被包装的实例，而不是通过注册表/会话/全局变量间接调用——例如，一个缓存提供者持有一个`delegate`字段，却通过`session.get(...)`而非`delegate.get(...)`来解析ID，这就会导致重复进入缓存或发生递归调用。同时还要确认包装器确实转发了调用方实际使用的所有方法。

### 复用

上述角度主要寻找缺陷；接下来的两个角度则专注于查找代码中的可优化之处。标记那些在已有的代码库中已有实现，却被新代码重新实现的部分——通过grep搜索共享/工具模块以及与变更相邻的文件，并指出应该调用的现有辅助函数。

### 简化

标记差异中引入的不必要的复杂性：冗余或可推导的状态、略有差异的代码复制粘贴、过深的嵌套层次、遗留的无用代码。同时指出能够完成同样功能的更简洁形式。

### 效率标记引入的无效工作：冗余计算或重复 I/O、
独立操作被串行执行、在启动或热点路径中添加了阻塞操作。同时标记由闭包或捕获环境构建的长期存活对象——它们会使整个封闭作用域在其生命周期内一直存活（当该作用域持有大对象时会造成内存泄漏）；应优先使用仅复制所需字段的类或结构体，并明确指出更优的替代方案。

### 高度

检查每一处改动是否在恰当的层次上修复了根本原因，而不是用脆弱的“创可贴”来掩盖症状。在共享基础设施上叠加的特殊处理是修复不够深入的标志——应优先选择对底层机制进行更简单、更通用的修改，而非增加特殊分支，并为该修改命名。

### 规范（CLAUDE.md）

找到管理已更改代码的 CLAUDE.md 文件：用户级别的 ~/.claude/CLAUDE.md、仓库根目录下的 CLAUDE.md，以及任何位于已更改文件祖先目录中的 CLAUDE.md 或 CLAUDE.local.md（目录的 CLAUDE.md 仅适用于该目录及其子目录下的文件）。阅读所有存在的 CLAUDE.md 文件，然后检查差异，确认是否存在明显违反其中规则的情况。

仅在能够准确引用具体规则及违反该规则的具体行号时才标记违规——不考虑个人风格偏好，也不做模糊的“文档精神”推断。在报告中注明 CLAUDE.md 的路径并引用相关规则，以便后续引用。若无适用的 CLAUDE.md，则此维度无需输出。

清理、高度和规范方面的候选问题均采用相同的 `file`/`line`/`summary` 格式；在 `failure_scenario` 中，应说明具体的代价（例如重复、浪费、维护难度增加，或违反了哪条 CLAUDE.md 规则），而非直接描述崩溃。当输出上限迫使必须裁剪时，正确性缺陷始终优先于清理、高度和规范方面的发现。

## 第二阶段 — 验证（一票制，三状态）

合并指向同一行或同一机制的候选问题，保留具有最具体失败场景的那个。对于每个剩余的候选问题，通过 Agent 工具运行 **一个验证器**：提供差异、相关文件及该候选问题，验证器应返回以下三种结果之一：

- **已确认** — 能够明确指出触发条件及错误输出或崩溃，并引用相关行号。
- **合理可能** — 机制确实存在，但触发条件尚不确定（如时机、环境、配置等），并说明需要哪些信息才能进一步确认。
- **已否定** — 事实不符（代码并未如此实现）或已在其他地方得到防护，并引用证明其错误的行号。

仅保留投票结果为“已确认”或“合理可能”的候选问题。

本阶段以召回率为重——只要有一票未被否定，该发现即予采纳。切勿因不确定性而舍弃。

## 第三阶段 — 拉网排查遗漏

以一名新审阅者的身份，基于已验证的问题列表再运行 **一次查找程序**。仅针对尚未列出的缺陷，重新阅读差异及周边函数。不得对已有内容进行重复推导或再次确认——重点在于寻找遗漏。重点关注第一轮容易忽略的内容：被移动或提取后丢失的防护或锚点；次级陷阱（数据类默认值仅求值一次、`hash()` 不确定性、锁作用域缩小、带有副作用的谓词方法）；测试中的设置与清理不对称；配置默认值被误设。

最多补充 **8 个新增候选问题**，每个问题均需指出列表中尚未涵盖的缺陷。若无新发现，返回空的拉网结果——不得人为凑数。

## 输出

以 JSON 数组形式返回最多 15 个问题对象：

```json
[
  {
    "file": "path/to/file.ext",
    "line": 123,
    "summary": "一句话概述的缺陷",
    "failure_scenario": "具体输入/状态 → 错误输出/崩溃"
  }
]
```

按严重程度从高到低排序。若超过 15 个，则保留最严重的 15 个。若所有问题均未通过验证，则返回空数组 `[]`。即使 ReportFindings 工具可用，也无需调用该工具——本次评审的输出格式仅为上述 JSON 块。
