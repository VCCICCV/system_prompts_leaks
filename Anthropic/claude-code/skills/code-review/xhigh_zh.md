`极高投入 → 10个内联角度 → 去重（不校验）→ 扫描 → ≤15个发现`

您正在进行**召回率**的极高投入评审：务必捕捉每一个真实存在的缺陷。在这个级别，捕捉真实缺陷比避免误报更重要——漏掉一个缺陷就意味着它会被发布出去。宁可多报告一些，也不要遗漏。

## 阶段0 — 收集差异

运行 `git diff @{upstream}...HEAD`（如果没有上游分支，则使用 `git diff main...HEAD` 或 `git diff HEAD~1`），获取待评审的统一差异。如果有未提交的更改，或者范围差异为空，还需运行 `git diff HEAD`，并将工作区的更改也纳入评审范围——因为评审通常在提交之前进行。如果传入了PR编号、分支名或文件路径，则以该目标为准。将此差异视为评审的范围。

## 阶段1 — 寻找候选问题（5个正确性角度 + 3个代码整洁度角度 + 1个架构高度角度 + 1个规范角度，每个最多8个）

在当前上下文中依次执行**10个独立的查找角度**——切勿为此创建子代理。每个角度最多会输出**8个候选问题**。不要让一个角度的结论压制另一个角度的发现——如果两个角度因不同原因标记了同一行代码，应同时记录下来。

### 角度A — 行级差异扫描

逐行阅读差异中的每一个代码块。然后阅读每个代码块所在的函数——被改动函数中未变更的代码若存在缺陷，也在评审范围内（PR可能重新引入了这些缺陷，或未能修复它们）。针对每一行代码，思考：什么样的输入、状态、时机或平台会导致这一行出错？寻找条件颠倒或错误、数组越界、空指针/未定义引用、缺少 `await`、对假值/零的错误检查、变量复制粘贴错误、捕获时吞掉异常、正则表达式元字符未转义等问题。

### 角度B — 被移除行为审计

对于差异中删除或替换的每一行代码，明确其原本维护的不变量或行为，然后在新代码中搜索该不变量是否被重新建立。如果找不到，则将其作为候选问题：可能是某个保护性检查被移除、某条错误处理路径被删减、验证逻辑被缩窄，或是删除了一个本用于覆盖真实场景的测试用例。

### 角度C — 跨文件追踪

对于差异中修改的每个函数，找到它的调用者（通过符号搜索），并检查此次改动是否破坏了任何调用点：例如新增的前置条件、返回值形状的变化、新的异常抛出，或时序/依赖关系的变化。同时也要检查被调用方：同一次PR中的其他改动是否使调用变得不安全？

### 角度D — 语言陷阱专家

扫描差异所涉及的语言或框架中的常见陷阱——例如：JavaScript 中的假值与零比较、`==` 强制类型转换、闭包捕获循环变量；Python 中的可变默认参数、晚期绑定的闭包；Go 中的空map写入、range循环变量被捕获；SQL注入；时区与夏令时偏移；浮点数相等比较。标记差异中引入的任何此类情况。

### 角度E — 包装器/代理的正确性

当PR新增或修改了一个包装其他组件的类型（如缓存、代理、装饰器、适配器）时，检查每个方法是否都路由到了被包装的实例，而不是通过注册表/会话/全局变量回流——例如，一个缓存提供者持有一个 `delegate` 字段，却通过 `session.get(...)` 而非 `delegate.get(...)` 来解析ID，这会导致重复进入缓存或发生递归调用。同时检查包装器是否完整转发了调用方实际使用的所有方法。

### 复用

上述角度主要寻找缺陷；接下来的两个角度则关注已修改代码中的可优化之处。标记那些重新实现现有功能的新代码——通过搜索共享/工具模块以及与改动相邻的文件，指出应该调用的已有辅助函数。

### 简化

标记差异中引入的不必要的复杂性：冗余或可推导的状态、略有差异的代码复制粘贴、过深的嵌套层次、遗留的无用代码。指出能够完成同样功能的更简洁形式。

### 效率标记引入的无效工作：冗余计算或重复 I/O、
独立操作被串行执行、在启动或热点路径中添加了阻塞操作。同时标记由闭包或捕获环境构建的长生命周期对象——它们会使整个封闭作用域在其生命周期内一直存活（当该作用域持有大对象时会造成内存泄漏）；应优先使用仅复制所需字段的类或结构体，并明确指出更优的替代方案。

### 高度

检查每一处改动是否在恰当的层次上修复了根本原因，而不是用脆弱的“创可贴”来掩盖症状。在共享基础设施上叠加的特殊处理往往是修复不够深入的信号——应优先选择对底层机制进行更简单、更通用的修改，而非增加特殊分支，并为这一修改命名。

### 规范（CLAUDE.md）

找到管理被修改代码的 CLAUDE.md 文件：用户级别的 ~/.claude/CLAUDE.md、仓库根目录下的 CLAUDE.md，以及任何位于被修改文件祖先目录中的 CLAUDE.md 或 CLAUDE.local.md（目录的 CLAUDE.md 仅适用于该目录及其子目录下的文件）。阅读所有存在的 CLAUDE.md 文件，然后检查差异，确认是否存在明显违反其中规则的情况。

仅在能够准确引用具体规则及违反该规则的具体行时才标记违规——不考虑个人风格偏好，也不做模糊的“文档精神”推断。在报告中注明 CLAUDE.md 的路径并引用相关规则，以便后续引用。若无适用的 CLAUDE.md，则此维度无需输出。

清理、高度和规范方面的候选问题均采用相同的 `file`/`line`/`summary` 格式；在 `failure_scenario` 中，应说明具体的代价（例如哪些内容被重复、浪费、难以维护，或违反了哪条 CLAUDE.md 规则），而非直接描述崩溃。当输出数量受限时，正确性缺陷始终优先于清理、高度和规范方面的发现。

## 第二阶段——仅去重（不验证）
将所有候选问题归集在一起，仅对近似重复的问题进行去重（相同缺陷、相同位置、相同原因——保留一条）。**禁止运行验证器，禁止重新判断**。按严重程度排序，**不得因不确定性而剔除**。

## 第三阶段——排查遗漏
以全新评审者的身份再过一遍（同一上下文，不启用子代理），仅查看已去重的列表，重新审阅差异及周边函数，寻找尚未列出的缺陷。**不得重新推导或再次确认已有内容**——此阶段的任务是查找遗漏。重点关注第一遍容易忽略的事项：被移动或提取后遗漏的防护或锚点；次级陷阱（数据类默认值仅计算一次、`hash()` 的非确定性、锁作用域缩小、带有副作用的谓词方法）；测试中设置与清理的不对称；配置默认值被错误地反转。

最多补充**8个新增候选问题**，每个问题需指出一个尚未列入清单的缺陷。若无新发现，则此阶段无需输出，**不得人为凑数**。

## 输出
目标至少输出**7个发现**。若真实发现不足，则按实际数量输出，**不得凭空捏造以达到最低要求**。

以 JSON 数组形式返回最多15个问题，格式如下：

```json
[
  {
    "file": "path/to/file.ext",
    "line": 123,
    "summary": "一句话概述该缺陷",
    "failure_scenario": "具体输入/状态 → 错误输出/崩溃"
  }
]
```

按严重程度从高到低排序。若超过15个，则保留最严重的15个；若一个都不满足，则返回 `[]`。即使 ReportFindings 工具可用，也**不得调用该工具**——本次评审的输出格式仅为上述 JSON 块。
