画图时要站在必须与这个决策共处的工程师视角，而不是装饰者的视角：只有当一张图能让不熟悉背景的读者一眼看清原本需要从文字中拼凑出的机制——数据流向、哪些组件之间交互、两种方案之间的差异、请求所经历的状态流转——这张图才有存在的价值。如果用一句话就能说得更清楚，那就写成句子。

## 该画什么

**描绘机制，而非名称。** 标着“缓存”的一个方框，不如描述请求在其中的路径、它夹在两个存储之间、以及移除缓存后箭头消失这些细节来得直观。展示那些决定论点的关键部分——跨越的边界、新增的跳步、流动的数据——而省略无关紧要的部分。

**比较多个方案？** 画出差异。把两种架构并排放置，呈现“之前”和“之后”，标出每种方案新增或删减的那一处改动——读者应能直接指出他们在权衡的是什么。如果每个方案都单独放一个带标签的框，且彼此与系统没有连接，那这不算比较，只是换了个形式列出选项而已。

**复杂度要匹配关键性。** 涉及单跳的问题，三框图就够了；而要把写入流量通过队列重新路由的迁移，则需要画出队列、写入端、读取端，以及标明顺序的箭头。只画出决策真正依赖的部分——既不必刻意极简，也不必把整个系统都罗列出来。

**给箭头加标签。** 不加标签的箭头只能让人觉得“大概有关联”；标注上“writes”“invalidates”“polls every 30s”才是信息。只有当同一种编码方式（虚线、颜色、双线）反复出现时，才值得用图例；否则就把含义直接写在图形上。

## 内联 SVG 的绘制规范

这些规范适用于页面原生渲染内联 SVG 的场景（HTML 页面）；由 Markdown 渲染的页面则按各自通道的渲染器支持的方式绘制图表，具体规则由负责该通道的技术负责人制定。手写内联 `<svg>` 时，仅使用原生图形元素（`rect`、`circle`、`line`、`polyline`、`path`）和 `<text>`，不使用任何库、不引入运行时、也不引用外部图片。

- **通过 `viewBox` 控制尺寸。** 设置 `viewBox="0 0 W H"`，让 CSS 来缩放（`max-width: 100%; height: auto`）；W 和 H 应根据内容自行选择，而非采用预设值。横向流程从左到右阅读，分层堆叠则自上而下。
- **用 `currentColor` 实现主题适配。** 线条、文本和箭头尾部若设为 `currentColor`，就能在浅色和深色主题下自动继承页面的前景色；只把唯一承载语义的元素保留为固定颜色（例如倾向的方案、讨论中的跳步），并确保在两种背景下都能清晰辨识。
- **箭头尾部用标记或多边形。** 使用 `<defs><marker>` 并通过 `marker-end="url(#arrow)"` 引用（片段内的 ID），或在线条末端放置一个小 `<polygon>`——绝不使用图片。
- **保证文本可读。** 绘制比例下字号约 11–13px，用 `text-anchor` 对齐，标签尽量简短（一到三个词）；解释性文字应放在图下方的说明中，而非图内。
- **对齐网格。** 共享基线和平齐间距是让手绘图看起来有设计感的关键；随意偏移只会显得杂乱。
- **一张图，一个观点。** 将 `<svg>` 包裹在 `<figure>` 中，并配上说明图片内容的 `<figcaption>`；同时为 `<svg>` 添加 `role="img"` 属性，以及面向无法看到图像用户的 `aria-label`，传达相同的信息。
- **保持自包含。** SVG 内部不得使用 `<script>`、`<style>` 或 `<foreignObject>`；渐变、图案和 `<use>` 都应引用同一文档片段中的 ID（`href="#id"`）。如果路径数据过于冗长，说明这张图更适合用专业绘图工具——不妨先简化再绘制。
