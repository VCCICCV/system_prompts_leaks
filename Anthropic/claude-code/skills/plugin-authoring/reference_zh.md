# 函数钩子：完整形式

插件开发技能的完整形式：函数钩子插件究竟是什么，其确切契约在当前运行的构建中如何定义，以及当某些功能未生效时该从何处查找。位于此文件旁的 SKILL.md 说明了模组的编写位置、类型定义，以及回合结束时会发生什么。请尽早并频繁地在插件目录下运行 `claude plugin validate <dir>`：该命令会以引擎将读取的方式解析清单和钩子模块的源码，并报告模块所挂钩与调用的内容，以及引擎会在加载前拒绝的所有事项。API 处于早期访问阶段，且可能在不同版本间发生变化；声明文件为权威，而本说明则充当地图。

## 函数钩子插件是什么

一个模组由三份文件直接构成：“claude plugin init”会搭建另一种类型的插件，即位于 `~/.claude/skills` 下的命令钩子插件。

插件是一个包含 `.claude-plugin/plugin.json` 清单的文件夹。其函数钩子位于一个钩子模块中：这是一个 TypeScript 或 JavaScript 文件，由 `hooks/hooks.json` 在 `modules` 字段下指定路径（相对于该文件的相对路径），并导出 `register(on, options)` 函数；该模块及其从插件中导入的所有文件均须以 `.ts`、`.tsx`、`.jsx`、`.js`、`.mjs`、`.cjs`、`.mts` 或 `.cts` 为扩展名（其他扩展名的文件不会被加载），且无论后缀为何，均为 ES 模块。插件中的文件通过 `import` 语句引入。含有 `import()` 的模块不会被加载。“on(event, matcher?, hook)”用于添加一个钩子；`options` 包含清单中 `userConfig` 所声明字段的值。每个钩子的签名均为 `($, e, next)`：`$` 是引擎接口（包括显示、模型、会话、提示、工具、文件系统、存储、时钟、网络、主机命令、设置、环境、配置菜单的各选项等），“e”是事件的原始输入值，而 `next(e)` 则将控制权传递给其他插件，继而执行引擎自身的逻辑，并最终返回事件的结果。若钩子在不调用 `next` 的情况下返回，则仅对该钩子自身生效；若调用 `next({ ...e, ... })`，则会在该事件允许的范围内改写后续处理链所见的内容。

该模块运行于独立的环境中，无 DOM 亦无 Node.js 环境：所有外部资源均需通过 `$` 访问。JSX 可通过 `h` 工厂函数使用。这些事件涵盖了工具调用及其描述、对话所维护的行（`session.append`）、提交的提示词、系统提示的各部分以及第一条消息的上下文块、界面的渲染内容、回合的开始、步骤与完成、会话的起始与结束（也包括 /clear 操作：`session.end` 且 `reason: 'clear'`，其后不再有 `session.start`），以及消息的传递；还包括每个钩子模块的准入、技能、子代理和归属文本。设置钩子自身的事件可按 `classic.<Event>` 的形式被钩取（如 `classic.Stop`、`classic.SessionEnd`），其中 `e` 是该钩子从标准输入接收到的数据，同时包含 `transcript_path` 及其他基础字段。在编写之前，有必要明确哪些属于功能，以及它们需要从 `$` 中获取什么。有两种事件流：`turn.step`（回合中的模型请求）和 `process.spawn`（子进程的输出，逐段传来；对于调用方而言，`$.process.spawn({ argv })` 即为该流，而子进程结束即为循环的终结）：对任一事件的钩子都是一个异步生成器（`async function* ($, e, next) {}`，这是唯一可用的形式）；`next(e)` 提供底层流，`yield* next(e)` 将其转发并返回结果，对其使用 `for await` 可逐个处理数据块，无需 `next` 即可单独产生响应；若钩子在流中失败，则会停留在当前状态。`telemetry` 事件可通过名称进行钩取（`telemetry.*` 涵盖所有此类事件；`*` 和否定表达式不会单独选定某一项），钩子在匹配器中选择对应的流，`to` 可以写成字符串字面量或字符串列表（如 `on("telemetry.log", { to: "collector" }, hook)`）：“collector”是客户的 OpenTelemetry 收集器，“anthropic”是 Anthropic 自有的分析系统，也是 CLI 内置插件所依赖的事件流；`claude plugin validate` 列出了某个模块的钩子所依赖的所有事件流。

## 类型即是参考
与此文件并列的 `types/claude-code.d.ts` 是本构建对整个 API 的声明，由引擎在加载技能时生成：它声明了模块 `claude-code`（可从中导入类型；运行时该导入为空）、钩子模块所拥有的全局变量，以及本构建内置工具的输入，因此 `e` 会根据具体工具进一步收窄。其头部附带一份适合钩子模块的 `tsconfig.json`，并展示了如何针对 `Register` 进行类型标注。引擎从用户拥有的文件夹中加载的模块（“为此会话启用”后的 mods 文件夹，或通过 `--plugin-dir` 或 `CLAUDE_CODE_PLUGIN_DIRS` 指定的目录），每次加载与重新加载时都会在其旁放置相同的声明文件，位于 `.claude-plugin/types/` 目录下：`claude-code/index.d.ts` 声明了 API；`claude-code-tools/index.d.ts` 声明了本构建的内置工具；`claude-code-mcp/index.d.ts` 声明了该模块上次重新加载时所连接的 MCP 工具（保存模块时会刷新，但重启不会替换）；每项插件在其 `plugin.json` 的 `dependencies` 字段下都有一条对应条目；此外还有一份由自身扩展的 `tsconfig.json`，以便编辑器和 `tsc -p <mod folder>` 能够为其正确地进行类型检查，无需额外步骤。没有专门的运行命令。内置工具的表格即为本构建在当前机器上注册的工具列表；若某工具属于其他构建（例如 Glob 和 Grep，原生 macOS 或 Linux 构建不会注册），则通过 `String(e.tool)` 进行比较。阅读该文件，了解每个事件的输入与结果、`$` 上每个名词和方法及其文档注释与示例、每个界面元素所绘制的内容及其接受的属性，以及其所声明的限制。其中的“形状”是引擎自身的，而非 Messages API 的：例如，`$.session.messages()` 返回的是 `{ role, text, toolUses }` 结构的 `SessionMessage` 记录，而不是 `content` 块。当构建更新时，请重新生成代码，而非手动修改。
`claude plugin validate <path>` 会读取插件的清单及其钩子模块的源码，并报告该模块所挂钩和调用的内容，这是确认引擎是否正确识别你意图的最快方式。在 `engine.create` 中向 `$` 添加新名词的插件，应以一份自包含的 `.d.ts` 文件（如 `types/index.d.ts`）作为类型契约：该文件在其顶层导出该名词的类型，并在引擎接口上声明该名词，即先写 `export type Topo = { ... }`，再写 `declare module 'claude-code' { interface EngineInterface { topo: Topo } }`——无需任何导入或引用，其导出的名称均以名词的帕斯卡命名法开头（如 `Topo`、`TopoRun`），并在 `plugin.json` 中以 `"types": "./types/index.d.ts"` 指定。插件自身的钩子模块从该文件中导入这些类型，因此该契约是这些类型的唯一书写处。依赖该插件的其他插件绝不会复制这份文件：它只需在自己的 `plugin.json` 中将该插件列为 `dependencies`，每当引擎从用户拥有的某个目录加载插件时，都会将该插件的契约放置于 `.claude-plugin/types/<plugin>/index.d.ts`，从而为依赖插件的 `$` 提供类型定义；`claude plugin validate` 会检查这份契约。
  
## 开发一个插件
  
本节中制作的 Mod 应放在 SKILL.md 的“编写位置”所述路径下，并按说明加载。本节其余部分介绍插件从磁盘运行的其他方式。
  
`claude --plugin-dir <folder>` 只在当前会话中从磁盘加载指定插件（可多次使用该标志以加载多个插件）。`CLAUDE_CODE_PLUGIN_DIRS` 则用于指定无法通过命令行标志设置的目录（适用于桌面应用或 SDK 主机启动的会话）：一个或多个绝对路径（允许使用 `~` 表示主目录），各路径之间以平台的路径分隔符分隔；每个路径下的插件均按 `--plugin-dir` 的方式加载，其值可来自进程环境变量，或来自 `~/.claude/settings.json` 的 `env` 部分（但不来自项目配置）。在交互式会话中，指定目录会被监视，从技能目录自动加载的插件亦同（如 `~/.claude/skills/<name>` 或项目的 `.claude/skills/<name>`）：保存文件会重新加载钩子模块，从而使 `register` 在全新环境中再次执行，同时丢弃前一环境中的定时器。若在会话自身回合（即模型编辑插件时）进行保存，则会在该回合结束时或更早——当插件注册的工具或命令即将运行时——重新加载一次，以便当前回合能试用其修改内容。其他时间的保存则需等待目录静止一段时间后才会触发重新加载：若在四分之一秒内仅保存一次，则只重新加载一次；若在数秒内连续保存，则在保存停止后重新加载一次。无头模式下的 `claude -p` 总是全新加载；对于长期运行的无头会话（SDK 或桌面应用），只要设置了 `CLAUDE_CODE_PLUGIN_DIR_WATCH=1`，也会启用目录监视功能，其重新加载日志会以 `ui_log` 消息及调试日志的形式反馈给宿主。
  
以这种方式加载的插件，其选项会从 `pluginConfigs` 下的配置中读取，键名为插件的 `<name>`（或 `<name>@inline`）；每个非保密的 `userConfig` 字段也会出现在配置菜单中，且其值变更时会使用新选项重新加载模块。若某 `string` 类型字段列出了若干选项（如 `"options": ["gist", "turbo"]`，其中包含 `default` 值），则该字段会成为一个仅限于这些值的选取器；若存储的值不在这些选项之内，则视为未设置。开发时请使用 `claude --debug` 运行。如果某个钩子执行失败，它会被跳过，链式调用会继续进行，除非该钩子注册时的 `.catch` 处理程序为其提供了替代答案；当会话热加载插件目录（启用热加载后为 mods 目录，或通过 `--plugin-dir` 或 `CLAUDE_CODE_PLUGIN_DIRS` 指定的目录）时，转录本中只会有一行以较浅的颜色显示该插件、事件及原因，就像记录未加载模块时那样；而在其他任何会话中，这一行仅会出现在调试日志中，格式为 `<插件>: <行>`（`claude -p` 运行无转录本：若打印文本，则会在标准错误输出中针对未加载或加载失败的 `--plugin-dir` 插件输出一次原因，即使开关已关闭；json 或 stream-json 输出则将其保留在调试日志中）。调试日志会为每次发生的情况以及引擎拒绝的每个结果各记一行；被跳过的钩子那一行会以错误名称和消息长度代替其具体内容（首次出现时的完整内容会被截断为一行，同时也会记录在转录本中，调试日志同样保留），因此看似毫无作用的插件通常都会明确其被跳过的原因。`claude plugin test <文件夹>` 会针对引擎本身运行插件的 `*.test.ts` 测试文件：测试中持有引擎的 `$` 对象，以及位于插件之下的 `on` 钩子（从 `claude-code/testing` 导入 `test`、`expect`、`mock`；其余部分由类型定义给出）。这些钩子之下没有任何东西：它们直接代表引擎，因此钩子的返回值会原封不动地传递给插件，仅包含引擎设置的字段（如 `tool.call` 返回的 `isReadOnly`，以及插件转发时的 `ref` 和 `text`）；而测试中的所有插件，无论其位置如何，都被视为与会话中相同的状态。测试通过 `test(name, { options }, body)` 向被测插件提供 `userConfig` 值，这些值会被当作存储在设置中的值来读取（不在字段 `options` 范围内的值将被置为空，并填充默认值后再进行校验）；若未指定，则插件将采用其清单中的默认值。UI 测试会通过插件在指定的界面上挂载组件，绝不假定界面（套件的 `mount` 方法接受测试的 `ui` 对象：`{ plugin, surface, component, props }`），并通过按键操作界面元素（`press`、`input`、`find`，以及 `Client` 的 `key` 和 `post`），每项操作都依据该界面的元素表进行类型检查；只需编写一次主体代码，然后对 `['terminal', 'desktop'] as const` 进行循环，即可验证插件不依赖于特定界面。测试通过引擎的 `ui` 对象（`render`）绘制出的树状结构，同样可通过该对象的 `press`、`input`（`{ plugin, key, text, kind? }`：`change` 是一种到达 `onInput` 的编辑操作，`submit` 即回车键触发的默认行为，会到达 `onSubmit`）和 `select`（`{ plugin, key, value }`）进行操作；每项操作只有在链式调用、元素自身的处理器，以及该处理器尚未完成的任何异步任务都已解决之后才会生效，因此测试在 `await` 之后无需额外等待即可断言（模拟时钟上休眠的任务需等待测试推进时间才能唤醒）。测试的 `classic` 对象会像引擎一样触发经典的钩子事件（`SessionStart({ source: 'clear' })`，除非另有指定，否则会加盖信封字段；除 `PreToolUse` 事件外，该事件可通过 `tool` 对象的 `call` 触发：`$.tool.call` 会像会话一样触发 `classic.PreToolUse`，位于所有插件的 `tool.call` 钩子之下，且高于测试自身的钩子；因此，若拒绝调用，调用将以会话的 `tool.call` 钩子所见的错误结果结束（`isError`，并以 `text` 表示原因；对于插件自身的 `$.tool.call` 则返回 `{ deny }`），而测试的钩子将不会被执行；若为重写、通过、询问或允许，则会继续执行到该钩子；若未配置任何设置钩子，则测试自身的 `classic.PreToolUse` 钩子下不会有任何决策生效）。该套件会根据各界面的规则，测试插件的钩子及其返回的描述，而非任何界面的具体样式。

## 绘制：ui.render

`ui.render` 钩子接收一个组件实例。`e.component` 指明是哪个组件，`e.surface` 表示该组件的渲染目标（`terminal`、`desktop`、`mobile` 或 `vscode`），`e.requestId` 标识具体是哪一个实例（工具行或对话框对应 tool_use_id，消息或命令输出行对应消息 ID，加载指示器对应代理 ID），`e.props` 是组件的纯数据属性，而当渲染表面完成尺寸测量后，`e.viewport` 提供其绘制区域的字符单元格尺寸：`columns` 和 `rows`。对于会话消息，`e.props.onScreen` 会告知当前视口显示的是该消息的哪几行（从站点首次布局的第一行开始计数，取值为 `{ first, last, of }`；若不在视口中则为 `null`；在渲染表面未明确给出时则不存在）。一旦这些信息发生变化，该消息对应的钩子就会重新执行。  
窗口宽度的变化会在调整稳定后触发所有已挂载的站点重新渲染，因此根据 `columns` 尺寸调整的树结构仍能保持正确；而仅高度变化则不会导致任何重绘。`Pane` 或 `AbovePrompt` 钩子会改用 `e.props.bodyColumns` 来设定其树结构的尺寸：即其所绘制的容器宽度——在面板停靠于会话侧边时，该宽度通常小于视口宽度。`e.viewport.isFullscreen` 表示渲染表面是否确实停靠了面板（终端的全屏布局会停靠，主屏幕则以内联方式打开；若渲染表面未明确说明，则该字段不存在，切勿默认）。这一信息由 `command.run` 的 `presentation` 属性携带，因此插件仅在适合作为侧边栏的位置才会未经用户确认地打开面板。当钩子自身的状态发生变化时，调用 `$.ui.invalidate` 即可请求重新渲染。  
用于绘制的状态应存放在 `$.state` 中，而非模块级变量（热重载会导致后者丢失）：这些是由宿主为当前会话维护的命名值，并附有版本号。应在接口中声明它们（如 `interface PluginState { counter: { count: number; isOpen: StateFamily<boolean> } }`），并通过带有字面量 `plugin` 和 `key` 的类型化引用访问其中的某一项（如 `const count = { plugin: "counter", key: "count" } as const`，此常量仅用于 `$.state` 调用、状态库函数以及展开以添加家族成员的 `id`），并在绘制时读取它：`const { value = 0 } = await $.state.get(count)`。这样的读取操作会为当前实例建立订阅关系；后续的 `$.state.set` 只会重新渲染那些已订阅的读者，因此无需再为此调用 `$.ui.invalidate`。渲染钩子绝不能直接写入状态（禁止在绘制过程中调用 `$.state.set`）；状态更新应通过事件处理函数或其他事件来触发，且绝不能基于绘制时捕获的值进行写入。例如：`import { update } from "claude-code"`，并设置 `onPress: () => update($, count, n => (n ?? 0) + 1)`，利用 `ifVersion` 在版本匹配时读取、应用并写入新值，即使在两次点击之间发生状态更新也能确保两次点击的结果都被正确记录。`atom(ref, initial)`、`derive(sources, fn)`、`memberOf(family, e)` 和 `read($, source)` 均来自同一模块。只有状态的所有者才能写入该值；其他插件若要修改它，需通过监听 `state.set` 事件，并使用 `plugin` 和 `key` 作为匹配条件，同时将新的 `value` 传递给回调函数。若需在会话结束后继续保留该值，还应将其写入 `$.store`。从表 `$.ui.resolve(e)` 返回的树：表面的元素构造函数，
被解构为钩子的 JSX 标签（模块没有全局元素）。各表面的表不尽相同，详见 `Elements`（`mobile` 没有 `Input`、`Select` 或 `Client`，`vscode` 没有 `Client`，`terminal` 没有 `Svg`，但独有 `Raster` 和 `Image`）；缩小 `e.surface` 的范围会相应缩小该表。由彩色单元格组成的网格（迷你折线图、热力图、渲染帧）是一个 `Raster`，其单元格按 `RasterProps` 打包，绝不会为每个单元格单独创建一个 `Box`；`$.ui.blit` 可在不重新渲染的情况下重绘已挂载的 `Raster`。一张图片（PNG 或 RGBA 字节，或另一本地进程写入的文件名或 POSIX 共享内存对象，按 `ImageProps`）是一个置于单元格盒之上的 `Image`：这是终端所支持的 kitty 图形协议（如 kitty、Ghostty），其 `alt` 在其他场合使用，或在终端无法读取本机文件时使用；新源可就地更新它，而带有键的则以帧率通过 `$.ui.blit({ requestId, key, source })` 进行切换，像素永远不会跨越 `$`。模型风格的文本（标题、列表、表格、代码块、链接；非 `https:`/`http:`/`file:` 的内容均作为文本绘制）是一个 `Markdown`，其绘制方式与助手回复相同。给定 `key` 和 `onLinkPress`，对它所绘制的链接（任意链接，或 `pressableLinks` 中命名的特定链接）进行一次普通点击，会触发 `ui.press` 事件，并携带该链接的 `href`，而非由表面直接打开链接；表面负责上报点击事件（例如全屏终端；Ctrl 或 Alt 点击仍会打开链接）。返回一棵树，或调用 `next({ ...e, props })` 来改变引擎的绘制内容，或调用 `next(e)` 保持原样。
若树无效（缺少表面支持的元素、传入了表面不接受的属性、在不允许嵌套子节点的地方出现了子节点），则不予绘制：引擎会自行绘制替代内容，并在调试日志中写入一行，以 `ui.render (<Component>): 钩子返回了一棵无效的树` 开头，后接具体原因。当会话热加载插件目录（启用热加载后为 mods 目录，或交互式会话监视的 `--plugin-dir` 或 `CLAUDE_CODE_PLUGIN_DIRS` 目录）时，每次加载也会在会话记录中注明组件及原因：`<plugin>: ui.render (<Component>) 被拒绝: <原因>; 引擎已自行绘制`，其中 `<plugin>` 是可能绘制该树的那个插件，其余情况归于 `hooks`；在其他任何会话中，只有调试日志会显示这一信息。某些值会被降级处理而非直接拒绝：`format: 'diff'` 的 `Code` 若其 `source` 无法解析为补丁块（如补丁切分至半块之间，或无 `@@` 头部），则会作为普通代码绘制，如同未指定 `format` 且无 `startLine` 一样，周围内容照常绘制；调试日志会予以说明，热加载插件目录时会话记录亦会记载，每次加载针对具体位置（某个窗格或带，以其实例计；会话记录中同一组件的多行视为一组）和对应的 Code：`<plugin>: ui.render (<Component>): Code <n> 作为普通代码绘制，其源并非统一差异格式: <原因>`，其中 `<n>` 表示该 `Code` 在树中按书写顺序排列的位置，若有路径则在其后标注 `(path "<path>")`。在树中，`Client` 的表面模块负责绘制时，会在 `ui.render (<Component>):` 后注明 `Client <module>`，每次加载分别记录模块和 Code。阅读时应重点关注该原因以及元素的属性类型。
按钮在终端上显示为 `[ label ]`，若设置 `plain` 则不加方括号：`1: label` 旁附其 `hotkey`，无快捷键时仅显示标签，因此单字标的按钮也是单字控制，焦点仍可反色显示；`variant="primary"` 标记主要操作（终端以强调色绘制 `[ label ]`，其他表面则采用各自的主视觉风格），`"secondary"` 或无标记为默认外观，`plain` 优先于此。`role="dismiss"` 仅作绘制提示，标记用于关闭所在界面的按钮：终端将其视同无此标记，桌面端则显示原生关闭控件。按钮、文本框和下拉选择器的处理器保留在插件中，并触发 `ui.press`、`ui.input` 和 `ui.select`；按键仅在控件获得焦点时生效，Esc 返回输入提示；按钮的 `hotkey`（一位数字或小写字母）可在其所在界面持有键盘时触发，按 Ctrl+X 后的选项卡或点击会激活对应按钮，窗格则与其相同，或通过 `focus` 打开；但若按钮指定了引擎的键绑定动作（如 `action: "app:cycleDiffBase"`），则在该动作的处理器挂载期间，用户也可通过提示中的组合键直接触发。通过 `focus` 打开、并设置 `closeOnEscape` 和 `holdToasts` 的窗格会表现为对话框：它会接管按键，Tab 和方向键可遍历其中的按钮，Esc 关闭窗口，吐司消息则在其后等待；设置了 `autoFocus` 的元素自始便占据焦点环，焦点环的每次移动都会首先触发 `ui.focus` 事件（其 `element` 即当前拥有焦点的元素，引擎的关闭标记除外；`{ deny }` 可阻止其发生），而 `$.ui.focus({ requestId, key })` 则可在界面持有按键时移动焦点环；`rows` 会以内联方式打开，高度根据内容需要调整（最多不超过布局允许的空间，且以用户自定义尺寸为准），因此短对话框可完整显示，其按钮可通过方向键遍历而非滚动查看；`command.run` 输入的 `presentation` 决定答案是否全屏显示，以及终端的宽度设定。带有键的 `Box` 可限定 `hover` 样式的作用范围，悬停作用域可在不同界面间分组元素；而设置了 `position: "absolute"` 并带有单元格偏移量（如 `top: -2, left: 2`）的 `Box` 会覆盖其周围内容而不使其移动，因此将 `display: "none"` 与 `hover: { display: "flex" }` 结合使用，即可实现鼠标悬停于某字标时上方出现卡片的效果。所有用户角色的会话记录行均为 `UserMessage` 界面：包括用户的输入提示、后台任务的通知（`e.props.task`：任务的 `id`、`status`、`durationMs`）以及其他代理、队友、会话或频道发送的消息（`e.props.from.name`），这些消息通过 `e.props.origin.kind` 区分，可用匹配器进一步筛选（如 `{ props: { origin: { kind: 'task-notification' } } }`）。若钩子绘制的是紧凑的自定义行，则在 `e.props.isExpanded`（Ctrl+O）时返回 `next(e)`，以便完整行仍能显示；而改写的 `text` 只会更改该行本身，绝不会影响模型读取的内容。斜杠命令的输出行是 `CommandOutput` 界面：插件通过 `command.run` 回答时，若返回 `{ text, context? }`（`text` 为模型同样读取的内容，`context` 仅为模型备注，记录于 `text` 之后），则可通过 `{ component: 'CommandOutput', props: { command: 'mine' } }` 将其钩住，并以树的形式内联绘制于会话记录中，取代原本内置命令的行。

## 对话所维护的行：session.append

`session.append` 本身就是追加操作：每当引擎向对话中添加一行时，都会以该行的发起者身份调用一次 `append`，而其底层则负责将该行存储下来。这些行包括：用户的提示、一条斜杠命令的记录及其输出、模型响应的每一部分、工具的执行结果及工具传递的行、被合并进当前回合的提示或通知、引擎注入的提醒与清单、设置钩子或链路的上下文、循环自身的推动信号、压缩操作的边界与摘要，以及在主对话和每个子代理中均可见的各类通知（事件的 `agentId` 标识了该子代理所属的循环）。每个列表的所有者都会追加由其产生的行（如交互式会话记录、无界面会话、子代理启动时的初始行），而查询循环则在其生成的每一行离开循环时进行追加；循环背后的所有者接收到的内容、会话文件中存储的内容，以及下一次请求发送的内容，都是该行经链路处理后的最终形态。绝不会出现仅属于某次请求的进度行，也不会有加载操作返回的行（如 `--resume`、传送、子代理的已保存会话）：加载不属于追加操作。同时，没有任何插件会挂钩“调用即存储”这一事件。

事件的 `door` 属性标识了该行进入的路径（`prompt`、`command`、`response`、`tool-result`、`tool-message`、`delivery`、`attachment`、`hook-context`、`note`、`compaction`、`notice`）；`origin` 表示引发该行的主体（提示的发送者、`{ kind: 'model', model }`、`{ kind: 'tool', tool }`、引擎自身、设置钩子、插件）；`uuid` 则是该行在会话记录中的唯一标识。其 `message` 即为该行本身：包含 `type`、`name`（附件的类型、通知的子类型）、`role`（对于不由请求携带的行，该字段为空）、`isMeta` 以及 `content`——即按照 Messages API 的定义组织的各个区块。因此，由请求携带的行的 `{ role, content }` 实际上就是一个 API 消息。除 `content` 外，其余字段均为固定值：若省略，则予以保留；若更改，则钩子失效并被跳过。

钩子通过 `next({ ...e, message })` 来重写 `content`：文本区块（可编辑、新增、删除、重新排序），以及工具结果的 `content` 和 `is_error`（对于未附带 `tool_use_id` 的工具结果，按顺序各占一个位置；若无错误，则保留该行的标记）。图像或文档区块可以被删除或移动，但不能被修改或新增。钩子置于所有固定区块之前插入的文本，应紧随该行原有的思考区块或工具结果之后，因为这些内容是请求最先需要的部分。钩子的最后一步必须原样返回记录所依赖的内容：思考区块、已脱敏的思考区块、工具使用区块，以及所有非其创作的区块，均须完整且保持原位；此外还需保留每个工具结果的 ID 及其集合。若 `content` 留空，则表示钩子可能删除的所有区块都将被移除：固定的区块会被恢复，而若最终留空，则会以引擎对空消息的默认表述 `(no content)` 存储，绝不会采用钩子所删除的内容。对于按请求渲染或携带媒体的附件，其重写仅用于调试日志记录，实际存储的行仍保持原始状态。`next(e)` 在行被存储后才会解析 `{ message, uuid }`；若钩子在不调用 `next` 的情况下直接返回，则该钩子会被跳过，行则予以保留：引擎追加的行绝不会被拒绝。引擎后续对已保留行的修改（如将工具结果缩减至预算范围、清除提示、执行压缩等），纯属引擎内部事务，不属于追加操作。在一次会话钩子中，当一条消息链执行完毕后，该行记录即被存储；会话中的追加操作严格按照其发生顺序进行。引擎从同步回调（通知）中追加的行，因此会出现在其所属消息链之后；而那些立即读取消息列表的地方（例如构建首次请求的回合），则会等待此前已完成的追加操作。工具调用的结果以结构化记录的形式与对应的 tool_result（即界面上显示的内容）一同存储，同时还会保存该行的时间戳和父级链接，以及附件的有效载荷。此外，消息队列在消息入队时对其 prompt 的记录（即转录文件中的 queue-operation 条目）也会被原样存储——但这并不属于会话本身的一条消息：如果某个插件需要在各处修改 prompt 的内容，则应在 prompt 提交阶段（prompt.submit）完成重写，即在消息入队之前进行。

`$.session.append({ message: { type, content }, agentId? })` 是来自插件的相同分发调用，并且会真正执行追加操作：无论是用户角色的消息行（type: "user"，标记为 isMeta 存储，模型会读取它），还是通知消息（type: "system"，单个文本块，模型不会读取它），在本版本中仅支持文本块类型，均可追加到主会话或正在运行的子代理会话中，带有 origin: { kind: 'plugin', name } 和 note 标记，以及由引擎生成的唯一 ID。该行会立即出现在消息列表中，并在下一次循环开始时进入当前回合的请求队列。底层会拒绝任何其他消息行或文本块、未指向当前运行循环的 agentId，以及任何不由插件控制的运行（例如已通过设置关闭的循环，或作为委托观察启动的循环），并给出拒绝原因（调用将返回该原因）。存储的用户消息行会携带插件名称作为来源，以便后续阅读转录时能够知晓是谁追加了这条消息。位于更高层级的插件可以像处理其他消息行一样对其进行改写，或者通过返回 { deny: reason } 而非 next 来拒绝它（在 next 之后消息行才会被存储，此时再拒绝则会导致钩子失败）：此时调用将解析为 { deny }，且不会有任何内容被存储。钩子的最终结果是其 next 返回的内容，即已存储的消息行或来自下层的拒绝，且保持原样不变：若传入的是另一条消息行，则该钩子将直接失败。这就是 session.append 钩子唯一可以拒绝的消息行；在组织将策略插件置于何处，该事件便会如同 prompt 事件一样，越过个人插件继续传播。

```js
on("session.append", ($, e, next) => next({ ...e, message: redact(e.message) }))
  .catch(($, e, next) => next({ ...e, message: placeholderFor(e.message) }))
```

## 超出单次分发范围的工作一个钩子会在一次调度中运行，并拥有自己的时间预算（正在执行的 `next` 或 `$` 调用不算在内；而 `$.clock.sleep` 算，因此使用它进行轮询的 `turn.step` 生成器会从其唯一的预算中为每次休眠付费），当该调度被放弃时（用户中断、其他钩子先完成、预算耗尽），`next.signal` 会触发中止；为该调度启动的所有任务都应随之停止。那些需要跨越多次调度持续运行的工作应当放在别处：从 `session.start` 钩子中启动，该钩子在会话就绪时仅触发一次，并且在首个提示前会被等待（因此在那里等待的 `$.tool.register` 会在第一轮就被列出），然后通过 `$.clock.every` 和 `$.clock.after` 继续运行，它们的计时器会一直运行，直到被取消或模块重新加载。`$.prompt.submit` 会将一个提示加入队列，待会话空闲时启动一轮新的对话（绝不会并入正在进行的轮次；调用在该轮开始时 resolve，而非结束时），从而允许后台工作唤醒处于静默状态的会话。`$.model.complete({ model, prompt })` 会在会话自身的客户端上执行一次无历史记录的文本补全，并始终返回一个结果对象（`ModelCompleteResult`），绝不会直接返回纯字符串，也不会因提供商的行为而 reject：如果已回答，则包含 `text` 和 `usage`（`ModelUsage`，即 API 所定义的四种 token 计数——与 `session.compact` 的结果、`turn.complete` 的 `usage` 以及上下文分解中的 `apiUsage` 一同报告调用成本）；若未回答，则包含 `isAnswered: false` 以及 `reason`，可能为 `api-error`（含 HTTP 状态码和错误类型，但不含错误详情）、`empty-reply` 或 `aborted`（因超时 `timeoutMs` 到期，或发起调用的调度被放弃），每种情况均附带 `usage`；只有当引擎拒绝发送请求时（如模型被屏蔽、`maxTokens` 设置不合理）才会 reject。`$.model.fork({ prompt })` 会以主线程上次发送的完整对话为上下文，提出一个不依赖工具的问题，使用相同的模型和系统提示，因此 API 会从其提示缓存中提供该前缀内容（`usage.cache_read_input_tokens` 表明已服务了多少 token）；其结果同样包含上述几种情况，外加 `nothing-to-fork`（新会话尚未开始第一轮，或刚执行过 `/clear` 后再次尝试）；其 `aborted` 意味着发起 fork 的钩子所在的轮次在 fork 进行时被中断。`$.ui.status`、`$.ui.toast` 和 `$.ui.log` 可在不启动新轮的情况下显示状态，`$.ui.copy({ text, surface })` 会将文本复制到调用者指定的界面上（按下事件的钩子会传入 `e.surface`；若未指定，则为会话的第一个界面）：终端通过机器的剪贴板工具和 OSC 52 实现，resolve 结果为 `{ isCopied: true }`；若目标界面不可用，则返回 `{ isCopied: false, reason }`，可能是 `no-clipboard` 或无任何可绘制的内容 `no-surface`；事件 `ui.copy` 会携带目标 `surface`，因此钩子可以修改、拒绝或接管该操作。`$.store` 可跨会话保存值，`$.session.version()` 返回引擎的版本信息，包括基础发行版和构建时间（这些数据也由引擎自身的分析系统记录，适用于所有模式和版本），而 `$.process.run` 则按 argv 执行宿主命令。`$.fs` 可读取（文本或以 `{ as: 'bytes' }` 格式获取 base64 编码的数据）、写入、列出目录及获取文件/目录的元数据；`$.fs.stat(path, { resolve: true })` 还会返回 `realPath`，即解析所有符号链接和 `..` 引用后的真实路径（与 `realpath` 的结果一致：硬链接、`/.vol/` 文件 ID 或大小写别名都会保留其原始路径表示），因此安全防护的最佳做法是在同一根目录下，对解析后的 `realPath` 建立白名单，而对于路径表示本身则采用尽可能严格的黑名单策略。`$.ui.selection()` 返回用户在全屏终端中最后一次用鼠标选中的内容，格式为 `{ text, requestId? }`：其中 `text` 是复制时会获取的文本，`requestId` 是该文本所在转录行的 ID，即该行 `ui.render` 中读取的 `e.requestId`（如果文本跨多行或位于转录之外，则不存在）。按下按键或点击会先取消高亮，然后再执行命令或触发操作，因此返回值会保持为用户上次的选择，直到他们再次选择、清除选择，或下一条提示/命令执行完毕：无论是用户输入的命令，还是点击的按钮，都会读取该选择。如果在一轮对话进行中输入了一条提示并将其合并到本轮对话中，则该提示不算单独的一次执行；选择状态会一直保留，直到下一轮执行完成。如果没有选择，则返回 `undefined`；当引擎未检测到任何选择时（如未启用全屏模式、使用 `-p` 参数或在远程界面中），也会返回 `undefined`。以下是一个将选择内容插入提示的命令示例：

```js
export function register(on) {
  on('session.start', async ($, e, next) => {
    await $.command.register({
      name: 'quote',
      description: '将当前选中的内容插入提示。',
    });
    return next(e);
  });
  on('command.run', { command: 'quote' }, async $ => {
    const selected = await $.ui.selection();
    if (selected === undefined) return { text: '当前未选中任何内容。' };
    const quoted = selected.text.replace(/^/gm, '> ');
    await $.prompt.fill({ text: quoted + '\n\n', mode: 'insert' });
    return { text: '已将选中的内容插入提示。' };
  });
}
```

## 模型可调用的工具与代理类型

`$.tool.register` 用于注册一个工具：指定其名称、模型可见的描述以及输入参数的 Schema；注册后的工具会以 `mcp__<plugin>__<name>` 的形式列出。插件通过监听 `tool.call` 事件，并使用匹配器 `{ tool: 'mcp__<plugin>__<name>' }` 来提供实现，若无匹配的钩子则调用失败。重复注册同名工具会替换原有定义；一个插件可以注册多个工具，每个工具都会按注册顺序列出。`$.agent.register` 以相同方式注册代理类型，格式为 `<plugin>:<name>`，基于代理定义的 JSON 配置（包括提示模板、可用工具、所用模型等所有配置项）；插件目录下的 `agents/*.md` 文件也可以用来声明这些代理。`$.agent.spawn({ subagentType })` 用于启动一个代理，其返回值为 `turn.complete`。如果插件提供了 `agent.offer` 钩子并返回 `{ isOffered: false }`，则该代理不会被模型调用，但插件自身仍可继续运行该代理。
