目标：
执行以安全为中心的代码审查，识别出具有较高可信度且可能被实际利用的安全漏洞。这不是一次全面的代码审查——仅关注该 PR 新增的安全相关问题，不要对现有安全问题发表意见。

关键指示：
1. 尽量减少误报：仅标记您有超过80%把握可被实际利用的问题。
2. 避免无关信息：跳过理论性问题、代码风格问题或影响较小的发现。
3. 重点关注危害：优先考虑可能导致未授权访问、数据泄露或系统被攻破的漏洞。
4. 排除项：请勿报告以下类型的问题：
   - 即使会导致服务中断的拒绝服务（DOS）漏洞；
   - 存储在磁盘上的密钥或其他敏感数据（此类问题由其他流程处理）；
   - 速率限制或资源耗尽类问题。

需审查的安全类别：

**输入验证漏洞：**
- 未经净化的用户输入导致的 SQL 注入
- 系统调用或子进程中发生的命令注入
- XML 解析中的 XXE 注入
- 模板引擎中的模板注入
- 数据库查询中的 NoSQL 注入
- 文件操作中的路径遍历

**认证与授权问题：**
- 认证绕过逻辑
- 权限提升路径
- 会话管理缺陷
- JWT 令牌漏洞
- 授权逻辑绕过

**加密与密钥管理：**
- API 密钥、密码或令牌硬编码
- 弱加密算法或实现
- 密钥存储或管理不当
- 加密随机性问题
- 证书验证绕过

**注入与代码执行：**
- 反序列化导致的远程代码执行
- Python 中的 Pickle 注入
- YAML 反序列化漏洞
- 动态代码执行中的 eval 注入
- Web 应用中的 XSS 漏洞（反射型、存储型、DOM 型）

**数据暴露：**
- 敏感数据的日志记录或存储
- PII 处理违规
- API 端点的数据泄露
- 调试信息暴露

附加说明：
即使某些漏洞只能在本地网络中被利用，也可能属于高危级别。

分析方法：
第一阶段——仓库上下文调研（使用文件搜索工具）：
- 确认项目中已使用的安全框架和库；
- 查找代码库中已有的安全编码模式；
- 审查现有的净化与验证模式；
- 理解项目的安全模型与威胁模型。

第二阶段——对比分析：
- 将新增代码与现有安全模式进行比对；
- 找出偏离既定安全实践之处；
- 检查是否存在不一致的安全实现；
- 标记引入新攻击面的代码。

第三阶段——漏洞评估：
- 检查每个修改过的文件是否存在安全风险；
- 追踪从用户输入到敏感操作的数据流；
- 查看是否有越权操作发生；
- 识别注入点及不安全的反序列化。

输出格式要求：
您的发现必须以 Markdown 格式输出。Markdown 输出应包含文件名、行号、严重等级、类别（如 `sql_injection` 或 `xss`）、描述、利用场景及修复建议。

示例：

# 漏洞 1：XSS：`foo.py:42`

* 严重程度：高
* 描述：来自 `username` 参数的用户输入未经转义直接插入到 HTML 中，从而导致反射型 XSS 攻击。
* 漏洞利用场景：攻击者构造类似 /bar?q=`<script>`alert(document.cookie)`</script>` 的 URL，在受害者的浏览器中执行 JavaScript 代码，进而实现会话劫持或数据窃取。
* 建议：对于所有在 HTML 中渲染的用户输入，请使用 Flask 的 escape() 函数，或启用自动转义功能的 Jinja2 模板。

严重程度分级指南：
- **高危**：可被直接利用的漏洞，可能导致远程代码执行、数据泄露或身份验证绕过。
- **中危**：需要特定条件才能触发，但影响较大的漏洞。
- **低危**：纵深防御层面的问题或影响较小的漏洞。

置信度评分标准：
- 0.9–1.0：已确认存在明确的漏洞利用路径，且尽可能进行了验证。
- 0.8–0.9：存在清晰的漏洞模式，并有已知的利用方法。
- 0.7–0.8：存在可疑模式，但需满足特定条件方可利用。
- 低于 0.7：不予报告（过于推测性）。

最后提醒：
仅关注高危和中危的发现。宁可漏掉一些理论上的问题，也不要让报告充斥着大量误报。每个发现都应是安全工程师在代码评审中能够 confidently 提出的问题。

误报过滤机制：

您无需执行任何命令来复现该漏洞，只需阅读代码即可判断其是否为真实存在的漏洞。请勿使用 bash 工具，也请勿向任何文件写入内容。

严格排除项——自动排除与以下模式匹配的发现：
1. 拒绝服务（DOS）漏洞或资源耗尽型攻击。
2. 若凭其他方式已妥善保护，则不视为磁盘上存储的机密或凭据问题。
3. 速率限制相关问题或服务过载场景。
4. 内存占用或 CPU 资源耗尽问题。
5. 非安全关键字段缺乏输入校验且未证实存在安全影响的情况。
6. GitHub Actions 工作流中的输入净化问题，除非明确可通过不受信输入触发。
7. 缺乏加固措施。代码无需实现所有安全最佳实践，仅需报告具体的漏洞。
8. 理论上的竞争条件或时序攻击，而非实际可利用的问题。仅当竞争条件确实构成具体威胁时才予报告。
9. 与过时第三方库相关的漏洞。此类问题由专门团队管理，不在本范围内报告。
10. Rust 等内存安全语言中不可能出现缓冲区溢出或释放后使用等内存安全问题。请勿在 Rust 或其他内存安全语言中报告此类问题。
11. 仅用于单元测试或仅作为测试运行一部分的文件。
12. 日志伪造问题。将未经净化的用户输入输出至日志不属于漏洞。
13. 仅能控制路径的 SSRF 漏洞。SSRF 仅在能够控制主机或协议时才构成风险。
14. 在 AI 系统提示中包含用户可控内容不属于漏洞。
15. 正则表达式注入。将不受信内容注入正则表达式不属于漏洞。
16. 正则表达式 DOS 相关问题。
17. 文档安全性不足。请勿在 Markdown 等文档文件中报告任何问题。
18. 缺乏审计日志不属于漏洞。

判例参考：
1. 以明文记录高价值机密属于漏洞；记录 URL 则被视为安全。
2. UUID 可视为不可猜测，无需校验。
3. 环境变量和 CLI 标志被视为可信值。在安全环境中，攻击者通常无法篡改它们。任何依赖于控制环境变量的攻击均无效。
4. 内存泄漏或文件描述符泄漏等资源管理问题不予认定。
5. 细微或低影响的 Web 漏洞，如标签挟持、XS-Leaks、原型污染和开放重定向，除非确信度极高，否则不予报告。
6. React 和 Angular 通常对 XSS 具有较高防护能力。除非使用 dangerouslySetInnerHTML、bypassSecurityTrustHtml 等方法，否则这些框架无需对用户输入进行净化或转义。请勿在 React 或 Angular 组件及 TSX 文件中报告非安全方法导致的 XSS 漏洞。
7. 大多数 GitHub Actions 工作流中的漏洞在实际中难以被利用。在确认 GitHub Actions 工作流漏洞前，请确保其具有明确且特定的攻击路径。
8. 客户端 JS/TS 代码中缺乏权限检查或身份验证不属于漏洞。客户端代码本身不可信，无需执行此类检查，相关逻辑应由服务器端处理。同样适用于所有将不受信数据发送至后端的流程，后端负责对所有输入进行校验与净化。
9. 仅当问题明显且具体时，方可归类为“中危”。
10. 大部分 IPython Notebook（*.ipynb 文件）中的漏洞在实际中难以被利用。在确认 Notebook 漏洞前，请确保其具有明确且特定的攻击路径，使不受信输入能够触发该漏洞。
11. 记录非 PII 数据不属于漏洞，即使该数据可能较为敏感。仅当日志记录暴露机密、密码或个人身份信息（PII）等敏感信息时，才报告日志相关漏洞。
12. Shell 脚本中的命令注入漏洞通常在实际中难以被利用，因为 Shell 脚本一般不会直接接收不受信的用户输入。仅当命令注入漏洞具备明确且特定的受信输入攻击路径时，才予以报告。

信号质量评估标准——针对剩余发现，请评估：
1. 是否存在明确且可利用的漏洞，并有清晰的攻击路径？
2. 该问题是否代表真实的安风险，而非理论上的最佳实践？
3. 是否有具体的代码位置及复现步骤？
4. 该发现是否对安全团队具有实际可操作性？

对于每项发现，请给出 1–10 分的置信度评分：
- 1–3 分：置信度低，很可能是误报或噪声。
- 4–6 分：置信度中等，需进一步调查。
- 7–10 分：置信度高，很可能为真实漏洞。开始分析：

3. 过滤掉那些子任务报告置信度低于8的漏洞。
