# 评估健康检查清单

每当一个评估正在被**构建**（`build-eval.md`）或**攀登**（`eval-hillclimb.md`）时，此文件都会被加载。它有两个作用。在编写评估时，下面的每一项都是构建要求——你生成的跑者、评分器和案例集应当默认满足这些要求，而不是等到有人指出问题后再去修正。当用户带来一个已有的评估时，这是你在其基础上构建任何内容之前需要执行的一次验证检查。无论哪种情况，在第一次完整付费运行以及攀登的第一轮之前，都应再运行一次该检查。

在信任某个评估来判断哪个模型、提示或配置更好之前，请先确认该评估本身是可靠的。一个有缺陷的评估会给出看似可信却指向错误方向的结果；而在有缺陷的评估上进行攀登，只会让误导更加严重：你会“改进”一个伪成果，最终却一无所获。实际上，那些最令人惊讶的评估结果往往源于评估本身的漏洞，而非模型的真实特性，因此事先花一小时进行审计，通常能节省数天用来追踪虚假差异的时间。

检查分为以下几类：**任务设计**（案例是否合理？）、**框架设计**（支撑代码是否正确？）、**指标规范性**（成本和延迟是否测量准确？）、**评分器设计**（评分机制是否合理？），以及**能否检测到预期的变化**（信号是否足够支持决策？）。这些检查以直接指令的形式给出：对于每项检查，都要查看评估的实际代码、配置和数据，而不是它的README文档。最后一节“**向用户报告发现**”则说明如何传达你的发现；检查本身是陈述性的，但对人类的报告应以观察和建议为主，因为评估的作者通常掌握着一些局外人可能会质疑的选择背后的背景信息。

在进一步审计之前，先在少量案例上端到端地运行一次评估，或者找到一份最近的运行结果文件。许多关于评估质量的讨论，其实是因为代码目前无法正常运行。

## 1. 任务设计

这些检查关注的是案例本身：究竟在问什么、什么才算正确，以及整个案例集是否能够区分被比较的系统。

### 大规模审计案例集

框架和评分器是你可以从头到尾阅读的代码；而案例集可能包含数百个条目，难以逐一细读。不要试图逐行查看每个案例。可以按以下三个层次开展工作：

**第一层：针对全集的程序化检查。** 编写一段简短脚本，加载所有样本并输出：完全重复与近似重复的比例；标签或类别分布的均衡性；提示长度与预期答案长度的分布；Schema 的有效性及缺失字段的数量；以及明显格式错误的行。这种检查成本低、覆盖全面，无论数据集规模大小，都能发现分布偏差、重复样本、截断问题和损坏的记录。

**第二层：分层抽样进行细致核查。** 从数据集中抽取20至50个样本，若存在 `tags[0]` 字段，则按该字段分层抽样，否则进行均匀随机抽样，并对这些样本逐一执行下文的逐条检查。同时建议用户自行抽查其中若干样本——人工复核能够发现清单式检查无法察觉的问题。（这就是构建-评估输入确认环节的作用；报告中的逐条表格即为这一过程的可视化界面。）

**第三层：逐条 LLM 审计。** 对于超过数百条样本的数据集，为每条样本单独调用一次模型，使用严格的审计提示生成结构化判断，并进行汇总。在执行前先征询意见——其成本大致相当于 N 次低成本模型调用——并明确告知：“我可以对全部 N 条样本进行逐条审计，费用约为 X 美元。需要我执行吗？”一个适用于单个案例的审计提示（请根据评估方案的字段名称进行调整）：

```
您正在对评估集中的一个单个案例进行审计。根据提示、参考答案以及评分者判定通过/不通过的标准描述，请标记以下任何一种情况。请保持谨慎——仅在有充分把握时才进行标记。

提示：
{prompt}

参考答案：
{gold}

评分者行为：
{grader_description}

对于每个问题，如果为“是”，请回答“是/否”，并附上简短的理由（1行）：
- 模糊：两位严谨的专家是否有可能对正确答案产生合理分歧？
- 参考答案存疑：参考答案看起来是否错误、不完整或存在争议？
- 无需思考即可作答：知识储备丰富的模型是否可以在不完成预期任务的情况下直接给出答案？
- 评分过严：是否存在明显正确的答案，但按描述的评分标准会被判定为错误？
- 评分过宽：是否存在明显错误的答案，但按描述的评分标准会被判定为正确？
- 易于作弊：是否存在某种捷径，能够在不解决任务的情况下满足评分要求？
- 其他：是否有其他因素会导致该案例的评估结果具有误导性？
```返回 JSON：{"case_id": "...", "flags": {"ambiguous": {"flagged": 布尔值, "reason": "..."}, ...}, "overall": "ok" | "review" | "broken"}
```

按标记类型聚类，将最突出的问题及其示例用例 ID 汇总并纳入报告（§6）。

逐个用例的检查（适用于二级样本）：

- **明确的成功标准。** 如果向两位独立的领域专家展示同一输出，他们是否会就通过或不通过达成一致？如果标准允许合理的分歧（如“写出一份*好*的摘要”），则评分更多反映的是评分者的主观意见，而非模型的能力。注意双重失败：要么规范过于宽松（遗漏了必要的输出、文件名或格式要求），要么过于严苛（提示成了分步操作指南，让模型无从发挥）。

- **存在且通过的参考答案。** 每个用例是否至少配备一个能真正通过评分的标准答案？如果所有变体的通过率均为 0%，这通常是用例本身存在问题，而非题目难度过高。可通过运行参考答案进行抽查。

- **真值标签正确。** 抽取十个用例，独立重新推导预期答案。广泛使用的基准数据集往往存在显著的标签错误；错误标签会限制可测量的准确率，而这与模型本身无关。

- **真值来源是什么？** 询问并记录来源标签：人工编写、人工验证，或**来自某模型——是哪个模型**。若预期答案出自某个模型，则基于参考匹配的评分奖励的是对原模型的模仿，而非正确的答案；这种情况在迁移场景下尤为严重，因为源自旧模型的黄金答案会让旧模型看起来表现最佳，并因任何风格上的差异惩罚新模型。此时应优先采用评分细则或两两比较的方式，而非单纯比对参考答案；或者先由人工核查部分参考答案。切勿在 A 与 B 的对比评测中使用 A 模型的输出作为黄金标准。

- **无标注伪迹。** 是否存在一种简单基线，仅凭表面模式（如问题长度、关键词、选项顺序）就能获得高分，而无需真正解决任务？若空操作或多数类基线得分远高于随机水平，则该评测实际上是在衡量某种伪迹效应。

- **提示中存在标签泄露。** 预期答案或其近义表述是否出现在模型可见的任何位置——提示、少样本示例、系统消息、工具描述，或代理可读取的文件中？这种现象常见于直接从黄金数据集中复制粘贴构建的少样本设置。

- **可凭记忆作答。** 对于涉及真实命名实体的用例，模型是否能在参数化记忆中找到答案，即使本意是测试检索或工具调用能力？若目标是评估模型能否*完成任务*，则测试对象应足够冷门或合成，以避免仅靠记忆就能得分。

- **难度源于问题本身，而非提示。** 看似困难的用例是否只是表述晦涩？如果是这样，那么得分反映的是解码提示的能力。建议以更直白的方式陈述问题，让真正的难度体现在问题本身。

- **代理类用例：症状而非调查。** 对于要求代理诊断或修复问题的用例，提示中已提供了多少调查信息？若提示中已包含日志行、失败测试名称或相关文件，则评测实际是在考察模型是否能读懂提示，而非发现提示。应提供用户可能上报的内容，让代理自行获取其余信息。

- **分布与交互形态符合实际。** 将少量用例与生产流量进行对比。同时检查*交互形态*：单轮评测无法捕捉那些仅在长对话或多轮交互或代理场景中才会显现的效果，反之亦然。提前指出任何明显差异，以便读者判断结果的适用范围。

- **难度空间。** 若已有评测结果，需关注分数分布。若基线得分已达约 95% 以上，则评测难以区分顶尖模型，后续优化大多只会带来成本或延迟的提升——虽有帮助，但应事先说明。若所有模型得分均接近 0%，则往往是用例或评分机制存在缺陷，而非任务本身不可完成。

- **饱和评测及其最终衡量内容。** 接近满分时，剩余的方差主要由格式细节、评分规则的微小差异或轻微的奖励机制利用主导，而非模型的真实能力。应标明最后几分可能不再反映评测初衷，并建议增加更具挑战性的题目。

- **类别平衡。** 对于分类评测，需检查标签分布；在报告模型得分的同时，也应列出多数类基线的得分。当正负样本均存在时，应优先关注精确率、召回率和特异性，而非仅看准确率。

- **双向覆盖。** 用于评测“代理在必要时是否进行搜索”的用例，也应包含“代理在不应搜索时是否停止搜索”；否则，总是搜索的模型会得满分，而单侧评测会导致优化方向偏颇。拒绝、工具使用和升级处理同样如此。

- **一题一能力（当诊断重要时）。** 同时需要检索、推理和格式化的用例，只要其中任一部分失效，整体得分即为 0。这可用于得出总体结论，但若用户希望了解不同变体之间的差异原因，则应予以标注。

- **反向题目作为烟雾测试。** 当某一明显较弱的变体在某道题上得分高于明显较强的变体时，这通常是用例或评分机制的错误，而非真实的反常现象——这是值得仔细排查的地方。

- **过时性。** 若用例引用实时信息（价格、日期、API 响应、库版本等），这些黄金答案最近一次何时被验证？当前正确的答案可能会因使用过时的参考而被判为错误。

- **对于生成的用例：修复生成器，而非过滤器。** 当用例来自流水线时，输出中的问题往往是上游环节的体现；仅修补个别条目无法根除同类缺陷。应调整生成器并重新生成。

## 2. 运行框架设计

这些检查针对模型调用周边的代码。核心的失败模式是**混淆**：只要非模型因素——基础设施故障、响应截断、工具异常、重试延迟——与真实的模型结果混在同一列，评测就会把属于底层设施的问题归因于模型。

- **基础设施故障与模型故障分离。** 运行程序如何处理超时、重试后仍出现的 API 或限流错误、无法解析的输出、响应因达到 `max_tokens` 而被截断、工具抛出异常、评分程序自身失败等情况？若上述情况被静默计为 0 分（或视为通过），并与真实答案混在一起，则整体结果会被污染。未能产生可评分输出的尝试应被记录到 `errors.jsonl` 辅助文件中，并注明故障类别（运行/服务错误、超时、服务模型不匹配），绝不能计入 `results.jsonl`，以免占用 `(case, rep)` 单元格、阻断续跑，并将底层问题误算为模型故障。成功产生输出的行应标注 `stop_reason` 和 `status: truncated`，以表明响应因达到 `max_tokens` 被截断，从而统计这部分答案，但不将其计入平均分。拒绝应被视为一种评分结果，而非错误——单独记录为一项指标，避免将拒绝零与能力零混为一谈。

- **“无回答”不等于“否定回答”。** 评分程序是否能区分模型*明确给出否定结果*（如“未发现漏洞”）与模型*未能产生回答*（为空、崩溃、被截断、无法解析）？若两者被归为同一标签，则对每个输入都报错的运行程序与谨慎地未发现任何结果的程序得分相同。应在检测、分类和检索评测中留意这一点，因为“无”可能是有效答案。

- **每次试验状态干净且隔离。** 每个 (case, rep) 是否都从全新环境开始——没有前次试验遗留的文件、行、Git 历史、环境变量或缓存结果？共享状态会将一个用例的副作用泄漏到另一个用例的得分中，使代理读取到先前运行留下的提示，并导致结果依赖于运行顺序。- **环境完整且可用。** 环境是否确实具备任务所需的一切——依赖项、测试数据、可访问的服务？如果某个案例在所有变体中都因缺少某个软件包而失败，则应将其归因于环境问题，而非刻意设置的障碍。

- **确定性初始化。** 未加种子的随机性、可能影响模型或评分器的无序迭代、依赖于时间戳的路径、未设置固定种子的随机模拟器等，都会引入与被测系统无关的运行间差异。应固定随机种子，对顺序敏感的内容进行排序，并使用与生产环境一致的采样参数。

- **将脚手架限制与模型限制区分开来。** 缺少工具、步数预算过紧、过早放弃的重试策略，或会丢失上下文的模板，从外部看都可能被误认为是模型的能力不足。在可行的情况下，固定模型并调整脚手架（或反之），以便将结果准确归因于相应的层次。

- **令牌和上下文限制不会截断任何案例。** 将最长的提示和最长的合理正确答案与配置的上下文窗口及 `max_tokens` 进行比较。截断很容易被误判为模型主动停止；它必须以 `status: truncated` 的形式明确标识，而不是作为错误答案返回。

- **瞬时错误采用抖动退避机制重试，并记录重试次数。** 未重试的 429/529 错误会表现为虚假失败，可能导致某个变体或某一时段的表现看起来更差；而零延迟的重试循环则更为严重——它会在无形中成倍增加成本，甚至可能将一个 429 错误演变为整个批次的中断。应采用带抖动的退避策略，限制重试次数，并在每条记录中注明重试次数，以便在分析时排除重试对延迟的影响，并使“实际执行的尝试次数与计费的尝试次数”这一指标既体现在数据中，也清晰可见于账单。

- **为每个案例设置硬性的时钟上限，且与流式连接的存活状态无关。** 卡住的流式连接可能会无限发送保活消息，从而绕过非活动超时机制；只有对案例总耗时设置上限，才能真正释放工作进程。当该上限触发时，该次尝试应被记录为超时（`errors.jsonl`），绝不能记为零分。

- **提供请求的模型正是所要求的模型。** 在冒烟测试中从响应中读取 `model` 字段，并在每次调用中加以断言——除了文档中规定的别名到快照的解析外，任何不匹配（如供应商回退或容量重路由）都应被视为明显的失败。由错误的模型提供的评分毫无意义，而静默替换可能在其他地方也无法被发现；若供应商提供了用量或计费记录，应定期对汇总数据进行交叉核验。

- **评估配置与生产配置一致。** 对比评估环境中的系统提示、工具定义、模型版本、采样参数以及脚手架，与实际部署的配置是否完全一致。运行程序必须调用应用的真实入口；自行实现的调用会无声地测量一套不同的配置。

- **完整保存每个案例的轨迹。** 记录每个消息、工具调用及其结果、错误，以及评分器的输入和输出，按（案例，重复次数）粒度存储，以便在出现意外评分时，无需重新运行即可追溯到模型本身的问题或评估中的缺陷。这是提升评估可调试性的最有效做法，也是报告“转录本”标签页所呈现的完整视图，以及每个案例行所链接的精简版内容。

- **多次试验并报告方差。** 单次重复只是一个点估计，没有误差范围；小于运行间波动的差异并无实际意义。运行程序必须支持多重复，并且报告的数值应附带置信区间。

- **随时间可复现。** 依赖项需固定，案例集与评分器版本需同步管理，环境需明确定义。评分器变更前后的得分不可直接比较。- **在已知良好和已知不良样本上测试评估框架。** 在首次完整跑通之前，先将（a）一个“预言机”——即参考答案，或一个理应获得接近100%得分的变体——以及（b）一个空基准——空输出、固定答案或多数类——分别通过整个流水线。如果预言机未通过，则说明评估框架或评分器有误；若空基准未被判为失败，则说明评分器过于宽松。只需两次运行，耗时数分钟，就能在正式跑通前发现大多数连接错误。

## 3. 指标规范性

仅凭通过率往往难以回答用户真正关心的问题，即“在给定成本和延迟下，我能获得怎样的质量？”务必确保每个性能指标反映的是被测模型本身，而非外围环境。

- **使用 API 返回的 token 计数，而非估算值。** 从响应的 `usage` 字段中获取每条记录的输入、输出、缓存读取和缓存写入 token 数量。字符串长度的估算误差足以导致成本对比结果出现反转。

- **根据实际记录的 token 数量及该条记录的真实模型计算成本**——包括缓存利用率——切勿采用固定的假设费率；同时单独记录评测者的成本（`judge_model`、`judge_usage`），以免掩盖或弱化不同变体之间的差异。

- **各变体间的缓存命中率应具有可比性。** 若一个变体在缓存预热状态下运行，而另一个在冷启动状态下运行，则成本和延迟的差异部分源于运行顺序的影响。对于缓存读取比例存在显著差异的情况，应予以标注。

- **按正确的边界测量延迟。** 仅计时最终成功的请求；客户端重试、退避等待、本地队列管理（由信号量控制）以及后处理步骤均不应计入模型延迟列（如有需要，可单独记录总耗时）。否则，任何遭遇更多临时性错误的变体都会显得更慢。

- **针对代理型评测提供逐次调用的细分数据。** 记录每次模型调用及每次工具调用的 token 数量、成本和时间，而不仅仅是每轮的结果，否则就无法区分是模型慢还是工具慢。

- **性能指标与质量指标并列报告**，以绝对数值呈现各变体的数据——这样质量与成本、质量与延迟之间的权衡关系一目了然，而非隐含推断。

## 4. 评分器设计

这些检查针对的是将输出转化为分数的函数——无论是精确匹配、单元测试、终态检查，还是 LLM 评测。

- **评分器与提示的一致性。** 评分器是否奖励了提示所要求的内容？常见偏差：提示要求“至少 X”，而评分器只对严格大于 X 的情况才判为通过；提示要求解释，但评分器只检查数字。这会惩罚那些严格遵循指令的模型。

- **评分结果，而非路径。** 评分器奖励的是得出正确答案，还是走出了特定路径？如果强制要求完全一致的工具调用序列、措辞或中间步骤，那么以其他有效方式解决问题的模型就会被判不合格。应确认答案正确且合理，而不应限定实现路径。

- **对于作用于外部环境的代理，应评价最终状态，而非对话记录。** 将任务置于一个可丢弃的工作空间中执行，然后以程序化方式评估其留下的结果——测试通过、补丁干净应用、预期文件/行/值存在、未触碰任何禁区、步骤数和工具调用次数在预算范围内——在此基础上再叠加评分标准或两两比较的专家评审，以评估那些自动化检查无法覆盖的主观维度（如可读性、补丁的简洁性、PR 描述的质量）。让专家阅读代码提交记录，实际上是在评判叙述过程；真正的答案在于环境本身。

- **避免过度严苛。** 对于精确匹配或子串匹配的评分器：空格、大小写、`4` 与 `4.0`、Markdown 代码块标记、单位、千位分隔符、以及包裹答案的句子等细节，都应在双方归一化后再进行比较，或接受少量等效形式。

- **避免过于宽松。** 对于基于测试的评分器：测试是否足够全面，能够识别出错误答案？故意构造一个看似合理但错误的答案，并确认其会被判定为失败。- **防作弊。** 模型如何能在不真正解决问题的情况下通过评分？例如：硬编码预期输出、读取答案标准、针对测试名称做特殊处理、使用宽松正则匹配的空字符串，或者采用一种在技术上优化指标但实际无效的退化策略，又或是向评判器的输入中注入指令？在优化压力下，模型会找到这些漏洞。必须将这些漏洞堵住。

- **待测模型无法触及的真值。** 无论是沙盒中的文件、已检出的代码库、残留的提交历史、评判器可见的提示，还是具备搜索能力时的公开网络，都不得让模型获取。这必须是结构性的限制；仅靠提示中的“不要查看”并不能作为防御手段。

- **对失败案例进行抽样检查。** 阅读几份被评判器标记为错误的输出。如果其中超过约十分之一看起来像是评判器的误判，则应在进行全面评估之前先修复评判器——否则，你实际上是在衡量哪种方案更符合评判器的盲点。

- **确定性，或明确量化方差。** 对同一份输出重复运行评判器两次。若结果发生变化，则说明除了模型本身的差异外，还存在评判器的随机波动；应对此进行测量并报告。

- **以原子级检查替代整体评分。** 将各项独立属性分别作为单独的指标进行打分（如 `{正确、格式规范、简洁}`），而非将其混合成一个综合分数——这样更易复现、更便于校准，也更有诊断价值。优先为每个属性单独调用评判器。

- **聚合方式与问题目标一致。** 对于典型场景下的质量，均值是合适的；而对于罕见但高风险的行为（如数据删除、不可逆操作），采用“只要有一次失败即判定为失败”或最坏情况的聚合方式，比被简单案例稀释的均值更能反映关键问题。

- **部分得分与惩罚机制不会使退化策略最优。** 如果尝试后出错的惩罚远大于成功带来的奖励，“什么都不做”反而会胜出。

- **能处理大体积输出。** 对于模型可能产生的最长输出，评判器不得截断、超时或崩溃；评判器崩溃应视为 `status: error`，而非模型故障。

### 当评判器是 LLM 时

- **位置偏差。** 在两两比较时，应针对每个案例随机调整 A/B 的顺序（或同时对两种顺序进行评分并取平均）。
- **冗长偏好。** 应明确告知评判器不得因长度本身而加分，否则评判器往往会倾向于选择较长的答案。
- **自我偏好。** 若评判器与待测模型出自同一家族，它往往更倾向于那些与其自身风格相似的输出；因此，避免让待测模型自评，并考虑选用不同家族的评判器，或在难以判断时组建小型评审团。
- **标签敬畏心理。** 不要告诉评判器哪个响应是“参考”、“基线”或“人类”的答案。
- **具体评分标准，而非主观感受。** 应设定可验证的具体属性，而非笼统地问“哪个更好？”；将候选文本视为不受信的数据，而非指令；使用结构化输出，以确保解析过程确定无歧义。
- **与人工标注结果校准。** 在数十个由人类独立标注的案例上验证评判器，并报告其一致性。若在明确案例上的一致性远低于 ~90%，则说明评判器的提示还需迭代改进，才能使其评分指导后续优化——也只有这个数值，才能让谨慎的决策者真正信任基于评判器打分的主观指标。
- **针对已知负面案例进行测试。** 向评判器输入空字符串、“我不知道”，以及对错误问题给出的自信回答；确认其在这三种情况下均判定为失败。

## 5. 它能否检测到你期望的变化？

即使评估在上述各项要求上都完全达标，若其分辨率不足以捕捉目标效应，仍可能对实际决策毫无帮助。务必在首次全面评估前，以及在梯度上升的第一轮之前再次确认这一点——在已经耗费多轮资源之后才发现这一问题，代价将极为高昂。- **噪声水平、余量与可采取行动的最小变化幅度。** 以目标指标在实际重复次数下的基线运行结果为基础，计算该指标的噪声水平——即当前 n × R 下配对差值 95% 置信区间的半宽度（对于通过率，大致为 `1/sqrt(n·R)`：25 个样本 × 2 次重复约 ±14 个百分点，100 个样本 × 2 次重复约 ±7 个百分点）。将其与**余量**（上限减去基线）以及**用户真正会采纳的最小改进幅度**并列比较。若噪声水平超过其中任一者，请立即明确指出，并给出各项措施按成本排序的建议：增加重复次数（最经济，且配对设计能更有效地利用）、增加样本量、改用成对或连续型指标而非二元指标，或筛选出最具区分度的样本进行迭代，最后再用全集验证。样本量与重复次数是同一枚硬币的两面；应在确定整体规模时统筹规划，而非事后调整。

- **训练集与测试集来自同一总体。** 若评估将采用分组爬坡法，则分组必须随机进行（按 `tags[0]` 分层），绝不能按基线分数划分。从得分最低的样本中人为挑选训练子集，必然导致两方面问题：分析器只会看到极端案例，其修复措施针对的是尾部而非整体；同时，基于低基线分数的选择会带来回归均值效应——这些样本在再次运行时仅凭偶然便会“改善”。表现特征是训练集得分显著提升，而保留集却毫无变化。在基线阶段检查训练集与测试集的均值是否在噪声范围内一致；若不一致，应在第一轮前重新划分。分析器仍可在训练集中重点关注失败案例。

- **机制已正确连接。** 无论评分应依赖于何种因素——工具、记忆库、指令文件——都应将其禁用并确认评分下降；再将其启用并确认其在记录中生效。若评分在两种状态下几乎不变，则说明该评估并未衡量您计划调整的杠杆。

- **核心指标应由原始数据重新计算。** 请自行根据每个案例的 `grade` 值重新计算最终报告的数值，切勿依赖聚合字段。平均值与总和、单次重复与单个案例之间的混淆，都会导致虚假的突破性进展。

## 6. 向用户汇报发现

上述检查是对您的要求，但提交给用户的报告不应带有指令式语气。构建评估的人往往掌握着您所不了解的背景信息——约束条件、截止期限、刻意权衡等——因此，我们的目的是指出值得进一步审视的问题，而非评判其工作成果。

- **将发现表述为观察与建议。** 使用“值得关注的是……”“您可以考虑……”“这里可能存在问题的是……”等措辞，而非“这是错误的”。说明您的观察结果、其可能的影响，以及一项具体的改进建议，然后交由用户判断。
- **区分严重程度。** 首先列出那些可能导致结果严重失真的问题——将基础设施错误误判为失败、“无回答”与“否定”混为一谈、存在可达的真值、用于对比的模型生成了黄金标准、按分数选择分组、噪声水平大于预期效应、裁判具有非确定性——然后再列出那些虽会增加噪声或限制普适性，但不会改变结论的问题。
- **具体说明并提供证据。** 明确指出相关文件、函数、案例 ID 或记录中的具体行号。“案例 14 的预期答案似乎过时了——该库在 v3 中更改了默认设置”是可操作的；而“部分标签可能已过时”则不够具体。
- **明确指出一切正常的情况。** 审计未发现问题本身也是有效的结果，无需刻意制造担忧。
- **避免说教或面面俱到。** 只需报告对用户决策至关重要的少数几项问题；罗列所有偏离理想的情况反而会掩盖重点。
- **主动提出解决方案，而不仅是指出问题。** 对于那些只需小幅改动即可解决的问题——添加 `status` 字段、固定随机种子、比较前进行归一化、A/B 测试时随机分配、重新划分分组——请直接代为处理。

无论审计结果如何，有两项做法都值得推荐：一是将评估视为一个动态迭代的体系——每当出现新的生产故障模式时将其纳入案例库，对已饱和的项目进行加固，并在评分标准出现偏移时重新校准；二是定期让一位经验丰富的模型审阅案例、评分细则以及若干已评分的记录文本，并指出在哪些地方合理的人可能会对标注结果持有不同意见——三级审核员正是这一机制的规模化体现。
