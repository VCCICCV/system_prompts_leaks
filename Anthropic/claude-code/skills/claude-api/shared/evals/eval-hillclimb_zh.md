# 在评估上进行爬山优化

> **如果你通过 `/claude-api hillclimb` 进入：** 这就是你要找的文件。请按顺序逐步执行——步骤0和0.5是必须先完成的前提；步骤1到2会生成启动循环前所需的方案确认。请不要概括本指南，而是照章执行。

本指南旨在针对一个固定的评估指标，迭代式地改进由Claude驱动的应用程序：运行评估、分析失败案例、修改代码库中的某些内容、再次运行，如此反复，直到分数不再提升或预算耗尽为止。它接续在评估构建之后——用户已经有了衡量标准，现在希望推动某个数值的变化：通常是提高质量得分，但也常常是在保证质量的前提下降低费用或延迟。

整个循环本身很简单，但能否成功取决于纪律性：要仔细阅读原始的对话记录，而不是仅依赖摘要统计；要清楚每项改动带来了何种影响；要完整记录已尝试过的方案；并且不要因为只优化那些自己得分较高的案例而自欺欺人。**最终最重要的指标是测试集相对于初始状态的增量**——在迭代过程中对特定案例的改进并不是结果，而是过程的一部分。本指南正是围绕这些方面提出明确建议的。至于具体改什么、跑多少轮、何时停止，则完全由用户决定，应主动询问而非自行假设。

始终保持推荐导向——在每个问题中都给出一个具体的默认选项，让用户只需说“是”即可；并将步骤2结束时的方案确认视为启动循环前所需的最低审批。关于在循环过程中多久检查一次进度的问题，已在步骤2中提出，请勿在此单独重复。

> **与用户沟通。** 这些步骤是你的执行计划，而非需要逐字解说的脚本。面向用户的反馈应简明扼要、聚焦结果：你运行了什么、得了多少分、接下来打算尝试什么，以及可打开的相关路径或链接。除非用户主动询问，否则无需向其说明当前处于哪个步骤、正在编写哪些文件，或透露内部的进度管理细节。每轮提供一条简洁的更新即可；详细信息请记录在`report.html`和`narrative.md`中，而非聊天窗口。当需要用户做出决策时——比如哪些内容属于变更范围、下一步该尝试哪种改动、是否再投入一轮——请使用`AskUserQuestion`工具，而非自由文本描述：可将最多四个相关问题合并为一次调用，为每个问题提供两到四个具体选项，并将你的推荐放在首位且标注为“（推荐）”；不要额外添加自己的“其他”选项——该工具会自动追加一个自由文本输入框。如果`AskUserQuestion`不可用（无界面运行），则退而求其次，每次只提一个简短的问题。> **在后台运行评估命令，保持对话畅通。** 一次评估可能需要几分钟到几小时——不要让用户一直等待，但也不要将其封装到子代理中。每一轮，由主会话自行完成快速部分——应用变更、写入 `vN/change.*`——然后以 **一个带有 `run_in_background: true` 和覆盖整个运行时长的超时设置（通常最多 7200000 毫秒；若无超时，后台命令将在 30 分钟后被终止）的 Bash 命令** 启动评估程序本身（而非 `Agent`），并设置合理的超时。当评估程序退出时，您会收到完成通知；在此期间，仍需随时响应用户的问题，并在必要时启动分析器子代理（步骤 4）——这是该循环中唯一使用的子代理。评估程序完成后，**在信任通知之前，请先在磁盘上进行验证**：`vN/results.jsonl` 应包含 N×R 行，且 `vN/summary.json` 文件应存在；若行数不足，可重新启动同一命令（恢复操作在 (case, rep) 级别是幂等的，因此会从上次中断处继续）。随后，根据 build-eval.md 的说明，通过报告生成器（全量或精简版）重新生成 `report.html`，告知用户得分及文件路径，并选择下一项变更——如果步骤 2 的节奏要求此时与用户确认，则通过 `AskUserQuestion` 提问；否则直接告知并继续。在首次无人值守轮次之前，向用户展示完整的评估命令，并请其为本次会话授权，以免权限提示卡住无人关注的轮次。务必向用户明确该白名单条目的含义：它是整个循环的安全边界——只要用户批准了该命令，其执行内容即在其授权范围内——因此仅保留这一条评估命令，并将评估程序的依赖项固定（使用锁定文件，执行 `npm ci`）。脚手架的完整性检查机制是一个叠加在上的变更检测层，而非第二道安全边界：评估程序会对其自身、其旁或运行目录中的任何锁定文件，以及 `_state.json.harness_paths` 进行哈希校验，并在哈希值与上次使用 `--approve-harness` 记录的不一致时退出（退出码为 2）。因此，若某轮次意外或因分析器建议修改了已列出的脚手架文件，下一运行将被暂停，直至用户查看差异并确认。该机制不涵盖 `node_modules/`、解释器或 SDK 版本，也不覆盖 `harness_paths` 中未列出的任何文件；它也无法阻止能够写入用户可写任意位置的代理；真正起到限制作用的是白名单范围。切勿在无人值守轮次中传递 `--approve-harness` 标志——该标志应由用户自行执行。若您以无界面模式运行（使用 `-p` 或 SDK），则无需保持对话畅通。在一次性 `-p` 运行中，请在前台执行评估，因为后台任务会在运行结束时被终止；而在持续打开的 SDK 会话中，则按上述方式在后台启动。当用户询问运行进度时，请直接引用评估程序自身的进度输出（脚手架每 30 秒打印一次 `k/N done ... ~Ns left`，并同步记录到 `vN/progress.txt`）——只需一句话，无需详细叙述。

## 步骤 0：确认存在可运行的评估

向用户提问：

> 您是否为此流程准备了评估脚本——即一段可以从命令行运行、针对固定的一组提示对应用进行测试并输出评分的脚本？如果是，询问该命令及其将每例结果写入的位置。同时询问运行器是否会重试失败的案例——如果会，是哪一次尝试的评分、完整对话记录和用量计入最终结果；每次尝试都严格计分（只有在重试时才通过的案例视为失败，除非用户另有决定），并确保重试次数计入成本核算，而非被悄然吸收。务必确认评估指标衡量的是你希望改进的结果，而不仅仅是你假定与其相关的某个行为。如果你使用行为代理指标是因为真实结果每轮都难以测量且成本过高，请事先说明，并在最后用真实评估指标对胜出方案再做一次验证。**每次评估运行都必须按案例粒度记录：完整的对话记录、`model`、`usage`（输入/输出/缓存的 token 数量）以及评分字典**，而不仅仅是汇总得分。每个案例的对话记录和评分必须来自同一次模型调用；切勿先单独重新调用模型获取对话记录，再用另一份样本进行评分。在用户的代码库中搜索是否有现成的评估运行器或封装器已能持久化这些字段，避免重复造轮子。先运行一次以确认其正常工作并查看输出格式（如有近期结果文件，也可直接使用）。然后**阅读 `shared/evals/eval-audit.md` 并针对该评估执行审计**——包括案例、运行器和评分器——按照其中第 6 条的要求报告；未通过 `build-eval` 流程构建的评估尚未经过这些检查，而下文的步骤 0.5 是必通过的部分，而非全部清单。

如果不是，**请在此停止**。没有评估的爬山式优化只是盲目修改和碰运气。引导用户前往 `/claude-api build-eval`（阅读 `shared/evals/build-eval.md` 并执行该流程），待其生成脚本并得出基准数值后再继续。

如果爬山式优化的原因是模型迁移——用户希望切换到更新的 Claude 模型并为其调整提示词——则请同时参考 `shared/model-migration.md`，以便你提出的改进建议能够考虑到新模型的破坏性变更及行为变化。

## 步骤 0.5：证明评估可被有效优化

一个可运行的评估（步骤 0）并不意味着它就是*可信*的。在投入一轮优化之前，必须排除评估框架可能误导你的可能性——基于有缺陷的度量进行的爬山式优化比完全不优化更糟，因为你可能会“改进”一个伪像，宣布成功，却最终交付毫无价值的结果。`eval-audit.md`（在步骤 0 加载，或由 `build-eval` 自动加载）是完整的检查清单；以下各项是在开始第一轮优化前必须通过的检查，任何一项未通过都可能导致评估运行出现严重问题：

- **证明评估能够检测到你期望的改进。** 以基线在当前迭代次数下的表现为基准，向用户展示三个数值：步骤1目标上的**噪声水平**（即当前样本量n与重复次数R对应的配对差异置信区间半宽——具体计算见`eval-audit.md`第5节）、**提升空间**（上限值减去基线值），以及**用户会采取行动的最小改进幅度**。如果噪声水平大于其中任何一个，则无论改动效果如何，本轮都无法显示出真正的有效改进——应在一开始就明确指出这一点，而不是等到五轮之后；并在开始前提出增加迭代次数、扩充案例集或采用更细粒度的指标。
  
- **证明相关机制确实已正确连接。** 无论评分依赖于什么——代理写入的内存存储、应调用的工具，或是应读取的文件——在信任任何评分结果之前，先运行一次端到端的独立验证，确保该机制确实生效：通过评估所用的同一路径写入一个值并将其读回，或确认该工具确实在代理的工具列表中出现。如果评估结果显示该机制毫无作用，请先检查其连接情况，再下结论说“模型无法完成此任务”。
  
- **从原始的逐例结果重新计算核心指标。** 不要直接信任清单中的聚合字段——请自行根据`results.jsonl`中的实例级数据重新计算将要报告的指标。均值与总和等聚合方式的混淆，可能会导致看似突破性的虚假结果，直到人工核验时才会被发现。在经过人工交叉验证之前，任何过于理想的结果都应视为测量误差；务必把交叉验证作为固定流程，而非偶然发现。
  
- **对基线中的低分案例进行抽样检查。** 随机选取几个基线得分最低的案例，仔细查看模型的实际输出、评审的判分依据以及预期答案：评审是否公正，且真实答案是否正确？错误的评分标准或错误的预期答案，会导致后续每一轮都在为测量误差修复框架而徒劳无功。一旦发现问题，应立即修正评分标准或真实答案，并在第一轮开始前就地重新对基线进行打分（仅需对已保存的对话记录再次执行评审，无需重新运行模型）。同时，对所有得分为零的基线案例进行分类：区分是框架问题还是评审判定问题（可通过runner记录的逐例错误字段或错误侧载信息判断），并在第一轮开始前将框架问题的案例从计分基数中剔除。此外，还应对依赖的评审人员进行抽查：确认每位评审都能正确读取代理实际生成的产物，且没有任何外部因素（如宿主仓库状态、预置文件、系统时间等）可能干扰其判断——若评审脱离了设定的测试环境，测出的将是环境特性而非代理能力。
  
- **核实请求由哪个服务提供，以及runner的重试机制。** 运行一个烟雾测试案例，并从*响应*中读取`model`字段，而非依赖配置文件——服务器端的隐式替换会使得所有对比失效——同时确认请求重试带有抖动且会被计入，而非被吞没。`runner-scaffold.mjs`默认会进行这两项检查；若使用自定义runner，则需额外添加此项验证（参见`eval-audit.md`第2–3节）。- **如果你的评分对象是通过你调整的参数生成的，首先要测量其构建过程中的变异。** 有些工作流会在调参和评分之间加入一个随机生成步骤：你迭代的提示词会“构建”出一些东西——比如记忆存储、检索索引或合成语料库——然后评估再基于这些构建结果进行打分。当每次变体只运行一次构建，且所有重复实验都使用同一个构建时，重复实验及其置信区间只能反映对固定构建打分时的噪声；而构建本身的运行间变异则每个变体只采样一次，对所有门控机制都不可见，而且往往才是更大的影响因素。在第一轮之前，用完全不变的提示词重新构建基线两次或三次，并以相同方式对每次构建进行评分：这些无变化构建之间的差异范围，就是单次修改效果必须超越的下限。在一次爬坡中，同一提示词的三个构建在训练集均值上的重评噪声约为±1.4，但它们的差异却达到了约7个点——这意味着每次修改都是与同一个基线构建比较，整个循环无法区分任何修改与默认状态。如果构建间的差异超过了合理的单次修改效应，那就对每个变体多跑K次构建，比较各次构建的平均值；或者把调参环节更靠近评分阶段，因为在单一构建上增加重复次数也无法捕捉到这种差异。

如果工作流会生成子代理，还要确认你正在迭代的参数——模型、资源投入、提示词——确实传递到了每个子代理，并且追踪日志能够记录它们的执行过程；如果某个参数悄悄没有传播下去，那么针对该参数的每一轮调整实际上都是无效的。

如果你可以选择从哪个评估指标或数据切片开始爬坡，**优先选择单位 token 信号最强的那个**：

- **该机制必须真正影响评分结果**——将其关闭后重新运行；如果评分几乎没有下降，说明这个评估指标并未衡量你所调整的内容，再多的调优也无济于事。
- **在少量重复实验下，评分的运行间变异要低**——如果基线的每次评分波动很大，“获胜”的效果很可能只是随机噪声。此时应增加重复次数，或选择波动更小的数据切片，而不是去追逐噪声。
- **机制可被检查**——优先选择那种你能清楚看到为什么某个变体胜出的评估（例如它写出并复用的产物、工具调用的追踪日志），而不是那种无法归因且可能不具备泛化性的黑箱式差异。

## 第一步：明确目标、确定要改变什么，以及它们是如何关联的

**首先是目标。** “让数值上升”只是爬坡优化的一种用途，不同的目标会让整个循环的行为有所不同——因此在开始任何操作之前，务必先通过 `AskUserQuestion` 提问，列出评估实际记录的各项指标和性能字段：

> 这次爬坡应该优化什么？  
> - **提升 `<核心指标>`**（推荐用于新评估且评分仍有明显改进空间的情况）  
> - **降低每次请求的成本**——将 `<核心指标>` 控制在基线的噪声范围内  
> - **降低延迟**——将 `<核心指标>` 控制在基线的噪声范围内  
> - **切换到 `<其他模型>` 并在其上恢复 `<核心指标>`**

回答会为后续流程设定三件事：分析器每轮关注的**主要目标**（第4步）、停止条件所参照的**指标**（第2步），以及**约束条件**——所有其他被记录的指标都会变成“不得超出噪声范围”的硬性约束，而非需要进一步优化的对象。如果目标是成本或延迟，无论构建-评估界面是否将其设为显示列，都要确保 `_state.json` 的 `perf_fields` 中包含 `cost_usd` 或 `latency_s`——因为目标会强制添加这一列。将目标记录在 `_state.json` 中（例如 `"approve_each_round": false, "goal": {"target": "cost_usd", "direction": "lower", "hold": ["accuracy"]}`），这样即使会话中断后恢复，也不会无意中又回到单纯优化评分的模式。

接下来询问本次调整涉及应用的哪一部分：> 您希望我在哪些方面进行迭代？例如：  
> - 系统提示词  
> - 代理读取的某个特定技能或指令文件  
> - 工具描述  
> - 模型选择或 API 参数（`effort`、`thinking`、`max_tokens`）  
> - 代理循环/框架代码本身  
> - 以上全部——只要能推动目标进展的任何内容  
>  
> 另外，有没有哪些部分是不能动的——即使我认为修改它们会有帮助，也应保持原样？

请记录下您的回答。这将定义每一轮您要编辑的内容；不可动的部分属于硬性约束。同时，请用户命名**框架路径**——即运行脚本、评分器以及评估命令会执行的所有文件——并将其记录在 `_state.json.harness_paths` 中（相对于仓库的路径）。当这些文件自用户上次使用 `--approve-harness` 运行以来发生过变更时，运行程序会拒绝启动，因此对已列出文件的未经审核的修改会导致本轮评估中断，而不是悄悄地产生不同的结果（该机制会检测其处理的文件是否发生变化——运行命令的会话白名单本身就是边界）。如果用户说“只要能推动进展就行”，也没问题——但仍需询问不可动的部分，因为几乎总有一些内容是必须保留的（如合规免责声明、语气要求，或合同规定的必用工具）。对于成本或延迟目标，模型选择和 API 参数（`effort`、`max_tokens`、缓存策略）通常是最重要的调节手段——务必明确哪些可以调整，哪些不能。

如果目标是某个技能或指令文件，请确认**它在评估过程中如何传递给模型**：是直接附加到系统提示词中（这样可以单独检验“内容本身是否合格”），还是通过应用的真实技能发现流程加载（这样还能测试“模型能否找到并使用它”）？这两种方式都合理，且衡量的侧重点不同——请询问用户希望采用哪种，并确保评估运行程序与之匹配。

有两件事您可以自由选择，除非用户提出异议：负责*阅读转录并提出改进建议*的模型不必与被测模型相同——使用更强的模型进行诊断往往更有价值；而且，提出的改进建议也不必是文字形式。如果一段具体的辅助脚本、代码片段或示例比再多一段说明更能引导模型，那就写成那样的形式。

---

## 第二步：商定停止条件（若涉及成本，则还需设定预算）

通过 `AskUserQuestion` 询问在再次汇报之前应运行多少轮：

> 对完整数据集进行一轮评估，即 N 个案例 × `<model>` 的 R 次重复，大约需要 Y 分钟。您希望运行几轮后再向您汇报？  
> - **直到达到平稳期（推荐）：**持续运行，直到第 1 步的目标在连续 K 轮中的提升小于 delta（K ≥ 3——连续两轮持平不足以判定为平稳），或者某个护栏指标出现超出噪声范围的恶化，此时再汇报。  
> - **每次一轮：**提出建议、运行、汇报，然后再次询问。选择此方式可对每次改动进行精细调控。  
> - **N 轮：**运行 N 轮后汇报，再询问是否继续。（由用户输入 N。）

这既是停止条件，也是汇报的频率——循环会在两次汇报之间自主运行。

将 delta 设置在第 0.5 步所确定的噪声水平之上——低于评估分辨率的停止阈值实际上永远不会触发。

**如果降低成本本身就是第 1 步的目标**——而不仅仅是本轮循环的上限——请在规划轮次前阅读 `shared/evals/cost-hillclimb.md`：它将本指南中的循环聚焦于成本优化目标，并给出了调优顺序（缓存健康度 → 提示词审计 → 模型与努力程度的阶梯式探索 → 在固定模型上逐步优化提示词 → 向左下方重新试探 → 注册联合确认），还预设了采纳门槛和针对成本的专门停止规则。（`shared/cost-optimization.md` 是实现同一目标的无评估版清单；在此循环内部，请遵循 `cost-hillclimb.md`。）**如果用户询问循环的费用或给出了预算**，也请同时展示**总循环成本**——基准加上每一轮计划的费用——并确定一个上限。请基于真实数据估算，不要凭空猜测：

1. 从最近的结果文件中（如果没有，则使用一个小样本运行），汇总所有案例的`usage`字段，如果是由模型评分的，还需计入裁判调用。
2. 将其乘以用户所用服务提供商的每 token 价格——`SKILL.md`中的“当前模型”表为官方定价；如果是 Bedrock/Vertex 等第三方，请咨询或查询。缓存读取的成本约为基础输入的十分之一。这样即可得出单次迭代、单个副本的费用。
3. 测量该轮的实际耗时——对一次完整运行进行计时并按比例换算，不要估算。
4. 再额外预留一小部分用于每轮分析的开销，通常这部分相对于评估本身而言较小。

向用户展示`(N + 1) × R × $X`，并询问他们能接受的总支出是多少。如果用户犹豫，可提供以下调整选项：减少轮数、减少副本数、选用更便宜的裁判模型，或者仅保留最具区分度的案例（根据与基准运行的跨副本方差排序，保留前 K 个，最后再用基准和胜者模型对全集跑一遍以确认）。无论用户选择哪种方案，循环内部的默认设置始终是每轮都运行**同一组**案例，绝不会为了凑数而悄悄删减。**您给出的 N、R 和案例数量必须是实际执行的数值**——如果后续因副本数或拆分导致总费用超出批准的上限，请在继续之前提前告知。

当目标是控制成本，且候选改动只是提示文本时，应先单独计算指令本身的成本——即每次请求的输入 token 数乘以每个案例的请求数，并与预估节省额对比；有些候选方案在尚未投入一轮之前就已因成本过高而被排除。

### 获得方案审批

在动任何文件之前，务必与用户确认方案并获得明确同意。需要包含以下三部分内容：

- **范围表**——两列：“会变更”和“不触碰”，内容来自步骤 1。用户应能一眼看出哪些文件和参数会被调整。
- **变更执行方**——默认情况下，您负责应用每轮的变更，用户负责审核结果；也可提供另一种方式：**在每轮运行前展示差异并由用户决定是否执行**（当产出物是面向客户的内容、法律/医疗/受监管的文本，或用户明确要求必须由人工把关的场景时，建议采用此方式）。将选择记录在 `_state.json.approve_each_round` 中。
- **简短的实施说明段落**——说明您打算如何运行循环。例如：“每轮我都会让新的分析器读取训练轨迹并提出一项改动；我会应用该改动，重新运行全部案例，并发布状态表。我只针对那些足以超过评估噪声水平的重大改动进行迭代——比如重写一段或新增一条规则，而不是简单改写一句。初期我会尝试不同的调整手段（工具描述、系统提示、`effort`等），以找到优化空间。最多运行 8 轮。”

不要让用户主动索要这些内容，而是作为默认输出提供。只有这样，用户才能放心地让循环运行，而不必每隔二十分钟就来查看进度。

## 步骤 3：初始化状态、拆分数据并获取基准

循环可能会持续多轮，甚至跨多个会话运行。因此，需将状态保存到磁盘，以便在中断后恢复，并方便用户查看历史记录。如果用户已有先前评估的结果目录和文件结构，**请沿用他们的设置**——关键在于每次运行都能生成步骤 0 中的案例级数据（完整对话记录、`model`、`usage`、评分字典，均来自同一次模型调用）；以下布局仅作为全新开始时的默认配置。否则，请创建一个工作目录——例如 `.claude/hillclimb/<flow-name>/` 是一个合理默认，但也可根据用户的代码库情况自行选择——并按如下结构组织文件。**报告生成器会直接读取该目录结构**，因此以下文件名和字段名均为严格约定，而非建议：

```
.claude/hillclimb/<flow>/
  _state.json            # 循环状态 + 报告配置 - 结构如下
  metrics.md             # 自由文本评分标准（Markdown 格式）- 描述各指标含义；完整查看器会渲染该文档
  narrative.md           # 模型撰写的运行摘要 - 每轮结束后重写；最终版本见步骤5
  trajectory/
    scores.tsv           # 由报告生成器（完整版或精简版）计算得出：每个案例的主指标均值，每轮一列
  baseline/
    results.jsonl        # 每个（案例，重复）对应一个JSON对象 - 结构如下
    summary.json         # 每个变体的头部信息 - 结构如下
    traces/
      <id>_rep<k>.json   # 完整日志，每个案例、每次重复一份文件（分析器仅接收训练集的日志 - 步骤4）
  v1/
    change.md            # 本轮发生了哪些变更及原因（由分析器提供）
    change.patch         # 实际应用到代码库的补丁
    results.jsonl  summary.json  traces/<id>_rep<k>.json
  v2/
    ...
```

**`_state.json`** - 此处除划分ID外均为可选项；`metrics`和`perf_fields`允许您覆盖报告从数据中推断的内容。`best.round`采用0索引（0 = 基线）。若评估包含多个指标，则**第一个类型为`binary`的指标（若无则取`metrics[0]`）将作为报告的头条**，请据此调整列表顺序。`goal`记录步骤1的答案——循环优化的目标指标或性能字段、其优化方向，以及必须保持稳定的其他指标——因此，最佳结果是对照目标而非单纯依据头条来选取：

```js
{ "current_round": 2, "reps": 2,
  "goal": {"target": "pass", "direction": "higher", "hold": ["cost_usd"]},
  "approve_each_round": false,
  "best": {"round": 1, "test_score": 0.70},
  "train_ids": ["case_01", ...], "test_ids": [...],
  "harness_paths": ["eval/run-eval.mjs", "eval/grade.mjs"],
  "harness_sha": "...由执行者在--approve-harness时填写，切勿手动修改...",
  "metrics": [
    {"id": "pass",      "kind": "binary", "label": "通过"},
    {"id": "quality",   "kind": "judge"},
    {"id": "verbosity", "kind": "float",  "better": "lower"}
  ],
  "perf_fields": [
    {"id": "cost_usd",  "label": "成本",    "unit": "$"},
    {"id": "latency_s", "label": "延迟", "unit": "s"}
  ],
  "prices": { "my-custom-model": {"in": 2.0, "out": 8.0} } }
```

**`results.jsonl`** - 每个案例、每次重复一行，**在每个案例完成后追加写入**，以防止崩溃导致已完成的工作丢失。`grade`可以是布尔值、数值，或`{metric_id: number}`字典；对于`judge`类型的指标，`explanation`是可选的同级字段，用于记录评判理由。将完整的提示文本放入`prompt`字段（报告会显示该文本）。`tags`按顺序排列——`tags[0]`为主要分组键。应记录响应中的`model`，而非配置中的模型；`cost_usd`由每行的`model`乘以用量计算得出（如有`judge_model`和`judge_usage`，还需加上相应部分），这样更换模型时不会沿用过时费率，且执行者无需自行计算成本。完整查看器会在文件存在时自动完成此计算；否则，在提交报告时需按build-eval.md § 第一次付费调用前的说明自行计算（“如果用户询问这会花费多少”部分：当前模型价格见`SKILL.md`；缓存写入按输入量的1.25倍计费，读取按0.1倍计费）——状态表中的`$/run`和`spend`即由此而来。适配器对输入较为宽容：`prompt_id`也可写作`id`或`case_id`；若`_state.json`未指定`metrics`，则会根据`grade`键的并集推断。性能字段按精确名称读取：

```json
{ "prompt_id": "case_17", "rep": 0, "prompt": "...完整提示文本...",
  "tags": ["topic-a", "hard"],
  "grade": {"pass": 1, "quality": 7.2, "verbosity": 3.0},
  "explanation": {"quality": "引用两篇文献；表述均衡。"},
  "model": "claude-opus-5-5",
  "latency_s": 12.4,
  "tool_calls": 2, "web_searches": 1,
  "usage": {"input_tokens": 1200, "output_tokens": 480} }
```

报告还支持两个可选的每行键：`attachments`（一个包含 `{kind: "image"|"file"|"url", ref, alt?}` 的列表，显示在提示旁边）和 `meta`（一个任意字典，会在转录文件头中展示）。

**`summary.json`**——报告的每个变体的头部信息，而非聚合统计（这些统计由报告从 `results.jsonl` 中重新计算得出）。所有字段均为可选；`target` 取值为 `"system_prompt" | "skill" | "tools" | "code"`：

```json
{ "description": "启用 web_search 工具",
  "target": "system_prompt",
  "suspicious": "在第二个随机种子上未复现效果提升" }
```

**`traces/<id>_rep<k>.json`**——对话的逐字记录，以 JSON 数组形式呈现，数组中的每一项为 `{role, content, thinking?, name?}`，其中 `role` 可取 `system | user | assistant | tool_call | tool_result`。

`traces/` 目录是分析器在各轮之间读取的数据。按轮次保存，并且每轮每个重复实验对应一个文件，这意味着到第 3 轮时，分析器就可以对比 `baseline/traces/case_17_rep0.json` 和 `v2/traces/case_17_rep0.json`，从而精确地看出哪些行为发生了变化。`trajectory/scores.tsv` 则提供了跨轮次的概览视图：每行对应一个案例，每列对应一轮，单元格内容为该案例的主指标平均得分——这一数值由报告生成器（无论是完整版还是精简版）从 `results.jsonl` 文件中计算得出，因此无需运行者手动编写，也不会出现偏差。**使工件可见。** 如果流程会消费或生成视觉或结构化工件——例如输入图像或 PDF、供计算机使用的截图、生成的 HTML/SVG/图表，以及模型写入的文件——请确保在审查案例时，人类能够实际看到这些工件，而不仅仅是文件名：在“转录”标签页中通过完整查看器渲染，否则则从引用的路径打开。完整查看器为此预设了专用插槽，运行器只需将内容填入即可：

- **输入工件**——在 `results.jsonl` 的对应行中：`"attachments": [{"kind":"pdf","ref":"baseline/inputs/case_3.pdf","alt":"source doc"}]`。渲染在第一条用户发言的上方。
- **输出工件**——在产生该工件的追踪记录行中：`{"role":"assistant","content":"...","attachments":[{"kind":"html","ref":"v2/out/case_3.html"}]}`。渲染在该条发言的下方。将工件写入磁盘的变体目录下，并以相对于流程根目录的相对路径进行引用。
- **响应文本中的富内容**——助手发言的 `content` 中，使用分隔符包裹的 ` ```html ```、```svg ```、```json ``` 块会自动添加一个“> 渲染”切换按钮；无需额外编写任何代码。完整版查看器会以内联方式渲染 `image` 和 `svg`，在沙箱化的可滚动 iframe 中渲染 `html`，使用浏览器原生查看器渲染 `pdf`，并将 `json` 和 `text` 放在 `<pre>` 标签中——每种类型都配有“隐藏/显示”切换按钮。其他任何内容（如 `file` 类型的 docx、pptx 等）则以下载卡片的形式展示。大小小于 2 MB 的文件会内联到 `report.html` 中；大于 2 MB 的文件则保留为下载链接，以免报告文件体积过大。**每个工件仅占用一个槽位**：当某一轮次包含 `attachments` 时，查看器会禁用该轮次文本中 fenced code block 的内联渲染切换——因此只需将输出放入 `attachments` 一次，响应文本便可保持纯源码格式。精简版报告则不会渲染上述内容，而是直接链接每个 trace 文件，由分析器和用户分别打开引用的文件——因此无论哪种情况，所有 `ref` 都应相对于流程根目录保持相对路径。如果某个流程需要的功能是预构建查看器所不支持的，请编辑 `report/frontend/atoms.jsx` 中的 `ArtifactView` 组件，并通过 `frontend/scripts/build.sh` 脚本重新构建（仅适用于 EAP 安装——CLI 不会提取前端资源）。

**请对提示集进行拆分，以防止分析器过拟合于您报告的指标数值。** 分析器会读取对话记录来提出改进建议——按设计，它只会针对其见过的具体案例进行优化。而您报告的评分必须来自分析器从未读过的案例。具体的划分方式取决于您的案例数量，请选择最轻量的结构，以便得到一个您可以信赖的留出验证指标：

- **默认：训练集/测试集。** *训练集* 是分析器每轮读取其转录本的数据集；*测试集* 则是其余所有数据：每轮与训练集一同评分，但分析器从不打开；其得分用于确定胜出轮次，并作为最终结果的 headline。**按 `tags[0]` 分层随机划分数据集——切勿依据基线得分进行划分。** 训练集需包含足够数量的失败案例以显现规律（几例至二三十例即可），但应通过扩大训练集规模来获取，而非手动挑选最差情形：若训练集仅由低分样本构成，则分析器只会接触到极端情况并针对尾部优化，而这些案例在后续重跑时又会向均值回归——健康的训练集得分提升、测试集得分持平才是理想状态。基线评估后，应检查训练集与测试集的均值是否在噪声范围内一致；若不一致，则在第一轮前重新划分。分析器仍可在训练集中重点关注那些失败案例。
- **小规模数据集，或跨案例指标**（如成对排序、排名等，任何会在单个切片内产生碎片化的指标）。无需划分。每轮对整个数据集进行评分，借助**重复实验**降低噪声，并让分析器阅读少量有针对性的失败案例转录本，而非固定读取某个切片。在报告中将每轮得分标注为**方向性指标**：若改进在多次重复中持续有效，则为真实信号；但在无独立验证集的情况下，最终结果只能作为迭代参考，而非可公开发表的数值。
- **大规模数据集**（约150+个案例），且希望得到一个不受轮次选择影响的最终结果：可选地划出第三个*验证集*——每轮参与评分以选出胜者——并将*测试集*留到最后再使用。对于大多数评估而言，额外的管理开销并不值得。
  
务必向用户坦诚说明其数据划分能揭示什么、不能揭示什么。对于二元通过率，95%置信区间的半宽大致为 `1/sqrt(n·reps)`——25个测试案例、每次重复2次时约为±14个百分点，50个案例、每次重复2次时约为±10个百分点。因此，应向用户展示其数据集对应的置信区间宽度，并由用户自行决定；重复次数与测试集规模其实是同一枚硬币的两面。无论用户如何选择，都应将 ID 按照 `baseline/results.jsonl` 中 `prompt_id` 的原样记录到 `_state.json` 中（处理文件路径时会对 ID 进行规范化，但应在该字段中保留原始形式），一次性确定划分方案并保持不变。
  
**每个 prompt 的重复次数**是另一项关键参数。模型输出存在运行间的变异性，对每个 prompt 多次重复可提高估计的精确度——尤其在小规模数据集上，或当第二阶段预算允许时更为必要。应提供此选项并让用户自主选择；若用户选择多次重复，则将结果记为“N 次重复中有 k 次通过”，而非单一的通过/未通过。切勿在任一方向上对此参数进行静默默认。重复仅能降低抽样带来的噪声；若某次生成的结果被多次重复利用，则其构建过程中的方差仍将存在（参见第 0.5 阶段的重建检查）。
  
**务必将真实答案与待测模型隔离开来。** 若评估包含参考答案、评分细则或预期输出，务必确保它们**无法被模型的上下文所触及**——既不在系统提示中，也不在模型可读的工具结果里，不在其代码执行或 bash 工具可打开的文件中，更不在容器挂载的测试用例中。这些内容应仅保留在评分程序中。这必须是结构性的约束：“不要看答案”的提示并不能作为防护手段，而在优化压力下，代理最终会找到一条类似 `cat evals.json` 的指令，在不真正解题的情况下赢得比赛。如果用户现有的评估将 prompt 和答案存储在同一文件中，则应在首轮前将其拆分。此外，若评估源自公开基准，且代理具备网络访问能力，则答案还可能通过互联网被获取——基准的公开镜像通常会附带解决方案。应对每份输出日志进行扫描，查找对基准仓库或解决方案镜像的请求（并考虑阻止对外访问）；若发现有下载解决方案的行为伴随通过结果，则判定该次结果无效，并且不应假定任何自动化污染检测能够完全识别此类情况。
**在追踪中处理非文本负载。** 不要在追踪文本中嵌入原始的 Base64 或二进制数据块——这会膨胀文件并产生大量噪声。相反，应将每张图片或二进制负载写入一个随附文件，并在该内容出现的对话环节处插入 Markdown 引用：对于图片使用 `![](<从流程根目录开始的路径>)`，其他内容则使用链接，这样报告中会显示缩略图，分析器也能打开真实文件。只有当负载确实不值得保留时，才退而使用简单的占位符，如 `<[binary: 12kB]>`。

**基线。** 在选定的重复次数下，对未修改的应用程序运行**完整测试集**，并将结果记录在 `baseline/` 目录及 `_state.json` 中。同时记录环境指纹——包括代码库提交、依赖锁文件哈希、本地补丁或桩代码、禁用的工具、模型 ID——并在每轮运行前重新验证该指纹：如果指纹发生变化，则需要重新生成基线，因为比较结果将不再可靠。如果由于时间推移或环境变更导致基线与某轮结果之间存在较大间隔，则应在评估候选版本的同时运行一个“无变化对照”，并以对照结果作为门限，而非过时的基线数值——不同测量日之间因相同代码产生的分数漂移几十分之一是常见现象；若随机性构建位于评估杠杆与最终评分之间，对照实验必须重新执行整个构建过程，而不仅仅是运行评分器。对照实验的再次运行还能免费估算同一环境下的波动率；因此，在设定保持门限时，不要将阈值设在这一噪声水平之内（参见步骤 2 的门限确定）。（如果成本敏感，且固定重复次数与拆分推送导致总开销超出步骤 2 的上限，请在此轮运行前说明。）如果您想先预览一下，现在就可以在流程目录上运行报告生成器（完整版或精简版——调用方式见步骤 4）：当磁盘上仅有一个变体（仅有 `baseline/`，或尚未生成 `_state.json`）时，完整版查看器只会显示“评估”和“转录”两个标签页；“摘要”标签页会在出现第二个可比较的变体时才会自动显示。

## 步骤 4：循环迭代

每一轮迭代的流程为：**分析 -> 应用 -> 运行 -> 记录**。在整个过程中有两条不可妥协的原则：始终只读取训练集的转录记录；评估集和预算一旦发生变化，必须重新征求用户意见。

**分析。** 如果下一次改动已明确——例如用户指定了具体修复方案，或者上一轮的结果直接指向某个问题——则跳过分析器，直接编写 `vN/change.md` 文件。否则，启动**一名全新的分析子代理**（使用 Claude Code Task 工具），并向其提供：上一轮的**训练集追踪文件**——运行器会为每个案例生成一条追踪记录，因此无需传递整个 `traces/` 目录；只需列出 `_state.json.train_ids` 中包含的特定 `vN/traces/<id>_rep<k>.json` 文件路径（或将这些文件复制到临时目录），并告知分析器不得读取 `traces/` 下的任何其他文件；**`results.jsonl` 中的训练集行**，以便分析器查看每个指标的逐案得分；**`trajectory/scores.tsv` 中的训练集行**，以便分析器了解每个案例在各轮之间的变化轨迹；当前正在迭代的工件版本；步骤 1 中定义的作用范围与禁止修改项清单；以及**本轮所针对的指标**——第一轮即为步骤 1 中设定的目标，并包含必须满足的约束指标。分析器会根据得分筛选需读取的转录记录，并按其偏好进行分析——例如按目标指标排序、对比高低分案例、跨指标相关性分析、识别在多轮中停滞不变的案例等——然后返回一份带有简短理由的改进建议，并在理由中引用支持该建议的具体转录记录。将该理由保存至 `vN/change.md`。每轮启用新子代理，可避免外层会话在其上下文中累积过多转录内容。

外层会话**本身并不读取转录记录**——它仅通过得分来决定改进建议。这种隔离机制确保了数据的独立性：被留作测试的样本不会以任何方式渗入到改进建议中，因为提出改进建议的组件从未接触过测试集的数据。有三点需要注意，以确保分析器的改进建议切实有效。首先，**要概括，不要照搬**：变更应描述故障的*行为*，而非故障的*内容*——在提示中直接粘贴训练用例中的具体名词或短语，只会导致过拟合的变更，对未见样本毫无助益。其次，转录本反映的是某个模块让模型*做了什么*，而不是它在无明显动作的情况下阻止或启用了什么——在提议移除某项功能时，应明确指出哪些用例会因此退步，而不仅仅是哪些用例会恢复。第三，在早期阶段尤其允许分析器建议尝试完全不同的手段（如调整工具说明、API 参数），而非仅对同一句话做细微措辞调整；探索潜在的改进空间往往值得投入一轮精力。

**每一轮只针对评测能够感知到的变更**，无论该变更由分析器提出还是由您直接撰写。（用户明确要求的修复仍可计入本轮；若您预计其效果低于噪声水平，请在本轮的状态信息中予以说明。）若变更的效果小于 Step 0.5 的噪声阈值，则其是否保留或回退在很大程度上取决于偶然因素。因此，应从根源上修复目标行为（重写引发该行为的段落、补充缺失的规则或能力），而非简单地修改某一行文字；衡量标准是实际效果，而非差异长度——一个遗漏的事实、新增的工具或不同的 `effort` 设置，就可能构成完整的修复方案。一项修复所能带来的提升，最多也只能等于当前表现出该行为的用例所损失的部分；若没有任何单一行为的损失足以突破噪声阈值，则应视作进展停滞，而非人为夸大变更幅度——此时可提前执行 Step 4.5 的归类，并在本轮状态信息中建议增加重复次数或提供更多用例，因为这才是降低噪声阈值的有效途径。从根本层面解决问题仍算一次变更——即针对用例失败原因的一个假设，以一个整体补丁的形式保留或回退，无论其触及多少处代码——而非将若干无关的修复捆绑在一起（只有 Step 4.5 的广度遍历才会这样做，用于处理那些单独测量时过于微小的差距）。

以下是分析器提示的草稿：

> 以下是我们当前正在迭代的 `<artifact>`。下方是来自 `results.jsonl` 的训练集行（每个用例的完整 `grade` 字典）及其对应的转录本。**本轮的目标是 `<metric>`（<higher|lower> 更优）；同时，`<guardrail metrics>` 不得退步。** 禁止修改的列表为：<...>。请找出在 `<metric>` 上表现最差的用例，并挑选几例表现最好的用例作为对比；确定最常导致该指标下降的单一行为，并针对该行为提出对 `<artifact>` 的**一项**具体变更，以统一的差异形式呈现；该变更可能涉及多个位置，但每个改动块都必须服务于这一单一行为。请说明有多少用例表现出该行为，以及这些用例在 `<metric>` 上总共损失了多少——修复所能带来的提升不得超过这一数值。`<metric>` 的噪声阈值约为 `<±X>`：若即便完全修复也无法超出该阈值，请直接说明，而不必提出变更；否则，请从根源上修复该行为（重写引发该行为的段落、补充缺失的规则或能力），而非仅仅调整某一行的文字。对于您引用的每一条调用链，请**逐字引用相关代码行**，并附上其调用链文件路径（`<vN>/traces/<case_id>_rep<k>.json`）——若已通过完整查看器生成了 `report.html`，还请提供深度链接 `report.html#tab=transcript&ex=<case_id>&cmp=<vN>&rrep=<k>`——以便用户一键打开该次重现的具体版本。请勿引用测试用例。

在读取 `trajectory/scores.tsv` 以选择重点关注的用例时，请仅筛选**训练集行**——将测试集行的变化反馈到变更提案中，会导致未见样本信号的泄露。**应用。**（如果设置了 `approve_each_round`，则先展示差异和简要理由，并等待用户确认后再执行；若用户拒绝，则视为本轮回滚，且用户的理由将记录在 `change.md` 中。）在应用之前，对拟议的变更进行一次“去冗余”处理：删除所有空话、对默认行为的重复陈述，以及缺乏实际操作意义的建议（如“要小心”“按步骤思考”）。每一轮都这样做——冗余会以一句听起来合理的句子为单位逐渐累积。然后，在用户的代码库中直接编辑文件，并将差异保存到 `vN/change.patch`，以便能够干净地回滚（对于完全没有历史版本的新产物，应与 `/dev/null` 对比生成差异）。该补丁即为本轮变更的记录（也是完整视图中差异面板所呈现的内容——可在摘要中点击某个变体行查看），因此请基于用户的真实源码路径生成补丁，而非 `.claude/hillclimb/` 下的临时副本，使每个补丁块都能直接应用于用户的仓库；如果循环是在临时副本上迭代，则应使用原文件生成差异。此外，还将变更后的完整产物——系统提示词、技能文件或其他正在迭代的对象——快照保存至 `vN/` 目录下（如 `vN/skill.md`），以便每一轮都能独立检查，而无需重新应用补丁序列。如果补丁触及 `_state.json.harness_paths` 中列出的路径，下次运行时将触发 `--approve-harness` 检查：向用户展示差异并等待其确认，而非让本轮在无人干预的情况下自动执行。

**运行。** 执行完整的评估——所有案例，按照选定的重复次数。每轮都运行全集，可确保历史中的各项得分具有直接可比性。将运行器的并发数保持在上限（直至达到速率限制）——循环的节奏由每轮的完成速度决定——同时确保重试策略带有抖动退避（步骤 0.5）；在共享配额的环境中，高并发配合热重试循环会将他人的突发流量转化为你的零分结果。将各案例的详细结果写入 `vN/results.jsonl`，汇总结果写入 `vN/summary.json`，并将每个案例的完整日志保存至 `vN/traces/<id>_rep<k>.json`（训练集与测试集的隔离在交接时强制执行——分析步骤仅传递训练集文件，而非通过从磁盘上屏蔽测试日志来实现，因为报告及步骤 5 的前后对比仍需这些测试日志）。（轨迹分数表 `trajectory/scores.tsv` 由报告生成器——无论是完整版还是精简版——根据这些文件重新生成，运行器不负责写入。）

在每轮正式运行前设有三道关卡，每道最多耗费一个案例的代价，而正式运行则会消耗全部案例：

- **前提探测配置参数。** 若本轮变更涉及的是配置层面的参数（如模型参数、工具配置、`effort` 等——凡是在创建或调用时由服务器端验证的项），而非提示词内容，则应先运行一个案例，确认该参数被接受，并且在响应中得到正确回显。最轻微的情况是出现明显的验证错误；更严重的问题则是运行器将配置错误降级为重试或零分，却仍然继续执行剩余的所有案例。
- **打印已解析的范围。** 在正式运行前，让运行器输出其实际解析的结果——包括案例数 × 重复次数 × 模型 × 预估成本——并与批准的计划进行比对。若预演解析的案例数与计划不符，则应立即停止，而非仅发出警告。
- **无人值守或高成本运行前的金丝雀测试**——先运行一个案例，将其错误和延迟特征与基线对比；若发现性能下降，则应暂停，避免浪费本轮资源。

每轮的基础架构健康状况——重试、超时、服务模型不匹配等——均记录在 `errors.jsonl` 中；若某轮的错误特征与基线存在显著差异，则该轮作废并重新运行，而不作为可比较的数据点。**记录并汇报。** 更新 `_state.json`（包含本轮编号，以及如果本轮测试分数优于历史最佳则更新 `best` 字段）。您所汇报的任何数值——包括私有预留测试用例及其原始结果——都必须写入已记录的 `vN/` 目录结构中，而不能仅保留在运行日志中。如果会话或机器是临时性的（例如 CI 构建器或远程会话），还应将每轮的 `vN/` 目录复制到持久存储中，以确保数据不会丢失。在所有用例都完成之前，不要汇报本轮得分——部分读取可能导致指标出现虚假波动；如确需在运行过程中汇报，请标注为“已完成/N”。每轮结束后，将状态表（行格式见下文）写入 `narrative.md` 的顶部并保持最新——该表即为每轮的正式记录，即使无界面运行时也保存在磁盘上——随后在聊天中简要汇报一句：“v3 测试 0.71 → 0.74，变化：<一句话>”。使用完整版报告时，应在标题后附上指向 `report.html#tab=summary` 的链接，而非直接展示表格——“Summary”标签页即为此表格，可排序且一键展开差异对比面板。对于仅显示主指标的精简版报告，则将 Markdown 表格粘贴在标题下方，因为它包含了护栏、性能、`$/run` 和 `spend` 等列。其中，`$/run` 和 `spend` 均来自 `cost_usd`（步骤 3：由完整版查看器在文件存在时自动计算，否则由您根据每行的 `model` × `usage` 手动计算）。若按预算跟踪支出，则累计支出为所有 `vN/results.jsonl` 中 `cost_usd` 的总和，再加上各变体 `errors.jsonl` 附带文件中记录的失败尝试所产生的计费用量（失败产生的费用仍计入总支出）——切勿使用持续累加的计数器。行格式如下：

> | 轮次 | 变化（一句话）    | 测试 | 训练 | 每轮耗时 | 输出 token 数量 | 工具调用次数 | $/run          | 支出  |  
> |-------|----------------------|-------|-------|--------|---------------|--------------|----------------|--------|  
> | 0     | 基线             | 0.62  | 0.60  | 19.8   | 480           | 3.1          | $2.60          |  2.60  |  
> | 1     | “何时搜索”规则  | 0.70  | 0.73  | 19.5   | 492（1.0×）    | 4.2（1.4×，上升） | $2.97（1.1×）   |  9.70  |  
> | 2     | 努力程度=中等    | 0.68  | 0.71  | 11.2   | 310（0.6×，下降）  | 3.0（1.0×）   | $1.40（0.5×，下降） | 12.90  |  
>  
> 至今最佳：第 1 轮（测试 0.70）。下一步：将第 1 轮的规则与“努力程度=中等”相结合，并重新检查延迟。

每轮评分完成后，还需 **重写 `narrative.md`** ——这是一份由模型生成的、关于所有测试框架变更及其迄今效果的动态执行摘要，而不仅仅是本轮的结果。阅读所有 `vN/change.md` 中的变更说明和 `vN/summary.json` 中的评估结果，撰写一段简短文字，说明当前哪个变体表现最优，并从变更角度解释其原因（例如：“v4 的召回率最高，但 v3 通过优化提示词，在牺牲少量召回率的情况下提升了精确率，从而获得了更高的综合得分”）。每轮均需完全覆盖该文件——它记录的是截至目前的故事全貌，而非追加式的日志。请将当前状态表置于段落之上。完整版查看器的 NARRATIVE 面板会渲染此文件；即便不使用完整版查看器，打开 `narrative.md` 也能了解全局——无论哪种方式，保持其最新状态，都能让用户（或恢复的会话）在任意时刻通过一页内容掌握当前进展。在状态表旁边，重新生成 **HTML 报告**，以便用户能够直观地深入查看：当报告构建器位于磁盘上（EAP 安装时），运行 `.claude/hillclimb/<flow>/` 下的 `shared/evals/report/build-report.mjs`；否则运行 `shared/evals/report/build-report-lite.mjs`（这两个路径均相对于本技能的根目录），使用 `node` 或 `bun` 执行（选择逻辑及无运行时回退机制详见 build-eval.md 的“报告构建器”章节）。完整版查看器会将一个自包含的 `report.html` 写入流程目录中，其中包含执行摘要表格、趋势图表、并排的对话记录对比以及每轮的差异；精简版构建器则只输出一份摘要表格，并为每个用例添加一行，显示每轮的主要指标及指向各轨迹文件的链接。两者都会写入 `trajectory/scores.tsv` 文件。它们读取的是你刚刚写入的同一套 `summary.json`、`results.jsonl`、`traces/` 和 `change.*` 文件，因此无需额外生成任何内容——务必在本轮的执行程序退出后再运行，切勿在其仍在追加数据时运行（否则，部分版本的行会显示截至当前已处理的用例数量——完整版查看器会将其标记为“部分运行，已完成 N/M 个用例”，而精简版报告则仅显示较低的用例计数——两种情况都不要发布）。**报告仅供用户在需要时查阅，而非必须主动推送的信息**：在基线结束后和最终汇总时分别给出报告路径，在每轮的状态消息末尾以单独的一行提供该路径，其余时间无需提及——不要对报告的大小、备注或是否应打开它发表任何评论——除非构建过程非正常退出，或用户主动询问。如果用户要求查看报告未展示的内容（对于精简版报告，这可能是一张图表、页面上的差异对比，或一个仪表板），请按照 `shared/evals/report/SCHEMA.md` 中“`report.html` 之外的页面”一节的要求，将其作为附加页面与 `report.html` 并列生成，绝不可替代后者；未经请求，不得主动提供此类页面。**在引导用户查看新轮次的报告之前，请先对新轮次的行重新执行步骤 0.5 的抽查**：确保所有指标和性能列均存在、合理且与本轮的变化一致——例如，费用为 `$0.00`、延迟为 `0.0s`（或对应的 `usage` / `latency_s` 字段在相关行中缺失），或者某列的变化方向与预期不符，这些都属于执行程序的错误，而非结果本身。此外，还应抽查：完整版查看器下，单个对话记录是否被渲染为独立的回合卡片，而非单一文本块；精简版下，关联的轨迹文件是否为由 `{role, content}` 回合组成的 JSON 列表。其余均为完整版查看器的功能：`build-report.mjs <flow> --check` 可在不实际渲染的情况下检查常见的轨迹格式错误；`build-report.mjs --index .claude/hillclimb/` 会在多个流程并行运行时，生成一个 `index.html` 文件，链接到每个子流程的报告；而对于结构不同的运行目录，则需根据 `shared/evals/report/SCHEMA.md` 编写少量适配代码——通常只有几十行：从原始内容块中组装出 `Turn[]` 数组，从 `usage` 计算出 `RepResult.perf`，并声明你的指标——这些都将直接传递给 `render()` 函数。**在你做出推荐之前，所有用于支持推荐的指标都必须有据可查——体现在数据行中、状态表里、报告里。** 如果在循环过程中，你在临时脚本中计算出一个新指标，并且它改变了你原本的选择，那么请立即停止并将其纳入流程：把它添加到运行器的评分器中，使每一行都包含该指标；在 `_state.json` 的 `metrics` 字段下声明它；就地重新对现有变体进行评分，确保比较条件一致；然后重建报告和状态表——再提出推荐。用户应当仅凭流程目录（`report.html`、`narrative.md`、`vN/` 文件）就能核实你推荐背后的每一个数值，而无需依赖你的聊天记录。对于那些本质上是聚合指标的项目——例如副本间的一致性，或任何按案例而非按行计算的指标——同样适用这一规则：在 `metrics.md` 中放置一张按变体对比的表格，让记录本身承载比较结果（完整视图会渲染该表格），而不仅仅是用文字描述。

如果评分器是以模型为评判标准，且分数跃升幅度远超合理范围，**在将其视为好消息之前，先将其视为可疑情况**：人工抽查几条输出结果，向用户展示，并确认评分器并非在奖励因变更引入的表面模式。将这一疑虑以一行“suspicious”字符串记录在该轮次的 `summary.json` 中，以便将该疑虑与变体关联起来（完整视图会以警告标识显示）。直到你亲自检查之前，被操控的 LLM 评分器看起来就像取得了突破。

**将“机制是否启动”与“是否有效果”区分开来。** 将机制触发的先行指标——例如智能体写入内存的频率、调用工具的次数、生成产物的情况——单独列为一列，与最终得分分开。这相当于环内版的 Step 0.5 接线探针：探针证明了机制*可以*起作用；而这一指标则证明了本轮机制确实*发挥了作用*。如果分数发生了变化，但机制的触发率却没有变化，那很可能是噪声或测试框架的伪影——在叠加下一次变更之前，务必查明原因。

如果训练集表现提升而测试集未见改善，说明变更过拟合于分析器读取的样本——撤销变更，并在下一轮尝试不同的方向。如果某一轮在训练集上也出现退步，则应在下一轮前先撤销，不要在此基础上继续叠加变更。如果训练集*下降*而测试集*上升*，在副本数较少时应视为噪声——只有当这一模式在第二次运行中重复出现时，才保留该变更。遇到平局时，优先选择较晚的版本。

**做出决策。** 检查 Step 2 中设定的停止条件。将预算视为**指导而非硬性约束**：当接近预算且分数仍在上升，或仍有明显可行的想法尚未尝试时，应如实告知并主动提出延长预算，而不是戛然而止。反之，如果连续几轮的分数变动均在*噪声范围内*——点估计有所波动但置信区间相互重叠——即便数字看似在上升，你也很可能已陷入 plateau：在开启新一轮内容迭代之前，先执行 Step 4.5 的归类分析。若需收窄某个变体的置信区间，可在其 `results.jsonl`（以及基线的对应文件，以保证公平比较）末尾追加更多副本数据并重新构建——报告会根据现有数据重新计算，无需新建一轮目录。否则，一旦 Step 1 的目标达到 plateau，应在停止前主动提议调整目标：选取还有较大改进空间且尚未尝试的护栏指标或性能字段，在不回退已有成果的前提下，让分析器针对该指标再跑一轮——但务必事先征询用户意见，因为目标由用户设定，他们可能认为任务已完成。只有当所有指标均无明显提升空间，或已汇报当前最优结果并征求用户意见时，方可停止。如果用户要求定期汇报，且已达到预定的置信区间，则汇报后等待下一步指示；否则，继续循环。

## Step 4.5：当循环停滞时，先归类再精耕细作分析→应用→运行的循环假设每次失败都是由你正在调优的工件造成的。一旦容易发现的内容缺失被填补，这一假设就不成立了——剩余的失败越来越多地源于评分器、测试框架、工件的结构，或是单纯的随机波动，而再进行一轮内容迭代也无法解决这些问题。判断标志是**连续两到三轮中，尽管做了本应有帮助的改动，测试得分仍未超出噪声范围**。遇到这种情况时，应停止继续迭代内容，转而用一轮时间进行归因分类。

启动一个新的分析子代理（与第4步的“分析”环节保持同样的隔离级别），将所有剩余的训练集划分失败按根本原因归类，并读取每份记录以确定其归属：

| 分类 | 判断依据 | 不做新一轮内容迭代时的应对措施 |
|---|---|---|
| **工件缺失** | 模型从未见过所需的事实；记录显示模型在猜测或检索 | 这是本轮的核心问题——继续推进 |
| **评分器分歧** | 模型输出在你看来是正确的，但评分器判定为错误；或者提示与评分标准要求不一致 | 修复评分器，然后基于已存储的输出对*所有*变体重新评分。覆盖前，请比较新旧评分结果——有多少案例的评分发生了变化，变体的排名是否改变？如果此前的最佳方案仍是最佳，且其相对于基线的优势未受影响，则继续；若排名发生逆转或优势缩至噪声水平，则说明前期迭代是在优化错误的信号：展示前后对比表，并建议从基线重新开始本轮循环。 |
| **测试框架/基础设施** | 在模型产生可评分输出之前，案例就已报错——认证失败、超时、限流、环境配置问题。某些框架会将错误“评分化”而非直接报错：那些得分为零且记录中带有基础设施标记（重试次数耗尽、停滞上限、空输出）的案例也归于此 | 修复测试框架；在此期间，将出错案例从分母中剔除。对于被评分化的零分案例，在比较分数前先明确处理规则。 |
| **结构性问题** | 内容确实存在于工件中，但模型未能触及；或者同一问题在各轮中反复出现；或者某一维度（如某种语言或某个供应商）无论你优化哪个特征都表现不佳 | 重新组织——将重复的事实合并到一张表中，拆分单体文件，修正路由逻辑——而不是继续添加更多未被触及的内容。 |
| **随机波动** | 相同代码的运行在通过与失败之间频繁切换，且这种波动幅度与轮间差异相当 | 此处已接近噪声下限。报告目前最优结果；提议增加样本量或更换优化目标。 |

若有失败无法归入上述任何一类，这本身也是一种信号：你正在调优的工件可能并非该场景的瓶颈——此时应建议更换优化目标，而非强行将其归入某一类别。

将各类别的数量写入`vN/change.md`，取代该轮的内容差异报告，并告知用户：剩余的M个失败中，有N个并非工件缺失——以下是每个集群需要解决的问题。随后按类别分别处理，不再对所有失败统一执行新一轮内容迭代。

这一过程还会暴露出两种每轮分析器无法识别的模式：- **长尾问题。** 分析器的“最常导致评分下降的单一行为”总是集中在得分最低的那个桶上，而不会形成一个由许多小桶组成的长尾，每个小桶只扣一两分。如果分类结果显示有十几个维度，每个维度的失分都不超过2分，且这些维度都没有被人工标注覆盖，那么一次性的**广度遍历**——并行为所有未覆盖的维度起草最低限度的覆盖——一次性就能比串行循环十轮覆盖更多的范围。这故意打破了“每轮只改一处”的原则：这些维度是相互独立的，关注的是覆盖率而非归因，而且没有哪个维度单独改动足以产生可测量的分数变化。
- **中期评分漂移。** 第0.5步已经证明了评估在初始阶段是可信的。如果某个评分细则对某项功能存在细微偏差，或者标准答案已经过时，这种问题并不会表现为评分的异常跳跃，而是表现为无论你添加什么内容，该维度的得分始终纹丝不动。当某个桶在你看来正确的三轮内容输入后仍然毫无进展时，在撰写第四轮内容之前请重新审视其评分细则；如果确实修改了细则，则需要对所有内容重新评分，量化评分的变化，并与用户共同决定现有各轮的结果是否仍然有效。

## 第5步：报告与交付

循环结束时，将代码库回滚到测试中胜出的版本。报告的标题应为**测试得分差值：基准 vs 胜者**——这两组数据你已经在每轮运行中获得了。（如果第3步选择了不分割，则报告整体得分差值，并标注为“方向性”；如果选择了可选的三分法，则此时仅对基准和胜者运行预留的测试子集。）最后再重写一次`narrative.md`，将其格式化为最终的状态表（置于顶部，如第4步所示），后接四部分的执行摘要——**建议的变更**、**与基准对比**、**为何可信**、**还尝试过哪些方案**——然后再次生成`report.html`（使用完整版或精简版构建器，同第4步）；这份HTML报告将成为用户查看逐个案例细节的依据。与此同时，另准备一份简短的文本报告（若用户希望以Pull Request形式提交，则放在PR描述中；否则以Markdown文件形式提供）。该文本报告是`report.html`的**补充材料**，而非替代品，因此应在需要查看完整记录（完整版查看器）、跟踪文件（精简版）或逐案细节时指向它，而不应在正文中重复这些内容。报告内容包括：

- **标题：** 基线测试分数 → 获胜轮次的测试分数，各附置信区间，并标注差值。这是主要结果。训练分数提升只是辅助信息，而非核心结论。**如果测试分数的差值在零附近的噪声范围内——即置信区间重叠，或针对各案例的配对检验不显著——应明确指出，并建议暂不合并。** 对用户而言，“这一改动未带来明显效果，若预算充足我会尝试以下方案”比一个看似亮眼却微不足道的改进更有价值。
  
- **每轮表格：** 包含轮次、变更的一行简述、训练分数、测试分数，以及带有基线比率的护栏列。仅标记那些超出噪声范围的差值；对未达阈值的差值予以抑制或灰化，使用户视线聚焦于真正产生变化的部分。训练分数与测试分数并列呈现的是泛化差距的变化轨迹——若两者逐轮出现分化，应明确指出。

- 当前实际应用到代码库中的各项变更，每项均附来自 `change.md` 的一句话“原因说明”，并分别标注为 **`[REQUIRED]`**（修复了某个问题，例如目标模型上会报错的参数）或 **`[TUNE]`**（基于判断提升了分数，但用户也可合理选择不采纳）。这便于用户按需选择性地接受变更差异。

- **失败分类，当零分存在多种成因时：** 统计拒绝、运行时或服务端错误、超时等导致的失败数量，与真正的能力不足造成的失败分开列出——单一比率会掩盖真实情况。当循环中比较多个模型时，在报告差距之前先按模型分类失败类型：若某种失败模式仅由某一模型触发（例如该模型使用的工具调用规范被运行时环境拒绝），则此为运行时环境的缺陷所致，而非模型能力的差异；应在剔除这些尝试后重新报告差距。

- **若有多个模型将共享同一制品，则进行第二模型验证：** 在推荐获胜版本前，将其在其他模型上再运行一轮，并分别报告各模型的数据——失败情况往往与具体模型相关，在某模型上取得的优势未必能直接迁移到其他模型。

- **两到三组前后对比样本：** 同一提示在基线与获胜版本下的输出并列展示，让用户直观感受质量变化，而无需单纯依赖数值。选取能够体现变更目标行为的案例。

- **下一步计划。** 主动列出当前仍可操作的具体调整方向——“`effort=medium` 在延迟方面表现不错，但我尚未为此重新优化提示；`summarize` 工具的描述仍较模糊；可以考虑切换到 `claude-sonnet-5-5`”——而不是等待用户询问是否还有其他可能。凡被认为需要超出本次目标范围的更大调整，均应纳入其中。

报告的作用在于让使用者足够信任变更内容，从而放心合并。务必具体说明每项变更为何有效；仅写“重写了系统提示”是不够的。

如果评估脚本和日志目录尚未提交，请提供与 `build-eval.md` 第四节“使其持久化”相同的三种选项（提交评估脚本 / 提交评估脚本及日志 / 不做任何提交），并根据当前多轮结果更新文件数和大小统计。建议提交评估脚本——此次 PR 中的运行时环境变更仅占一半价值，另一半在于未来能在新模型上无需重建评估框架即可重新进行基线测试。

## 需要避免的失败模式- **不要触碰保留集。** 数据划分是区分真正改进与过拟合的唯一屏障。不要查看测试集的真实答案，也不要让测试用例的内容影响提出的修改——分析器读取训练数据，评分结果来自测试集，这道“墙”决定了结果的可信度。
- **确保真实答案不可被模型直接获取。** 如果待测模型能够从磁盘读取预期答案，优化过程最终会找到这条路径并“获胜”，却并未带来任何实质提升。应在结构上隔离答案，切勿依赖指令提示。在公开基准上，“可获取”还包括互联网——具备联网能力的代理可以检索到答案镜像（参见步骤3）。
- **不要轻信不合常理的分数跃升。** 当模型评分的提升幅度远超合理范围时，最可能的原因是评测被“攻破”，而非模型本身变强。在庆祝之前，务必人工抽查核实。
- **不要基于不可靠的评估指标进行优化。** 跳过步骤0.5意味着你可能是在针对一个失效的机制或错误聚合的总分进行调优——表面上“改进”的只是伪象，实际毫无收获。在首轮优化前，必须验证机制是否正常运行，并确认总分确实由各案例的原始结果重新计算得出。
- **不要在瓶颈处无谓地堆积内容。** 对于连续三轮未见进展的功能，不要一味增加内容，而应先查明问题出在评测者、测试框架还是架构设计上。步骤4.5就是用来排查这一点的。
- **不要将拒绝回答纳入平均得分。** 安全性拒绝回答并非能力缺失，被测试框架终止的尝试亦非如此。应为每次尝试记录失败类别（拒绝/框架或服务端错误/超时/真正失败），并将拒绝率零值与能力零值分开报告；同时预先定义异常零值的清洗规则（例如：在耗时和请求数远低于任务正常下限时仍得分为0），并分别报告原始值与清洗后的值——规则应在评分产生前确定。
- **不要让平台在优化过程中发生变动。** 如果服务端平台或测试框架在运行中改变了执行语义（如环境复用、批处理、默认配置等），各轮次的结果便不再具有可比性。在整个优化周期内锁定运行环境及其依赖，并通过运行产物（如每个案例使用独立环境）来验证所依赖的语义，而不是凭空假设。
- **不要基于无法解释的收益进行优化。** 如果评分有所提升，但你无法指出具体是哪种行为导致了这一变化——例如机制触发频率的变化或追踪日志中的特定翻转——那么这次“胜利”很可能只是噪声或测量误差，而非真正的改进。每项改动都应与某个机制相关联；对于那些无法关联的改动，要保持警惕。
- **不要以单个案例推及全局。** 仅从一次失败中看到某种模式就据此重写整个提示词，这是导致评分下降的最常见原因。分析器应引用能说明改动依据的追踪日志，描述的是“行为”而非简单粘贴失败内容到提示词中；且改动的力度应与表现出该行为的案例数量相匹配，而非仅针对一个典型的失败案例。
- **不要无记录地合并改动。** 将多项无关的修改打包成一轮的改动，会导致即便有效也难以定位具体贡献，而一旦造成负面影响也无从回退。每轮只提出一个想法：针对案例失败原因的一个假设，即使其补丁涉及多个位置。
- **不要做微小到无法察觉的改动。** 改动的最佳收益若处于噪声水平之内，其去留很大程度上取决于偶然因素；一连串这样的改动只会白白耗费资源，却毫无收获（步骤4）。
- **不要让提示词中充斥冗余信息。** 若缺乏每轮的精简环节，提示词会逐渐积累大量模糊且无法证伪的建议，既浪费token，又稀释了关键指令。
- **不要丢失运行状态。** 如果会话被打断，下一次会话应能读取`_state.json`文件和`vN/`目录，精确接续上一次的进度。应在每轮结束后立即保存状态，而非等到最后。如果提案者/分析者以独立的长期会话运行，则其工作产物——接手的追踪日志和评分，以及每项改动的理由——也应存放在流程目录下，以便中断的循环能够重建提案者的工作，而不仅仅是恢复评分。
- **不要修改用户明确禁止的部分。** 用户已在步骤1中告知哪些部分不可触碰。若某项改动虽提升了评分，却违反了用户设定的约束，则不能视为改进。
- **不要把预算当作不可逾越的障碍（或完全忽视它）**——当成本是约束条件时。应根据`results.jsonl`文件重新计算累计支出（包括所有`errors.jsonl`中失败尝试的计费用量），并在每轮检查是否超出步骤2设定的上限。若预计会超支，应事先征询意见。同样，当测试仍在持续提升时，也不应在达到预算上限后立即停止，而应主动询问是否继续。
