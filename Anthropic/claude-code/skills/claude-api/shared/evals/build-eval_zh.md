# 为基于 Claude 的应用构建评估体系

> **如果您通过 `/claude-api build-eval` 进入：** 这就是您需要的文件。如果用户提供了参数，将其视为他们对第一个问题的回答——即他们希望衡量的内容。直接开展访谈流程，不要向用户总结访谈内容，只需按顺序提问并完成各项确认。我们的目标是生成一个用户信任且可运行的评估方案，而非一份关于评估的文档。

本指南适用于用户希望评估其 Claude 应用是否正常工作的情况——通常是在即将进行某些变更（如迁移到新模型、重写提示词、添加工具）之前，需要确认这些变更是否有效。您的任务是构建一套可用于辅助部署决策的评估体系。

从这个角度来看，一个评估体系包含三个要素：**一组输入示例**、**一种针对每个输入运行应用的方式**，以及**一种对每个输出进行评分的方法**。运行器通常是一个简单的 Python 脚本；也可以是命令行工具、pytest 测试套件，或其他适合其技术栈的形式。具体实现的形态并不关键，关键在于用户看到输入后能说“是的，这些正是我关心的场景”，看到评分后能说“是的，这确实衡量了我想关注的内容”。请勿强加任何框架，而是根据现有代码库的结构来适配评估体系。

在整个过程中，请始终以推荐为导向：每一个决策都通过 `AskUserQuestion` 工具提出，您的首选选项置于首位并标注为“（推荐）”，这样信任默认设置的用户只需几秒钟即可点击确认，而不信任的用户则可在其真正关心的环节进行调整。相较于从零开始回答开放式问题，用户更容易接受“这是我建议的做法——可以吗？”这样的引导。

> **与用户的沟通。** 这些步骤是您的执行计划，而非逐字解说的脚本。面向用户的消息应简明扼要、聚焦结果：您构建了什么、得出了什么数值、需要用户查看哪些内容、以及打开相关文件或链接的路径。除非用户主动询问，否则无需逐一说明当前所处的步骤、正在编写的文件或内部进度。每一步只需一次简洁的更新；在聊天中，避免罗列单个案例、提示词或各案例的分数，而应直接提供 `report.html` 的路径及一行概要性标题——仅当有明确理由让用户优先查看某些特定案例时，才在聊天中特别提及一两个案例。当需要做出决策时（例如评分方式、输入来源、何为“良好”、哪些安全约束重要等），请使用 `AskUserQuestion` 工具，而非自由文本描述：可将最多四个相关问题合并为一次调用，为每个问题提供两到四个具体选项，并将您的推荐选项置于首位且标注“（推荐）”；请勿自行添加“其他”选项——该工具会自动附加一个自由文本输入框。如果 `AskUserQuestion` 不可用（无界面运行），则改为每次只提一个问题。

有两个环节必须获得用户的明确同意——输入和评分方法。这两个环节都是实实在在的暂停点：先陈述您的方案，征得批准，然后**等待明确的“是”**——而不是沉默，也不是您自认为“没问题”的判断。如果达成一致经历了多轮讨论，请在一条消息中重述最终版本，并在继续推进前再次确认；经过五次迭代后，双方很容易忘记实际达成的共识。只有在这两个地方才需等待文字回复，其余环节均为指导性建议，您可以根据用户的具体情况灵活调整。

**请在开始第 0 步之前立即阅读 `shared/evals/eval-audit.md`，并在整个过程中始终保持可见。** 这份文档是所有评估体系必须满足的健康检查清单——涵盖任务设计、运行框架设计、指标规范性、评分器设计，以及评估体系能否检测到用户期望的变化。在构建过程中，将其中的每一项视为默认要求，确保运行器、评分器和案例集均符合标准；若用户已提供现有评估方案，则以此作为验证依据；在首次正式付费运行前，还需对照您构建的内容再执行一次检查，并按照文档第 6 节的要求提交报告。

---## 步骤 0：明确评估目标

如需查看该流程从头到尾的完整示例——包括用例、标注策略、运行器以及五轮迭代优化——请参阅 `shared/evals/examples/clawd-triggering/`（位于 EAP 包和源代码仓库中；CLI 不会将其解压，因此如果该目录不存在，请跳过）。

首先应明确用户真正希望衡量的内容：

> 您究竟想评估什么——是哪个用例或功能？如果该应用涉及多项任务，您首先需要为哪一项得出量化指标？

一个应用往往有十项值得评估的内容——这里是一个分类器，那里是一个摘要生成器，还有其他地方的代理循环——它们所需的输入和评分方式各不相同。请先确定其中一项。每次评估只针对一个流程，不要试图构建一个“大一统”的基准测试。如果用户在调用 `/claude-api build-eval` 时已指定了参数，则以此作为答案并予以确认，而无需重新询问。

接下来，请与用户确认该流程中“应用”的具体含义。找到入口点：即接收用户输入并产生关键输出的函数、端点或脚本。阅读相关代码，了解所使用的模型、**其调用的提供商**（Anthropic 官方 API、AWS 上的 Claude Platform、Amazon Bedrock、Vertex AI、Foundry 等）、系统提示词、工具集，以及输出的格式（文本、JSON、工具调用轨迹、文件等）。如果入口点是一个流式代理或封装层，且未暴露 `model`、`usage` 或 `stop_reason` 等信息，请建议对其最终事件进行小幅修改，以便运行器能够逐个用例记录这些数据——缺少这些信息，报告将无法计算成本或标记截断问题。运行器编写的任何代码（包括评判逻辑）都必须使用同一提供商的客户端类和模型 ID 格式；有关各提供商的具体细节，请参阅 `SKILL.md` 及其引用的 `shared/` 相关文档。

如果该流程依赖于实时的外部状态——例如数据库、搜索索引或客户的私有文档——请在此阶段予以记录。您将需要准备测试数据或搭建测试实例，以确保评估的可复现性，而这些资源的有无将影响后续的所有环节。只要可能，应尽量通过真实的入口点来测量实际的*结果*。只有当无法安全或可重复地执行时——例如工具具有真实世界的副作用（发送邮件、写入数据库、删除文件）或依赖于已发生变化的实时外部状态——才应模拟这些工具（可选择回放预先录制的工具响应），并以模型的工具调用及响应文本作为评价对象，而非下游的实际效果。

此外，还需询问除了用户消息之外，系统在每个样本中还需要哪些内容：

> 除了文本之外，向该流程发送的请求还包含哪些内容——附加的文件或图片？用户元数据或个人资料？先前对话的摘要记忆？还是供代理运行的容器镜像或工作空间？

这一回答将决定评估“输入”的构成。通常情况下，输入只是一个提示字符串；有时则还包括 PDF 文件、用户档案、对话前缀，或指向用于代理环境的 Docker 镜像的路径。不要强行规定固定格式，只需弄清楚应用实际需要哪些数据，确保每个评估用例都能携带入口点所需的一切。如果输入是多轮对话，还需明确评估的对象：仅评估最终响应、分别评估每一轮助手回复，还是整体评估整个对话轨迹。单轮回复本身可能看起来不错，但若其基于此前的一次错误决策，则按轮次评估会将其判定为“良好”，而整个对话却并不理想。默认情况下应评估对话的整体结果，除非用户明确要求按轮次评估。

## 步骤 1：寻找或构建输入集合

向用户提问：

> 您是否已经拥有部分所需材料——例如一组测试用例（即使是非正式的表格）、一位评分员或评分函数，或者一段能够对输入执行应用的测试脚本？**凡是现有的，就利用；只构建缺失的部分。** 现有的评分器只需封装，不必重写；现有的适配器只需添加一层薄层，使其在第三步输出符合 `results.jsonl`/`traces/` 格式的文件（该格式是报告唯一需要遵守的契约——参见 `report/SCHEMA.md`），而无需用脚手架代码完全替换。在动笔之前，先明确哪些部分复用、哪些部分新增。**如果有案例：** 先通读这些案例，然后针对案例、运行器和评分器执行 `eval-audit.md` 中的评估流程，并在决定复用程度之前，按其第6节的要求汇报发现。有两类问题应直接询问用户，而非自行推断：一是输入是否仍能代表真实流量，二是**预期输出的来源**——是人工编写、人工验证，还是某个模型的输出（具体是哪个模型）。如果黄金标准来自待比较的模型——尤其是在迁移场景中——那么基于参考匹配的评分会鼓励对那个模型的模仿；对此应予以说明，并优先采用评分细则或成对评判，或者先对样本进行人工验证。如果用户与审计结果都认可，则以此为起点并复用现有评分逻辑；若仅部分认可（“输入没问题，但评分凭感觉”），则保留输入并重新构建评分逻辑；若完全不认可，则将其视为众多来源之一。

**无论如何，** 都要询问真实的输入可能来自何处。按照以下顺序逐一排查，选用第一个既可用且用户也愿意使用的来源：

1. **生产环境的转录本或日志。** 这是保真度最高的来源。询问数据存放在哪里（如 Datadog、数据库、S3 或日志端点），以及是否可以获取样本。在提取任何数据之前，务必确认该来源**在实际操作中可用**，而不仅仅是当下可得：*是否存在会强制删除这些数据的保留策略？数据中是否包含不能存储在代码仓库中的个人敏感信息？* 如果评估所依据的数据用户无法长期保存，那么下个季度就无法重复执行该评估——这比使用可重复的合成数据更糟。若上述任一问题的答案为“是”，则有三种选择：仅将**标识符**存储在代码仓库中，让运行器在评估时实时拉取真实输入（确保无任何敏感数据落盘）；让用户自行拉取并匿名化样本；或者将每个真实输入改写为保持结构与难度但替换掉识别性内容的合成输入（在使用前向用户展示改写后的样例）。
2. **错误报告、客服工单或“出错案例”。** 最有价值的输入往往是那些曾被用户投诉过的案例。询问是否有专门的渠道或跟踪系统用于收集此类数据。
3. **由用户手动编写。** 请用户提供五到十个随手想到的示例。这类示例往往偏向于用户认为重要的内容，而非实际发生的高频场景，因此应将其视为种子样本，而非完整数据集。
4. **根据代码库自行合成。** 阅读系统提示、工具描述以及相关文档或测试用例，生成能够覆盖业务流程的候选输入。这是保真度最低的方式——务必向用户说明这一点，且切勿贸然实施：首先从用户处获取三到五个真实示例（来源3），并请用户提供一句关于该领域“难例”的定义，然后再在此基础上合成变体，而不是仅凭提示词凭空捏造。若缺乏真实案例作为锚点而纯靠提示词合成的评估，往往会过于简单，事后调整的成本甚至高于用户亲自编写案例的投入。首次评估时，输入样本的数量宜在15到100之间。少于15个样本，单个不稳定案例就会大幅影响评分；超过100个，用户实际上也不会逐一审阅，这就失去了签核的意义——对于较大的样本集，可让他们阅读分层抽样的子集，并借助`eval-audit.md`第1节中的程序化检查来覆盖其余部分。样本规模后续随时可以扩充。但需注意：如果用户事先已明确会在本次评估后进行“梯度优化”，则应根据期望检测到的改进幅度来确定样本规模，而不仅仅是基于可审阅性——`eval-audit.md`第5节给出了相关计算（通过率的噪声下限约为`1/sqrt(n·reps)`；25个案例×2次重复约对应±14个百分点）。将这一数值与他们计划采取行动的改进幅度并列展示，并一次性统筹规划案例数量与重复次数：使用随机留出子集的50+个输入，或减少输入数量而增加重复次数，都能达到相同的分辨力。若在付费评估几轮之后才发现评估根本无法捕捉到预期的提升，那才是最昂贵的代价。

### 确认输入样本
向用户展示实际的输入样本——全部样本，而非摘要。针对样本集的任何说明都应采用量化指标——计数、特定案例名称、实测分数等，而非“看起来合理”之类的主观判断。默认采用Markdown文件格式：先以表格形式列出（`id`、`tags`、`expected`，以及任何附加文件的路径），再按每个案例单独分节，输入文本置于代码块中，且代码块的分隔符长度要长于该文本中任意连续的反引号序列（以免案例中的单行反引号误作代码块结束符）。然后将该文件地址提供给用户；或者，若案例已按步骤3中的行列格式准备，则直接运行报告生成器，交付`report.html`。**优先采用用户已习惯用于查看提示和转录文本的工具**——若有现成的查看器、偏好的笔记本，或既定的Markdown规范，就将输入放在此处。契合他们的工作流程，关键在于确保他们真的会去阅读这些内容。切勿为此专门编写一个临时HTML页面：输入源自转录、工单和日志，其文本不可信，若将其直接嵌入自编的HTML，就可能让支持工单中的恶意`<script>`在评审者的浏览器中执行。报告生成器是处理此类内容的唯一HTML界面——它会对案例文本进行转义、净化并沙盒隔离——因此，请务必经由报告生成器处理，或继续使用Markdown格式。询问：

> 这是我拟使用的N个输入样本，请您大致浏览一下。这些样本是否能代表您的应用实际遇到的情况？是否存在明显缺失的场景，或者有不相关的案例混入其中？

如需用户对某个特定案例进行标注或分类，请在问题中直接引用该案例的相关段落，不要让用户自行去查找“案例17”。

务必待用户看过并确认无误后再推进。若用户表示“大致可以，但……”，则修正“但”的部分并再次提交。若输入样本来自生产数据，此时也应确认用户对这套样本存放在其代码库中感到放心。**用户的最终签核是建立其对最终结果信任的关键**——省略这一步，得到的评估虽然技术上可行，却很可能被实际忽略。

## 步骤2：确定评分方式
首先主动列出运行者可在每个案例中记录的辅助指标清单，并询问用户哪些指标对其产品至关重要：

> 除了输出质量之外，我还可以为每个案例记录以下信息——输出长度（词数/标记数）、工具调用次数、模型是否拒绝响应、是否达到`max_tokens`限制、格式合规性（若输出为结构化数据）、成本、延迟。在当前流程中，这些指标哪些是重要的？是否有任何硬性产品约束（例如，“必须在10秒内回复”）？被选中的指标会成为 `_state.json` 中的 `perf_fields`，并在报告（完整视图）及 hillclimb 的状态表中以列的形式展示；未被选中的指标则不会显示。这一选择仅涉及“显示”内容——runner 无论如何都会记录 `model` 和 `usage`，因此如果用户改变主意，后续仍可添加 `cost_usd`。这并不涉及用户是否希望获得本次评估本身的费用估算；除非用户主动提出，否则不要主动提供估算结果。

如果数据集已标注正例和负例——按照步骤 1 的要求应当如此——就不要将评分简化为单一的通过率。对于分类任务，最自然的一组指标是混淆矩阵：分别报告正例的精确率和召回率、负例的特异性，以及假阳性率，并将其与总体准确率并列呈现。某个方案可能在整体准确率上“胜出”，却暗中以牺牲召回率为代价换取更高的精确率，或悄然提高了假阳性率，而单一数值会掩盖这些细节。将每个单元格单独列为一列，能让这种权衡在报告中清晰可见，便于用户判断自己更关注哪一方面。

接下来，对于每条输入，评估需要将应用的输出转化为一个分数或通过/不通过的结果。应选择与输出形式相匹配的评分方法——优先选用真正能衡量用户关心指标且成本最低的方案，但切忌因成本因素而采用程序化检查来判定本应由人工判断的属性。下文按成本由低到高排序；具体选择取决于输出空间是受限的还是开放式的：1. **程序化检查。** 完全匹配、包含子字符串、JSON符合模式约束、分类标签来自固定集合、代码可编译、测试通过。判定确定且无需人工参与。当输出空间受限时——例如一个数字、闭集中的某个标签、结构化数据，或仅需判断“通过/不通过”——应采用这种检查方式，以便评估的是答案本身，而非表达措辞。**当应用是一个作用于外部环境的智能体**（如编写代码、编辑文件、调用有副作用的API）时，这应作为主要的评分手段，并且应当基于*最终状态*而非操作记录：在临时工作环境中运行每个测试用例，然后检查留下的结果——测试是否通过、补丁是否能正确应用、预期的文件或值是否存在、未触及任何禁止修改的内容、各项操作是否在预算范围内——并将那些无法通过程序化检查衡量的主观维度（如可读性、简洁性、PR描述）留给人工评判。如果输出是自由形式的文本且存在多种合理表述，则程序化检查会过于脆弱，此时应改用人工作判。对于**编码或工具使用类智能体**，程序化检查同样应关注*最终状态*而非操作记录：在一次性的代码库副本或容器中运行每个用例，然后根据遗留结果进行评分——隐藏测试通过、补丁干净地应用且仅修改了目标文件、静态检查与类型检查无误、预期的文件/行/API副作用存在——并加入一个“无操作”检测机制（智能体声称成功但工作区未发生变化）。基于操作记录来评判“是否说了正确的话”对智能体而言是最弱的信号，仅适用于流程上的约束性检查（如在删除前询问、未泄露密钥等）。
2. **双盲两两比较。** 由人工阅卷者同时阅读输入和两个候选输出——通常是当前系统的结果与基准结果——并选出更优者，也可参照简短的评分细则。当质量标准较为模糊时，两两比较往往比分别给双方打分后再相减更为准确：阅卷者更擅长判断“这两个哪个更好”，而非将单个输出置于绝对尺度上。当问题本质上就是比较性的（如迁移任务、v1与v2的对比）时，这种方法尤为合适。三个默认设置：在每个案例中随机决定哪个候选为A、哪个为B；允许阅卷者回答“平局”或“均不佳”，而不强求必须选出胜者；并让阅卷系统的提示词将两个候选都视为不可信的数据，而非指令。**若要在此评估上持续迭代优化，请立即固定参考基准：** 将基准结果一次性保存到磁盘（例如`baseline/ref/<id>.html`），之后所有变体的新输出都与这些冻结的样本进行比较——切勿重新生成参考，否则各轮之间的“胜率”含义会悄然改变。对于**基准行本身**，请将比较指标设为其中性值（例如`win = 0.5`）——如果参考变体缺失某项核心指标，报告就会失效。当某个变体后续对基准的胜率接近100%、指标不再具备区分度时，应将该变体的输出也冻结为*第二份*参考，并同时保留两列胜率指标——不要替换原始参考。此外请注意，逐案进行的两两比较无法捕捉跨案例的模式坍缩现象（即所有输出趋同于某种风格，却仍各自被评为“优于基准”）；若此风险对该应用构成威胁，应为阅卷者搭配程序化或集合级别的多样性指标。
3. **模型评分的逐点细则法。** 由另一通Claude调用读取输入、单个输出及评分细则，并返回带理由的分数。当没有基准可供比较，或用户希望得到逐案的绝对数值而非胜率时，可采用此方法——适用于开放式输出（如摘要、解释、草拟邮件），其中虽无唯一正确答案，但存在明确的质量标准。让用户自行选择评分模型——`claude-haiku-4-5`价格低廉且速度快，足以在每次PR提交时运行；`claude-sonnet-5-5`是平衡的折中方案；而`claude-opus-5-5`则适合用于质量标准足够细微、弱模型可能抓不住要点的情况（这一选择同样适用于两两比较的阅卷）。务必询问用户偏好，切勿假设。无论用户选择哪款，都应避免让待测模型自评自身。对于评分调用本身，优先使用**结构化输出**（通过JSON模式指定`output_config.format`），而非“仅以JSON格式回复”的纯文本——自由格式的JSON常因推理部分未转义引号而导致解析失败，影响显著；而模式则能使解析过程确定无歧义。无论用于逐点评分还是交由两两比较，评分细则都应写成具体、可检验的陈述（如“回复至少引用上下文中的一个来源”、“回复未捏造API参数”），而非模糊的等级量表（如“按1–5级评价帮助程度”）。
4. **人工抽样检查。** 对于连评分细则都难以制定的输出场景（如“这份法律文书是否论证严谨？”），坦诚的答案可能是：少量人工标注的样本，其价值远胜过百份模型评分。向用户推荐一小批精心挑选的样本供其手动评分，并明确告知这会限制评估的执行频率。大多数案例除了输入之外，还会附带一个 `expected` 字段，但其具体含义取决于评分方法——它并不总是标准答案。对于程序化检查，它是明确的目标值；对于成对比较，它是用于对比的基准响应；而对于逐项评分的量表，它可能是评委阅读的针对该案例的评分说明文本。让数据结构由评分器来决定，而不是反过来。

在提出评分量表或评价标准时，请展示你的思考过程：列出你纳入的标准，以及曾考虑过但最终舍弃的标准，并简要说明原因，这样用户可以随时补充遗漏的内容，而不会怀疑你是否真的考虑过这些因素。当评价体系同时包含正面和负面指标时，应优先报告混淆矩阵相关的指标——如精确率、召回率、特异度，而非仅用准确率。将每项标准提炼为背后的通用原则——如果用户提出“不应引用维基百科”，就写成“引用可信来源”，而不是硬编码某个特定领域；同时确保两项标准不会重复衡量同一本质内容。当用户明确表达某种权衡取舍时（例如“越短越好，但不能以牺牲完整性为代价”），应优先采用可连续量化并反馈的指标，而非简单的通过/不通过阈值；阈值可以事后设定，但二元化的评分会丢失这种权衡的细微差异。此外，若某项标准涉及可验证的事实（如“API 返回字段 X”），应在正式纳入前主动对照文档或代码进行核实——评分量表和其他生成文本一样，也容易出现幻觉。

无论评分的是何种质量指标，都应在每个案例中记录用户从上方菜单中选择的辅助指标。**先以绝对数值呈现**（如“每轮 19.8 秒，每次调用 0.031 美元，输出 480 个 token”），再以相对变化形式说明（如“比基准快 33%”）；用户在实际生产环境中感受到的是绝对值，而没有绝对值的百分比则会掩盖到底是 2 秒还是 20 秒的差异。将这些辅助指标作为独立列与质量得分并列，而不是将其合并到质量得分中。

对少量案例运行评分器，并将评分结果与模型输出并列展示。在抽象层面看似合理的评分量表，实际运行时可能奖励了错误的行为；发现并纠正这一问题的唯一途径，就是观察其真实表现。

### 确认评分方法

将试点案例按步骤 3 中所述的格式写入 `.claude/hillclimb/<flow>/baseline/` 目录（`results.jsonl` 行 + `traces/<id>_rep0.json` 文件），然后在该流程目录下运行报告生成器（参见步骤 3 中的“报告生成器”部分），并将生成的 `report.html` 提供给用户——用户正是通过这份报告而非聊天摘要来审阅试点结果。使用完整版查看器时，引导用户进入“对话记录”标签页，逐一点击每个案例：他们应当能看到完整的交互过程（系统提示、每一次工具调用及结果、模型响应）以及评分结果和评委的评语。使用精简版报告时，每条案例记录都链接到对应的追踪文件——请用户打开两三个案例，仔细阅读其中的交互内容。**如果案例中包含附加材料**（如输入的 PDF 或图片、生成的 HTML/SVG/图表，以及模型写入的文件），也要确保用户能够查看这些内容：使用完整版查看器时，按照下文“使附加材料可见”的说明填充 `attachments` 字段，使其在“对话记录”标签页中正常显示；使用精简版报告时，则在交接信息中注明这些附件的路径。务必在请求确认之前完成上述操作。用户无法对尚未阅读原始材料的评分结果予以认可。直接询问：

> 这里有五个已评分的示例，位于 `report.html` 中，请逐一打开查看。**您是否会以不同的方式给其中任何一例打分？** 是否有您关注但当前未被衡量的方面——或者有哪些被扣分的地方其实您并不在意？

如果对“是否会以不同方式打分”的回答有任何一例为“是”，则说明评分量表尚未成熟——需要迭代调整，直到用户的判断与评分器的结果一致，最后再获得用户对最终版本的明确肯定。

## 第三步：使其可运行编写一个脚本（或测试文件，或其他适合他们代码库的形式），实现以下功能：加载输入数据，对每个输入运行应用，对每个输出进行评分，将每轮结果写入磁盘，并打印一行汇总信息，包含总分及置信区间，以便用户区分信号与噪声。并发执行各用例——通过类似 `asyncio.Semaphore` 的机制限制并发请求数量，使其接近账户的速率限制——从而使一轮完整执行在数分钟内完成，而非数小时；快速的评估反馈是迭代优化结果的关键。保持代码简洁，并遵循其代码库的惯用风格——如果他们有一个存放 Click CLI 工具的 `scripts/` 目录，就将其作为其中之一；如果所有内容都基于 pytest，就将其做成一个 pytest 测试。

让运行器将输出写入 `.claude/hillclimb/<flow>/baseline/` 目录（后续的爬山循环会在同一父目录下依次创建 `v1/`、`v2/` 等子目录）。如果用户已有偏好的结果布局，则沿用之——关键在于每个用例应携带来自同一次模型调用的完整对话记录、用量、成本及评分——但全新开始时则采用此默认布局。**在每个用例完成后立即写入一行结果**，而非在最后一次性批量写入——这样即使运行中途崩溃，已完成的用例结果也不会丢失；并确保在 **(case, rep)** 键上实现幂等续跑，使得崩溃后重启时能跳过已写入的部分，且绝不会出现重复的重试行，其分数和对话记录来自不同的调用。此外，一个可靠的运行器还需具备以下四项特性——前期添加成本极低，但在运行中发现缺失则代价高昂：

- **严格的单用例时钟时间上限，且独立于流式响应的活跃状态。** 卡住的流式连接可能无限发送心跳，从而绕过任何基于不活动的超时机制；只有对单用例总耗时设置上限，才能可靠地释放资源占用。当时间上限触发时，应标记该用例为失败，并记录为超时，而非计为零分——同时需注意，被超时终止的调用可能仍在后台继续运行：时间上限仅用于回收槽位并停止后续重试，无法主动取消底层请求。
  
- **针对 429/过载的带抖动退避策略，并保留可见的重试记录。** 零延迟的重试循环会在速率限制下无形中放大成本，并可能将一次短暂的 429 错误演变为整个批次的中断。应采用带抖动的退避策略，限制最大重试次数，并在每次重试时记录重试次数——实际发起的重试次数与最终计入评分的重试次数应在数据中清晰可见，而不仅体现在账单上。
  
- **明确的用例重试语义。** 如果运行器允许重新执行失败的用例，需明确规定以哪次尝试的评分、对话记录和用量作为最终结果。默认按每次尝试严格评分——只有在重试中才通过的用例视为失败，除非用户另有指定——且所有尝试均计入成本。
  
- **为每次失败的尝试标注失败类别**——拒绝 / 框架或服务端错误 / 超时 / 真正的失败——并与该次尝试一同记录（对于拒绝等有评分的结果，在 `grade` 字段或行的 `meta` 中注明；框架类错误可使用单独的错误侧车文件记录，且此类错误不应占用 `results.jsonl` 中的 `(case, rep)` 键，否则后续续跑时将永远跳过这些用例）。侧车文件在多次续跑过程中始终追加——每个 `(case, rep)` 只在首次失败时出现一行，后续若成功，则由 `results.jsonl` 中的成功记录覆盖其错误行。当调用确实完成时，应在错误行中携带该次尝试的 `model` 和 `usage`，并在任何支出统计中计入该用量——已计费但失败的调用仍属于支出。不同原因导致的零分应区别对待，而在评分列中极易混淆。

每次运行生成两个文件，此外还有一个名为 **`errors.jsonl`** 的辅助文件，用于记录在产生可评分输出之前失败的尝试（如重试后的 API 错误、工具异常、时间上限超时、评分器崩溃、服务模型不匹配等）。每个失败的尝试占一行，包含其失败类别、重试次数，以及如果调用已成功完成，则还包括 `model` 和 `usage` 信息。这些失败记录绝不会写入 `results.jsonl`：若在 `(case, rep)` 键下添加一行，后续恢复时会永久跳过该条目，并将流水线本身的故障误判为模型失败。报告会在每个变体的案例数旁显示相应的错误计数。- **`results.jsonl`** - 每个案例一行 JSON 对象，包含 `prompt_id`、`prompt`（完整文本）、有序的 `tags` 列表、`stop_reason` 和 `status`（`ok`，或当响应达到 `max_tokens` 时为 `truncated`——报告会统计被截断的行数，并将其排除在平均值计算之外，而不会将被截断的回答判定为错误）、`grade`，以及用户在步骤 2 中选择的辅助指标。`tags[0]` 是主要的分组键（主题、任务类型、难度等级——由用户最关心的维度决定），并在评估表格中作为小节标题；**后续的 `tags` 条目会在评估视图和对话记录视图中以标签形式显示在 prompt 旁**，因此可在此处放置任何用户一眼就能理解案例评分所需的简短标识，如难度、来源、用户细分、语言等。请明确区分哪些信息适合作为标签：如果对结果解读有重要意义，则归为标签；若仅为辅助数据（如出处 ID、原始标注者备注），则应放入 `meta` 字段，该字段会被传递但不会渲染显示。`grade` 可以是布尔值、数值，或 `{metric_id: number}` 的字典，还可附带一个可选的 `explanation: {metric_id: str}` 子字段，用于裁判评分标准。当您同时跟踪多个质量指标时——例如步骤 2 中的精确率/召回率/特异度系列——`grade` 必须采用以指标 ID 为键的字典形式，如 `{"precision": 1.0, "recall": 1.0, "specificity": 0.0}`。适配器仅从 `grade` 字段读取每个案例的得分，因此若在声明了多个指标的情况下仅提供单纯的布尔值或数值，则所有指标列都会显示为破折号。请在 `.claude/hillclimb/<flow>/_state.json` 文件的 `metrics` 部分声明指标 ID（及其标签）——完整的 `_state.json` 结构参见 `eval-hillclimb.md`——以便报告知道绘制哪些列，然后让运行程序在每个案例的 `grade` 字段中填写所有指标的得分。**顺序很重要**：报告的主指标（即“摘要”页、精简报告、轨迹文件以及 `--verify` 命令所追踪的指标）是第一个 `kind: "binary"` 的条目，若无则为第一个条目——因此请将您真正关心的指标放在首位，而非仅用于格式检查的常量指标。每个指标的 `label` 应控制在 14 个字符以内——完整查看器的图例宽度有限，超出部分会以省略号截断；限定词、单位和定义应写入 `metrics.md`，而非挤入标签中。辅助性能指标按确切名称读取——`latency_s`、`tool_calls`、`web_searches`、`usage: {input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens}`——这些是完整查看器默认渲染的性能列；若运行程序未记录其中某些指标，或本流程有意义的案例级字段有所不同，请在同一 `_state.json` 中通过 `perf_fields` 列表声明您自己的字段，使表格显示您实际测量的数据而非零值。此外，每行还应记录 `model`，该值应取自响应而非您的配置——`cost_usd` 是根据每行的 `model` × `usage` 计算得出的，如有裁判模型则还需加上 `judge_model` × `judge_usage`（因此由模型评分的评估也会显示裁判的消耗；否则，真实成本可能有一半无法体现）：完整查看器在数据已落盘时自动计算，否则由您在报告时按下方“第 1 次付费调用前”章节中“如果用户询问这会花费多少”的说明自行计算（当前模型价格见 `SKILL.md`；缓存写入按输入的 1.25 倍计费，缓存读取按输入的 0.1 倍计费）。无论哪种方式，运行程序均不负责计算成本；模型更换时不能沿用过时费率；未实际发生的更换也应如实反映。更进一步，您可以**进行断言**：当响应中的 `model` 与请求的模型不符，且超出文档规定的别名→快照解析范围时，应明确报错——静默替换的模型（供应商的后备方案或容量重路由）会使比较无效。静默回退可能根本不会出现在响应字段中，因此若供应商提供用量或账单记录，请将汇总数据与其核对。对于完整查看器内置价格表中未列出的模型，请在 `_state.json` 中添加 `prices: {model_id: {in, out}}` 映射。
- **`traces/<id>_rep<k>.json`** - 该案例的完整对话，以 JSON 数组形式呈现，每个元素为 `{role, content, thinking?, name?, attachments?}`，其中 `role` 取值为 `system | user | assistant | tool_call | tool_result`。每个工具调用都作为一个独立的 `{role: "tool_call", name, content}` 条目（content 即参数，以美观格式输出），每个工具结果则为 `{role: "tool_result", content}`，助手的扩展思考则置于其或其前置工具调用回合的可选 `thinking` 字段中。示例：
```json
  [
    {"role": "system", "content": "你是一位 helpful trading assistant."},
    {"role": "user", "content": "AAPL 的当前交易价格是多少？"},
    {"role": "tool_call", "name": "get_quote",
     "content": "{\n  \"symbol\": \"AAPL\"\n}",
     "thinking": "需要获取当前价格。"},
    {"role": "tool_result", "content": "{\"price\": 187.42}"},
    {"role": "assistant", "content": "AAPL 的当前交易价格是 187.42 美元。"}
  ]
  ```

如果流程中涉及图片、截图或生成的文件，请将其保存为附带文件，并通过结构化的 `attachments` 字段引用（输入行使用该字段，输出则在追踪记录中使用），以便报告能够内嵌显示这些内容——请参阅下方的“使工件可见”说明。

**使产物可见。** 如果案例会使用或产生某些产物——输入的 PDF 或图片、机器操作的截图、生成的 HTML/SVG/图表，以及模型写入的文件——完整视图已为其预置了渲染功能；运行程序只需将相应内容填入指定位置即可（精简报告不会渲染这些内容——它仅链接追踪文件，由用户直接打开 `ref` 指定的路径——因此无论哪种情况，所有 `ref` 都应相对于流程根目录保持相对路径）。**每个产物对应一个槽位**：只需将输出内容一次性放入 `Turn.attachments`，由视图负责渲染；不要再将其单独截屏保存为文件，也不要在响应文本中使用代码块来引用。视图会在已有附件的回合中自动禁用内联渲染开关，因此结构化的附件槽位才是唯一来源。**输入产物**应添加到 `results.jsonl` 的对应行中，格式为：`"attachments": [{"kind":"pdf","ref":"baseline/inputs/case_3.pdf","alt":"source doc"}]`，并在首个用户回合上方渲染。**输出产物**则应置于产生它们的追踪回合中：`{"role":"assistant","content":"...","attachments":[{"kind":"html","ref":"baseline/out/case_3.html"}]}`——将文件写入变体目录下，并以相对于流程根目录的相对路径进行引用。助手回合的 `content` 中若包含 fenced block 格式的 ` ```html ```、` ```svg ```、` ```json ``` 等内容，会自动添加“> 渲染”切换按钮。完整视图对 `image` 和 `svg` 进行内联渲染，对 `html` 使用沙箱内的可滚动 iframe，对 `pdf` 调用浏览器原生查看器，对 `json` 和 `text` 使用 `<pre>` 显示，其他类型（如 `file`: docx、pptx 等）则以下载卡片形式呈现——每种类型均配有“隐藏/显示”切换按钮。大小在 2 MB 以下的文件会内嵌至 `report.html`；超过此大小的则以下载链接形式保留。

运行器调用应用程序的方式比听起来更重要。不要根据你找到的系统提示和模型字符串自行重构 Claude API 调用——评估必须能够触发用户的重试逻辑、工具集成、上下文组装，以及从“输入到达”到“调用 Claude”之间的一切处理流程。在确保安全的前提下，选择以下选项中与生产环境最接近的一个，并能连续运行 N 次：

- 直接调用步骤 0 中的**真实入口点**；
- 使用测试或模拟用户 ID 访问**真实的生产 API 或端点**——走的是真实代码路径，但归属于测试账号，便于隔离和清理；
- 调用一个围绕入口点的**轻量级测试模式封装层**，仅对涉及生产环境的依赖（如数据库写入、外发邮件、外部副作用）进行模拟，其余部分保持真实——这是步骤 0 中提到的存根回退方案。

然后**运行一次**：如果代价较低，就对完整数据集运行；如果代价较高，则只对少量输入运行。在进行任何计算之前，**务必读取运行器写入的那一条记录，而不仅仅是打印出的数字**：所有需要上报的字段——`model`、`usage`、追踪日志文件，以及用户配置的各类护栏字段——都应在试点记录中存在且非空。当前缺失或为零的任何内容，在后续 N 个案例中也都会缺失或为零，而且在完整运行结束后通常无法补全。请持续修复运行器，直到有一条完整的记录生成。

### 在首次付费调用之前针对你刚刚构建的内容运行 `eval-audit.md`——这只需几分钟，就能在问题演变成全面故障之前发现大多数配置错误。至少要做到：将一个**基准答案**（参考答案，或必须通过的输入）和一个**空值**（空输出、固定答案）完整地通过整个执行器加评分器，并确认分别得到约100%和约0%的分数；如果存在裁判，则向其输入空字符串、“我不知道”以及对错误问题的确定答案，并确认它在这三种情况下均判定为失败；确保人为触发的 API 错误返回的状态是 `status: error`，而非 `grade: 0`；并将试点阶段的噪声水平与用户期望看到的变化放在一起对比（§5）。对于检查清单中发现的其他任何问题，按其 §6 的要求报告——简明扼要，先说明严重程度，并主动提出修复方案。

然后告知用户你即将运行的内容——“对 `<model>` 进行 N 个案例 × R 次重复，耗时约 Z 分钟”（其中 Z 是试点阶段的实际用时 × N/M，而非凭直觉估算），并在获得同意后继续。这就是同意关卡。

**如果用户询问成本或给出了预算限制**，请用基于试点阶段实际 `usage` 数据得出的真实估算来替换上述简短说明，且仅以此为准——因为历史日志统计和数据集的中位数往往偏差达 2 至 4 倍，它们无法反映模式标志、缓存状态、代理式调用次数或评估实际执行时的重试情况。从试点阶段的数据行中计算：

- **每个案例的总 token 数**（输入 + 输出，若由模型评分则还包括裁判的输入 + 输出），以实测为准。报告分布范围，而不仅是平均值——按每个案例给出 `最小值 / 中位数 / 最大值`。
- **每次完整运行的费用**：token 总数乘以用户所选服务提供商的每 token 单价——《SKILL.md》中的“当前模型价格表”为官方定价；若应用部署在 Bedrock、Vertex 或其他服务商上，请向用户索取其费率表。对所有 `usage` 字段分别计价：基础输入和输出按表中价格，缓存写入按输入价的 **1.25 倍**，缓存读取按输入价的 **0.1 倍**。
- **每次完整运行的耗时**：测量试点运行的端到端时间并进行缩放——`(试点耗时) × (N 个案例 / M 个试点案例)`。切勿凭直觉估算。

随后**展示计算过程**——公式能让假设清晰可见：

> 试点阶段：M 个案例，平均约 Xin / Xout token（范围 Xlo–Xhi）。按 `<model>` 价格（输入 $A/百万 token，输出 $B/百万 token，缓存读取为输入价的 0.1 倍）：约 $C/案例（范围 $Clo–$Chi）。完整运行 = N 个案例 × R 次重复 × $C，总计约 **$Y**（范围 $Ylo–$Yhi），耗时约 Z 分钟。

询问用户是否接受。若不接受，可提供以下调整选项：更换为更便宜的裁判模型、更积极地使用缓存，或**精简至最具区分度的案例**——从试点结果中按信号强度排序（跨重复评分方差、与中位数的偏离程度、裁判意见分歧），保留前 K 个案例；那些始终通过或始终失败的案例在各轮之间并无变化，无法提供增量信息。若进行精简，则每轮只对这 K 个案例循环运行，最后再分别对基线和优胜方案运行一次全集以确认——这两组样本属于不同群体，切勿混为一谈。**经批准的公式中的案例数和重复次数即为实际运行参数**——如有变更，需重新提交审批。完整运行结束后，将预估成本替换为实测成本，并更新所有相关记录。

## 第四步：交付成果

当各项确认完成后，用户将拥有：一份已审核的输入集合、一种已验证的评分方法、一段可执行的脚本，以及一个基线数值。**主动出击——无需等待用户询问**——针对用户关注的模型执行一次完整的基线测试（若第三步的试点已覆盖全部案例，则复用该结果；否则此时再运行一次全集），然后构建并打开报告：

```bash
R="<base directory>/shared/evals/report"   # 技能加载时显示的“本技能的基础目录”
B="$R/build-report.mjs"; [ -f "$B" ] || B="$R/build-report-lite.mjs"
node "$B" .claude/hillclimb/<flow>/
```

**在交付报告之前请先进行验证。** 首先自行打开 `report.html`。对于精简版报告，需要检查的内容包括：报告头中的变体数量和计数，以及确保每一列变体数据都显示数字而非空白（若某列为空，则说明 `grade` 不是 `{metric_id: number}` 格式的字典，或者所有样本的 `status` 均为非“正常”状态）；本段剩余内容适用于完整版查看器。报告头应显示您预期的变体数量——如果您运行了基准测试加一个变体，但显示“1个变体”，则说明某个目录未命名为 `baseline` 或 `v<N>` 而被静默跳过（请重命名该目录并重新构建）。在“Summary”图表中，纵轴刻度应为简短且易读的数字——若出现类似 `6.838607594936709` 的刻度，则表示缺少格式化器；任何“越低越好”的指标（如延迟、成本、错误率）也应如此显示；若图表或颜色标度将“越低越好”的指标误判为“越高越好”，则查看器的第一印象会适得其反。如果有多个变体，请点击“Summary”表格中每个非基准行以展开其差异面板：每项都应显示差异及其理由；若面板为空，则说明该变体的 `change.md` 或 `change.patch` 丢失。在“Transcripts”标签页中，至少点击两个示例：您应看到系统提示以可折叠卡片形式呈现，用户与助手的对话气泡分明，所有工具调用及结果均以独立卡片形式渲染——而非作为原始 JSON 出现在文本气泡内；若出现一大块乱码、对话轮次缺失，或直接显示 `{"type": "tool_use", ...}`，则说明运行器的轨迹记录器输出了错误格式（按第3步修复并重新构建；运行 `build-report.mjs <flow> --check` 可在不渲染的情况下执行轨迹检查）。在“Eval”表格中，分别点击一个通过的案例和一个未通过的案例：所有已声明的指标列都应显示数字而非破折号——破折号意味着 `grade` 不是 `{metric_id: number}` 格式的字典。所有性能指标列都应包含有意义的数值——若某一列全为 `$0.000` 或 `0`，则说明运行器未输出该字段。表格上方的指标面板应清晰易读，无需额外解释——若指标 ID 看似晦涩，需添加 `label`。如有上述问题，请按第3步在 `_state.json` 或运行器的 `grade` 输出中修正，并重新构建。

确认无误后，将 `.claude/hillclimb/<flow>/report.html` 作为最终交付物提交。交接时请告知文件路径（或直接为其打开文件），并附上一句简明标题（如“基准测试在 N 个案例中得分 X——每行均可链接到对应转录”）。尽量避免在聊天中枚举案例或分数——各案例的详细信息都在查看器中，而一整段纯文本反而会降低用户打开它的意愿；仅当有特别希望他们优先查看的案例时，才点出一两个具体例子。您刚刚完成的第4步验证是为了自己发现渲染缺陷，而非向用户解释。如果磁盘上只有单个基准变体，报告将仅作为评估查看器呈现——包含各案例表格及可点击的转录（含轨迹文件链接，精简版报告亦然）。请指向 `report.html`，而非 `results.jsonl`；原始 JSON 属于实现细节。

总结各产物的存放位置及基准得分。若用户进行评估的目的是为了在此基础上持续优化，请引导其使用 `/claude-api hillclimb`。

### 提升持久性

评估只有在用户能够重复运行时才有价值——无论是针对下一个模型、下季度的流量，还是在下一次提示改写之后。统计 `.claude/hillclimb/<flow>/` 目录下的文件和字节数（含和不含 `traces/`），以及运行器和输入文件的实际存放位置，然后通过 `AskUserQuestion` 提问：

- **提交评估结果（推荐）** - 提交 runner、输入数据、评分器，以及 `.claude/hillclimb/<flow>/` 目录下除 `traces/` 之外的所有内容。请明确列出具体数量：“N 个文件，约 X MB”。同时将 `**/traces/`、`report.html`、`state.json` 和 `trajectory/` 添加到 `.gitignore`，以确保衍生的大量输出文件不会被纳入版本控制。
- **提交评估结果及完整日志** - 同上，但额外包含 `traces/` 目录。请注明“M 个文件，约 Y MB”。仅当用户希望将这些日志作为证据保留在仓库中时才这样做。
- **不提交** - 这是一次性操作，后续不再重复运行。

无论选择哪种方式，都请按流程执行：先暂存更改，更新 `.gitignore` 文件，然后提交并附带一条包含流程名称和基线得分的提交信息。轻量版报告生成器随本技能一同提供，而非置于用户的仓库中；团队成员可通过运行任意 `/claude-api` 命令（该命令会从指南中提取 `shared/evals/report/build-report-lite.mjs`）再执行上述构建命令来重新生成 `report.html`；完整版查看器在 EAP 环境中也可通过相同方式重新生成。若用户希望评估完全自包含，可将 `shared/evals/report/build-report-lite.mjs`（15 KB，无依赖）复制到已提交的评估目录中；而完整版查看器的 `{build-report.mjs,lib/}`（约 1 MB）仅在本地存在时才一并提供。

## 需要避免的常见问题

以下是评估构建过程中容易出现的错误。您在执行上述流程时有一定的灵活性，但绝不能陷入以下误区：
- **跳过用户确认环节**。在未向用户展示的情况下，仅凭四十组看似合理的输入和一份看似合理的评分标准生成的评估结果，往往难以获得信任。用户确认才是最终的产品。
- **未经用户同意就启动评估**。在设计细节尚未敲定时就擅自启动小规模试点，或在用户还在讨论“完善评分标准”时就悄然转为“我已经运行了”，这种做法会迅速消耗用户的信任，远比消耗 API 调用次数更快。在首次付费沟通前务必获得明确许可。
- **强制要求特定格式**。切勿要求用户必须采用某种评估框架、重构其代码库，或以特定的数据结构组织输入。应让评估适配用户的代码基线，而不是反过来。
- **重新实现应用逻辑**。runner 必须调用用户的真实入口函数。如果在评估脚本中从头重建 Claude 的调用逻辑，就会与生产环境的行为产生隐秘偏差，从而导致测量结果失真。
- **估算成本不严谨** - 当用户询问成本时，务必基于至少一次实际运行的结果进行估算；仅凭 token 数量猜测的成本往往误差达 3 至 10 倍。应先运行一次，读取 `usage` 数据后再做乘法计算——且应基于 **试点运行** 的数据，而非历史日志的统计。
- **盲目相信零值**。在任何数值对外呈现之前——无论是聊天界面、`metrics.md` 文件还是 `report.html` 页面——都要进行合理性校验。每一行的每项指标都应 **真实且合理**：例如，`cost_usd` 为 `$0.00`、`latency_s` 为 `0.0`、`usage` 字段为空，或某项指标在所有案例中均为固定常数，这些情况几乎都不是真实的测量结果，而是字段名不匹配、查找失败或默认值掩盖了异常所致。对于本不应为零的列中的零值，应视为 runner 的 bug，而非真实结果。对于成功案例中缺失的必填字段，runner 应主动报错（抛出异常，而非写入空行）；对于即将展示的输出中发现的此类问题，开发者也应立即停止处理并中断展示。
- **忽视数据管理**。若输入数据来自生产流量，则数据保留期限及 PII 处理问题绝非可选项。应在获取数据之前就与用户明确相关事宜，而非等到文件已提交后再讨论。
- **过度依赖模型评分**。LLM 评分器方便且通常表现尚可，但它们也可能被“攻破”，并过分关注表面特征。在确定评分标准之前，务必向用户展示评分示例，并尽可能优先使用程序化的验证机制。
- **试图构建“大一统”的评估体系**。一个流程对应一套评估。若用户有六个流程，则应分别构建六套评估；只构建用户所要求的那一套即可，无需扩展。
