# 保留思维——在对话过程中保持早期推理的有效性

> **如果您通过 `/claude-api preserved-thinking-migration` 进入（或直接打开了此文件）：** 这就是正确的文档。请按顺序执行以下步骤，不要将指南总结后反馈给用户——展示中断概况、排序后的原因列表以及每项修复的实测结果，这些都是执行流程的一部分。从步骤0（范围、质量标准、基线）开始，到步骤4的两项交付物结束：中断概况和变更内容。

保留思维的衡量单位是“保持推理的对话次数”，而不是“通过的请求次数”。对先前一轮的任何一次编辑都会使该轮之后的所有思维块失效，而同一个过时的思维块在后续每次重放它的请求中都会再次失败——因此，以请求为单位的统计会夸大实际影响，而以对话为单位的统计（即本次对话是否中断，以及在哪一轮中断）才是判断修复是否有效的关键指标。

**检查机制简述：** 在支持保留思维的模型上（目前包括Claude Fable 5.1、Claude Opus 5.5和Claude Sonnet 5.5；保留思维页面列出了相关模型及强制启用的账号，并说明后续版本将对所有用户强制实施该检查），每个`thinking`块的`signature`都会记录生成该块的完整对话信息——包括顶层的`system`提示、工具集，以及该块之前的每一条消息——同时还会记录生成该块的模型。当对话历史返回时，API会根据您发送的内容重新计算这一记录，并要求两者完全匹配（另一项模型检查则决定当前模型是否能够读取该块；详见`shared/preserved-thinking-migration/causes.md`中的“跨模型切换”部分）。对于以追加方式保存历史的集成，这一机制不会产生影响。而那些在请求之间改写先前轮次内容的集成——如截断、客户端侧压缩、重新渲染的系统提示、插件接入时动态扩展的工具列表、每轮注入后又被移除的提醒、事后修剪的旧工具结果、因大小限制被丢弃的媒体、或经过应用自身消息格式的有损转换——都会在编辑点之后失去推理能力（触发`drop_block`），或者导致请求失败（触发`error`）。该检查比对的是*您发送时*的对话状态，即任何服务端编辑之前的版本，因此Anthropic自身的服务端压缩与上下文编辑都不会被视为编辑。官方说明详见`shared/model-migration.md`中的“从Claude Fable 5迁移到Claude Fable 5.1”章节——**破坏性变更3**（包含三步检查机制及每次编辑的追加形式；若您初次接触该检查，请先阅读该部分）。本流程仅以查表方式重述规则，并结合`shared/preserved-thinking-migration/causes.md`中的原因表格与保留清单，逐一排查本测试框架所引入的编辑，通过API响应验证问题，逐项修复并再次验证修复效果。

**本流程的定位：** `migrate`子命令负责解释检查机制并列出每次编辑的追加形式；而本流程则是其可执行版本——扫描、测量、修复、再测量——适用于已存在的测试框架。`cost-optimize`是其兄弟流程，而非前置条件：因为一份会使其自身推理失效的历史也会在同一位置重置提示缓存，因此在此处的修复通常也会反映在缓存命中率的提升上；而在那里发现的前缀编辑（“审计任务中途的缓存中断者”）与此处发现的中断本质上是同一问题。缓存管理规范与保留思维规范几乎一致，因此对于已在缓存层面保持追加特性的框架而言，此处无需额外投入。一旦项目具备评估体系，步骤3即可作为一场以中断次数为指标的爬山优化过程来执行——每轮只做一项变更，经测量后保留或回滚——此时可使用`hillclimb`子命令作为循环流程。本指南随附两个脚本，位于 `shared/preserved-thinking-migration/` 目录下，分别用于步骤 1 和步骤 2。这两个脚本均为无依赖的 Python 3 脚本；除探针的实时模式外，均无需凭据，且不会输出任何凭据信息。以下命令给出的是这些脚本相对于本技能根目录（即终端提示符最顶端那一行所显示的路径）的相对路径，请在用户项目目录下运行时加上该根目录作为前缀，以便相对捕获路径能够正确解析到目标位置。此外，还提供了一篇参考文档 `shared/preserved-thinking-migration/causes.md`：其中包含了模型切换对话的规则、“原因 → 检测 → 修复”对照表、保留清单以及应避免的失败模式。该文档独立存放，以便将本指南内容浓缩于一份读物中；请在下方某个步骤指引您查阅时再阅读（最迟在步骤 1.4），切勿提前阅读。

- `shared/preserved-thinking-migration/prefix_diff.py`：比较检查所涉及部分中连续请求体之间的差异，并以 API 自身的术语命名这些差异；`--scan` 参数会从代码库中筛选常见的问题根源。
- `shared/preserved-thinking-migration/drop_block_probe.py`：在启用控制机制的情况下回放已捕获的对话，逐轮、逐次记录 API 在每一轮和整个对话中丢弃的内容及其原因；`--self-test` 是一个由三次请求组成的验证流程，用于确认检查是否正常运行（步骤 0.5），若未正常运行则返回非零退出码。

## 严重程度分级——一次性与重复性

在规划工作之前，务必对每个问题原因进行分级。**0 至 2 级属于一次性修复：只需执行一次，测试框架便不再中断。而 3 至 4 级则会持续产生影响**——每次对话只要触及这些问题，就会反复出现，因此在做出决策前必须对其进行量化评估。

| 级别 | 含义 | 原因 | 处理方式 |
|---|---|---|---|
| 0 | 正常——无需修改 | `cache_control` 标记；`tools` 数组的重新排序；服务端压缩与上下文编辑；重试；重新生成、回退、恢复的检查点或分支；最新一轮被编辑后重新提交；模型切换（模型检查是单独的，不属于前缀修改） | 无需处理。以上情况都不会改变被比较的前缀内容，因此无需将其纳入报告。 |
| 1 | 非故意引入 | 系统提示词根据每次请求的内容重新渲染（如日期、计数器、实时状态）；SDK 或领域模型往返过程中产生的偏差 | 移除相关修改。产品本身并不需要此类改动。 |
| 2 | 可修复 | 对话过程中工具集发生变化；同名工具的描述或 Schema 被重新构建；每轮注入后又被移除的提醒；尾部状态每轮都被重新渲染 | 按照追加式修复方案（步骤 3）处理。添加或移除工具都有对应的追加式操作（`tool_addition` / `tool_removal`，并在 `tools` 中保留原有条目）。对于同名工具的描述或 Schema 变更，仅在 `inline-tools-2026-09-15` 试验版（Claude API）中存在追加式处理方式：此时可通过 `tool_addition` 传递新的定义（步骤 3）；若无此功能，则需在整个对话生命周期内保留首次发送的数据并接受过时的定义，或者以新名称提供变更后的文本。尾部状态应作为新回合追加，而非覆盖重写。 |
| 3 | 重复发生 | 保留尾部的压缩；后台压缩（在会话进行的同时，第二次请求写入摘要并随后替换）；滚动截断；固定文档每轮都被重写 | 度量丢弃情况并作出决策。在没有 `compact-2026-09-04` 试验版（按需压缩）的情况下，这些场景尚无客户端侧的追加式处理方式：从替换开始发送 `drop_block`，或将保留的回合中的思考内容剥离；推荐采用同步执行的简单压缩方式。有了该试验版后，保留尾部和后台压缩即可实现追加式处理——参见步骤 3。 |
| 4 | 必须停止 | 前缀手术——剪切、删减、修剪旧工具结果，或为节省成本而在缓存断点后移除部分内容；缺失前置内容；未记录的剥离与重试 | 不存在可行的规避方案。修改点之后的推理过程已丢失，唯一的解决办法就是停止此类操作。层级是原因的属性，而非单次对话的属性：首先按层级排序，再在同一层级内按推理内容的丢失程度排序（步骤3）。

## 步骤0：确定范围、质量标准与基线

**您的工具链是否改变了前期的轮次、系统提示或工具列表？如果不是，请停止**——此时无需进行迁移，明确指出这一点即为结论。

当已回放的思考块不再匹配时，默认会返回**400错误**。选择丢弃该思考则需显式启用，但这并非真正的修复方案：它只是用可见的失败替换了对该推理的无声丢失，而且也并非免费——被丢弃的思考块不会计入计费，但会话的令牌用量仍可能增加，因为Claude有时会通过更多思考来重新生成被丢弃的部分（详见`causes.md`中的“应避免的故障模式”）。

**首先，根据请求及其对应的回答来源仓库，以及用户未提供答案的情况，明确三件事。** 本流程的设计即为交互式：对真实请求体的捕获、测试切片以及每次在线回放，均需要用户的参与或确认；而“这些修改中哪些是刻意为之”这一问题，只有用户才能回答。请在报告顶部同时列出这三点（初始状态下，基线可暂定为“待完成步骤2”）。1. **范围。** 如果某款官方的 Claude 产品或 SDK（Claude Code、claude.ai、Claude Managed Agents、Claude Agent SDK）负责管理对话历史，则无需迁移——直接说明并停止。否则：若请求中涉及文件或目录的命名，则以此为范围；否则，范围即为项目在一次对话的两次请求之间，构建并用于比对的三个请求组成部分——`system` 提示词、`tools` 数组和 `messages` 数组——所经过的每一个相关路径：请求构建器、压缩或截断、提醒或上下文注入、媒体处理、持久化与恢复（任何从存储中重新读取并重新渲染对话的操作）、进程重启与部署、插件或 MCP 连接、子代理转录，以及模型切换。请注意区分不同的流量类别（即使使用同一密钥，交互式聊天路径与后台代理循环也是不同的处理流程）：针对每种类别分别记录配置、修复项，以及后续执行的每一项验证。在旧模型上捕获的请求可能包含 Claude Fable 5.1 在任何检查之前就会拒绝的请求格式——例如 `thinking.type` 的 `enabled` 或 `disabled` 状态、强制的 `tool_choice`（`any` 或 `tool`）、将助手预填充作为最后一则消息、带有思考配置的 `temperature`、`top_p` 或 `top_k`——因此请先列出这些需要转换的内容，再进行测量（步骤 2.1 列出了探针会转换的内容；它不会动用预填充，而相应的 400 错误会出现在其“未评估”一行中）。**同时明确代码所面向的平台**（Claude API、AWS 上的 Claude Platform、Amazon Bedrock、Google Cloud Vertex AI 或 Microsoft Foundry）以及**所运行的模型**：该检查仅适用于启用了保留思考功能的模型。保留思考功能页面指出，在 Amazon Bedrock 和 Google Cloud 上，只要该功能处于测试阶段，其名称便保持一致；对于其他平台，请查阅相应平台的官方文档及 `shared/platform-availability.md`，切勿自行推断。最后，确认**当前是否已强制实施该规则**。根据保留思考功能页面于 2026 年 9月23日的说明：在 Claude Fable 5.1 和 Claude Opus 5.5 中，自 2026 年 8月31日 00:00 UTC 起创建的账户默认强制执行该检查，Claude API 及各云平台的定义相同；任何设置了 `prefix_mismatch_behavior` 的请求均会启用该检查，无论账户创建时间长短；后续版本的模型将对所有用户强制执行此检查。可通过现有生产环境的响应来确认：已强制实施的账户会收到带有该头字段的 `input_transformations` 条目，或返回文本中注明“绑定到不同对话”的 400 错误；尚未强制实施的账户在请求未设置该字段前不会出现被丢弃的区块或 400 错误；仅携带测试头时，其响应会将每个本应失败的区块列为 `thinking_mismatch_allowed` 条目（步骤 2.2）。页面自带的探针——发送一段未加测试头的编辑后历史——如果返回的 400 错误中提及该头字段，则表明账户已默认强制实施；若返回 200，则表明尚未强制实施（Message Batches API 无论哪种情况都会返回 200）。为进一步确认 200 响应，可再次发送请求，仍不添加该字段：响应会将编辑后的每个思考区块都列为 `thinking_mismatch_allowed`。步骤 0.5 用于验证强制实施的路径——请使用测试密钥运行，切勿作用于生产流量。
2. **质量标准。** 查找该项目针对其模型调用所使用的评估、测试套件或结果检验机制。本流程中的修复项在设计上均能保持行为不变（它们改变的是历史的传递方式，而非告知模型的内容），但有两项例外：替换压缩方案，以及选择在边界处丢弃思考内容。这两项需要评估支持。若不存在评估机制，请在报告中醒目地说明，并且不必停止：丢弃次数本身即可作为一项度量，所有移除编辑的修复均可安全提出，而对于那两项例外，下一步便是执行步骤 3 中的最低限度评估方案。
3. **基线数据。** 两项数值，均来自步骤 2 探针在同一测试片段上的结果：至少存在一次前缀冲突的对话占比，以及每次冲突首次发生的回合数。在应用任何修复之前先予记录。步骤 2 的三臂协议还要求获取当前处理流程下关闭保留思考功能时的评估分数（即评估现有的数值）——如有，请立即记下。

## 步骤 0.5：验证机制已正确配置

在信任任何测量结果之前，先运行一次故意构造的异常对话，并确认 API 能够报告这一情况。探针的自检会发送三条请求——一条创建请求和两条重放请求：它首先创建一个包含一轮对话的思考块，然后以正常方式将其作为第二轮进行重放（预期 `input_transformations: []`），接着再对第一条用户消息进行编辑后重放（预期出现一条 `{"type": "thinking_dropped", ...}` 记录，其中 `reason: "prefix_binding_mismatch"`；在 Claude API 上，还会在诊断头中注明 `pattern=first_message_rewritten`）：

```text
python3 shared/preserved-thinking-migration/drop_block_probe.py --self-test --model <目标模型ID> --yes
python3 shared/preserved-thinking-migration/drop_block_probe.py --self-test --model <目标模型ID> --yes --mode error   # 预期返回 400 错误
```

探针始终携带 `thinking-binding-controls-2026-08-01` 的 Beta 值；如果生产请求使用其他 Beta，则添加 `--beta <值>`（在 Claude API 上仅使用该命令即可）。探针仅限于第一方使用：它通过 `/v1/messages` 接口进行身份验证，使用 `ANTHROPIC_API_KEY`（作为 `x-api-key` 发送）或 `ANTHROPIC_AUTH_TOKEN`（作为 Bearer Token 发送；当两个变量同时设置时，仅发送令牌，因为 API 会拒绝同时携带这两个头的请求），且无法重放从 Amazon Bedrock 或 Google Cloud Vertex AI 捕获的请求——在这些平台上，请使用客户自己的客户端，并从其响应中读取 `input_transformations`。

这三条简短的请求（一次创建、两次重放）将按模型的正常费率计费——在每次调用模型的测试前，请先告知用户费用并征得其同意。如果编辑后的重放未检测到任何丢弃（探针会打印 `NOT WIRED` 并退出代码 1），则应立即停止：说明此次检查并未生效（可能是模型 ID 错误、平台不支持相关控制、缺少相应头字段、字段拼写错误，或者在测试框架与 API 之间存在网关或代理，导致 `anthropic-beta` 头或 `block_binding` 字段被丢弃——请通过生产环境使用的相同路径运行自检），后续的所有数据都将毫无意义。如果正常重放也报告了丢弃，同样需要停止：说明探针路径中的某个环节已经在修改对话历史——例如代理、SDK 中间件或序列化器——这就是我们要定位的第一个问题。请将这两条响应记录在报告中。

## 步骤 1：查找修改点

查找修改点主要有三个来源，按证据强度排序：API 自身的诊断信息（步骤 2）、连续请求体之间的差异，以及代码。本步骤主要进行差异比对和代码分析：它们能在花费成本进行重放测试之前告诉你应该关注哪些地方，并且在 API 已经明确问题形态后，还能帮助你将故障精确定位到某一行代码。

### 1.1 捕获测试框架实际发送的内容

捕获几组正常对话的完整请求体——每条请求按发送顺序，以 JSON 格式保存原始传输内容，包括助手回复中的 `thinking` 块和 `signature` 值，务必与 API 返回时完全一致。其中应包含：一段足够长的对话，以便触发压缩或截断（如果产品具备此功能）；一段在会话中途接入插件或工具的对话（如果适用）；以及一段从存储恢复或经历进程重启后仍能继续的对话。尽可能在 HTTP 层捕获（例如通过 SDK 钩子、日志传输或代理），而非直接从应用的消息对象中获取——后者会隐藏本次检查所捕捉的重新序列化过程。如果请求在到达 API 之前经过网关、代理或模型路由层，请在离开该层时进行捕获：路由层可能在你的代码构建完请求之后，对系统提示词、工具或对话历史进行改写。每个对话保存为一个 `.jsonl` 文件，每条请求体占一行。十到三十个对话即可，它们也将作为步骤 2 的测试样本集。

仅捕获请求体和 `anthropic-beta` 头部——绝不要捕获 `x-api-key` 或 `Authorization`；MCP 服务器的 `authorization_token` 会以其原始形式（即连接器工具所包含的内容）出现在请求体中，因此应在测试范围内使用专用令牌进行捕获，并在测试后及时轮换该令牌。探针不会读取其他任何内容，并会在捕获中包含凭据时发出警告。

**捕获数据的处理。** 捕获数据即最终用户的真实对话记录，若对其进行编辑或删减，将导致测量结果失效（因为检查是逐字节比对的）。请将捕获数据存放在代码仓库之外（或置于版本控制的忽略列表中），切勿将其提交到版本库，也勿提交由此衍生的评估集。运行相关脚本的机器可以暂存这些数据，但工作完成后务必删除捕获数据。探针的 `--json` 输出可安全共享——其中仅包含请求 ID、状态、条目、头部、摘要、令牌计数及文件名，不含任何消息内容；对于对话检查自身产生的 400 错误，其错误文本会被存储为固定格式的重建信息（包括块路径、固定条款以及首次变更的消息诊断——但绝不包含服务器返回的具体行内容）；其他所有错误则仅保留其类型和字段路径，因为 API 验证消息可能会回显请求中的值（完整文本仍会在终端输出）。而 `prefix_diff.py` 的输出则不可共享，因其归属行会引用变更内容的片段。

如果应用尚无法捕获请求体，则添加这一捕获功能本身就是该流程中的首次差异：它将成为后续一切测量的通道。

### 1.2 对连续请求对进行差异比较

```text
python3 shared/preserved-thinking-migration/prefix_diff.py captures/conversation-0001.jsonl
```

对于每一对连续请求，该脚本会报告 `MATCH` 或 `MISMATCH`，并以 API 的术语给出判定结果——例如：`kind=system_changed; pattern=system_rerendered; sections=system; changed_validated=system.0`——同时附上一条归属行，标明站点及首个发生变更的字符位置：

```text
system[0] 在第53个字符处变更：“... Be concise.” -> “... Be concise. Current time: 2026-09-02T15:04:05Z.”
tools: lookup_order 描述在第23个字符处变更：“...order by id.” -> “...order by id. Today is 2026-09-02.”
messages[2]（用户）content[1]（文本）被移除：“{"text":"<reminder>Answer in one sentenc...
messages[1..2] 被移除（助手、用户）
```

除了判定结果外，还有两行信息同样重要：`replayed thinking blocks in the later request: N`——当 N 为 0 时，表明这对请求无法证明思维的保留情况（因为不存在可供检查的思维块），这种情况在每段对话的第一对请求以及那些剥离了思维块的测试环境中很常见；另一行为带有感叹号的链路行（显示为 `CHAIN-BREAK`，并在退出状态中计数），这是一种硬性失败而非警告——当已发送的回合以一种 API 不认可的方式返回，且其中的思维块已被更改时，就会触发此错误：保留的思维块必须是原始序列中的一个连续窗口（从开头、结尾或两端同时删除均可），因此若中间某块被移除，或顺序被重新排列，则即使前缀的其余部分未变，也会导致该间隙后的块验证失败。

比较时会忽略 API 本身也会忽略的内容：`cache_control` 标记、字符串内容与单个文本块的区别、文本块首尾的空白、仅含空白的文本块、键的顺序、工具数组中的顺序（按名称键进行比较）、尚未被任何工具结果、工具搜索结果或 `tool_addition` 引用过的 `defer_loading` 工具、位于 `system` / `tools` / `messages` 之外的请求参数、最后一个服务端压缩块之前的所有内容（检查会从该块处重新开始；差异报告会注明比较起始点），以及思维块本身。而内部空白、`tool_use.input` 字节、工具结果文本、图片字节及其他内容则均计入比较。请将脚本给出的 `pattern` 视作 API 语言下的推测——当两者不一致时，应以步骤 2 中 API 自身的标注为准。

### 1.3 阅读代码
```text
python3 shared/preserved-thinking-migration/prefix_diff.py --scan path/to/repo
```

扫描会按原因分组输出 `文件:行` 引用——包括提示词构建器中的时间戳和环境读取、消息数组的切片操作、会话开始后被修改的工具列表、从状态中重新构建的开场消息、事后裁剪的工具结果、用正则表达式剥离的提醒标签、被过滤掉的思考块、在应用自身消息模型中的往返处理、媒体数量限制以及 URL 重签名。**这些只是正则匹配得出的线索，而非最终发现**：在将其纳入报告之前，请逐一阅读，并通过成对差异或 API 响应加以确认。扫描是可选的；而下面的检查清单则是必选项。应用程序总有可能以模式无法识别的方式进行编辑，因此即使扫描未发现任何线索，也不能证明完全合规；而即便扫描发现了线索，也仅是一份待审阅清单——真正的判断依据仍是成对差异。

无论扫描发现了什么，都必须手动逐一核对——这份检查清单是步骤 1.3 的强制部分，因为编辑往往隐藏在其中：

- **提示词组装**：`system` 或第一条用户消息中是否有任何内容是根据每次请求动态计算的——例如日期或时间、工作目录、账户或用户信息、Git 状态、从磁盘重新读取的记忆或指令文件、功能标志、模型或客户端版本字符串、令牌或轮次计数？
- **工具声明**：`tools` 是否基于实时状态（已连接的 MCP 服务器、插件、权限、功能标志）构建，从而导致请求 1 和请求 2 之间的工具列表不同？描述或 Schema 是否使用了任何动态内容渲染？
- **历史管理**：是否存在缩短、摘要化、重新排序或改写已发送消息的逻辑——例如滑动窗口、保留最后 N 条、客户端侧摘要、“微压缩”旧工具结果、媒体数量限制、错误发生后的上下文长度恢复——以及摘要之后是否仍有某些轮次会被原样重放（这将决定采用哪种处理方案——步骤 3 中的方案，还是位于 `shared/preserved-thinking-migration/causes.md` 中的“测试版”部分）？
- **注入**：是否有任何内容仅附加到某一次请求的用户发言中（如提醒、状态行、令牌计数），并在下一次请求中被移除或重新构建？
- **模式切换**：进入某种模式（如计划模式、只读模式）时，是否会就地替换工具列表或系统提示词？请使用 `tool_removal` / `tool_addition` 来撤回并重新提供工具，并将模式的说明作为附加消息发送。
- **提示词中的工具列表**：系统提示词中是否仅列出一个通用的调度工具，而实际可调用的工具则在其后命名？如果是这样，增减某个工具即为系统提示词的编辑：保持提示词不变，并通过附加消息宣布每次变更（例如：“您现在可以调用 X”）。
- **持久化与恢复**：对话是否会在数据库或 ORM 中往返，且重放时是否从这些对象而非存储的原始 JSON 构建消息？重启、恢复、部署或模板版本更新时，是否会对系统提示词或开场消息进行重新渲染？
- **思考块处理**：是否有代码对 `thinking` / `redacted_thinking` 块进行过滤（例如，序列化器若跳过 `thinking` 文本为空的块也算作一次过滤：默认情况下文本为空，推理过程记录在 `signature` 中）、重新排序，或对其文本进行截断、重新换行（被修改的思考块本身即构成 400 错误），亦或在遇到 400 错误时直接去除这些块而不记录这一操作？
- **会话共享**：来自一个对话的思考块是否可能在另一个对话中被重放（例如共享会话密钥、多用户复用场景）？

### 1.4 为每项编辑命名，并判定其是否为有意为之

对于每一条成对差异判定和每一条已确认的线索，记录以下信息：API 返回的“原因”（即 `pattern` 字段）、代码中的相关位置、所属的流量类别，以及该编辑是**有意为之**（产品依赖的一种压缩机制；用户触发的重置操作，用于开启新一轮对话）还是**无意失误**（系统提示中多出了一条无人需要的时间戳；某个插件在请求 2 中被错误地内嵌到响应中）。在步骤 3 中，无意失误将被直接移除；而有意为之的编辑则会被替换为其仅追加的形式，或者——若尚无此类形式——则需经过评估并作出决策（参见步骤 2 的注意事项及步骤 3 的最后一节）。位于 `shared/preserved-thinking-migration/causes.md` 文件中“原因 -> 检测 -> 修复”表格，就是这两类情况的查询依据：如果你尚未阅读过该文件，请立即查阅，并在将其纳入报告之前，对照其中的“保留列表”逐一核验每个候选项。

## 步骤 2：在测试切片上启用 `drop_block` 进行测量

API 的响应才是唯一的事实依据。客户端的差异比对可能遗漏其无法感知的内容（如 URL 后面的媒体字节，或捕获时未包含的请求部分中的编辑），也可能误报 API 实际允许的情况；而 API 的响应则不会出现这些问题。

### 2.1 请求结构

测试切片中的每一条请求都携带 beta 标头，并**显式地**设置相关行为——这正是为那些默认未强制启用的组织打开检查开关的方式，也是在响应中添加报告内容的途径：

```http
POST /v1/messages
anthropic-beta: thinking-binding-controls-2026-08-01

{"model": "<目标模型>", "max_tokens": 4096,
 "thinking": {"type": "adaptive", "block_binding": {"prefix_mismatch_behavior": "drop_block"}},
 "system": ..., "tools": [...],
 "messages": [ ...完整的历史记录，包括思维块按原样回放... ]}
```

以下是一些有助于调试的规则：

- 如果缺少该标头，当前会返回一个 400 错误，错误信息为 `block_binding: Extra inputs are not permitted`。这与强制启用的账户在未携带该标头的情况下回放已编辑历史时收到的 400 不同；后者错误信息显示该 block “绑定到另一轮对话”，并在末尾指明了该设置所需的 beta 值。你可能会遇到这两种 400 错误，只有后者才表明检查已执行。如果仅有标头而缺少该字段，则不会为尚未强制启用的组织打开检查开关：既不会丢弃任何 block，也不会导致失败。此时 API 会记录此次检查，并将所有本应失败的 block 以 `thinking_mismatch_allowed` 条目列出（详见 2.2）——这是在生产流量中查找编辑的零风险方式。若要衡量强制启用的成本，请设置该字段；它是针对每条请求的可选配置。
- `prefix_mismatch_behavior` 可取值为 `"error"` 或 `"drop_block"`。请务必准确书写该字段名；探针会移除 `block_binding` 下发现的任何其他键，并明确指出是哪一个。
- 在携带该标头的情况下，所有支持 `thinking` 的模型都会接受该请求体，因此在模型切换前后均可使用同一份请求体，前提是思维配置是路由中所有模型均支持的（例如，在 Claude Fable 5.1 上，缺少该键的请求会返回 400 错误；而设置 `enabled` 则会被改写为 `adaptive`）。对于不支持保留思维的模型，该请求将被视为无操作，但仍会报告因模型不兼容而导致的 block 被丢弃情况。
- 请保持请求中其余部分与生产环境完全一致。探针仅会处理比较前缀之外的字段，并打印每次变更：标头、上述字段、`max_tokens`（有上限，详见 2.3）、`stream`（除非另有要求，否则关闭）、`tool_choice`（设为 `none`，详见 2.3），以及思维配置——若请求中未指定 `thinking` 配置，则会自动赋予 `{"type": "adaptive"}`（在 Claude Fable 5.1 上，这也是缺少该键时的默认行为）；`enabled` 会被改写为 `adaptive`，`temperature` 会被设为 1，`top_p` 和 `top_k` 会被移除；这些变更均不会影响最终判定结果。禁用思维的请求将被跳过。`system`、`tools` 和 `messages` 将按捕获时的原样发送。

### 2.2 响应提供的信息**通过请求差异检测缺失。** `prefix_diff.py` 在连续请求之间进行比较（步骤 1.2），就是这一检测器：它只读取您的测试框架发送的内容，因此无论响应的格式如何都能正常工作。下方的三个指标将确认并解释其检测结果。

按可靠性从高到低排列的三个指标：

1. **`input_transformations`**（响应体，顶级字段，与 `usage` 并列）——这是契约。在具备思考能力的模型的所有响应中，只要带有该头部字段，就会出现此字段：若无任何内容被丢弃且未发生错误，则为 `[]`；否则，每块内容对应一条记录，分为两种类型。`{"type": "thinking_dropped", "path": "messages.7.content.0", "reason": "prefix_binding_mismatch"}`：该块内容已被移除。`thinking_mismatch_allowed`（相同 `path`，`reason` 始终为 `prefix_binding_mismatch`）：该块在 API 未强制执行前缀检查的请求中未能通过前缀校验（例如旧账户未设置该字段），因此原封不动地传至模型并被计费；编辑之后的每一项都会出现此类条目，而设置了该字段的请求则不会出现（探测工具始终会设置该字段，因此会将此类条目解读为途中被剥离的字段：未评估变更，结果不确定）。`path` 按您发送时的顺序索引 `messages` 数组。`reason` 可能是 `prefix_binding_mismatch`（您的对话历史发生了变化——本流程的核心问题）或 `model_binding_mismatch`（对话切换到了无法识别该内容块的模型——并非您的代码问题；参见 `shared/preserved-thinking-migration/causes.md` 中的“对话中途切换模型”部分）；探测工具会对所有不属于 `WARN` 类别的原因进行标记。无论何种原因，被丢弃的内容均不计费。请忽略那些您无法识别其 `type` 或 `reason` 的条目；后续检查会补充更多信息。流式传输时，该数组会在 `message_start` 事件中随 `message` 对象一起到达（并在最终的 `message_delta` 中再次出现，仅在服务端中途发生模型回退时）；若无该头部字段，则该字段不存在，内容丢失也将无声无息。
   
2. **诊断头字段（如存在）。** 一些报告了内容丢失（或在 `error` 模式下返回 400 错误）的响应还会携带一个名为 `anthropic-thinking-prefix-mismatch` 的响应头——**但在流式响应中可能被遗漏**（此时探测工具的 `--stream` 模式可能不会输出“why:”一行），因此应将其作为第二重检查，并结合请求差异来判断。**Anthropic 尚未公开此头部字段；它可能会在未通知的情况下发生变化或被取消。如有则使用，但切勿依赖。** 若存在该字段，其 `pattern` 和 `changed_validated` 两个子字段可提供线索——即编辑的形态，采用与 `prefix_diff.py` 相同的表述方式，以及请求中首个发生变化的路径——探测工具会在其“why:”行中显示这些信息。若该字段不存在，则视为“无诊断”，而非“无中断”：详细信息（类型、模式、变更路径）仅针对您自身组织创建的内容块提供；对于其他内容块，该头部仅传递“有中断”这一事实；而且合作伙伴云的代理也不一定会转发该头部。
   
3. **`error` 模式的 400 错误文本**——以一句话形式给出的相同诊断，适用于无法获取响应头的代码：`messages.7.content.0: Invalid `signature` in `thinking` block. The block is bound to a different conversation. Remove the block, or set `thinking.block_binding.prefix_mismatch_behavior` to "drop_block". Content that preceded this block when it was created is missing from this request, starting at `messages.2`.` 其末尾通常会有一句指出首个发生变化的路径，如示例所示（具体语句会因编辑类型而异，有时甚至不存在）。请求在任何输出产生之前即被拒绝；重复发送相同的请求体仍会以相同方式失败（生产代码应采取的应对措施，请参阅 `causes.md` 中的“应避免的失败模式”部分）。**令牌计数端点会执行相同的对话检查。** `/v1/messages/count_tokens` 会将该检查应用于重放的块：在 `error` 模式下，它会返回相同的 400 错误（如果存在诊断头，则一并返回）；在 `drop_block` 模式下，它会返回 200，并且不在计数中包含被丢弃的块。在每次请求前进行令牌计数的测试框架会首先捕获这里的 400 错误。计数端点不产生任何费用，也不进行采样，因此是最经济的第一道筛查：在付费的 `/v1/messages` 重放之前，先以 `error` 模式对其重放切片进行测试（`drop_block_probe.py --count-tokens --mode error`）。它不会返回任何 `input_transformations`，因此回答的是“哪里出了问题”，而不是“有多少个块”。

这三者都没有指出*你的代码中的哪一行*导致了变更。这就是第一步的差异分析和扫描所要做的：头部的 `pattern` 和 `changed_validated` 告诉你应在请求的哪个位置查找；对比差异告诉你那里发生了什么变化；扫描则告诉你是谁写的。

### 2.3 运行切片

```text
python3 shared/preserved-thinking-migration/drop_block_probe.py captures/ --dry-run                       # 验证捕获，打印计划，不发送任何内容
python3 shared/preserved-thinking-migration/drop_block_probe.py captures/ --yes --count-tokens --mode error  # 在令牌计数端点上进行免费的第一遍检查：400 错误标记出中断点
python3 shared/preserved-thinking-migration/drop_block_probe.py captures/ --yes --json probe.json         # drop_block 重放；每个对话一个文件
python3 shared/preserved-thinking-migration/drop_block_probe.py captures/ --yes --mode error              # 使用响亮模式（prefix_mismatch_behavior "error"），如果你需要查看 400 的错误文本
```

没有 `--yes` 参数时不会发送任何内容：单纯调用只会打印计划并停止。对于持续集成，非零退出码即为信号——探针在无中断时退出码为 0，当某个对话结果不确定时为 1，至少有一个对话中断时为 2（顺序不代表严重程度）；差异脚本在出现任何不匹配或链路中断时退出码为 1。

重放请求并不会运行应用自身的工具——捕获中已保存了它们的结果——但如果模型在请求中调用了服务器端工具（如网络搜索、代码执行、MCP 连接器），这些工具会在 API 端再次运行，且每笔请求都会被计费；探针默认将 `max_tokens` 设为 16，因为判断结果在第一个输出 token 之前就已经得出，这样回复较短，输入侧的成本也较低。探针会对所有声明使用工具的请求都将 `tool_choice` 设置为 `none`（`tool_choice` 不在比较的前缀范围内），因此在重放过程中既不能调用服务器端工具，也不能调用测试框架自带的工具；16 token 的限制是为了控制成本，而非出于安全考虑。不要为了同样的目的从捕获中移除工具：工具集是检查比对的一部分，移除其中任何一个都会使每笔请求都变成 `tool_set_changed` 类型的中断。这会产生实际费用：根据切片估算费用（请求数量 × 当前费率下的输入大小——务必查询最新费率，不要凭记忆报价），并在首次运行前一次性获得用户对整个工作流测量预算的批准。`--max-requests` 和 `--max-conversations` 可用于限制首次运行的规模。请使用与捕获同组织的密钥——理想情况下应使用该组织的专用密钥或工作空间；若使用其他组织的密钥进行捕获重放，则无法得到诊断结果，此次运行也无法为测试框架提供任何信息。

**每笔请求应记录的内容**（探针会记录全部信息，生产环境的遥测也应如此）：对话 ID 和轮次索引；该请求中重放的思考块数量；每条 `input_transformations` 记录；如果存在，则记录 `anthropic-thinking-prefix-mismatch` 头部；HTTP 状态码，以及在 400 错误时的错误文本；请求 ID；以及客户端侧对三个绑定部分的摘要——对规范化的 `system`、按名称键控的 `tools`，以及截至每个重放的思考块的 `messages` 分别计算哈希值——以便在缺少头部的情况下也能通过摘要找到发生变更的请求。**计数规则。** 按每次对话中“新增”的被丢弃块进行统计，而非按每次请求的条目数统计。一个块一旦失败，在后续每次重放该块的请求中都会再次失败，因此一段十轮的对话在第3轮进行了编辑，虽然会有8次回复的条目记录，但只算一次中断。识别被丢弃的块应以思考块本身为依据——解析每个条目的`path`指向您发送的请求体中的相应块，并以其`signature`（对于`redacted_thinking`块则以其`data`）作为键值——而不要依赖路径：只要历史被截断或压缩，路径就会发生变化，同一个块在新索引下会被重复计入。探针会执行这一操作，并将路径保留在记录中。其对话级汇总信息包括`first_break_turn`（首次中断的轮次）、`distinct_dropped_blocks`（对话丢失推理的轮次）以及观察到的模式；首次中断的对话占比即为步骤0的基线，而首次中断的轮次则是与代码对比的基准：摘要发生改变的请求即为编辑后的下一次请求。

**先怀疑测试切片，再怀疑测试套件。** 如果某个切片从未重放任何思考块，则会得出满分结果，但这毫无意义——当某次对话的最大重放思考次数为零时，探针会发出警告。每次运行时都应首先检查这一数值。每段对话的第一条请求按定义不会重放任何内容；自适应思考的模型可能在简短的回复中完全不输出思考块（Claude Fable 5.1在默认力度下经常如此，因此仅包含简短交互的切片可能全程无思考）；如果测试套件在发送前就剥离了思考内容，那就无从检验。此外，切片还必须在目标模型上捕获：由未保留思考的模型生成的块无法提供用于验证的对话记录，因此重放此类捕获永远无法显示前缀中断（探针会打印捕获的模型ID，请核对）。在重放之前，先统计捕获的助手回复中的`thinking`块数量（探针的`--dry-run`会输出其将要重放的数量）。如果生产流量确实很少包含思考，请在报告中如实说明——这属于暴露程度的发现，而非通过判定；而对于专门用于测试套件的捕获，应使用需要推理的任务来驱动对话，或在捕获时提高`output_config.effort`（Claude Fable 5.1设为`"max"`），使助手回复中包含思考；其余部分则保持与生产环境一致。如果某个切片的大部分轮次都能重放思考，且最终结果为零，这才是期望的；而在其他情况下出现零值，则意味着测量存在缺陷。

### 2.4 三臂协议（与评估集的验证）

当项目有评估集时，应将迁移视为在一个冻结的输入集合上进行的A/B/C实验。第一臂是当前的测试套件，不强制启用检查：沿用评估集的现有得分，无需额外运行。第二臂是同一套件，但在评估运行器的配置中启用了`drop_block`（绝不写入生产代码），并记录每条回复的`input_transformations`，将其与每段对话的得分和令牌用量关联起来；这种关联可以回答那些丢失推理的对话是否得分更低或消耗了更多令牌，以及具体差多少。第三臂是经过步骤3修复后的测试套件，同样启用`drop_block`；目标是在该切片上不再出现`prefix_binding_mismatch`条目（模型检查类条目另行统计：“causes.md”中的“对话中途切换模型”），且得分与第一臂的差异在噪声范围内。请按流量类别并列报告三个得分、令牌用量以及两次丢弃计数。

### 2.5 影响测量结果解释的注意事项- **在没有 `compact-2026-09-04` 试验功能的情况下，保留尾部和背景压缩都没有纯追加式的客户端形式。** 对较早的回合进行摘要、仅保留最新回合原文的做法，在被保留的回合上会失败——因为这些回合的思考是基于完整历史生成的；而在关键路径之外进行压缩、并在稍后用摘要替换的做法，同样会在替换点之后的所有回合上失效。可供选择的方案有：服务器端压缩或上下文编辑，让应用能够使用它们；简单压缩（摘要加上新回合，不再回放更早的内容）；保留现有机制，并以确定性、可记录的方式从被保留的回合中剥离思考；或者保留现有机制，直接发送 `drop_block`（效果等同：两者都会丢失相同的推理过程；剥离是显式的，而 `drop_block` 只是一个字段）。请对您保留的机制进行度量——第二组数据会显示其代价——并记录决策，不要假定必须通过压缩来重写逻辑。有了该试验功能（按需压缩；步骤3），其纯追加式形式也成为一种需要以同样方式度量的机制，第二组数据即为其“改造前”的基准。
  
- **同名工具定义变更与重新列出的工具。** 在 `mid-conversation-tool-changes-2026-07-01` 规则下，`tool_addition` 是按引用添加的，因此无法表达“同一个工具，只是描述不同”的情况；而那些在重新连接时工具列表会发生变化的连接器，也没有天然的纯追加式处理方式。严格来说，确实存在一种方法——以新名称声明修订后的工具，并设置 `defer_loading: true`，再通过 `tool_addition` 宣布它，最后用 `tool_removal` 撤销旧名称——但在未启用 `inline-tools-2026-09-15` 的情况下，更简单的做法，也是推荐的做法，是在整个对话期间冻结每个工具的文本并原样回放：虽已过时但仍然有效。在 Claude API 上，则应在该试验功能（步骤3）下以值传递的方式发送变更后的定义。

- **合作伙伴云也会执行该项检查**（Amazon Bedrock 和 Google Cloud Vertex AI）。Preserved thinking 页面指出，只要相关试验功能在这两家云平台上可用，其名称就保持一致；各试验功能的独立页面会列出适用的平台，而对于其他平台，请务必先查阅该平台自身的文档以及 `shared/platform-availability.md`，切勿贸然假设已提供相应控制选项。在所有平台上，结果都只会在响应中可见，至于是否在 HTTP 200 响应中转发诊断头信息，则由各平台自行决定。若平台未提供相关控制选项，主动开启测试便不适用；遇到 400 错误时的恢复策略与步骤3的最后手段相同：从被拒绝的区块开始，将后续内容中的思考部分剥离，并予以记录和持久化保存。

- **Message Batches API** 在未设置默认行为时，会直接丢弃失败的批次而非使整个请求失败，且不会附加任何响应头；若希望批次中的个别项也失败，请显式设置 `"error"` 标志。批量结果是否携带 `input_transformations` 尚未经验证，请在依赖之前先行测试一个批次。

- **尚未强制实施的组织** 在请求未设置相关字段之前，既不会收到被丢弃的区块，也不会收到 400 错误。仅凭响应头时，它们会收到 `thinking_mismatch_allowed` 记录，因此在生产环境中发送该头信息并记录这些条目，即可发现潜在的编辑问题，而不会改变模型实际接收到的内容——这是一次仅用于记录的试运行，值得在步骤2的回放之前执行。该字段允许逐个请求进入回放流程，同时不影响其余生产流量。然而，这一特性也带来了生产风险：一旦将该字段复制到生产代码中，所有携带该字段的请求都将失去豁免，而当前仍在正常运行的对话也将立即开始丢失推理过程（或直接失败）——请务必在步骤3的修复措施上线后再进行此操作。

- **两项检查共用同一响应。** 当对话切换到无法读取该区块的模型时，会生成 `model_binding_mismatch` 记录；这些记录是预期之内的，不会计费，迄今为止的所有测试中也未导致 400 错误，更不是测试框架的缺陷——但毕竟意味着推理的丢失，因此探测器会将其与前缀绑定错误分开统计，并在报告中予以说明（参见 `shared/preserved-thinking-migration/causes.md` 中的“对话中途切换模型”一节）。本工作流的唯一衡量指标仅为 `prefix_binding_mismatch`。

## 第3步：每次只修复一个原因，重新测量，保留或回滚

按照**推理轮次损失的顺序**逐一处理各个原因：对于每个原因，对那些首次中断诊断中包含该模式的对话，汇总`distinct_dropped_blocks`（探针的每对话摘要同时提供这两项；在较早回合中断的对话比在较晚回合中断的对话损失更多块）——能在第2回合就让所有对话中断的原因，优先于仅在第30回合才让十分之一的对话中断的原因。

**当多个原因同时作用于同一请求时**——这在随时间逐步扩展的测试框架中是常见情况——工作的最小单位是“归属行”，而非模式。对每条对话的首次中断前后版本运行`prefix_diff.py`；它输出的每一行（如`system[0] 在第78个字符处发生变化`、`messages[0]（用户）content[0]（文本）发生变化`、`messages[2]（用户）content[1]（文本）被删除`……）都对应代码中的一个修改位置，而API仅报告最早的那一条（标题标明首个失败块的原因，类型为`multiple`）。对这些行进行排序，将每行作为**单独的差异**进行修复，并通过前后版本对比来评估每次修复的效果：只有当该行从首次中断的前后版本对比中消失时，才算修复正确。只有在该版本对上的所有行都被消除后，才使用探针进行端到端的重新测量——只要首次中断版本上还存在任何未修复的修改，丢块计数就不会变化，因此在仅修复一行后运行探针仍会显示相同的中断现象。切勿据此认为“修复无效”而将其回滚，应以前后版本对比为准。

每个被确认为有效的原因都会形成**独立的差异**（一个差异对应一个原因，这样回滚时操作干净且效果可追溯）。差异默认处于“待提议”状态——向用户展示其对应的归属行以及能够证明修复有效的度量结果——并且**仅在用户明确要求时才会应用**；随后再次测量：先进行前后版本对比，待首次中断版本完全修复后，再对该切片重新运行探针，比较出现中断的对话比例及首次中断的轮次与先前已保留的状态，并在存在评估指标且变更属于两种影响行为的类型之一时，重新运行第三组实验。归属行指向MATCH的差异予以保留；若差异在前后版本对比中未产生任何变化，则要么是漏测（该切片未覆盖相关路径——应扩大切片范围而非夸大结论），要么是诊断错误；若差异清除了其归属行但改变了评估指标，则予以回滚并记录。切勿仅根据单个对话的结果决定保留或回滚，以整个切片为单位。

无意的修改会被移除。以下提供的配方专用于有意的修改，形式均为追加式，与Anthropic自有的代理产品所采用的相同，因为它们同样面临这些问题（`shared/preserved-thinking-migration/causes.md`中的“原因→检测→修复”表格将每个模式映射到此处的相应配方，其模型切换部分则涵盖了在不同模型间路由的测试框架）。它们遵循同一个原则：**完整对话记录是唯一真相来源，模型后续所需的一切信息均追加至末尾，绝不写入开头部分。****冻结已渲染的系统提示；后续变更以追加消息的形式传递。** 在对话开始时对系统提示进行一次渲染，并将渲染后的字节与对话记录一同存储；此后该对话的每次请求都发送存储的字节——即使经历进程重启、部署更新、模板升级或客户端版本迭代——而不依赖于本轮可能重新渲染的内容。将所有会话级或请求级的固定信息从 `system` 字段及开场消息中移出：如日期时间、用户或账号标识、工作目录、环境变量、指令文件或记忆文件、功能开关、模型与客户端版本等。这些信息只需在首次用户发言（或在其后追加的一条 `role: "system"` 消息中）声明一次，之后仅以增量形式发送，即通过一条新的追加消息说明发生了哪些变化（例如：“主工作目录：`/repo/worktrees/x`（原为 /repo）”；“指令文件已重新读取；以下内容与其先前副本不同：……”）。对话中途插入的 `role: "system"` 消息具有系统提示的权威性，并会被纳入后续区块校验的对话记录中，因此以这种方式传递的变更效力等同于重新渲染提示，且不会使任何内容失效；而普通的系统消息则无需在 Claude Fable 5.1 中添加 beta 标头（只有 `clear_at` 和下方的工具变更区块才需要）。只有在明确划定的边界处才会再次渲染提示——例如新对话开始、用户主动触发重置，或在一次完整压缩后的下一次请求——并且日志中会显式记录这些边界，以免在该点的差异被误认为是错误。

**在对话初始声明工具集；绝不编辑已有条目；通过引用方式引入新增工具或撤回工具。** 对于一个规模较小且固定的工具集，在首次请求前构建完整的 `tools` 数组，并对可能尚未就绪的工具设置 `defer_loading: true`；将该数组按原样存储并原封不动地复用。对于一个庞大但模型几乎不会使用的工具目录，可暂不将未启用的工具列入 `tools`；当某个工具可用时——或在后续阶段有工具接入（如 MCP 服务器、插件，或会话中途授予的权限）——将其以 `defer_loading: true` 的形式追加至 `tools`（尚未被任何内容引用的延迟加载工具不在比较的前缀范围内，因此追加是安全的；Preserved 思考页面对此形式有详细说明），并通过一条追加的 `role: "system"` 消息中的 `tool_addition` 块予以宣告（beta 版本 `mid-conversation-tool-changes-2026-07-01`；该块必须紧跟在用户消息之后，例如 `tool_result` 所在的回合；若紧接在以服务器端工具结果结束的暂停助手回合之后，则仅允许纯文本系统消息，而工具变更会导致 400 错误，因此需先恢复该回合）。切勿直接追加常规工具。如果某个工具的提供方不再存在，也绝不要从 `tools` 数组中移除该工具；要撤回它，只需在一条追加的 `role: "system"` 消息中加入 `tool_removal` 块（同样为 beta 版本），并保留其定义，一旦模型仍尝试调用该工具，则返回正常的“不可用”错误。在整个对话生命周期内，冻结每个工具的描述与 Schema 文本——描述中出现刷新过的令牌、日期、实时列表或版本字符串，都将导致重新渲染。

**当请求中包含工具搜索工具时，可在工具可用之前暂不将其列入 `tools`。** 工具搜索功能能够发现并调用延迟加载的工具（参见“工具搜索”页面），因此可在工具可用的回合将其以 `defer_loading: true` 的形式追加，并附上一条 `tool_addition` 块。**在对话历史中保留每轮提醒。** 应当适用于某一轮的提醒会以轮次作用域的系统消息形式发出——`{"role": "system", "clear_at": "next_user_message", "content": "..."}`，并附加在其适用的 `tool_result` 消息之后（测试功能 `mid-conversation-system-clear-at-2026-08-21`；`role: "system"` 消息必须紧跟在用户消息或以服务端工具结果结尾的助手消息之后——否则将返回 400 错误，而非绑定失败）——并且**所有更早的副本均原样保留**，字节不变：被清除的消息不会渲染任何内容，不计入输入 token，但仍作为思维校验所依据的对话记录的一部分。平台页面中的三个细节：轮次作用域的消息仅包含 `text` 内容；它不带 `cache_control` 标记，因此应将缓存断点设置在其之前的用户轮次上；而仅包含 `tool_result` 块的用户消息被视为会清除该提醒的“下一条用户消息”。若未启用该测试功能，则应在同一用户消息中将提醒作为 `text` 块附加在 `tool_result` 块之后，并保留更早的副本；模型只会响应最新的那条提醒。对已发送的副本进行改写、从当前状态重新构建或删除，均视为一次编辑。同样的规则也适用于任何对话中途的 `role: "system"` 消息：将其与对话记录一同保留并回放，包括在子代理的对话记录中。

**在消息发送前调整其大小，绝不在发送后调整。** 工具结果、文档和图片在首次携带它们的请求之前即已完成尺寸调整——截断输出、缩小图片、统计 token——此后不再改动。后续的裁剪通过服务端上下文编辑（如清除工具结果、清除思维内容）或服务端压缩来实现，这些操作不计为编辑。针对图片，优先顺序如下：(a) **在摄入时就缩小尺寸**，以便在历史中保存所有图片仍具经济可行性——这是唯一不会造成信息损失的方式；(b) **将生成或获取的图片直接放回产生它们的工具的 `tool_result` 中返回**，因为服务端上下文编辑可以在无需客户端编辑的情况下清除旧的工具结果，而无法通过服务端手段移除静置于普通用户轮次中的图片；(c) 若客户端不得不对用户轮次中的图片设限，则应使剔除部分成为追加式历史的确定性函数，每次剔除至容量上限减去一定余量，使每 N 张图片才发生一次剔除，而非每次请求都触发——并明确说明每次剔除仍是一次编辑，会影响其后的推理过程；(d) 文件 API（`file_id`）适用于那些其*字节*否则会在各轮之间漂移的内容（如重新获取的 URL、重新编码的上传文件）——它并不能减少图片所占的 token 数量，因此不能用作容量限制。

**存储并原样回显网络传输的字节；切勿从领域模型重建历史。** 将 `messages` 数组按发送时的原样持久化，并将助手内容按接收时的原样保存——尤其是 `tool_use.input`，按 API 输出的原貌保留（如有需要，可自行保存一份规范化副本用于内部执行，但对外回显原始版本），文本块也不做修剪。原封不动地回放这些字节。一旦经过 ORM 对象、数据类或“规范化”处理，内部空白、数字格式、键名强制转换以及字符串与单文本块之间的形态差异就会发生变化；校验过程仅允许首尾空白及字符串与单文本块之间的形态差异，除此之外一概不容。**以符合检查要求的结构进行紧凑化。** 优先采用服务端紧凑化（其 `instructions` 参数可传入您自定义的摘要提示；在 Claude 5.1 及更高版本的模型上，带自定义 `instructions` 的阈值紧凑化会省略之前的思考过程，而按需紧凑化的摘要器则始终读取该提示），或使用上下文编辑——经检查的前缀会在紧凑化块处重新开始。在客户端，推荐采用简单紧凑化：当对话过长时，将其总结为一条消息，并以该摘要和新的用户轮次作为下一次请求的输入，不再回放更早的内容——既不回放更早的轮次，也不回放更早的思考。由于摘要是一条普通用户消息，因此不会留下任何可能使检查失败的思考内容。阈值紧凑化会使用请求中指定的模型生成摘要；按需紧凑化请求可以指定其他受支持的模型，但已保留轮次的思考内容仅在自该轮次产生以来的所有紧凑化请求均在同一款保留思考的模型上执行时才有效。切勿在工具调用回合的中途进行紧凑化（助手轮次若其 `tool_use` 尚未收到对应的 `tool_result`，则应连同思考内容一并完整返回）。只要不原样回放摘要之前的内容，“将最后 N 轮总结并丢弃其余”也属于简单紧凑化。如果产品需要保留一段原样回放的尾部，则应从被保留的轮次中剥离 `thinking` 和 `redacted_thinking` 块——文本和工具调用仍予保留——并将这一剥离操作设计为存储的紧凑化记录的确定性函数（所有早于紧凑化边界的助手轮次均不带思考内容输出），从而确保每次后续请求以及重启后输出相同的字节序列；若使用一种能够从仍保存思考内容的存储中重新推导记录的框架，则需记录一个标记以获得一致的结果。滚动保留最近 N 轮的方案会在每次紧凑化时付出这一代价（步骤 2.5 会将剥离结果与 `drop_block` 进行比对）。在日志中将紧凑化标识为唯一一个允许合法改变前缀的边界。

**当产品可选用两项较新的 Beta 功能时，其追加专用形式便成为又一种可供评估的方案**：`compact-2026-09-04`（按需紧凑化；亚马逊 Bedrock 不支持——其页面上的兼容性列表列出了适用的模型和平台）用于背景信息及保留尾部的紧凑化；`inline-tools-2026-09-15`（Claude API）用于会话中途新增的工具、同名工具的变更，以及重新列出的连接器。相关配方与规则详见 `shared/preserved-thinking-migration/causes.md` 中的“较新 Beta 下的追加专用形式”；请先查阅各平台页面以确认可用性。

**仅以连续区间的形式移除思考内容，并记录每一次剥离。** 检查接受原始思考块中的任意连续窗口——可从开头（最旧的部分；在紧凑化块之后，即紧随其后的最旧部分）移除一段，也可从末尾移除一段，或两者兼有——除此之外一律不合格：若从中间移除某一块，或对块的顺序进行调整，则该缺口之后的所有块及其后续块均将无法通过检查。由此衍生出两种处理方式。当因 400 错误而需剥离后重试时，应从被拒绝的块起向后剥离（即剥离尾部），并记录此次剥离的发生，以便后续请求发送相同的已剥离历史，而非那些被拒绝的块。切勿对中间部分进行删减。一旦某一块被移除，就应永久保留这一状态：将其重新插入将使此前缺失期间产生的思考内容失效。

**保持不同对话之间的独立性。** 来自其他对话的块会被判定为 `kind=unrelated` / `pattern=foreign_prefix` 而拒绝。这属于会话密钥设置错误，而非前缀编辑问题；请修复密钥。推理内容不得延续至新对话：若分支在分叉点之前完全沿用原有历史，则可予以保留；否则，新对话必须从摘要开始。**当某种形状不存在天然的追加式形式时**——在未启用 `compact-2026-09-04` 试验性功能的情况下进行尾部保留或后台压缩；或者在未启用 `inline-tools-2026-09-15` 试验性功能时，通过同名工具定义变更或重新列出连接器的方式（上述重命名并撤回的形式虽存在，但通常不值得采用）——此时差异本身就是决策，而非代码变更：使用 Arm 2 测量成本，在生产环境中明确选择 `"error"`（不匹配只意味着 bug，应立即报错）或 `"drop_block"`（降级处理，继续服务），并在配置头部显式设置该选项，并无论哪种情况都记录 `input_transformations` 或 400 状态码。在报告中将原因标注为“已测量并决策”，注明所选设置及其代价，以便后续人员无需再次讨论。

**最小化评估方案**，适用于两种会影响行为且尚无评估的情况：一组从采集中冻结的 20–30 条真实对话；针对每条对话，根据工作负载成本最低的原则作出判断（以黄金输出作为比对基准、制定简明评分标准，或使用自动化检查器）；以及一个运行器，用于回放单一配置，并在探针的中断占比旁报告通过率。共设计三条对照组，统一纳入一项预算审批。

最后，**生产环境中的设置本身就是一份差异，而且是最后一份**。在配置头部明确选择 `"error"` 或 `"drop_block"`，切勿留空，因为不同界面和不同账号年龄的默认值可能不同，而在尚未强制执行的账号上若字段为空，则表示检查已被记录但未生效。仅在用户明确批准后才应用该差异，并且仅当切片显示所有已修复的问题均不再导致中断时方可应用；只要仍有经测量但尚未修复的原因存在，绝不可在生产中使用 `"error"`——`"error"` 应用于 CI 环境，即每个流量类别的多轮对话样本都会在启用该模式下回放，以便任何新的前缀变更都能使构建失败。在生产环境中，应按对话粒度对首次出现的 `prefix_binding_mismatch` 进行告警，而非统计总数。

在撰写报告之前，请对照 `shared/preserved-thinking-migration/causes.md` 中的“需避免的故障模式”核对本次运行结果。

## 第四步：交付成果

1. **中断特征与改进计划**：包含步骤 0 的各项假设（范围、流量类别、平台与模型、强制执行状态、质量门槛）、步骤 2 的基线数据（含中断的对话占比、首次中断的回合分布、切片的回放思考覆盖率），以及所发现的问题——每项问题均附带其 `pattern`、在代码中的位置、是否为有意设计，以及由此损失的推理轮次，并按推理损失量排序。对于不存在追加式形式的问题，标注为“已测量并决策”，并注明所选设置。
2. **变更内容**：按建议顺序（以及用户要求时的实际应用顺序）列出每项问题对应的差异，分别标注为“已应用并测量”（含中断占比及首次中断回合的前后对比；若有评估则附上 Arm 3 分数）、“已提出”（注明预期效果）或“需开展评估”（指两类尚未有评估的行为相关问题）。此外，还将生产环境设置（`"error"` 或 `"drop_block"`）单独列为最后一份、需明确批准的差异——仅在切片中已修复的所有问题均不再导致中断时才应用，且只要还有未修复的问题存在，绝不使用 `"error"`。同时说明设置的位置、CI 回放情况及告警机制。“无需推荐变更”——即切片在大多数回合的回放思考中均未发生中断——也是一种成功的结果，请直接明确指出。

**报告框架**（章节顺序及必填字段——其余部分可灵活调整）：- **范围 / 流量类别 / 平台与模型 / 强制执行状态 / 质量门槛**（步骤0）
- **基线**——带中断的对话（占比）、首次中断时的轮次（中位数及范围），以及该切片的重播式思维覆盖率（步骤2）
- **已发现的原因**——表格列：`模式 | 站点（文件:行） | 流量类别 | 是否有意？ | 受影响的对话数 | 首次中断轮次 | 思维丢失（轮次）`——标题为“按思维丢失排序”
- **变更**——每项原因对应一个差异，按应用顺序编号，每个差异标注为*已应用并测量* / *已提议* / *待评估*，并附上变更前后的中断占比
- **已测量并决策的原因**——非仅追加形式的记录：测量结果、维持现状的成本，以及最终选定的设置
- **因路由导致的思维丢失**——被路由至无法读取其思维的模型的对话（`model_binding_mismatch`），受影响的轮次，以及建议的路由决策
- **生产环境设置、CI 重播、告警**——各处的具体设置内容
- **下一步 / 所需审批**——测量预算、评估前置条件，或“暂不建议变更”
