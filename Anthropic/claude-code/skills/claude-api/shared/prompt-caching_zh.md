# 提示词缓存 - 设计与优化

本文件介绍了如何设计提示词构建代码以实现高效的缓存。有关特定语言的语法，请参阅各语言README或单文件文档中的`## 提示词缓存`章节。

## 所有设计都遵循的唯一不变原则

**提示词缓存基于前缀匹配。前缀中任何位置的变更都会使该位置之后的所有内容失效。**

缓存键由渲染后的提示词在每个`cache_control`断点之前的精确字节序列决定。只要在第N个位置出现一个字节差异——例如时间戳、JSON键顺序调整或工具列表中的不同工具——就会导致所有位于≥N位置的断点对应的缓存失效。

渲染顺序为：`tools` -> `system` -> `messages`。如果在最后一个系统块上设置断点，则会同时缓存工具和系统部分。

围绕这一约束来设计提示词构建路径。只要顺序安排得当，大部分缓存效果就能自动生效。一旦顺序错误，再多的`cache_control`标记也无济于事。

---

## 优化现有代码的工作流程

当被要求添加或优化缓存时：

1. **追踪提示词的组装路径。** 找出`system`、`tools`和`messages`的生成位置，并识别所有流入这些部分的输入。
2. **按稳定性对每个输入进行分类：**
   - 永不变化 -> 放在提示词的最前面，在任何断点之前
   - 每次会话变化 -> 放在全球前缀之后，按会话缓存
   - 每轮变化 -> 放在最后，最后一个断点之后
   - 每次请求变化（如时间戳、UUID、随机ID）-> **消除或移至最末尾**
3. **检查渲染顺序是否与稳定性顺序一致。** 稳定的内容必须在物理上先于易变的内容。如果时间戳被插入到系统提示的开头，那么无论设置多少标记，其后的内容都无法被缓存。
4. **将断点放置在稳定性边界处。** 具体放置模式见下文。
5. **排查隐性失效因素。** 参见反模式表格。

## 断点放置模式

### 大型系统提示，多请求共享

在最后一个系统文本块上设置断点。如果有工具，它们会在系统之前渲染——因此在最后一个系统块上设置标记即可同时缓存工具和系统。

```js
"system": [
  {"type": "text", "text": "<大型共享提示>", "cache_control": {"type": "ephemeral"}}
]
```

### 多轮对话

在最近一轮消息的最后一个内容块上设置断点。后续每次请求都会复用整个历史对话的前缀。较早的断点仍然是有效的读取点，因此随着对话的推进，命中率会逐步提升。

```js
// 最后一轮用户消息的最后一个内容块
messages[-1].content[-1].cache_control = {"type": "ephemeral"}
```

### 共享前缀，可变后缀

许多请求共享一个较大的固定前导部分（如少样本示例、检索到的文档、指令），但最终问题各不相同。应将断点放在**共享**部分的末尾，而不是整个提示词的末尾——否则每次请求都会写入一条独立的缓存记录，导致无法复用。

```js
"messages": [{"role": "user", "content": [
  {"type": "text", "text": "<共享上下文>", "cache_control": {"type": "ephemeral"}},
  {"type": "text", "text": "<可变问题>"}  // 不设标记，每次不同
]}]
```

### 对话中途的系统消息

**Claude Opus 5、Claude Opus 5.5、Claude Opus 4.8、Claude Fable 5、Claude Fable 5.1、Claude Mythos 5、Claude Mythos 5.1 和 Claude Sonnet 5.5；无会话前导头。Claude Sonnet 5 不支持此功能**——请在该模型中使用顶层 `system` 字段。（关于 Claude Sonnet 5 的资料存在冲突：模型配置显示其支持，但所有官方文档均未提及。请将其视为不支持，并捕获返回的 400 错误。）当对话中途收到操作指令——如模式切换、上下文更新或动态注入的状态——应将其作为 `{"role": "system", "content": "..."}` 追加到 `messages[]` 中，而非修改顶层 `system`。修改顶层 `system` 会改变整个对话历史之前的前缀，导致所有已缓存的轮次都需要重新处理；而 `role: "system"` 消息则置于历史之后，保持缓存前缀不变。

```js
// 顶层 system 保持字节级不变；新指令追加至缓存的历史之后
"system": [{"type": "text", "text": "<稳定核心>", "cache_control": {"type": "ephemeral"}}],
"messages": [
  ...history,
  {"role": "user", "content": "..."},
  {"role": "system", "content": "已启用简洁模式——回复长度不超过 40 字。"
]
```

这也是防止提示注入的安全替代方案，可用来避免将操作指令以文本形式嵌入用户消息中（即 `<system-reminder>` 模式）：两者具有相同的缓存行为，但 `role: "system"` 是不可伪造的操作者通道，而用户或工具内容中的文本可能被任何可写入用户可见输入的内容所篡改。

必须紧跟在 `role: "user"` 消息（或以服务端工具调用结尾的 `assistant` 消息）之后，且必须是 `messages` 数组的最后一项，或后接一条 `assistant` 消息；不能位于 `messages[0]`——初始提示请使用顶层 `system`。内容仅限文本。不支持此功能的模型会返回 400 错误（`BadRequestError`：“此模型不支持 role 'system'”）——请捕获该错误，并回退至将指令放入用户消息的 `<system-reminder>` 块中。

**工具循环中的每轮提醒：作用于单轮的消息，永不删除。** 如果在历史中注入提醒并在下一次请求时将其移除，则相当于对历史进行了编辑——从该点开始缓存失效；在 Claude Fable 5.1、Claude Opus 5.5 和 Claude Sonnet 5.5 上，后续所有思考块也会被无效化。此时应为 `role: "system"` 消息设置 `clear_at: "next_user_message"`（测试版 `mid-conversation-system-clear-at-2026-08-21`；适用模型及平台同会话中系统消息）。该消息仅渲染一轮，随后在对话记录中被清空——不消耗输入 token，也不参与缓存（为其设置 `cache_control` 会返回 400 错误；应在前一条用户消息上设置断点），但仍属于前缀的一部分。每次 `tool_result` 消息后追加一份新的副本，并保留之前的副本；若不使用该测试版，则可在同一用户消息中，在 `tool_result` 后添加一个 `text` 块，并保留之前的副本。此外，按消息力度控制（测试版 `mid-conversation-output-config-2026-07-01`；适用于开启思考功能的 Claude Fable 5.1、Claude Mythos 5.1、Claude Opus 5、Claude Opus 5.5 和 Claude Sonnet 5.5；Claude API 和 Google Cloud）：带有 `content: []` 和 `output_config: {effort: ...}` 的 `role: "system"` 消息，自下一轮用户消息起改变思考力度，**不会**引发顶层 `effort` 变更所导致的对话缓存失效，且不受放置规则限制（可置于任意位置）——参见下方的“失效层级”以及 `shared/model-migration.md` 中的“从 Claude Fable 5 迁移到 Claude Fable 5.1 —— 新的 API 功能”。

### 每次都从头变化的提示

不要缓存。如果每次请求的前 1K 个 token 都不同，则不存在可复用的前缀。即使添加 `cache_control`，也只会支付缓存写入的费用而无法获得读取收益。请保持关闭状态。

## 架构指导

以下决策比标记的放置更为重要，请优先解决这些问题。**请保持系统提示词不变。** 不要在系统提示词中插入“当前日期：X”、“模式：Y”、“用户名：Z”等动态信息——这些内容位于前缀的最前面，会使得后续的所有内容失效。应在 `messages` 中稍后注入动态上下文——在支持的地方以 `{"role": "system", ...}` 消息的形式插入（参见上文“对话中途的系统消息”一节），否则就作为用户消息中的文本插入。第5轮的消息不会使第5轮之前的任何内容失效。

**不要在对话中途更换工具或模型。** 工具会在位置0被渲染；添加、移除或重新排序工具都会使整个缓存失效。切换模型也是如此（缓存是按模型划分的）。如果需要实现“模式”功能，不要直接更换工具集——可以给Claude配备一个记录模式切换的工具，或者将模式作为消息内容传递。工具应按确定性顺序序列化（按名称排序）。

**分叉操作必须复用父级的完整前缀。** 一些辅助计算（如摘要生成、压缩、子代理）往往会发起一次独立的API调用。如果分叉重建了 `system` / `tools` / `model` 并且有任何差异，就会完全错过父级的缓存。应原封不动地复制父级的 `system`、`tools` 和 `model`，然后在末尾追加分叉特有的内容。

## 静默失效因素

审查代码时，请在所有用于构建提示前缀的代码段中搜索以下模式：

| 模式 | 为何会破坏缓存 |
|---|---|
| 系统提示词中使用 `datetime.now()` / `Date.now()` / `time.time()` | 每次请求前缀都会变化 |
| 内容开头使用 `uuid4()` / `crypto.randomUUID()` / 请求ID | 同上——每次请求都是唯一的 |
| 使用 `json.dumps(d)` 但未指定 `sort_keys=True`，或遍历 `set` | 序列化不具有确定性，导致前缀字节不同 |
| 在系统提示词中通过f-string插值会话/用户ID | 每个用户的前缀都不同，无法跨用户共享 |
| 条件性的系统部分（`if flag: system += ...`） | 每种标志组合都会形成不同的前缀 |
| `tools=build_tools(user)`，且工具集因用户而异 | 工具在位置0被渲染，跨用户无法共享缓存 |

修复方法：将动态部分移到最后一个断点之后，使其具有确定性，或者在不影响功能的情况下将其删除。

## API参考

```js
"cache_control": {"type": "ephemeral"}              // 默认5分钟TTL
"cache_control": {"type": "ephemeral", "ttl": "1h"} // 1小时TTL
```

- 每个请求最多可设置 **4** 个 `cache_control` 断点。
- 可应用于任何内容块：系统文本块、工具定义、消息内容块（`text`、`image`、`tool_use`、`tool_result`、`document`）。
- 在 `messages.create()` 的顶层设置 `cache_control` 会自动放置在最后一个可缓存的块上——这是无需精细控制放置时最简单的方式（参见“自动与显式断点”一节）。
- 在Claude API、AWS上的Claude Platform以及Microsoft Foundry上，缓存按工作空间隔离（在Amazon Bedrock和Google Cloud上则按组织隔离），且绝不跨组织共享。同一提示在不同工作空间间产生的流量会写入并读取不同的缓存条目——在怀疑命中率低之前，请先确认这一点。
- 最小可缓存前缀取决于具体模型。即使设置了标记，更短的前缀也会静默不被缓存——不会报错，只会显示 `cache_creation_input_tokens: 0`：

| 模型 | 最小长度 |
|---|---:|
| Claude Opus 5.5、Claude Opus 5、Claude Fable 5、Claude Mythos 5、Claude Fable 5.1、Claude Mythos 5.1、Claude Sonnet 5.5（在依赖其值之前，请查阅提示缓存文档） | 512 tokens |
| Opus 4.8、Claude Sonnet 5、Sonnet 4.6、Sonnet 4.5、Opus 4.1、Opus 4、Sonnet 4 | 1024 tokens |
| Opus 4.7、Mythos Preview、Haiku 3.5 | 2048 tokens |
| Opus 4.6、Opus 4.5、Haiku 4.5 | 4096 tokens |

**最小值在不同代际间并不单调递增**——最新模型为512，而Opus 4.6/4.5和Haiku 4.5则为4096。对于3K token的提示，在Claude Opus 5、Opus 4.8以及Sonnet 4.5上都会被缓存，但在Opus 4.6或Haiku 4.5上却会静默地不被缓存。Claude Opus 5将Opus 4.8的最小值减半（从1024降至512），因此原本因太短而无法缓存的提示，如今无需任何代码改动即可生成缓存条目。

这些最小值适用于该模型**所有**可用的平台——此前针对Claude Fable 5.1的Amazon Bedrock覆盖已移除，且不再存在任何平台特例。

**经济性：** 缓存读取的成本约为基础输入价格的0.1倍——在Claude Fable 5.1上为0.025倍（$0.25/百万token，Claude Mythos 5.1亦同），而在Claude Opus 5.5上为0.05倍（$0.20/百万token）。这使得各模型的盈亏平衡点相应降低。缓存写入的成本为：**5分钟TTL时为1.25倍，1小时TTL时为2倍**。盈亏平衡取决于TTL：若使用5分钟TTL，两次请求即可打平（1.25倍 + 0.1倍 = 1.35倍，而未缓存时为2倍）；若使用1小时TTL，则至少需要三次请求（2倍 + 0.2倍 = 2.2倍，而未缓存时为3倍）。1小时TTL能够在突发流量的间隙中维持缓存条目的存活，但其双倍的写入成本意味着需要更多读取才能弥补这一开销。

### TTL的选择

无论采用哪种TTL，缓存读取都不会额外计费，且会重置条目的计时器。生命周期是从写入或读取该条目的请求**开始**算起的——生成时间会计入其中，因此若生成耗时4分钟，则留给下一次请求的时间仅剩约1分钟，之后5分钟的条目就会过期。如果共享前缀的请求间隔小于5分钟，那么5分钟的缓存便可无限期保持“温暖”——此时1小时TTL除了带来双倍的写入成本外并无其他优势。应根据共享前缀的请求之间“开始到开始”的间隔来选择：

| 共享前缀的请求之间“开始到开始”的间隔 | TTL |
|---|---|
| 小于5分钟（持续流量；每轮生成远低于5分钟的代理循环） | 5分钟——每次请求都会刷新它，且成本更低 |
| 5–60分钟（用户20分钟后回复；代理式子任务或两次读取间生成耗时超过5分钟） | 1小时——这是唯一能让2倍写入成本得到回报的时间窗口 |
| 超过1小时 | 两种TTL均无直接帮助——按计划重新预热缓存（见§ 预热缓存）或接受冷缺失 |

**Claude Fable 5.1 / Claude Mythos 5.1：保活通常比1小时TTL更划算。** 在Claude Fable 5.1和Claude Mythos 5.1上，缓存读取仅为0.025倍（而Claude Opus 5.5为0.05倍，其他地方为0.1倍——参见上文的经济性部分），因此相比命中而言，未命中代价更高，而读取几乎免费。所以在5–60分钟的间隔内，与其支付1小时TTL的2倍写入费用，不如继续使用默认的5分钟TTL，并在空闲时于条目即将到期前稍早重新发送上一次请求，同时设置`max_tokens: 0`。该请求会重置条目的计时器，且仅收取廉价的缓存读取费用（不产生输出token）。按照Claude Fable 5.1的价格，除非停顿经常接近一小时，否则这种方式优于1小时TTL。`max_tokens: 0`遵循§ 预热缓存中被拒绝的组合；在这些模型上，可能遇到的情况包括`stream: true`、结构化输出以及批量请求（强制`tool_choice`和`thinking.type: "enabled"`在此处已返回400错误）。发送保活请求时请关闭`stream`——流式传输只是传输方式，并非缓存前缀的一部分，因此为此请求关闭它不会有任何损失；若请求无法如此调整，例如涉及结构化输出（`output_config.format`）或位于消息批量请求内部，则应改用1小时TTL。提示缓存页面（`shared/live-sources.md`）提供了针对示例工作负载的成本对比，以及一个保活请求的示例。

在Claude API上，大多数模型的缓存读取也不计入输入token的速率限制（Haiku 3.5是已知的例外——参见速率限制文档），因此在间隙中保持缓存条目活跃不仅能降低成本，还能提升有效吞吐量。

## 自动断点与显式断点自动缓存是请求顶层的 `cache_control` 字段，而非任何内容块上的设置。系统会将断点置于最后一个可缓存的块上，并随着对话的推进逐步向前移动；如果最后一个块不符合缓存条件，系统会无声地向后回溯至最近的符合条件的块；若未找到任何符合条件的块，则跳过缓存。自动断点的默认 TTL 为 5 分钟（顶层字段也接受 `ttl: "1h"` 的配置），并占用 4 个断点槽位中的一个。它与同一请求中的显式标记可以共存，但也存在两种已知的 400 错误场景：所有 4 个槽位已被显式标记占满，以及最后一个块上的显式标记所指定的 TTL 与顶层字段的 TTL 不一致（若该处的显式标记与顶层 TTL 相同，则自动缓存将不起作用）。

对于多轮对话而言，自动模式是最合适的默认设置——采用上述无需维护标记的多轮放置策略。在以下情况下应使用显式断点：

| 情况 | 为何自动模式不适用 |
|---|---|
| 提示以每次请求独有的内容结尾（如检索到的行、每请求上下文、一次性问题） | 自动断点会落在独有尾部之后，导致每次请求都为那些永远不会被读取的字节支付写入溢价——纯粹的额外费用。其特征表现为：每次请求都有 `cache_creation_input_tokens`，而 `cache_read_input_tokens` 却从未覆盖完整的共享前缀。此时应在共享部分的末尾设置显式标记（参见“共享前缀，变化后缀”一节）。 |
| 各部分内容更新频率不同（如工具调用几乎不变、上下文每日更新、对话逐轮变化） | 自动模式仅设置一个断点；多个稳定边界需要显式标记。 |
| 某个块的 TTL 应为 1 小时，而另一个块为 5 分钟 | 块级 TTL 需要显式标记——且较长 TTL 的条目必须出现在较短 TTL 条目的前面（1 小时时长的条目必须位于所有 5 分钟条目之前）。 |
| 单轮新增超过 20 个位置（连续的 tool_use 和 tool_result 调用，每个都会折叠为一个位置） | 回溯窗口可能遗漏前一条目——参见“20 块回溯窗口”一节。 |
| 平台或集成不支持自动缓存（请查阅 `shared/platform-availability.md`） | 在此类环境中，顶层字段会被拒绝——只能使用显式标记。 |

**针对代理循环的稳健组合：** 在静态系统前缀的最后一块上设置一个显式断点——这样，昂贵的共享部分便能获得一个可靠的读取点，无论后续 `messages` 中发生什么变化；同时对不断增长的对话尾部启用顶层的自动缓存（仅在支持自动缓存的平台上——参见 `shared/platform-availability.md`）。若根据“TTL 的选择”确定使用 1 小时时长，则应在显式标记和顶层字段上均设置 `ttl: "1h"`。两者的默认值均为 5 分钟，而在 5 分钟标记之后再出现 1 小时的自动条目会违反前述排序规则：较长的 TTL 必须优先。反之，即 1 小时标记搭配 5 分钟的尾部，则是允许的。

## 验证缓存命中

响应中的 `usage` 对象会报告缓存活动：

| 字段 | 含义 |
|---|---|
| `cache_creation_input_tokens` | 本次请求写入缓存的 token 数量（您为此支付了约 1.25 倍的写入溢价） |
| `cache_read_input_tokens` | 本次请求从缓存中读取的 token 数量（您为此支付了约 0.1 倍的费用） |
| `input_tokens` | 以全价处理的 token 数量（未被缓存） |

如果在多次具有相同前缀的重复请求中，`cache_read_input_tokens` 始终为零，则说明存在静默失效机制——可通过对比两次请求的渲染后提示字节来定位问题。

**`input_tokens` 仅代表未被缓存的部分。** 总提示大小 = `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`。若您的代理运行数小时，但 `input_tokens` 仅为 4K，则其余部分均由缓存提供——请核对总和，而非单个字段。语言特定的访问方式：`response.usage.cache_read_input_tokens`（Python/TS/Ruby）、`$message->usage->cacheReadInputTokens`（PHP）、`resp.Usage.CacheReadInputTokens`（Go/C#）、`.usage().cacheReadInputTokens()`（Java）。

**每次变更后都要验证，而不仅仅是在设置时。** 生产环境中最昂贵的缓存失效是无声的：请求依然成功，但账单却变高了——没有任何错误提示，也无人察觉。这类问题通常是回归而非首次实现的缺陷：缓存最初是有效的，但在后续对提示组装的改动中（例如系统提示中新增了一个动态字段、引入了历史重写功能、工具列表不再具有确定性等），每次请求都会漏掉缓存，且持续数月未被发现。`usage` 字段是判断缓存是否正常工作的唯一依据。每当提示组装代码发生变化时，都应重新检查这些字段；建议采用持续性的检查机制——例如在集成测试中断言第二次相同请求的 `cache_read_input_tokens > 0`，或对 `usage` 字段进行监控——而不是仅做一次性的查看。

**健康循环的特征。** 写入操作仅计费超出最高缓存命中范围的增量部分，因此在稳定的多轮对话中，每次请求都应读取迄今为止累积的所有内容，并仅写入上一轮新增的部分：

- `cache_read_input_tokens`：整个先前的前缀，逐轮增长；
- `cache_creation_input_tokens`：大致为上一轮助手的输出加上新追加的输入，相对于整个对话而言较小；
- `input_tokens`：仅包含最后一个断点之后的部分。

如果每次请求的 `cache_creation_input_tokens` 都接近整个对话的大小，则要么是断点上游的前缀被重写了，要么是由于某些原因导致写入发生，而这种原因无法通过负载差异和缓存诊断来定位——当模型启用了思维模式时，若其会剥离前一轮的思维块，则失效发生在服务端（参见“失效层级”）；此外，如果某一轮新增的内容超过20个位置（并行工具调用会被压缩为一个位置——参见“20块回溯窗口”），则会导致前一条记录被移出回溯窗口，从而使得每次请求都以字节完全相同的负载重写整个对话（参见“20块回溯窗口”）。首先应在模型层面和本轮对话结构上排除这两种“无变化”的情况。读取操作只能落在之前请求已写入断点的位置，因此 `usage` 字段只能表明前缀发生了断裂（读取量通常会骤降甚至归零），但无法指出具体位置——需借助下方的负载差异分析或缓存诊断来精确定位。

**定位失效源头。** 记录连续几次请求的完整负载（即完整的 JSON 请求体），并对相邻两份进行差异比较。在不断增长的对话中，相邻请求的末尾部分理应存在差异（即新追加的一轮）；真正应该保持字节一致的是重叠部分——前一次请求的提示应作为下一次请求的前缀原样重现。进行差异比较前，请先去除 `cache_control` 标记：移动标记在相邻请求之间总是不同的，且它本身并非失效因素（此前已标记的块仍被视为缓存命中）。在重叠区域内，第一个剩余的差异点即为失效位置。这种方法能够捕捉到代码审查难以发现的一类缺陷——例如序列化的非确定性、库对键或字段的重新排序，以及那些在不同请求间变化但在同一请求内不变的值。在 Claude API 中，缓存诊断功能（beta 头部 `cache-diagnosis-2026-04-07`）会在您启用后于服务端自动执行此类比较：请在**每次**请求中都携带该头部——指纹仅针对携带过该头部的请求存储，因此事后补加只会导致 `previous_message_not_found` 错误；随后将前一次响应的 `id` 作为 `diagnostics.previous_message_id` 传递，并从响应的 `diagnostics` 对象中获取两次请求发生分歧的具体位置（模型、系统、工具或消息历史）。无需再额外记录负载。可用性信息请参阅：`shared/platform-availability.md`。**未说明的写入行为：** `usage.cache_creation` 会按 TTL 将 `cache_creation_input_tokens` 细分为 `ephemeral_5m_input_tokens` 和 `ephemeral_1h_input_tokens`。当请求已启用缓存时，诸如网络搜索之类的工具会在工具调用结果后自动插入一次 5 分钟的缓存写入——该写入发生在您未显式标记的位置；这是预期行为，并非失效机制。

## 失效层级

并非每次参数变更都会导致所有内容失效。API 具有三层缓存，且变更仅会使本层及以下各层失效：

| 变更 | 工具缓存 | 系统缓存 | 消息缓存 |
|---|:---:|:---:|:---:|
| 工具定义（新增/删除/重新排序） | 否 | 否 | 否 |
| 模型切换 | 否 | 否 | 否 |
| `speed`、网络搜索、引用开关 | 是 | 否 | 否 |
| 系统提示内容 | 是 | 否 | 否 |
| `tool_choice`、图像 | 是 | 是 | 否 |
| `thinking` 或 `effort` 变更 | 模型相关 | 模型相关 | 否 |
| 消息内容 | 是 | 是 | 否 |

由此可知：您可以在每个请求中单独更改 `tool_choice` 而不会使工具与系统缓存失效；消息内容的变更也始终不会触及这些缓存。思维模式和 `effort` 的变更总是会使消息缓存失效；而在那些会先渲染思维配置再处理工具与系统的模型上，它们还会进一步使工具与系统缓存失效——因此，请在路由级别固定思维与努力设置，而非在每个请求中随意调整。只有工具定义和模型变更才会触发所有模型的完整重建。

**这三行中各有其保留缓存的“逃生通道”**——即工具行、系统提示行，以及（在 Claude Fable 5.1 / Claude Mythos 5.1 / Claude Opus 5.5 / Claude Opus 5 上）`effort` 行——其方法均为将变更从顶层请求移至 `messages[]` 中的系统消息内，在已缓存的前缀之后进行。注入后再删除的模式也有其专属通道：在用户消息中的 `tool_result` 块之后追加一段文本块，且该文本块始终不被删除。**各通道的适用性因行而异**——它们之间并不相互绑定：| 使缓存失效的顶级变更 | 保留缓存的形式 | 可用版本 |
|---|---|---|
| 工具定义（新增/删除） | `tool_addition` / `tool_removal` 块——参见 `shared/tool-use-concepts.md` 第“会话中工具变更”节 | Claude Opus 5、Claude Opus 5.5、Claude Opus 4.8、Claude Fable 5、Claude Fable 5.1、Claude Mythos 5、Claude Mythos 5.1、Claude Sonnet 5.5（不包括 Claude Sonnet 5），受 `mid-conversation-tool-changes-2026-07-01` 功能标志控制 |
| 系统提示内容 | 一条 `{"role": "system", "content": "..."}` 消息——参见上文“会话中的系统消息”节 | Claude Opus 5、Claude Opus 5.5、Claude Opus 4.8、Claude Fable 5、Claude Fable 5.1、Claude Mythos 5、Claude Mythos 5.1——**现已可用**（Claude Sonnet 5.5 在发布时即支持），无测试版标识 |
| 每轮提醒（注入后在下一轮请求中删除） | 一条作用于本轮的 `clear_at: "next_user_message"` 系统消息，保留在对话记录中——参见上文“会话中的系统消息”节（不含测试版：紧接 `tool_result` 块之后的一段文本块，之前的副本仍被保留） | 同会话中系统消息所适用的模型，受 `mid-conversation-system-clear-at-2026-08-21` 功能标志控制 |
| `effort` 变更 | 一条 `{"role": "system", "content": [], "output_config": {"effort": ...}}` 消息——参见 `shared/model-migration.md` 中的“从 Claude Fable 5 迁移到 Claude Fable 5.1”部分 | Claude Fable 5.1、Claude Mythos 5.1、Claude Opus 5.5、Claude Opus 5、Claude Sonnet 5.5（仅限思考模式），受 `mid-conversation-output-config-2026-07-01` 功能标志控制 |
| 被丢弃的思考块（将 Claude Fable 5.1/Claude Mythos 5.1/Claude Opus 5.5/Claude Sonnet 5.5 的块发送给无法识别该块的模型——只有 Claude API 上的 Claude Fable 5.1 和 Claude Mythos 5.1 能读取 Claude Opus 5.5 的块，其他模型均无法读取 Claude Sonnet 5.5 的块——或使用历史编辑检查 `drop_block`） | 无——API 会在该次请求中直接丢弃该块，并自其位置起更新消息缓存；工具和系统缓存保持不变。接收方模型能够识别的块会原样返回，缓存不受影响 | - |

模型切换没有例外机制：缓存是按模型划分的。请将主循环维持在同一模型上，为较便宜的子任务启动一个子代理（参见 `agent-design.md` 第“代理的缓存”节）。

**思考块与消息缓存（特定于模型）。** 在 Claude Fable 5、Claude Fable 5.1、Claude Mythos 5、Claude Mythos 5.1、Mythos Preview、Opus 4.5 及更高版本（包括 Claude Opus 5.5），以及 Sonnet 4.6 及更高版本上，默认会保留前一轮的思考块，因此在启用思考的情况下传递一条常规（非工具结果）用户消息时，消息缓存仍然有效。而在更早的 Opus 和 Sonnet 模型，以及所有 Haiku 模型（直至 Haiku 4.5），同样的请求会从上下文中移除之前缓存的思考块，且自第一个被移除的思考块之后的所有消息都会脱离缓存——在代理循环中，这表现为在工具调用之后紧接着普通用户消息的那几轮出现 `cache_creation_input_tokens` 突增。（在不同请求之间切换思考的开启与关闭状态，会对所有模型的消息缓存造成无效——参见上方的层级表。更改 `output_config.effort` 的行为与更改思考参数相同；显式设置模型的默认努力程度等同于省略该项，因此固定默认值不会带来额外开销。）

## 20条回溯窗口

每个断点最多向后查找 **20 条记录**以寻找先前的缓存条目。在 Claude API 上，连续的 `tool_use` 块算作一条记录，连续的 `tool_result` 块也视为一条记录，因此包含多个*并行*工具调用的回合并不会将前一请求的条目挤出窗口；但如果某一轮添加了超过 20 条其他内容（如长串的顺序工具调用、大量文本或图像块），则仍有可能发生这种情况——下一次请求的断点将找不到之前的缓存，从而导致缓存缺失且无声跳过。修复方法：在长轮次中，每隔约15个位置设置一个中间断点，或将标记放置在距离上一轮最后一次缓存块20个位置以内的区块上。

## 并发请求的时序

只有当首次响应**开始流式传输**后，缓存条目才会变为可读状态。N个具有相同前缀的并行请求都会按全额计费——没有一个能够读取其他请求仍在写入的内容。

对于扇出模式：先发送1个请求，等待首个流式传输的令牌（而非完整响应），然后再发出剩余的N-1个请求。这些后续请求将读取第一个请求刚刚写入的缓存内容。

同样的逻辑也适用于多代理设计：N个并行工作的代理各自基于同一上下文组装略有不同的提示，会分别写入N个独立的缓存条目，且彼此之间无法读取对方的写入内容。当输入成本占主导时，在字节完全相同的共享前缀基础上减少工作通道数，或者由单个工作进程进行N次连续处理，都能将写操作转化为读操作。

## 预热缓存

为消除*首次*真实请求的缓存未命中延迟，请在应用启动时（或按一定间隔）发送一个`max_tokens: 0`的请求。API会执行预填充操作——按照您设定的`cache_control`断点写入缓存——并立即返回`content: []`、`stop_reason: "max_tokens"`，以及一个已填写的`usage`字段（无输出token计费；但会按`cache_creation_input_tokens`收取正常的缓存写入费用）。

**何时进行预热**——预热是以当前的一次缓存写入费用，换取下一次真实请求更低的TTFT。当以下三个条件同时满足时，预热是值得的：(a) 首次请求的延迟对用户可见（如聊天、语音或交互类场景，而非后台任务）；(b) 共享前缀足够大，冷写入明显较慢；(c) 在流量到来之前有空档期可以触发预热——例如应用启动、工作进程初始化、部署后或定时窗口开启时。

| 何时无需预热 | 原因 |
|---|---|
| 流量持续不断（请求间隔小于或等于TTL） | 首次真实请求即可预热缓存，后续请求均能命中；额外的预热调用只是多余的写入操作 |
| 前缀较小或低于可缓存的最小长度 | 冷写入的性能损失可以忽略不计 |
| 每个请求或用户的前缀各不相同 | 不存在可供预热的共享内容 |
| 您需要针对大量不同前缀进行推测性预热 | 每次预热都相当于约1.25倍的写入开销，成本可能超过节省的延迟 |

**定时重预热**：仅在流量存在超过TTL的间歇时才需要。如果真实请求的到达频率高于每5分钟一次，它们本身就能保持缓存常温，无需再添加间隔重预热。对于突发性流量且存在长时间空闲的情况，可在略早于TTL时进行重预热，或改为设置`ttl: "1h"`，并降低重预热的频率。

```python
client.messages.create(
    model="claude-opus-5-5",
    max_tokens=0,
    # 示例值——请使用与实际流量相同的思考和努力配置（见下文）
    thinking={"type": "adaptive"},
    output_config={"effort": "high"},
    system=[{
        "type": "text",
        "text": SYSTEM_PROMPT,
        "cache_control": {"type": "ephemeral"},
    }],
    messages=[{"role": "user", "content": "warmup"}],
)
```

**断点设置**：将`cache_control`置于与真实请求**共享的最后一块内容**（系统提示或工具定义）上——**不要**放在占位符用户消息上，也不要通过顶层的自动缓存机制来设置（那样会导致缓存以占位符为键）。占位符可以是任意非空白字符串；它会在预填充阶段被读取，但永远不会被回复。**使预热请求的思考模式和力度设置与真实流量保持一致。** 这两种设置都会被渲染到提示中（参见§无效化层级），因此使用不同设置进行的预热可能会写入一条真实流量永远不会命中的缓存条目。对于采用自适应思考模式的流量，应在预热请求中传入相同的 `thinking` 和 `effort` 值。使用扩展思考模式的流量（`thinking.type: "enabled"`，仅在 Claude 4.6 及更早版本以及 Claude Mythos Preview 中支持）无法匹配，因为 `max_tokens: 0` 会拒绝该设置（详见下方“被拒绝的组合”）。预热是否仍对这类流量有帮助，取决于模型在何处渲染思考配置，而各模型的具体行为并未在文档中说明——请在首次真实请求时检查 `cache_read_input_tokens` 的值。

**被拒绝的组合：** 当 `stream: true`、`thinking.type: "enabled"`、`output_config.format`、`tool_choice` 为 `{"type":"tool"}` 或 `{"type":"any"}`，或在消息批处理请求中时，若同时设置 `max_tokens: 0`，将引发 `invalid_request_error` 错误。

**TTL 仍然适用**——对于默认缓存，至少每 5 分钟重新预热一次，或使用 1 小时的 TTL。这取代了旧版的 `max_tokens: 1`  workaround（无需丢弃单 token 回复，不计输出 token 费用，且意图明确无歧义）。
