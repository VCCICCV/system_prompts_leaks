# 保留思维——原因、修复与保留列表

> **`shared/preserved-thinking-migration.md` 的参考文档**（即 `preserved-thinking-migration` 工作流）。该文件本身并非工作流，而是包含了指南中使用的四项查找表：用于模型切换的对话规则、“原因 → 检测 → 修复”对照表、保留列表，以及应避免的失败模式。这些内容被单独存放，以便使指南能够在一个阅读视图中完整呈现。当指南指引您来到此处时（步骤 1.4、步骤 2 或步骤 3），请阅读本文件，并参照下方的步骤编号以定位指南中的相关内容。

## 对话中途切换模型

一种将同一对话路由至多个模型的机制——在简单轮次使用更便宜的模型，在主模型不可用时启用备用模型，或从对话初始使用的模型升级——会额外进行一项检查，即与前缀检查并行的响应共享检查。以下规则是当前 API 的行为，基于对 Claude API 在 `claude-opus-5`、`claude-opus-5-5`、`claude-fable-5` 和 `claude-fable-5-1` 四个模型上、两种 `prefix_mismatch_behavior` 模式的观察得出；“保留思维”页面（位于 `shared/preserved-thinking-migration.md` 中的“来源与实时参考”部分）也载明了相同规则，“扩展思维”页面（“仅由生成该块的模型或更新版本的模型读取”一节）则列出了各模型可读取哪些区块。

**模型是否记录在签名中？** 是的。`thinking` 区块的 `signature` 会连同对话记录及前一个 `thinking` 区块一起记录生成该区块的模型。当该区块被重放时，API 首先会检查当前读取该区块的模型是否能读取生成它的模型所生成的区块（页面规则：“生成该区块的模型，或更新版本的模型”）——即*模型检查*；只有通过这一检查后，才会进一步检查该区块之前的对话是否未发生变化——即*前缀检查*。请求中的 `model` 字段并不属于对话记录的一部分，因此更改它不算编辑：**仅模型切换本身绝不会导致前缀检查失败。**

**模型切换是否会破坏检查？** 截至 2026 年 9 月 3 日，API 的表现如下：模型切换不会导致请求失败——无论是升级、降级、往返切换，还是降级结合编辑，无论是在 `"error"` 模式下还是在 `"drop_block"` 模式下，均返回 200 状态码。“`error`”模式会使*编辑*显性化；但它并不会使*模型切换*显性化，因为模型检查没有错误设置：当前模型无法读取的区块会被丢弃，而非被拒绝。有关当前规则，请参阅“保留思维”页面。不同之处在于方向的变化是否会影响先前推理的使用：- **升级（将旧版模型的区块回放至 Claude Fable 5.1）：无需任何操作。** Claude Fable 5.1 可以读取由 Claude Opus 5 和 Claude Fable 5 等更早版本模型生成的思考内容（完整列表见“扩展思考”页面）。这些区块会被保留并输入到模型中，计入输入 token 数量，且 `input_transformations` 为 `[]`。旧版模型的区块不携带可供 Claude Fable 5.1 比对的对话记录，因此在该区块之前的编辑不会使其失效；从 Claude Opus 5 迁移而来的对话仅会在 Claude Fable 5.1 自此之后生成的轮次中出现问题。
  
- **降级（将 Claude Fable 5.1 的区块回放至 Claude Opus 5 或 Claude Fable 5）：丢失的是该请求中的推理信息，而非整个请求。** 较旧的模型无法读取这些区块，因此 API 会将其从本次调用中排除，并在启用 beta 标头时将每个被丢弃的区块报告为 `{"type": "thinking_dropped", "reason": "model_binding_mismatch", "path": ...}`，且不对这些被丢弃的 token 计费。截至 2026 年 9 月 3 日，在两种模式下这都不会触发 400 错误，且不存在诊断标头（该标头用于前缀检查）。您的 `messages` 数组始终保持不变：这些区块仍保留在对话历史中。

- **往返循环（先 Claude Fable 5.1，再旧版模型，最后再回到 Claude Fable 5.1）：只要客户端保持历史完整，就不会有任何损失。** 当再次切换回 Claude Fable 5.1 时，所有区块都会被重新读取——包括切换前的区块、旧版模型生成的思考区块，以及返回后新生成的区块。经四轮观察：旧版模型回合之后生成的 Claude Fable 5.1 区块是有效的，Claude Fable 5.1 的区块链并不在意其间插入了来自其他模型的一轮。同样这段四轮历史若再回传给旧版模型，则只会丢弃其中的 Claude Fable 5.1 区块，而保留其自身的区块。

- **Claude Opus 5.5 执行相同的前缀检查，并与 Claude Fable 5.1 并列，而非在其之下。** 本文件中凡提及 Claude Fable 5.1 执行前缀检查之处，同样适用于 Claude Opus 5.5（2026 年 9 月 23 日观察：在 `"error"` 模式下，编辑过的历史会触发 400 错误；在 `"drop_block"` 模式下则会触发 `prefix_binding_mismatch` 的丢弃；同时会出现一个 `thinking_mismatch_allowed` 条目，但相关字段未设置）。不同之处在于各模型所读取的区块归属，详见“保留思考”页面：Claude Opus 5.5 可以读取来自 Claude Opus 5 及更早的 Opus、Sonnet 和 Haiku 模型的思考内容，但无法读取来自 Claude Fable 或 Claude Mythos 模型的思考；而在 Claude API 上，只有 Claude Fable 5.1 和 Claude Mythos 5.1 能读取 Claude Opus 5.5 的区块，其他模型均不能。因此，在 Claude API 上，从 Claude Opus 5 到 Claude Opus 5.5，以及从 Claude Opus 5.5 再到 Claude Fable 5.1 的过程都会保留推理信息（`[]`）；而从 Claude Fable 5.1 到 Claude Opus 5.5，或从 Claude Opus 5.5 到任何其他模型，则属于上述意义上的降级——会触发 `model_binding_mismatch` 的丢弃，在两种模式下均返回 200。

- **降级可能会掩盖一次编辑的影响。** 模型检查优先进行，因此旧版模型无法读取的区块根本不会进入前缀判断流程：如果一次请求既进行了降级切换，又编辑了先前的内容，则无论在何种模式下，都只会报告 `model_binding_mismatch`。编辑本身仍然存在；它会在下一轮 Claude Fable 5.1 中作为普通的前缀违规出现（在 `"error"` 模式下为 400 错误，在 `"drop_block"` 模式下为 `prefix_binding_mismatch`）。请逐轮检查并统计混合模型对话中的每一回合，而不仅限于发生切换的那一轮。

- **来自非 Claude 模型的回合** 不会使之前的思考失效，前提是它们以普通助手消息的形式追加到现有历史之后（包含 `text` 和 `tool_use` 内容，不含 `thinking` 区块），且之前的内容未被修改。在此类回合之后生成的 Claude Fable 5.1 思考仍将有效。

- **一种能够读取区块但不执行对话检查的孪生模型**（哪些模型能读取哪些区块详见“扩展思考”页面）：即使在编辑过的历史上，其回合也会报告 `[]`，因此在该模型回合上所做的编辑仅会在下一轮 Claude Fable 5.1 中显现——与降级时的情形类似，只是用 `[]` 而非模型丢弃来提示这一问题。**修改工具描述会使检查失效吗？** 会。工具是按其完整定义——名称、描述和 `input_schema`——进行比较的，因此即使只修改一个工具的描述，也会使该变更前生成的所有思维块失效，并以 `prefix_binding_mismatch` 错误、`pattern=tool_schema_changed` 标识上报（API 在报告描述编辑和模式编辑时会使用相同的措辞）。添加或移除普通工具也会产生同样的效果，错误类型为 `tool_set_changed`。调整工具顺序则不会有问题，而标记为 `defer_loading: true` 的工具在被引用之前不会参与比较。解决方法是针对 `tool_schema_changed` 和 `tool_set_changed` 这两种情况：在对话生命周期内冻结每个工具的文本，并通过引用的方式添加或移除工具；或者，在 `inline-tools-2026-09-15`（Claude API）下，追加一个携带新定义的 `tool_addition`（详见下文“较新测试版中的追加式表单”）。

**原因 -> 检测 -> 修复。** 模型切换会产生两种形式的发现，其中只有第二种才是夹具缺陷：1. **对话被路由到了一个无法读取其思考内容的模型。** *检测*：在旧模型的轮次中会出现`model_binding_mismatch`条目；探针会按轮次打印`model_drops=N`，按对话打印`model_drop_turns`，此外还会统计前缀中断次数；而`prefix_diff.py`会在`model`字段发生变化的那一对轮次上打印`model_switch=A->B`（绝不会显示为MISMATCH）。*修复*：这是路由决策的问题，而非历史记录的编辑。将包含思考块在内的相同`messages`发送给所有模型，并在切换时保留beta头和`block_binding`字段（只要模型支持`thinking`，该对象就能被接受）。如果产品需要这些轮次的推理过程，则应让对话继续留在产生推理的模型上，并在对话边界处切换模型；如果确实需要使用旧模型处理这些轮次，则应允许其在没有新推理的情况下运行。将其报告为“因路由导致的推理丢失”——列出受影响的对话和轮次——并与前缀中断一并上报，以便负责人作出决策。
2. **切换触发了编辑。** 有三种情况，每一种都可视为由切换触发的普通前缀中断：(a) 框架在切换时会剥离思考块，或根据各模型所见重建历史——差异中会显示被移除的块（若发生在中间则标记为`predecessor_missing`），且当对话返回时推理将永久丢失；*修复*：停止剥离，API本身已会过滤掉当前模型无法读取的内容。(b) 重新渲染的系统提示或工具列表在切换后仍“持续存在”——例如，一段回退横幅从此之后一直保留在`system`字段中，或者一条依赖于最后回答模型的提示——这些内容会与旧文本下生成的思考块一同传递至Claude Fable 5.1：在紧随其后的第一轮Claude Fable 5.1中会标注`system_rerendered`、`tool_set_changed`或`tool_schema_changed`（降级时，中间旧模型的轮次仅报告模型切换）。然而，若提示或工具集完全由调用的模型决定，则情况不同：此后每次Claude Fable 5.1请求都会携带与思考块生成时相同的文本，因此检查无法发现异常（经验证：返回Claude Fable 5.1时恢复原始提示，在两种模式下均返回200状态码及空数组`[]`），尽管差异对比会标记出切换对以及旧模型轮次仍因模型检查而丢失推理。*针对持续存在的场景的修复*：对于这类模式，保持每个模型在其自身轮次内的提示与工具文本不变，并将任何必须在对话中途更改的内容以追加的`role: "system"`消息形式传递。(c) 目标模型不接受的请求格式——拒绝某种`thinking`配置（来自请求校验的400错误，其错误信息会明确指出相关字段，而非绑定失败），或对话中途出现的`role: "system"`消息，以及伴随的`tool_addition`、`tool_removal`和`clear_at`等操作，而这些操作所涉及的模型并未列在“对话中途系统消息”页面中（该页面注明Claude Sonnet 5不支持此类操作：“请改用顶级的system字段”）；*修复*：采用一条所有路由中的模型都能接受的请求体。

## 原因 -> 检测 -> 修复

`pattern`列是API诊断头和差异脚本共同使用的关键词。“差异显示”出自`prefix_diff.py`的归属行；“扫描主导”则是`--scan`报告的启发式判断；修复方案则来自`shared/preserved-thinking-migration.md`第三步中的追加式写法。阅读模式关键词时需注意一点：对于“摘要+尾部”的压缩，头部显示的关键词取决于被移除的内容量——同一段代码路径在不同对话中会分别报告`tail_kept`、`compaction_summary`或`unknown`，同时附带`kind=blocks_replaced`标签——因此，应结合差异中的归属行以及`kind`字段（`blocks_removed`或`blocks_replaced`）来确定具体原因，而不能仅凭单一的模式关键词进行判断。| 层级 | `pattern`（和 `kind`） | 框架做了什么 | 差异显示 | 扫描线索 | 修复方案 |
|---|---|---|---|---|---|
| 1 | `system_rerendered`（`system_changed`） | 系统提示词根据每次请求的内容重新构建：时间、工作目录、账户行、内存或指令文件、标志、版本字符串 | `system[i] 在第 N 个字符处发生变化` | 提示词构建器附近读取时间和环境；模板按请求渲染 | 只渲染一次，将字节与对话一起存储并重放；会话级别的事实放入第一轮；变更以追加的 `role: "system"` 消息形式发出 |
| 2 | `tool_set_changed`（`tools_changed`） | 在首次请求之后新增或移除了工具：插件或 MCP 服务器晚接入、提供商断开连接、权限变更 | `tools: X 新增` / `移除` | 会话开始后 `tools` 被修改；每次请求都获取工具列表 | 在会话开始时声明完整工具集；对于晚加入的工具，使用 `defer_loading: true` 标记（未被引用时安全），并通过追加的系统消息中的 `tool_addition` 通告——绝不再追加普通工具；绝不从数组中移除工具——应通过 `tool_removal` 块将其撤下，并保留定义，若模型仍调用则返回“不可用”的常规错误 |
| 2 | `tool_schema_changed`（`tools_changed`） | 工具名称不变，但描述或 Schema 文本不同：日期、刷新的令牌、实时列表、描述中的版本号 | `tools: X 描述在第 N 个字符处发生变化` | 描述或 Schema 由模板或状态生成 | 冻结每个工具在本次对话中的文本；按发送时的定义存储并重放。在没有 `inline-tools-2026-09-15` 测试版的情况下，无法用仅追加的形式表达同名工具的变更——只能通过新名称来提供变更后的文本；在此基础上，追加一条携带新定义的 `tool_addition` 消息（详见下方测试版部分） |
| 1–2 | `system_and_tools_changed`（`multiple`） | 系统与工具均被重新渲染，消息未动：某个连接器在第二次请求时接入，或重启/恢复时两者都被重新推导 | 上述两种情况皆有 | 启动、恢复、重新连接路径 | 在重启及模型切换时重播已存储的提示词和工具文本（切换本身不是边界：如果重新渲染的结果延续到该模型后续的请求中，则此次中断以切换为触发点；而纯由调用模型决定的提示词在各模型自身的回合中是稳定的，不构成中断）；唯一明确的边界是新对话、用户发起的重置，以及完全压缩后的下一次请求 |

| 3 | `rolling_truncation`（`blocks_removed`） | 最早的几轮对话被整体丢弃——滑动窗口 | `messages[0..k] 被移除` | `messages[-N:]`，保留最后若干条，设置窗口大小 | 在没有 `compact-2026-09-04` 测试版的情况下，客户端无法保留思考过程（有了该测试版，按需压缩可以做到，但窗口必须进行摘要而非单纯丢弃——详见下方测试版部分）。可选方案：服务端压缩或上下文编辑；简单压缩（摘要加新轮，不再保留更早内容）；或者保留窗口，将保留轮次的思考过程以确定性方式记录剥离，或发送 `drop_block`（效果等同）——需衡量 |

| 3 | `compaction_summary`（`blocks_replaced`） | 较早的对话被一段更短的摘要原地替换，尾部保持不变 | `messages[i..j] 被 1 条或多条消息替换` | 同上 | 同上；也可将摘要转为简单压缩（不再重放摘要之前的任何内容）；或在 `compact-2026-09-04` 下采用按需压缩（详见下方测试版部分） |
| 4 | `tool_results_rewritten`（`blocks_modified`） | 已发送的旧 `tool_result` 内容被修剪或清除 | `messages[i]（user）内容[j]（tool_result）在第 N 个字符处发生变化` | 对早期轮次应用工具结果截断 | 在首次发送前固定输出；后续通过服务端上下文编辑清除（`clear_tool_uses_20250919`，测试版 `context-management-2025-06-27`）；客户端修剪仅在明确边界处进行，作为成长历史的纯函数 |
| 1 | `tool_use_rewritten`（`blocks_modified`） | 旧的 `tool_use.input` 在重放时被重新编码或归一化 | `content[j]（tool_use）发生变化` | 输入归一化器，在工具调用时执行 `to_dict` | 完整回显接收到的 `tool_use.input`；仅对副本进行执行时的归一化处理 |

## 维护清单——永远无需标记的内容

扫描与差异比对可能会诱使您报告一些检查并不关注的事项。以下内容无需列入报告（或可归入“已检查，无问题”的条目中）：

- 在不改变工具本身的情况下，对 `tools` 数组中的工具进行重新排序——比较时将其视为按名称键控的集合。
- 添加一个尚未被任何内容引用的 `defer_loading: true` 工具。
- 在任意位置添加、移动或移除 `cache_control` 标记。
- 更改 `model`、`max_tokens`、`temperature` 等采样参数，`tool_choice`、`metadata`、`stop_sequences`、`stream`、`service_tier`、`output_config`（包括 effort），或 `thinking` 配置本身——这些都不属于当前比较的前缀部分（模型变更会触发单独的模型检查，并报告为 `model_binding_mismatch`，而非本次检查）。请求头也不在其中，但有一个实验性功能会在服务端由 API 注入一个工具（代码执行或网络搜索回退），这会导致在请求体相同的情况下工具集发生变化。
- 字符串内容与由相同文本组成的一个单独文本块之间的差异；文本块开头或结尾的空白字符；仅包含空白字符的文本块；JSON 键的顺序；`1` 与 `1.0` 的区别。
- 图像或文档的 URL 经过旋转或重新签名，但仍提供相同的字节数据。
- 从历史记录的开头（最早的消息）或末尾移除思考块，或者全部移除——这是允许的，且“保留的思考”页面详细说明了这三种情况。保留的块必须保持原始序列的连续性；这样做会影响推理过程，但不会影响已保留块的有效性。对于那些 `tool_use` 尚未收到 `tool_result` 的助手回合，应保留其思考内容（该页面会提示这一点）。有两件事不在上述列表中：从中间移除一个块，这会使它之后的所有块失效；以及将已移除的块重新放回，这同样会使它缺席期间生成的块失效。
- API 本身在服务端添加或重写的任何内容（如服务端压缩、上下文编辑、清除思考内容，或其自行注入的文本）——校验是在您发送的请求上进行的。
- 对话中途插入的 `role: "system"` 消息，以及被清空但原样保留并重复播放的回合级消息。

## 应避免的失败模式- **在从不重放思考的切片上进行度量。** 每次对话的第一个请求都不会重放任何内容；短回合可能不会返回任何思考块；剥离了思考的流水线也无思考可检查。每次运行时，先读取重放思考的计数，再读取丢弃计数。
- **统计条目而非中断次数。** 一个过时的阻塞会在后续每次请求中再次失败。报告首次出现中断的对话及其发生的回合；每次请求的条目数只会随对话长度增加而上升。
- **信赖头部而非主体。** 诊断头部是尽力而为且未公开的；`input_transformations`才是契约。没有头部的丢弃仍然是丢弃；仅含头部的流水线会漏掉所有头部未到达的丢弃。
- **将仅含头部的运行视为强制执行测试。** 对于尚未强制执行的组织，仅含头部的记录会将失败记为 `thinking_mismatch_allowed`，且不丢弃任何内容：这有助于在生产环境中发现编辑问题，但无法衡量强制执行的成本。为此请设置 `prefix_mismatch_behavior`。
- **拼写字段错误。** 只有 `block_binding.prefix_mismatch_behavior` 是文档中记载的名称；探针会移除 `block_binding` 下找到的其他键，并报告具体是哪一个；生产代码应使用文档中的正确名称。
- **从应用自身的对象中读取捕获数据。** 从 ORM 或领域对象重建的捕获会掩盖检查所捕捉的重新序列化问题。应在 HTTP 层进行捕获。
- **重放他人的对话。** 来自其他组织的捕获仍会被丢弃其阻塞，但不会被诊断，且此次丢弃也无法为流水线提供任何反馈。请使用生成该捕获的组织的密钥进行重放。
- **合并修复。** 在一次变更中同时修复两个原因，将导致无法分别追溯或回滚。每次只修复一个原因，并在修复后重新测量。
- **将压缩改写当作必选项来推荐。** 保留尾部和后台压缩在没有 `compact-2026-09-04` 测试版的情况下，客户端侧并无仅追加的形式（按需压缩）；应测量产品当前采用的方案，选择 `error` 或 `drop_block`，并记录这一决策。
- **设置 `drop_block` 即认为完成。** `"drop_block"` 只是隐藏了错误，并不能修复引发该错误的编辑问题。被丢弃的阻塞不会计费，但会话的 token 使用量仍可能增加，因为 Claude 有时会通过更多思考来重新生成被丢弃的部分。当被丢弃的思考块越多，或在一个长会话的更多回合中发生丢弃时，这种增加往往更为显著。应使用 `drop_block` 进行度量（步骤 2），并将其作为临时止措，统计每个会话中 `input_transformations` 包含 `prefix_binding_mismatch` 条目的响应数量，然后修复相关编辑。
- **重新发送被拒绝的主体，或逐请求修复损坏的会话。** “保留思考”页面上的“在代码中处理错误”建议：使用测试版头部并设置 `prefix_mismatch_behavior: "drop_block"` 再试一次，并将此选择与会话一同保存，以便后续每次请求都发送该头部，包括重启后；对于无法发送测试版头部的情况，一次性从历史中移除所有 `thinking` 和 `redacted_thinking` 阻塞，并在后续请求中不再包含它们。如果某个已保存的会话现在每次请求都会失败，则说明其中已存储了相关编辑：同样适用上述处理方法，此后产生的思考只要之前的内容不变，就仍然有效，但仍需找出该编辑，以免新会话再次触发。
- **对转发内容进行改写的库、代理或网关。** 其改写是用户无法看见或修复的编辑。应原封不动地转发调用方的 `anthropic-beta` 值及 `thinking.block_binding`，并将 `input_transformations` 原样返回给调用方（拒绝未知键的选项模式可防止调用方选择 `"drop_block"`）；将调用方放置的 `role: "system"` 消息保留在原位——若将其移至顶层 `system` 字段，则会使得对话中的所有思考块失效；通过 `tool_choice: {"type": "none"}` 关闭工具使用，切勿通过删除 `tools` 来实现；并且不要隐藏 400 错误码——拦截该错误、剥离思考并代表调用方重试的日志应如实记录这一过程。
- **未记录的剥离操作。** 在收到 400 错误后剥离思考，却未使该剥离过程具有确定性且可记录，会导致下一轮再次发送被拒绝的阻塞，并在整个对话剩余过程中每轮都会重复失败。
- **未设置生产环境的值。** 默认值因界面和账户年龄而异；对于尚未启用强制执行的账户，未设置的字段仅表示检查已被记录（`thinking_mismatch_allowed`），且该默认值会在账户或模型启用强制执行之日发生变化。请务必设置，并监控条目数或 400 错误的发生次数。
- **误将模型检查当作本次检查。** 切换模型后出现的 `model_binding_mismatch` 条目是预期且不计费的；只有 `prefix_binding_mismatch` 才属于流水线检测到的问题。
