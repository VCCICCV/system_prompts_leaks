# 代理设计模式

本文件介绍了基于 Claude API 构建代理的决策启发式方法：应选用哪些基础组件、如何设计工具接口，以及在长时间运行中如何管理上下文和成本。有关各工具的具体机制和代码示例，请参阅 `tool-use-concepts.md` 及各语言专用文件夹。

---

## 模型参数

| 参数 | 使用场景 | 预期效果 |
| --- | --- | --- |
| **自适应思考**（`thinking: {type: "adaptive"}`） | 当希望 Claude 自主控制何时以及投入多少思考时 | Claude 会根据每次请求动态决定思考深度，并在工具调用之间自动穿插思考过程。无需调整 token 预算。 |
| **努力程度**（`output_config: {effort: ...}`） | 当需要在思考的全面性和 token 效率之间进行权衡时 | 努力程度越低，工具调用次数越少且更集中，前言更简洁，确认信息更精炼。“medium”通常是较为理想的平衡点。当正确性比成本更重要时，可使用“max”。 |

有关模型支持及参数详情，请参阅 `SKILL.md` 第四节“思考与努力”。

## 设计您的工具接口

### Bash 与专用工具

Claude 并不了解您的应用的安全边界、审批策略或用户界面。Claude 会发出工具调用，而由您的适配器负责处理这些调用。工具调用的形式决定了适配器能够执行的操作。

**Bash 工具**赋予 Claude 广泛的程序化操作能力——几乎可以执行任何动作。但适配器接收到的只是单一的命令字符串，无论执行何种操作，其形式都相同。将某项操作提升为**专用工具**后，适配器便能获得针对该操作的特定钩子，并通过类型化的参数对其进行拦截、准入控制、渲染或审计。

**何时将某项操作提升为专用工具：**

- **安全边界。** 需要准入控制的操作是天然的候选者。可逆性是一个有用的判断标准：难以撤销的操作（如外部 API 调用、发送消息、删除数据）可以通过用户确认来加以控制。例如，“send_email”工具易于设置准入控制，而“bash -c 'curl -X POST ...'”则无法做到。
- **时效性检查。** 专用的“edit”工具可以在文件自上次被 Claude 读取后发生变更时拒绝写入操作。Bash 无法强制实施这一约束。
- **渲染。** 某些操作受益于定制的用户界面。Claude Code 将提问操作提升为工具，以便以模态窗口的形式呈现选项，并在得到答复之前阻塞代理循环。
- **调度。** 像“glob”和“grep”这样的只读工具可以标记为可并行执行。如果所有操作都通过 Bash 执行，适配器无法区分可并行的“grep”与不可并行的“git push”，因此必须串行处理。

**经验法则：** 先使用 Bash 以覆盖更多场景。当需要对操作进行准入控制、渲染、审计或并行化时，再将其提升为专用工具。

## Anthropic 提供的工具

| 工具 | 角色 | 使用场景 | 预期效果 |
| --- | --- | --- | --- |
| **Bash** | 客户端 | Claude 需要执行 shell 命令 | Claude 发出命令，由您的适配器负责执行。提供参考实现。 |
| **文本编辑器** | 客户端 | Claude 需要读取或编辑文件 | Claude 通过您的实现查看、创建和编辑文件。提供参考实现。 |
| **计算机使用** | 客户端或服务器 | Claude 需要与 GUI、Web 应用或可视化界面交互 | Claude 截取屏幕截图并发出鼠标/键盘指令。可由您自行托管环境，也可由 Anthropic 托管。 |
| **代码执行** | 服务器 | Claude 需要在您无需管理的沙箱中运行代码 | Anthropic 托管的容器，内置文件和 Bash 子工具。客户端不执行代码。 |
| **网络搜索/抓取** | 服务器 | Claude 需要获取超出其训练截止时间的信息（如新闻、时事、最新文档）或特定 URL 的内容 | Claude 发出查询或 URL 请求，Anthropic 执行并返回带引用的结果。 |
| **记忆** | 客户端 | Claude 需要跨会话保存上下文 | Claude 读写 `/memories` 目录。存储后端由您实现。 |

**客户端**工具由 Anthropic 定义（名称、Schema、Claude 的使用模式），但由您的运行时环境执行。Anthropic 提供参考实现。**服务器端**工具完全在 Anthropic 的基础设施上运行——只需在 `tools` 中声明，其余由 Claude 自动处理。

## 组合工具调用：程序化工具调用

在标准的工具使用模式下，每次工具调用都是一次往返：Claude 调用工具，结果进入 Claude 的上下文，Claude 对其进行推理，然后再调用下一个工具。三个连续的操作（读取用户档案 → 查询订单 → 检查库存）意味着三次往返。每次往返都会增加延迟和 token 消耗，而且大部分中间数据此后都不会再被使用。

**程序化工具调用（PTC）**允许 Claude 将这些调用组合成一段脚本。该脚本在代码执行容器中运行。当脚本调用某个工具时，容器会暂停，工具调用被执行（无论是客户端还是服务器端），结果直接返回到正在运行的代码中，而不是回到 Claude 的上下文中。脚本以正常的控制流程（循环、过滤、分支）来处理这些结果。最终只有脚本的输出会返回给 Claude。

| 适用场景 | 预期效果 |
| --- | --- |
| 多个连续的工具调用，或需要在进入上下文窗口前对大量中间结果进行过滤。 | Claude 会编写代码，将工具作为函数进行调用。代码在代码执行容器中运行。token 成本与最终输出相关，而非中间结果。 |

## 扩展工具集与指令集

| 功能 | 适用场景 | 预期效果 |
| --- | --- | --- |
| **工具搜索** | 可用工具众多，但每次请求仅需其中少数几个。不希望所有 Schema 一开始就全部加载到上下文中。 | Claude 会从工具集中搜索并仅加载相关的 Schema。工具定义是追加的，而非替换，因此可保留缓存（详见下方的缓存机制）。 |
| **技能** | 任务相关的特定指令，仅在必要时加载。 | 每个技能是一个包含 `SKILL.md` 文件的文件夹。技能描述默认保留在上下文中；当任务需要时，Claude 才会读取完整文件。 |

这两种模式都能保持固定上下文的规模较小，并按需加载细节。

## 长时间运行的代理：上下文管理

| 模式 | 适用场景 | 预期效果 |
| --- | --- | --- |
| **上下文清理** | 经过多轮交互后，上下文逐渐过时（旧的工具结果、已完成的思考）。 | 根据可配置的阈值清除工具结果和思考块，使对话记录保持精简，而无需进行摘要。 |
| **压缩** | 对话很可能达到或超过上下文窗口的限制。 | 较早的上下文会在服务器端被总结为一个压缩块。关于关键的 `response.content` 处理，请参阅 `SKILL.md` 中的“压缩”部分。 |
| **记忆** | 状态需要跨会话持久化（而不仅仅是单次对话内）。 | Claude 会在记忆目录中读写文件，即使进程重启也能保持状态。 |

**如何选择**：上下文清理和压缩都在单个会话内生效——清理会剔除过时的交互，压缩则在接近上限时进行摘要。记忆功能用于跨会话的状态保存。许多长时间运行的代理会同时使用这三种机制。

## 代理的缓存机制

**请先阅读 `prompt-caching.md`。** 其中介绍了前缀匹配不变性、断点设置、静默失效器审计，以及为何在会话中途更换工具或模型会导致缓存失效。本节仅讨论针对这些约束的代理层特有应对方案。| 约束（摘自 `prompt-caching.md`） | 针对特定代理的 workaround |
| --- | --- |
| 会话中途修改系统提示会导致缓存失效。 | 改为在 `messages[]` 中追加一条 `{"role": "system", ...}` 消息（无需添加 beta 标头；适用于支持该功能的模型——参见 `prompt-caching.md` § 会话中的系统消息）。缓存前缀将保持不变，且模型会将其视为操作者权限指令而非用户输入文本。对于不支持此功能的模型，则回退至用户轮次中使用 `<system-reminder>` 文本块。 |
| 会话中途切换模型会导致缓存失效。 | 为子任务启用一个使用更低成本模型的**子代理**，主循环则继续使用原模型。在托管代理中，可通过 `multiagent` 名单条目实现——参见 `managed-agents-multiagent.md`。 |
| 会话中途增删工具会导致缓存失效。 | 使用**工具搜索**进行动态发现——它会追加工具 Schema 而非直接替换，因此现有前缀得以保留。 |

对于多轮对话的断点设置，请结合使用 `prompt-caching.md` § 自动断点与显式断点中的方案：在静态系统前缀上设置一个显式断点，并对对话尾部（在支持自动缓存的情况下）启用顶层自动缓存。
