# 成本优化——降低每项已完成任务的支出

> **如果您通过 `/claude-api cost-optimize` 进入：** 这就是您需要的文件。请按顺序执行以下步骤，不要将指南摘要后返回给用户——呈现成本概况、排序后的方案以及分析结果本身就是执行的一部分。从步骤0（明确范围、质量标准和基线）开始，到步骤4的两项交付物结束：成本概况与变更建议。

API 支出优化以“每项已完成任务的成本”为单位，而非“每 token 的成本”。如果某个模型虽然单价较高，但能在更少的轮次内完成任务，它反而可能成为更经济的选择；而价格较低的模型若因失败导致重试，仍需为其消耗的 token 付费，并且失败还会带来下游的额外成本。因此，下文中的每一项决策都需综合考虑成本与质量。

优化手段可分为两类，且步骤顺序至关重要：

- **免费收益**——提示缓存、输入 token 的优化（含提示审计）、循环优化、输出 token 的优化、批量处理——在不降低输出质量的前提下减少支出。这些措施优先实施，其中缓存功能应始终开启。
- **权衡取舍**——预算、工作量、模型选择、多模型架构——用成本换取智能。这些措施放在最后，因为每一项都会改变模型的能力，过度追求成本优化可能会损害由免费收益所保障的质量。

**该流程的位置**：`prompt-audit` 子命令（`shared/prompt-audit.md`）仅针对提示表面（提示、技能、工具描述）进行审计；而本流程则涵盖整体成本优化——请求结构、缓存、循环设计、输出、批处理、工作量、模型等，并将提示审计作为输入优化（§2.2）的一个子环节纳入其中，不再重复其模式；一旦项目有了评估指标，各项优化措施便转化为逐步改进的过程——每次只调整一项，对照评估结果决定保留或回退（步骤3）。

下文中的量化预期参考 Anthropic 公开测试的结果，给出各效应的大致方向与幅度（来源见文末）；各模型的具体数据均在其官方页面上更新，随每次模型发布而变化，因此此处大多不再重复。这些数据仅为方向性参考，而非绝对保证——只有步骤3中的验证闭环才能确定对当前项目的实际效果；获取定价与成本优化页面是必经步骤，而非背景信息（步骤0：先获取数据再做估算）。对于量化数值，若所获取的页面内容与本文引用不一致，则以页面为准。关于历史修订的适用性，以“Preserved thinking”页面的规定为准（§2.1）；成本指南与操作手册中的客户端侧修剪方案未考虑这一因素。

## 步骤0：明确范围、质量标准与基线

**首先，从请求本身及其对应的代码库中，以及在缺乏相关信息时向用户确认，明确三件事。** 与提示审计不同，本流程的设计即为交互式：当某项优化措施所需上下文缺失，或某一步骤可能产生实际费用时，应与用户共同商讨，而非自行假设。本流程并不期望一次性完成审计。报告开头应同时列出这三项内容（初始状态下，基线值可暂定为“待步骤1确定”）。1. **范围。** 如果请求中指定了文件或目录，则以此为范围；否则，范围应涵盖项目调用 Claude API 的所有位置——包括请求构建器、代理循环和批处理作业。请注意区分不同的流量类别（例如，交互式路径与夜间作业即便使用同一密钥也属于不同负载）：针对每一类分别进行性能剖析、排序以及后续的各项验证；“每任务成本”这一指标在跨类别混合时并无意义。**同时明确代码所面向的平台**（Anthropic 官方 API、AWS 上的 Claude Platform、Bedrock、Vertex 或 Foundry）——各平台的功能支持情况各异，这也决定了可用的优化手段有哪些。
2. **质量基准。** 找到该项目用于评估、测试或验证其 LLM 调用结果的相关机制。若不存在此类机制，请在报告中予以明确说明：缺少评估机制，就无法区分节省的成本是否伴随着性能退化。尽管如此，仍可提出无需额外评估的“无风险收益”，但需将所有涉及权衡的优化项标记为“须先完成评估方可实施”，并询问用户能够提供何种结果验证方式。评估仅对其覆盖的流量类别有效；对于未被覆盖的路径上的优化项，同样按此标注。如果唯一的验证手段是用户的手动审查，则该验证会成为“无风险收益”的瓶颈——且绝不能作为任何权衡方案的放行依据。完整的“无评估”解决方案（含一套能解锁权衡优化的最低限度评估流程）将在第 3 步中给出。
3. **每任务基准成本。** 基准值应取获取成本最低的可靠数值，优先级如下：
   - **从历史数据中免费获取**：在具备 Admin API 访问权限的情况下，提取第 1 步中的用量与费用报表，并据此计算基准值——报表提供美元金额，但每任务的分母必须来自用户或应用自身的日志；或者按任务而非按请求汇总应用自身记录的 `usage` 对象，其中包含四项计费指标，各自适用不同费率：常规输入、缓存写入（5 分钟有效期时为输入的 1.25 倍，1 小时时为 2 倍）、缓存读取（占基础输入的一小部分，因模型而异）以及输出——乘数结构以定价页面公布为准；获取费率时务必参考定价页面，而非凭记忆。
   - **通过基准运行付费获取**：运行项目的评估程序（若无评估，则回放一组具有代表性的真实请求），并按上述方式汇总。此项操作会消耗真实的 API 费用，因此需事先告知预计成本——基于第 1 步的 token 估算及实时定价；首次回答时可暂定为“估算中，待第 1 步确认”——**并在执行前征得用户同意。** 若用户拒绝支出，则可根据代码及控制台可见的账单信息估算基准值，将其标注为“估算值”后继续推进。
   
   **先获取再量化——这是审计中所有费率及测量数据的前置条件。** 在任何美元金额、乘数或公开数据被写入报告或代码之前，务必通过 WebFetch 从 `shared/live-sources.md` 中提取两部分内容：**定价信息**（各模型的费率及乘数）和**成本优化指南**（当前的实测预期及初始模型推荐）。这两部分内容应在一次请求中一并获取。当涉及编辑对话历史、`system` 参数或 `tools`（参见 §2.2、§2.3，以及模型切换）的优化方案进入候选清单时，在提出具体变更建议之前，还应先获取“保留思考”页面（URL 见 §2.1），以确认哪些模型和账户适用于该项检查。在报告中记录每次获取的具体页面及其时间，以便读者核实操作已发生，并在引用相关数据时注明其来源页面。对于任何模型的费率或数据，仅凭记忆得出的结果均不视为有效来源。若获取失败，应在报告中予以说明。关于费率：在拥有 Admin API 访问权限的情况下，可通过将费用报表中的金额除以用量报表中对应 token 数量（相同模型、相同 token 类型）来推算实际有效费率；否则，应向用户询问当前费率。关于实测预期：应以相对区间而非具体数值来描述。只有在上述途径均不可行，且用户仍要求提供具体数字时，方可出现此类数值，并在所有出现处标注为“未经验证——凭记忆”。关于提示词和文件中的 token 计数，请参阅 `shared/token-counting.md`（`count_tokens` 函数在不进行推理的情况下返回 token 数）。将估算的基准与已知的月度账单进行核对：如果出现较大偏差，通常意味着多轮对话历史的增长被单轮估算所遗漏。

## 步骤 1：分析 token 的分布情况

token 分布可以通过测量或估算获得。在组织权限允许的情况下优先选择测量；否则退而求其次，通过阅读代码来估算。无论采用哪种方式，真正起作用的优化手段都由工作负载的特性决定，而非单纯依赖现有功能清单。

### 测量方法——使用用量与费用管理 API（推荐）

如果用户拥有 **管理 API 密钥**（`sk-ant-admin01-...`，这是一种不同于标准 API 密钥的密钥类型，个人账户不可用；其创建及权限范围详见管理 API 文档，可通过 `shared/live-sources.md` 中的“用量与费用管理 API”链接访问），则应直接获取真实数据，而非进行估算。这些操作属于报告读取，不会调用模型，因此不会消耗任何 token。完整的参数说明及响应格式请参考 `shared/live-sources.md` 中的“用量与费用管理 API”链接。

- **Token 分布**：使用 `GET /v1/organizations/usage_report/messages` 接口，设置 `group_by[]=model` 和 `bucket_width=1d`（默认分页为 7 天的数据，可通过增加 `limit` 参数扩展至最多 31 天；`group_by` 维度还包括 `api_key_id`、`workspace_id`、`service_tier` 和 `context_window` 等）。每个结果会精确拆分为以下各项，这些正是后续优化手段所针对的对象：`uncached_input_tokens`（未缓存输入 token）、`cache_read_input_tokens`（缓存读取输入 token）、`cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`（临时缓存 5 分钟/1 小时的输入 token）以及 `output_tokens`（输出 token）。
- **美元支出分布**：使用 `GET /v1/organizations/cost_report` 接口（按日粒度，以美分为单位的十进制字符串表示金额），并设置 `group_by[]=description`。按描述分组的结果包含结构化的 `model`、`cost_type`、`token_type` 和 `service_tier` 字段；其中 `token_type` 可直接将缓存部分的支出以美元形式呈现。代码执行的费用归类于“Code Execution Usage”描述项下；优先级服务层的费用不包含在此接口中，需通过用量接口的 `service_tier` 维度单独追踪。
- 数据会在请求完成后约 5 分钟内显示；持续使用时，查询频率不应超过每分钟一次。
- 平台特例说明：Claude Enterprise（claude.ai）组织需改用 Analytics API，且目前 AWS 上的 Claude Platform 尚未开放相关接口。在这种情况下，请用户从控制台的用量与费用页面手动抄录总览数据并转告我们。用量与费用页面不会列出 Amazon Bedrock、Google Cloud 或 Microsoft Foundry 的流量；若代码调用了这些服务，则不能假定报告已覆盖这些部分，应确认是否存在用于这些流量的控制台组织及管理密钥；否则只能根据应用记录的 `usage` 对象或各平台自身的计费视图来进行分析。

通过测量得到的分布信息能够直接回答以下问题：实际缓存命中率（`cache_read_input_tokens` 占比未缓存输入 token）、已有多少流量处于批处理层级、输入与输出的平衡状况，以及支出在不同模型、密钥和工作空间之间的分布情况。**务必核对测量结果与代码审计所得是否合理吻合**（使用的模型一致，数量级也在可接受范围内）：报告涵盖整个组织，而跨项目共享的密钥会导致各项目的流量混杂在一起，使得后续的项目级读数（包括步骤 3 的切换后确认）无法准确归因。若发现不一致，应结合代码估算进行校正，并在条件允许的情况下，通过 `api_key_ids[]` 或 `workspace_ids[]` 对用量报告的查询范围加以限定（成本报告不支持此类过滤，仅能通过 `group_by` 按工作空间细分）。对于无法实现项目级隔离的情况，建议将使用独立的项目级密钥或工作空间作为测量的前提条件。优化工作的重点应以经审计的范围及其支出为准，而非组织层面的汇总数据。

### 从代码估算分布情况

在没有管理员 API 访问权限的情况下（即没有管理员密钥、不属于 Claude Enterprise 组织、未使用 AWS 上的 Claude Platform——其功能可用性已在 `shared/claude-platform-on-aws.md` 中说明——或其他云平台），这些报告均无法涵盖；即便拥有相关权限，对于那些仅涉及结构层面而无法通过用量报告体现的事实，也请直接查看请求构建代码：

> **各模型的默认设置、参数支持以及各平台的功能可用性会随版本迭代而变化。** 对于“省略 `thinking`/`effort` 参数时会发生什么”“该模型是否接受 `effort` 参数”“支持哪些取值级别”或“该功能在 Bedrock/Vertex/Foundry 上是否可用”等问题，请查阅 SKILL.md 中的“思考与努力”部分、`shared/models.md` 或 `shared/platform-availability.md`（亦可参考实时 Models API）——切勿自行假设，也切勿将答案硬编码于此指南中。

- **前缀**：系统提示和工具 Schema 的规模有多大？其中是否有动态内容（如时间戳、请求 ID）被插入？
- **参考资料**：每次请求中是否内嵌了文档或手册？
- **工具**：工具 Schema 共占用多少 Token？每次请求是否都需要用到所有工具？
- **循环**：对话轮次有多深？各轮中是否会累积大量工具调用结果？
- **媒体**：图像、PDF 或大文件是否以完整尺寸进入上下文？
- **输出**：可见响应的长度是多少？`max_tokens` 设置为多少？
- **模型与努力程度**：使用的是哪个模型、哪个努力程度？是否曾针对某个评测进行过测试？请查阅当两者均未指定时该模型的行为（SKILL.md → “思考与努力”）——若未设置默认思考模式，则会产生隐性的输出 Token 费用；且由于不同模型的默认努力程度不同，未指定 `effort` 参数可能导致在更换模型后运行在更高或更低的努力等级上。此外，还需注意该模型是否比当前同档位的最新版本落后一两代——向上升级也是一种优化手段（§ 2.7）。
- **缓存**：是否已设置了 `cache_control` 断点？实际运行中，`cache_read_input_tokens` 和 `cache_creation_input_tokens` 分别显示怎样的数值？
- **延迟容忍度**：用户是否需要等待每一条响应，还是可以对部分任务进行批量处理？
- **价格调节因子**：是否有请求设置了 `speed`、`inference_geo` 等需按高于标准费率计费的参数（费率信息参见 `shared/live-sources.md` 中的定价链接）？如果相当一部分响应的终止原因为 `stop_reason: "refusal"`，则应将其单独列为一项费用——某些拒绝响应也会被计费（参见 `shared/model-migration.md` → 关于 `refusal` 终止原因）。仅凭 Token 数量本身无法反映这一点。

### 首先获取应用自身的使用日志

在基于估算进行排名之前，**请先询问用户，该应用是否已按每次请求记录 `response.usage`**——如果是，请用户提供某一天的代表性日志样本。这样一来，缓存命中率、输入/输出比例以及思考型 Token 的消耗就从猜测变成了零 API 成本的实测数据，并据此确定应采用下文排名表中的哪一档。如果响应中包含以下两个字段，则可进一步精确计算：`usage.output_tokens_details.thinking_tokens` 直接计量思考型 Token 的消耗；而对于执行了诸如压缩等服务端步骤的请求，该步骤所用的 Token 会列在 `usage.iterations` 中——此时应汇总迭代次数，而非仅读取顶层的计数。如果应用尚未记录使用情况，请说明添加这一功能本身就是一个“免费增益”的改动（步骤 3），然后继续基于代码估算推进。

**在缺乏使用数据时估算缓存命中率。** 如果应用记录了请求时间戳，可通过模拟 TTL 过期过程来估算：对时间戳排序，每当与前一次请求的时间差小于或等于 TTL 时即视为一次命中（读操作会刷新缓存项），并对平台提供的每个缓存 TTL 分别运行上述过程（参见 `shared/prompt-caching.md`）——不同 TTL 对应的耗时差异，即为较长 TTL 在用户实际流量中所能达到的上限。若仅知总请求数量，可按泊松分布近似估算：命中率 ~ `1 - e^(-lambda·TTL)`，其中 λ 为每秒请求数。无论采用哪种方法，都比单纯比较平均请求间隔与 TTL 更为准确，因为后者忽略了请求的突发性。

### 对各优化手段进行排名

在接触代码之前，先根据配置文件所适用的每个优化项估算其规模，以便确定最终候选列表并安排实施顺序。**如何标注规模取决于您掌握的数据类型**——估算值与实测值在报告中必须加以区分：

| 可用数据 | 每个天花板的标注方式 |
|---|---|
| 管理 API 使用量/费用报告 | **美元区间**，标注为“实测” |
| 应用端 `usage` 日志，或仅用户提供账单总额 | **占当前账单的百分比**，美元金额仅作为括号补充（如“约 $Y，基于您报告的 $X/月”）——百分比为用户自行计算的结果，美元金额则由用户核对得出 |
| 两者皆无（仅读取代码） | **相对等级**——“最大/中等/较小”，或数量级区间——不提供具体数值 |

**在估算规模之前，请剔除目标平台不支持的优化项**（参见 `shared/platform-availability.md` 作为唯一权威来源——切勿假设 1P 平台的支持情况可直接迁移到 Bedrock、Vertex、Foundry 或 AWS 上的 Claude Platform）。如果某项优化无法在用户平台上落地，则无需纳入排序；将其列入“已跳过”类别，并注明不可用的原因。

在适用的单位范围内，根据步骤 2 中描述的实测（或估算）支出构成及量化结果来评估每个优化项的规模——对于各模型相关的数值，使用步骤 0 获取的文案（若获取失败，则按相对等级标注上限）——举例说明：

- **缓存天花板**：指那些在不同请求间共享且字节稳定的输入部分所产生的费用——即潜在的前缀部分——以所用模型的缓存读取费率重新计费；这部分费用占基础输入的比例因模型而异（参见 `shared/live-sources.md` 中的定价链接；`shared/prompt-caching.md` § API 参考提供了盈亏平衡计算）。在此将实测的 `uncached_input_tokens` 与代码分析结果相结合：对于主要由动态负载构成（或已充分缓存）的工作负载，每次请求的独有部分都无法被缓存，因此该天花板的实际规模往往很小。最终结果应与公开的代理循环范围进行合理性校验（高命中率下可实现数倍缩减——当前数据参见 `shared/live-sources.md` 中的费用优化页面）。
  
- **批处理天花板**：指标准层级流量中，那些无需即时响应的部分所对应的费用的 50%。按模型分组的配置文件无法直接体现这一划分——需先进行细分：按 `service_tier` 分组，识别出已自动批处理的部分；再使用更细的 `bucket_width` 查找定时峰值；最后向用户确认哪些流量可以延后处理。

- **输入净化天花板**：指用于参考材料、工具 Schema 或过大的媒体内容的输入费用占比，这些内容可通过步骤 2.2 中提到的优化手段移除或延迟处理。

- **投入/模型天花板**：将公开的权衡曲线（见费用优化页面）应用于支出最为集中的部分——以区间形式呈现，因为质量成本需待评估运行后方可确定。

对于占用相同 token 的优化项（例如内联文档的缓存与删除），其天花板应互斥：应无条件计算每个天花板，排序后再根据其与上方优化项的重叠部分予以调减，确保最终候选列表的总规模不超过账单总额。

在呈现排序后的候选列表时，需附上每项数值背后的配置证据——标注为按节省天花板排序，而非按应用顺序（步骤 2 中的 § 2.x 编号决定执行顺序），并明确列出清单的截止点：若某项优化的天花板仅为账单的一小部分，或验证所需的试运行及投入无法带来足够回报，则不应进入评估周期；且大多数优化项在特定工作负载上也未必适用（本文件末尾的“工作负载形态 → 优化项”表格可用于匹配配置与优化项）。对于小额账单，诚实的候选列表可能为空：“此处无值得调整之处”是有效的结论，而非失败——请如实报告。预期节省仅为规划数值，而非实际结果——步骤 3 的实测数据才是最终成果。

## 步骤 2：按序实施优化项当请求需要进行编辑时，免费奖励可直接应用（仅调用子命令而不提出修改请求的情况除外）。自 2.6 版本起，权衡选项始终会显示其对应的度量质量成本，并且仅在用户明确接受后才会应用——绝不会在未告知的情况下以牺牲准确性为代价来降低开销。此外，每次运行模型时——无论是基线测试还是各权衡选项的验证通过——都会实际消耗 API 资源；因此，在每次运行前都需获得明确许可，并告知预期成本；或者在步骤 3 中预先设定一个涵盖所有运行的预算额度。

以下所列的价格乘数（缓存写入费率、批量折扣）为撰写本文时的最新价格，请在计算任何上限之前对照 `shared/live-sources.md` 中的定价链接予以确认。缓存读取费率因模型而异，此处未予列出。

### 2.1 提示词缓存——首次启用后持续生效

在代理型任务的每一轮中，系统都会重新发送整个不断增长的对话内容——包括系统提示、工具定义以及此前的所有轮次——因此，一个包含 40 轮的任务会在第 1 轮就重复发送 40 次，任务成本大致随轮次数的平方增长。缓存并不会阻止这种重复发送；它只是将已缓存的内容按模型的缓存读取费率重新计费，而该费率仅为基础输入费用的一小部分。

关于设计与部署——例如前缀匹配不变性、按稳定性对输入进行分类、断点模式以及反模式表——请务必阅读并遵循 `shared/prompt-caching.md` 中的工作流程，切勿自行添加 `cache_control` 标记。以下几点尤其关乎成本控制：- **可衡量的期望**：这是 Anthropic 在所有模型和基准测试中观察到的最大优化杠杆——在高命中率情况下，它将代理循环的成本降低了数倍。
- **当多个独立对话共享一个静态前缀时的显式断点**（或前缀层以不同速率变化）。自动缓存仅在单个对话内实现成本摊销；在手册中的示例中，在静态系统前缀上设置一个显式断点，大约使队列中一系列独立任务的每任务成本降低一半。针对代理循环的稳健配置——在静态前缀上设置一个显式断点，并在尾部使用顶层自动缓存——以及仅靠自动缓存反而会增加额外开销的情形，详见 `shared/prompt-caching.md` 的“自动与显式断点”一节。
- **当循环在各轮之间等待人类输入时，使用 1 小时的缓存有效期**。此时写入量为 2 倍而非 1.25 倍，因此只有通过减少未命中来体现收益；若间隔超过 1 小时，则成本会高于默认值。应根据请求间起始间隔的分布情况（生成时间计入 TTL）而非其平均值来决定，参见 `shared/prompt-caching.md` 中的“TTL 的选择”一表；该节还介绍了可通过 `max_tokens: 0` 的保活机制来应对远短于 1 小时的停顿，尤其在模型缓存读取成本较低的情况下效果更佳。
- **排查任务中途导致缓存失效的因素**：断点之上的动态内容；在两次请求之间更改 `thinking` 或顶层 `effort`（始终会使消息缓存失效，某些模型还会使工具与系统缓存失效——详见 `shared/prompt-caching.md` 的“失效层级”一节）；设置或变更结构化输出格式；切换 `speed`；任务中途调整预算；每次上下文编辑操作；API 抛弃的思考块（自此之后消息缓存即发生变化）；对话中途更换模型（缓存按模型区分）。
- **不属于失效因素，以及应在何处进行此类变更**：将 `effort` 显式设为模型默认值等同于省略该项；按消息级别的 `effort` 变更（测试版）仅在模型与代码所传的 `thinking` 设置均接受时保留缓存，否则返回 400 错误（详见 `shared/live-sources.md` 中“Effort Parameter”URL 的按消息部分）；此外，对 `system` 或 `tools` 的多数编辑都有追加形式，可保留前缀：用对话内的 `role: "system"` 消息替代直接编辑 `system`；用 `tool_addition`/`tool_removal` 块替代直接编辑 `tools`；为不应持久化的文本设置回合范围内的提醒（`clear_at`）。`shared/prompt-caching.md` 的“失效层级”一表列出了各项及其在各模型上的适用性。若确实需要变更模型或顶层 `effort`，则应将其安排在缓存本就即将失效的时机：紧接压缩操作后的首次请求（而非触发压缩的那次），或在两轮对话之间。
- **对于执行“保留思考”检查的模型，对 `system`、`tools` 或早期消息的任何编辑不仅会破坏缓存，也会破坏模型先前的推理过程**。每个思考块都与其生成的对话绑定，使其失效的编辑同样会重启缓存，因此只需遵循同一原则：会话期间保持 `system` 和 `tools` 不变，并将 `messages` 视为只增不减。`cache_control` 标记、`effort`、`max_tokens` 和 `tool_choice` 不受该检查影响。若部署时有差异将内容从 `system` 或 `tools` 中移出，则需确保该差异仅向新对话发送新内容，而继续向正在进行的对话提供原有存储的 `system` 和 `tools` 字节。若运行环境无法做到这一点，例如报告称正在进行的对话会产生一次冷未命中，且在强制执行检查时会被拒绝直至其思考块被丢弃（下一条）。
- **无效编辑的代价**：默认情况下，若强制执行检查，相关请求将被拒绝。也可选择丢弃失败的思考块（“保留思考”页面设有相应字段，同时响应中会列出被丢弃的块），这样这些块不会被计费，但会话总成本仍可能上升，因为模型可能会重新计算以重建它们。哪些模型和账户会接受检查随版本更新而变化——请以该页面（`https://platform.claude.com/docs/en/build-with-claude/preserved-thinking.md`）为准，而非本指南；并借助 `preserved-thinking-migration` 子命令（`shared/preserved-thinking-migration.md`）查找并修正运行环境中的相关变更。
- **短前缀**：可缓存的最小前缀长度因模型而异，因此每次更换模型后，都应重新确认简短提示是否仍可缓存，或是否新增了可缓存的可能性——详见 `shared/prompt-caching.md` 的“API 参考”一表。
- **以实际用量而非代码审查来验证——并在每次提示组装变更后重新验证**：在已预热的循环中，`cache_read_input_tokens` 应显著高于常规的 `input_tokens`，而 `cache_creation_input_tokens` 应约为一轮的用量，而非整个对话的用量（“成本优化”页面给出了健康循环从缓存读取多少输入的当前标准）。若不符合预期，请参照 `shared/prompt-caching.md` 的“验证缓存命中”一节，寻找具有健康循环特征的缓存失效因素——除非工作负载的输入几乎完全是每请求独有的有效载荷（这种情形无法缓存），或未命中是并发批处理的产物（§2.5）；这两种情况都不属于失效因素，也无需修复。要定位失效源头，优先使用平台提供的缓存诊断功能（可用性参见 `shared/platform-availability.md`）：在每次请求中包含一个 `diagnostics` 对象（首次请求设为 `previous_message_id: null`，后续请求设为前次响应的 `id`），响应中的 `diagnostics` 对象会指出两次请求的分歧之处——无需记录有效载荷。`shared/prompt-caching.md` 的“验证缓存命中”一节还建议在每次请求中添加一个测试版头部；“缓存诊断”页面（`https://platform.claude.com/docs/en/build-with-claude/cache-diagnostics.md`）说明该头部已不再必需，携带该头部的请求仍可正常工作，而 `diagnostics` 对象才是可选项，因此已包含该头部的运行环境可继续保留，且无论何种情况每次请求都必须包含该对象。该页面提供了当前的具体要求。在其他平台上，则退而求其次，采用同一节中的有效载荷差异法。
- **无历史用量可供参考时的缓存探测**：编写一个项目专有的脚本，向目标系统发送两次完全相同的请求，打印两次请求的所有四项用量指标（`input_tokens`、`cache_creation_input_tokens`、`cache_read_input_tokens`、`output_tokens`），若第二次请求的 `cache_read_input_tokens` 为零，则退出码非零。将该脚本与缓存相关变更一同交付，以便用户自行对比变更前后的结果。该脚本会消耗真实令牌，并可能调用项目的工具——仅在获得正式批准的前提下运行，并在请求涉及状态变更的工具时指向隔离的测试环境。

### 2.2 输入令牌——渐进式披露

只向模型传递任务所需的内容，其余部分由模型按需获取。每个子层级都设有“跳过条件”；本节末尾的注意事项适用于所有这些情况。

- **在每个提示中都包含大型参考文档** → 将其置于工具或技能之后，让模型按需检索相关段落。如果大多数调用实际上都会查阅文档的大部分内容，则可跳过——因为缓存前缀中的文档成本很低；或者当评估显示，某些依赖于规则的场景会因模型需要额外查找而出现遗漏时，也应如此。
- **系统提示中的工具概要** → 删除它们。工具 Schema 已经会直接嵌入请求中；再用文字重复只会增加前缀长度。
- **大量或体积较大的工具 Schema** → 对不常用工具启用 `defer_loading` 的工具搜索功能，仅在需要时加载定义。当 Schema 超过约 1 万令牌时，这种做法才划算（MCP 服务器很快就会达到这一阈值）；低于此值，搜索步骤反而会带来额外开销。计量陷阱：令牌计数端点会拒绝服务器端工具——应通过一个 `max_tokens: 1` 的请求来读取计费输入量（这是一次付费的小型模型调用，但已纳入常规审批流程）。
- **全分辨率的图片和 PDF** → 预先缩小到任务所需的尺寸。视觉输入按像素面积进行分块编码，每 28×28 像素的块约占用 1 个令牌，因此成本与分辨率成正比，而非信息量；1280×720 是一个安全的默认值，可将一张图片的令牌数控制在约 1,200 以内（当前公式，请参阅 `shared/live-sources.md` 中的视觉文档以确认）。
- **内联的大表格及其他结构化数据** → 使用文件 API 结合代码执行：挂载文件，让模型在沙盒中计算，最终仅将结果纳入上下文。若无任何可提取或计算的内容，则可跳过——因为沙盒的往返交互只会增加令牌数（且沙盒容器超出免费额度后按小时计费）。
- **抓取的网页** → 在网页抓取工具中使用动态过滤，将无关的模板内容排除在上下文之外。
- **链式工具调用且中间结果无关紧要** → 通过程序化方式调用工具，仅将过滤后的结果纳入上下文；相关文档显示，在代理式搜索基准测试中，这种方法可减少约 24% 的输入令牌数，同时提升得分。
- **宽泛的数据转储类工具** → 优先使用窄范围的访问器（如 `get_policy(claim_id)` 而非 `get_all_policies()`），并为列表类工具提供 `limit`、`fields` 和 `date_range` 参数。
- **用户提供的无限制输入** → 将令牌计数端点作为入口闸门（参见 `shared/token-counting.md`）：先计数，再截断、摘要，或将超大负载路由至文件 API。
- **提示文本本身** → 在此步骤中运行 `prompt-audit` 子命令（参见 `shared/prompt-audit.md`）；其模式表是历史提示文本的参考依据（本指南不再重复列出），其报告及建议的差异变更也将纳入此工作流的交付成果。若提示表面较小且近期已审计，则可跳过。为旧版模型编写的提示会让新版模型负担过重：在 Anthropic 的客服支持评估中，未经审计的迁移提示在新版模型上每工单的成本明显更高，但准确率并未提升；而经过审计的版本则更便宜，并且在一次迁移中还更为准确（当前数据请参见 `shared/live-sources.md` 中的“成本优化”链接）。

**本节的注意事项**：缩短前缀并不必然意味着任务成本降低。延迟引入上下文可能导致模型在后续步骤中花费更多轮次去检索原本内联读取的内容。务必通过评估加以验证——在本手册的工作负载下，将手动操作封装为工具，其成本与显式断点配置相当，且准确率有所提升。这些更改涉及 `system` 或 `tools` 配置，因此仅在运行时环境允许的情况下应用于新对话；对于已在进行的对话，则应在报告中说明部署这些变更后其实际成本：包括缓存重新启动，以及在那些执行“保留思考”检查的模型上，其历史记录中可能出现无效的思考区块（参见 § 2.1）。预先声明并启用 `defer_loading` 的工具是唯一能保持有效性的形式。

### 2.3 代理循环的卫生管理——防止长循环效应叠加

仅在性能剖析显示存在累积大量结果的深层循环时才相关；短循环不会触发此类问题，而额外的机制只会带来纯粹的开销。

- **上下文清理**（清除旧工具调用或思维记录）**是用于管理上下文窗口的工具，而非节省成本的手段。** 每次清理都会重写缓存的对话内容，这与提示词缓存的作用相悖——在平台文档所测的运行中，上下文清理的成本高于其带来的收益。应将其用于为窗口腾出空间；将触发阈值设得足够高，以减少清理频率，并尽量以少量大批次的方式进行清理，而非每轮都清理一次（`clear_at_least` 参数设定了每次清理至少需要移除的内容量，因此只有当清理能移除足够多的内容、足以抵消缓存写入的开销时才会执行）。对于那些会执行“保留思维”检查的模型，这也是安全的清理方式：该检查比较的是发送时的对话内容，因此服务器端的清理与压缩并不被视为编辑操作，而客户端执行的类似裁剪则会被视为编辑。
  
- **压缩**（即服务器端的总结并续写编辑）仅在会话长度达到需要压缩的程度时才有效；在平台文档所测的长时间运行中，它大约将费用降低了三分之一，而在短时间运行中则未见节省。如果平台提供按需压缩功能，文档建议优先使用该功能，而非基于令牌数阈值的压缩形式（状态与平台信息参见 `shared/live-sources.md` 中的“压缩”URL）。自定义的 `instructions` 字符串会替换默认的总结提示，而不是在其基础上叠加，因此应编写该字符串以保留默认情况下会保留的任务关键状态；且总结调用与其他请求一样计费（显示在 `usage.iterations` 下）。

- **在支持“保留思维”检查的模型上，于自然边界处进行客户端修剪**：当一个工作阶段完成后，将庞大的工具结果折叠为单行摘要，这一操作会改写之前的对话回合。在这些模型上（“保留思维”页面列出了具体型号——参见 § 2.1 中的 URL），这会导致后续所有思维块失效，且《保留思维迁移指南》（`shared/preserved-thinking-migration.md` § 严重程度分级）指出目前尚无可行的规避方案。在这种情况下，应在首次携带这些结果的请求之前就对工具结果和图片进行尺寸调整，并通过上述服务器端编辑来清理后续内容；而在客户端，唯一仍有效的做法是执行一次不回溯任何先前内容的压缩（即一条总结消息），或者在修剪后由客户端丢弃所有后续的思维块，但代价是损失相应的推理过程。在其他场景下，修剪的处理方式与以往相同：确保两次修剪之间的消息数组字节完全一致，这样每次修剪只是一次冷缓存缺失，而非每轮都产生新的缺失。

- **为自洽的繁重步骤使用子代理**：嵌套循环可以自行吸收沉重的工具结果，并返回一行摘要，且可选择在更低成本的模型上执行。如果决策模型需要中间上下文才能做出准确判断，则应避免使用子代理；同时请注意，子代理会开启一个新的前缀，与父代理之间不共享缓存。

### 2.4 输出令牌数- **`max_tokens` 是一个兜底设置，而非调优参数。** 模型本身并不会感知该值；一旦达到此上限，响应会在未完成时被截断，且 `stop_reason` 会显示为 `"max_tokens"`。在 Anthropic 的编码任务中，过低的上限导致大量尝试被提前终止，其中能成功解决的任务寥寥无几——受限的运行每次尝试的开销更低，但相应地成功解题数也更少，因此每道题的平均成本并未降低。对于代理类工作，建议将其设为 64,000（这也是在 `xhigh` 或 `max` 等级下公开的初始设置；上限不应超过模型的最大输出长度，详见 `shared/models.md` 中的说明——单次因上限而中断的尝试代价高昂），并流式接收如此规模的响应；遇到 `stop_reason: max_tokens` 时应视作一次失败，而非在同一上限下重试。设置前，请先查阅“Effort”页面中对应目标模型的部分（详见 `shared/live-sources.md` 中的“Effort Parameter”链接）：若该处有推荐的 `max_tokens` 值，则应以之为准，而非沿用 64,000。
  
- **若需缩短可见响应的长度**，请在提示词中明确指定期望的输出格式，最好附上示例。若希望压缩推理过程的长度，应调整的是“努力”参数（§2.6），而非 `max_tokens`，更不能随意关闭或限制思考功能：部分现有模型会对禁用或过度压缩“思考”的配置返回 400 错误，因此在对“思考”进行任何调整之前，请先阅读 SKILL.md 中关于目标模型的“思考与努力”章节。在“思考”始终开启的情况下，“努力”是控制思考消耗的主要手段；原本无需思考的工作负载，在启用思考后可能会产生更多的输出 token 费用。

- **利用停止序列实现内容感知的提前退出**：注册一个模型在无法继续时会发出的特殊标记（例如 `<CANNOT_REVIEW>`），使其在无法推进时直接停止，而非继续消耗 token 来解释原因。

### 2.5 批量处理

请求中的所有 token 均可享受五折优惠，包括缓存的读写操作——折扣可叠加。这是继缓存之后，无人值守代理任务（如评估运行、补全任务、定时作业）可用的第二大免费优化手段。

- 结果将在 24 小时内异步送达；该时限仅为结果的有效期，并非服务等级协议（SLA）。面向用户的工作仍应保持同步。
- 批量请求是一次性执行的，不支持中途工具循环。有时可通过预先获取输入数据，将工具循环合并为一个可批量处理的请求；在食谱中的示例中，这样做使成本降至交互式配置的一半左右，但这属于架构层面的决策，而非参数调整——它会改变模型的推理方式（合并后的运行其通过率稳定性有所下降），且并发批次内的缓存命中仅作为尽力而为的服务。
- 批量处理功能暂不适用于托管代理会话（当前机制及可用性详见 `shared/live-sources.md` 中的“Batch Processing”链接）。

### 2.6 努力与预算——首批权衡
从本节开始，每个优化手段都会在能力与成本之间做出取舍。请在评估过程中逐项调整，每次只变更一项。- **在调整模型之前先进行力度扫描**（对于那些公开了“力度”参数的模型，请查阅 `shared/models.md` 或 `shared/live-sources.md` 中的“力度参数”部分）。仅使用代码在 `thinking` 设置下所发送的那些力度级别——某些设置会以 400 错误拒绝最高级别的请求（请参阅 SKILL.md 中该模型的“思考与力度”一栏，而不仅仅是其“力度级别”单元格）。力度会在不改变模型本身的情况下，同时影响思考深度和工具调用的递归深度。在独立的会话中测试每个力度级别——在一次会话中中途更改顶层力度会导致缓存失效，并使比较结果失真。为确保比较的公正性，请遵循以下扫描流程：
  - 各个单元除 `output_config.effort` 外均字节完全一致；全程使用同一模型。在一个稳定的顺序下，先完成某一设定下的所有样本请求，再开始下一设定，以便各设定之间的缓存读取具有可比性——如果不同设定下的缓存计量仍存在显著差异，应予以说明，并将读取结果更多地偏向输出侧的成本。
  - 包含一个用户熟悉的难点案例：在简单任务上曲线最为平缓，而在困难任务的尾部，更高的力度才能体现出其成本价值。
  - **副作用防护机制**：如果重放某个样本请求时会触发修改真实状态的工具，请将重放指向一个隔离环境，或事先对这些工具进行模拟/打桩；任何力度扫描都不应导致生产环境的变更。若无法做到这一点，则仅对可安全重放的请求进行扫描，并明确标注。
  - 根据曲线形态判断：平坦（较低力度已能胜任该工作负载）、陡峭（较高力度物有所值——此时其价值已成为可量化的数字，而非单纯的担忧），或混合型（列出哪些任务发生了转折——这些任务将成为后续“重试失败”策略的候选对象）。单次运行中，通过率相差一两处，或平均成本相差几分钱，都可能属于噪声范围；应对之策是在相关设定下重复试验，并如实披露其成本。
  - 曲线是针对特定工作负载且针对特定模型的。请将样本及结果校验保留在报告指定的位置，并在模型迁移、提示词发生重大变化或工作负载发生变动后重新进行扫描。不同模型的默认力度不同，且各力度背后的令牌分配也可能随模型变化，因此在迁移后，应从新模型的默认设置（见 SKILL.md 中的“思考与力度”）开始全新扫描，而不应直接沿用旧模型的某个力度级别。按工作负载形态的预期表现：
- 研究与知识型任务：曲线近乎平缓——在 Anthropic 的实验中，“低”设置以三分之一到一半的成本换取了略低的性能，“中”设置在显著降低成本的同时保持了与“高”相当的准确率，而“高”设置在“中”基础上并未带来可观的提升。较低的资源投入也意味着更快的执行速度。
- 长周期编码任务：存在明显的权衡——每降低一个等级，通过率都会下降几个百分点（公开实验中为个位数），但单任务成本大幅降低；而最高设置则需付出数倍成本却收益甚微。
- 重度任务并不必然需要高资源投入：在一项深度研究基准上，公开结果表明“低”、“中”、“高”三档的表现几乎持平，但单任务成本随资源增加而上升。只有通过全面的参数扫描才能确定，在该工作负载下进一步提升资源是否仍能带来准确率的提升。
- 各模型当前的优化曲线：详见 `shared/live-sources.md` 中的“成本优化”链接。

- **在更高资源下重跑失败任务**——当工作负载具备可用的失败信号（如测试、检查器或验证器）时。先以低资源运行所有任务，仅对失败的任务使用较高资源重新执行：在 Anthropic 的编码实验中，这种方式以略高于原成本一半的代价，维持甚至略微超越了全程使用高资源时的通过率，其中已计入失败的低成本尝试。应将其视为一种节约手段而非性能提升，并将检查器的成本以及因失败导致的双倍执行时间纳入预算。
- **告知模型时间的重要性，并向其展示已用时长**——当实际耗时至关重要时：公开实验显示，这样做可使任务更早完成且单位成本更低，代价是准确率略有下降。在最新一轮对话后追加一条新的时钟消息（作为模型可接受的会话中系统消息），切勿通过改写 `system` 角色来实现——具体做法及数据参见 `shared/live-sources.md` 中的“成本优化”链接。像对待其他权衡一样对其进行验证。
- **任务预算**（模型可见预算并据此调整节奏——这是用于节省成本的预算控制机制）：初始预算设为循环中第90百分位的令牌用量，随后逐步收紧。预算仅为参考性指导，旨在引导模型行为而非强制停止，因此需在实际工作负载上验证其执行情况。编码任务实测显示：随着预算收紧，通过率小幅下降，而单位成本降幅远大于通过率降幅——预算带来了效率提升，但代价是通过率随之降低，且预算越紧缩，这一代价越大。低于文档规定的最低预算会被拒绝；过紧的预算可能导致类似拒绝响应的行为；预算应在首次请求时设定，中途更改将使缓存失效。接入前请确认模型是否支持（目前处于 Beta 阶段，且并非所有现役模型均支持）——相关参数配置、流式传输要求及支持的模型列表详见本技能的 SKILL.md → “任务预算（快速参考）”以及 `shared/model-migration.md` → “任务预算”。
- **不直接节省单任务成本但能限制损失的兜底措施**：托管代理会话预算是一道硬性的金额上限；工作空间支出限额则是针对整个工作空间的最后一道防线。

### 2.7 模型选择——最后，且刻意为之
模型的选择决定了智能水平的上限，因此应在所有非模型相关的优化手段之后再做决定。（例外情况是项目有评估指标且正在执行成本优化迭代时：此时可参照 `shared/evals/cost-hillclimb.md` 提前尝试不同模型与资源组合，因为评估指标能够识别出在较低资源下更强的模型反而更经济的情形。若无评估指标，则此类情形难以察觉，更换模型仍是风险最高的变更，应留到最后。）- **在降级前先评估是否值得升级。** 如果工作负载当前使用的模型比其所在层级的最新模型落后一两代，最经济的调整手段可能是更换模型：在已发布的实验中，往往通过切换到同一层级中参数量更小、推理成本更低的新模型就能实现降本。不过这一趋势并非绝对——在某项研究基准上，同样的升级反而导致每任务成本上升——因此在假设能节省成本之前，务必针对当前工作负载进行实测。这仍然是一次迁移操作：需运行 `migrate` 子命令以处理可能存在的不兼容变更，重新执行提示审计（§ 2.2），并从新模型的默认设置出发重新调整推理力度。
  
- **基于自有流量，按每个完成任务的成本对候选方案进行定价**，包括将大模型的推理力度调低的情况——仅凭按令牌计费的价格表无法准确预测排序结果。在 Anthropic 的实验中，不同工作负载下的排序存在显著差异：在某项基准测试上，前沿模型以较低的推理力度在“每个解决任务”的成本上优于较小的模型；而在一个编码子集上，前沿模型与低一级别的模型均接近饱和，此时后者以其默认设置的成本仅为前者的一小部分。至于应从哪个模型起步，并非本指南的职责范围：请参考 `shared/live-sources.md` 中的“成本优化”链接给出的当前推荐起点及各模型间的每任务对比，以及其中的“定价”链接获取最新费率。另一方面，最小的模型在回答知识类问题时，其每题成本仅为同层级但略高于它的模型的几分之一，但准确率也明显较低——它适用于输出可验证的大规模任务，而不适合长时间的代理式循环。

- **关注尾部而非中位数。** 在工作负载中最难的 10% 任务上比较各模型的表现：在普通任务上，各模型看起来相差无几，最便宜的那个似乎最优，但最终账单主要由那些被低价模型失败的任务决定——即使没有失败，大部分支出也集中在这些困难任务上（在一次包含 20 道题的研究实验中，仅两道题就占用了 43% 的总成本）。

- **逐步降级法**：首先在当前模型上调整推理力度；若 `low` 级别通过评测，则下移一个模型层级，**确认目标层级支持哪些参数与推理力度配置**（参见 SKILL.md -> “思考与力度”）——包括当前代码所传递的 `thinking` 配置，因为目标模型可能不接受该配置——随后将推理力度重置为目标层级的默认值（而非硬编码的某个固定值；不同模型的默认值及支持范围各异），并在此基础上继续向下微调（对于不支持 `effort` 参数的层级，仅在其唯一默认设置下进行评测）。每次只降低一个档位，并持续对照评测结果；当不存在更低成本的层级时，说明已无进一步优化空间，此时应如实说明，而非强行虚构新的步骤。当前模型阵容及发现路径参见 `shared/models.md`；关于模型切换的机制及针对不同目标的不兼容变更，请查阅 `migrate` 子命令的相关文档（`shared/model-migration.md`）。应在不同对话之间切换模型，而非在同一对话内中途切换：对话中途切换会冷启动缓存，且在新模型无法读取旧模型的思考状态块时，将失去相应的推理过程（参见 `shared/preserved-thinking-migration/causes.md` 第 5 节“对话中途切换模型”）。

- **两种特定架构组合能够胜过单一模型**——两者均为架构层面的调整；评估方式与单一模型相同，任何将单个对话拆分至多个模型间处理的设计都会继承上述模型切换带来的额外开销：
  - **顾问模式**（由一个成本更低的执行器负责整体流程，并在遇到难题时向前沿模型咨询）：只有当两者的性能差距足够大、且执行器确实会发起咨询时，这种模式才具备成本优势。咨询频率是关键变量——降低推理力度可能导致原本多数任务都需要咨询的组合几乎不再发起咨询，从而表现不如单独使用执行器；而要有效控制咨询触发条件，需要一个廉价的信号；若让执行器自行识别难题，则又要求其具备本不具备的判断能力。务必先行基准测试：在 Anthropic 的编码基准上，旗舰组合的总体成本大致与执行器自身的成本曲线持平——顾问模式所带来的提升约等于提高执行器的推理力度所能达到的效果——因此，在引入顾问模式之前，应先单独调整较强模型的推理力度并测算其成本。
  - **协调者模式**（由前沿模型规划并把大量任务委派给成本更低的执行器）：只有在存在大量可拆分任务时才有意义——理想情况下是许多彼此独立的小任务，且数量多到单个上下文窗口难以容纳。对于超出任何单个上下文窗口容量的工作，该模式的成本约为前沿模型单独运行的一半，但得分有所下降；在常规搜索类任务上，它起到了尾部风险保障的作用（平均成本约为一半，而在高成本尾部则更低），但在难度更高的完整任务集上反而表现不及。当任务为单条依赖链，或可纳入单个上下文时，协调者模式需要付出规划、任务交接与结果合并的代价，而这些步骤对于单模型来说都是免费的——在所有已测量的案例中，协调者所用模型在较低推理力度下的表现始终更优。

## 第3步：逐一应用、测量、保留或回滚——每次只操作一个开关- 按照排序后的备选清单逐项评估，确定哪些优化措施能带来差异——但**按照§2的顺序应用备选措施**（先做免费收益→再考虑投入/预算→最后调整模型），而非按节省金额的排序：排序决定是否纳入以及评估预算的分配；§2.x的编号决定执行顺序。每项入选的优化措施都作为**独立的差异**（一个差异对应一项优化），应用后进行度量：针对该优化措施所覆盖的流量类别重新运行评估，并将通过率与每任务成本与上一版保留配置（仅对首个优化措施为基线）综合对比。若某项优化既省钱又损失精度，则不属于可接受的改进——应将其回滚并记录原因。若某项优化涉及未被当前评估覆盖的路径，则无法通过现有评估验证：此类“免费收益”仅以成本衡量，并明确标注；而存在权衡的方案则仍作为未应用的提案保留（参见步骤0.2的标记规则）。
- **一次性申请测量预算，而非每次运行单独申请。** 提交包含总预计运行次数及成本的验证计划——一次全面的参数扫描通常涉及多个配置、每个配置多次试验——并获得预算批准；在已获批预算范围内，各次运行无需再次审批。在生产流量上进行影子运行时，其期间的生产支出大致翻倍：这本身就是一种审批方式。
- **切勿基于单次结果做出保留或回滚决策。** 在获批预算内重复试验，直至决策结果足以排除偶然性干扰。面向生产切换的标准是约50个案例、每个配置至少5次试验；对于单个优化措施的决策，若能充分重复试验，也可接受较小规模的评估。此外，缓存相关差异的验证需要预热缓存：按顺序运行样本，从第二次请求开始度量，否则写入开销占比过高，可能导致看似“免费收益”的效果实为性能退化。
- **当用户完全无法提供结果验证时**：免费收益类优化仅以成本衡量（或如无预算则列为提案）；存在权衡的方案仍作为未应用的提案，附带公开的预期指标，并提供少量真实答案的手动前后抽查——用户负责审核免费收益类优化，但不参与权衡类方案的评估。尤其对于参数扫描，即使仅以成本衡量的运行也值得提供：采用同一矩阵，但不设通过率列，仅按任务粒度并列展示各配置下的输出——这正是用户自行判断质量所需的信息。报告中须明确说明运行模式，切勿虚构评分机制填补空白。若应用本身不记录使用情况，则增加`response.usage`日志记录本身即为一项免费收益类优化，且在无Admin API密钥的情况下，后续所有数据采集均由此渠道完成。
- **最小化评估方案**——以最低成本验证权衡型优化措施，确保“需评估”成为下一步而非死胡同。可与用户共同构建：
  - **输入**：从生产日志中提取或由用户提供的固定集约20–30条真实请求——足以支持单个优化措施的保留/回滚决策（最终生产切换的标准为约50个案例）。这些请求应保持不变，所有配置均使用同一组输入。
  - **判定依据**：根据工作负载选择最经济的方式——用于对比的黄金答案、用户用于打分的简明评分标准，或自动化检查器（测试通过、JSON校验通过、必填字段齐全）。若无更低成本的方案，也可使用模型评分，但这也属于经批准的API调用支出。
  - **运行程序**：脚本依次运行冻结的输入，针对每个配置记录输出及`response.usage`，并统计通过率和每任务成本。每个配置对应一次调用，整个扫描过程为配置间的循环迭代。
  - **成本与审批**：估算总成本（输入数量×配置数×基准每任务成本），并在运行前征得用户同意——此为在既定审批框架下的实际API支出。
- 保留或回滚的决策应基于评估证据本地作出。在切换前，将最优配置在生产流量上进行影子运行；切换后继续运行评估，并在切换**之后**，结合用量与成本报告确认节省效果——且仅限于可归属的流量部分（步骤1中关于共享密钥的注意事项同样适用于确认环节）。
- 预计多数优化措施并不适用于特定工作负载。以手册中的示例为例，大多数未能入选——工具Schema过小无法用于工具搜索，循环过短无法编辑或压缩，无数值计算需求无法利用代码执行等；而成本方面表现最佳的几项优化虽有优势，却未能保证正确性。步骤1生成的负载画像旨在避免盲目优化。
- 将各配置的得分与每任务成本绘制成图，并提取帕累托前沿——这是生产切换决策的主要依据。

## 工作负载形态 → 调优手段

改编自手册中的要点总结表，用于将成本分析映射到调优手段（第1行的注意事项已扩展）：

| 成本所在 | 优先采用 | 避免或需谨慎的情况 |
|---|---|---|
| 每次调用都重复计费的同一系统提示和工具 | 提示缓存：优先使用自动缓存，当多个独立对话共享静态前缀或前缀层级变化频率不一致时，再设置显式断点；对于间隔超过5分钟的场景，可使用1小时TTL或保活机制（§2.1） | 动态内容应置于断点之上——将其移至用户输入部分。若缓存效果已佳，则无需额外优化：并发批量未命中（§2.5）不会导致缓存失效，且1小时TTL不会影响相隔数小时的调用 |
| 每个提示中都包含大型参考文档 | 将其置于工具或技能背后 | 每次调用都需要文档的大部分而非某一部分，或者评估显示模型需要主动查找规则才能处理的部分存在大量未命中 |
| 工具Schema数量多或体积大 | 使用`defer_loading`的工具搜索 | 当Schema总token数低于约1万时，搜索步骤会带来额外开销 |
| 上下文中包含图片、PDF或大文件 | 将图片按任务需求缩放，并对表格和PDF使用Files API结合代码执行 | 若无提取或计算需求，沙盒仅增加token消耗 |
| 用户提供的输入无限制 | 在摄入阶段进行token计数作为准入控制 | |
| 长循环中堆积大量结果 | 服务端进行上下文编辑或压缩；在客户端自然边界处进行裁剪，并针对运行“保留思考”检查的模型加以限制（§2.3） | 循环较短或被清除的内容仍有必要保留；注意每次编辑都会使该点之后的缓存失效——且在运行“保留思考”检查的模型上，客户端对早期轮次的编辑也会使后续推理失效 |
| 单个自洽步骤产生大量中间结果 | 使用子代理，可选更低成本的模型 | 决策模型需要这些中间上下文才能做出准确判断 |
| 可见响应过长 | 通过示例指定输出格式，并以`max_tokens`作为兜底，同时使用停止序列提前退出 | |
| 思考与工具调用占主导，且评估仍有优化空间 | 先降低`effort`；检查同档位是否有更新的模型（§2.7），再降一级并重新调整`effort` | 这始终是直接的能力权衡，因此应逐级下调，并结合评估结果 |
| 大多数为常规场景，少数为疑难案例 | 使用廉价驱动模型的顾问工具 | 缺乏有效的信号来筛选咨询请求，只能让驱动模型自行识别疑难案例 |
| 无人等待响应 | 使用Batch API，必要时预取输入以将工具循环扁平化为一次请求 | 若有用户正在等待，或扁平化会改变模型的推理方式 |

## 第4步：交付成果

1. **成本分析与调优方案**：包括第0步的假设（范围、质量目标、基线）、第1步的token分析，以及所选调优手段及其预期效果——同时注明哪些手段因故被刻意跳过及原因，以免后续重复讨论。将备选方案按节省上限排序，而非应用顺序，避免被误读为实施顺序。
2. **变更清单**：每项调优手段对应一份差异说明，明确其影响——在用户批准的情况下，记录实际应用后的效果（每任务的成本预期与实测值，以及通过率是否保持）；若未获批准，或某些权衡型手段尚需评估，则以建议形式列出预期节省及公开的质量成本。若所有方案均未达到最低门槛，则交付“暂无改进建议”——这本身即为成功结果，应明确说明，而非强行提出调优方案。

**报告框架**（章节顺序及必填字段——其余部分可灵活调整）：- **范围 / 质量基准 / 基线 / 平台 / 抓取的页面，附日期**（步骤0的假设）
- **Token画像**（步骤1）
- **排序后的候选清单**——表格列：`优化项 | 类型（无成本收益 / 权衡） | 节省上限 | 数据来源（实测 / 使用日志 / 代码估算）`。上限单位与数据支持的量级一致（步骤1→对优化项进行排序）。在表格下方标注：“按节省上限排序，而非应用顺序。”
- **拟议变更**——每个优化项对应一个差异对比，按§2的应用顺序编号（无成本收益→投入/预算→模型），每项均标注为*已应用并测量* / *拟议* / *需评估*。
- **跳过的优化项**及原因（包括因平台可用性而放弃的项）
- **下一步 / 需要的审批**——测量预算申请、评估前置条件，或“暂不建议变更”
