`/simplify → 4 个清理助手并行执行 → 应用修复`

你的任务是提升已修改代码的质量，而不是寻找 bug。请从可复用性、简化性、效率和抽象层次等角度进行审查，并对发现的问题进行修复。不要专门查找正确性方面的 bug——那正是 `/code-review` 的职责。

## 第0阶段 — 收集 diff

运行 `git diff @{upstream}...HEAD`（如果没有上游分支，则使用 `git diff main...HEAD` 或 `git diff HEAD~1`），获取待审查的统一格式 diff。如果有未提交的更改，或者范围内的 diff 为空，还需额外运行 `git diff HEAD`，并将工作区的改动也纳入审查范围——因为审查通常在提交之前进行。如果传入了 PR 号、分支名或文件路径，则以该目标为准。将此 diff 视为本次审查的范围。

## 第1阶段 — 审查（4 个清理助手并行执行）

通过 Agent 工具同时启动 **4 个独立的审查助手**，并在同一条消息中发出指令，使它们并发运行。为每个助手传入 diff 和以下四个审查角度之一。每个助手会返回其发现的结果，包括文件名、行号、一句话摘要，以及具体问题所在（例如重复、浪费或难以维护之处）。

### 可复用性

标记那些重新实现代码库中已有功能的新代码——搜索共享/工具模块以及变更附近的文件，并指出应调用的现有辅助函数。

### 简化性

标记 diff 中引入的不必要的复杂性：冗余或可推导的状态、略有差异的复制粘贴、过深的嵌套、遗留的无用代码。并给出能完成同样功能的更简洁形式。

### 效率

标记 diff 中造成的工作浪费：冗余计算或重复的 I/O 操作、本可并行却串行执行的独立操作、在启动或关键路径上添加的阻塞型工作。同时标记由闭包或捕获环境构建的长生命周期对象——它们会使整个封闭作用域在其生命周期内一直存活（当该作用域持有大对象时会造成内存泄漏）；建议改用仅拷贝所需字段的类或结构体。并给出更经济的替代方案。

### 抽象层次

检查每一处改动是否在合适的深度解决了根本原因，而不是用脆弱的“创可贴”来掩盖症状。在共享基础设施上叠加特殊处理通常是修复不够深入的信号——优先选择对底层机制进行更简单、更通用的改进，而非增加特例，并明确指出这一改进。

## 第2阶段 — 应用修复

等待所有四个助手完成审查，对指向同一行或同一机制的发现进行去重，并直接修复剩余的每一项。对于那些修复会导致预期行为改变、需要对审查范围之外的部分进行大幅改动，或被判断为误报的发现，可以跳过；但需记录下跳过的理由，无需争论。最后简要总结已修复的内容和被跳过的内容（或确认代码本身已很整洁）。
