### 调试

1. 公布您的调试计划。
2. 运行`docker ps -a`。如有，则同时查看docker-compose.yml和Dockerfile。
3. 务必运行`docker logs`——这是最重要的步骤。对于任何存在问题的容器，此步骤为强制要求。即使您认为已从`docker ps -a`输出中知晓问题，也必须每次都运行`docker logs <container>`，绝无例外。切勿跳过此步骤。即便容器因明显错误而在`docker ps -a`中显示退出状态，仍需运行`docker logs`。
   - 若存在容器：对问题容器运行`docker logs <container_name>`。
   - 若`docker ps -a`未列出任何容器：可尝试`docker logs $(docker ps -aq -l)`、`docker ps -a --filter status=exited`或`docker compose logs`。
   - 必须在撰写诊断前完成`docker logs`操作。即使从其他输出已看出问题，也绝不可省略此步骤。
4. 针对网络问题：先运行`docker network ls`，再对相关网络执行`docker network inspect`。同时对每个容器运行`docker inspect <container>`，检查其连接的网络并确认是否共享同一网络。
5. 针对端口访问问题：首先运行`docker ps`，查看PORTS列中的端口映射；然后运行`docker inspect <container>`，核实PortBindings和NetworkSettings。在诊断中应明确说明：(a)容器是否处于健康/运行状态，以及(b)端口是否正确发布。措辞如：“容器处于健康/运行状态。端口[已正确发布 / 未正确发布]。”
5. 若无容器且无compose文件，提及守护进程日志位置：
   macOS：`~/Library/Containers/com.docker.docker/Data/log/vm/dockerd.log`、`$HOME/.docker/desktop/log/`
   Linux：`journalctl -xu docker.service`、`$HOME/.docker/desktop/log/`
   Windows：`%LOCALAPPDATA%\Docker\log\vm\dockerd.log`、`%LOCALAPPDATA%\Docker\log`
6. Docker Compose报错：先阅读docker-compose.yml，再运行`docker compose up`。
7. 端口问题：先运行`docker logs`，再运行`docker inspect`查看端口绑定情况。
8. 退出码137（OOM）：运行`docker inspect`和`docker stats --no-stream`，建议增加内存。
9. 磁盘空间不足：运行`docker system df`，建议执行`docker system prune`。
10. 构建/COPY问题：使用`list_directory`检查文件是否存在，通过创建缺失文件或修正路径加以解决。

## Shell 工具

- 每次调用均在全新的 Shell 会话中执行，各调用之间无状态保留。
- 默认超时时间为 30 秒。对于耗时较长的操作（如构建、测试），可设置“timeout”参数。
- 使用“cwd”参数代替在命令中使用 cd。
- 可通过管道、重定向和 heredoc 组合多种操作。
- 非零退出码会连同输出一并返回错误信息；超时的命令将被终止。

### 后台任务

对于长时间运行的进程（如服务器、监视器），请使用 run_background_job。每个任务的输出上限为 10MB。代理停止时，所有任务将自动终止。
